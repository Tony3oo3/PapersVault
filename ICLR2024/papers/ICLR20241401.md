## Problem

Designing reward functions for reinforcement learning is a longstanding bottleneck: hand-crafted rewards demand domain expertise, inverse RL requires large amounts of expert trajectory data, and preference learning needs costly human annotations. Existing LLM-based approaches (e.g., L2R) generate unshaped or sparse reward code with fixed APIs, limiting task coverage and RL training effectiveness. TEXT2REWARD addresses this gap by producing interpretable, shaped dense reward code in a data-free manner that generalizes across diverse robotic tasks.

## Input / Output

The method takes a natural language goal instruction (e.g., 'push the chair to the marked position'), a compact Pythonic environment abstraction (a class hierarchy with typed attributes like `RigidObject.pose`, `PandaRobot.ee_pose`, and methods like `check_grasp`), and optionally retrieved few-shot instruction-code pairs from a skills library. It outputs a free-form Python `compute_dense_reward(self, action) -> float` function that can employ conditional staging, NumPy/SciPy operations over point clouds, and quaternion math. The generated code is then executed by an RL algorithm (PPO or SAC) to produce a trained policy; in the interactive setting, rollout videos and learning curves are fed back to a human who provides natural-language corrections to refine the reward.

## Method

TEXT2REWARD grounds LLM code generation in a Pythonic environment representation (classes, type annotations, docstrings) that is more token-efficient and familiar to LLMs than tabular listings. It augments the prompt with background knowledge (function signatures and usage examples for NumPy/SciPy) and retrieves the single most similar instruction-code pair via sentence-embedding search to provide few-shot structure. After generation, the code is executed in a code interpreter to catch syntax and runtime errors, with error messages fed back to the LLM for iterative repair (reducing error rates from ~10% to near zero). The key distinction from prior work is that the generated reward is shaped and staged (using nested if-else to encode sub-goals like approach → grasp → lift) rather than a constant function across timesteps, enabling it to leverage established packages and cover tasks with complex geometry (e.g., point-cloud-based chair surfaces). A human-in-the-loop refinement cycle—where users watch rollout videos and provide natural-language feedback on failure modes or preferences—allows the system to resolve ambiguity and improve success rates from 0 to ~100% in fewer than 3 iterations.

## Results

On 13 of 17 manipulation tasks across MANISKILL2 and METAWORLD, policies trained with TEXT2REWARD-generated reward code achieve comparable or better success rates and convergence speed than expert-written oracle rewards, and on 4 of 17 tasks (e.g., Open Cabinet Door, Handle Press, Pick Cube, Drawer Open) the generated rewards actually outperform the oracle. For six novel locomotion tasks in Gym MUJOCO, zero-shot generated rewards yield success rates of 94–100% (Hopper: Move Forward 100%, Front Flip 99%, Back Flip 100%; Ant: Move Forward 94%, Lie Down 98%, Wave Leg 95%). With human feedback, the Stack Cube task success rate improves from 0% to near 100% in fewer than 3 iterations, and the simulator-trained policy transfers successfully to a real Franka Panda robot.

## Baselines & Comparisons

The primary comparison is against oracle (expert-written) dense reward functions provided by the simulation environments. TEXT2REWARD matches or exceeds the oracle on 13 of 17 manipulation tasks in terms of final success rate and convergence speed, and strictly outperforms it on 4 tasks (faster convergence on Open Cabinet Door and Handle Press; higher success rate on Pick Cube and Drawer Open). The L2R baseline (adapted from Yu et al., 2023) is significantly weaker: it can only be effectively applied to 2 of 6 MANISKILL2 tasks and fails on tasks involving complex object surfaces represented as point clouds (e.g., the ergonomic chair in Push Chair), because L2R uses unshaped, constant-across-timesteps rewards with hand-designed APIs rather than free-form shaped dense code. Few-shot TEXT2REWARD (k=1) further improves over zero-shot on 2 of 6 tasks that are not fully solvable in zero-shot, demonstrating the benefit of retrieving similar instruction–code pairs from a skills library. For locomotion, no oracle reward exists (the six tasks are novel), so performance is evaluated by human judgment of rollout videos, with all six tasks exceeding 94% success.

## Relation to Prior Work

This paper departs from three main lines of prior work on reward design: (1) inverse RL and preference learning, which require substantial trajectory or preference data and produce opaque neural-network reward models; (2) L2R (Yu et al., 2023), which uses LLMs to generate unshaped, sparse reward code tied to hand-designed APIs for MPC; and (3) LLM-as-policy approaches (ReAct, Reflexion, etc.), which use the LLM directly as the decision-making agent. TEXT2REWARD carves new ground by repurposing LLM code generation to produce *shaped, dense, free-form* reward programs grounded in a compact Pythonic environment abstraction, then training a conventional RL policy (PPO/SAC) on that reward—combining the interpretability of symbolic rewards with the flexibility of RL training and the zero-data nature of LLM generation.

## Why It Matters / Open Questions

The practical impact is significant: it lowers the barrier to reward design from requiring RL expertise to requiring only natural-language goal descriptions, and the human-in-the-loop refinement loop lets non-expert users iteratively improve policies by watching rollouts and giving verbal feedback. Key limitations include dependence on GPT-4 (open-source models underperform), the need for a hand-crafted Pythonic environment abstraction per simulator, and the observation that interactive improvement is sensitive to initial code quality. Open questions include whether a sparse-to-dense generation paradigm can make iterative refinement more robust, whether the approach generalizes to environments without clean Pythonic APIs, and whether next-generation LLMs can close the remaining zero-shot-to-few-shot gap without retrieved examples.
