## Problem

Existing coding benchmarks such as HumanEval involve self-contained problems solvable in a few lines of code, failing to capture the complexity of real-world software engineering where resolving a bug requires navigating large repositories, coordinating changes across multiple files, and processing extremely long contexts. SWE-bench addresses this gap by constructing a benchmark from real GitHub issues and their corresponding pull request solutions, demanding repository-scale code editing that goes far beyond traditional code generation.
![Teaser figure](../imgs/ICLR20242115/cropped_page0_idx0.webp)

## Input / Output

The model receives a natural language issue description (averaging 195 words, up to 4,477) along with retrieved code files from a large codebase (averaging 3,010 files and 438K lines), selected via BM25 sparse retrieval or oracle retrieval under a token budget (13k, 27k, or 50k). The output is a unified diff patch file specifying line-level additions and removals across potentially multiple files. Evaluation is execution-based: the patch is applied to the codebase and scored by whether all fail-to-pass tests (verifying the issue is resolved) and pass-to-pass tests (verifying no regressions) succeed.

## Method

The benchmark is constructed through a 3-stage pipeline: scraping ~90,000 PRs from 12 popular Python repositories, filtering to merged PRs that resolve linked issues and contribute test file changes, and execution-based validation requiring at least one test to transition from fail to pass, yielding 2,294 task instances. For the open-model baseline, CodeLlama-Python 7b and 13b are fine-tuned via LoRA (r=16, α=16, dropout=0.05) on only the attention sublayer weights using 19,000 issue-PR pairs from 37 disjoint repositories, with sequences capped at 30,000 tokens and trained for up to 4 epochs using DeepSpeed Ulysses and Flash Attention for long-context efficiency. At inference, BM25 retrieval selects relevant files to fit within the model's context window, and the model generates a patch file that is automatically applied (with a repair step for malformed patches) and evaluated against the repository's test suite.

## Results

Across all evaluated models, SWE-bench proves extremely challenging: the best-performing model, Claude 2, resolves only 1.96% of issues under BM25 retrieval (43.07% patch apply rate). With oracle retrieval (providing the exact files edited by the reference PR), Claude 2 improves to 4.80% resolution. The fine-tuned SWE-Llama 13b achieves 0.70% under BM25 and 3.97% under oracle retrieval, making it competitive with Claude 2 in the oracle setting. GPT-4 (evaluated on a 25% subset due to budget constraints) resolves 0.00% under BM25 and 1.74% under oracle retrieval.

## Baselines & Comparisons

The paper evaluates five models: Claude 2, ChatGPT-3.5, GPT-4, and the authors' fine-tuned SWE-Llama 7b/13b. Claude 2 dominates on resolution rate in both retrieval settings (1.96% BM25, 4.80% oracle), outperforming SWE-Llama 13b (0.70% BM25, 3.97% oracle) and GPT-4 (0.00% BM25, 1.74% oracle). However, SWE-Llama 13b achieves the highest patch apply rate (53.62% BM25, 66.78% oracle), indicating better patch formatting. In the oracle setting, Claude 2 and SWE-Llama 13b resolve 110 and 91 instances respectively, but only 42% of SWE-Llama's solved instances overlap with Claude 2's, suggesting complementary strengths. GPT-4 underperforms notably, resolving 0% under BM25 and only 1.74% under oracle retrieval, though its evaluation was limited to a 25% subset. ChatGPT-3.5 is the weakest overall at 0.17% (BM25) and 0.52% (oracle).

## Relation to Prior Work

This paper extends the code generation benchmarking lineage (HumanEval, MultiPL-E, CodeXGLUE) from self-contained, function-level problems to repository-scale, multi-file editing grounded in real GitHub issues. It builds directly on CodeLlama as the base model for SWE-Llama, applying LoRA fine-tuning to adapt it for patch generation over long contexts. The paper also departs from prior ML-for-SE work on program repair and bug localization by operating at a much larger codebase scale (thousands of files, hundreds of thousands of lines) and using execution-based evaluation with fail-to-pass tests rather than exact-match or unit-test-only verification.

## Why It Matters / Open Questions

SWE-bench establishes a realistic, continually updatable benchmark that exposes a stark gap between current LM capabilities and practical software engineering, with even the best model (Claude 2) resolving under 2% of issues. Key open questions include whether agent-based or tool-augmented approaches can close this gap, how to handle multi-modal issues (images in bug reports), and whether the Python-only scope limits generalizability. The paper also highlights that execution-based testing, while robust, is insufficient to guarantee code quality, efficiency, or readability of model-generated patches, pointing to a broader evaluation challenge for the field.
