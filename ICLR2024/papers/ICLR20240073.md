## Problem

PyTorch lacks a native, comprehensive library for decision-making and control tasks, and the existing RL ecosystem is fragmented: high-level frameworks obscure internals and resist repurposing, while low-level toolkits produce complex, hard-to-maintain code. The dynamic requirements of decision-making algorithms create a fundamental trade-off between modularity and component integration that no existing library resolves satisfactorily for large development teams working across diverse domains.

## Input / Output

All data flows through TensorDict, a dictionary-like PyTorch primitive that stores tensors with explicit batch-size metadata, supporting both key-based indexing (e.g., td['observation']) and shape-based indexing (e.g., td[:10]) along multiple dimensions simultaneously. Environments accept and return TensorDict instances rather than fixed tuples, unifying heterogeneous simulator backends (Gym, IsaacGym, Brax, DMControl) under a single step/reset API. Loss modules consume TensorDict batches of transitions and return TensorDicts containing one or more named loss terms, while data collectors output TensorDict-formatted batches that can be directly fed into replay buffers or training loops without format conversion.

## Method

The core technical contribution is TensorDict, a new PyTorch primitive that acts as a universal, shape-aware data carrier enabling all library components to be developed independently while communicating seamlessly. TensorDict supports tensor-like shape operations (reshape, stack, split, permute, mask) alongside dictionary-like key operations (flatten, rename, delete), and carries batch-size and device metadata that separates the 'batch' dimension from the 'feature' dimension. Built on this foundation, TorchRL provides composable components: a generic environment API with TensorSpec-based validation, sync/async/distributed data collectors, fully composable replay buffers (independent storage, sampler, and transform slots), TensorDictModule/TensorDictSequential for programmable and runtime-configurable model architectures, and stateful objective classes with a uniform forward signature for on-policy, off-policy, offline, and model-based RL algorithms. The design natively supports vectorized simulation (leveraging GPU SIMD for batched environments), distributed training via torch.distributed, and torch.compile compatibility through a dedicated symbolic tracer, achieving throughput comparable to or exceeding specialized libraries like RLlib and Tianshou.

## Results

TorchRL reproduces results matching the original papers for A2C, PPO, DDPG, TD3, SAC, and IMPALA across MuJoCo and Atari 2600 environments (e.g., SAC achieves 11077±323 on HalfCheetah, TD3 achieves 10285±837). On vectorized data collection in the VMAS simulator, TorchRL scales to ~530K FPS at 20K vectorized environments, while RLlib plateaus at ~1.5K FPS. For GAE computation on 1000×1000 trajectories, TorchRL-vec achieves 1.33 ms on GPU, outperforming Tianshou (5.15 ms), RLlib (9.38 ms), and SB3 (14.1 ms), and matching CleanRL (1.43 ms, JAX/GPU). On data collection with 32 workers, TorchRL's async collector reaches 19,401 FPS on Breakout-v5 versus 1,212 (Tianshou) and 97 (RLlib).

## Baselines & Comparisons

Against RLlib, TorchRL demonstrates a decisive advantage in vectorized data collection: at 20K vectorized environments, TorchRL achieves ~539K FPS while RLlib plateaus at ~1.6K FPS (a >300× gap), because RLlib cannot exploit GPU SIMD parallelism in simulators like VMAS or IsaacGym. On GAE computation, TorchRL-vec (1.33 ms, PyTorch/GPU) outperforms RLlib (9.38 ms, scipy/CPU) by ~7×, and on data collection TorchRL's async collector (19,401 FPS on Breakout) exceeds RLlib (97 FPS) by over 200×. Against Tianshou, TorchRL-vec is ~4× faster on GAE (1.33 vs 5.15 ms) and the async collector is ~16× faster on Breakout data collection (19,401 vs 1,212 FPS). Against SB3, TorchRL-vec is ~10× faster on GAE (1.33 vs 14.1 ms). Against CleanRL (JAX/GPU), TorchRL-vec is marginally faster on GAE (1.33 vs 1.43 ms), though CleanRL sacrifices component reusability for single-file clarity. Against Gymnasium (raw environment stepping), TorchRL's parallel-env collector (9,092 FPS) is comparable to Gymnasium (9,289 FPS), while the async collector (19,401 FPS) more than doubles it by overlapping collection and computation.

## Relation to Prior Work

TorchRL builds on PyTorch as its foundational framework and introduces TensorDict as a new PyTorch primitive that generalizes beyond RL to serve as a flexible data carrier for any sequential decision-making workflow. It departs from high-level RL libraries (Stable-baselines3, Acme, RLlib, DI-engine) that couple components through fixed signatures and obscure internal structure, and from single-file implementations (CleanRL) that sacrifice reusability for clarity. The design philosophy is closest to Tianshou in modularity, but TorchRL emphasizes component independence and composable building blocks over turnkey trainers, and its environment API extends Gym's two-function interface with TensorDict-based I/O to natively support batched, multi-agent, and multi-task simulation across diverse backends (IsaacGym, Brax, VMAS, DMControl).

## Why It Matters / Open Questions

TorchRL fills a significant gap in the PyTorch ecosystem by providing a comprehensive, actively maintained decision-making library that spans on-policy, off-policy, offline, model-based, multi-agent, and distributed RL with a single coherent API. The TensorDict abstraction and its nn primitives (TensorDictModule, TensorDictSequential) offer a programmable alternative to nn.Sequential that supports runtime architecture modification, functional calls, and torch.compile compatibility—capabilities that could influence model design beyond RL. Open questions include whether the modest TensorDict overhead (~10–15% vs. PyTree for deep nesting) becomes a bottleneck at extreme scale, whether the modular design's flexibility is sufficient for the most performance-critical distributed training loops, and whether the library can sustain the rapid pace of algorithmic innovation in RL while maintaining backward compatibility.
