## Problem

While LLMs can be augmented with external tools, the availability of suitable tools remains a critical bottleneck, and deploying a powerful model for every inference is prohibitively expensive. This paper asks whether LLMs can close the loop by generating their own reusable tools, thereby combining the capability of a strong model with the cost-efficiency of a lightweight one.
![Teaser figure](../imgs/ICLR20242113/cropped_page1_idx0.webp)

## Input / Output

The tool-making stage consumes a small set of natural-language demonstrations (3 training, 3 validation) and produces a self-contained Python utility function wrapped with usage examples showing how to parse a question into a function call. The tool-using stage then takes a new natural-language task instance, converts it into a concrete function call via in-context learning, executes the function, and returns the task answer (option letter for multiple-choice, or a direct value). The wrapped tool is the reusable artifact that gets cached and served to subsequent instances of the same task class.

## Method

LATM is a two-stage closed-loop framework. In the tool-making stage, a powerful model (e.g., GPT-4) follows a programming-by-example paradigm: it proposes a generic Python function from few-shot demonstrations, verifies it via auto-generated unit tests on held-out samples (with self-debugging on failure), and wraps the validated function together with question-to-call conversion examples. In the tool-using stage, a lightweight model (e.g., GPT-3.5 Turbo) performs a single in-context-learning call to translate a new question into a function invocation, which is then executed to produce the answer. The key design choice is the asymmetric division of labor: the expensive model is invoked once per task class to forge the tool, while the cheap model handles all subsequent instances, amortizing the tool-making cost. An optional dispatcher LLM extends the framework to a streaming setting by maintaining a functional cache of tools, routing each incoming instance to an existing tool or triggering new tool creation for unseen task types.

## Results

With GPT-4 as tool maker and GPT-3.5 Turbo as tool user, LATM achieves 79.7%, 99.6%, 92.2%, 98.3%, 100.0%, and 100.0% accuracy on Logical Deduction (5), Tracking Shuffled Objects (5), Dyck Language, Word Sorting, Chinese Remainder Theorem, and Scheduling Meeting respectively, compared to 66.4%, 61.6%, 20.4%, 59.2%, 0.0%, and 18.9% for CoT prompting. When GPT-4 serves as both tool maker and tool user, LATM reaches 86.6%–100.0% across the six tasks, matching or exceeding GPT-4 + CoT (0.0%–100.0%) on five of six tasks. The cost of LATM with GPT-3.5 Turbo is O(nc + C) versus O(nC) for GPT-4 alone, where C is over 15× the cost of c per call.

## Baselines & Comparisons

Against the standard CoT prompting baseline (Wei et al., 2022), LATM with GPT-3.5 Turbo as tool user wins decisively on all six tasks, with gains ranging from +13.3 (Logical Deduction) to +100.0 (Chinese Remainder Theorem, where CoT scores 0%). GPT-4 + LATM also outperforms GPT-4 + CoT on five of six tasks (e.g., Dyck Language 87.5 vs. 63.6, Word Sorting 99.1 vs. 90.9, Schedule Meeting 100.0 vs. 55.6), with a slight 2.2-point drop on Logical Deduction (86.6 vs. 88.8). Against the human-written CoT demonstrations from Suzgun et al. (2022), LATM achieves 79.7% vs. 66.4% on Logical Deduction (5) and 99.6% vs. 61.6% on Tracking Shuffled Objects (5), confirming that programmatically generated tools substantially outperform hand-crafted reasoning traces. Notably, on Dyck Language, GPT-3.5 Turbo + LATM (92.2%) even surpasses GPT-4 + LATM (87.5%), as GPT-4 occasionally over-edits bracket arguments during function-call generation.

## Relation to Prior Work

LATM extends the tool-augmented LLM paradigm (ReAct, Toolformer, TALLM, Chameleon) by closing the loop: rather than relying on a fixed library of pre-existing tools, the LLM itself synthesizes reusable Python functions via a programming-by-example process. The cost-efficiency angle draws on model cascades and speculative decoding, but repurposes the idea at the task level (one expensive tool-making call amortized over many cheap tool-using calls) rather than at the token level. The functional cache mechanism generalizes GPTCache-style response caching from storing natural-language answers to storing executable code, and the concurrent Voyager and Creator works independently explore LLM-generated skills but without the explicit maker/user split or serving-cost framing.

## Why It Matters / Open Questions

The practical takeaway is a concrete recipe for reducing LLM serving cost: a single GPT-4 call to forge a tool, then GPT-3.5 Turbo calls at ~1/15 the price to solve each instance, while matching or exceeding GPT-4 accuracy on algorithmic reasoning tasks. The functional cache idea opens a path toward LLM infrastructure that caches *capabilities* rather than *answers*, potentially reducing latency and cost for recurring task classes. Open questions include how tools can be incrementally refined as new edge cases appear, how to handle tasks where the tool maker fails (only 2/60 self-correction successes observed), and the absence of high-quality datasets reflecting real-world recurring interactions (scheduling, booking) that would stress-test the framework beyond synthetic Big-Bench tasks.
