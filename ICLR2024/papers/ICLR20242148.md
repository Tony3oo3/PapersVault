## Problem

Existing LM pipelines rely on hard-coded prompt templates—long strings of instructions and demonstrations hand-crafted through manual trial and error—that are brittle, unscalable, and fail to generalize across different LMs, data domains, or pipeline configurations. There is no systematic, programmatic framework for automatically generating and optimizing the prompting strategies within multi-stage LM pipelines.

## Input / Output

The compiler takes a DSPy program (Python code composing declarative modules), a small training set (as few as 200 examples, where only final-output labels are required and intermediate-step labels are bootstrapped automatically), and a validation metric. The compiled pipeline then accepts a text question or math word problem and produces a structured answer (text or numerical value). A key design choice is that training examples may be incomplete—only input values are necessary—and the same program can be recompiled for different LMs or metrics without re-annotating data.

## Method

DSPy introduces three abstractions: natural-language signatures (typed input/output declarations that replace free-form prompts), parameterized modules (composable units like Predict, ChainOfThought, and ReAct that abstract prompting techniques and carry learnable demonstrations), and teleprompters (gradient-free optimizers that compile programs). The compiler operates in three stages: (1) candidate generation, where it simulates the program on training inputs and collects multi-stage execution traces filtered by the metric to bootstrap valid demonstrations for each module; (2) parameter optimization, where it selects the best subset of demonstrations via random search or fine-tunes small LMs on the bootstrapped data; and (3) higher-order optimization, where it ensembles multiple compiled programs with majority voting. The key insight is that bootstrapping demonstrations from the pipeline's own successful execution traces—rather than hand-writing prompts—yields self-improving, LM-adaptive, and pipeline-adaptive prompting that outperforms expert-written demonstrations while enabling much smaller LMs to match proprietary model performance.

## Results

On GSM8K, the best DSPy program (CoT + bootstrap + ensemble) achieves 81.6% test accuracy with GPT-3.5 and 46.9% with Llama2-13b-chat (reflection + ensemble), compared to 25.2% and 9.4% respectively for zero-shot vanilla. On HotPotQA, the multihop program with bootstrap + ensemble reaches 45.6% answer EM (GPT-3.5) and 41.0% (Llama2-13b-chat) on the test set. A fine-tuned T5-770M model (770M parameters) trained via DSPy's BootstrapFinetune teleprompter achieves 39.3% answer EM on HotPotQA dev, competitive with GPT-3.5 baselines, using only 200 labeled inputs and 800 unlabeled questions.

## Baselines & Comparisons

The paper's primary comparison is between DSPy-compiled programs and hand-crafted prompt templates (the standard practice in frameworks like LangChain). On GSM8K, DSPy's bootstrap compilation matches or surpasses human-written Chain-of-Thought demonstrations: CoT + human_CoT achieves 72.4% test accuracy while CoT + bootstrap reaches 72.9% with GPT-3.5, and the gap widens further with ensembling (81.6% vs. no human CoT baseline reported). For Llama2-13b-chat, compilation improves accuracy from 9.4% (zero-shot) to 46.9% (reflection + ensemble), a 5x gain. On HotPotQA, the multihop program with bootstrap makes Llama2-13b-chat (36.4% Ans EM) competitive with GPT-3.5's vanilla few-shot baseline (31.5% Ans EM), and the fine-tuned T5-770M model (39.3% Ans EM dev) approaches GPT-3.5's multihop few-shot performance (31.2% Ans EM test). The key finding is that no hand-crafted prompt strings are needed: all demonstrations, instructions, and module configurations are automatically bootstrapped by the DSPy compiler in minutes.

## Relation to Prior Work

DSPy draws a direct analogy to deep learning frameworks (PyTorch, Theano, Chainer), where modular layers are composed into architectures and trained via optimizers rather than hand-tuned. It translates established prompting techniques—Chain of Thought (Wei et al., 2022) and ReAct (Yao et al., 2022)—into parameterized, composable modules, and generalizes prior prompt-optimization work (Guo et al., 2023; Pryzant et al., 2023) that targeted single LM calls to arbitrary multi-stage pipelines. The paper explicitly positions itself against existing LM pipeline libraries (LangChain, LlamaIndex, Semantic Kernel), arguing that their reliance on hand-crafted prompt templates is brittle and unscalable, and against LMQL, which constrains decoding but does not optimize pipeline-level quality.

## Why It Matters / Open Questions

DSPy offers a concrete, open-source programming model that could shift LM pipeline development from artisanal prompt engineering toward systematic, reproducible optimization, with the practical benefit of making small open models (770M T5, 13B Llama2) competitive with proprietary LMs like GPT-3.5. Key open questions include whether the bootstrap-and-select strategy scales to longer or more heterogeneous pipelines, how to incorporate richer optimization (RL, Bayesian hyperparameter search, LM-as-optimizer) beyond rejection sampling, and whether the approach generalizes to open-ended generation tasks where metrics are harder to define. The evaluation is limited to two well-structured tasks (GSM8K, HotPotQA) with two LMs, leaving broader generalizability untested.
