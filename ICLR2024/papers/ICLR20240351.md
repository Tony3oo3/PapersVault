## Problem

For complex programming tasks, LLMs frequently generate incorrect code on the first attempt, and prior work shows they cannot correct code without external feedback such as unit tests or human instructions. Existing approaches either require sampling tens of candidate programs with reranking or depend on trained verifier models, making them sample-inefficient. The paper asks whether an LLM can be taught via prompting alone to identify and fix its own code errors without any human guidance or pre-trained repair model.

## Input / Output

The method consumes a problem description (database schema for SQL, C++ source code for translation, or a natural language specification for Python) along with the model's initial predicted code and, when available, unit test execution results. It iteratively produces a natural-language code explanation, a self-generated correctness judgment, and a revised code prediction. The process is structured as a multi-turn prompt where each turn appends the previous code, explanation, and feedback to the context, terminating when the model judges the code correct or a maximum of 10 turns is reached.

## Method

SELF-DEBUGGING is a few-shot prompting framework that teaches a pretrained LLM (no fine-tuning) to perform iterative self-debugging through three steps per turn: Generation (predict or revise code), Explanation (describe the code line-by-line in natural language or simulate an execution trace), and Feedback (judge correctness based on the explanation and execution results). The key insight is that the model can identify its own bugs by explaining the code and comparing the explanation to the problem description—mirroring rubber duck debugging—without needing explicit error messages. Four feedback formats are evaluated: simple correct/incorrect, unit test execution results, code explanation, and execution trace, with richer feedback consistently yielding larger gains. Execution-based majority vote selects the initial candidate from multiple samples, and SELF-DEBUGGING is then applied to that candidate, achieving state-of-the-art results on Spider, TransCoder, and MBPP while matching or outperforming baselines that sample over 10× more programs.

## Results

On Spider (text-to-SQL), SELF-DEBUGGING with Codex and code explanation achieves 84.1% execution accuracy (n=32), outperforming the best trained baseline (T5-3B + N-best Reranking at 80.6%, n=25) and the best prompting-only baseline (MBR-Exec at 75.2%, n=50). On MBPP (text-to-Python), SELF-DEBUGGING with unit test + code explanation reaches 75.6% (n=10), surpassing LEVER (68.9%, n=100) by 6.7 points while using 10× fewer samples. On TransCoder (C++→Python translation), SELF-DEBUGGING with Codex achieves 92.5% pass@1, compared to 55.1% for PaLM-Coder and 44.5% for the original TransCoder model.

## Baselines & Comparisons

SELF-DEBUGGING outperforms all compared baselines across all three benchmarks. On Spider, it beats the trained T5-3B + N-best Reranking (80.6%) by 3.5 points and LEVER (81.9%) by 2.2 points, while also surpassing prompting-only methods Coder-Reviewer (74.5%) and MBR-Exec (75.2%) by 8.6–9.6 points. On MBPP, SELF-DEBUGGING (75.6%, n=10) exceeds LEVER (68.9%, n=100) by 6.7 points despite using 10× fewer initial samples, and outperforms MBR-Exec (63.0%) and Coder-Reviewer (66.9%) by 12.6 and 8.7 points respectively. On TransCoder, SELF-DEBUGGING (92.5%) dramatically surpasses PaLM-Coder (55.1%) and the original TransCoder model (44.5%), though these are not directly comparable as they use different model architectures. Notably, SELF-DEBUGGING matches or outperforms baselines that generate more than 10× candidate programs, demonstrating significant sample efficiency gains.

## Relation to Prior Work

This paper sits at the intersection of LLM-based code generation, execution-guided reranking (MBR-Exec, Coder-Reviewer, LEVER), and self-correction prompting (Reflexion, Self-Refine). It departs from prior code repair work (DeepFix, Synthesize-Execute-Debug) by requiring no separate repair model or human feedback, and from prior self-correction work by targeting code generation specifically. The key conceptual departure is the 'rubber duck debugging' framing: rather than predicting error messages or relying on unit tests, the model explains its own code in natural language to identify discrepancies with the problem description, a mechanism prior work (Chen et al., 2023a) suggested was insufficient for code correction without external feedback.

## Why It Matters / Open Questions

SELF-DEBUGGING offers a practical, training-free recipe that improves code generation accuracy while dramatically reducing sample cost (matching or exceeding 10× sampling baselines with 1–2 debugging turns), which is directly relevant to deployment where inference cost matters. The finding that code explanation alone enables meaningful self-correction on Spider (where no unit tests exist) opens a path for debugging in settings where automated verification is unavailable. Limitations include dependence on the underlying LLM's capability, modest absolute gains on harder tasks, and unclear scalability to large codebases where bugs arise from cross-module interactions. Future work on richer semantic explanations and more informative self-generated error messages is identified as a natural next step.
