## Problem

While LLMs demonstrate strong code-understanding capabilities, prior work combining them with formal verification either lacks a formalization of the LLM–verifier interaction, requires manual intervention, or is confined to invariant generation as a standalone procedure. No fully automated framework existed that provably integrates LLMs with automated reasoners for end-to-end program verification while preserving soundness.

## Input / Output

The method takes a C program and a reachability property (a Boolean assertion at a specific line) as input. It produces a three-valued verdict: SUCCESS (the property is an invariant), FAIL (it is not), or UNKNOWN (inconclusive). In practice, the program is preprocessed with line-number placeholder markers (e.g., '// Line A') inserted before and at loop heads to help the LLM correctly associate generated predicates with program locations, since GPT models are unreliable at counting lines.

## Method

LEMUR is a proof calculus that formally defines transition rules (Propose, Decide, Backtrack, Repair 1/2, Success 1/2, Fail) over configurations of (program, assumption, trail of proof goals), with soundness proven via two theorems. The key mechanism is a division of labor: LLM oracles (GPT-3.5/GPT-4 via in-context learning) propose and repair candidate invariants that decompose the verification task into smaller sub-goals, while automated verifiers (ESBMC via k-induction, UAUTOMIZER via predicate abstraction) validate each implication step. A terminating instantiation (Algorithm 1) bounds the number of proposals per goal and enforces a line-number ordering constraint on proposed sub-goals to prevent infinite recursion. Practical prompting strategies include forcing structured output format, inserting line markers, and ordering proposals by frequency across multiple LLM calls with AST-based deduplication.

## Results

On the 133 Code2Inv loop-invariant benchmarks, LEMUR(GPT-4) solves 107 instances (vs. 92 for Code2Inv and 68 for ESBMC alone) within a 10-minute timeout, with an average of 4.7 LLM proposals per solved instance. On 47 hard SV-COMP'23 benchmarks that ESBMC and UAUTOMIZER each solve only 1 of, LEMUR(GPT-4) solves 25 instances (53%) within a 15-minute timeout, averaging 7.2 proposals. LEMUR(GPT-3.5) also outperforms the conventional verifiers on both sets (103 and 14 solved, respectively) but lags behind the GPT-4 variant.

## Baselines & Comparisons

Against Code2Inv (Si et al., CAV 2020), LEMUR(GPT-4) solves 15 more instances (107 vs. 92) on the same 133-benchmark set, despite using a general-purpose LLM rather than a purpose-trained RL invariant synthesizer. Against ESBMC (Gadelha et al., ASE 2018), LEMUR(GPT-4) more than doubles the number of solved Code2Inv instances (107 vs. 68) and solves 25× more SV-COMP instances (25 vs. 1). Against UAUTOMIZER (Heizmann et al., TACAS 2013), the overall SV-COMP'23 winner, LEMUR(GPT-4) solves 25 of the 47 hard benchmarks where UAUTOMIZER solves only 1, with 8 of the solved instances containing multiple loops. LEMUR(GPT-3.5) also beats both conventional verifiers on both benchmark sets but is consistently outperformed by the GPT-4 variant, highlighting the sensitivity of the framework to oracle quality.

## Relation to Prior Work

This paper carves new ground by formalizing the interaction between LLMs and automated program verifiers as a sound proof calculus, whereas prior work (Pei et al. 2023 on LLM invariant generation, Charalambous et al. 2023 on LLM-assisted code repair) treated LLMs and formal methods as loosely coupled components without a deductive framework. It departs from Code2Inv's reinforcement-learning-based invariant synthesis by replacing the learned generator with an LLM oracle operating within a rule-based proof system, and from conventional verifiers (ESBMC, UAUTOMIZER) by delegating high-level decomposition to the LLM while retaining low-level checking to the verifier. The key conceptual move is treating LLM-proposed invariants as temporary assumptions that must themselves be proven, yielding a compositional and sound verification procedure.

## Why It Matters / Open Questions

LEMUR provides the first formal soundness guarantee for LLM-augmented program verification, addressing a critical trust concern that has limited adoption of LLMs in safety-critical settings. The practical results—solving 25/47 SV-COMP benchmarks where state-of-the-art verifiers solved only 1—suggest that LLMs can supply the high-level abstract reasoning (e.g., recognizing x%4==0 as an invariant when modulo is absent from the code) that conventional predicate-abstraction and k-induction techniques struggle to automate. Open questions include scaling to larger programs beyond current verifier capabilities, extending to functional languages, handling LLM token limits on real-world code, and whether fine-tuning LLMs specifically for invariant generation can reduce the number of proposals needed.
