## Problem

LLMs tend to generate code solutions as monolithic blocks rather than decomposing them into logical sub-tasks, which severely limits performance on complex competitive programming tasks. Prior self-revision methods rely solely on feedback from individual generation samples (compiler errors, test outcomes, natural language reflections), neglecting the collective insights available across all samples and their reusable sub-components. CodeChain addresses this by introducing a modular, reuse-based revision process that mimics how experienced developers iteratively improve solutions by reusing previously developed code fragments.

## Input / Output

The method takes a natural language problem description and optional public test cases (input-output pairs) as input. In each revision round, it additionally conditions on a set of representative sub-modules (centroid functions selected via K-means clustering over embeddings from all N=20 prior generation samples). The output is a modularized Python program structured as a sequence of function definitions with docstrings followed by a main execution block. The framework runs up to 5 revision rounds with a fixed generation budget of 20 samples per round, using temperature 0.6 and a 2048-token max output length. Sub-module embeddings are computed with StarEncoder to support long-context programs common in competitive programming.

## Method

CodeChain is a training-free inference framework that iterates between two steps: (1) extracting sub-modules from N generated programs, embedding them, performing K-means clustering, and selecting the centroid sub-module from each cluster as a representative; and (2) augmenting the original chain-of-thought prompt with these representative sub-modules and instructing the LLM to reuse or adapt them when regenerating a new modularized solution. The CoT prompting scheme first asks the model to outline sub-module signatures (function headers and docstrings) before implementing them, creating natural decomposition boundaries. A key design choice is selecting representatives at the sub-module level rather than the whole-program level, since program-level correctness is extremely rare on hard tasks. The number of clusters follows a decreasing schedule (K, K-1, ..., 1) across revision rounds, transitioning from exploration to exploitation as sub-modules become semantically more similar. Optional filtering by public test cases before clustering shifts the output distribution toward more likely correct samples, and the framework is compatible with additional filtering methods like CodeT's synthetic-test-based ranking.

## Results

On APPS, CodeChain+GPT3.5 achieves 30.24% pass@1 (vs. 22.33% for GPT3.5 alone), a 35% relative improvement, and CodeChain+WizardCoder-15B reaches 10.50% (vs. 7.90% baseline). With CodeT filtering, CodeChain+GPT3.5 attains 35.34% pass@1 on APPS, setting a new SoTA. On CodeContests, CodeChain+GPT3.5 with CodeT filtering achieves 13.75% pass@1 (vs. 11.34% for GPT3.5+CodeT), a 76% relative improvement over direct generation. On the 20-sample APPS subset, CodeChain+GPT4 reaches 61.50% pass@1, outperforming Self-repair+GPT4 with human feedback (52.60%).

## Baselines & Comparisons

CodeChain consistently outperforms all baselines across difficulty levels. On APPS, CodeChain+GPT3.5 (30.24%) surpasses GPT3.5 alone (22.33%) by 7.91 points, and CodeChain+WizardCoder-15B (10.50%) beats WizardCoder (7.90%) by 2.6 points. Against self-revision methods, CodeChain+GPT4 (61.50%) outperforms Self-repair+GPT4 with human feedback (52.60%) by 8.9 points on the 20-sample subset, and also beats Self-debug and Reflexion over 5 revision rounds on APPS validation. On CodeContests, CodeChain+GPT3.5 with CodeT filtering (13.75%) improves over GPT3.5+CodeT (11.34%) and code-davinci-002+CodeT (3.20%). The gains are most pronounced on competition-level problems (e.g., 12.38% vs. 5.42% for GPT3.5 on APPS competition), indicating CodeChain benefits harder tasks more. CodeChain also complements filtering methods: when combined with CodeT, it adds ~2.8 points over CodeT alone on APPS.

## Relation to Prior Work

CodeChain builds on chain-of-thought prompting (Wei et al., 2022) by adapting it to elicit modularized code generation, and on the growing line of self-revision methods (Self-debug, Reflexion, Self-repair, CodeRL) that iteratively improve generated programs using feedback. However, it departs from prior self-revision work in two key ways: (1) it operates at the sub-module level rather than the whole-program level, extracting and clustering individual functions across all N samples, and (2) it uses collective, cross-sample feedback (centroid sub-modules from k-means clustering) rather than per-sample feedback (compiler errors, test outcomes, or natural-language reflections). This positions CodeChain as a bridge between the filtering/ranking literature (AlphaCode, CodeT) and the iterative revision literature, combining representative-sample selection with multi-round self-revision in a unified inference pipeline.

## Why It Matters / Open Questions

CodeChain demonstrates that encouraging LLMs to reuse verified sub-modules across revision rounds can substantially close the gap between LLM code generation and experienced developer workflows, achieving 35% and 76% relative pass@1 gains on APPS and CodeContests respectively. A notable limitation is that CoT prompting for modularity alone actually degrades performance (22.43% vs. 26.00% on APPS validation), meaning the framework's benefit is tightly coupled to the self-revision loop; without it, the modular structure is a liability. The method is also sensitive to test-case quality for filtering, and performance can drop in later revision rounds due to overfitting to limited public tests. Open questions include whether better embedding models that capture functional correctness (not just semantic similarity) could reduce reliance on public tests, and whether the approach generalizes to multi-file or multi-language codebases.
