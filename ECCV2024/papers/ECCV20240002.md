## Problem

Existing embodied vision-language models either output low-level manipulation actions or high-level abstract plans, leaving a gap between planning and executable manipulation. The programming paradigm—using code as an intermediate representation to bridge System-II reasoning (planning) and System-I execution (predefined actions)—remains largely unexplored when visual perception is incorporated, and existing simulators lack the carefully designed, vision-dependent function calls needed to train such models.
![Teaser figure](../imgs/ECCV20240002/cropped_page0_idx0.webp)

## Input / Output

The model consumes a multi-view visual observation (8 first-person-view images captured at 45° intervals for full 360° coverage plus 2 bird's-eye-view images in OctoGibson/OctoGTA; 4 FPV images in OctoMC) together with a natural-language task instruction. It produces a structured text response containing scenario analysis, a step-by-step action plan, and executable Python-style code that calls environment-specific functions (e.g., moveBot(), easyGrasp(), goForward(), turnPlayer()). A post-processing step substitutes generic object references in the generated code with exact simulator object names via string similarity matching, selecting the nearest object when multiple matches exist.

## Method

Octopus builds on the Otter VLM architecture (MPT-7B language decoder + CLIP ViT-L/14 vision encoder) with Perceiver Resampler and Cross-Gated Attention modules for vision-language fusion. Training data is collected by having GPT-4 (32K) control an explorative agent in the OctoVerse simulators, generating paired (vision + environment state → plan + code) examples along with step-level and task-level binary success/failure feedback from the simulator. The model is first trained via token-level supervised fine-tuning (SFT), then refined with Reinforcement Learning with Environmental Feedback (RLEF): a CodeLLaMA-7B reward model with an added value head is fine-tuned on the tree-structured feedback data to score candidate responses, and the policy is optimized with PPO using a KL penalty against the SFT-initialized reference model. The key design choice is making all environment function calls vision-dependent (e.g., teleport(yaw, distance) instead of exploreUntil(), goForward(distance) instead of walkTo(location)), forcing the agent to actively perceive and navigate rather than relying on oracle spatial information.

## Results

On OctoGibson (60 evaluation tasks), Octopus (SFT+RLEF) achieves 18% task completion with 42% plan accuracy overall, outperforming EmbodiedGPT (10%/40%) and TAPA step-level (15%/38%). On unseen environments, Octopus reaches 33% completion / 53% plan accuracy, substantially ahead of TAPA (13%/27%) and CodeLLaMA (20%/40%). On reasoning tasks specifically, Octopus (SFT+RLEF) achieves 20%/53% versus 0%/40% for EmbodiedGPT and 0%/07% for CodeLLaMA. On OctoMC, Octopus (SFT+RLEF) completes 30% of all tasks (65% plan accuracy), and on OctoGTA it reaches 20% completion (56% plan accuracy) despite only 160 training tasks.

## Baselines & Comparisons

Octopus (SFT+RLEF) outperforms EmbodiedGPT on every OctoGibson metric: 18%/42% overall vs. 10%/40%, with the largest gap on reasoning tasks (20%/53% vs. 0%/40%) and unseen environments (33%/53% vs. 27%/53%). Against TAPA (step-level), Octopus wins on unseen environments (33%/53% vs. 13%/27%) and reasoning tasks (20%/53% vs. 7%/40%), though TAPA slightly edges Octopus on seen-environment completion (16% vs. 13%). CodeLLaMA, despite 92% code execution success, achieves only 12%/25% overall task completion, far below Octopus's 18%/42%, confirming that coding ability alone does not translate to effective embodied planning. However, GPT-4 and GPT-4V remain substantially stronger on raw task completion (43–45% vs. 18%), indicating that the 7B-parameter Octopus still lags behind frontier proprietary models. The RLEF training stage consistently improves over SFT-only by 3–7 percentage points in plan accuracy across all settings, validating the environmental feedback signal.

## Relation to Prior Work

Octopus builds directly on the Otter VLM architecture (MPT-7B + CLIP ViT-L/14 with Perceiver Resampler and Cross-Gated Attention from Flamingo) but repurposes it for a fundamentally different output: executable code rather than free-form text. It departs from embodied planners like TAPA and SayPlan, which use separate vision modules to convert visual data into textual scene graphs before LLM planning, by integrating visual perception natively into the code-generation process. It also extends the code-invocation paradigm of Voyager and VisProg, which operate on text-only or game-API inputs, by requiring all function calls to be vision-dependent (e.g., goForward(distance) instead of walkTo(location)), and introduces RLEF—a PPO-based fine-tuning scheme using step- and task-level environmental feedback—as a training mechanism not previously applied to embodied code generation.

## Why It Matters / Open Questions

OctoVerse provides the first multi-environment benchmark (household, Minecraft, GTA) specifically designed for vision-dependent embodied code generation, filling a gap where prior simulators either lacked formulated tasks or provided vision-agnostic shortcuts like exploreUntil(). The RLEF training scheme demonstrates that environmental feedback can refine an agent's planning strategy, though the absolute task completion rates remain low (18% on OctoGibson, 30% on OctoMC), and GPT-4V still outperforms the specialized model on several splits. Key open questions include whether the code-generation medium scales to more complex manipulation, how to handle the spatial-reasoning failures observed in Minecraft and GTA, and whether the approach transfers to real-world robotic settings beyond simulation.
