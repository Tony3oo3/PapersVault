## Problem

Existing Visual Programming methods generate an entire program in a single monolithic code block, forcing the LLM to handle all logic, details, and API calls simultaneously. This approach underutilizes the LLM's step-by-step reasoning capacity and produces code that lacks modularity, resulting in suboptimal accuracy and poor interpretability. No prior VP method leverages the recursive, top-down decomposition strategy that human programmers naturally employ.

## Input / Output

The system receives a visual input (a single image, a set of images, or a video) and a natural-language question, and produces a text answer evaluated by exact match. The visual input is consumed through the ViperGPT API, which exposes predefined vision functions (find, exists, verify_property, simple_query, compute_depth, crop) operating on ImagePatch objects, plus video-specific functions (trim, frame_from_index, frame_iterator). The code generator operates in a few-shot setting with at most 50 in-context examples shared between recursive and non-recursive variants, using GPT-3.5-turbo for code generation.

## Method

RVP introduces a recursive_query(image, sub-question) function into the VP API, enabling the LLM to decompose a question into sub-questions and recursively invoke itself to generate and execute modular code pieces for each. During execution, when recursive_query is called, the LLM is prompted with the sub-question to produce a new program, which is executed and whose return value is passed back to the caller, continuing until an atomic level where only external vision APIs are needed. Termination is enforced by a maximum recursion depth of 10 and by falling back to a direct simple_query when the generated code would recursively call the same input question. A key additional mechanism is dynamic type assignment: the return type is embedded in the sub-question string (e.g., 'Return a bool, is there a black cat?'), allowing the model to generate code with context-appropriate return types, including types unseen in in-context examples such as List[ImagePatch] and List[str].

## Results

RVP achieves exact-match accuracy of 63.53% (Random Split) and 66.09% (Zero-shot Split) on VSR, 48.82% on NextQA Hard Temporal, 45.62% on GQA Test-dev, and 52.67% on COVR Test. Across all five evaluation settings, RVP outperforms the ViperGPT baseline (which uses the same API and in-context examples but without the recursive_query function), with gains ranging from +1.0 to +4.5 points. The ablation on dynamic type assignment (Table 2a) shows that explicit type specification in recursive queries yields the largest improvement, reaching 70.23% on GQA and 67.86% on COVR versus 55.99% and 60.71% for the non-recursive baseline.

## Baselines & Comparisons

RVP consistently outperforms ViperGPT (the closest non-recursive VP baseline using the same API and prompts) on all five settings, with the largest margin on VSR Zero-shot (+4.5 pts, 66.09 vs 61.59) and GQA (+1.0 pts, 45.62 vs 44.63). Against CodeVQA, RVP wins on COVR (52.67 vs 50.7) but trails on GQA (45.62 vs 49.0), which is the single setting where RVP does not achieve the best zero/few-shot result. RVP also surpasses CLIP on both VSR splits (63.53 vs 56.0; 66.09 vs 54.5) and BLIPv2 on GQA (45.62 vs 42.31). Compared to fully supervised models, RVP remains competitive on NextQA (48.82 vs 48.6 HiTeA) but falls short on VSR (63.53 vs 69.3 ViLT), GQA (45.62 vs 65.1 VinVL), and COVR (52.67 vs 57.9 VisualBERT), reflecting the inherent gap between few-shot code generation and task-specific training.

## Relation to Prior Work

This paper extends the Visual Programming (VP) paradigm established by ViperGPT and CodeVQA, where an LLM generates a single Python program that calls predefined vision APIs to answer visual questions. The key departure is replacing monolithic code generation with a top-down recursive decomposition: the LLM first writes a high-level program containing recursive_query calls, then generates and executes sub-programs for each sub-question, mirroring how human programmers structure complex code. The dynamic type assignment mechanism (letting sub-queries specify their expected return type) is a novel addition to the VP API that prior frameworks did not support. The approach also draws on NLP findings that decomposing complex reasoning into sub-problems improves LLM performance (e.g., least-to-most prompting, graph of thoughts), transplanting that insight into the visual code-generation setting.

## Why It Matters / Open Questions

RVP demonstrates that recursive, modular code generation consistently improves both accuracy and interpretability over single-shot VP across four diverse benchmarks, and that the technique is plug-and-play with any existing VP system. The generalization to unseen return types (e.g., List[ImagePatch]) suggests the framework can handle more complex data structures than current VP methods support. However, the authors acknowledge that most questions in current VQA benchmarks are short and non-recursive, limiting the observable benefit; the approach's full value would likely require more complex, multi-hop visual reasoning benchmarks. The ~3× cost and ~2.1× runtime overhead for recursive queries, combined with 52% of errors stemming from underlying API model inaccuracy rather than code structure, indicate that the recursive layer is a necessary but not sufficient fix for VP accuracy.
