## Problem

Existing tool-augmented LLM frameworks (e.g., HuggingGPT, Visual ChatGPT, InternGPT) rely on LLMs to generate task plans as chains or trees of thoughts, which breaks down when solutions require intricate topological structures with multiple tool dependencies. This leads to inaccurate tool selection, hallucinated arguments, and failed execution on complex multi-modal tasks. The paper asks: can we replace LLM-generated plans with a structured search over a pre-built dependency graph to achieve reliable tool invocation?
![Teaser figure](../imgs/ECCV20240302/cropped_page1_idx0.webp)

## Input / Output

The system accepts a free-form user text prompt that may reference attached resources (images, videos, audio files) and produces a structured solution path — an ordered sequence of tool calls with resolved arguments — which is then executed to yield multi-modal outputs (processed/generated images, edited videos, processed audio) plus a natural-language summary. During decomposition, each subtask is formalized as a JSON object with fields for description, domain scope, input arguments (key-value pairs of resource type and path), and expected return type (using temporary placeholders like ⟨GEN⟩-0 to capture inter-subtask dependencies).

## Method

ControlLLM introduces a three-stage pipeline: (1) a task decomposer (LLM-based) splits the user request into subtasks with well-defined inputs, outputs, and domain scopes; (2) a Thoughts-on-Graph (ToG) module performs depth-first search over a pre-built tool graph whose nodes are resources (typed) and tools (with description, accepted args, and return type) connected by tool-resource and resource-tool edges, using one of four search strategies (greedy, beam, adaptive, exhaustive) guided by LLM-scored tool relevance; (3) an execution engine parallelizes independent subtasks, maintains a state memory for runtime argument correction, and generates a user-friendly response. The key insight is that explicit tool dependencies encoded in the graph eliminate LLM hallucination in tool selection, and the search-based planning avoids token-length limitations of asking an LLM to generate the full solution. The default configuration (ControlLLM-Mix) fine-tunes LLaMA-7B for task decomposition while using ChatGPT for tool scoring and solution ranking, achieving 93% overall solution accuracy versus 59% for the best baseline.

## Results

ControlLLM-Mix (the default setting combining LLaMA-7B for task decomposition and ChatGPT for tool selection) achieves a 93% overall solution evaluation score, substantially outperforming the best baseline ViperGPT (75%). It also attains the lowest Irrelevant Tool Inclusion Rate (IR = 0.03), highest Necessary Tool Inclusion Rate (NR = 0.93), lowest Resource Hallucination Rate (HR = 0.02), and highest Resource Type Consistency Rate (CR = 0.98) among all methods. On the hardest difficulty level (>3 APIs), ControlLLM-Mix reaches 81% solution evaluation versus 52% for ViperGPT and 0% for InternGPT and GPT4Tools.

## Baselines & Comparisons

ControlLLM-Mix outperforms all six baselines across every metric. The strongest baseline, ViperGPT, achieves 75% overall solution evaluation but drops to 52% on hard tasks; ControlLLM-Mix reaches 93% overall and 81% on hard tasks, a 18-point and 29-point margin respectively. ViperGPT also leads among baselines in NR (0.86) and CR (0.93), yet ControlLLM-Mix surpasses it on both (0.93 and 0.98) while simultaneously achieving a much lower IR (0.03 vs. 0.13). HuggingGPT and VisProg, both relying on CoT-style planning, show the highest IR (0.45 and 0.50), indicating frequent inclusion of irrelevant tools, and achieve only 59% overall solution evaluation. InternGPT and GPT4Tools completely fail on hard tasks (0% solution evaluation), while ControlLLM-Mix maintains 81%. Notably, even ControlLLM-ChatGPT (using only ChatGPT without fine-tuning) outperforms HuggingGPT and Visual ChatGPT in overall solution evaluation (64% vs. 59% and 57%), demonstrating the benefit of the ToG graph-search paradigm over pure LLM-based planning.

## Relation to Prior Work

ControlLLM departs from the dominant paradigm in tool-augmented LLMs (HuggingGPT, Visual ChatGPT, InternGPT, ViperGPT, VisProg, GPT4Tools) where the LLM itself generates the solution path via chain-of-thought or tree-of-thought prompting. Instead, it pre-builds a tool graph encoding parameter and dependency relations among tools, then applies classical graph search (DFS with scoring) to find solution paths, thereby sidestepping the hallucination problem inherent in LLM-generated planning. The task decomposition stage formalizes what prior methods handle implicitly, producing structured subtask descriptions with explicit domains, arguments, and expected outputs. The approach is conceptually related to Graph-of-Thought (GoT) work, but differs in that the graph is pre-constructed from tool specifications rather than generated by the LLM at inference time.

## Why It Matters / Open Questions

The framework addresses a practical bottleneck in deploying tool-augmented LLMs: complex multi-tool invocations with intricate topological dependencies that chain- or tree-shaped planning cannot handle. The 93% vs. 59% solution success rate gap (ControlLLM-Mix vs. best baseline) is compelling, though the evaluation rests on only ~100 instructions assessed by multi-person voting rather than fully automated metrics, limiting statistical confidence. Open questions include how the tool graph scales to thousands of tools without combinatorial explosion, whether the pre-built graph assumption holds in dynamic environments where tools change frequently, and whether the DFS search latency (236 tools visited on average for the adaptive strategy) is acceptable for real-time interactive use. The open-source release and modular design (swappable LLM backends, pluggable toolbox) make it a useful reference implementation for the field.
