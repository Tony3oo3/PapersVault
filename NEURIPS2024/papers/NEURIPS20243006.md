## Problem

Existing spreadsheet manipulation benchmarks rely on synthetic queries (via self-instruct) or manually crafted instructions paired with overly simplified spreadsheets containing only a single regular relational table, and they evaluate solutions with a single test case per instruction. This fails to capture the complexity of real user demands—multi-table sheets, non-standard headers, non-textual elements, and contextual information like previous failed attempts—and risks rewarding solutions that are overfit to one specific spreadsheet rather than generalizing to varying data.

## Input / Output

The model receives a natural-language instruction (averaging 85.7 words, often including the user's prior attempts, encountered errors, and an output example) together with an XLSX spreadsheet file that may contain multiple tables per sheet, non-standard relational tables with nested/incomplete/missing headers, free-form text cells, and formatting elements such as cell colors. The model must produce a Python code solution (typically using openpyxl or pandas) that, when executed, modifies the spreadsheet in place; correctness is then verified by applying the same code to three structurally similar but value-different test cases per instruction and checking exact match of the answer-position cells against ground truth.

## Method

SPREADSHEETBENCH is constructed through a four-stage pipeline: sourcing 912 solved questions from four real Excel forums/blogs (ExcelForum, Chandoo, MrExcel, ExcelGuru), filtering for feasibility and representativeness, formatting instructions via GPT-4 plus human annotation with explicit answer-position constraints, and generating two additional test cases per instruction by modifying spreadsheet data to target real-world corner cases. The evaluation adopts an Online Judge (OJ)-style metric with two scoring variants—soft restriction (partial credit per test case, IOI-style) and hard restriction (all-or-nothing per instruction, ICPC-style)—requiring a single code generation to pass all test cases. The paper evaluates five model categories (TableQA models, open-source code/general LLMs, close-source GPT-3.5/GPT-4o, and spreadsheet-specific products) under both single-round and multi-round (ReAct + code execution feedback, up to 5 rounds) inference settings, revealing that even GPT-4o achieves only ~18% soft-restriction accuracy versus 71% for human Excel experts, and that coding ability and spreadsheet-structure understanding are the primary bottlenecks.

## Results

On SPREADSHEETBENCH, the best-performing LLM (GPT-4o, single-round) achieves only 18.35% overall soft restriction and 15.02% overall hard restriction, while the most advanced spreadsheet agent (Copilot in Excel) reaches 20.00% soft restriction. Open-source models perform substantially worse, with scores ranging from 0.33% (CodeQwen-7B) to 5.31% (DeepseekCoder-33B with multi-round) on soft restriction. TableQA-specific models (TaPEx, TaPas) score 0% across all metrics, highlighting the fundamental difficulty gap between table QA and spreadsheet manipulation. Human Excel experts achieve 71.33% soft and 62.00% hard restriction, revealing a ~50-point gap between SOTA models and human performance.

## Baselines & Comparisons

GPT-4o (18.35% soft / 15.02% hard overall) is the strongest LLM, outperforming GPT-3.5 (2.34% / 1.64%) by roughly 8× and all open-source models by a wide margin. Copilot in Excel (20.00% soft) edges out GPT-4o on the 5% sample, while SheetCopilot (14.00% soft) trails both. Among open-source models, DeepseekCoder-33B (2.60% single-round, 5.31% multi-round) outperforms Llama-3-70B (1.32% / 3.74%) and Mixtral-8x7B (3.11% / 3.88%), confirming that coding-specialized models have an advantage for spreadsheet manipulation. Multi-round inference with ReAct and execution feedback yields substantial gains for smaller models (e.g., GPT-3.5 improves from 2.34% to 7.09%, a ~3× increase), but GPT-4o actually declines slightly (18.35% → 16.96%) due to redundant content retrieval. TableQA models (TaPEx, TaPas) and the prompt-based Binder (GPT-3.5) are effectively non-functional on this benchmark, scoring 0% and 1.17% respectively, underscoring that spreadsheet manipulation is a fundamentally harder task than table question answering.

## Relation to Prior Work

This paper departs from prior spreadsheet manipulation benchmarks (SheetCopilotBench, SheetRM, InstructExcel) that rely on synthetic or manually simplified queries and single-test evaluation, instead sourcing 912 instructions exclusively from real Excel forums with complex, context-rich user questions. It also draws on the online judge paradigm from competitive programming to introduce multi-test-case evaluation, a methodological shift from the single exact-match scoring used in prior work. Conceptually, the paper positions spreadsheet manipulation as fundamentally distinct from TableQA and Text2SQL tasks, arguing that the flexible, non-standard, multi-table structure of real spreadsheets (nested headers, non-textual elements, free-form text) cannot be captured by relational table abstractions.

## Why It Matters / Open Questions

The benchmark reveals a substantial gap between the best LLM (GPT-4o at ~18% soft restriction) and human Excel experts (~71%), highlighting that current models lack both the coding precision and structural understanding needed for real-world spreadsheet manipulation. The OJ-style evaluation exposes that many seemingly-correct solutions are overfit to specific spreadsheet values and fail on minor data variations, a robustness concern directly relevant to production deployment. Open questions include how to improve LLMs' ability to handle non-standard table structures, whether the multi-round interaction paradigm can be made to benefit even frontier models, and how to scale the benchmark to cover the full breadth of spreadsheet operations (charts, pivot tables, Power Query).
