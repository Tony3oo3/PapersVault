## Problem

LLM-based embodied agents excel at high-level planning and code generation but cannot acquire low-level motor skills through practice, while pure RL methods are sample-inefficient and lack the prior world knowledge that LLMs provide. The unresolved question is how to let an LLM agent autonomously decide which sub-actions to handle with code versus which to delegate to a trainable RL policy, and how to integrate both into a single coherent learning pipeline without requiring human-designed skill libraries or massive pre-training data.

## Input / Output

The system consumes a natural-language task description (e.g., 'craft a wooden pickaxe'), MineDojo environment observations (RGB frames, inventory state, location stats, and lidar distances via the MineDojo API), and a set of human-written code examples for crafting primitives. It produces two complementary outputs: (1) Python generator functions implementing coded sub-actions (navigation, attacking, crafting, placing items) that are either executed directly or inserted as high-level actions into the RL action space, and (2) a PPO-trained neural network that selects among these high-level actions and raw environment actions based on observations. The RL action space is augmented with dedicated tokens for each coded action, so the policy learns when to invoke them.

## Method

RL-GPT employs a two-level hierarchical multi-agent framework: a slow agent (GPT-4) decomposes the task into sub-actions and decides which are codeable versus which require RL learning, while a fast agent (GPT-4) writes the actual Python code and instantiates the RL training configuration (observation space, action space, reward function). The key architectural insight is inserting LLM-generated coded actions into the RL action space via temporal abstraction, so the PPO network learns when to trigger high-level actions (e.g., 'attack 20 times') versus performing raw low-level control. A critic agent evaluates each sub-action's success and provides structured feedback (success/failure, reasoning, improvement suggestions) that drives a two-loop iteration: the inner loop refines the fast agent's code through environment execution errors, while the outer loop refines the slow agent's action decomposition based on aggregated critic outputs. For long-horizon tasks like ObtainDiamond, a GPT-4 task planner further decomposes the goal into sequential sub-tasks, each handled by an independent RL-GPT instance with its own neural network.

## Results

On the MineDojo benchmark (Table 1), RL-GPT achieves the highest success rate across all 9 selected long-horizon tasks, ranging from 0.38 (mutton) to 0.93 (bucket), outperforming Plan4MC (best: 0.83) and MineAgent (best: 0.50). On the ObtainDiamond challenge (Table 2), RL-GPT achieves an 8% success rate using only 3M environment samples, compared to DreamerV3's 2% at 100M samples and VPT's 20% at 16.8B samples, demonstrating a 33× and 5,600× sample-efficiency advantage respectively. Ablations confirm that the two-loop iteration mechanism improves success rates from 0.26 (zero-shot) to 0.65 (3 iterations) on the crafting-table task, and that the slow+fast+critic agent structure outperforms a single-agent design (0.65 vs. 0.34).

## Baselines & Comparisons

RL-GPT decisively outperforms MineAgent (pure PPO + CLIP reward), which achieves 0% on nearly all long-horizon tasks, confirming that naive RL cannot handle multi-step embodied tasks without high-level structure. Against MineAgent with AutoCraft (human-coded crafting actions), RL-GPT wins on all 9 tasks, with the largest margin on stick (0.65 vs. 0.00) and wooden pickaxe (0.67 vs. 0.00), demonstrating that LLM-generated code-as-policy generalizes beyond hand-coded crafting. Plan4MC is the closest competitor, achieving competitive results on milking (0.83 vs. 0.85) and wool (0.53 vs. 0.56), but RL-GPT leads on all 9 tasks, with the largest gaps on stick (+0.35) and stone pickaxe (+0.47), attributable to its ability to insert arbitrary coded actions (e.g., 'attack 20 times') into the RL action space rather than being restricted to three human-designed action types. On the ObtainDiamond challenge, RL-GPT (8%, 3M samples) surpasses DreamerV3 (2%, 100M) and Plan4MC (0%, 7M) while using far fewer samples; however, it trails VPT (20%, 16.8B samples) and DEPS-Oracle (60%, human-written code), though it achieves this with roughly 5,600× fewer environment interactions than VPT and without any expert demonstrations.

## Relation to Prior Work

This paper unifies two previously separate paradigms: Code-as-Policies (Liang et al., 2023), where LLMs generate executable Python code as agent actions, and temporal abstraction in RL (Sutton et al., 1999), where high-level skills are inserted into the action space of a learned policy. Prior LLM+RL work either fine-tunes LLM parameters with RL (RLAdapter, Octopus) or keeps LLM planning and RL learning in separate pipelines (Plan4MC, DEPS), with human-designed skill libraries bridging the gap. RL-GPT departs by treating the entire RL training pipeline as a callable tool for the LLM agent, and by having the LLM autonomously decide which sub-actions to code versus which to learn, then inserting the coded actions directly into the RL action space via temporal abstraction.

## Why It Matters / Open Questions

The key practical implication is that LLM agents can autonomously acquire low-level motor skills without human-designed skill libraries or large-scale video pretraining, reducing the manual engineering bottleneck in embodied agent construction. The 33× sample efficiency gain over DreamerV3 on ObtainDiamond (3M vs. 100M steps) is notable, though the absolute 8% success rate remains modest. Open questions include whether the approach generalizes beyond Minecraft to continuous-control robotics, whether the GPT-4 API dependency can be replaced by open-weight models without significant performance loss, and whether the two-loop iteration converges reliably on tasks with more complex visual grounding. The upper bound is inherently constrained by the LLM's coding ability, and the method's cost (GPT-4 API calls per iteration) limits scalability.
