## Problem

Designing and updating computational workflows (AI agents, robots, copilots) requires optimizing heterogeneous parameters—prompts, orchestration code, ML hyper-parameters—under rich, non-scalar feedback and non-differentiable operations. Existing approaches reduce this to black-box optimization with scalar scores, which is highly inefficient when the parameter space is large (e.g., natural language or code). No framework existed for end-to-end generative optimization of general, potentially non-differentiable computational workflows.

## Input / Output

The method takes a Python computational workflow annotated with Trace decorators (@trace.bundle for operators, node for parameters), a context/instruction string describing the optimization goal, and output feedback that can be any compact text (scores, natural-language suggestions, error messages, or console output). It produces updated parameter values—code function bodies, prompt strings, or numerical hyper-parameters—that improve the workflow's behavior. A key constraint is that the workflow must be representable as a DAG (no in-place stateful mutations), and the feedback and context must be expressible in text for the current OptoPrime optimizer.

## Method

Trace converts a computational workflow into an Optimization with Trace Oracle (OPTO) problem using PyTorch-like syntax: a forward pass builds a directed acyclic graph (DAG) of computed values, and a backward pass propagates feedback via a Minimal Subgraph Propagator (MSP) that extracts the minimal subgraph connecting trainable parameters to the output. The core insight is that this execution trace plays the role of back-propagated gradients—it provides the structural information needed to relate rich output feedback to specific parameters, even in non-differentiable settings. The first OPTO optimizer, OptoPrime, formats the extracted subgraph as a pseudo-algorithm debugging report (showing code, operator definitions, intermediate values, and feedback) and prompts an LLM (GPT-4) with a ReAct-CoT template to reason about the graph and propose concrete parameter updates in a single call. This graph-based design cleanly separates the tracing infrastructure from the optimization algorithm, enabling different optimizers to be plugged in, and supports joint optimization of heterogeneous parameters (code, prompts, numbers) within a single workflow.

## Results

On BigBench Hard (23 tasks, 0-shot), Trace achieves 59.5% overall accuracy, outperforming DSPy (41.6%) and DSPy's own COPRO optimizer (55.3%), with the largest gap on algorithmic tasks (51.1% vs. 32.6% and 45.2%). With Chain-of-Thought prompting, Trace+CoT reaches 78.6% overall (80.6% on algorithmic tasks) versus 70.4% for DSPy+CoT and 71.6% for DSPy-PO+CoT. In the TextGrad comparison, OptoPrime achieves comparable or slightly better success rates (e.g., 86.6% vs. 86.1% on MMLU-ML) while running ~3× faster in wall-clock time (1.7 min vs. 3.5 min). On numerical optimization, Trace matches the best-in-class Adam optimizer, and on robot manipulation (LLF-Bench Meta-World), Trace with memory clearly outperforms OPRO across Reach, Pick-place, and Push tasks.

## Baselines & Comparisons

Against DSPy and its COPRO optimizer [22], Trace wins on all BigBench Hard splits, with the most dramatic improvement on algorithmic tasks (51.1% vs. 32.6%/45.2% in 0-shot; 80.6% vs. 68.0%/70.0% with CoT), demonstrating that jointly optimizing prompts and code outperforms prompt-only optimization. Against OPRO [13], Trace consistently outperforms across numerical optimization, traffic control, robot manipulation, and Battleship, with the gap attributed to OPRO's lack of access to the execution trace; even when given 7–10× more iterations to equalize token budgets, OPRO plateaus at worse performance. On numerical optimization, Trace matches Adam [25] (the gold-standard first-order optimizer), while a masked variant without the graph struggles significantly. In traffic control, Trace quickly reaches the level of the domain-specific SCATS heuristic [27], whereas black-box methods GP [8] and PSO [28] require far more iterations to converge. Against TextGrad [24], OptoPrime achieves similar or marginally better success rates (e.g., 86.6% vs. 86.1% on MMLU-ML, 89.4% vs. 89.2% on BBH Counting) but runs approximately 3× faster in wall-clock time due to making a single LLM call per optimization step rather than one per graph node.

## Relation to Prior Work

This paper extends the AutoDiff/PyTorch paradigm (forward pass, backward pass, optimizer step) from differentiable neural networks to general, potentially non-differentiable computational workflows by replacing gradients with execution traces. It departs from prior LLM-based optimizers (OPRO, PromptBreeder, DSPy's COPRO) that treat optimization as black-box search over isolated prompts or code snippets, by introducing the OPTO formulation where the optimizer receives the full computational graph alongside output feedback. The concurrent TextGrad work shares the end-to-end optimization goal but propagates text feedback per-node, whereas Trace propagates minimal subgraphs and cleanly separates the tracing infrastructure from the optimization algorithm, enabling heterogeneous parameter types (code, prompts, hyperparameters) in a single workflow.

## Why It Matters / Open Questions

Trace provides the first tractable, PyTorch-like framework for end-to-end optimization of general computational workflows with heterogeneous parameters and rich (non-scalar) feedback, positioning itself as a research platform for the next generation of self-adapting AI agents. Key open questions include: how to design informative feedback (analogous to loss function design in deep learning), how to scale OptoPrime beyond moderate-size graphs given LLM context limits, and how to handle non-textual feedback (images, video) and distributed/stateful workflows. The paper explicitly acknowledges that OptoPrime is a proof-of-concept optimizer akin to vanilla gradient descent, and that the true value of the Trace framework lies in enabling future, more sophisticated generative optimizers.
