## Problem

As LLM context lengths grow to 128K–1M tokens, the KV cache becomes the dominant source of memory consumption and decoding latency, since attention computation scales linearly with prompt length. Existing KV compression methods (H2O, ScissorHands, FastGen) primarily target KVs appended during generation but neglect the prompt KV cache, which in real-world applications (chatbots, code assistants, document QA) constitutes the overwhelming majority of the cache and is the true bottleneck.

## Input / Output

SnapKV takes a long text prompt (tested up to 380K tokens) and the per-head key/value tensors produced during the prefilling stage. It outputs a compressed KV cache of fixed size (e.g., 1024, 2048, or 4096 tokens per head) by selecting clustered important prefix positions and concatenating them with the full observation window KVs. The compressed cache is then used identically to a full cache during autoregressive generation, requiring no architectural changes to the model.

## Method

SnapKV exploits the empirical finding that each attention head's focus on prompt tokens remains stable throughout generation and can be predicted from a short observation window (last L_obs tokens) at the end of the prompt. A voting mechanism sums the softmax attention weights of the observation window's queries over the prefix keys per head, then selects the top-k positions (k = (1−p)·L_prefix) to form the compressed prefix. To preserve contextual integrity around selected positions, a 1D max-pooling layer with a small kernel (e.g., 5–7) clusters neighboring tokens before the top-k selection. The final compressed cache concatenates the selected prefix KVs with all observation-window KVs, yielding a constant-size cache regardless of prompt length. The entire procedure is fine-tuning-free, runs once during prefilling, and integrates into HuggingFace-style implementations with only a few lines of code.

## Results

On LongBench (16 datasets, avg prompt ~13K tokens), SnapKV with only 1024 prompt KV tokens (92% compression) maintains near-parity with full KV caching across all four tested models (LWMChat, LongChat, Mistral-7B, Mixtral-8x7B). At 16K input length, SnapKV achieves a 3.6× generation speedup and 8.2× memory efficiency improvement over the baseline, and extends the maximum processable sequence from 16K to 131K tokens at batch size 2. In the Needle-in-a-Haystack pressure test, SnapKV correctly retrieves the needle up to 380K context tokens on a single A100-80GB GPU (380× compression ratio), while the unmodified implementation OOMs at 33K tokens.

## Baselines & Comparisons

Against H2O (Heavy-Hitter Oracle), SnapKV delivers substantially better accuracy at the same or smaller KV budget: on Mistral-7B-Instruct-v0.2, SnapKV with only 1024 prompt KV tokens outperforms H2O with 4096 tokens on 11 out of 16 LongBench benchmarks (e.g., NrtvQA 25.54 vs. 22.61, HotpotQA 40.94 vs. 36.54, 2WikiMQA 25.70 vs. 20.60). The gap widens on multi-document QA and summarization tasks where H2O's generation-time eviction discards prompt information that SnapKV retains via its observation-window voting. Against Medusa (parallel decoding), SnapKV is complementary rather than competitive: combining SnapKV with Medusa yields a 1.3× speedup over Medusa alone and 2.2× over native decoding at 10K sequence length, since SnapKV's constant-size prompt KV cache removes the linearly growing attention bottleneck that slows Medusa's speculative verification on long contexts.

## Relation to Prior Work

SnapKV carves out a distinct niche within the KV cache compression literature by targeting the *prompt* KV cache rather than the KVs appended during generation, which is where prior methods (StreamLLM, H2O, FastGen, ScissorHands) primarily operate. Its conceptual departure is the observation-window-based voting mechanism: instead of applying a fixed eviction policy or cumulative-attention scoring during decoding, SnapKV reads attention patterns from a short window at the end of the prompt to pre-select which prefix positions to retain, then uses 1D pooling to cluster neighboring positions for contextual integrity. This positions it as a pre-generation, context-aware compression step that is orthogonal to (and combinable with) generation-stage eviction strategies.

## Why It Matters / Open Questions

SnapKV offers a simple, fine-tuning-free, drop-in solution to one of the most pressing practical bottlenecks in LLM serving: the linear growth of decoding latency and memory with prompt length. The demonstrated ability to process 380K tokens on a single A100-80GB GPU with negligible accuracy loss, combined with a 3.6× speedup and 8.2× memory reduction at 16K tokens, makes it immediately deployable in production chatbot and agent pipelines. Key limitations remain: SnapKV does not extend a model's inherent long-context capability, does not reduce prefilling cost, and its hyperparameters (observation window size, pooling kernel) require per-model tuning. Open questions include how it interacts with quantized KV caches, multi-modal attention, and whether the observation-window assumption holds for architectures with sliding-window or sparse attention.
