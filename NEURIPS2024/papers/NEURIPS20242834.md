## Problem

EHRs combine structured database tables with unstructured clinical notes, but discrepancies between the two are common due to unintuitive system design and human error, posing patient safety risks. Existing fact-verification datasets (e.g., TabFact, FEVEROUS) target single claims against small tables, making them unsuitable for the multi-claim, large-scale relational database setting of real EHRs where both tables and notes can contain errors.

## Input / Output

The method takes a full clinical note (discharge summary, physician note, or nursing note, averaging ~1,953 tokens) and a relational EHR database (13 tables, up to 330M rows) as input. It produces a per-entity consistency label (CONSISTENT or INCONSISTENT) along with the specific table and column where the mismatch occurs. Entities are restricted to Type 1 (numeric values, e.g., 'WBC 10.0') and Type 2 (existence-verifiable, e.g., 'Vancomycin was started'), and the dataset is provided in both the original MIMIC-III schema and the standardized OMOP CDM schema.

## Method

CheckEHR is an eight-stage LLM pipeline that decomposes the consistency check into sequential sub-tasks, each solved via in-context learning with few-shot examples: (1) Note Segmentation splits long notes into topic-focused sub-texts to handle context-length limits; (2) NER extracts verifiable entities; (3) Time Filtering classifies temporal expressions (standard, narrative, or absent); (4) Table Identification selects relevant tables using schema descriptions and foreign keys; (5) Pseudo Table Creation extracts structured column values from free text; (6) Self-Correction re-evaluates the pseudo table against the source note to suppress hallucinations; (7) Value Reformatting aligns data types between the pseudo table and actual schema; and (8) Query Generation produces an SQL query executed against the database, with entity names resolved via an Item Search Tool that maps abbreviations and brand names to database items. The framework operates in both few-shot and zero-shot settings without any fine-tuning, and ablation studies show each stage contributes roughly 8 percentage points of recall improvement.

## Results

On MIMIC-III, CheckEHR with GPT-3.5 (0613) in a few-shot setting achieves the best overall performance: 61.06% recall, 48.63% precision, and 86.25% intersection across all note types. In the zero-shot setting, Llama-3 70B leads with 52.39% recall and 38.01% precision. On the MIMIC-OMOP variant (few-shot, with gold entities provided to skip NER), Llama-3 achieves the highest precision at 65.07% and Tulu2 the highest recall at 54.36%. The framework substantially outperforms direct GPT-3.5 prompting, which yields only 10.12% recall and 8.75% precision without the eight-stage decomposition.

## Baselines & Comparisons

The paper does not compare CheckEHR against external consistency-checking baselines; instead, it ablates the effect of the base LLM and the shot setting within the framework. GPT-3.5 (0613) in few-shot mode is the strongest configuration, reaching 61.06% recall and 48.63% precision, outperforming Llama-3 70B (53.05% / 42.61%) and Mixtral 8X7B (54.70% / 45.79%) in the same setting. The eight-stage decomposition yields a dramatic gain over direct prompting: GPT-3.5 without CheckEHR achieves only 10.12% recall and 8.75% precision, a roughly 6× improvement in recall from the framework. Few-shot examples help Tulu2 (12.08% → 44.95% recall) and Mixtral (0% → 54.70%) substantially, but Llama-3 shows almost no benefit (52.39% → 53.05%), and its nursing-note recall actually drops from 53.45% to 52.60%, suggesting difficulty generalizing from in-context examples on free-form text. On MIMIC-OMOP (Table 3, few-shot with gold entities), Llama-3 achieves the best precision (65.07%) while Tulu2 leads on recall (54.36%), and overall performance is comparable to or slightly below MIMIC-III, contrary to the authors' initial expectation that the simpler OMOP schema would be easier.

## Relation to Prior Work

This paper departs from the table-based fact verification line (TabFact, INFOTABS, FEVEROUS) in two fundamental ways: it operates on entire clinical notes rather than single claims, and it checks consistency between two potentially erroneous sources (notes and tables) rather than verifying a claim against a ground-truth table. The CONSISTENT/INCONSISTENT labeling scheme replaces the traditional SUPPORTED/REFUTED paradigm, reflecting the reality that neither EHR component is authoritative. Methodologically, CheckEHR draws on compositional reasoning and task decomposition techniques (StructGPT, KG-GPT) but applies them to a novel eight-stage pipeline that includes note segmentation, pseudo-table creation, and SQL generation against a large relational database.

## Why It Matters / Open Questions

EHR inconsistencies pose direct patient-safety risks (misdiagnosis, incorrect medication), yet no prior dataset or benchmark existed for automated consistency checking at the scale of real hospital databases. EHRCon's dual MIMIC-III/OMOP CDM versions and the CheckEHR framework establish a foundation for future work, though the modest best-case recall (61%) and the severe NER bottleneck highlight that LLMs still struggle with clinical text understanding. Key open questions include whether the inconsistencies found in preprocessed MIMIC-III reflect real hospital errors, how to scale annotation beyond 105 notes, and whether interactive database querying (rather than one-shot SQL generation) can close the gap to the 92.83% recall achieved with oracle intermediate steps.
