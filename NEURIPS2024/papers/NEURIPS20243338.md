## Problem

LLMs fail to generate syntactically valid programs for very low-resource programming languages (VLPLs) such as formal verification languages like UCLID5, where public training examples number in the hundreds rather than millions. Existing remedies—grammar-constrained prompting, constrained decoding, and cross-language fine-tuning—each make restrictive assumptions (context-free grammars, linear generation, general-purpose target languages) that do not hold for real VLPLs, leaving a gap in reliable text-to-code for these critical but underrepresented languages.

## Input / Output

The pipeline takes a natural-language task description and a textual description of the child language C (a constrained subset of a parent language like Python) as prompt inputs to the LLM. The LLM outputs a program in the parent language P, which is then repaired into a program in C (possibly containing '??' holes) and compiled via a syntax-directed translation to the target VLPL T. The repair loop iterates up to five times, each iteration feeding a partial program with holes back to the LLM for completion before the final compilation step.

## Method

SPEAC combines two ideas: (1) synthetic programming elicitation, a grounded-theory-inspired study where LLMs are the 'subjects'—they are prompted to write code using a hypothetical API in a popular host language, and their outputs are coded, grouped into concepts, and categorized to select a parent language P and child language C that match LLM generation tendencies; and (2) formal repair via MAX-SMT, where an error-tolerant parser builds an AST of the LLM output, an aggressive program slice prunes it to the largest consistent subtree in C, and a weighted MAX-SMT solver (solved with Z3) identifies the minimal set of AST nodes to replace with holes so all static checks of C pass. A satisfying model from the SMT solver then automatically fills resolvable holes (e.g., inferring variable types), while unresolvable holes are sent back to the LLM for iterative completion. This makes the approach complementary to prompting, decoding, and fine-tuning strategies, and the entire repair step runs in under 2 seconds on commodity hardware.

## Results

On 33 UCLID5 textbook benchmarks, Eudoxus (GPT3t) achieves an 84.8% parse rate (28/33), while Eudoxus (GPT4t) achieves 72.7% (24/33). The best baseline, three-shot prompting with GPT4t, parses only 4/33 (12.1%), and fine-tuned GPT3t parses only 2/33 (6.1%). Among Eudoxus outputs that pass compiler checks, 33/52 programs (24 unique problems) receive a semantic correctness score of 4 or higher on a 1–5 scale. MAX-SMT repair steps average 0.9 s (GPT3t) and 1.8 s (GPT4t), far cheaper than the 7.2 s and 35.1 s LLM call times respectively.

## Baselines & Comparisons

Eudoxus dominates all baselines on syntactic correctness by a wide margin: the best baseline (three-shot GPT4t) parses 4/33 benchmarks versus 28/33 for Eudoxus (GPT3t), a roughly 7× gap. Fine-tuning GPT3t on 317 UCLID5 regression tests yields only 2/33 parseable outputs, and self-repair with compiler feedback produces zero parseable outputs for both GPT3t and GPT4t. On semantic correctness, every unique problem where a baseline scored ≥4 was also solved by Eudoxus, suggesting Eudoxus does not sacrifice meaning for syntax. However, because so few baseline outputs even compile, direct semantic comparison is limited; Eudoxus achieves score ≥4 on 33 of its 52 parsed programs (24 unique problems), indicating most outputs are at least partially useful. The two Eudoxus variants together cover 30/33 unique problems with fully parseable code, whereas all 11 baseline variants combined cover only 6/33.

## Relation to Prior Work

SPEAC departs from the dominant text-to-code strategies for low-resource languages—constrained decoding (Agrawal et al., Wang et al.), cross-lingual fine-tuning (Cassano et al.), and iterative LLM self-repair (Chen et al., Olausson et al.)—by instead designing an intermediate 'parent' language that LLMs naturally produce, then using formal methods to repair and compile to the target. The repair mechanism directly adapts the MAX-SMT-based minimum type error source finding of Pavlinovic et al. [32], extending it from identifying error locations to actively generating satisfying models that fill in repaired code. The synthetic programming elicitation step borrows the grounded-theory methodology from natural programming elicitation studies (Myers et al. [29]) but repurposes it with LLMs as subjects rather than human programmers, making it a conceptual transplant from PL design to LLM interface design.

## Why It Matters / Open Questions

The approach offers a general recipe for any VLPL: identify what the LLM naturally produces, define a compilable subset, and use SMT-based repair to bridge the gap. This is particularly relevant for formal verification languages, domain-specific tools, and legacy systems where training data is scarce and direct generation fails. Key limitations include evaluation on a single VLPL (UCLID5), only two LLMs, and a single-author semantic assessment, leaving open whether the approach generalizes across domains and model families. The dramatic parse-rate gap (84.8% vs. 9–12%) suggests the intermediate-language paradigm could be a practical default for VLPL code generation, but broader validation is needed before it displaces fine-tuning or retrieval-based approaches in more data-rich settings.
