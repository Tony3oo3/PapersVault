## Problem

Recent LLM-based planning methods (ToT, RAP, LATS, ReAct, Reflexion, etc.) are neither sound nor complete, yet they remain prohibitively expensive, requiring hundreds of thousands of LLM evaluations per dataset. The paper identifies that abandoning soundness and completeness provides no efficiency benefit, and asks whether LLMs can be used for planning in a way that preserves both algorithmic correctness and computational efficiency.

## Input / Output

The method takes a natural-language description of a search problem domain (e.g., the rules of the 24 Game or the BlocksWorld domain) and produces two Python functions: a successor generator and a goal test. These functions are then plugged into a standard BFS or DFS implementation, which consumes concrete problem instances (e.g., four integers for the 24 Game, a 5×5 crossword grid, a block configuration, or a set of logical facts) and outputs a solution plan as a sequence of states or a proof as a sequence of applied reasoning rules. The LLM is queried only during the code-generation phase (a few interactions per component), not during the search itself.

## Method

The proposed approach, Thought of Search (ToS), inverts the standard paradigm: instead of calling an LLM at every state expansion and evaluation during search, it uses the LLM once per domain to generate Python implementations of the two critical search components — the successor function and the goal test. The process is iterative and user-guided: the user provides the problem description, the LLM produces code, the user validates correctness (checking soundness: all produced successors are valid; completeness: all possible successors are produced), and provides error feedback for corrections. Once validated, the generated functions are plugged into a standard BFS or DFS, which then runs without any further LLM calls, inheriting the soundness, completeness, and (for BFS) optimality guarantees of the underlying search algorithm. On four representative problems (24 Game, Mini Crosswords, BlocksWorld, PrOntoQA), this requires only 1–4 LLM interactions per component and achieves 100% accuracy across all instances, compared to 100K–1.7M LLM calls and 75–94% accuracy for the compared LLM-based search methods.

## Results

The proposed Thought of Search (ToS) approach achieves 100% accuracy on all four benchmark datasets (24 Game: 1362 instances, Mini Crosswords: 20 games, BlocksWorld: 502 instances, PrOntoQA: 4000 questions) using only 2–4 LLM calls per domain to generate the successor function and goal test code. Total solve times range from 0.56s (BlocksWorld) to 346s (Mini Crosswords), with the 24 Game solved in under 7s and PrOntoQA in under 3s. In contrast, the most expensive baselines (RAP, LATS) require 245K–1.68M LLM calls and are estimated to cost $14,000–$16,000, while achieving only 75–94% accuracy.

## Baselines & Comparisons

ToS dominates all nine baselines on both accuracy and efficiency. On the 24 Game, ToT [24] reports 75% accuracy with ~100 LLM calls per instance, while ToS achieves 100% with ~2.2 calls total for the entire 1362-instance dataset. On PrOntoQA, RAP [7] achieves 94.2% answer accuracy and 78.8% proof accuracy using MCTS with 20 iterations and 20 self-consistency samples (~1.44M LLM calls), whereas ToS achieves 100% on both with only ~2.6 calls. On BlocksWorld, LATS [28] requires ~562K calls and explores 388% of the state space (with redundant re-exploration), while ToS uses 3.8 calls and explores 125% (with duplicate detection). The simpler baselines (IO [21], CoT [22], ReAct [25], ReWOO [23]) use fewer calls but explore only 0.02–7.8% of the state space, making them fundamentally incapable of finding solutions in larger problems. GoT [1] and Reflexion [19] occupy intermediate positions but remain unsound and incomplete. The key distinction is that ToS inherits soundness, completeness, and (for BFS) optimality from the underlying search algorithm, a guarantee no LLM-at-every-step approach can provide.

## Relation to Prior Work

This paper departs sharply from the dominant paradigm of embedding LLMs as per-step search components (expansion, evaluation, heuristic) in algorithms like ToT, RAP, LATS, and ReAct. Instead, it repurposes the LLM as a one-time code generator for the symbolic search machinery (successor function and goal test), drawing conceptual inspiration from generalized planning with LLMs [20] and PDDL generation work [6, 16], but producing executable Python directly rather than a domain description. The approach is also related to LLM-based code generation for mathematical reasoning [29], but applied to search problem structure rather than arithmetic. By removing the LLM from the search loop entirely, the paper reclaims soundness, completeness, and (for BFS) optimality that all compared LLM-in-the-loop methods forfeit.

## Why It Matters / Open Questions

The paper makes a compelling case that the field's current direction—calling LLMs at every expansion and evaluation—is simultaneously unsound, incomplete, and orders of magnitude more expensive than necessary, with the efficiency gap reaching 1000×+ in LLM calls on the evaluated datasets. The open question of automating the code-generation loop (removing human feedback) is critical for practical adoption, as the current approach still requires a human to validate and debug the generated successor/goal functions. Scaling to larger state spaces will also require heuristic or pruning code generation, which the authors leave for future work. The broader implication is a reframing of where LLMs add value in planning: as a one-time symbolic modeler rather than a per-step oracle.
