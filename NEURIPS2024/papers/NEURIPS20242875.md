## Problem

While text-to-SQL semantic parsing is well-studied, the challenge of handling ambiguous questions has received limited attention. Existing benchmarks either cover only a single type of ambiguity (vagueness) or rely on artificial database modifications (e.g., duplicating tables with synonymous names) that produce unrealistic schemas. This paper addresses the gap by introducing a benchmark where ambiguity is a genuine linguistic phenomenon that persists even when full database context is provided.

## Input / Output

The model receives a natural language question (which may be ambiguous) along with the complete database schema and content rendered as CREATE TABLE and INSERT INTO SQLite statements. For ambiguous questions, the expected output is multiple SQL queries (2–3) corresponding to all valid interpretations, separated by empty lines; for unambiguous questions, exactly one SQL query is expected. Evaluation is execution-based: predicted queries are run against the database and their result sets are compared to gold result sets, so structurally different but semantically equivalent queries (e.g., JOIN vs. UNION formulations) are treated as correct.

## Method

The core contribution is a controlled, multi-step database generation pipeline that ensures each database structurally supports a specific ambiguity type: scope ambiguity requires a many-to-many relationship with a shared element, attachment ambiguity requires two entity classes sharing a common property, and vagueness requires a general entity that can refer to multiple specific subtypes. OpenChat-7B is used to generate key concepts/relations (filtered from 1,883 predictions down to 881) and then to produce executable CREATE TABLE and INSERT INTO statements across 16 domains, yielding 846 multi-table databases. Human annotators (via Prolific) write the ambiguous questions and natural-language interpretations, while SQL queries for scope and attachment ambiguity are generated from predefined templates and those for vagueness are written by SQL experts. For benchmarking, two prompting strategies are used: a Prompt method that explicitly instructs the model to output all interpretations, and a Beam method that collects top-5 predictions, with models ranging from OpenChat-7B to Llama3-70B and GPT-4o evaluated zero-shot and few-shot.

## Results

On AMBROSIA, the best-performing model, Llama3-70B (Prompt), achieves only 30.7% recall on ambiguous questions versus 64.5% on unambiguous ones, with an AllFound score of just 1.9% (i.e., it recovers all interpretations for fewer than 2% of ambiguous questions). GPT-4o attains the highest precision on ambiguous questions (51.1%) but still lags on recall (27.1%). Across all six LLMs tested, the gap between ambiguous and unambiguous recall ranges from 21% (OpenChat-7B) to 38% (Llama3-70B), and no model exceeds 2% AllFound, indicating that even state-of-the-art LLMs fundamentally struggle to recognize and enumerate multiple valid SQL interpretations.

## Baselines & Comparisons

As a dataset, AMBROSIA is compared to NoisySP (Wang et al., 2023) and AmbiQT (Bhaskar et al., 2023) in Table 1. Both prior datasets cover only vagueness (8,673 and 23,295 vague questions respectively), while AMBROSIA uniquely includes scope ambiguity (501 questions) and attachment ambiguity (362 questions) alongside vagueness (414 questions), and provides natural-language interpretations for every ambiguous question. AMBROSIA also uses multi-table databases (5.0 tables/DB on average, comparable to AmbiQT's 5.1) versus NoisySP's single-table databases (1.0 tables/DB). Among the LLMs benchmarked, Llama3-70B (Prompt) leads on recall for ambiguous questions (30.7%) and AllFound (1.9%), while GPT-4o leads on precision (51.1%); however, all models fail to reliably produce all valid interpretations, with the best AllFound being under 2%. Attachment ambiguity proves most challenging for all models (Llama3-70B recall drops to 12.7% ambiguous / 24.0% unambiguous), while scope ambiguity is easiest (41.5% / 90.4%).

## Relation to Prior Work

This paper extends the text-to-SQL semantic parsing task to explicitly handle linguistic ambiguity, building on prior work that has only partially addressed this challenge. NoisySP (Wang et al., 2023a) and AmbiQT (Bhaskar et al., 2023) introduced vagueness into existing benchmarks (WikiSQL, Spider) by modifying databases with synonymous names, but both are limited to single-table databases and one ambiguity type. AMBROSIA departs from this augmentation approach by using controlled LLM-based database generation to create multi-table databases that structurally support three distinct ambiguity types (scope, attachment, vagueness), and by providing human-written natural language interpretations alongside multiple gold SQL queries per ambiguous question. The formal definition of ambiguity (Definition 2) and the multi-interpretation evaluation protocol (recall, precision, AllFound) are novel contributions that go beyond the standard execution-accuracy metric used in prior text-to-SQL work.

## Why It Matters / Open Questions

The benchmark reveals a significant and consistent gap in LLM capabilities: even the strongest model (Llama 3-70B) achieves only 31% recall on ambiguous questions versus 66% on unambiguous ones, and the AllFound metric (capturing all interpretations) is below 2% across all models. This suggests that current LLMs, despite strong performance on standard text-to-SQL benchmarks, fundamentally struggle with recognizing and enumerating multiple valid interpretations—a critical capability for practical semantic parsing systems. Open questions include whether the findings generalize to larger, more realistic databases (the current setup displays full database content), whether the strong interpretation biases (e.g., 98% high-attachment preference) can be mitigated through training or prompting, and how to handle the scalability challenge when database content exceeds context limits.
