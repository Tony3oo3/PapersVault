## Problem

Existing Text-to-Query benchmarks evaluate systems on a single database model and query language (predominantly SQL), leaving the impact of database model choice—relational, document, or graph—on LLM-based query generation entirely unexplored. This gap is particularly acute in healthcare, where EHRs are increasingly stored across heterogeneous systems (PostgreSQL, MongoDB, Neo4j, RDF triple stores) but no benchmark enables cross-model comparison.
![Teaser figure](../imgs/NEURIPS20242811/cropped_page1_idx0.webp)

## Input / Output

The system takes a natural language question about synthetic medical records (e.g., patient allergies, medications, encounters) and optionally a database schema/ontology description plus 1–5 few-shot question-query examples, producing a single syntactically correct query in SQL, SPARQL, Cypher, or MQL. The benchmark comprises 10K question/query pairs per language (40K total) built from 408 manually authored templates augmented with parameterizable values (patient names, disease codes, IDs) sampled from the underlying database. Evaluation uses exact Execution Accuracy (EA) and Valid Efficiency Score (VES), with a 6K/2K/2K train/dev/test split stratified by entity type.

## Method

The benchmark is constructed in two stages: (1) synthetic patient data is generated via Synthea following the SNOMED-CT taxonomy and loaded into four database systems (PostgreSQL, MongoDB, Neo4j, GraphDB) through custom ETL pipelines that encode the same 18 entity types in relational, document, and graph schemas; (2) 408 template questions covering all entity types are manually paired with verified queries in all four languages, then automatically augmented with database-sampled values to scale to 10K pairs per language. For empirical evaluation, the authors implement five ICL prompting strategies (0/1/5-shot, with and without schema) across four LLMs (Llama3-8b, Llama3-70b, GPT-3.5-turbo, Gemini 1.0 Pro), and further test a BM25-based similarity retrieval that selects the five most relevant training examples per question, improving SQL accuracy from 56.3% to 88.55% and SPARQL from 30.5% to 75.75%.

## Results

On the SM3-Text-to-Query benchmark (10K questions per query language), the best standard ICL setting (w/ schema 5-shot) yields Execution Accuracy of 57.50% (SQL), 30.49% (SPARQL), 57.07% (Cypher), and 40.35% (MQL) for Llama3-70b, the top-performing model. With a BM25-based similarity retrieval for few-shot selection, accuracy improves substantially to 88.55% (SQL), 75.75% (SPARQL), 78.30% (Cypher), and 78.70% (MQL) using GPT-3.5. SQL consistently outperforms the other three query languages across all models and prompting strategies, while SPARQL shows the largest relative improvement from ICL (from <4% at 0-shot to ~30% at 5-shot, a 10-fold gain). Schema information more than doubles 5-shot accuracy for SQL, Cypher, and MQL but has minimal impact on SPARQL, suggesting LLMs already encode SNOMED-CT ontology knowledge from pre-training.

## Baselines & Comparisons

The paper evaluates four LLMs (Llama3-8b, Llama3-70b, GPT-3.5-turbo, Gemini 1.0 Pro) as baselines across five prompting strategies. Llama3-70b consistently achieves the highest EA across all four query languages in the w/ schema 5-shot setting (57.50% SQL, 30.49% SPARQL, 57.07% Cypher, 40.35% MQL), outperforming GPT-3.5 (56.30/23.58/41.12/35.06) and Gemini 1.0 Pro (49.32/26.32/53.84/30.65), while Llama3-8b trails significantly (27.49/4.27/34.89/11.33). The key finding is a large performance gap between SQL and the other languages: at 0-shot with schema, the best model reaches 47.05% for SQL but only 3.30% for SPARQL, correlating with Stack Overflow post frequency (673K SQL vs. 6K SPARQL posts). ICL via few-shot examples provides a 10-fold relative improvement for SPARQL (0-shot <4% → 5-shot ~30%) but only ~25% relative improvement for SQL (40% → 57%), confirming that LLMs are already proficient in SQL but genuinely learn from examples for less-represented query languages. The BM25-based similarity retrieval (Table 4) yields the largest absolute gains for SPARQL (+52.17 points) and MQL (+43.64 points) over fixed 5-shot, narrowing the cross-language gap but not eliminating it (SQL still leads at 88.55% vs. 75.75–78.70% for others).

## Relation to Prior Work

This paper extends the template-based Text-to-Query benchmarking approach established by EHRSQL, MIMICSQL, and MIMIC-SPARQL by generalizing from a single query language to four (SQL, SPARQL, Cypher, MQL) across three core database models (relational, document, graph). The closest prior work, FootballDB, analyzes schema dependency within a single relational database, while the ICL evaluation protocol follows standard prompting strategies from Nan et al. and the BM25-based few-shot selection is inspired by EHRXQA. The key conceptual departure is treating the database model itself as a first-class variable in Text-to-Query evaluation rather than an implementation detail, using SNOMED-CT-standardized synthetic data from Synthea to ensure cross-model comparability.

## Why It Matters / Open Questions

This benchmark is the first to enable systematic comparison of Text-to-Query systems across heterogeneous database models, revealing that LLM performance varies dramatically by query language (SQL ~47% vs. SPARQL ~3% at 0-shot with schema), a gap that persists even with advanced BM25-based ICL. The finding that schema information barely helps SPARQL (suggesting LLMs already encode the SNOMED ontology) while being critical for SQL/Cypher/MQL has practical implications for prompt design. Open questions include whether better schema encodings or ICL strategies can close the non-SQL gap, whether results generalize to real (non-synthetic) patient databases, and how multilingual and temporally complex queries would affect the cross-model comparison.
