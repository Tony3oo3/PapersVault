## Problem

Existing code generation benchmarks (HumanEval, MBPP, APPS) evaluate only functional correctness via test-case passing, completely overlooking code efficiency — yet two solutions can both pass all tests while differing by 50× in runtime. This gap means Code LLMs are never incentivized or measured on producing computationally efficient code, a critical dimension for real-world software productivity.
![Teaser figure](../imgs/NEURIPS20240529/cropped_page1_idx0.webp)

## Input / Output

Each Mercury task provides a natural-language problem description (pretty_content) and a code starter prompt (entry point) as input to the Code LLM, which must produce a complete Python solution. Evaluation runs the generated code in an isolated sandbox against a comprehensive set of test cases produced by a per-task GPT-4-generated test case generator (not a fixed handful), measuring both pass/fail correctness and wall-clock runtime. The Beyond metric then maps each solution's runtime to a percentile on a locally-constructed distribution of ~18 historical LeetCode solutions per task, yielding a single score in [0, 100] that jointly encodes correctness (failed cases score 0) and relative efficiency.

## Method

Mercury curates 1,889 Python tasks from LeetCode through three filters (≥2 unique solutions, restricted to built-in + two custom data structures, guaranteed unique outputs), split into 256 eval and 1,633 train tasks across Easy/Medium/Hard levels. The key metric, Beyond, normalizes absolute runtime into a percentile against each task's historical-solution runtime distribution, making scores environment-agnostic and comparable across hardware. For empirical baselines, the paper fine-tunes 10 open-source Code LLMs (1.3B–34B) via LoRA using either SFT on the fastest solution or DPO on top-5 fast/slow solution pairs, with DPO showing consistent efficiency gains (up to +21.5 Beyond for CodeLlama-34b) while preserving or improving Pass scores, whereas SFT often degrades both metrics due to catastrophic forgetting.

## Results

On Mercury, leading Code LLMs achieve approximately 65% on Pass (functional correctness) but less than 50% on Beyond (code efficiency), revealing a significant efficiency gap. After DPO fine-tuning, deepseek-coder-33b-base reaches the highest Beyond score of 66.47 (+17.94 over vanilla) and CodeLlama-34b-hf reaches 63.94 (+21.54), while SFT generally detracts from Beyond scores across most models. The Gap between Beyond and Pass shrinks substantially under DPO for larger models (e.g., deepseek-coder-33b: 18.50 → 5.79), indicating that DPO effectively narrows the efficiency-correctness tradeoff.

## Baselines & Comparisons

The paper compares two fine-tuning strategies—SFT and DPO—against the original (vanilla) models across 10 open-source Code LLMs (1.3B–34B parameters). DPO consistently outperforms SFT on the Beyond (efficiency) metric for models exceeding 6.7B parameters: deepseek-coder-33b-base gains +17.94 Beyond with DPO versus −10.21 with SFT, and CodeLlama-34b-hf gains +21.54 with DPO versus −5.50 with SFT. On functional correctness (Pass), DPO also generally preserves or improves scores (e.g., CodeLlama-34b-hf: 52.4 → 70.6 with DPO), while SFT causes catastrophic forgetting on the two largest models (deepseek-coder-33b: 65.0 → 58.7; CodeLlama-34b: 52.4 → 47.5). For smaller models (<7B), both SFT and DPO show mixed or negative effects on Beyond, suggesting insufficient capacity to absorb efficiency knowledge without degrading correctness. The Gap between Beyond and Pass narrows most dramatically under DPO for large models (e.g., deepseek-coder-33b: 18.50 → 5.79), confirming DPO as the more robust strategy for jointly improving efficiency and correctness.

## Relation to Prior Work

This paper departs from the dominant NL2Code benchmarking tradition (HumanEval, MBPP, APPS, EvalPlus), which evaluates generated code solely on functional correctness via test-case fuzzing, by introducing code efficiency as a first-class evaluation axis. It also distinguishes itself from prior software-engineering efficiency benchmarks (EFFIBENCH, SUPERSONIC, DeepPERF) that measure relative speedup between two solutions, instead proposing the Beyond metric that normalizes runtime against a per-task distribution of historical solutions. The empirical baselines draw on the DPO preference-learning framework and LoRA-based fine-tuning, positioning the work at the intersection of code generation evaluation and LLM alignment.

## Why It Matters / Open Questions

By quantifying the gap between functional correctness (~65% Pass) and efficiency (<50% Beyond) across leading Code LLMs, the paper reveals a substantial and previously unmeasured efficiency deficit that matters for real-world deployment where runtime directly affects cost and user experience. The finding that DPO consistently improves efficiency while preserving correctness—while SFT often degrades both—provides a practical recipe for practitioners. Open questions include whether the uniform-distribution assumption in Beyond holds for more complex tasks, whether the approach generalizes beyond Python, and whether the efficiency gap can be closed further with more sophisticated alignment strategies.
