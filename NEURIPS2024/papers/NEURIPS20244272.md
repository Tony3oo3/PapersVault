## Problem

No benchmark exists to quantitatively evaluate LLMs' ability to generate Infrastructure-as-Code (IaC) programs, despite IaC being the standard for cloud infrastructure development. General code generation benchmarks (HumanEval, EvalPlus) target imperative languages like Python, while IaC programs in Terraform HCL involve domain-specific cloud services, complex resource interdependencies, and provider-specific rules that are largely absent from public training data. This leaves it unknown whether state-of-the-art code LLMs can produce correct, intent-fulfilling cloud infrastructure configurations.

## Input / Output

Each of the 458 dataset scenarios provides a natural language prompt (e.g., 'Set up an AWS Aurora cluster with a proxy...') as the sole user input to the LLM, which must produce a complete, deployable Terraform HCL configuration. The generated program is then consumed by a two-phase pipeline: first by `terraform plan` to produce a dependency graph, then by OPA matching against a human-written Rego intent specification (averaging 37.5 LOC, up to 205 LOC) that encodes valid resources, optional attribute ranges, and required attribute constraints. The final output is a binary pass/fail verdict per generated program, aggregated into pass@k scores over 20 samples per problem.

## Method

IaC-Eval introduces a compile-time-only evaluation pipeline that avoids costly cloud deployment: Phase 1 runs `terraform plan` on the LLM-generated HCL to validate syntax and basic provider constraints, producing a dependency graph; Phase 2 matches this graph against OPA Rego intent specifications using the OPA policy engine, repurposing a standard IaC compliance tool to verify user-intent fulfillment. The 458-scenario dataset spans 10+ AWS service categories (compute, databases, networking, storage, security, streaming) with difficulty levels automatically computed from lines of code, resource count, and interconnection count (ranging from <10 LOC single-resource configs to 280 LOC with 24 resources and 33 interconnections). Intent specifications are crafted by domain experts to resolve ambiguity (e.g., 'AWS Database' could mean RDS, DynamoDB, or Aurora) by explicitly constraining which resources, attribute values, and interconnections are acceptable. The paper evaluates 8 LLMs (GPT-4, WizardCoder-33B, CodeLlama variants, etc.) and tests four enhancement strategies—few-shot prompting, chain-of-thought, multi-turn repair with compiler feedback, and retrieval-augmented generation over Terraform documentation—finding that RAG yields the largest average improvement (+6.14%) while few-shot and CoT can actually degrade performance.

## Results

On IaC-Eval (458 AWS Terraform scenarios), GPT-4 achieves the highest pass@1 accuracy at 19.36%, followed by WizardCoder-33B-V1.1 (8.93%) and GPT-3.5-turbo (7.99%), while the weakest model, CodeLlama Instruct (7B), scores only 1.97%. In stark contrast, the same GPT-4 model scores 86.6% on the EvalPlus Python code generation benchmark, underscoring the substantial difficulty of IaC code generation. Intent specifications in the two-phase evaluation pipeline remove approximately 50% of false positives that pass Terraform compilation but fail to satisfy user intent.

## Baselines & Comparisons

The paper compares IaC-Eval's functional correctness metric against three existing evaluation approaches: BLEU, CodeBERTScore, and LLM-as-a-judge (GPT-4). All three baselines show a downward trend in scores consistent with IaC-Eval rankings, but none can effectively differentiate correct from incorrect solutions. BLEU assigns similar scores to correct and incorrect programs with an average difference of only 8.3%, and CodeBERTScore shows an even smaller gap of 6.9%. The LLM-judge (GPT-4) performs worst, with precision hovering between 10% and 30%, meaning incorrect solutions are frequently misclassified as correct. IaC-Eval's two-phase pipeline (Terraform plan + OPA Rego intent matching) thus provides a substantially more reliable correctness signal than any of the three text-similarity or LLM-judge baselines.

## Relation to Prior Work

This paper carves new ground by introducing the first benchmark for evaluating LLM-generated Infrastructure-as-Code (IaC) programs, a domain entirely absent from existing code generation benchmarks (HumanEval, EvalPlus, MBPP) that target general-purpose languages. It repurposes two existing tools in novel ways: Terraform's native `terraform plan` command for compile-time validation without deployment, and the OPA/Rego policy engine (typically used for security/compliance) as an intent-verification mechanism. The closest prior work, CloudEval-YAML, evaluates simpler YAML configurations for Kubernetes/Envoy/Istio, whereas IaC-Eval targets the far more complex Terraform HCL language with multi-service, multi-resource dependency graphs. The evaluation methodology inherits the pass@k framework from HumanEval but replaces unit-test-based correctness with human-crafted infrastructure intent specifications.

## Why It Matters / Open Questions

The stark performance gap (GPT-4: 19.36% on IaC-Eval vs. 86.6% on EvalPlus) reveals that current LLMs are far from capable of generating production-ready cloud infrastructure code, with critical implications for the growing ecosystem of AI-assisted IaC tools (Pulumi AI, Firefly, InfraCopilot). The benchmark is practically important as IaC is the standard paradigm for cloud infrastructure management, and 92% of enterprises maintain dedicated cloud engineering teams. Key limitations include AWS-only and Terraform-only coverage, no function generation, and the subjective difficulty-level system. Open questions include whether automated intent synthesis can scale the dataset, whether security-awareness can be incorporated into evaluation, and whether the findings generalize to other IaC frameworks (CloudFormation, Pulumi) and cloud providers (Azure, GCP).
