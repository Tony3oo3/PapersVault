## Problem

Traditional dataflow analysis techniques rely on compiler-generated intermediate representations (e.g., LLVM IR), making them inapplicable to incomplete or uncompilable programs, and require expert-level customization of sources and sinks for each analysis task. While LLMs show strong code comprehension, their hallucinations—misidentifying sources/sinks, fabricating dataflow facts, and failing to reason about path feasibility—make them unreliable for precise dataflow analysis without targeted mitigation strategies.

## Input / Output

LLMDFA consumes raw source code (no compilation or IR required), a control flow graph, and a natural-language specification describing the forms of sources and sinks relevant to the target bug type. It produces intra-procedural dataflow summaries (pairs of variable-line references indicating value dependence), which are stitched into inter-procedural dataflow paths, and ultimately path-validated bug reports. The source/sink specification is expressed in plain English with example programs, eliminating the need for users to understand program representations like LLVM IR or write formal queries.

## Method

LLMDFA decomposes dataflow analysis into three phases, each designed to outsource a specific class of reasoning to a more reliable mechanism. In Phase I (Source/Sink Extraction), LLMs iteratively synthesize Python scripts that traverse the AST via tree-sitter to deterministically identify sources and sinks, with a fix loop that feeds execution errors back until the script correctly labels all example programs. In Phase II (Dataflow Summarization), a few-shot chain-of-thought prompt—containing short examples with step-by-step explanations of typical dataflow patterns (direct uses, assignments, pointer loads/stores)—guides the LLM to reason about intra-procedural value flow within a single function, keeping prompts short and aligned with program semantics. In Phase III (Path Feasibility Validation), LLMs synthesize Python scripts that encode the collected path conditions as Z3 SMT solver constraints, decoupling logical satisfiability checking from the LLM's own reasoning. This tool-synthesis-plus-CoT design targets each hallucination mode separately: deterministic parsing for extraction, semantic alignment for summarization, and formal verification for path feasibility.

## Results

On the Juliet Test Suite (Java), LLMDFA with gpt-3.5 achieves 73.75%/92.16% precision/recall (F1=0.82) for DBZ, 100%/92.31% (F1=0.96) for XSS, and 100%/78.38% (F1=0.88) for OSCI detection, averaging 87.10% precision and 80.77% recall. On real-world Android malware (TaintBench), LLMDFA reaches 75.38% precision and 61.25% recall (F1=0.67). On the JavaScript benchmark SecBench.js, it achieves 92.52% precision and 71.74% recall (F1=0.81), and on Juliet C/C++ it obtains F1 scores of 84.77% (DBZ), 92.92% (APT), and 83.98% (OSCI).

## Baselines & Comparisons

Against CodeFuseQuery (a compilation-free AST-based analyzer), LLMDFA improves average F1 by 0.23: it dramatically outperforms CodeFuseQuery on DBZ (F1 0.82 vs. 0.43, driven by CodeFuseQuery's path-insensitive analysis yielding only 29.41% precision) and OSCI (F1 0.88 vs. 0.67, where CodeFuseQuery's inability to handle global variables causes low recall of 54.05%), while matching or exceeding it on XSS (F1 0.96 vs. 0.86). Against Pinpoint (a compilation-dependent LLVM-IR-based analyzer), LLMDFA improves average F1 by 0.23 as well: Pinpoint achieves high precision (93.78–100%) but very low recall (31.35–63.19%) due to missing customized source/sink support, whereas LLMDFA balances both (e.g., DBZ: 73.75% P / 92.16% R vs. Pinpoint's 93.78% P / 63.19% R). On TaintBench, LLMDFA (F1=0.67) outperforms CodeFuseQuery (F1=0.55) by 0.12 and the LLM-based end-to-end baseline (F1=0.32) by 0.35, with the end-to-end approach suffering from incorrect source/sink identification (43.48% precision) and the inability to handle lengthy prompts in large programs.

## Relation to Prior Work

This paper departs from the classical dataflow analysis lineage (SVF, Klee, Pinpoint, CodeFuseQuery) that depends on compiler-generated IRs and expert customization, and from ML-based bug detectors that require large training datasets. Rather than using LLMs as direct semantic reasoners (as in prior LLM-for-invariants or LLM-for-repair work), LLMDFA repurposes LLMs as code synthesizers that generate scripts delegating delicate reasoning to external expert tools (tree-sitter for AST traversal, Z3 for SMT solving). The few-shot CoT prompting for intra-procedural dataflow summarization is a novel application of chain-of-thought to align LLMs with program semantics at the granularity of single functions, a subtask not previously isolated in the dataflow analysis literature.

## Why It Matters / Open Questions

LLMDFA demonstrates that compilation-free, customizable dataflow analysis is feasible with current LLMs, opening the door to on-the-fly analysis in IDEs and for incomplete programs where classical tools fail. Key limitations remain: path condition encoding can be incorrect for library functions, user-defined functions, and global variables; dataflow summarization degrades on large or pointer-heavy functions; and the token cost limits whole-program analysis. The decomposition-then-delegate strategy (LLM synthesizes tool code rather than reasoning directly) is a generalizable pattern that could extend to program verification, slicing, and repair, but its scalability and soundness guarantees remain open questions.
