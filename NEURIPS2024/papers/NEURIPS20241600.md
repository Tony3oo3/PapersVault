## Problem

LM agents tasked with software engineering typically interact with computers through human-oriented interfaces like the Linux shell, which are poorly suited to LMs' limitations: they lack visual understanding for GUIs, cannot flexibly ignore irrelevant context, and struggle with the granular, highly configurable action spaces of standard tools. This paper asks whether purpose-built agent-computer interfaces (ACIs) that account for these LM-specific characteristics can substantially improve agent performance on real-world software engineering tasks without modifying the underlying model.

## Input / Output

The system takes a natural-language GitHub issue description and a full Python repository as input, and produces a unified diff patch that must pass all existing unit tests to be considered resolved. The agent operates in a ReAct-style loop (thought + command per turn) within a Docker container, with a per-instance API cost budget of $4. The file viewer presents at most 100 lines at a time with line numbers, search results are capped at 50 entries, and the agent's message history is managed by collapsing observations older than the last 5 turns into single-line summaries to control context length.

## Method

SWE-agent introduces the Agent-Computer Interface (ACI), a curated abstraction layer between the LM and the Linux shell that replaces the shell's granular command space with a small set of high-level, LM-friendly actions. The ACI comprises four components: (1) an interactive file viewer with line-numbered windows and scroll/goto navigation; (2) a single-command file editor that replaces a line range in the open file and auto-refreshes the viewer, with an integrated flake8 linter that rejects edits introducing syntax errors and returns a detailed before/after error message; (3) summarized search commands (find_file, search_file, search_dir) that cap results at 50 and suggest more specific queries when exceeded; and (4) a context management system that collapses stale observations and provides informative no-output messages. The design follows four principles derived from HCI-inspired analysis: actions should be simple and few, operations should be consolidated into single steps, feedback should be informative but concise, and guardrails should mitigate error propagation. Ablations on SWE-bench Lite show the ACI yields a 10.7-percentage-point improvement over a shell-only baseline, with the file editor, summarized search, and linting guardrails each contributing several points.

## Results

SWE-agent with GPT-4 Turbo achieves 12.47% pass@1 on the full SWE-bench test set (286/2,294 instances) and 18.00% on SWE-bench Lite (54/300), with an average cost of $1.59 per resolved instance. On HumanEvalFix, SWE-agent w/ GPT-4 Turbo reaches 87.7% pass@1 on Python, 89.7% on JavaScript, and 87.9% on Java. With Claude 3 Opus as the base LM, SWE-agent still resolves 10.46% of full SWE-bench and 13.00% of SWE-bench Lite, demonstrating portability across models.

## Baselines & Comparisons

Against the RAG baseline from Jimenez et al. [20], SWE-agent w/ GPT-4 Turbo improves % Resolved from 1.31% to 12.47% on full SWE-bench (≈9.5×) and from 2.67% to 18.00% on SWE-bench Lite (≈6.7×), at roughly 8–13× the inference cost. Against the Shell-only interactive baseline adapted from InterCode [59], SWE-agent w/ GPT-4 Turbo achieves 18.00% vs. 11.00% on SWE-bench Lite, a 64% relative improvement, confirming that the custom ACI outperforms the default Linux shell as an agent interface. On HumanEvalFix, SWE-agent w/ GPT-4 Turbo (87.7% Python) substantially outperforms the strongest non-agent baseline, WaveCoder-DS-6.7B (57.9%), by nearly 30 percentage points, and also surpasses GPT-4's non-interactive score of 47.0%. The paper also shows that removing the demonstration from the Shell-only setting drops performance from 11.00% to 7.33%, highlighting the sensitivity of interactive agents to in-context guidance.

## Relation to Prior Work

This paper builds on the interactive coding paradigm of InterCode (Yang et al., 2023) and the ReAct thought-action loop (Yao et al., 2023), but introduces a fundamentally new design abstraction: the Agent-Computer Interface (ACI). Prior LM agent work treated existing human-oriented interfaces (Linux shell, Python REPL) as fixed substrates, whereas this paper argues that LM agents constitute a new user category requiring purpose-built interfaces, drawing explicitly on HCI design principles. The contribution unifies tool use, prompting, and code execution within a single ACI framework rather than treating them as orthogonal concerns, and demonstrates through ablation that interface design choices (search format, edit granularity, linting guardrails, context management) are first-order determinants of agent performance independent of the underlying model.

## Why It Matters / Open Questions

The ACI concept provides a generalizable design vocabulary for building LM agents across domains, and the finding that interface design alone (without weight modification) yields a 64% relative improvement over a shell-only baseline shifts the field's focus from purely scaling models to co-designing the agent-environment boundary. Key limitations include the still-low absolute resolution rate (12.47% on SWE-bench), evaluation restricted to two frontier LMs with large context windows, and the observation that most remaining failures are incorrect implementations rather than interface failures—suggesting a model-capability ceiling that ACI design alone cannot overcome. Open questions include whether ACI design principles transfer to non-software domains, whether the approach benefits smaller models with limited context, and how to address the dominant failure mode of functionally incorrect (but syntactically valid) fixes.
