## Problem

Prior work on LLM-based DS code generation assumes that models implicitly learn the numeric parameter constraints of DS library APIs (e.g., in_channels % groups = 0 for Conv2d) through massive training, yet this assumption has never been rigorously verified. Existing DS benchmarks like DS-1000 focus on task-level correctness rather than whether models genuinely understand the underlying numerical constraints. This paper asks whether LLMs truly comprehend these constraints or merely memorize common usage patterns from training data.

## Input / Output

The evaluation operates at three granularities: full program synthesis (LLM generates everything from a 3-step instruction), all-parameter completion (concrete input tensor shape is given, LLM fills all API parameters), and single-parameter prediction (LLM fills one specific parameter, sometimes with additional partial values provided to increase difficulty). Inputs are structured as Python code snippets with the target parameter left as a blank to infill; outputs are extracted parameter values or complete programs. Validation is performed via SMT solvers (Z3) that check whether the generated values satisfy the encoded constraint formulas, rather than by executing the generated code, enabling fast and deterministic correctness checking.

## Method

The paper constructs an empirical evaluation framework over 28 representative APIs from PyTorch and NumPy, categorizing their numeric constraints into four types: equality, inequality, arithmetic, and set-related. Difficulty is systematically scaled by increasing tensor rank (2–8) or dimension value ranges (up to [128, 256)), with SMT solvers (Z3) used both to generate valid problem inputs and to validate LLM outputs, avoiding costly execution-based evaluation. Eight LLMs (GPT-4-Turbo, DeepSeek Coder 33b/6.7b/1.3b, CodeLlama 13b/7b, StarCoder 15b, CodeQwen1.5 7b) are evaluated across all three settings, with additional experiments probing chain-of-thought, ReAct, and documentation-augmented prompting strategies. The authors release DSEVAL, a 19,600-problem benchmark spanning 12 APIs and 7 difficulty levels, which supports lightweight SMT-based verification for fast model comparison.

## Results

On the DSEVAL benchmark (19,600 problems across 12 APIs), GPT-4-Turbo consistently achieves the highest accuracy across all difficulty levels: 77.2% (Easy), 66.2% (Medium), and 57.5% (Hard) on PyTorch, and 95.3%, 85.1%, and 71.4% on NumPy. The best open-source model, StarCoder-15b, reaches only 65.6%, 46.3%, and 39.2% on PyTorch (a 18.3-point gap on Hard), while DeepSeek Coder-33b achieves 64.7%, 41.5%, and 28.2%. All models show a steep accuracy drop as difficulty increases, with even GPT-4-Turbo falling below 60% on the hardest PyTorch constraints, confirming that LLMs largely memorize common patterns rather than genuinely understanding numeric API constraints.

## Baselines & Comparisons

GPT-4-Turbo dominates all open-source models across every difficulty level and both libraries, with the gap widening on harder problems (e.g., 57.5% vs. 39.2% on PyTorch Hard, a 18.3-point margin over the best open-source model StarCoder-15b). Among open-source models, StarCoder-15b is the strongest on PyTorch (39.2% Hard) while DeepSeek Coder-33b leads on NumPy (48.8% Hard), but both trail GPT-4-Turbo by 18–20 points on the hardest settings. CodeQwen1.5-7b is notable for achieving the second-best Easy accuracy on PyTorch (67.5%) and the highest diversity score (53.2), yet it collapses to near-worst performance on Medium and Hard PyTorch problems (33.2% and 25.2%), revealing poor generalization to more complex constraints. DeepSeek Coder-33b, the largest open-source model tested, still lags GPT-4-Turbo by 18.7 points on PyTorch Hard (28.2% vs. 57.5%) and by 22.6 points on NumPy Hard (48.8% vs. 71.4%), underscoring a substantial capability gap between proprietary and open-source LLMs on numeric constraint reasoning.

## Relation to Prior Work

This paper builds on the NNSmith constraint-encoding framework and SMT-based validation (Z3) to isolate and systematically evaluate a specific dimension of DS code generation that prior benchmarks (DS-1000, ARCADE, HumanEval) have not addressed: whether LLMs genuinely understand numeric parameter constraints in DS library APIs. It departs from the implicit assumption in prior LLM-for-DS-code work (e.g., Deng et al. 2023 on fuzzing, Lai et al. 2023 on DS-1000) that massive pre-training on correct API usage suffices to internalize these constraints. The paper also connects to the ML library testing/fuzzing literature by reusing formal constraint encodings, but repurposes them as an evaluation harness for LLMs rather than as a test-generation tool.

## Why It Matters / Open Questions

The finding that LLMs memorize common input patterns (e.g., 3×224×224 from ImageNet) rather than reasoning about constraints has direct practical implications for DS code assistants, automated fuzzing, and vulnerability detection that rely on LLM-generated DS programs. DSEVAL (19,600 problems) provides the first systematic, fast (SMT-based, no execution) benchmark for this capability and is extensible to other libraries. Key limitations include coverage of only 28 APIs across two libraries, single-API-call programs, and numeric-only constraints; open questions include whether fine-tuning, retrieval-augmented generation, or multi-step reasoning can close the gap, and whether findings generalize to non-numeric constraints or multi-API pipelines.
