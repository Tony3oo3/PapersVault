## Problem

Existing code generation benchmarks (HumanEval, MBPP, APPS, DS-1000) focus almost exclusively on correctness, leaving the efficiency of LLM-generated code largely unexamined. This is a critical gap because code efficiency directly impacts execution speed, memory consumption, energy use, and sustainability—especially in resource-constrained environments. EFFIBENCH fills this gap by providing a dedicated benchmark of 1,000 efficiency-critical coding problems with optimal human-written baselines for measuring how far LLM-generated code falls short in time and memory performance.

## Input / Output

The benchmark feeds natural-language coding problem descriptions (sourced from LeetCode, averaging 212 words) to LLMs, which produce Python function implementations. Each generated solution is then executed against a suite of 100 auto-generated test cases (varying in input size, data distribution, and edge cases) produced by a dedicated test case generator, and its runtime and memory profile are compared against an executable canonical solution that achieved the top efficiency rating on LeetCode's leaderboard. The output is a set of six metrics—absolute and normalized execution time (ET/NET), max memory usage (MU/NMU), and total memory usage (TMU/NTMU)—where normalized values >1 indicate the generated code is less efficient than the canonical baseline.

## Method

EFFIBENCH is constructed in three stages: (1) collecting 2,605 LeetCode problems from HuggingFace, filtering to 1,146 with recognized algorithm tags (greedy, DP, backtracking, DFS, BFS, binary search, two pointers, sliding window, bit manipulation, sorting, divide-and-conquer), and further narrowing to 1,000 problems that have an executable canonical solution; (2) sourcing canonical solutions from top-starred LeetCode discussion posts and manually fixing them for standalone executability (adding missing imports like TreeNode, ListNode, bisect); and (3) building a per-problem test case generator (prompted via GPT-3.5-turbo) that produces diverse inputs across sizes and distributions to stress-test efficiency. The evaluation protocol first filters to only correctly generated code (passing all test cases), then measures six efficiency metrics under a fixed 10-second timeout on a standardized server (Intel Xeon Platinum 8336C, 8×A100). The key empirical finding is that even the best-performing models (GPT-4, StarCoder2-15B) produce code with 2.6–3.1× the execution time and 4.8–6.4× the total memory usage of canonical solutions, and that higher pass@1 does not correlate with better efficiency.

## Results

Across 42 LLMs evaluated on EFFIBENCH (1,000 LeetCode problems), all models generate code less efficient than human-written canonical solutions. GPT-4 achieves the best closed-source efficiency with a mean Normalized Execution Time (NET) of 3.12× and Normalized Total Memory Usage (NTMU) of 6.36×, while in the worst case its code runs 13.89× slower and uses 43.92× more total memory than the canonical solution. Among open-source models, StarCoder2-15B is the most efficient (NET 2.59×, NMU 1.71×, NTMU 4.83×), yet still substantially behind the canonical baseline. Notably, higher pass@1 does not correlate with better efficiency: GPT-4-turbo-preview (pass@1 65.4%) is less efficient than GPT-4 (pass@1 50.8%) on both NET (3.19 vs 3.12) and NTMU (6.57 vs 6.36).

## Baselines & Comparisons

All 42 evaluated LLMs underperform the human-written canonical solutions on every efficiency metric, with NET ranging from 2.59× (StarCoder2-15B) to 3.40× (GPT-3.5-turbo-1106). Among closed-source models, GPT-4 (NET 3.12, NTMU 6.36) outperforms GPT-4-turbo-preview (NET 3.19, NTMU 6.57) and both Claude-3 variants (NET 3.22–3.28), despite GPT-4-turbo-preview having the highest pass@1 (65.4%). Within the GPT-3.5-turbo family, efficiency degrades across versions: NET increases from 3.18 (0301) to 3.40 (1106) while pass@1 rises from 42.3% to 49.3%, indicating that correctness improvements do not translate to efficiency gains. Among open-source models, StarCoder2-15B leads on NET (2.59), NMU (1.71), and NTMU (4.83), outperforming CodeLlama-13b-hf (NET 2.71), DeepSeek-Coder-1.3B-instruct (NET 2.82), StarCoder-base (NET 2.80), and WizardCoder-15B (NET 2.84). On the 210 problems correctly solved by all closed-source models (Table 4), GPT-4 again achieves the best NET (3.06) and NTMU (6.17), confirming its efficiency advantage is not an artifact of differing problem subsets. The worst-case analysis (Section 5.4) shows that inefficiency is concentrated in dynamic programming and backtracking problems, where GPT-3.5-turbo-0301 generates O(n×k) matrix-based DP solutions instead of the O(k) rolling-array approach used by canonical solutions, yielding up to 70.62× memory overhead.

## Relation to Prior Work

This paper carves new ground by introducing the first benchmark dedicated to evaluating the *efficiency* (execution time and memory usage) of LLM-generated code, rather than its correctness. It draws on the canonical-solution paradigm from DS-1000 (top-starred Stack Overflow answers) but adapts it to LeetCode's algorithmic problem set, where optimal solutions are well-defined and leaderboard-ranked. Existing code generation benchmarks (HumanEval, MBPP, APPS) are positioned as inadequate for efficiency assessment because their tasks are too simple and not inherently efficiency-critical. The paper also builds on recent observations [40, 46] that LLM code is less efficient than human code, but provides the first systematic, large-scale (42 models, 1,000 problems) quantification with normalized metrics.

## Why It Matters / Open Questions

EFFIBENCH provides the first standardized framework and public leaderboard for measuring code efficiency, connecting code generation research to green computing and sustainability goals. The finding that even GPT-4's code is on average 3.12× slower and 6.36× more memory-hungry than optimal human solutions, with extreme cases reaching 43.92× memory overhead, quantifies a gap that was previously only anecdotally noted. Key limitations include Python-only scope, LeetCode-only problem types (algorithmic rather than real-world), and environment-dependent absolute metrics. Open questions include whether efficiency can be improved through targeted training or prompting, whether the findings generalize to other languages and real-world codebases, and how to balance correctness and efficiency in model optimization.
