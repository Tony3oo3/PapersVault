## Problem

LLM-based code transpilation lacks formal correctness guarantees, while existing verified lifting tools require 1000+ lines of domain-specific heuristics and DSL-specific training data to build, making them hard to generalize to new DSLs. This paper asks whether LLMs can serve as the synthesis engine in verified lifting, producing formally verified transpiled code with dramatically less human effort.
![Teaser figure](../imgs/NEURIPS20241310/cropped_page3_idx0.webp)

## Input / Output

The method takes a side-effect-free source program (C++, Java, or C; no pointers or objects) and the semantics of target DSL operators defined as recursive Python functions (the IR). It produces a verified program summary (a composition of DSL operators in Python IR), corresponding loop invariants (templated as index bounds conjoined with an inductive expression over DSL operators), the transpiled concrete DSL code, and a machine-checked proof of functional equivalence via an SMT solver. The PS and invariants are generated in Python rather than SMT-LIB or the target DSL syntax, since Python is well-represented in LLM training data and amenable to syntax-driven parsing.

## Method

LLMLIFT instantiates Oracle-Guided Inductive Synthesis (OGIS) with LLM oracles, using Python as an intermediate representation to decouple code generation from the target DSL's concrete syntax. The approach is two-phase: first, the LLM is prompted zero-shot to generate a program summary (PS) as a composition of DSL operators; second, it is prompted one-shot to generate loop invariants conditioned on the already-generated PS. A rule-based parser rejects candidates using constructs outside the defined IR, and the surviving PS–invariant pairs are translated to SMT solver syntax and checked for functional equivalence using Floyd-Hoare Logic (initial condition, preservation, termination). Once verified, the PS is translated to the target DSL's concrete syntax via simple pattern-matching rewrite rules. This eliminates the need for DSL-specific search-space grammars, fine-tuning, or domain-specific heuristics that traditional symbolic verified lifting tools require.

## Results

Across four DSL domains, LLMLIFT matches or exceeds all prior verified-lifting baselines in both benchmark coverage and solving speed. On TACO, LLMLIFT solves all 60/60 benchmarks (vs. C2TACO's 57/60) with an average solving time of 2 s versus C2TACO's 41 s. On Spark (distributed computing), LLMLIFT solves 44/45 benchmarks in under 1 minute on average, compared to MetaLift's 40/45 in 3 minutes. Across all domains, LLMLIFT requires roughly 1000× less human effort (~70–320 lines of prompt vs. 1000–1200+ LoC of search-space heuristics) while being ~6× faster on average.

## Baselines & Comparisons

Against MetaLift [25] (symbolic solver using Rosette), LLMLIFT wins on Spark by solving 4 additional benchmarks (44/45 vs. 40/45) and is ~3× faster (<1 min vs. 3 min average); on Domino (network packet processing) both solve all 10 benchmarks but LLMLIFT is 3× faster (2 s vs. 6 s average). Against C2TACO [6] (enumerative synthesis for tensor code), LLMLIFT solves 3 more benchmarks (60/60 vs. 57/60) and is ~20× faster (2 s vs. 41 s average); C2TACO fails on expressions of depth >4 even with a 1-day timeout. Against Tenspiler [24] (verified lifting for tensor IR), both solve all 23 benchmarks, but LLMLIFT is ~20% faster (95.89 s vs. 115.14 s) and, critically, Tenspiler without its three domain-specific optimizations drops to only 5/23, whereas LLMLIFT requires no such heuristics. In every comparison, LLMLIFT also reduces the engineering effort by roughly an order of magnitude (tens-to-hundreds of prompt lines vs. 1000+ LoC of hand-crafted search-space descriptions).

## Relation to Prior Work

This paper instantiates the Oracle-Guided Inductive Synthesis (OGIS) framework [18,19] with LLM oracles, replacing the traditional symbolic or neural 'learner' in verified lifting with a prompted language model. It departs from prior verified lifting tools (MetaLift, C2TACO, Tenspiler) by eliminating the need for hand-crafted search-space grammars and domain-specific heuristics, instead using Python as a universal IR that leverages LLMs' existing code-generation competence. The approach also extends prior LLM-for-verification work (which typically generates invariants or proofs in isolation) by jointly generating both the transpiled program and its correctness proof in a single OGIS loop, with a theorem prover as the oracle.

## Why It Matters / Open Questions

The ~1000× reduction in engineering effort to build a verified lifting compiler (from 1000+ LoC of search-space description to ~100 lines of prompt) makes it practical to build verified transpilers for new DSLs that previously would have required dedicated synthesis expertise. Key limitations include restriction to side-effect-free programs, reliance on Boolean (rather than counterexample-based) feedback from the verifier, and complete failure of smaller open-source models (Llama 3 8B, Mistral Nemo 12B), suggesting the approach currently depends on frontier proprietary models. Open questions include whether richer verifier feedback (counterexamples, partial proofs) can reduce the query budget, whether semantic filtering via test cases can prune spurious candidates before SMT verification, and whether the approach extends to programs with side effects or to optimization objectives beyond functional equivalence.
