## Problem

Code LLMs trained primarily on static source code and docstrings excel at code generation but struggle to reason about deeper program semantics such as execution effects, dynamic state transitions, and input/output behavior. This semantic gap leads to poor performance in debugging, program repair, and execution reasoning tasks, even when execution traces are provided. The paper asks whether training Code LLMs to verbally reason about comprehensive program semantics—mimicking how human developers perform rubber-duck debugging—can bridge the gap between static code text and dynamic execution understanding.

## Input / Output

The model handles four task modalities distinguished by task-specific prefixes: (1) NL-to-code takes a problem description with constraints and test cases and produces executable Python code; (2) forward monologue takes source code plus a concrete input and produces a step-by-step natural-language execution walkthrough ending with the predicted output; (3) backward monologue takes source code plus a concrete output and produces an abstract reasoning chain that deduces a valid input, using abstract intermediate constraints when the prior state is non-unique (e.g., after sorting); (4) debugging takes a problem, buggy code, and a failing test, and produces a verbal root-cause analysis followed by a refined patch. All training data is synthetic Python, filtered to be fully executable, with monologue annotations verified by execution-based rejection sampling.

## Method

SEMCODER introduces monologue reasoning, a training strategy that teaches a 6.7B Code LLM (initialized from DeepSeekCoder) to articulate program semantics in natural language across four levels: approximate semantics (high-level functional summaries), abstract semantics (key properties and invariants that hold for all inputs), operational semantics via forward monologue (step-by-step verbal simulation of variable changes and control flow), and backward monologue (abstract deduction of prior states from observed outputs). The model is jointly fine-tuned with next-token prediction on PYX (32k executable NL-to-code pairs with unit tests), 29.9k forward monologues, 31k backward monologues, and PYX-R (18.5k debugging samples with rubber-duck rationales and verified patches). Monologue annotations are generated by GPT-4o-mini via rejection sampling, accepting only explanations whose predicted outputs match actual execution. The key design choice is that monologues focus on key properties and causal state transitions rather than enumerating all concrete variable values, making them more compact and learnable than structured trace formats like Scratchpad or NeXT.

## Results

SEMCODER-S (6.7B) achieves 79.3% pass@1 on HumanEval (vs. GPT-3.5-turbo's 76.8%) and 27.5% on LiveCodeBench-Lite (vs. 23.9%), while dramatically outperforming GPT-3.5-turbo on execution reasoning: 63.6% on CRUXEval-I (vs. 50.3%), 63.9% on CRUXEval-O (vs. 59.0%), and 61.2% on LiveCodeBench-CodeExecution (vs. 43.6%). Compared to its base checkpoint DeepSeekCoder-Inst-6.7B, the semantic training yields +21.7% absolute improvement on CRUXEval-I and +27.2% on LCB-Exec. In the ablation (Table 2), monologue reasoning achieves 61.8% on CRUXEval-I versus 48.8% for Scratchpad and 49.4% for NeXT, confirming that natural-language semantic reasoning outperforms concrete trace formats.

## Baselines & Comparisons

SEMCODER-S (6.7B) outperforms GPT-3.5-turbo on HumanEval (79.3 vs. 76.8), LiveCodeBench-Lite (27.5 vs. 23.9), CRUXEval-I (63.6 vs. 50.3), CRUXEval-O (63.9 vs. 59.0), and LCB-Exec (61.2 vs. 43.6), though it trails on MBPP (79.6 vs. 82.5). Against same-size open-source models, SEMCODER-S beats Magicoder-S-DS by +19.0 on CRUXEval-I and +22.8 on LCB-Exec, and surpasses DeepSeekCoder-Inst (its own base) by +21.7 on CRUXEval-I and +27.2 on LCB-Exec. It also dominates larger models: StarCoder2-Inst (15B) scores only 47.1 on CRUXEval-I and 29.6 on LCB-Exec, while CodeLlama-Inst (13B) reaches 45.6 and 25.7 respectively. In the execution-reasoning ablation, monologue reasoning (61.8 on CRUXEval-I) clearly outperforms Scratchpad (48.8), NeXT (49.4), and a concise trace format (52.1), demonstrating that natural-language semantic descriptions are more effective than concrete state enumerations for teaching code execution understanding.

## Relation to Prior Work

This paper extends the line of synthetic instruction-tuning for Code LLMs (OSS-INSTRUCT, Magicoder, Evol-Instruct) by introducing a multi-modal semantics training objective that jointly optimizes NL-to-code generation, forward execution simulation, and backward state deduction. It departs from prior execution-reasoning approaches (Scratchpad, NExT) that encode concrete program states as structured traces, instead proposing 'monologue reasoning'—a natural-language verbalization of execution that mimics rubber-duck debugging and handles abstract/non-deterministic states more flexibly. The base model (DeepSeekCoder-6.7B) and the debugging/self-refinement task (building on Self-Debugging, CYCLE, LeTI) are inherited from prior work, but the joint training on PYX with execution-verified monologues is the core methodological contribution.

## Why It Matters / Open Questions

The paper demonstrates that a 6.7B model trained on comprehensive semantics can match or exceed GPT-3.5-turbo on execution reasoning, suggesting that targeted semantic training is more effective than raw scale for understanding program behavior. The finding that monologues with occasionally flawed intermediate steps outperform guaranteed-correct concrete traces challenges the assumption that trace fidelity is the primary driver of execution reasoning quality. Key limitations include reliance on a stronger LLM (GPT-4o-mini) for monologue annotation, Python-only scope, and the acknowledged risk that flawed intermediate reasoning in training data may cap further gains. Open questions include whether the approach scales to larger base models (enabling self-annotation), whether process supervision can fix intermediate reasoning errors, and whether monologue-based self-verification can be directly integrated into the code generation loop.
