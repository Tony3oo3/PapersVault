## Problem

Representation learning for relational databases with multiple interconnected tables remains underexplored due to the absence of large-scale, openly available training corpora. Existing multi-table resources are extremely small (CTU Prague: 83 databases, SQLShare: 64), while large tabular corpora like GitTables and WikiTables contain only individual self-contained tables. Synthetic benchmarks (TPC-H, TPC-DS) lack the domain diversity and textual content needed to train realistic foundation models for relational data.

## Input / Output

The construction pipeline ingests the full Wikidata JSON dump (loaded into MongoDB for efficient querying) and produces 100,000 relational databases, each stored as CSV table files plus a JSON schema file encoding table structure and foreign-key relationships. Each database contains 2–100 tables (median 3), with an average of 52.72 columns and 118.16 rows per table, and includes Wikidata QIDs for every cell referencing a Wikidata item. For the experimental models, input is linearized table rows with randomly masked cell values, column names, or table names; output is the generated (unmasked) token sequence for the missing element.

## Method

Databases are built table-by-table from Wikidata items: a start table is selected via a pre-built lookup structure mapping concepts to items, then connected tables are added by traversing foreign-key properties. To maintain topical coherence, Sentence-BERT embeddings of candidate column names are scored by cosine similarity against a running database-topic embedding, and only the highest-scoring relation above a 0.2 threshold is followed. GPT-4o is then used to paraphrase all table and column names (since Wikidata has only 11,887 generic property names) to increase schema diversity. For experiments, T5 models (220M–2.8B parameters) are fine-tuned with LoRA (r=64, α=128) on masked-reconstruction objectives over linearized tables, and a hybrid LM+GNN architecture models tables and databases as graphs where the LM encoder produces node embeddings, GNN message passing propagates information across foreign-key edges, and the LM decoder generates the masked target.

## Results

On the WikiDBs-10k test set, the T5-3B model achieves the best cell imputation accuracy (60.71%) and column name accuracy (92.46%), substantially outperforming the BART-based baselines (24.14% and 48.98% for BART alone; 30.22% and 69.37% for BART+GNN). For table name prediction, BART+GNN (50.08%) still outperforms all T5 variants (best: T5-large at 42.89%), suggesting that explicit relational structure via GNNs remains important for schema-level tasks. In the downstream column type annotation experiment, T5 pre-trained on WikiDBs reaches 44% validation accuracy on GitTablesCTA versus 41% for vanilla T5, and converges faster (37% vs. 25% after 100 fine-tuning steps).

## Baselines & Comparisons

The paper compares its T5-based models against two BART-based baselines from prior work (RPT [46] and the BART+GNN architecture from WikiDBs-10k [48]). On cell imputation and column name prediction, all T5 variants decisively outperform both BART baselines: T5-3B achieves 60.71% cell accuracy versus 30.22% for BART+GNN and 24.14% for BART alone, while T5-large reaches 90.87% column accuracy versus 69.37% for BART+GNN. However, on table name prediction, BART+GNN (50.08% accuracy) still leads over the best T5 model (T5-large at 42.89%), indicating that the explicit GNN-based relational structure remains advantageous for schema-level generation. The multi-table GNN model (T5+GNN) also shows a small but consistent gain over its single-table counterpart on table name prediction (18.40% vs. 18.00% exact match; 28.34% vs. 26.07% token-wise accuracy), confirming that relational context provides additional signal. For the downstream CTA task, WikiDBs pre-training yields a 3-point absolute improvement over vanilla T5 (44% vs. 41%), with notably faster convergence during fine-tuning.

## Relation to Prior Work

This paper scales and refines the WikiDBs-10k methodology [48] by increasing the corpus to 100,000 databases with up to 100 tables each, improving domain coherence via Sentence-BERT-based relation selection, and using GPT-4o to paraphrase table and column names for greater diversity. For the experimental component, it adopts the LM+GNN hybrid architecture from [49] to model multi-table relational structure, positioning itself against single-table corpora (GitTables, TabLib) and small multi-table repositories (CTU Prague, SQLShare, GitSchemas) that are either too small, lack table content, or are synthetically generated. The key conceptual departure is grounding database construction in Wikidata's real-world knowledge rather than TPC-style synthetic benchmarks, ensuring textual content and domain diversity that prior resources lack.

## Why It Matters / Open Questions

WikiDBs fills a critical gap: no prior openly available corpus provided 100k+ multi-table relational databases with actual cell content, which is a prerequisite for training foundation models on structured data. The initial experiments, while preliminary, confirm that multi-table context provides measurable (if small) benefits over single-table models and that pre-training on WikiDBs accelerates downstream convergence, validating the corpus's utility. Key limitations remain: average table size is only 118 rows, Wikidata coverage is skewed toward well-documented domains, and the LLM-based paraphrasing introduces potential hallucinations. Open questions include what model architectures (beyond naive LM scaling) can effectively exploit relational structure, how to augment table sizes, and whether the corpus generalizes to enterprise data characteristics not reflected in Wikidata.
