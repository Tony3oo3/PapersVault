## Problem

LLMs excel at function-level code generation but fail at repository-level tasks like resolving GitHub issues, with GPT-4 resolving fewer than 2% of SWE-bench instances even when target files are provided. The paper identifies two root causes through empirical analysis: LLMs struggle to accurately locate the specific lines to modify, and the complexity of code changes (number of files/functions modified) strongly and negatively correlates with resolution success. Existing multi-agent LLM systems focus on generating code from scratch rather than modifying existing repositories during software evolution.

## Input / Output

The framework takes a GitHub issue description, the full code repository (accessed via file-level retrieval rather than full-context input), and optionally pull request hints (textual comments from PRs created before the first commit) as input. It produces a repository-level code change structured as git-applicable diffs across one or more files. A key design constraint is that the LLM never sees the entire repository at once; instead, files are retrieved via BM25 ranking and filtered by an LLM-based relevance check with a memory mechanism that reuses compressed file summaries across iterations to stay within context limits.

## Method

MAGIS decomposes GitHub issue resolution into a four-agent collaborative workflow inspired by GitHub Flow: a Repository Custodian locates relevant files using BM25 plus LLM-based relevance filtering with a cross-version memory mechanism; a Manager decomposes the issue into file-level tasks, designs specialized Developer agent personas for each task, and organizes a kick-off meeting to establish task dependencies and execution order; Developers then perform line-level localization (identifying specific line intervals to modify), generate replacement code snippets, and produce git diffs; and a QA Engineer iteratively reviews each code change, providing feedback until approval or a maximum iteration limit. The core insight is that breaking the monolithic code-change generation into sequential sub-operations—file localization, line localization, snippet generation, and review—exploits LLMs' strength in short-context code generation while circumventing their weakness in long-context code modification. This multi-step decomposition, combined with agent specialization and iterative QA feedback, yields a 13.94% resolved ratio on SWE-bench, an eight-fold improvement over direct GPT-4 application.

## Results

On SWE-bench (25% subset), MAGIS achieves a 97.39% applied ratio and a 13.94% resolved ratio, representing an eight-fold improvement over the base LLM GPT-4 (1.74% resolved). On SWE-bench lite, MAGIS reaches 25.33% resolved, outperforming SWE-Agent (18.00%) and AutoCodeRover (16.11%). In a direct comparison with Devin on 140 shared instances, MAGIS resolves 21 issues (15%) versus Devin's 18 (12.86%), while completing each instance in under 5 minutes on average.

## Baselines & Comparisons

MAGIS decisively outperforms all direct LLM baselines on SWE-bench: it achieves 13.94% resolved versus GPT-4's 1.74% (8×), Claude-2's 4.88% (~2.9×), GPT-3.5's 0.84% (~16.6×), SWE-Llama 13b's 4.36% (~3.2×), and SWE-Llama 7b's 2.12% (~6.6×). The applied ratio also jumps dramatically to 97.39%, compared to 13.24% for GPT-4 and 49.36% for Claude-2, indicating the multi-agent pipeline produces far more syntactically valid patches. On SWE-bench lite, MAGIS (25.33%) leads SWE-Agent (18.00%) by 7.33 percentage points and AutoCodeRover (16.11%) by 9.22 percentage points. Against Devin on 140 overlapping instances, MAGIS resolves 21 issues (15%) versus Devin's 18 (12.86%), though the comparison is noted as not entirely equitable since Devin has access to a browser and internet. The ablation results further confirm that the QA Engineer contributes +1.57 to +3.31 percentage points and human hints contribute +1.57 to +3.66 percentage points to the resolved ratio.

## Relation to Prior Work

MAGIS repurposes the LLM-based multi-agent paradigm established by MetaGPT and ChatDev—systems designed to build code repositories from requirements—toward the distinct problem of software evolution, i.e., modifying existing code to resolve GitHub issues. The empirical study builds directly on SWE-bench (Jimenez et al., ICLR 2024), which demonstrated that even GPT-4 resolves fewer than 2% of issues, and extends the automatic program repair literature (Xia et al., Bouzenia et al.) by identifying line-localization accuracy and code-change complexity as the primary failure factors. Unlike prior multi-agent code-generation systems that assume a blank slate, MAGIS introduces a Repository Custodian role with a memory mechanism for file summarization and a QA Engineer role for iterative code review, both tailored to the constraints of operating within a large, evolving codebase.

## Why It Matters / Open Questions

The 8× relative improvement over direct GPT-4 application (1.74% → 13.94% resolved) demonstrates that decomposing repository-level code changes into specialized agent roles can substantially unlock LLM capability for software evolution, a task where single-model approaches have plateaued. However, the absolute resolution rate remains low, the evaluation is confined to 12 Python repositories on SWE-bench, and the framework's sensitivity to prompt design and its reliance on GPT-4 as the backbone limit generalizability claims. Open questions include whether the multi-agent overhead scales to larger or polyglot repositories, whether the memory-based file summarization transfers to non-Python ecosystems, and whether the modest gains from QA review (+1.5–3.3%) justify the additional LLM calls at production scale.
