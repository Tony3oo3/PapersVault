## Problem

Existing code generation benchmarks suffer from two critical limitations: data leakage (test data appearing in LLM training corpora, inflating scores) and the absence of domain-specific evaluation, which prevents practitioners from identifying which LLMs excel in particular programming domains (e.g., database, internet, multimedia). This paper addresses both gaps by introducing an evolving, domain-labeled benchmark for repo-level code generation.
![Teaser figure](../imgs/NEURIPS20241836/cropped_page2_idx0.webp)

## Input / Output

Each benchmark sample provides a natural language requirement, a function signature, and repository context (hundreds of code files from which local-file contexts above/below the target function are extracted). LLMs produce generated code that is scored on two axes: Pass@k (unbiased functional correctness via pytest execution) and Recall@k (fraction of reference dependencies—intra-class, intra-file, cross-file—correctly invoked). The domain-specific layer adds a Domain-Specific Improvement (DSI) score per LLM per domain, flagging comfort domains (DSI > 10%) and strange domains (DSI < −10%).

## Method

EvoCodeBench is constructed by a four-stage automatic pipeline: (1) crawling high-quality Python repositories created within the last six months from GitHub, (2) execution-based filtering using pip + pytest to retain only functions with runnable test cases, (3) automatic annotation via a static-analysis parser (signatures, reference code, dependencies) and GPT-4 (natural-language requirements and domain labels from a 10-domain taxonomy derived from PyPI statistics), and (4) balanced benchmark assembly aligned with code and dependency distributions of 500 real-world repositories. The benchmark is designed to be re-collected every ~6 months so that new versions post-date LLM training cutoffs, reducing the measured leakage rate from 41.47% (HumanEval) to under 3%. The DSI metric computes each LLM's average relative Pass@1 improvement over all other LLMs in a given domain, enabling practitioners to match models to domains and trainers to identify weak spots for future iterations.

## Results

On EvoCodeBench-2403 (Local File Infilling setting), gpt-4 achieves the highest Pass@1 of 20.73% and Recall@1 of 68.24%, while DeepSeek Coder-33B reaches 19.64% Pass@1 and 71.46% Recall@1. Performance drops dramatically compared to prior benchmarks: gpt-4's Pass@1 falls from 53.04% on DevEval to 20.73% here, confirming EvoCodeBench is significantly harder and less contaminated. Data leakage detection (CDD) shows the leak rate drops from 41.47% on HumanEval to 2.18% on EvoCodeBench-2403 for gpt-4. In domain-specific analysis, gpt-4 leads in most domains (e.g., 38.89% in Database, 16.67% in Text Processing where all other LLMs score 0%) but underperforms in the Internet domain (20.00% vs. 26.67% for gpt-3.5 and DeepSeek Coder).

## Baselines & Comparisons

The paper evaluates 8 LLMs (gpt-4, gpt-3.5, DeepSeek Coder-33B/6.7B, StarCoder 2-15B/7B, CodeLLaMa-13B/7B) on the new EvoCodeBench-2403 benchmark. gpt-4 leads in Pass@1 across all three context settings (20.73% Infilling, 17.45% Completion, 7.27% Without Context), but DeepSeek Coder-33B surpasses it in Recall@1 (71.46% vs. 68.24%) and Pass@10 (26.01% vs. 25.34%), indicating stronger dependency retrieval. StarCoder 2 models trail significantly in Pass@1 (15.27% and 14.91%) but StarCoder 2-15B unexpectedly matches gpt-4 in the Database domain (38.89% Pass@1). In the Internet domain, gpt-4 (20.00%) underperforms gpt-3.5, DeepSeek Coder, and StarCoder 2 (all 26.67%), revealing a domain-specific weakness. CodeLLaMa models (13B/7B) achieve the lowest Pass@1 (12.73%) in the Completion setting but show competitive Recall@10 (80.11% for 13B), suggesting they retrieve dependencies well even when functional correctness is low.

## Relation to Prior Work

This paper extends the repo-level code generation benchmark line (DevEval, CoderEval) by introducing an evolving data paradigm and domain-specific evaluation metrics. It departs from snippet-level benchmarks (HumanEval, MBPP, ClassEval) that lack repository context, and from prior domain-labeled benchmarks (ClassEval) whose domains were manually designed rather than derived from community statistics. The data leakage detection leverages CDD, and the RAG experiments build on prior retrieval-augmented code generation work (AixBench, ACECoder), but the core contribution is the automatic collection pipeline and the Domain-Specific Improvement (DSI) metric for characterizing LLM strengths and weaknesses across programming domains.

## Why It Matters / Open Questions

The evolving benchmark paradigm directly addresses the data contamination problem that undermines the reliability of all static code generation benchmarks, and the domain taxonomy grounded in PyPI statistics provides a practical framework for practitioners to select LLMs for specific programming domains. Key open questions remain: the benchmark is Python-only with just 275 samples and an unbalanced domain distribution, cross-file dependency modeling is still poorly handled by all LLMs (20 of 50 error cases due to missing contexts), and whether the comfort/strange domain patterns persist as models scale or as new versions are released. The dramatic performance drop (gpt-4 Pass@1 from ~53% on DevEval to 20.73% here) suggests prior benchmarks may have been substantially contaminated, raising questions about the validity of many published LLM code generation results.
