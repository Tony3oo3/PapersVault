## Problem

Existing LLM graph-analysis benchmarks require models to reason directly over adjacency lists embedded in prompts, restricting evaluation to graphs with only a few dozen nodes and shallow reasoning depths. This does not reflect how human experts actually solve graph problems—by writing short programs against popular graph libraries—and thus fails to test whether LLMs can handle real-world-scale graphs (up to 10^6 nodes). The paper asks whether LLMs can analyze graphs like professionals by generating code that calls external APIs rather than reasoning over raw topology.

## Input / Output

Each problem provides a graph either as a natural-language edge list or as a file reference (enabling scalability to 10^6 nodes), plus a role-play-rephrased question drawn from four types (true/false, calculation, drawing, hybrid) at two difficulty levels (easy = one API, hard = multiple APIs). The model must produce executable Python code using one of six graph libraries; the evaluation extracts the code, runs it, and uses GPT-4o to compare execution results against reference answers, scoring pass rate (code runs) and accuracy (correct result). For RAG-enhanced closed-source models, the input additionally includes top-K retrieved API documentation entries from the LLM4Graph document pool.

## Method

The paper introduces ProGraph, a 512-problem benchmark spanning three task categories (basic graph theory, graph statistical learning, graph embedding) built from six Python libraries (NetworkX, igraph, CDlib, graspologic, Karate Club, Little Ball of Fur), with questions rephrased via GPT-4 turbo into realistic role-play scenarios and answers including reference code, key APIs, and execution results. To enhance model performance, the authors construct LLM4Graph: a document dataset of 1,413 crawled API entries and a code dataset of 29,260 QA pairs auto-generated via back-instruction with GPT-4 turbo, where the Doc+Code variant prepends relevant API documentation to each answer to enable chain-of-thought learning. Closed-source LLMs are augmented with RAG (top-K API documents retrieved via LlamaIndex, K∈{3,5,7}), while open-source models (Llama-3-8B, DeepSeek-Coder-7B) are instruction-tuned on the code datasets using the alignment-handbook framework. The Doc+Code fine-tuning strategy uses a two-step inference process—first generating candidate APIs, then retrieving their documentation and writing code—yielding 45–47% accuracy, surpassing the best closed-source model with RAG (46.2%). Automated evaluation via GPT-4o achieves 98.9% self-consistency and 97.5% human-consistency across all 512 problems.

## Results

On the ProGraph benchmark (512 problems across three graph task categories), the best closed-source model without RAG is GPT-4o at 36.3% overall accuracy, while the best with RAG is Claude 3 Opus RAG 7 at 46.2%. Among open-source models, Deepseek Coder Doc+Code achieves the highest overall accuracy at 46.6%, and Llama 3 Doc+Code reaches 44.9%, both substantially surpassing the best closed-source model without RAG. The LLM4Graph datasets yield 11–14% absolute accuracy gains for closed-source models via RAG and 20–32% gains for open-source models via instruction tuning.

## Baselines & Comparisons

Among closed-source models, GPT-4o leads without RAG at 36.3% overall accuracy, outperforming Claude 3 Opus (34.7%), GPT-4 turbo (31.2%), and Gemini 1.5 Pro (24.8%). With RAG using LLM4Graph, Claude 3 Opus RAG 7 achieves the highest closed-source accuracy at 46.2%, edging out GPT-4o RAG 7 (42.7%) and Gemini 1.5 Pro RAG 5 (37.3%). For open-source models, fine-tuning on LLM4Graph dramatically closes the gap: Deepseek Coder Doc+Code (46.6%) and Llama 3 Doc+Code (44.9%) both surpass the best closed-source model without RAG (GPT-4o at 36.3%) by 8–10 percentage points. Notably, adding RAG on top of code-fine-tuned open-source models actually degrades performance (e.g., Llama 3 Code+RAG 7 drops to 27.7% vs. 43.8% for Code Only), suggesting small models struggle with long retrieved contexts. The fine-tuned open-source models also show strong generalizability on hard-level problems (requiring multiple APIs), reaching ~40% accuracy versus only ~32.5% for the best closed-source model, despite LLM4Graph containing only single-API training examples.

## Relation to Prior Work

This paper departs from prior LLM graph-analysis benchmarks (NLGraph, GraphInstruct, GraphTMI, GPT4Graph, LLM4DyG, GraphWiz) that require models to directly reason over graph topology embedded in prompts, limiting them to graphs with only a few dozen nodes. Instead, ProGraph reframes the task around the way human experts actually work: writing short Python programs that call APIs from established graph libraries (NetworkX, igraph, CDlib, etc.), enabling scalability to 10^6 nodes. The enhancement techniques—RAG for closed-source models and instruction tuning with CoT-style Doc+Code data for open-source models—are repurposed from general LLM literature (Self-Instruct for back-instruction, standard RAG pipelines), but their application to graph-library API knowledge is novel.

## Why It Matters / Open Questions

The benchmark reveals a significant capability gap: even GPT-4o achieves only 36% accuracy on API-based graph analysis, and performance drops sharply (to ~32%) when problems require multiple APIs, suggesting current LLMs lack reliable multi-step API orchestration for structured data. Practically, the finding that 7–8B fine-tuned open-source models (45–47% accuracy) can match or exceed RAG-augmented closed-source models (37–46%) offers a cost-effective path for deploying graph-analysis capabilities. Open questions include whether the 512-problem benchmark is sufficiently comprehensive, whether the single-turn, single-API-per-training-sample design limits generalization to truly complex multi-library workflows, and whether the approach extends to other structured-data domains (databases, knowledge graphs, tabular data).
