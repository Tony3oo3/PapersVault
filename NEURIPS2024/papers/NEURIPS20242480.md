## Problem

Existing LLM code benchmarks (HumanEval, APPS, SWE-Bench) evaluate models on isolated programming puzzles or userspace Python repositories, failing to capture the challenges of systems-level software. The Linux kernel—over 20M lines across 50k files, multilingual (C/Assembly/Bash/Rust), highly concurrent, and deployed on billions of devices—presents a drastically harder SE task where crash root causes are ambiguous, fixes must be memory-safe and hardware-aware, and bugs are non-deterministic. No prior benchmark or execution platform enables large-scale evaluation of LLMs on real-world kernel crash resolution.

## Input / Output

Each KBENCHSYZ sample provides a kernel crash report (averaging 84.3 lines of stack traces, up to 624), a Syzkaller reproducer (a syz DSL program of up to 10 system calls, or its C translation in KBENCHC), a kernel commit ID with build config, and a set of relevant C source files retrieved via BM25 (top-3) or oracle (gold-fix files). The LLM must produce a syntactically valid git diff patch; correctness is verified not by unit tests but by actually compiling the full kernel (~15–20 min) and running the reproducer in a VM for 10 minutes—no crash means the bug is resolved. The non-deterministic nature of many kernel bugs necessitates parallel and replicated test execution.

## Method

KGYM is a scalable execution platform built atop Syzkaller's syz-build and syz-crush components, organized around four modules: Kbuilder (compiles kernels at specified commit IDs with user-specified compiler, linker, arch, and userspace image), Kreproducer (launches GCE VMs to execute reproducers and collect kernel panic output), a Scheduler (coordinates parallel jobs across 11 c2-standard-30 VMs via RabbitMQ, tracking state in SQLite), and Clerk (a Python client API for submitting jobs). KBENCHSYZ contains 279 curated bugs from Syzbot, each validated by three checks: the bug reproduces at Commit_bug, reproduces at Commit_parent (the parent of the fix commit), and is resolved at Commit_fix. Evaluation uses two retrieval settings—Oracle (gold-fix files disclosed, reducing to 117 or 228 bugs depending on context length) and BM25 sparse retrieval (top-3 files, reducing to 227 or 275 bugs)—with LLMs prompted via a structured template containing the crash report and retrieved files, asked to output a single git diff patch. The paper benchmarks GPT-3.5/4 Turbo, Claude-3 Sonnet, Gemini-1.5 Pro, and Code Llama/Llama-3 models, running over 17k kernel jobs, finding best solve rates of only 5.38% (Oracle) and 0.72% (BM25).

## Results

On KBENCHSYZ (279 Linux kernel bugs), the best-performing LLM (GPT-4 Turbo, top-10) achieves a 5.38% bug solve rate in the Oracle (assisted) setting and only 0.72% in the BM25 (unassisted) setting. GPT-4 Turbo also has the highest patch application rate at 56.99% (Oracle) and 55.20% (BM25). All open-source Llama models (Code Llama 7B/13B/34B, Llama-3-8B) achieve 0% solve rate across all settings. Combining patches from all models yields a union solve rate of 10.39% (29 unique bugs resolved out of 279).

## Baselines & Comparisons

The paper benchmarks eight LLMs (four closed, four open) on KBENCHSYZ under two retrieval settings. Among 50k-context models, GPT-4 Turbo dominates: it achieves 5.38% solve rate (Oracle, top-10) versus 1.79% for Claude-3 Sonnet and 3.58% for Gemini-1.5 Pro, and is the only model with a non-zero BM25 solve rate (0.72%). Among 16k-context models, GPT-3.5 Turbo leads with 1.08% (Oracle) and 0.36% (BM25), while all Code Llama and Llama-3 variants score 0% in every setting. The gap between Oracle and BM25 settings is stark (5.38% vs. 0.72% for GPT-4 Turbo), revealing that BM25 retrieval is a major bottleneck: it correctly includes all oracle files in only 2.91% of cases (top-3, 50k context). Even the best model resolves fewer than 1 in 15 bugs unassisted, underscoring that current LLMs are far from capable of autonomous Linux kernel crash resolution.

## Relation to Prior Work

This paper extends the SWE-Bench paradigm of repository-level program repair from userspace Python libraries to the Linux kernel, a 20M-line multilingual (C/Assembly/Bash/Rust) systems codebase with non-deterministic crash oracles. It reuses Syzkaller's syz-build and syz-crush components as the execution backbone but wraps them in KGYM, a scalable parallel platform that makes kernel experimentation accessible to ML researchers who lack kernel development expertise. The evaluation methodology (oracle vs. sparse retrieval, patch application rate, solve rate) directly follows SWE-Bench, but the domain introduces fundamentally new challenges: hardware-aware memory safety, concurrency reasoning, and bug localization across 50k+ files.

## Why It Matters / Open Questions

The extremely low solve rates (0.72% unassisted, 5.38% assisted for GPT-4 Turbo) establish that current LLMs are far from capable of resolving real-world systems-level bugs, identifying a clear research frontier. The poor BM25 retrieval performance (~10% recall at K=20) reveals that bug localization in massive codebases is a fundamental bottleneck that must be solved before patch generation can improve. KGYM lowers the barrier for ML researchers to conduct kernel experiments, and KBENCHSYZ/KBENCHC provide a reproducible, diverse benchmark spanning 72 subsystems and 10 years of kernel versions. Open questions include whether dynamic execution traces (kernel logs, dmesg) can improve localization, how to handle non-deterministic oracles more robustly, and whether models can learn subsystem-specific coding conventions.
