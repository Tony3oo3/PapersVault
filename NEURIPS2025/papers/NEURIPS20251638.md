## Problem

State-of-the-art SE agents achieve strong resolution rates on traditional software (e.g., 50.80% on SWE-bench), but LLM-based agent systems constitute a new software paradigm with unique failure modes—LLM nondeterminism, volatile external tool dependencies, and agent-specific components like memory and planning—that are absent from traditional codebases. This paper asks whether existing SE agents can effectively resolve real-world issues in agent systems, and if not, what categories of agent issues remain out of reach.

## Input / Output

Each task provides a user-reported issue description and the buggy commit of an agent system repository, both packaged inside a self-contained Docker environment with all dependencies pre-configured. The SE agent must output a code patch applied to the buggy codebase. Evaluation uses three metrics: file- and function-level localization accuracy (does the patch touch the same location as the golden patch?), plausible resolution rate (does the patch pass the failure-triggering tests?), and correct resolution rate (human-verified semantic equivalence to the developer-committed patch, guarding against test overfitting).

## Method

The paper contributes three artifacts. First, a taxonomy of agent issues with 6 categories and 20 sub-categories, built via grounded theory (open coding by 3 annotators, consensus review) from 201 closed GitHub issues with developer-committed patches across 18 agent systems, and validated on a held-out 30-issue set (Cohen's Kappa = 0.849). Second, AGENTISSUE-BENCH, a benchmark of 50 reproducible issue-resolution tasks constructed through a 3-step filtering pipeline—failure reproduction, patch reproduction, and non-flakiness verification (each repeated 3× to account for LLM stochasticity)—that required approximately 500 person-hours because most of the original 201 issues could not be stably reproduced. Third, a quantitative and qualitative evaluation of three SE agents (Agentless, AutoCodeRover, SWE-agent) paired with GPT-4o and Claude-3.5-Sonnet, showing correct resolution rates of only 0.67%–4.67%; the qualitative breakdown reveals that resolved issues are concentrated in utility and dependency categories, while LLM-provider incompatibility, memory, and LLM-operation issues remain almost entirely unsolved.

## Results

On AGENTISSUE-BENCH (50 agent issue resolution tasks), all state-of-the-art SE agents exhibit very limited effectiveness, with correct resolution rates ranging from only 0.67% (SWE-agent + GPT-4o) to 4.67% (AutoCodeRover + Claude-3.5-Sonnet). Plausible resolution rates are somewhat higher (0.67%–12.67%), but many plausible patches are not semantically correct. File-level localization accuracy never exceeds 27.82% and function-level localization never exceeds 19.18%, indicating that SE agents struggle even to identify the correct code locations. These results are dramatically lower than the 23.20%–50.80% resolution rates these same agents achieve on traditional software issues (SWE-bench Lite).

## Baselines & Comparisons

The paper evaluates three SE agents—Agentless, AutoCodeRover, and SWE-agent—each paired with GPT-4o and Claude-3.5-Sonnet on AGENTISSUE-BENCH. AutoCodeRover with Claude-3.5-Sonnet achieves the highest correct resolution rate (4.67%) and best function-level localization (19.18%), while SWE-agent is consistently the weakest (0.67%–2.00% correct resolution). Agentless achieves comparable plausible resolution rates (12.00%) to AutoCodeRover with Claude-3.5-S but slightly lower correct resolution (4.00% vs. 4.67%). Across all agents, Claude-3.5-Sonnet outperforms GPT-4o on every metric, suggesting stronger reasoning about agent-specific code. Critically, all three agents resolve far fewer agent issues than traditional software issues: on SWE-bench Lite, the same agents achieve 23.20%–50.80% correct resolution, a 5–75× gap that underscores the unique difficulty of agent system maintenance. No single agent resolves all issue categories; the few resolved issues are concentrated in utility and tool-dependency sub-categories, while LLM-provider incompatibility, memory, and LLM-operation issues remain essentially unsolved by all three agents.

## Relation to Prior Work

This paper extends the SWE-bench lineage of real-world issue resolution benchmarks (SWE-bench, SWE-bench Java, SWE-bench Multimodal, SWE-Lancer) from traditional software to LLM-based agent systems, a software paradigm with fundamentally different failure modes (nondeterminism, LLM provider dependencies, tool interactions, memory mechanisms). It also builds on the SE agent evaluation line (SWE-agent, AutoCodeRover, Agentless) by applying these agents to a new domain, and complements Cemri et al.'s runtime failure taxonomy by focusing on user-reported issues and developer-committed patches rather than execution trajectories. The key departure is that prior benchmarks and agents assume deterministic, self-contained software, whereas agent issues involve volatile external resources and LLM-specific semantics that existing agents were never designed to handle.

## Why It Matters / Open Questions

As agent systems proliferate across medicine, robotics, and programming, the finding that state-of-the-art SE agents resolve only 0.67%–4.67% of agent issues (versus 23–50% on traditional software) signals a critical gap in automated maintenance for this emerging paradigm. The 500 person-hours needed to reproduce just 50 of 201 issues underscores how much harder agent-system debugging is than traditional software debugging, largely due to LLM nondeterminism and shifting external dependencies. Open questions include whether augmenting SE agents with evolving knowledge bases of LLM provider APIs, incorporating dynamic runtime analysis, or fine-tuning on agent-specific trajectories can close this gap. The benchmark's small size (50 tasks) and focus on reactive (post-hoc) issues limit generalizability, and the authors note the benchmark is being extended.
