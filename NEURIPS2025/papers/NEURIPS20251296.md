## Problem

Out-of-tree Linux kernel patches (e.g., RT-PREEMPT, HAOC, Raspberry Pi kernel) require labor-intensive manual migration across kernel versions, a task that demands specialized experts and weeks of effort. Existing code migration tools rely on predefined rules and assume known target code locations, making them inadequate for the complex two-step task of locating and migrating out-of-tree patches. While LLMs offer a promising alternative, they suffer from structural ambiguity, boundary indeterminacy, missing associated code fragments, and ambiguous migration point identification.

## Input / Output

The method consumes three C-language inputs: the old kernel code snippet (s_old), the patched old code snippet (s'_old) reflecting the out-of-tree modification, and the full new-version kernel source file (file_new) from which the target snippet must be located. It produces two outputs in sequence: the retrieved target code snippet (s_new) from the new kernel, and the final migrated patch code snippet (s'_new) that integrates both the kernel update changes and the out-of-tree patch modifications. The benchmark spans kernel versions 4.19, 5.4, 5.10, and 6.6, with 135 examples split into non-conflicting (Type 1, 80) and conflicting (Type 2, 55) migration scenarios.

## Method

MIGGPT introduces a Code Fingerprint (CFP), a lightweight sequential data structure that records per-line content and positional information for all C statements including comments and inline assembly, avoiding the limitations of AST-based analysis on incomplete kernel code snippets. Three modules leverage CFP to guide zero-shot LLM prompting: the Retrieval Augmentation Module extracts function signatures from CFP_old to build a Structure Prompt that constrains LLM attention to the correct function and retrieves newly appeared associated function definitions via set-difference of call sets; the Retrieval Alignment Module uses the first and last CFP anchor lines to construct an Alignment Prompt that pins snippet boundaries; and the Migration Enhancement Module diffs CFP_old against CFP_old' to determine the exact count and positions of migration points, encoded in a Location Prompt. The overall pipeline is two-step—first retrieving s_new from file_new using the combined Retrieval Prompt, then generating s'_new using the Migration Prompt—requiring only ~2.26 average LLM queries per example.

## Results

On the out-of-tree kernel patch migration benchmark (135 examples), MIGGPT achieves an average human-match completion rate of 74.07% (↑45.92% over vanilla LLMs' 28.15%) and 73.12% semantic match (↑45.61%). For the retrieval subtask, MIGGPT reaches 84.55% average semantic match (↑20.53% over vanilla). On the FixMorph CVE patch backporting benchmark (350 instances), MIGGPT with GPT-4-turbo achieves 91.78% semantic match, outperforming all prior methods. MIGGPT requires only 2.08% of the average time taken by human experts (0.25 days vs. 12.51 days).

## Baselines & Comparisons

On the CVE patch backporting benchmark (350 instances, Table 5), MIGGPT with GPT-4-turbo achieves 91.78% semantic match, substantially outperforming FixMorph (24.63%), PPatHF (75.12%), and TSBPORT (87.59%); with DeepSeek-V3 it reaches 92.59%, again beating all three. Against vanilla LLMs on the primary out-of-tree migration benchmark, MIGGPT consistently wins across all six tested models: the largest absolute gains appear for weaker models (e.g., GPT-3.5 human match jumps from 7.41% to 53.33%, Llama-3.1-8B from 20.00% to 62.96%), while even the strongest baseline (DeepSeek-R1 at 60.00% human match) is surpassed by MIGGPT-augmented DeepSeek-R1 (80.00%). The average query count increases only marginally (1.00 → 1.26), indicating the performance gains come from structured prompting rather than brute-force multi-query. MIGGPT also generalizes beyond C: on a Python migration subset it improves semantic match by 16.13% over vanilla, and on Linux driver migration it gains 20.83–25.00% semantic match.

## Relation to Prior Work

This paper departs from prior code migration work (FixMorph, TSBPORT, PPatHF) that addresses single-step CVE patch backporting or API cross-version updates with predefined rules, by reframing out-of-tree kernel patch migration as a two-step problem: first retrieving the target code snippet from the updated kernel, then performing the actual patch migration. Rather than relying on AST-based static analysis (which fails on incomplete kernel snippets and misses comments/inline assembly), the authors introduce a lightweight Code Fingerprint (CFP) structure that encodes function signatures, call relationships, and anchor lines in a linear format. The framework is the first to apply LLMs to this specific out-of-tree kernel patch maintenance task, combining retrieval-augmented prompting with structured code context to guide the model through both retrieval and migration subtasks.

## Why It Matters / Open Questions

Out-of-tree kernel patch maintenance (e.g., RT-PREEMPT, Raspberry Pi, HAOC) is a critical but labor-intensive engineering task requiring weeks of expert effort per kernel upgrade; MIGGPT's 74.07% completion rate at 2.08% of human time cost demonstrates a practical path toward automating this bottleneck. The introduced benchmark (135 real-world examples across three projects and four kernel versions) is the first to systematically evaluate tools on this task, providing a foundation for future research. Key open questions remain: handling of very large code snippets (>150 lines) where LLM attention degrades, correct fusion of divergent Type 2 changes (27.59% of failures), and whether the CFP approach generalizes beyond C to other kernel-adjacent languages at scale. The 41% of errors requiring fewer than 3 line corrections suggests a near-term human-in-the-loop workflow is viable, but full autonomy remains distant.
