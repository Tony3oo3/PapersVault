## Problem

LLMs prompted to generate plans end-to-end produce incorrect plans and fail to generalize to larger or out-of-distribution tasks, even with advanced prompting techniques like Tree of Thoughts or Algorithm of Thoughts. Meanwhile, specialized LLM planning approaches increase computational costs without matching the reliability of automated planners. The paper asks whether LLMs can be repurposed to generate the heuristic functions that guide classical planners, thereby ensuring plan correctness while leveraging LLM reasoning about domain structure.

## Input / Output

The method takes a PDDL domain file, the smallest and largest training tasks for that domain, two example domain-dependent heuristics (for Gripper and Logistics) implemented in Pyperplan, example state/static representations, Pyperplan's task and operator source code, and a checklist of common pitfalls. The LLM is prompted n=25 times at temperature 1.0 to produce a pool of Python heuristic classes subclassing Pyperplan's Heuristic base class. The selected heuristic is then injected into Pyperplan's greedy best-first search, which outputs a sequence of PDDL actions; the heuristic only affects search efficiency, never plan correctness.

## Method

The pipeline prompts an LLM to write a domain-dependent heuristic function in Python, using a multi-component prompt that includes the target PDDL domain, example tasks, worked heuristic examples for two other domains (a perfect heuristic for Gripper and a counting heuristic for Logistics), Pyperplan's internal data structures, and a pitfall checklist. The LLM is called 25 times with identical prompts at temperature 1.0 to generate a diverse pool of candidate heuristics. Each candidate is evaluated on the training set via GBFS with a 5-minute timeout, and the best-performing heuristic (most tasks solved, tie-broken by accumulated agile score) is selected for all test tasks in that domain. This is a zero-shot, domain-dependent approach: no gradient-based training occurs, and a single selected heuristic is reused across all tasks of the domain, drastically reducing LLM inference costs compared to per-task planning. The key architectural insight is that the LLM's role is confined to heuristic generation (influencing search efficiency), while the classical GBFS algorithm guarantees plan correctness, decoupling the LLM's reliability from the final plan's validity.

## Results

On the IPC 2023 Learning Track (8 domains, 720 test tasks), the DeepSeek R1-generated heuristic (h^R1) in Pyperplan (Python) solves 373/720 tasks, and DeepSeek V3 (h^V3) solves 343/720, both outperforming every domain-independent heuristic in the C++ Fast Downward planner (best: h^add at 324) and slightly exceeding the state-of-the-art learned heuristic h^GPR_WLF (371). End-to-end LLM plan generation is far weaker: DeepSeek R1 solves only 174 tasks and Gemini 2.0 Flash Thinking 202, while the same models used for heuristic generation solve 373 and 305 respectively. The Python-vs-C++ implementation gap (up to 669× slower state expansions in Fast Downward) is overcome by the superior informativeness of the LLM-generated heuristics in several domains (Blocksworld, Spanner, Transport).

## Baselines & Comparisons

Against the six domain-independent Fast Downward heuristics, h^R1 (373) and h^V3 (343) both achieve higher total coverage than every single one: h^add (324), h^cg (318), h^cea (306), h^FF (295), h^lmc (295), and h^GC (294). Against the state-of-the-art learned heuristic h^GPR_WLF (371, Chen et al. ICAPS 2024), h^R1 edges ahead by 2 tasks while h^V3 falls short by 28. Within Pyperplan, both LLM-generated heuristics substantially outperform h^FF (243) and the blind heuristic h^0 (120), with h^R1 solving 130 more tasks than h^FF. The comparison is particularly striking because Pyperplan is an unoptimized Python implementation while all Fast Downward baselines are in C++; in domains like Blocksworld and Spanner, h^R1 also expands fewer states than h^FF, indicating the heuristics are genuinely more informative, not just faster to compute. The one domain where h^R1 underperforms h^FF is Floortile (4 vs. 10 in Pyperplan; 4 vs. 14 in Fast Downward), where the LLM heuristic fails to capture the blocking constraints of the grid.

## Relation to Prior Work

This paper departs from the dominant line of LLM-for-planning work (end-to-end plan generation, chain-of-thought, Algorithm of Thoughts) by restricting the LLM's role to generating domain-dependent heuristic code, while a classical GBFS planner guarantees plan correctness. Conceptually, it occupies the domain-dependent heuristic learning paradigm (where h^GPR_WLF is the prior SOTA) but replaces learned models with LLM-synthesized Python functions. The closest prior work is Tuisov et al. [77], which also uses LLMs to generate heuristic code, but requires manual Rust translation per domain and produces task-dependent heuristics; this paper generates domain-dependent heuristics directly from PDDL with no manual translation. The sampling-and-selecting pipeline draws inspiration from FunSearch [58], though without the iterative feedback loop.

## Why It Matters / Open Questions

The result that a Python-based planner with LLM-generated heuristics outperforms C++-based Fast Downward with multiple SOTA heuristics (and is competitive with the SOTA learning-based h^GPR_WLF) is a strong signal that heuristic quality can dominate implementation efficiency, opening a new axis for improving planners without re-engineering the search infrastructure. The cost advantage is also significant: 200 LLM calls per domain (reusable heuristics) versus 720+ calls for end-to-end planning, and the approach bridges the performance gap between expensive reasoning models and cheap non-reasoning ones. Key limitations include the Python proof-of-concept (a C++ implementation could further widen the gap), dependence on PDDL formalism, and the heuristic selection step being itself a heuristic that may not optimally generalize. Open questions include whether feedback loops (à la FunSearch) or better selection strategies can push coverage further, and whether the approach extends to numeric or temporal planning.
