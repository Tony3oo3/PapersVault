## Problem

Existing code benchmarks evaluate LLMs on end-to-end outcomes (e.g., patch correctness, vulnerability detection) without directly probing their fundamental ability to reason about program semantics such as data dependency, control dependency, and information flow. This leaves it unclear whether models truly understand how values propagate and how control structures govern execution, or merely pattern-match surface-level code features.

## Input / Output

Each task instance presents a source code snippet (21–100 LoC, intra-procedural, in C/C++, Java, or Python) with line numbers, followed by either a pairwise query ("Does variable/line X have [dependency type] over variable/line Y? If so, provide a trace.") or a target-centric query ("List all variables/lines that have [dependency type] over target Z"). The model must output a yes/no classification, a transitive trace of direct dependencies (e.g., x₁→D y₃→D z₅), or a complete orderless set of dependency sources. Evaluation uses F1 for classification, Correct Trace Rate for trace validity, and Exact Match for source enumeration.

## Method

CORE is constructed from 180 functions (60 per language) sampled from CodeNet and Google Code Jam, balanced across four LoC buckets (21–40, 41–60, 61–80, 81–100). Annotation is semi-automated: a custom tree-sitter-based tool generates initial dependency labels, which are then manually validated by two experienced authors (87.5% agreement, conflicts resolved by a third), yielding 6,306 annotated variables and 48,050 lines of annotation. A Semantics-Aware Diverse Sampling strategy governs both target selection and instance generation: targets are chosen to maximize structural diversity (avoiding overlapping dependency traces) and reasoning complexity (requiring dependency depth ≥ 2 or involvement in implicit flows), while negative instances are prioritized from structurally plausible but semantically incorrect candidates (e.g., variables in the same loop block or condition lines before the target). This produces 12,553 task instances (5,798 positive, 6,755 negative) across three dependency types, evaluated on 10 LLMs (6 reasoning, 4 non-reasoning) using three complementary metrics.

## Results

On CORE Lite, Gemini 2.5 Pro achieves the best overall performance with 91.74% F1 on dependency classification, 84.02% correct trace rate, and 50.25% exact match on source enumeration. GPT o3 follows closely with 92.56% F1 (highest classification score) but trails on trace generation (72.80%) and enumeration (42.61%). Reasoning models outperform non-reasoning models by 5.2–31.5% across tasks, while the weakest model (Llama3.1 405B) scores only 68.93% F1, 28.48% CT, and 3.28% EM, highlighting a large performance spread.

## Baselines & Comparisons

Among the 10 evaluated models, Gemini 2.5 Pro leads on trace generation (84.02% CT) and source enumeration (50.25% EM), while GPT o3 achieves the highest classification F1 (92.56%) but lags Gemini by 11.22 points on trace generation. All six reasoning models (Claude 3.7, DeepSeek R1, Gemini 2.5 Pro, GPT o3, GPT o4-mini, Qwen3 235B) outperform the four non-reasoning models (Claude 3.5, DeepSeek V3, GPT 4o, Llama3.1 405B) by a consistent margin of 5.2–31.5%, with the gap largest on source enumeration (e.g., Gemini 2.5 Pro at 50.25% vs. Llama3.1 at 3.28%). Information flow is the hardest task across all models: even the best model (Gemini 2.5 Pro) scores only 68.66% CT and 26.73% EM on InfoFlow trace generation and enumeration, respectively. Control dependency enumeration is relatively easier (avg. 4.0 sources) compared to data and information flow enumeration (avg. 7.7 and 17.0 sources), explaining why models achieve higher EM on control (up to 75.66%) than on data (up to 49.43%) or info flow (up to 26.73%). The paper also shows that requesting a trace alongside classification increases false positives, and that clipping irrelevant context improves performance by up to 5.7%.

## Relation to Prior Work

This paper carves new ground by introducing a fine-grained, human-verified benchmark (CORE) that directly evaluates LLMs on fundamental static analysis properties—data dependency, control dependency, and information flow—rather than end-to-end code outcomes. It departs from existing code reasoning benchmarks (CRUXEval, CRQBench, CodeMMLU, REval) that focus on high-level behaviors, input-output matching, or runtime traces, and from program repair benchmarks (SWE-Bench, SWE-Lancer) that assess patch correctness without probing underlying semantic reasoning. The benchmark construction draws on traditional program analysis concepts (def-use chains, control dependence graphs, information flow) but repurposes them as evaluation targets for LLMs, using a semi-automated annotation pipeline with tree-sitter and manual verification to overcome the infeasibility of full automation (motivated by Rice's Theorem).

## Why It Matters / Open Questions

CORE provides the first systematic, multi-lingual (C/C++, Java, Python) benchmark for assessing whether LLMs truly understand program semantics at the level required for downstream SE tasks like vulnerability detection, program repair, and fuzzing. The finding that even top reasoning models (Gemini 2.5 Pro, GPT-o3) achieve below 50% on source enumeration and that performance drops up to 49.5% for backward dependencies reveals a significant gap between surface-level pattern matching and genuine multi-step semantic reasoning. Key limitations include the restriction to intra-procedural analysis and functions under 100 LoC, and the manual annotation process that limits scalability. Open questions include whether inter-procedural reasoning is tractable for LLMs, how performance degrades under code obfuscation, and whether structure-aware retrieval (rather than standard sparse/dense retrievers) could improve few-shot performance.
