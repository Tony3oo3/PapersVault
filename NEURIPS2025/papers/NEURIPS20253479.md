## Problem

Existing tool-use benchmarks for LLM agents predominantly evaluate single-turn planning and treat tool calls as isolated atomic actions, failing to capture the realistic challenge of coordinating interdependent tools across multi-turn, multi-domain conversations. This paper addresses the gap by introducing a dataset and evaluation framework that specifically tests an agent's ability to reason about tool selection order, manage inter-tool dependencies, and make dynamic replanning decisions (e.g., whether to recompute or reuse cached results) over extended dialogues.

## Input / Output

At each user turn, the agent receives the full conversation history, a deterministic rule-based summary of the execution cache (rather than the full cache, to manage token load), and the set of 14 tool definitions. It outputs executable Python code that invokes domain-specific tools (e.g., search_flights, search_hotels), generic utilities (e.g., adjust_date, filter_flights), and cache-management tools (save_to_cache, get_results_from_cache), or issues information-seeking queries to the user when mandatory parameters are missing. The generated code is executed in a sandboxed environment, and the resulting cache state is updated for subsequent turns.

## Method

T1 is a 13.5k-dialogue dataset spanning four single-domain and five multi-domain travel settings (flights, hotels, restaurants, attractions, and their combinations), constructed via a three-step pipeline: (1) Llama-3.3 70B generates 60 dialogue templates per category with placeholder entities, (2) human annotators write ground-truth Python code using 14 predefined tools, and (3) placeholders are programmatically filled from a knowledge base of 321 US cities, 128 airports, 480k synthetic flights, 47k hotels, and 18k restaurants, with city-level partitioning to prevent data leakage. T1-AGENT evaluates models by generating code per user turn with a caching mechanism that enables dynamic replanning: the agent decides whether to re-invoke a tool or retrieve and filter previously cached results. For domain adaptation, the authors apply LoRA-based supervised fine-tuning (one epoch, 8×A100 GPUs) on Llama 3.1 8B Instruct, and evaluate both SFT and few-shot (k=13) in-context learning across open-weight and proprietary models using metrics for tool-call F1, parameter matching, code execution rate, information-seeking quality (SacreBLEU/BERTScore), and cache-summary exact match.

## Results

On the large dataset (1,000 dialogues per domain), the domain-adapted Llama 3.1 8B Instruct SFT model achieves the highest Tool Call F1 (87.17) and Parameter Matching F1 (75.76) among open-weight models, surpassing the base Llama 3.1 8B Instruct (52.11 and 31.79) and even the much larger Llama 3.3 70B Instruct (79.72 and 67.74). On the small dataset, proprietary models lead overall: Gemini 2.5 Pro reaches 94.28 Tool Call F1 and 94.46 Code Execution Rate, while GPT-5 achieves 93.14 Tool Call F1 and 76.25 Cache Summary EM. The SFT 8B model's Cache Summary EM (63.95) and Information Seeking SacreBLEU (41.58) are the best among all evaluated models, demonstrating that task-specific fine-tuning yields strong performance even at small scale.

## Baselines & Comparisons

Among the two explicitly cited baselines, s1.1 32B (82.72 Tool Call F1, 70.01 Param. Match F1) outperforms Phi-4-reasoning-plus (69.14, 51.84) on both tool-calling and parameter-matching metrics, but both are substantially outperformed by the SFT-adapted Llama 3.1 8B (87.07, 75.39). The SFT 8B model also beats s1.1 32B on Code Execution Rate (83.77 vs. 60.65) and Cache Summary EM (63.79 vs. 52.75), while Phi-4-reasoning-plus edges out s1.1 32B on Code Execution Rate (86.45 vs. 60.65). Against proprietary models, the SFT 8B trails Gemini 2.5 Pro by ~7 points on Tool Call F1 and ~9 points on Parameter Matching F1, and GPT-5 by ~6 and ~11 points respectively, indicating a persistent gap between fine-tuned open-weight and top proprietary systems. Notably, the SFT 8B model achieves the highest Cache Summary EM (63.79) and Information Seeking SacreBLEU (42.39) among all open-weight models, and even surpasses several proprietary models on these specific metrics.

## Relation to Prior Work

This paper carves new ground by combining multi-turn conversational context, multi-domain tool planning, inter-tool dependencies, and a caching mechanism into a single benchmark—none of which prior tool-use datasets (APIBank, TravelPlanner, ToolBench, GTA, etc.) address simultaneously, as summarized in their comparison table. Conceptually, it extends the single-turn, single-domain tool-calling evaluation paradigm (e.g., Toolformer, APIBank) into a stateful, dialog-driven setting where agents must decide whether to recompute or reuse cached results. The T1-AGENT architecture, which generates executable Python code per turn and leverages a rule-based cache summary to manage context, draws on the code-generation-as-planning approach but adds the novel dimension of dynamic replanning across turns.

## Why It Matters / Open Questions

T1 provides the first comprehensive benchmark for evaluating multi-turn, multi-domain tool-use agents with inter-tool dependencies and caching, filling a clear gap identified in the literature where prior datasets treat tool calls as isolated atomic actions. The finding that a LoRA-fine-tuned 8B model outperforms a 70B model on most metrics underscores the practical value of task-specific adaptation for agentic workloads, while the persistent gap between open-weight and proprietary models on tool calling highlights remaining challenges. Limitations include the travel-only domain, synthetic entity generation, and US-centric geography, leaving open whether the caching and dependency mechanisms generalize to other application domains. Future work could extend T1 to additional domains, explore whether the caching benefit persists with longer contexts, and investigate whether the SFT advantage holds under distribution shift.
