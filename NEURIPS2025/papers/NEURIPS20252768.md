## Problem

Foundation models require sophisticated multimodal data processing pipelines, but existing frameworks are either text-only, lack cross-modal semantic-aware operations, or struggle with the unique computational pattern of simple per-sample operations applied at petabyte scale. Data-Juicer 1.0 addressed text pre-training with ~50 operators but could not handle images, video, audio, post-training tasks, or scale beyond ~1,000 cores. The paper tackles the combined gaps in multimodal functionality, efficiency-scalability tradeoffs, and ecosystem fragmentation across dataset hubs and compute engines.

## Input / Output

The system consumes multimodal datasets (text, image, video, audio) in formats such as JSONL, Parquet, and MP4 from local paths, Hugging Face, or ModelScope hubs, with an intermediate token-aligned schema that represents media via special tokens (e.g., <__dj__image>) and chunk-based separators to preserve positional relationships across interleaved content. Processing is specified via YAML recipes, low-level Python API calls, RESTful endpoints, or natural language instructions interpreted by a ReAct-based agent. Outputs include cleaned/filtered datasets, synthesized or annotated samples (e.g., captions, QA pairs, preference data), deduplicated corpora, and per-operator insight reports tracking statistical and semantic shifts across the pipeline.

## Method

Data-Juicer 2.0 is a layered system with 150+ composable operators (Mappers, Filters, Deduplicators, Groupers, Aggregators, FusedOP, HumanOP) spanning four modalities, where model-based OPs integrate foundation models (Qwen, SDXL, BLIP-2, CLIP) as first-class pipeline components for semantic filtering and cross-modal synthesis. The runtime introduces a unified Data-Juicer-Dataset class using a Facade pattern to abstract over Hugging Face Datasets, Ray Data, and MaxFrame-DataFrame, enabling seamless transitions between standalone and distributed execution. Key adaptive optimizations include: (1) workload-aware OP reordering via probe_small_batch() that estimates per-OP speeds and reorders within commutativity constraints, (2) automatic resource allocation that assigns GPU/quantization to model-based OPs and hierarchical batched/multiprocessing/multithreading parallelism to I/O-bound OPs, (3) adaptive data pre-splitting for Ray that reduces peak network I/O from ~160 MB/s to ~60 MB/s, and (4) operator-level checkpointing with fine-grained recovery that avoids full pipeline restarts on transient failures. The MinHash-based RayDeduplicator achieves 3.3× speedup over vanilla Ray through load-balanced union-find and hash-based aggregation, processing 5 TB in 2.8 hours on 8 CPU nodes.

## Results

Data-Juicer 2.0 scales to ~70B samples (PB-level) across 10,000+ CPU cores, a 100x data-scale and 10x compute-scale improvement over its predecessor. The MinHash-based RayDeduplicator processes 5TB of data in 2.8 hours using 8 Ray nodes (1,280 CPU cores), achieving a 3.3x speedup over vanilla Ray. Key adaptive optimizations yield substantial gains: workload-aware OP reordering cuts processing time by up to 70.22%, automatic GPU resource allocation saves up to 99% of processing time, and adaptive data splitting provides 2x–3x acceleration on large datasets (reducing peak network I/O from ~160 MB/s to ~60 MB/s).

## Baselines & Comparisons

The primary external comparison is with NVIDIA's NeMo Curator on large-scale deduplication. NeMo Curator (leveraging cuDF and Dask) processes 1.1 TB of Redpajama data in 1.8 hours using 64 A100 GPUs (~396K CUDA cores), whereas Data-Juicer's RayDeduplicator processes 5 TB (~4.5× more data) in 2.8 hours using only 1,280 CPU cores across 8 Ray nodes — a substantially more resource-efficient configuration. Internally, the paper benchmarks three execution engines (Standalone/HF Datasets, Ray, MaxCompute) across small, medium, and large scales: at small scale (≤2.24M samples), standalone mode is competitive; at medium scale (56M samples), Ray on DLC outperforms ECS by 24.8%; at large scale (70B samples), MaxCompute is fastest for text-only workloads (~1/4 the time of Ray with 1/2 fewer cores), while Ray-DLC is preferred for multimodal recipes due to MaxCompute's overhead in loading large multimodal files. The adaptive subset splitting strategy also outperforms Ray's default block-splitting, reducing peak network I/O from ~160 MB/s to ~60 MB/s and achieving more consistent CPU utilization across nodes.

## Relation to Prior Work

This paper is a direct architectural extension of Data-Juicer 1.0, which provided ~50 text-only operators for LLM pre-training data curation. It generalizes the operator-based pipeline paradigm to multimodal data (text, image, video, audio) and post-training tasks (SFT, RFT, RLHF), while integrating foundation models (Qwen, SDXL, BLIP-2) as first-class processing primitives rather than external tools. The runtime layer builds on Hugging Face Datasets for standalone execution and Ray for distributed scaling, with additional integration of Alibaba MaxCompute for cloud-scale text processing, and departs from prior systems by introducing adaptive execution (OP reordering, auto resource allocation, operator-level checkpointing) that abstracts away engine-specific complexities. The natural language interface leverages AgentScope and ReAct agents, and the HumanOP type builds on Label Studio for human-in-the-loop workflows.

## Why It Matters / Open Questions

This is a practically significant open-source system already in production at Alibaba Cloud (PAI-Designer, DLC-Ray), processing TB-level data for over five months and supporting 3,000+ teams in data competitions. It addresses a real ecosystem gap: no prior open-source framework unified multimodal data processing with foundation-model-based semantic operations at cloud scale. Key limitations include a single-node transmission bottleneck in Ray's head node, lack of GPU backend engines (e.g., NeMo Curator-style), and limited multilingualism. Open questions include whether the adaptive execution strategies generalize beyond the tested workloads, how the system scales to the next order of magnitude (PB-level), and whether the storage-compute co-design insights transfer to non-Alibaba cloud environments.
