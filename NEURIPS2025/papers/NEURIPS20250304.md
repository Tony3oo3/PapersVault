## Problem

LLMs generate functionally correct code but consistently produce solutions with suboptimal computational efficiency, a critical bottleneck for real-world deployment where latency and memory budgets are paramount. Existing fine-tuning approaches (SFT, DPO) quickly saturate in efficiency gains because they learn static patterns or offline preferences that cannot adapt to novel inefficiencies. The paper asks whether reinforcement learning with real-time execution feedback can enable LLMs to truly self-improve code efficiency through iterative test-time optimization, and dissects why online RL outperforms offline methods in this setting.

## Input / Output

The Afterburner model receives a problem description, an efficiency instruction (time-efficient, memory-efficient, or integral-efficient), an optional original code solution, and its Monolith-derived performance metrics (pass/fail status, execution time, peak memory, integral score) as a single-turn prompt. It outputs a structured response with reasoning in <thinking> tags followed by the optimized code in <solution> tags, which is then parsed and executed. At inference, the framework runs a greedy iterative loop: each iteration's generated code is executed in the Monolith sandbox, and the better-performing code (compared against the current best) is carried forward as the next iteration's input, repeating for a fixed number of iterations.

## Method

The core contribution is the Iterative Optimization Framework (IOF), a closed-loop system pairing Afterburner (the code optimization model) with Monolith, a Docker-based execution sandbox that provides empirical time, memory, and integral metrics with 95% confidence intervals via bootstrapping. The paper compares three training strategies on the Venus dataset: SFT (cross-entropy on inefficient→efficient code pairs), DPO (preference optimization on ranked code triples with the SFT model as reference), and GRPO (group-relative policy optimization with 16 online rollouts per prompt evaluated by Monolith). GRPO's composite reward combines format compliance (±1), functional correctness with upgrade/downgrade penalties relative to the baseline code (±1.0/±0.5), and a tanh-scaled relative efficiency gain, with correctness weighted at β_c=0.5 to ensure training stability. The key mechanistic insight is that GRPO's online interaction with execution feedback cultivates adaptive optimization proficiency—actively exploring diverse algorithmic solutions and learning from its own successes and failures—whereas SFT memorizes superficial transformation patterns and DPO internalizes static pairwise preferences, both of which plateau after a few iterations. This is validated by GRPO boosting PASS@1 from 47% to 62% and BEYOND-I from 31% to 45% over 10 iterations on Venus, while SFT and DPO saturate early, and by ablations showing GRPO degrades most severely when feedback or original code context is removed.

## Results

On the Venus benchmark, Afterburner_GRPO (trained on Qwen 2.5 3B) at iteration 10 achieves 61.67% PASS@1, 45.17% BEYOND-T, 48.05% BEYOND-M, and 38.95% BEYOND-I, substantially outperforming its base model (Qwen 2.5 3B: 27.99% PASS@1, 12.40% BEYOND-T). The iterative optimization framework boosts PASS@1 from 47% to 62% and BEYOND-I from 31% to 45% over successive iterations. In Table 3, Afterburner_GRPO achieves the highest 'Better than all human' (B%) scores across all efficiency dimensions: 8.00% for time, 7.00% for memory, and 5.33% for integral, surpassing even reasoning models like O4-mini (7.00% time B%) and QwQ 32B (6.67% time B%).

## Baselines & Comparisons

Afterburner_GRPO, built on the small Qwen 2.5 3B base, dramatically outperforms its base model (PASS@1: 61.67 vs. 27.99; BEYOND-T: 45.17 vs. 12.40) and even surpasses much larger open-source models like Qwen 2.5 7B Instruct (60.78 PASS@1, 27.67 BEYOND-T) and Llama 4 Scout (62.82 PASS@1, 33.10 BEYOND-T) on efficiency metrics. Against closed-source models, Afterburner_GRPO beats GPT-4o on BEYOND-T (45.17 vs. 38.22) and BEYOND-M (48.05 vs. 42.09), and approaches Claude 3.7 Sonnet on BEYOND-M (48.05 vs. 49.86), though it trails the top reasoning models (O4-mini, QwQ 32B) on absolute efficiency. The SFT variant, by contrast, plateaus early and remains well below the base 7B models, confirming that RL with execution feedback is essential for sustained iterative gains. On the APPS benchmark (Table 9), Afterburner shows similar improvement patterns, confirming generalization beyond the Venus distribution. In the human-comparison analysis (Table 3), Afterburner_GRPO achieves the highest B% (better-than-all-human) scores, indicating it discovers structurally novel optimizations beyond canonical human approaches.

## Relation to Prior Work

This paper extends the code efficiency optimization line (EffiBench, Mercury, PIE4PERF, EVALPERF) by introducing a closed-loop iterative test-time optimization framework where an LLM (Afterburner) is guided by real execution feedback from a sandbox (Monolith). Methodologically, it builds directly on GRPO (DeepSeekMath) for the RL training loop and DPO for the preference-optimization baseline, but departs from prior RL-for-code work (CodeRL, RLEF, StepCoder) by targeting computational efficiency rather than functional correctness as the primary reward signal. The Venus dataset extends Mercury's percentile-rank evaluation paradigm to a multilingual setting with substantially more reference solutions per task (avg. 106.6 vs. 18.4).

## Why It Matters / Open Questions

The paper provides a clean empirical demonstration that online RL with execution feedback enables sustained iterative code optimization, while SFT and DPO plateau after a few iterations—a distinction that matters for practitioners choosing training strategies for test-time compute scaling. The Venus benchmark (multilingual, 1,300 test tasks, ~79 solutions per task) and the Monolith sandbox are reusable infrastructure for the code-efficiency community. Key open questions include whether the approach generalizes to real-world software repositories with complex code contexts, whether the 3B model results scale to larger architectures, and whether the multi-turn history-aware variant (which underperformed) can be made to work with proper credit-assignment techniques.
