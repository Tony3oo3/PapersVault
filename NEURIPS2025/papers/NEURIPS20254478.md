## Problem

While LLMs are increasingly explored as scientific research assistants, no prior benchmark evaluates whether an LLM-mediated workflow produces visualizations that convey correct scientific insights. Existing coding benchmarks test general programming or isolated scientific computation but do not assess the end-to-end process of implementing domain-specific research workflows that culminate in publication-quality visualizations.
![Teaser figure](../imgs/NEURIPS20254478/cropped_page1_idx0.webp)

## Input / Output

The subject LLM receives a natural language query (synthesized to mimic how an astronomer would phrase a task without step-by-step specifics) along with prior Jupyter notebook cells as context, and must generate a single Python code cell. For processing tasks, the generated code is executed and its output variables are compared against ground-truth key products via a variable inspection score. For visualization tasks, the executed code produces a rendered figure that is compared against a ground-truth visualization using a VLM-as-a-judge, with the judge receiving both images, both code snippets, and the original query.

## Method

ASTROVISBENCH comprises 864 tasks (432 processing, 432 visualization) extracted from 110 curated Jupyter notebooks spanning spectroscopy, photometry, image processing, time series, cosmology, and simulation. The benchmark introduces two complementary evaluation pipelines: an execution-based variable inspection test for processing tasks that measures recall of key intermediate variables, and a VLM-as-a-judge for visualization tasks that classifies errors as No Error, Minor Error, or Major Error. The VLM judge (Claude 3.5 Sonnet) was validated against 270 gold-standard annotations from five professional astronomers, achieving Spearman correlations of 0.82+ with expert judgments. Queries are LLM-synthesized to avoid leaking domain knowledge while remaining specific enough for reliable evaluation, with underspecified spans resolved to concrete values from ground-truth code. The benchmark covers 38 libraries (26 astronomy-specific) and diverse visualization types including color-magnitude diagrams, spectral energy distributions, all-sky projections, and time-series light curves.

## Results

Across 864 tasks (432 processing, 432 visualization), even the best model (Gemini 2.5 Pro) crashes on 30.8% of processing tasks and 20.1% of visualization tasks, with ~43% of all generated code failing to execute. The highest variable inspection score (VI score) is 0.694 (o3-mini), meaning even the best model recovers only ~70% of required processing products. For visualization, Gemini 2.5 Pro achieves the highest 'No Error' rate (15.7%) but still produces major errors in 28.5% of cases; at least 58% of the time, the best models produce code that either fails to generate a visualization or yields one with major errors.

## Baselines & Comparisons

The paper evaluates eight state-of-the-art LLMs (Gemini 2.5 Pro, Claude 3.7 Sonnet, Claude 4.0 Opus, o3-mini, GPT-4o, QwQ, Qwen-2.5, Llama-4 Maverick) as the subject models on the new ASTROVISBENCH benchmark. Gemini 2.5 Pro leads in code executability (lowest crash rates: 30.8% processing, 20.1% visualization) and in producing correct visualizations (15.7% No Error), but its VI score (0.600) is not the highest, showing that fewer crashes does not guarantee correct scientific computing. o3-mini achieves the best VI score (0.694) and the lowest VisFail rate (2.8%), indicating it most reliably produces the required intermediate variables and a single visualization, yet still suffers 29.6% major errors. Claude 4.0 Opus has the lowest major error rate (16.0%) among models that execute, but its high crash rate (50.3% processing) limits its overall utility. GPT-4o and QwQ trail significantly on VI scores (0.480 and 0.472), reflecting poor knowledge of domain-specific astronomy APIs. No model exceeds 16% 'No Error' on visualization tasks, confirming a substantial gap in current LLMs' ability to produce publication-quality astronomical visualizations.

## Relation to Prior Work

This paper carves new ground by combining three previously separate threads: execution-based code evaluation (as in SWE-bench and BigCodeBench), LLM/VLM-as-a-judge for output quality assessment (as in VisEval and EvaLLM), and domain-specific scientific coding benchmarks (as in SciCode and PaperBench). No prior benchmark evaluates the full pipeline from scientific data processing through to domain-standard visualization in a specific research field, and the authors explicitly note that evaluating whether an LLM-mediated workflow produces visualizations conveying correct scientific insights 'has not been addressed in past work.' The VLM-as-judge methodology is validated against five professional astronomers, distinguishing it from prior visualization evaluation that relies on rule-based or surface-level code similarity metrics.

## Why It Matters / Open Questions

ASTROVISBENCH provides the first end-to-end evaluation framework for AI assistants in domain-specific scientific research workflows, revealing that even the strongest SOTA models fail at least 58% of the time on astronomy tasks—a gap that was previously unquantified. The validated VLM-as-judge approach offers a reusable template for building expert-informed automatic evaluation in other scientific domains (physics, biology, chemistry) where visualization is central to insight. Key open questions include whether the poor performance stems primarily from insufficient training data on niche libraries (e.g., ADQL, specutils, photutils) or from deeper reasoning gaps, and whether the benchmark's single-domain focus (astronomy) limits generalizability of the findings to other scientific fields with different tool ecosystems.
