## Problem

Building executable test environments for code repositories is labor-intensive, time-consuming, and expert-knowledge-dependent, creating a critical bottleneck for scaling up executable code data for LLM training and evaluation. Existing approaches either rely on unreliable static code metrics or require developers to manually build limited repository environments without scalability. No prior work automates the full pipeline of environment building and Dockerfile synthesis at scale.
![Teaser figure](../imgs/NEURIPS20251096/cropped_page0_idx0.webp)

## Input / Output

The method takes a Python code repository (with pytest-compatible unit tests in test/ or tests/ directories) as input and produces a runnable Dockerfile as output. The Dockerfile is structured using four keywords (FROM, ENV, COPY, RUN) and encodes the exact sequence of dependency installations, environment variable settings, and code modifications needed to reproduce the working environment. The generated Dockerfile must satisfy two criteria: it builds without errors, and pytest can execute (regardless of pass/fail) within the resulting container.

## Method

Repo2Run is an LLM-based agent (gpt-4o) that operates in two phases: a build phase and a record phase. During the build phase, it employs a dual-environment architecture where an internal Docker container executes five actions (environment monitoring, dependency installation, test running, code editing, bash commands) while an external terminal handles three supporting actions (rollback via docker commit snapshots, base image change, and output truncation). The rollback mechanism is critical: before each non-safe command, a snapshot is taken, and if the command fails (non-zero return code), the environment is restored to prevent 'pollution' that would make the Dockerfile non-reproducible. During the record phase, a rule-based Dockerfile synthesizer converts the validated command sequence into Dockerfile statements, pinning package versions and converting export commands to persistent ENV statements. The agent follows the ReAct framework, iteratively observing test results and adjusting the build until all tests execute successfully.

## Results

On the 420-repository Python benchmark, Repo2Run achieves a 100% Dockerfile Generation Success Rate (DGSR) and an 86.0% Environment Building Success Rate (EBSR), successfully building executable environments for 361 out of 420 repositories. This represents a 63.9 percentage-point improvement over the strongest baseline (LLM generator at 22.1% EBSR) and a 77.0 percentage-point improvement over SWE-agent (9.0% EBSR). The average time to successfully build an environment is 29.03 minutes, comparable to the 21.33-minute average for manual building by experienced developers.

## Baselines & Comparisons

Repo2Run decisively outperforms all three baselines on both metrics. Against pipreqs (a rule-based dependency extraction tool), Repo2Run improves EBSR from 6.0% to 86.0% and DGSR from 29.8% to 100%, as pipreqs frequently fails on version conflicts (63.1% of cases) and cannot produce a buildable Dockerfile. Against the LLM generator (which reads the README and directly writes a Dockerfile), Repo2Run achieves 86.0% vs. 22.1% EBSR and 100% vs. 47.6% DGSR; the LLM generator lacks any verification or rollback mechanism, so its Dockerfiles often fail to build. Against SWE-agent (a general-purpose LLM agent with bash, file editing, and reading actions), Repo2Run achieves 86.0% vs. 9.0% EBSR and 100% vs. 26.9% DGSR; the paper attributes SWE-agent's weakness to its lack of specialized actions for environment building (e.g., no rollback, no base image switching, no dependency management), causing it to get stuck on four recurring error types. Notably, the LLM generator outperforms SWE-agent, suggesting that a general agent framework without domain-specific actions is less effective than a simple prompt-based approach for this task.

## Relation to Prior Work

Repo2Run adopts the ReAct action-observation loop as its core interaction paradigm but departs sharply from general-purpose coding agents like SWE-agent by introducing a purpose-built dual-environment architecture (internal Docker container + external terminal) with specialized actions including an adaptive rollback mechanism. It positions itself against prior Dockerfile generation tools (pipreqs, DockerizeMe, DockerGen) that rely on static analysis or template matching, instead using iterative LLM-driven exploration with test-based verification. The paper explicitly notes that no prior LLM-based agent was designed specifically for automated executable environment building, carving out a new problem space at the intersection of LLM agents and containerized infrastructure.

## Why It Matters / Open Questions

This work addresses a critical scalability bottleneck: the manual, expert-dependent process of building executable environments that limits the growth of SWE-bench-style datasets and RL training for software engineering agents. The 86% success rate on a 420-repo benchmark, combined with a 100% Dockerfile build success rate, makes it a practical foundation for scaling executable code data. Key limitations include Python-only scope, dependence on GPT-4o, and residual failures on hardware-intensive or timeout-prone repositories. Open questions include generalization to other languages, handling of monorepos with complex multi-service dependencies, and whether the approach transfers to environments requiring GPU or proprietary hardware.
