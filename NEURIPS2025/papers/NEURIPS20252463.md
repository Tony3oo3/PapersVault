## Problem

Evaluating LLM-based code optimization requires performance-stressing tests that expose implementation-specific bottlenecks, but existing approaches either rely on correctness tests that fail to reveal inefficiencies or prompt LLMs to generate length-stressing inputs that miss nuanced performance-characterizing behaviors (e.g., reverse-sorted input triggering O(n²) quicksort). The core difficulty is that LLMs struggle to reason end-to-end from local program behavior (e.g., a deeply nested variable being reverse-sorted) back to the program inputs that would trigger it.

## Input / Output

WEDGE takes a competitive-programming problem statement, a correct C++ solution, a set of default correctness test inputs, and an LLM (GPT-4o), and produces a set of performance-stressing test inputs (top-10 slowest per program, forming the PERFFORGE benchmark) along with C++ constraint-checker functions instrumented into the fuzz driver. Inputs must conform to the problem's validity specification, and generated tests are filtered through an LLM-synthesized validator plus a cross-solution output-consistency check (95% agreement threshold) before selection.

## Method

WEDGE decomposes stress-test generation into two sub-problems: (1) local performance-characterizing constraint reasoning, delegated to the LLM, and (2) constraint-guided input search, delegated to a coverage-guided fuzzer. In the profiling stage, WEDGE mines a contrastive (slow, fast) input pair from existing tests using similarity and execution-cost-ratio ranking, then collects per-statement hit counts. The LLM then reasons in multiple phases—identifying expensive code fragments, deriving natural-language constraints, and implementing them as C++ conditional checkers inserted at appropriate program points. For the search stage, WEDGE replaces AFL++'s default byte-level mutator with an LLM-generated constraint-aware mutator that steers mutations toward constraint-satisfying inputs while respecting input grammars, and uses the inserted checker branches as explicit coverage signals to bias the fuzzer toward exercising inefficient code paths. This design avoids expensive iterative LLM queries during search and sidesteps the need for the LLM to reason globally about input-to-behavior mappings.

## Results

On CodeContests (154 problems, 33,020 C++ programs), WEDGE-generated tests (PERFFORGE) cause programs to execute 5.96×10⁸ average CPU instructions (median 0.75×10⁸), a 363× average slowdown over default CodeContests tests. WEDGE achieves a 60% win rate (i.e., its tests are the slowest among all techniques) and outperforms the strongest baseline (EVALPERF_SLOW) by 84.5% in average instruction count. Constraint-satisfying inputs are 38.6× slower on average than constraint-violating inputs, confirming the discriminative power of the synthesized constraints.

## Baselines & Comparisons

WEDGE dominates all four baselines across every metric. Against EVALPERF_SLOW (the strongest LLM-based baseline), WEDGE generates tests that execute 84.5% more CPU instructions on average (5.96 vs. 3.23 ×10⁸) and achieves a 60% win rate versus EVALPERF_SLOW's 8%. Against TG-prompt (direct LLM prompting for test generators), WEDGE leads by 54% in average instructions and 48 percentage points in win rate (60% vs. 12%). Against PerfFuzz (coverage-guided performance fuzzing), WEDGE achieves 81.5% more instructions and a 49-point win-rate advantage (60% vs. 11%). The gap widens for small inputs (<1KB), where WEDGE's advantage over TG-prompt nearly doubles (3.0× vs. 1.5× slowdown), confirming that WEDGE's gains come from targeting implementation-specific bottlenecks rather than merely increasing input length. In utility experiments, PERFFORGE tests improve EFFI-LEARNER's code optimization by ~10 percentage points over default tests and reveal 24–149% more speedup for PIE-optimized code, demonstrating that the performance-stressing tests expose bottlenecks invisible to correctness-only evaluation.

## Relation to Prior Work

WEDGE sits at the intersection of two prior lines of work: LLM-based test generation (EvalPerf, TG-prompt) and performance-aware fuzzing (PerfFuzz, SlowFuzz). It departs from both by decomposing the end-to-end input synthesis problem into a local LLM reasoning step (synthesizing performance-characterizing constraints as branch predicates) and a fuzzer-driven search step (AFL++ with a custom constraint-aware mutator). This decomposition is inspired by the contrastive profiling idea from feedback-based debugging, but repurposed here to guide constraint synthesis rather than bug localization. The resulting PERFFORGE benchmark extends CodeContests with performance-stressing tests, filling a gap that prior efficiency benchmarks (EvalPerf, EffiBench, COFFE) left open by relying on length-stressing or correctness-only inputs.

## Why It Matters / Open Questions

The paper demonstrates that existing code efficiency benchmarks systematically understate performance gaps because their tests fail to exercise implementation-specific bottlenecks, which has downstream consequences for evaluating and improving LLM-based code optimization. The PERFFORGE benchmark and the WEDGE method provide a practical path to more faithful performance evaluation, and the utility experiments (≈10 pp additional efficiency gain with EffiLearner, 24–149% higher measured speedup for PIE) show concrete impact on the code-optimization pipeline. Key limitations include the per-solution token and execution overhead, the dependence on mining contrastive input pairs from an existing test corpus, and AFL++'s input-length ceiling (~10 MB), which restricts applicability to problems with very large inputs. Extending the constraint-synthesis + guided-fuzzing paradigm to repository-level or real-world workloads remains an open direction.
