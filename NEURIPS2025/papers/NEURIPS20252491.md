## Problem

Existing code efficiency benchmarks for LLM-generated code suffer from three critical limitations: they are predominantly single-language (mostly Python), rely on widely circulated problem sets (LeetCode, HumanEval, MBPP) that risk data contamination, and feature tasks of limited algorithmic complexity that fail to expose meaningful efficiency differentials. EFFIBENCH-X addresses all three gaps by introducing the first multi-language benchmark built from recent, complex competitive programming problems with verified human-expert baselines.

## Input / Output

The benchmark consumes natural language problem descriptions (competitive programming tasks) and LLM-generated code solutions, which are executed inside Docker containers pinned to dedicated physical CPU cores under a 10-second timeout and 1024 MiB memory limit. Each problem is evaluated against 100 test cases produced by an LLM-generated test case generator, with correctness verified by a logical (not string-based) evaluator. The output is three efficiency scores—Execution Time (ET), Memory Peak (MP), and Memory Integral (MI)—each computed as the per-problem ratio of expert-to-LLM resource usage clipped to [0,1] and averaged across all 623 problems, alongside a Pass@1 correctness rate.

## Method

EFFIBENCH-X's construction pipeline has four stages: (1) collecting 623 competitive programming problems from five platforms (Aizu, AtCoder, CodeChef, Codeforces, LeetCode) released after October 2023 to minimize training-data contamination; (2) assembling canonical expert solutions in all six target languages (Python, C++, Java, JavaScript, Ruby, Golang) from public forums, platform APIs, and open-source repositories, with missing translations performed by o3-mini under strict algorithm-preservation instructions, and all solutions verified by resubmission to their original platforms; (3) generating per-problem test suites via LLM-prompted test case generators and solution evaluators, validated through multi-stage execution checks with up to 3 automatic repair attempts; and (4) executing all code in a sandboxed Docker environment with a custom high-resolution profiler sampling at 10 kHz to capture peak memory and time-series resource usage. Efficiency is quantified by comparing each LLM solution's runtime, peak memory, and memory-time integral against the best expert baseline per metric, with ratios clipped at 1 to cap the influence of outlier-fast solutions.

## Results

On EFFIBENCH-X (623 competitive programming tasks across 6 languages), the best-performing model Qwen3-32B achieves 62.21% Execution Time (ET) and 61.48% Memory Integral (MI), while Gemini-2.5-Pro leads in Memory Peak (75.60%) and Pass@1 (79.43%). DeepSeek-R1 is the strongest open-source model overall (ET 61.33%, MP 69.41%, MI 60.06%, Pass@1 72.79%). Even the most efficient LLM-generated solutions reach only ~62% of human-expert runtime performance on average, with significant language-specific gaps: Python (67.30% ET for DeepSeek-R1) substantially outperforms Java (52.23%) and Go (60.24%).

## Baselines & Comparisons

Among open-source models, Qwen3-32B edges out DeepSeek-R1 on ET (62.21% vs. 61.33%) and MI (61.48% vs. 60.06%), while DeepSeek-R1 leads on MP (69.41% vs. 67.26%) and Pass@1 (72.79% vs. 70.41%). Among proprietary models, Gemini-2.5-Pro dominates in correctness (Pass@1 79.43%) and memory peak (75.60%), but its ET (47.82%) and MI (45.08%) trail both Qwen3-32B and DeepSeek-R1, indicating that top proprietary models are not necessarily the most time-efficient. GPT-4o (ET 24.53%, Pass@1 43.61%) and Claude-3.7-Sonnet (ET 47.79%, Pass@1 56.23%) fall well behind the leaders on all metrics. Language-specific analysis (Table 5) reveals that DeepSeek-R1's Python ET (67.30%) exceeds its Java ET (52.23%) by 15 percentage points, while Claude-3.7-Sonnet shows a similar gap (51.90% vs. 46.33%), confirming that dynamically typed languages yield more efficient LLM-generated code. The Llama-4 series (ET 16–23%) and Gemma-3 series (ET 10–17%) represent the weakest performers, highlighting a wide capability spread across model families.

## Relation to Prior Work

This paper extends the line of code-efficiency benchmarks (EffiBench, Mercury, EvalPerf, ENAMEL, PIE) by addressing three limitations they share: single-language focus (mostly Python), data contamination from widely circulated problem sets (LeetCode, HumanEval, MBPP), and limited task complexity. It draws on the sandboxed execution infrastructure from llm-sandbox and CodeArena, and adopts the ratio-based efficiency metrics (ET, MP, MI) established by EffiBench and ENAMEL. The key conceptual departure is sourcing problems from recent (post-October 2023) competitive programming platforms across six languages, paired with verified human-expert solutions as baselines, rather than reusing existing function-level benchmarks.

## Why It Matters / Open Questions

The finding that even the best LLM (Qwen3-32B) reaches only ~62% of human expert efficiency, with a pronounced gap between dynamically typed (Python, Ruby, JS) and statically typed (Java, C++, Go) languages, provides a concrete target for optimization research and cautions against assuming language-agnostic code quality from LLMs. The identification of algorithmic complexity (not micro-optimizations) as the dominant inefficiency source suggests that improving LLMs' algorithm selection and pruning strategies would yield the largest gains. Open questions include whether efficiency-aware fine-tuning or RL can close the gap, whether the competitive-programming focus generalizes to system-level and I/O-intensive code, and how to extend the benchmark to capture hardware-specific optimizations (cache locality, vectorization).
