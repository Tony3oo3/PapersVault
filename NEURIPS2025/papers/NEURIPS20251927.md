## Problem

Existing private inference frameworks for LLMs (e.g., BOLT, Bumblebee, CipherPrune) only support dense architectures and cannot handle the dynamic routing mechanism inherent to Mixture-of-Experts layers. Revealing which experts are activated for a given token leaks sensitive information about both the input's semantic content and the model's internal expert specialization, yet naively routing all tokens through all experts (the dense baseline) incurs up to 15× computation overhead, negating the efficiency benefits of MoE sparsity.

## Input / Output

The client P0 and server P1 each hold additive secret shares of m input token embeddings [x] ∈ Z^{m×d}, where d is the hidden dimension. The server additionally holds the MoE model weights in plaintext. The protocol outputs the secret-shared MoE layer result [y] ∈ Z^{m×d}, from which the client can reconstruct the final LLM output. Crucially, all routing scores [W], expert indices [K], and per-expert token assignments remain as secret shares throughout; no party learns which experts were activated or how many tokens each expert received.

## Method

CryptoMoE introduces Inference-Time Balanced Expert Routing, where each of the n experts processes exactly t tokens (with dummy padding or token dropping) so that expert contributions become input-independent, preserving routing privacy without increasing total computation. To mitigate accuracy loss from token dropping, a confidence-aware selection strategy re-ranks tokens assigned to each expert by their routing score W and retains only the top-t. The secure dispatch protocol (Π_dispatch) computes per-expert priority scores via Π_equal and Π_mux, selects top-t indices via Π_topk, and retrieves token embeddings via Π_onehot and HE-based Π_matmul, reducing communication from O(nkmtd) (CipherPrune's secure swaps) to O(nkm·log(km) + ntm). The combine protocol (Π_combine) reuses the dispatch one-hot matrices with a single Π_mul and Π_matmul to reorder and weight expert outputs. Finally, a Batch Ciphertext-Plaintext MatMul protocol packs partial token embeddings from all n experts into a single ciphertext of shape (nt × d₁/n), reducing HE rotations from O(nd₁) to O(d₁) and accelerating the dominant expert linear layers by 3–6×.

## Results

On three MoE-based LLMs (DeepSeekMoE-16.4B, OLMoE-6.9B, QWenMoE-14.3B) evaluated across eight zero-shot reasoning tasks, CryptoMoE (t=2.0) retains 99.2% of the original model's average accuracy (61.8%, 62.5%, 62.0% vs. 62.2%, 63.0%, 62.0% for the insecure baseline). Compared to the dense baseline, CryptoMoE achieves 2.8–3.5× LAN latency reduction, 1.7–2.2× WAN latency reduction, and 2.9–4.3× communication reduction. Against the CipherPrune-based baseline (CryptoMoE†), CryptoMoE achieves up to 4.3× communication reduction and 2.4× latency reduction while maintaining higher accuracy.

## Baselines & Comparisons

CryptoMoE is compared against three baselines: (1) the Dense baseline, which evaluates all experts for every token to protect routing privacy; (2) the Insecure baseline, which reveals routing information and serves as an accuracy/efficiency upper bound; and (3) CryptoMoE†, which adapts CipherPrune's (ICLR'25) secure pruning protocol for MoE dispatch and combine. Against the Dense baseline, CryptoMoE wins decisively on efficiency: 2.8–3.5× lower LAN latency, 1.7–2.2× lower WAN latency, and 2.9–4.3× less communication, while losing only 0.0–0.5% in average accuracy. Against CipherPrune (CryptoMoE†), CryptoMoE achieves up to 4.3× communication reduction (e.g., 1.76 GB vs. 7.54 GB on QWenMoE) and 2.4× latency reduction (0.56 vs. 1.36 min/token on QWenMoE LAN), while also recovering 1.8–2.2% accuracy that CipherPrune's uniform token selection loses. Notably, CryptoMoE matches or even surpasses the Insecure baseline in latency on some configurations (e.g., 0.76 vs. 0.83 min/token on DeepSeekMoE LAN), because the insecure baseline cannot exploit the Batch MatMul optimization due to variable per-expert token counts.

## Relation to Prior Work

This paper extends the hybrid HE/MPC private inference line (BOLT, Bumblebee, CipherPrune) from dense Transformers to MoE architectures, where the dynamic routing mechanism introduces a fundamentally new privacy challenge: revealing which experts process which tokens leaks input semantics. It departs from the dense baseline (which evaluates all experts for every token at 15× compute cost) by proposing inference-time balanced expert routing, and from CipherPrune's secure pruning protocol by decoupling token index selection from embedding manipulation, reducing dispatch complexity from O(nkmtd) to O(nkm log(km) + ntm). The batch ciphertext-plaintext MatMul protocol adapts BOLT's packing strategy to the MoE setting where per-expert token counts are small, reducing HE rotations by a factor of n.

## Why It Matters / Open Questions

With MoE now the core architecture of frontier LLMs (LLaMA-4, DeepSeek-V3, QWen-3), the inability to run private inference on these models was a significant gap; CryptoMoE closes it with near-original accuracy (99.2% retention) and 2.8–3.5× speedup over the only prior private option (dense evaluation). Key open questions remain: the top-k protocol's many communication rounds become a WAN bottleneck, very short sequences (<64 tokens) suffer from severe load imbalance, and memory constraints currently prevent private inference on the largest MoE models (e.g., LLaMA4-Scout-109B). The balanced routing paradigm is generalizable and likely to inform future private inference designs for any sparsely-gated architecture.
