## Problem

Cloud-based LLM mobile agents upload the full XML UI state at every decision step, exposing large amounts of redundant and often sensitive user information (contacts, calendar events, messages) to the cloud. Local LLMs avoid this exposure entirely but suffer from severely limited reasoning, yielding task success rates 30–60% below cloud models. No prior work addresses how to upload only the minimal sufficient UI content to the cloud while preserving near-cloud-level task accuracy.

## Input / Output

The agent receives a natural-language task description, a sequence of past decisions (app launches, clicks, text inputs), and the current screen parsed from an XML hierarchy into HTML-style UI elements with attributes like text, content-description, and resource-id. The XML is first partitioned into semantically coherent blocks on-device; the local LLM sees all blocks while the cloud LLM sees only a dynamically selected subset. The output is a tuple of a target UI element index and an action type (tap, long-tap, or input text), executed via ADB on the device.

## Method

CORE is a training-free, asymmetric cloud-local collaboration framework with three stages. First, layout-aware block partitioning performs a depth-first traversal of the XML tree, records each important node's ancestor path, and groups elements by their shared ancestor at the shallowest depth level that yields at least three blocks, preserving the UI's original logical structure. Second, co-planning uses a divide-and-conquer strategy: the local LLM independently generates a sub-task candidate for each block (without leaking element-level details), and the cloud LLM selects or revises the best candidate, indirectly inferring page context from these abstractions. Third, co-decision-making has the local LLM assign normalized probabilistic relevance scores to all blocks given the confirmed sub-task, transmitting only the top-ranked block to the cloud LLM for element-level action selection; a multi-round accumulation mechanism lets the cloud LLM iteratively request additional blocks if the current context is insufficient, balancing information minimization against decision confidence. The key architectural insight is that the cloud LLM never sees the full UI, while the local LLM never performs fine-grained element selection—each model handles the granularity level where it is strongest.

## Results

On DroidTask (143 tasks, 12 apps), the best CORE configuration (GPT-4o + Gemma2-9B) achieves 69.23% task success rate with a 55.60% reduction in UI elements uploaded to the cloud, only 4.9% below the GPT-4o cloud-only baseline (74.13%). On the more challenging AndroidLab (98 tasks, 9 apps), GPT-4o + Qwen2.5-7B reaches 41.84% success with 29.97% reduction, just 3.06% below GPT-4o (44.90%). CORE also reduces sensitive UI element exposure by 70.49% on DroidTask and 38.84% on AndroidLab. Overall latency is 1.52–1.66× the GPT-4o baseline, while cloud token usage is comparable (0.94–1.15×).

## Baselines & Comparisons

Against the GPT-4o cloud-only baseline (following AutoDroid's workflow), CORE trades a small success-rate drop (4.9% on DroidTask, 3.06% on AndroidLab) for substantial UI exposure reduction (55.60% and 29.97% respectively), while also cutting sensitive-element uploads by 70.49% and 38.84%. Against the Gemma2-9B local-only baseline, CORE (GPT-4o + Gemma2-9B) improves success rate from 32.87% to 69.23% on DroidTask (+36.36 pp) and from 17.35% to 37.76% on AndroidLab (+20.41 pp), while sacrificing only 44.4% of the 100% reduction. Against Qwen2.5-7B local-only, CORE (GPT-4o + Qwen2.5-7B) lifts success from 14.69% to 61.54% on DroidTask (+46.85 pp) and from 5.10% to 41.84% on AndroidLab (+36.74 pp). Against LLaMA3.1-8B local-only, CORE (GPT-4o + LLaMA3.1-8B) improves success from 9.79% to 49.65% on DroidTask (+39.86 pp) and from 11.22% to 34.69% on AndroidLab (+23.47 pp). In all cases, CORE dominates the local-only baselines on accuracy while retaining meaningful UI reduction, and it approaches cloud-only accuracy at a fraction of the uploaded data.

## Relation to Prior Work

This paper departs from the dominant paradigm in mobile GUI agents (AutoDroid, MobileGPT, MobileAgent) where a single cloud LLM receives the full UI state at every step, and from local-only approaches that sacrifice accuracy for privacy. Its key conceptual departure is an asymmetric cloud-local collaboration in which the cloud LLM never directly accesses the UI, while a weaker local LLM with full UI visibility handles coarse-grained filtering (block ranking) and the cloud LLM handles fine-grained element-level decisions. Unlike prior multi-agent mobile frameworks (e.g., MobileAgent v2) that deploy multiple cloud LLMs with distinct roles but all under full UI access, CORE establishes a fundamentally different information-asymmetry: the strong model is blind to the UI and the weak model is the only one that sees it, coordinating through sub-task candidates and ranked block selections.

## Why It Matters / Open Questions

The work addresses a practically important and previously unformalized privacy concern: mobile agents routinely upload entire screen contents (including contacts, calendar events, messages, financial data) to cloud APIs, and CORE demonstrates that 55–70% of this exposure is unnecessary for correct decision-making. The framework is training-free and modular, making it integrable into existing XML-based agent pipelines without retraining. Key limitations include a ~50% latency increase from local inference, dependence on both a cloud API and a capable local model (≥7B parameters), and evaluation restricted to XML-based (not vision-based) agents. Open questions include whether the approach extends to screenshot/multimodal pipelines, how it behaves with even smaller local models, and whether the multi-round accumulation mechanism scales to highly complex or dynamic UIs.
