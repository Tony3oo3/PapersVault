## Problem

StarCraft II has been the most authoritative validation platform for decision-making algorithms for over a decade, yet its vector-based pysc2 interface is fundamentally incompatible with LLMs, which require natural-language action spaces. Existing LLM StarCraft II environments (SwarmBrain, TSC2) work around this by severely restricting the action space to a handful of discrete commands, eliminating the very complexity that makes the platform valuable. Additionally, current LLM multi-agent platforms lack native support for genuine multi-agent collaboration in real-time game settings.

## Input / Output

Each agent receives a multi-modal observation assembled by a wrapper that aggregates structured text (game state, unit counts, valid action list with costs, relevant Wiki knowledge about unit abilities) and base64-encoded images (RGB screen, RGB minimap, RGB feature maps, original pysc2 feature maps) into a single OpenAI-format query message. The LLM must respond with structured text actions of the form <Action_Name(args)> where args are screen coordinates, minimap coordinates, or unit tags, plus optional <MessageTo(Target, content)> communication actions. The environment parses these text actions through a transform protocol that maps each text action to one or more pysc2 function calls with the correct bridge object.

## Method

LLM-PySC2 exposes the full ~500-action pysc2 space (unit control, skills, building, researching, training, warping) as text actions, avoiding the policy-space clipping of prior LLM StarCraft environments. A four-role multi-agent hierarchy (Commander for macro combat, Developer for macro economy, Builder for construction, and CombatGroup agents for micro-operations) communicates via natural-language messages, supporting both centralized and decentralized decision-making. The key architectural innovation is an asynchronous query system: each agent issues its LLM query in an independent thread, and the environment polls for responses in a 50 ms loop, so total step latency remains constant (~5.2–5.6 s per query) regardless of how many agents are active. Observations are wrapped per-agent with role-specific prompts, valid-action lists, and Wiki knowledge entries, while images are annotated with auxiliary lines to aid coordinate recognition. The environment also provides two 'Easy Modes' (Easy Build, Easy Control) that simplify specific subsystems so researchers can isolate particular aspects of LLM decision-making.

## Results

On the novel LLM-PySC2 micro-operation tasks (level-1), GPT-4o achieves the best overall performance with 2.27 KD and 80% WR on task1 (2 Adept harass), while Claude3-haiku reaches 90% WR on the same task. Performance drops sharply on skill-intensive tasks: task2 (3 Phoenix harass) yields ≤10% WR across all models, and task4 (Blink-Stalker combat) yields 0% WR for every tested LLM. In complete StarCraft II games (ECEB mode), GPT-4o-mini wins 100% of level-1 games but drops to 0% by level-7, and the more complex SCEB mode collapses to 0% WR from level-3 onward. LLM inference latency dominates at 5.2–5.6 s per query, while environment-side processing is negligible (<0.1 s).

## Baselines & Comparisons

This is a benchmark/environment paper, so the 'baselines' are the various LLMs evaluated on the proposed tasks rather than competing methods. GPT-4o leads on task1 (2.27 KD, 80% WR) and task4 (0.46 KD), while Claude3-haiku achieves the highest WR on task1 (90%) and task5 (25%). Notably, scaling Llama3.1 from 8B → 70B → 405B yields only marginal gains (e.g., task1 WR: 5% → 15% → 30%), indicating that the scaling law does not transfer well to this decision-making domain. The reasoning model GPT-o1-mini does not significantly outperform GPT-4o-mini on the tasks it was evaluated on, suggesting that chain-of-thought reasoning alone cannot compensate for missing domain knowledge. All models uniformly fail on task2 (Phoenix harass, ≤10% WR) and task4 (Blink-Stalker, 0% WR), pointing to a shared inability to execute precise skill-based micro-operations. In the complete-game setting, the simpler ECEB mode (discrete actions) is the only configuration where LLMs remain competitive past level-3, while the full action-space modes (SCEB, ECSB) cause immediate collapse, highlighting the gap between simplified and realistic StarCraft II control.

## Relation to Prior Work

This paper extends the StarCraft II Learning Environment (SC2LE) by Vinyals et al. into an LLM-native decision-making platform, departing fundamentally from prior LLM StarCraft II environments (SwarmBrain, TextStarCraft II) that severely restricted the action space to a handful of discrete commands. Where those earlier works reduced the ~500 pysc2 actions to simplified text commands, LLM-PySC2 exposes the complete continuous action space and adds multi-modal observations (screen, minimap, feature maps) plus structured Wiki knowledge. The multi-agent framework with asynchronous query architecture also distinguishes it from prior LLM multi-agent systems that either expose a single agent or focus on social simulation rather than cooperative game control.

## Why It Matters / Open Questions

The paper provides the first comprehensive diagnostic of where current LLMs fail in complex sequential decision-making: hallucinations (confusing ally/enemy units, screen/minimap coordinates), lack of basic domain knowledge (not knowing shields recharge), and inefficient multi-agent communication. The finding that scaling (Llama 405b vs. 70b) and reasoning models (GPT-o1-mini) do not significantly improve performance challenges the assumption that pre-training scale alone will solve complex control tasks. Open questions include whether task-specific fine-tuning, retrieval-augmented knowledge, or learned policies in the deployment environment can close the gap, and whether the asynchronous multi-agent architecture generalizes to other real-time decision-making domains.
