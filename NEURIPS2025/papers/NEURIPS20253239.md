## Problem

Training open-source LMs for software engineering is bottlenecked by the lack of large-scale, high-quality training data with execution environments. Existing datasets contain at most 1,000s of instances from 11 or fewer repositories, require hundreds of hours of human labor to curate, and demand terabytes of storage for per-instance Docker environments, severely limiting scalability and accessibility for the research community.

## Input / Output

The SWE-smith pipeline takes a single Python GitHub repository as input and produces hundreds to thousands of SWE-bench-compatible task instances, each consisting of a bug patch (.diff file), an LM-generated problem statement mimicking GitHub issue style, and a shared Docker execution environment per repository (rather than per instance). For the trained agent, the input is a problem statement plus the buggy codebase, and the output is a code patch that resolves the bug, validated by FAIL_TO_PASS and PASS_TO_PASS unit tests. The shared-environment design reduces storage from an estimated 50–150 TB (SWE-bench-style) to 295 GB for 50k instances across 128 repositories.

## Method

SWE-smith inverts SWE-bench's collection strategy by building the execution environment first (via SWE-agent auto-installation of the latest commit) and then synthesizing task instances within it. Four bug generation strategies produce candidate patches: LM Modify (prompting an LM to introduce subtle logical bugs in a function), LM Rewrite (asking an LM to reimplement a function from its signature and docstring), Procedural Modification (applying random AST transformations such as removing conditionals, swapping operators, or deleting loops), and PR Mirror (using an LM to revert a historical PR's changes in the current codebase). A Combine Bugs strategy aggregates multiple single-function patches from the same file or module to create multi-location tasks. All candidates are validated by execution: only patches that break one or more previously passing tests are retained. For training, the paper uses rejection sampling fine-tuning: Claude 3.7 Sonnet runs SWE-agent on curated SWE-smith instances to generate expert trajectories, and the 5,016 successful trajectories are used to fine-tune Qwen 2.5 Coder Instruct 32B, achieving 40.2% Pass@1 on SWE-bench Verified.

## Results

SWE-agent-LM-32B, fine-tuned on 5,016 SWE-smith expert trajectories, achieves 40.2% Pass@1 on SWE-bench Verified and 30.7% on SWE-bench Lite, setting a new state-of-the-art among open-weight models. The 7B variant (SWE-agent-LM-7B, trained on 2k trajectories) reaches 15.2% Verified. At a controlled 500-trajectory training set size, the model achieves 28.2% Verified, outperforming SWE-gym (+8.2% relative) and R2E-Gym (+0.7% relative) under identical conditions.

## Baselines & Comparisons

SWE-agent-LM-32B (40.2% Verified) outperforms all open-weight baselines: SWE-gym-32B (20.6%, +19.6 pts), R2E-Gym-32B (34.4%, +5.8 pts), SWE-fixer-72B (32.8%, +7.4 pts), Lingma-SWE-GPT-72B (28.8%, +11.4 pts), and Qwen3-235B-A22B (34.4%, +5.8 pts). Against the strongest closed-weight open-source-adjacent model, Llama3-SWE-RL-70B (41.0% Verified), SWE-agent-LM-32B trails by only 0.8 points despite being 2.2× smaller. At a controlled 500-trajectory training budget, the paper reports 28.2% Verified versus approximately 20% for SWE-gym and 27.5% for R2E-Gym, confirming the advantage is not merely a function of training data volume. The ablation in Table 4 further shows that PR Mirror and Procedural Modification trajectories are the most effective training signals (9.2% and 8.6% Verified for the 7B student), while LM Modify trajectories are substantially weaker (5.7%).

## Relation to Prior Work

SWE-smith inverts the collection paradigm of SWE-bench: rather than identifying task instances first and then laboriously constructing per-instance execution environments, it builds a shared environment per repository and then synthesizes hundreds to thousands of bug instances within it. This design draws on Haluptzok et al.'s idea of using LMs to break code, but applies it at the repository level with four complementary strategies (LM modification, LM rewrite, AST-based procedural modification, and PR mirroring) plus execution-based validation. It also builds directly on SWE-agent as both the environment-setup tool and the inference scaffold, and positions itself as a scalable alternative to SWE-gym and R2E-Gym, which extended SWE-bench's collection pipeline but inherited its per-instance environment bottleneck.

## Why It Matters / Open Questions

The 50k-instance dataset from 128 repositories at 295 GB of storage (vs. an estimated 50–150 TB for an equivalent SWE-bench-style collection) dramatically lowers the barrier to training open-source SWE agents, and the resulting SWE-agent-LM-32B sets a new open-weight SOTA at 40.2% on SWE-bench Verified. Two findings have broader implications: LM-generated issue descriptions perform comparably to original GitHub issue text, and task difficulty does not correlate with downstream training effectiveness, suggesting that volume and diversity matter more than curated difficulty. Key limitations include Python-only coverage (relying on the ast library) and exploration limited to rejection-sampling fine-tuning, leaving open whether the pipeline transfers to other languages and whether RL or other training paradigms would further benefit from the dataset.
