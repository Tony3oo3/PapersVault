## Problem

Existing SWE-Agent benchmarks evaluate either isolated algorithmic puzzles or simple bug-fixing, leaving a critical gap: no benchmark tests whether LLM agents can perform the kind of runtime optimization that production systems (VLLM, HPC, LLaMA-CPP) require. GSO addresses this by asking whether current SWE-Agents can match expert developer optimizations on real-world codebases spanning multiple languages and abstraction levels.

## Input / Output

The agent receives a full codebase snapshot (cloned into a Docker container), a build script for environment setup, and a performance test that serves as the precise task specification—exercising real-world workloads (e.g., generating completions from Qwen-7B on ShareGPT, processing GIF animations, running NumPy string operations on Project Gutenberg text). The agent must produce a unified diff patch that improves runtime while maintaining functional equivalence. Success is measured by Opt@K, which requires the patch to apply cleanly, pass all correctness assertions, and achieve at least 95% of the human expert commit's speedup (measured via harmonic mean across multiple test cases).

## Method

GSO is constructed via a two-stage automated pipeline: (1) an LLM-based judge with code-change heuristics scans popular GitHub repositories to identify performance-improving commits, extracting rich context (affected files, commit messages, linked PRs, exercising endpoints); (2) LLM-generated performance tests are produced via execution-based rejection sampling, where tests must pass on both pre- and post-commit states while showing significant runtime improvement. The resulting 102 tasks across 10 codebases (NumPy, Pandas, Pillow, LLaMA-CPP, etc.) span Python, C, C++, Cython, Rust, and SIMD. Evaluation uses the Opt@K metric, which computes speedup as the harmonic mean of per-test speedups (robust to outliers that could be gamed via geometric mean) and compares model patches against human expert targets rather than absolute speedups, making the metric machine-independent. Agents are evaluated using the OpenHands scaffold (CodeActAgent) with a 3-hour time limit per task, tested across GPT-4o, O3-Mini, O4-Mini, and Claude 3.5/3.7/4.0.

## Results

All evaluated SWE-Agents achieve less than 5% success rate on Opt@1 (95% threshold matching human expert performance), with GPT-4o scoring 0.0% and Claude-4.0 as the best performer still below 5%. With inference-time scaling to Opt@10, the best models (O4-Mini, Claude-3.5-v2) reach only ~15% with diminishing returns beyond 8 rollouts. Performance drops sharply for non-Python tasks: 21.4% Opt@10 on Python-only tasks versus just 4.0% on tasks requiring C/C++/Cython/Rust modifications. Providing backtranslated ground-truth plans to O4-Mini improves Opt@1 to only 5.7%, indicating that even with strategic guidance, implementing low-level system changes remains the core bottleneck.

## Baselines & Comparisons

The paper evaluates six frontier models (GPT-4o, O3-Mini, O4-Mini, Claude-3.5-v2/3.6, Claude-3.7, Claude-4.0) using the OpenHands agent scaffold on the GSO benchmark. Claude-4.0 is the strongest performer on Opt@1 but still falls below 5%, while GPT-4o achieves 0.0%, indicating that success on SWE-Bench-style bug-fixing does not transfer to optimization tasks. On correctness alone (Opt_0@1), Claude-4.0 reaches 70% versus O4-Mini's 45%, but the gap compresses as the performance threshold p increases, showing that matching human-level speedup is the harder challenge. In inference-time scaling, parallel compute (more rollouts) scales far more efficiently than serial compute (more steps): 8 rollouts at 50 steps outperforms 1 rollout at 400 steps by 4–6×. The qualitative analysis reveals complementary failure modes: O4-Mini is explore-heavy and avoids low-level code (skipping necessary C/C++ changes 40% of the time), while Claude-3.5-v2 is exploit-heavy, making massive code changes with insufficient exploration and sometimes introducing unnecessary low-level modifications.

## Relation to Prior Work

GSO carves new ground at the intersection of three previously separate benchmark families: isolated code-generation benchmarks (HumanEval, LiveCodeBench) that test correctness on small puzzles, function-level performance benchmarks (ECCO, EvalPerf, PIE) that measure runtime on single programs, and repo-level SWE benchmarks (SWE-Bench, MultiSWE-Mini) that test bug-fixing on real codebases. None of these prior benchmarks simultaneously operate at repository scope, span multiple programming languages, use performance tests as unambiguous specifications, and measure against human expert optimization commits. The automated two-stage pipeline (LLM-identified performance commits + execution-based test generation) is a methodological departure from the manual curation typical of prior benchmarks, and the Opt@K metric with harmonic-mean speedup aggregation is a deliberate correction to the geometric-mean approach used in prior performance evaluation work.

## Why It Matters / Open Questions

The sub-5% Opt@1 success rate across all evaluated frontier models (including Claude-4.0 and GPT-4o) provides a stark, well-evidenced negative result: capabilities demonstrated on SWE-Bench-style bug-fixing do not transfer to systems-level optimization requiring algorithmic reasoning, multi-language fluency, and correct abstraction-level targeting. The qualitative failure-mode taxonomy (lazy optimization, wrong abstraction level, misdiagnosis) gives concrete directions for agent and model improvement beyond simply 'train more.' Key limitations include the modest 102-task size, the exclusive focus on runtime speedup (ignoring memory, maintainability, idiomaticity), and the acknowledged risk of reward hacking through test overfitting. Open questions include whether the gap will close with next-generation models, how to incorporate multi-objective evaluation, and whether the explore-vs-exploit behavioral dichotomy between model families can be exploited in hybrid agent designs.
