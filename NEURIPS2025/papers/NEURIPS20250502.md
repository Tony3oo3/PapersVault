## Problem

Production LLM serving clusters must be provisioned for peak online request rates, which can fluctuate up to 3x within minutes, leaving GPUs substantially underutilized during off-peak periods. The standard remedy—segregating latency-sensitive online workloads from throughput-oriented offline workloads onto separate clusters—simplifies SLO management but wastes resources. The open question is how to elastically co-locate both workload types on the same inference instance while guaranteeing strict latency SLOs (TTFT, TBT) for online requests despite unpredictable arrivals, variable output lengths, and batch-level interference.

## Input / Output

HyGen operates as an instance-level scheduler receiving two streams: latency-sensitive online requests (e.g., chatbot interactions with P99 TTFT/TBT bounds) and throughput-oriented offline requests (e.g., arXiv document summarization with relaxed latency). At each iteration it consumes the current running request set, the waiting request queues, a profiled latency budget, a chunk-size cap, and a memory budget, then emits a concrete batch composition specifying which requests to decode, which to prefill and with how many tokens (chunked prefill length), and which offline requests to preempt. The downstream engine executes this batch to produce generated tokens for both online and offline requests.

## Method

HyGen's core mechanism is a two-phase SLO-aware scheduler built on three components. First, a linear-regression latency predictor models batch execution time as a function of total prefill/decode token counts (including quadratic terms for attention complexity) and per-phase request counts, trained via systematic hardware profiling in ~15 ms on CPUs. Second, an SLO-aware profiler uses binary search over candidate latency budgets to find the maximum per-iteration latency that still satisfies the target SLO (e.g., P99 TBT) under the given workload mix. Third, the scheduler runs an online phase that greedily admits latency-sensitive requests (with priority-based preemption of offline requests when memory is tight), followed by an offline phase that fills residual latency, chunk-size, and memory budgets with throughput-oriented requests. To maximize offline throughput, HyGen organizes waiting offline requests in a prefix tree (Trie) and schedules them in DFS order to exploit KV-cache prefix sharing; a fairness extension introduces a utility ratio that probabilistically selects between the prefix-tree order and a freshness-sorted balanced BST to prevent starvation of low-sharing requests.

## Results

HyGen achieves up to 3.87× offline throughput improvement over pure online serving (Sarathi) and up to 5.84× over the SLO-aware fixed-QPS baseline (HyGen*), while maintaining strict latency SLOs across mean/P99 TTFT and TBT metrics. The latency predictor achieves a mean absolute percentage error of only 1.78% (Llama2-7B) and 1.07% (Qwen-14B). HyGen reaches up to 84.3% of the throughput of a dedicated pure-offline system (Sarathi-offline), demonstrating near-optimal resource utilization under co-location. On the Yi-34B model with TP=2/PP=2, HyGen achieves up to 1.89× offline throughput gain; on A5000 GPU with Sheared-LLaMA-2.7B, it achieves up to 2.18× offline and 1.30× overall throughput gain.

## Baselines & Comparisons

The paper compares HyGen against four baselines: (1) Sarathi (pure online serving), (2) Sarathi-offline (pure offline with optimal chunk size), (3) Sarathi++ (SLO-unaware hybrid with online-first scheduling and preemption), and (4) HyGen* (SLO-aware hybrid with a fixed offline QPS profiled to bound interference). HyGen decisively outperforms Sarathi++ on SLO compliance: while Sarathi++ yields identical (uncontrolled) latency across all SLO metrics and tolerance ratios, HyGen adapts its offline batching to meet each specific SLO target. Against HyGen*, which uses a static offline QPS cap, HyGen's dynamic per-iteration latency budgeting achieves up to 5.84× higher offline throughput under the same SLO constraints. Compared to the pure-offline ceiling (Sarathi-offline), HyGen retains up to 84.3% of maximum offline throughput, confirming that the fine-grained latency predictor and SLO-aware profiler approach is more efficient than a simplified fixed-QPS strategy. The prefix-sharing maximization policy adds up to 4× additional offline throughput on top of the base scheduling, and the system remains robust even when predictor accuracy degrades (MAPE > 20%).

## Relation to Prior Work

HyGen builds directly on Sarathi-Serve's chunked prefill and iteration-level scheduling as its execution substrate, extending it with a two-phase online-offline co-location scheduler. Conceptually, it adapts the well-studied data-center co-location paradigm (OLPART, PARTIES, CLITE) to LLM inference, where interference patterns are fundamentally different due to quadratic prefill complexity, linear decode scaling, and KV cache dynamics. It also extends prefix-sharing techniques (Prompt Cache, SGLang, Hydragen) by formulating an SLO-aware Prefix Sharing Maximization policy that balances cache reuse with latency guarantees and fairness, rather than treating prefix sharing as a purely throughput-oriented optimization.

## Why It Matters / Open Questions

The 3.87–5.84× offline throughput gain over online-only baselines while maintaining strict SLOs addresses a real and costly production problem: GPU underutilization during off-peak hours in LLM serving clusters. The system's practicality (1,300 lines of code on top of vLLM/Sarathi, O(n) scheduling complexity, ~18 μs predictor overhead) makes it deployable without major infrastructure changes. Open questions include extending to multi-tenant or heterogeneous-model settings, handling adversarial or highly dynamic input distributions that may degrade the linear-regression predictor, and integrating with cluster-level autoscaling to complement (rather than replace) instance-level elasticity.
