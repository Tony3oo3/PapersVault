## Problem

Cross-system SQL translation (SQL-to-SQL) is critical for enterprises operating heterogeneous database environments, yet no dedicated benchmark exists to evaluate LLMs on this task. Existing SQL benchmarks target Text-to-SQL with a narrow set of systems (mostly SQLite) and fail to capture system-specific dialect characteristics such as customized functions, data types, and syntax rules, making them ill-suited for assessing translation capability.

## Input / Output

The benchmark takes a SQL query written in a source database system's dialect along with explicit source and target dialect specifications, and expects the model to produce a syntactically valid and semantically equivalent query in the target dialect. Evaluation is execution-first: AccEX measures whether the translated query runs without syntax errors on the target system, while AccRES checks whether it returns strictly identical results (data, precision, order) to the source query. The benchmark spans 22 production-grade systems including PostgreSQL, MySQL, Oracle, ClickHouse, DuckDB, and SQL Server, with SQL token lengths ranging from 4 to 2,182 tokens.

## Method

PARROT is constructed through a five-step curation pipeline applied to real-world SQLs collected from 38 open-source benchmarks and ByteDance's proprietary ByteHouse workloads (102 tables, 343 SQL pairs). The pipeline performs: (1) preprocessing with three-level anonymization, (2) type-based filtering using ANTLR dialect parsers and prefix-based clustering with code-coverage-guided selection, (3) ensemble annotation via rule-based tools (SQLGlot, jOOQ) and small-scale LLMs to expand single-dialect SQLs into cross-dialect pairs, (4) error-guided selection that validates syntax via parsers and semantics via LLM-generated test cases, and (5) unified JSON serialization. Three variants are released: PARROT (598 manually verified pairs across 8 dialects), PARROT-Diverse (28,003 pairs across 22 dialects for extensive syntax testing), and PARROT-Simple (5,306 unit-style test cases isolating single translation types). The key design principle is using real production SQLs rather than LLM-synthesized queries to preserve structural nuances and operational patterns characteristic of actual workloads.

## Results

On the main PARROT benchmark (598 translation pairs across 8 dialects), the best single-dialect accuracy is 60.71% (GPT-4o → DuckDB), while the average accuracy across all evaluated LLMs and dialects is below 38.53%. On the real-world ByteHouse workload (Table 3), the highest result-consistency score (AccRES) is 54.23% achieved by o3-mini, with GPT-4o and Claude 3.7 Sonnet trailing at 21.87% and 22.74% respectively. Performance degrades significantly as SQL length increases, with all models showing average accuracy drops when token counts rise from 0–402 to 1214–2182.

## Baselines & Comparisons

The paper evaluates three families of LLMs as baselines on the PARROT benchmark. GPT-4o (OpenAI, 2024) achieves the highest single-dialect accuracy (60.71% on DuckDB) and strong Oracle performance (55.17%), but drops to 50.00% on MySQL, underperforming even DeepSeek-R1 32B (58.82%). DeepSeek-R1 (2025) shows a notable scale inconsistency: the 32B variant outperforms the 671B variant on PostgreSQL (58.62% vs. 48.28%), MySQL (58.82% vs. 44.12%), and SQL Server (42.11% vs. 36.84%), suggesting that larger parameter counts do not guarantee better dialect translation. DeepSeek-V3 671B (2024) provides the most balanced cross-dialect profile, staying above 51% on four of five target dialects, but still lags GPT-4o on DuckDB (53.57% vs. 60.71%) and Claude 3.7 Sonnet on Oracle (51.72% vs. 58.00%). Overall, no single LLM dominates all dialects, and the best average accuracy remains below 60%, confirming the benchmark's difficulty.

## Relation to Prior Work

This paper carves new ground by formalizing cross-system SQL dialect translation as a dedicated LLM evaluation task, departing from the dominant NL2SQL benchmark lineage (Spider, BIRD, WikiSQL) that the authors show is ill-suited for this purpose due to its SQLite-centric focus and lack of multi-dialect annotations. The curation pipeline repurposes existing rule-based translation tools (SQLGlot, jOOQ) and ANTLR parsers as annotation and validation infrastructure, while introducing an execution-based evaluation protocol (AccEX, AccRES) that rewards semantic correctness over string similarity. Conceptually, the work bridges the gap between production database migration tooling and LLM capability assessment, positioning SQL-to-SQL as a distinct problem from text-to-SQL with its own error taxonomy and difficulty profile.

## Why It Matters / Open Questions

Cross-system SQL translation underpins real production workloads (e.g., ByteDance's 1,000+ QPS migration from Postgres-variant to ClickHouse), yet the paper shows state-of-the-art LLMs achieve only 17–60% accuracy, revealing substantial headroom. The finding that function resolution and usage account for ~89% of errors points to a concrete bottleneck: LLMs lack reliable internal knowledge of database-specific function catalogs and argument conventions. Open questions include whether specialized fine-tuning on dialect pairs can close the gap, how to handle increasingly lengthy production queries where performance degrades, and whether the benchmark's 22-dialect coverage is sufficient for the long tail of enterprise systems. The benchmark's modular design (PARROT, PARROT-Diverse, PARROT-Simple) allows the community to stress-test specific translation types independently.
