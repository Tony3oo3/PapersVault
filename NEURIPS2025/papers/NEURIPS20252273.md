## Problem

Generating Building Information Modeling (BIM) designs directly from textual descriptions of modular building layouts (MBLs) remains largely unexplored. Existing layout generation methods produce 2D images or raw coordinates that require error-prone post-processing (e.g., raster-to-vector conversion, IFC reconstruction) to become BIM-compatible, and they do not account for MBLs' unique hierarchical three-tier structure of modules, units, and rooms. The gap is a method that produces fully parametric, semantically rich, and executable BIM code in one step from natural language.

## Input / Output

The input is a free-form textual description specifying precise spatial and geometric requirements in a parametric design style (e.g., room types, dimensions, relative positions, and architectural elements like doors). The output is a sequential C# code program following a custom object-oriented architecture (Module, Unit, Room, Utils classes) that compiles and executes within Autodesk Revit via the Revit API to instantiate a complete BIM model. Two coding styles are supported—named arguments (explicitly labeling each parameter's semantic role) and positional arguments (relying on parameter order)—and the code uses relative positioning (e.g., 'south of module_1, aligned east, offset 2000mm') rather than absolute coordinates, making the output inherently hierarchical and order-dependent.

## Method

Text2MBL reframes MBL generation as a sequence-to-sequence code generation task, where the key architectural insight is an object-oriented code layer (Module, Unit, Room, Utils classes) that encapsulates all geometric reasoning—wall creation, boundary computation, spatial containment—behind high-level constructor and utility interfaces, so the language model only needs to emit semantic action sequences rather than perform spatial calculations. The model is a fine-tuned Qwen2.5 variant (0.5B–7B, across Instruct/Coder/Math series) trained with LoRA (rank 64, alpha 64) on a curated dataset of 198 real-world modular housing designs, each annotated with two textual descriptions and two code variants. To address data scarcity, synthetic augmentation is applied in both partial (code-to-text via template or GPT-4.1-mini) and full (grammar-based code synthesis plus text generation) settings, mixed with original data during training. Evaluation spans three dimensions: executable validity (compile rate, pass rate in Revit), semantic fidelity (instance-level and argument-level F1), and geometric consistency (IoU at module, unit, and room levels), with the code-driven approach substantially outperforming a coordinate-sequence baseline, especially as component counts increase.

## Results

The code-driven approach substantially outperforms the coordinate-driven baseline across all model families and scales. The best configuration, Qwen2.5-Coder-7B with code output, achieves 98.43% overall IoU (98.78% Module IoU, 99.19% Unit IoU, 97.37% Room IoU), compared to 84.64% for the same model with coordinate output. Even the smallest model (Qwen2.5-Coder-1.5B-Code) reaches 94.19% IoU, surpassing the 7B coordinate baseline (84.64%). Pass rates (fully executable code) peak at 79.25% for Qwen2.5-Coder-7B-Positional, while argument F1 scores exceed 97% for the 7B models, indicating strong semantic extraction even when full executability is not achieved.

## Baselines & Comparisons

The paper does not compare against external published baselines but instead contrasts two output paradigms (code vs. coordinate sequences) and three model families (Instruct, Coder, Math) at two scales (1.5B, 7B). Code output consistently wins over coordinate output by 10–14 percentage points in IoU across every model family and scale, with the gap widening for rooms (e.g., 97.37% vs. 77.53% for Coder-7B). Among model families, Qwen2.5-Coder-7B-Code achieves the highest IoU (98.43%), slightly edging out Qwen2.5-Instruct-7B-Code (95.83%) and Qwen2.5-Math-7B-Code (94.86%). In a supplementary comparison (Appendix F), proprietary models GPT-4.1 and GPT-4.1-mini achieve much lower pass rates (22.50% and 6.25% respectively) and IoU scores (90.03% and 88.40% for code; 29.94% and 27.06% for coordinates), confirming that fine-tuned open-source models substantially outperform zero-shot proprietary LLMs on this specialized task.

## Relation to Prior Work

This paper extends the text-to-code generation paradigm established by works like Text2CAD and AutomaTikZ to the specific domain of modular building layout (MBL) design in BIM environments. While Text2BIM [11] attempted LLM-based BIM component coordinate generation, and prior floorplan generation work (Tell2Design, House-GAN++) produced 2D pixel or bounding-box outputs, Text2MBL departs by generating executable, object-oriented C# code through a hierarchical class architecture (Module, Unit, Room, Utils) that mirrors the three-tier structure of modular construction. The MBL design principles from Lin et al. [22] inform the formal definition of the layout, and the 'space without form' theory [15] underpins the relative-positioning code design that avoids absolute coordinate reasoning.

## Why It Matters / Open Questions

The framework establishes a direct pipeline from natural language to automation-ready BIM models, eliminating error-prone post-processing steps (raster-to-vector, IFC reconstruction) that plague image-based approaches. However, the current system is limited to rectangular modules, four room types, and parametric (fully specified) design inputs, with no mechanism for handling abstract user preferences or evaluating design satisfaction. Open questions include whether the code-driven advantage over coordinates persists at larger scales (more modules, non-rectangular geometries), how to incorporate user-centric criteria beyond geometric fidelity, and whether the 198-design dataset is sufficient for robust generalization across diverse MBL typologies.
