## Problem

LLMs are increasingly applied to clinical information extraction, but evaluations remain fragmented across task-specific datasets and informal protocols, lacking a unified framework for fair, reproducible comparison of diverse LLM architectures across multiple clinical domains. No existing benchmark simultaneously standardizes input data formats, prompt configurations, output validation, and practical efficiency metrics (runtime, API cost) needed for real-world model selection in healthcare.
![Teaser figure](../imgs/NEURIPS20252284/cropped_page2_idx0.webp)

## Input / Output

ClinBench ingests preprocessed clinical texts as standardized CSV files (774 TCGA pathology reports, 700 MIMIC-IV-ECG interpretations, 1,405 MIMIC discharge summaries) paired with version-controlled YAML prompt configurations that embed task instructions, domain knowledge (e.g., AJCC 7th edition staging criteria), and explicit JSON output schemas. The LLM produces a single JSON object per input, which is then validated against the schema via the strictjson library before metric computation; invalid outputs are flagged rather than silently parsed, ensuring structural correctness of every evaluated prediction.

## Method

ClinBench implements a five-step automated pipeline: (1) standardized CSV ingestion, (2) dynamic YAML prompt loading that encapsulates system prompts, domain knowledge, few-shot examples, and JSON output schemas in a single version-controlled file, (3) a unified LLM Orchestrator that routes inference to either local open-source models via Ollama or proprietary API models via Azure OpenAI under identical context-window and temperature-0 settings, (4) strictjson schema validation of every LLM output to enforce field names, data types, and enumerated value constraints, and (5) an evaluation module that applies predefined standardization transforms (e.g., mapping stage mentions to AJCC categories) before computing weighted F1, precision, recall, specificity, accuracy, and total runtime per model-task pair. The YAML-based prompting strategy was validated via ablation: replacing structured prompts with unstructured free-text equivalents caused 50–73% F1 drops on the lung cancer task, confirming that separating role, domain knowledge, and output schema into distinct YAML fields is critical for reliable extraction.

## Results

Across four clinical extraction tasks (Lung Cancer staging, AF detection, SDOH-Employment, SDOH-Housing), GPT-3.5-turbo achieved the highest mean F1 of 0.83 with a mean runtime of 16.8 minutes, followed by LLaMA3.1-70b (mean F1 0.82, 42.7 min) and GPT-4o-mini (mean F1 0.81, 13.4 min). On the most complex task (Lung Cancer staging), GPT-4o and GPT-4o-mini led with F1 0.92, while LLaMA3.1-70b matched at F1 0.91 but required ~106 minutes versus ~24 minutes for GPT-4o-mini. For AF detection, GPT-3.5-turbo and LLaMA3.1-70b both reached 95% accuracy (F1 ≈ 0.79), with GPT-3.5-turbo offering higher precision (0.97) at only 5.9 minutes runtime.

## Baselines & Comparisons

Among proprietary models, GPT-3.5-turbo achieves the best overall mean F1 (0.83) at the lowest runtime (16.8 min), outperforming GPT-4o (0.78, 18.5 min) and GPT-4o-mini (0.81, 13.4 min) on average, though GPT-4o-mini matches GPT-4o on Lung Cancer staging (both F1 0.92) at a fraction of the API cost ($0.30 vs. $9.66 for the full dataset). Among open-source models, LLaMA3.1-70b (mean F1 0.82) edges out LLaMA3-70b Instruct (0.77) by 5 percentage points but at a 15.7-minute runtime penalty; both substantially outperform Qwen2-72b (0.78) and Yi-34b (0.75) on Lung Cancer staging (0.91 vs. 0.88 and 0.86 respectively). Smaller open-source models (Gemma-7b at 0.61, Gemma-2b at 0.52, Mistral-OpenOrca at 0.68) trail the top performers by 15–30 F1 points, with Gemma-7b incurring an extreme 211.4-minute mean runtime. The key trade-off finding is that LLaMA3.1-70b's near-parity with GPT-3.5-turbo on mean F1 (0.82 vs. 0.83) comes at 2.5× the runtime, making GPT-3.5-turbo and GPT-4o-mini the most efficient choices for clinical deployment.

## Relation to Prior Work

ClinBench carves new ground as a standardized, open-source multi-domain benchmarking framework rather than extending a specific prior method. It departs from task-specific LLM evaluations (e.g., Huang et al. 2024 for lung cancer staging, Agrawal et al. 2022 for few-shot clinical extraction) and narrower biomedical benchmarks (MedGPTEval for Chinese medical context, LLM-AIx for locally deployable models) by unifying the entire evaluation pipeline—standardized CSV inputs, YAML-configured prompts, JSON schema validation via strictjson, and a single orchestrator for both local and API-based inference—across three distinct clinical domains. The conceptual lineage draws from prompt engineering and in-context learning literature, but the contribution is the reproducible infrastructure that makes cross-model, cross-domain comparison fair and transparent.

## Why It Matters / Open Questions

ClinBench provides the field with a practical, extensible tool for making informed LLM selection decisions in clinical settings, where performance, cost, and latency all matter. The ablation showing 50–73% F1 degradation with unstructured prompts underscores that prompt architecture is not a minor detail but a critical determinant of extraction reliability. Key open questions remain: whether findings generalize to multi-institutional data, how RAG or fine-tuning would shift the performance-efficiency landscape, and whether the benchmark can support prospective validation in active clinical workflows. The hardware-dependent runtime metrics and absence of a random or fine-tuned baseline limit the interpretability of absolute scores.
