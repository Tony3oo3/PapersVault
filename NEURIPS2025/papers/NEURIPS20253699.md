## Problem

Language models are increasingly deployed as autonomous data analysis agents, yet their ability to detect and handle data artifacts—missing values, outliers, logical inconsistencies, bad values, and formatting irregularities—remains unexplored. Existing tabular QA benchmarks assume clean tables or test only structural robustness (e.g., row/column shuffling) that does not require semantic understanding of the data. This leaves open whether models can perform genuine data-aware reasoning over the messy, imperfect tables that dominate real-world settings, and how such reasoning scales with table size.

## Input / Output

Each task instance presents a CSV-serialized tabular table (ranging from 2K to 16K tokens, with 5, 10, or 20 columns) containing one type of programmatically injected data artifact affecting fewer than 5% of rows, paired with a natural language analytical query. The model must produce a single answer (numeric, string, or list) that is scored via exact match against a ground truth computed on the corresponding recovered (artifact-free) table. Evaluation runs under two zero-shot settings: direct prompting (single-turn textual reasoning) and a code agent with a Python shell limited to five interaction steps.

## Method

RADAR's core mechanism is a dataset-agnostic programmatic perturbation framework in which, for each of 53 expert-curated tasks, dedicated Python functions generate both a perturbed table T_p (with one of five artifact types injected) and a recovered table T_r (the intended correction), while a separate answer function f computes the ground truth as A = f(Q, T_r). The model is scored on whether its answer to (Q, T_p) matches A, meaning correct performance requires the model to autonomously detect the artifact, decide whether to recover or discard affected rows, and then compute the answer over the cleaned data. The framework is scalable by design: perturbation and answer functions operate over any number of rows and auxiliary columns as long as the core schema is preserved, enabling systematic variation of table size (2K–16K tokens) and width (5–20 columns) while holding task semantics constant. Across 27 source tables spanning 9 domains, 260 expert-written perturbation functions yield 2,980 task instances, with two curated subsets (RADAR-T for artifact-type coverage at fixed 8K/10-col size, and RADAR-S for size-scaling analysis across 10 tasks).

## Results

On RADAR-T (313 instances, 8K tokens, 10 columns), o4-mini achieves 100% exact match on clean tables with code execution but drops to 41.1% on logically inconsistent tables, a 59-point degradation. Gemini 2.5 Pro leads among reasoning models on direct prompting, reaching 71.7% on clean tables and 42.9% on logically inconsistent tables. General-purpose models (Gemma3 27B, DeepSeek-V3) score below 2% on clean tables under direct prompting, while code execution lifts GPT-4.1 from 17.0% to 98.1% on clean tables but still leaves it at only 30.4% on logically inconsistent tables. Table-tuned models (StructLM, TableGPT2) perform poorly across all settings, with StructLM scoring 2.3% on clean tables under direct prompting.

## Baselines & Comparisons

RADAR is a benchmark rather than a method, so the comparisons are across model families and evaluation settings. Reasoning models (o4-mini, Gemini 2.5 Pro, DeepSeek-R1) substantially outperform general-purpose models (GPT-4.1, Gemini 2.5 Flash, Gemma3 27B, DeepSeek-V3) under direct prompting: o4-mini reaches 83.0% on clean tables versus 17.0% for GPT-4.1 and 1.9% for Gemma3 27B. Code execution narrows the gap on clean tables (GPT-4.1 jumps to 98.1%, DeepSeek-V3 to 96.2%) but the advantage of reasoning models persists on perturbed tables, where o4-mini retains 83.3% on outliers versus 60.4% for GPT-4.1. Table-tuned models (StructLM, TableGPT2) are the weakest across all settings, with StructLM scoring only 2.3% on clean tables under direct prompting and TableGPT2 reaching just 35.0% with code execution. Inconsistent Logic is the hardest artifact type for all models: even the best performer (DeepSeek-R1 with code) achieves only 48.2%, and o4-mini drops from 100% (clean) to 41.1% (logic), a 59-point collapse that no other artifact type matches.

## Relation to Prior Work

RADAR departs from prior tabular QA benchmarks (TableBench, FinQA, WikiTableQuestions) that assume clean, artifact-free tables, and from robustness studies (RobuT, TORR, FREB-TQA) that test structural perturbations like row/column shuffling rather than semantic data quality issues. It also complements data science agent benchmarks (BLADE, InfiAgent-DABench, DACO) that evaluate end-to-end analysis but do not systematically assess resistance to data quality issues. The paper's key conceptual departure is introducing schema-aware, semantically grounded perturbations (missing values, outliers, logical inconsistencies) paired with programmatic answer functions, enabling controlled evaluation of 'data awareness' as a distinct reasoning capability that neither clean-data QA nor structural robustness benchmarks capture.

## Why It Matters / Open Questions

RADAR exposes a critical and practically consequential gap: frontier models that achieve near-perfect accuracy on clean tables degrade by up to 59% when realistic data artifacts are introduced, and code execution—while helpful—does not close this gap because models resort to generic routines rather than targeted artifact detection. The finding that logically inconsistent entries are the hardest artifact type, and that direct prompting collapses to near-zero accuracy at 16K tokens, provides concrete guidance for building reliable data science agents. Open questions include whether specialized data-awareness training or hybrid text-code reasoning architectures can close the gap, and whether the benchmark's single-artifact-per-instance design adequately reflects the compounding complexity of real-world messy data.
