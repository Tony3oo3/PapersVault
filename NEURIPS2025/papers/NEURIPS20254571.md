## Problem

Per-instance program synthesis for LLM reasoning faces three unresolved challenges: deciding when code execution is preferable to direct CoT inference (open domain), the absence of task specifications to guide program search (causing over 50% of PoT outputs on algorithmic tasks to be trivial hardcoded answers), and the need to interface unstructured inputs like images and free text with structured program inputs. Existing methods such as PoT produce undesirable programs with syntax errors, wrong return types, and brittle image-processing code, while degrading performance on non-algorithmic tasks.

## Input / Output

The method takes a raw reasoning query (natural language text or an RGB image) and first uses an LLM to infer an ad hoc JSON schema capturing salient entities, attributes, and relationships specific to that instance. The synthesized Python program then takes this structured symbolic dictionary as its sole argument and returns the answer, explicitly decoupling perceptual inference (symbol extraction) from algorithmic computation (program execution). The program is written in a Turing-complete language and executed to produce the final symbolic answer.

## Method

PIPS operates in three coordinated stages. First, a confidence metric based on 10 self-assessment criteria (e.g., simple formalizability, straightforward executability, hallucination risk reduction) predicts per-instance whether CoT or program synthesis will yield a correct answer, using either a zero-shot heuristic or a logistic classifier trained on a 20% calibration split. Second, an LLM extracts structured symbolic input from the raw query with an ad hoc schema tailored to the instance's semantics. Third, an iterative synthesis loop (Algorithm 1) generates a Python program conditioned on the symbols, evaluates it against 8 structural criteria (input dependence, valid return, proper output format, no example usage, simplifiability, correctness bugs, symbol extraction issues, sanity check), and refines both the program and the extracted symbols based on structural feedback for up to k iterations. Unlike prior iterative debugging methods, PIPS requires no test cases, examples, or task-specific specifications—only general structural properties of well-formed code—making it fully zero-shot with respect to the downstream task.

## Results

Across 30 benchmarks (all 23 BBEH tasks plus CLEVR, Leaf, CLUTTR, and 4 OmniMath tasks), PIPS achieves a harmonic mean accuracy of 0.201 (Gemini-2.0-Flash), 0.305 (GPT-4.1-mini), and 0.397 (o4-mini), improving absolute harmonic mean accuracy by up to 8.6% over PoT and 9.4% over CoT. On the 17 majority-algorithmic tasks, PIPS gains up to 15.9% absolute harmonic accuracy over PoT (o4-mini: 0.548 vs 0.389), while on the 10 majority-non-algorithmic tasks it matches CoT within ~1.5%. PIPS also reduces undesirable program generations (trivial, syntax errors, wrong return type, placeholders) by 65.1% on algorithmic tasks compared to PoT with Gemini-2.0-Flash.

## Baselines & Comparisons

PIPS outperforms all five baselines on the primary harmonic mean accuracy metric. Against PoT (Chen et al., TMLR 2023), PIPS gains 8.6% absolute for Gemini-2.0-Flash (0.201 vs 0.115), 0.8% for GPT-4.1-mini (0.305 vs 0.297), and 5.7% for o4-mini (0.397 vs 0.340), with the largest per-task gain reaching 23.7% on BBEH Boolean Expressions. Against CoT (Wei et al., NeurIPS 2022), PIPS improves by 9.4% (Gemini), 9.4% (GPT-4.1-mini), and 9.3% (o4-mini) in absolute harmonic mean. Against the Gemini Code Interpreter (CI) agentic baseline, PIPS achieves 0.201 vs 0.134 (6.7% absolute) while using roughly 1/7th the input tokens (11.8K vs 80.1K). Against CodeAct (Wang et al., ICML 2024) and Buffer-of-Thoughts (Yang et al., NeurIPS 2024) on BBEH tasks with Gemini-2.0-Flash, PIPS achieves 0.171 vs 0.040 and 0.027 respectively, a 4–6× improvement. Notably, on non-algorithmic tasks PIPS slightly underperforms CoT (e.g., 0.184 vs 0.199 for Gemini-2.0-Flash), confirming that the confidence switch correctly routes those instances to direct inference rather than forcing program synthesis.

## Relation to Prior Work

PIPS extends the Program of Thought (PoT) line of work, which generates instance-level Python programs to offload computation from LLMs, by adding three key mechanisms absent in prior approaches: (1) a confidence-based switch that decides per-instance whether to use code or CoT, (2) iterative structural feedback (non-triviality, type, syntax checks) that refines programs without requiring test cases or task specifications, and (3) explicit symbolic extraction that decouples perceptual understanding from program search. It departs from fixed-program neuro-symbolic methods (PAL, FCoT) by synthesizing programs per instance, and from debugging-based approaches (Hypothesis Search, self-debugging) by using general structural properties rather than input-output examples as the search signal. The agentic baselines (CodeAct, Buffer-of-Thoughts, Code Interpreter) represent a parallel direction toward iterative code execution, but PIPS achieves comparable or better accuracy at a fraction of the token cost.

## Why It Matters / Open Questions

The paper demonstrates that a large fraction of PoT's failures (trivial hardcoded answers, syntax errors, wrong return types) are addressable with lightweight structural feedback, yielding an 8.6% harmonic mean accuracy gain over PoT across 30 benchmarks. The finding that forcing non-trivial code on non-algorithmic problems actively degrades performance (Appendix F) underscores the importance of the confidence switch, and the 65% correct switch rate suggests LLMs have meaningful self-knowledge about their own code-generation reliability. Open questions remain: PIPS does not handle hybrid problems best solved partly with CoT and partly with code, the symbolic extraction step lacks faithfulness guarantees, and it is unclear whether additional undesirable code patterns beyond the eight structural checks would yield further gains. The method's practical cost (3–4× CoT) makes it a viable drop-in improvement for systems already using PoT.
