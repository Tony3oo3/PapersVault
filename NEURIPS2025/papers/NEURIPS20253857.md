## Problem

Existing benchmarks for formally verified code generation (e.g., FVAPPS, miniCodeProps, DafnyBench) rely on computable or automatically generated specifications that leak implementation logic, allow trivial or vacuous solutions, or depend on test-case supervision rather than full semantic proofs. This makes it impossible to distinguish models that genuinely reason about program correctness from those that merely copy specification syntax into implementations. CLEVER addresses this gap by providing hand-crafted, non-computable Lean specifications that are complete, implementation-agnostic, and resistant to shortcutting.

## Input / Output

The benchmark takes a natural language problem description (adapted from HUMANEVAL) and a Lean 4 function signature as input. The model must produce four artifacts in sequence: a formal specification expressed as a Lean Prop (a predicate over the implementation and inputs), a proof of semantic equivalence between the generated spec and a hidden ground-truth spec, a Lean implementation matching the given signature, and a proof that the implementation satisfies the ground-truth spec. All outputs are verified post-hoc by Lean's type checker; a task counts as solved only if both proofs are fully accepted, with a 600-second time budget per problem (pass@k-seconds metric).

## Method

The core design decision is the use of non-computable specifications — predicates in Lean's Prop universe built from inductive definitions, quantifiers, and logical connectives that cannot be reduced by computation. This contrasts with computable specs (executable functions or decidable predicates) that allow models to mirror the specification's logic directly into the implementation and produce trivial proofs via unfolding and simplification. The evaluation pipeline is staged into two certification goals: specification certification (generate spec + prove isomorphism to ground truth) and implementation certification (generate implementation + prove correctness against ground truth), enabling fine-grained failure diagnosis. For empirical evaluation, the paper tests few-shot prompting with GPT-4o, Claude-3.7, o4-mini, and DeepSeek-R1, as well as the COPRA neuro-symbolic proof-search agent for the proof-generation stages, and a hybrid configuration pairing GPT-5-mini with KiminaProver-7b. Despite high compilation rates (60–90%), no approach exceeds 1/161 end-to-end verified solutions, establishing CLEVER as a challenging frontier benchmark.

## Results

On CLEVER (161 problems), no evaluated approach achieves more than 1/161 (0.621%) end-to-end verified code generation; the only problem solved across multiple models is problem 53 (add two integers). Compilation rates are relatively high—specification compilation ranges from 71.4% (DeepSeek-R1) to 90.1% (GPT-5-mini hybrid), and implementation compilation from 60.9% to 84.5%—but formal proof acceptance is the critical bottleneck, with specification certification at 0–1.86% and implementation certification at 0.62–8.70%. The best implementation certification is achieved by Claude-3.7 with COPRA at 8.696% (14/161), while the best specification certification is GPT-4o with COPRA at 1.863% (3/161).

## Baselines & Comparisons

The paper evaluates three families of approaches—few-shot prompting, COPRA (neuro-symbolic proof search), and a hybrid with KiminaProver—across four state-of-the-art LLMs. For specification certification, COPRA with GPT-4o achieves the highest proof rate (1.86%, 3/161), outperforming all few-shot baselines (0.62–1.24%), suggesting that guided proof search helps recover algebraic structure in equivalence proofs. For implementation certification, Claude-3.7 with COPRA dominates at 8.70% (14/161), roughly 1.5× the next best (DeepSeek-R1 few-shot at 5.56%), and successfully certifies every implementation that any other approach can prove. The GPT-5-mini + KiminaProver hybrid achieves the highest compilation rates (90.1% spec, 84.5% impl) but certifies almost nothing due to parsing issues with KiminaProver's non-standard output. Critically, end-to-end success is capped at 0.62% (1/161) for all approaches, with the sole success being problem 53, indicating that the joint requirement of both specification and implementation proofs remains an unsolved challenge for current LLMs and agentic systems.

## Relation to Prior Work

CLEVER extends the verified code generation benchmarking line initiated by FVAPPS, miniCodeProps, and DafnyBench, but departs sharply in its specification design: where prior benchmarks use computable or auto-generated specs that leak implementation logic (allowing trivial programs to pass), CLEVER mandates non-computable, hand-written Lean propositions that force genuine symbolic reasoning. It builds directly on HUMANEVAL's 161 programming tasks as the natural-language substrate, and evaluates using COPRA, a neuro-symbolic proof-search agent, alongside raw few-shot prompting of frontier LLMs. The two-stage certification pipeline (specification equivalence + implementation correctness) is a novel structural contribution not present in prior benchmarks, which typically verify only a subset of program properties.

## Why It Matters / Open Questions

By demonstrating that even GPT-4o, Claude-3.7, o4-mini, and DeepSeek-R1 solve at most 1 of 161 problems end-to-end, CLEVER establishes a concrete, machine-checkable frontier for verified code generation and exposes a critical gap: models are fluent at producing compilable Lean but nearly incapable of producing accepted proofs. The non-computable specification design is a reusable methodological principle that closes a class of loopholes in prior benchmarks. Open questions include whether the benchmark's difficulty is inherent to formal verification or an artifact of Lean-specific proof obligations, whether scaling or RL fine-tuning can close the proof gap, and whether the staged pipeline's mismatch phenomenon (spec-certifiable tasks are impl-hard and vice versa) reflects a fundamental tension in program reasoning.
