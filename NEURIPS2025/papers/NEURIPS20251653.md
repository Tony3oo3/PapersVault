## Problem

Training large language models is increasingly constrained by GPU memory capacity, and existing offloading solutions either rely on expensive host DRAM (ZeRO-Offload) or use coarse-grained layer-level offloading to SSDs that wastes both SSD bandwidth and GPU memory (ZeRO-Infinity). No prior system can exploit the predictable, fine-grained tensor activity patterns in LLM training to achieve near-ideal throughput using low-cost PCIe SSDs.

## Input / Output

TERAIO takes an unmodified PyTorch LLM training program (via TorchTitan) and requires only the first few training iterations for profiling; it needs no source-code changes to the model. The profiler extracts per-tensor sizes and active/inactive time intervals at GPU-kernel granularity, which feed into a planning algorithm that produces a migration schedule (offload/prefetch triggers with deadlines and target devices) compiled into the execution graph. At runtime, the migration engine executes this plan, transparently moving tensors between GPU HBM, host DRAM, and SSDs, and the user only specifies GPU memory capacity, maximum host memory, and the SSD array configuration.

## Method

TERAIO comprises three tightly coupled components. First, a tensor lifetime profiler instruments PyTorch's automatic operator generator to record each tensor's size and the kernel-range during which it is active, then computes inactive periods (including cross-iteration periods for global tensors like weights and optimizer states). Second, a lifetime-aware migration algorithm iteratively selects offloading candidates by maximizing a benefit-to-cost ratio—benefit is the integral of critical memory-pressure reduction over the tensor's feasible offload window (accounting for I/O bandwidth already consumed by prior migrations), and cost is the total offload-plus-prefetch time—until peak GPU memory fits within capacity; it prefers SSDs and falls back to host memory only when SSD bandwidth is saturated. Third, a runtime migration engine executes the plan using GPUDirect Storage (cuFile) to transfer tensors directly between GPU HBM and SSDs over PCIe, bypassing the host CPU to avoid the scalability bottleneck in multi-GPU systems, while a hashmap-based location table tracks each tensor's current device. The key differentiator from ZeRO-Infinity is kernel-granularity offloading driven by precise per-tensor lifetime analysis, which yields high and consistent SSD bandwidth utilization rather than bursty layer-level I/O.

## Results

TERAIO improves LLM training throughput by 1.47× on average over ZeRO-Offload and ZeRO-Infinity, and achieves 80.7% of the ideal performance assuming unlimited GPU memory. For Llama3-8B and Granite-8B, TERAIO-Mixed reaches near-ideal throughput, while for Llama3-70B it achieves 59.7% of ideal (vs. 43.0% for ZeRO-Infinity). In terms of cost, TERAIO-SSD and TERAIO-Mixed reduce training cost by 5.88× and 5.41× respectively compared to a pure multi-GPU server setup, and deliver 1.45× better cost efficiency than ZeRO-Offload/ZeRO-Infinity.

## Baselines & Comparisons

Against ZeRO-Offload, TERAIO wins decisively: ZeRO-Offload achieves only 65.9% (Llama3-8B) and 65.5% (Granite-8B) of ideal throughput, and it fails entirely on Llama3-70B because 1TB of host memory is insufficient to hold offloaded tensors. Against ZeRO-Infinity, TERAIO also wins across the board — for Llama3-70B, TERAIO-Mixed reaches 59.7% of ideal vs. ZeRO-Infinity's 43.0% (a 1.33× gap), and the average improvement across all models is 1.47×. The key architectural difference is granularity: ZeRO-Infinity offloads at the DNN-layer level, producing bursty I/O that underutilizes SSD bandwidth, while TERAIO offloads at the GPU-kernel level using precise tensor lifetime analysis, maintaining >16 GB/s sustained migration bandwidth for over 82% of training time on Llama3-70B. TERAIO also requires less CPU memory than ZeRO-Infinity (e.g., 64 GB vs. 170 GB for Llama-8B) while delivering higher throughput, and it can train configurations (long sequence lengths >3072) where ZeRO-Infinity fails with out-of-memory errors.

## Relation to Prior Work

This paper extends the GPU memory expansion line initiated by ZeRO-Offload (CPU memory) and ZeRO-Infinity (SSD offloading at layer granularity), but departs from both in two key ways: it operates at kernel-level granularity rather than layer-level, and it introduces a lifetime-aware scheduling algorithm that profiles tensor activity patterns to generate globally optimized offloading/prefetching plans. The use of GPUDirect Storage for direct GPU-to-SSD data transfer builds on NVIDIA's hardware capability and prior GPU-initiated storage work (BAM, GoFS), but TERAIO is the first to integrate this mechanism into a full LLM training offloading pipeline with I/O-bandwidth-aware planning. The characterization study of tensor activity patterns (1.7% active memory, long inactive periods) provides the empirical foundation that distinguishes TERAIO's fine-grained approach from the heuristic, coarse-grained policies in prior offloading systems.

## Why It Matters / Open Questions

TERAIO addresses a practical and growing bottleneck: LLM training memory demand outpacing GPU HBM capacity, with a solution that is both performance-effective (80.7% of ideal, 1.47× over ZeRO-Infinity) and cost-effective (5.41× cheaper than pure-GPU setups). The lifetime-aware scheduling and GPUDirect Storage integration offer a template for future memory-hierarchy management in ML training, and the characterization insights (sparse tensor access, long inactive periods) are broadly applicable. Limitations include evaluation on only 2 H100 GPUs with 8 SSDs, reliance on predictable execution graphs (which may not hold for dynamic architectures), and the current GDS implementation still depending on the host filesystem for control-path operations. Open questions include scaling to multi-node clusters, integration with emerging memory technologies like CXL, and whether the profiling-based approach generalizes to non-LLM or dynamically-shaped workloads.
