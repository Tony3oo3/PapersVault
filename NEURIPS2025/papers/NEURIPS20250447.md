## Problem

Existing benchmarks for evaluating the security risks and capabilities of code-generating LLMs suffer from three coupled limitations: limited coverage of CWE-based risk categories and security tasks (e.g., many support only code completion or only vulnerability detection), reliance on imprecise static metrics such as rule-based detectors or LLM-as-judge rather than dynamic execution, and a fundamental trade-off between manual data quality and automated scale. No prior benchmark simultaneously provides broad risk coverage, dynamic evaluation, and large-scale, human-verified data across multiple programming languages.

## Input / Output

Each SECODEPLT sample is a structured JSON record containing a task description (function name, natural-language description, arguments, context, return/raise specs, and an optional security policy), a vulnerable code snippet, a patched code snippet, and both functionality and security (PoC) test cases with assertions. For secure coding, the model receives either the full task description (instruction generation) or a partial code snippet with the vulnerable region masked (code completion); for vulnerability detection, it receives the vulnerable or benign code and must output a CWE label; for patch generation, it receives the vulnerable code plus task description and must produce a corrected version. Evaluation is performed by dynamically compiling and executing the model's output against the test cases, with pass@1 and pass@5 metrics for patching and F1 for CWE identification.

## Method

SECODEPLT is built via a two-stage pipeline that balances manual quality with automated scale. In the seed stage, authors manually analyze each of 44 CWEs and create high-quality coding scenarios with full artifacts (vulnerable code, patched code, functionality tests, security PoCs); Python seeds are authored from scratch, C/C++ seeds are extracted from the Arvo dataset using clangd for context extraction and libfuzzer/afl++ for reachable functionality test generation, and Java seeds are derived from the Juliet Test Suite with aggressive obfuscation (identifier renaming, comment removal) to eliminate 'good'/'bad' naming artifacts. In the expansion stage, a GPT-4o text mutator rephrases task descriptions at high temperature while a set of lightweight code mutators (variable/function renaming, symmetric instruction reordering) preserve core logic; each seed yields up to 10 mutated samples. Mutated samples are validated by dynamic execution (both vulnerable and patched versions must pass functionality tests, and only the patched version must pass security tests) and filtered for redundancy using word-level Levenshtein distance with a 0.8 similarity threshold, ultimately producing 5.9k samples (1.6k verified seeds) across Python, C/C++, and Java.

## Results

On SECODEPLT's vulnerability detection task (F1 score), the best model O4-Mini achieves 0.713 on Python (with policy) but drops to 0.342 on C/C++ and 0.507 on Java. For patch generation (Pass@1), Claude-3.7-Sonnet leads with 0.639 on Python but all models fall below 0.17 on C/C++ and 0.28 on Java. In secure coding, even the top models (Claude-3.7-Sonnet, O4-Mini) show >50% incorrect rate on C/C++ and ~40% on Java. SECODEPLT achieves ~100% security relevance and prompt faithfulness, compared to CYBERSECVAL's 67.81% security relevance.

## Baselines & Comparisons

SECODEPLT outperforms all eight compared benchmarks on coverage, data quality, and scale simultaneously. Versus CYBERSECVAL [4], SECODEPLT achieves ~100% security relevance and prompt faithfulness (vs. 67.81% and lower faithfulness for CYBERSECVAL) and adds dynamic testing that CYBERSECVAL lacks. Compared to PrimeVul [11] (236k samples, 140 CWEs), SECODEPLT is smaller but provides human-verified data (1.6k verified vs. 0), supports three tasks (secure coding, vulnerability detection, patch generation) rather than only vulnerability detection, and uses dynamic metrics. Against SecLLMHolmes [56] (78 verified samples, 8 CWEs), SECODEPLT is ~20x larger in verified data and covers 44 CWEs. Versus BaxBench [57] (392 samples, 13 CWEs, 6 languages) and AutoPatchBench [34] (136 samples, 6 CWEs, C/C++ only), SECODEPLT provides 4x and 12x more verified data respectively, covers 44 CWEs, and supports all three security capabilities. Among the evaluated models, Claude-3.7-Sonnet and O4-Mini consistently outperform the others across all three tasks, while Qwen2.5-Coder (non-reasoning) performs worst, with 0% patch generation success on C/C++ and the lowest vulnerability detection F1 scores.

## Relation to Prior Work

This paper carves new ground in the benchmark construction methodology for code security evaluation rather than building on a single prior method. It departs from prior secure-coding benchmarks (CYBERSECVAL, CodeLMSec, SVEN) that rely on static rules or LLM judgment by introducing dynamic testing as the primary evaluation metric, and from vulnerability-detection benchmarks (PrimeVul, SecLLMHolmes) that either sacrifice quality for scale or vice versa. The key conceptual contribution is the two-stage pipeline—manually validated seeds expanded via LLM-based text and code mutation with dynamic validation—which reconciles the quality-scale trade-off that has limited prior work. The benchmark also unifies three previously fragmented evaluation tasks (secure coding, vulnerability detection, patch generation) under a single artifact set, whereas prior benchmarks typically addressed only one or two.

## Why It Matters / Open Questions

SECODEPLT provides the first large-scale, multi-language benchmark with dynamic evaluation that can simultaneously assess a code model's security risk (does it generate vulnerable code?) and security capability (can it detect and fix vulnerabilities?), filling a gap that no single prior benchmark addressed. The finding that even top models (Claude-3.7-Sonnet, O4-Mini) exceed 50% incorrect rate on C/C++ secure coding and achieve <20% patch generation success on C/C++ quantifies a significant and actionable gap for the field. Open questions include whether the two-stage pipeline generalizes to repository-level vulnerability detection, whether dynamic testing can be made more sound for patch validation, and whether the benchmark's data can effectively fine-tune models to close the observed security capability gap. The cyberattack helpfulness appendix also raises the broader question of how to evaluate and constrain LLMs' offensive security capabilities in realistic network environments.
