## Problem

Existing LLM decoding strategies are either rule-based (top-k sampling, beam search, self-consistency) with limited performance ceilings, or rely on large auxiliary reward models that introduce substantial computational overhead during both training and inference. The paper identifies a fundamental redundancy: reward models re-extract features from scratch for ranking, ignoring the rich representations already computed by the base model during generation. This motivates reframing decoding as a lightweight ranking problem analogous to the reranking stage in recommender systems.

## Input / Output

The method takes an instruction prompt and K candidate responses (typically K=10) sampled from the base model, and outputs the single best response selected by the ranker. Rather than processing raw text, the ranker consumes hidden-state vectors extracted from a fixed intermediate layer (~60% from the bottom) at the final token position of both the instruction and each candidate response. These vectors are compact (~8KB per token), making them transmissible over a network and enabling the ranker to run independently on CPUs or edge devices while the base model remains on a central server.

## Method

Language Ranker introduces a <0.5M-parameter ranker that reranks candidate responses using features already extracted by the base model, eliminating the need for a separate forward pass through a reward model. Two variants are proposed: a listwise ranker that processes all K candidates simultaneously through a single Transformer block (enabling direct inter-candidate comparison), and a pointwise ranker that scores each candidate independently via a shared MLP block. Both first project high-dimensional hidden states into a 64-dimensional space, then compute relevance scores between the instruction feature and each response feature using cosine similarity (for binary labels) or a learnable linear function (for regression labels). Training uses KL divergence loss for listwise classification, binary cross-entropy for pointwise classification, or MSE for regression, with the ranker trained in under 70 seconds on CPU. The key architectural insight is that the base model's earlier layers serve as shared feature engineering for both retrieval (generation) and ranking, mirroring the pipeline structure of recommender systems and enabling a single base model to be paired with multiple task-specific or user-specific rankers.

## Results

On Llama3.1-8B-Instruct, the ListRanker (0.30M params) achieves 46.3% on MATH, 54.5% on MBPP, and 32.6% on xLAM, outperforming the GPT-2-based reward model (137M params) by 3.4, 6.8, and 3.2 points respectively, while matching or exceeding the Llama8B-based reward model (176M trainable / 8.2B GPU-loaded). On Qwen2.5-7B-Instruct, the ListRanker reaches 74.8/63.2/71.0, surpassing the Qwen7B-based reward model on all three tasks. On Qwen2.5-32B-Instruct, the ranker with only 0.36M parameters achieves 81.1/74.2/72.8, comparable to the 32B-scale reward model (537M/32.8B) at 80.7/75.9/73.6, while the ranker trains in ~67 seconds on CPU versus 24 minutes on A100 for the Llama8B reward model.

## Baselines & Comparisons

Against the GPT-2-based reward model (Radford et al., 2019; 137M params), the Language Ranker consistently wins across all three tasks and all three base models, e.g., 46.3 vs. 42.9 on MATH and 54.5 vs. 47.7 on MBPP with Llama3.1-8B, despite being over 100× smaller. Against the Llama8B-based LoRA reward model (Dubey et al., 2024; 176M trainable / 8.2B GPU-loaded), the ListRanker matches or slightly exceeds performance on MATH (46.3 vs. 45.1) and MBPP (54.5 vs. 52.9) while trailing by only 0.2 on xLAM (32.6 vs. 32.8), all with <0.5M parameters versus 8.2B loaded on GPU. Against the Qwen2.5-based reward models (Yang et al., 2024), the ranker outperforms RM(Qwen7B) on all three tasks (74.8/63.2/71.0 vs. 74.6/62.9/70.2) and is competitive with RM(Qwen32B) (81.1/74.2/72.8 vs. 80.7/75.9/73.6). Against Self-Consistency (Wang et al., 2023), the ListRanker achieves substantially higher scores on MBPP (54.5 vs. 41.9), xLAM (32.6 vs. 24.6), and AlpacaEval (30.7 vs. 20.4), while being slightly ahead on MATH (46.3 vs. 44.9), confirming that majority-voting-based reranking is far less effective for non-math tasks.

## Relation to Prior Work

This paper repurposes the recommender system pipeline (feature engineering → retrieval → ranking) as a conceptual and architectural framework for LLM decoding, departing from both rule-based decoding strategies (top-k, self-consistency, contrastive decoding) and the dominant reward-model paradigm for inference-time compute scaling. Rather than training a separate reward model that redoes feature engineering from scratch, it reuses the base model's intermediate hidden states as pre-computed features and trains a <0.5M-parameter ranker on top, directly addressing the redundancy the authors identify in existing approaches. The 'Large Language Monkeys' result (oracle selection from samples can outperform larger models) motivates the work, while the recommender-systems literature provides the architectural template (listwise/pointwise rankers, projection layers, relevance functions).

## Why It Matters / Open Questions

The practical impact is significant: a ranker with fewer than 0.5M parameters matches or exceeds 8B-scale LoRA reward models across math, code, and function-calling tasks, while being CPU-trainable and deployable on edge devices for personalization. This opens a path toward a single base model paired with multiple lightweight, task-specific or user-specific rankers, reducing both training and inference overhead by orders of magnitude. Key limitations include the requirement for hidden-state access during inference (not yet fully supported by frameworks like vLLM) and the continued need to sample K candidates, meaning the base model's forward-pass cost is unchanged. Open questions include how to combine this ranking stage with sampling-stage optimizations (e.g., optimized compute allocation) and whether the approach extends to open-ended generation tasks where objective labeling is infeasible.
