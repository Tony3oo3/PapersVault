## Problem

Existing IR-oriented datasets for LLM-based compiler optimization lack optimization-sensitive samples—programs whose IR triggers diverse and representative transformations under real-world optimization sequences. This scarcity prevents LLMs from learning when and where specific optimizations apply, limiting their ability to generalize across varying program structures and capture the intricate logic encoded in handcrafted compiler rules.

## Input / Output

The input is a single-function, normalized LLVM IR snippet (standardized block/variable naming, no comments or extraneous whitespace) constrained to a 4K-token context window. The dataset defines two output tasks: Code Analysis, which produces structured textual representations of dominator trees, loop structures (header/latch/exiting roles), and MemorySSA definitions/uses; and Optimized Code Generation, which produces the full optimized LLVM IR after applying the -O3 pass sequence. Only IR files where at least 8% of executed passes result in actual transformations are retained, ensuring each sample is genuinely optimization-sensitive.

## Method

IR-OptSet is constructed by crawling 1,704 GitHub repositories across 8 optimization domains, extracting unoptimized LLVM IR via the LLVM 19.1.0 frontend, splitting into function-level units with llvm-extract, deduplicating via StructuralHash, normalizing, and annotating with effective optimization steps identified through the -O3 sequence and -print-changed flag. The dataset defines two tasks mirroring the compiler pipeline: Code Analysis (Dominator Tree Construction, Loop Detection, Memory Access Analysis) and Optimized Code Generation, with ground truth from LLVM's official APIs and -O3 output respectively. Three LLMs (LLM Compiler 7B, StarCoder2-3B, Qwen2.5-Coder-1.5B) are fine-tuned via LoRA (r=32, α=16) on a 5,000-sample subset using sequence-to-sequence prediction. A three-part toolchain supports evaluation: Alive2-based formal verification for functional equivalence, llvm-mca static performance estimation on target hardware, and an extensible pipeline for incorporating new compilers, targets, or autotuned optimization sequences.

## Results

Fine-tuning LLM Compiler (7B) on a 5,000-sample subset of IR-OptSet yields dramatic gains: Code Analysis EM jumps from 0.00% to 38.52% (BLEU 0.96) and Optimized Code Generation EM rises from 0.00% to 52.00% with correctness improving from 6.00% to 84.40%. StarCoder2 (3B) achieves the highest Code Analysis EM at 48.10% after fine-tuning. In the head-to-head performance comparison against LLVM -O3 on 422 correctness-verified samples, the IR-OptSet-fine-tuned LLM Compiler matches the compiler in 307 cases and outperforms it in 64 cases.

## Baselines & Comparisons

The paper compares IR-OptSet against three existing IR-oriented datasets—SLTrans, ProGraML, and ComPile—by fine-tuning the same LLM Compiler on 5,000 samples from each. IR-OptSet achieves the highest accuracy across nearly all subtasks: Dominator Tree Construction (90.60% EM vs. 78.00% for SLTrans, 78.20% for ProGraML, 73.60% for ComPile), Loop Detection (81.60% vs. 73.00%, 63.80%, 62.00%), and Memory Access Analysis (54.00% vs. 22.60%, 33.80%, 38.40%). For Optimized Code Generation, IR-OptSet leads in EM (45.40%) and correctness (81.00%), though ComPile is close on EM (43.40%) and SLTrans is competitive on BLEU (0.86 vs. 0.86). In the diversity analysis (Fig. 5), IR-OptSet triggers the highest effectiveness frequency across nearly all top-30 optimization steps, and in the generalization test (Fig. 6), the IR-OptSet-fine-tuned model consistently outperforms other fine-tuned models on cross-dataset test samples, confirming broader transformation coverage.

## Relation to Prior Work

This paper positions itself within the emerging line of LLM-based IR optimization work initiated by LLM Compiler [13, 14] and IRCoder [52], which formulated IR-to-IR transformation as a sequence-to-sequence generation problem. Its key conceptual departure from prior IR-oriented datasets (SLTrans, ProGraML, ComPile) is the 'optimization-sensitive' criterion: rather than collecting arbitrary IR samples, IR-OptSet specifically selects programs whose IR undergoes diverse and representative transformations under the -O3 pipeline, filtering out samples where fewer than 8% of executed passes produce changes. The methodological approach (LoRA fine-tuning of existing LLMs, function-level IR splitting, structural hashing for deduplication) follows established practices from the LLM Compiler and IRCoder pipelines, making the contribution primarily a dataset and evaluation framework rather than a new modeling architecture.

## Why It Matters / Open Questions

IR-OptSet fills a concrete gap in the LLM-for-compilers ecosystem by providing the first publicly available dataset explicitly designed to expose models to transformation-rich IR, along with a practical toolchain for correctness verification (Alive2), static performance evaluation (llvm-mca), and dataset extension. The finding that a model fine-tuned on just 6K samples from IR-OptSet outperforms LLVM -O3 in 64 of 422 cases is encouraging but rests on static cycle estimation rather than real execution, and the function-level granularity precludes cross-function optimizations. Open questions include whether the optimization-sensitive framing generalizes to whole-program or cross-compiler settings, whether the 64-case advantage holds under dynamic evaluation, and whether the dataset's 8-domain coverage is sufficient to capture the full breadth of real-world optimization sensitivity.
