## Problem

API-augmented LLM requests break the assumption that output token count correlates with total execution time, rendering traditional size-based schedulers (e.g., Shortest Job First) ineffective. Existing systems like INFERCEPT rely on FCFS scheduling and only select memory-handling strategies (Preserve, Discard, Swap) at the moment an API call is reached, causing head-of-line blocking and poor latency guarantees under memory constraints.

## Input / Output

MARS ingests user text prompts and, before any tokens are generated, produces three scheduling artifacts: a predicted pre-API output length (via OPT-125M embeddings fed into a 50-bin linear classifier, each bin spanning 10 tokens), an API handling strategy label (Preserve, Discard, or Swap) chosen to minimize predicted memory waste, and a priority score equal to the request's predicted total memory consumption over its lifecycle. The final output is the generated text response, but the scheduling decisions are made entirely before the request enters the running batch, enabling the scheduler to interleave pre-API work of shorter requests during longer requests' API waits.

## Method

MARS operates in two tightly coupled steps. First, a lightweight predictor (OPT-125M + linear head, trained on ToolBench with cross-entropy loss over 50 length bins) estimates the pre-API output size, while API duration and response size are estimated from per-API-class averages extracted from the prompt; these predictions feed INFERCEPT's memory-waste equations to select the handling strategy that minimizes the integral of idle KV-cache memory over the API wait. Second, the scheduler ranks all waiting requests by their predicted total memory consumption (the time-integral of KV-cache occupancy across the request's full lifecycle, including API handling), which subsumes both request size and strategy effects—unlike SJF, which ignores how a Preserve strategy inflates memory during an API call. A per-request starvation counter (threshold 100 iterations) promotes long-waiting requests to the head of the queue to bound tail latency. The entire pipeline is implemented on top of vLLM's paged-attention KV-cache manager, and multi-API requests are segmented so each API call is treated as a fresh scheduling decision.

## Results

MARS achieves 27%–85% improvements in end-to-end latency and 4%–96% reductions in TTFT compared to INFERCEPT across three datasets (single-API, multi-API, ToolBench) and four model sizes (TinyLlama 1.1B, GPT-J 6B, Vicuna 13B, Llama 70B). At low request rates (3 req/s) on the single-API dataset, gains are modest (4–5% TTFT reduction vs. INFERCEPT, up to 15% E2E latency vs. vLLM), but at higher rates (4–5 req/s), MARS achieves over 90% TTFT reduction and 80–90% E2E latency improvement over both baselines. On the ToolBench dataset at rate 3, MARS yields 75–99% TTFT improvements and over 60% latency gains. Gains over vanilla vLLM are consistently larger than over INFERCEPT across all settings.

## Baselines & Comparisons

MARS is compared against two baselines: INFERCEPT (Abhyankar et al., ICML 2024), which uses dynamic handling-strategy selection at API-call time combined with FCFS scheduling, and vanilla vLLM (Kwon et al., SOSP 2023), which has no API-aware scheduling. MARS consistently outperforms both across all datasets, model sizes, and request rates. Against INFERCEPT, the key advantage comes from integrating predictive handling-strategy assignment with memory-based scheduling rather than FCFS; the component breakdown (Figure 6) shows that adding only the predicted handling strategy to vLLM (without the new scheduler) yields performance close to but slightly worse than INFERCEPT, while the full MARS scheduler provides the decisive gains. Against vanilla vLLM, MARS shows larger absolute improvements because vLLM has no API-handling logic at all, so MARS's memory-aware scheduling and strategy assignment address a fundamentally missing capability. The paper also notes that MARS handles mixed API/non-API workloads (50% non-API) with consistent improvements over both baselines (Appendix C.2).

## Relation to Prior Work

MARS builds directly on vLLM's paged attention and KV cache management as its inference substrate, and on INFERCEPT's formulation of memory waste for the three API handling strategies (Preserve, Discard, Swap). The key departure is that INFERCEPT makes handling decisions dynamically at API-call time under FCFS scheduling, while MARS integrates predictive handling-strategy assignment with a novel memory-integral-based scheduling policy, unifying what were previously separate concerns. The paper also positions itself against the broader LLM scheduling literature (Orca, FastServe, Trail, LTR, Sarathi, Splitwise), noting that all prior size-based or prediction-based schedulers assume output length correlates with execution time—an assumption that breaks down once API calls are introduced.

## Why It Matters / Open Questions

As compound AI systems with tool calls, retrieval, and multi-model pipelines become the dominant deployment pattern, efficient scheduling for API-augmented requests is a practical bottleneck that existing inference engines do not address. The paper's clean framing—ranking by predicted total memory (the time-integral of KV cache occupancy) rather than by output tokens—offers a principled generalization of SJF to the augmented setting. Open questions include theoretical algorithmic bounds for scheduling with API calls (which the authors note is unstudied in the scheduling literature), handling highly variable API response sizes beyond class averages, and extending the single-segment handling strategy to truly multi-API requests with cumulative memory effects. The moderate prediction accuracy (68.5% within 5 tokens) and reliance on per-API-class averages suggest room for improvement in the predictive component.
