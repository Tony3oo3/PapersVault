## Problem

Existing LLM coding benchmarks evaluate function-level generation or algorithmic tasks, and when security is assessed it is typically on isolated functions or via static analyzers with high false-positive/negative rates. No benchmark tests whether LLMs can generate complete, deployment-ready backend applications that are simultaneously functionally correct and resistant to real, executable security exploits.
![Teaser figure](../imgs/ICML20252431/cropped_page0_idx0.webp)

## Input / Output

Each task provides an OpenAPI 3.0.3 specification (averaging ~430 tokens) describing REST API endpoints, combined with a target framework's language, allowed packages, and environment-specific constraints (e.g., single-file vs. multi-file structure, SQLite database path, port binding). The LLM must produce a complete, runnable backend application (one or multiple source files) that starts an HTTP server on 0.0.0.0:5000. Evaluation yields two metrics per task: pass@k (all functional tests pass) and sec_pass@k (all functional tests pass AND no security exploit succeeds), with k=1 in the main results and k=5 for non-reasoning models.

## Method

BAXBENCH constructs 392 tasks by crossing 28 framework-agnostic backend scenarios (54 total API endpoints, 1–5 per scenario) with 14 frameworks across 6 languages (Go, JavaScript, PHP, Python, Ruby, Rust). Correctness is verified by manually written, framework-agnostic functional tests that exercise every endpoint per the OpenAPI spec. Security is assessed not by static analysis but by expert-written dynamic exploits—both black-box (malicious API requests targeting path traversal, SQL injection, code injection, XSS, etc.) and white-box-like (inspecting SQLite databases and filesystem artifacts for plaintext secrets)—covering 13 high-severity CWEs, 9 of which appear in the MITRE Top 25. Generated code is executed in isolated Docker containers, and three prompt variants (no security hint, generic best-practices reminder, oracle CWE-specific instructions) are compared to isolate the effect of security-aware prompting. The benchmark is modular: adding a new framework requires no changes to tests or exploits, and the evaluation pipeline is fully reproducible.

## Results

On BAXBENCH (392 tasks across 28 scenarios and 14 frameworks), the best model OpenAI o1 achieves only 62% pass@1 on functional correctness, while the best sec_pass@1 (correct AND secure) is 35% achieved by OpenAI o3-mini. On average, approximately 50% of functionally correct programs generated by each model are exploitable by the security tests. The overall best correct-and-secure generation rate across all models does not surpass 37%, indicating that even flagship LLMs are far from deployment-ready for backend code generation.

## Baselines & Comparisons

The paper evaluates 11 LLMs (6 providers, 4 closed-source, 7 open-source) on the same 392 BAXBENCH tasks. OpenAI o1 leads on functional correctness (62% pass@1) but is outperformed on security by OpenAI o3-mini (35% vs. ~29% sec_pass@1), DeepSeek-R1, and Claude-3.5 Sonnet. Reasoning models (o1, o3-mini, DeepSeek-R1) show the strongest response to security-specific prompting: a generic security reminder yields considerable sec_pass@1 gains for these models, while non-reasoning models show minimal improvement. When Claude-3.5 Sonnet is augmented with the OpenHands agent scaffolding, pass@1 improves from 53.6% to 59.5% (no security prompt), and under the oracle security prompt, sec_pass@1 improves by +7.2% (agent) versus +2.5% (base model), underscoring the value of test-time compute for security. Across frameworks, models consistently struggle more with less popular languages (Rust-Actix, PHP-Lumen) and multi-file frameworks, where even the few correct solutions contain a higher share of vulnerabilities. The OpenAPI specification format yields a consistent +6.8% to +9.3% pass@1 improvement over plaintext descriptions across o3-mini, GPT-4o, and Claude-3.5 Sonnet.

## Relation to Prior Work

BAXBENCH carves new ground at the intersection of two previously separate benchmarking lines: function-level code generation (HumanEval, MBPP, APPS) and code security evaluation (CWEval, SecCodePLT, CodeGuard+). Prior correctness benchmarks are saturated and limited to single functions, while prior security benchmarks adopt a bottom-up approach that crafts isolated tasks around individual CWEs. BAXBENCH departs from both by taking a top-down approach—starting from realistic multi-endpoint backend scenarios and then identifying multiple CWEs per scenario—and by jointly evaluating correctness and security on the same complete application, something no prior benchmark does. The use of dynamic, expert-written exploits (rather than static analyzers) for security evaluation also distinguishes it from tools like Snyk Code, which the paper shows to be unreliable at scale due to high false positive and false negative rates.

## Why It Matters / Open Questions

The finding that even the best model (OpenAI o1) achieves only 62% correctness and that roughly half of all correct programs are exploitable provides a concrete, reproducible measure of how far LLMs are from deployment-ready code generation—a gap that prior saturated benchmarks have obscured. The benchmark's modular design (28 scenarios × 14 frameworks, framework-agnostic tests) makes it a practical, extensible tool for tracking progress as models improve. Key open questions include whether post-training on security-specific data can close the security gap without sacrificing correctness, whether reasoning models will eventually make security prompting unnecessary, and whether the 28 scenarios and 13 CWEs provide sufficient coverage as LLM capabilities grow. The paper also highlights that less popular frameworks (Rust-Actix, PHP-Lumen) are a particular weak point, suggesting that training data diversity remains a bottleneck.
