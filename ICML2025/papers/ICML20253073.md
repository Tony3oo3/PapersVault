## Problem

Existing software engineering benchmarks like SWE-Bench depend on human-submitted GitHub issues, requiring extensive cleaning and failing to capture the full spectrum of iterative development tasks. Commit0-Bench requires generating an entire library in one shot, which does not reflect real-world incremental coding. There is no systematic, automatically synthesizable benchmark that evaluates LLMs on step-by-step, test-verified code construction with explicit dependency ordering.

## Input / Output

The pipeline consumes a complete Python codebase with passing unit tests and a Docker development environment, and produces 16,061 training and 2,020 test instances, each a tuple of (partial codebase, LLM-generated requirement document, ground-truth patch, unit tests). The partial codebase is created via skeletonization: Target Core Function implementations are replaced with LLM-generated docstrings, while Dependent Core Function definitions are removed entirely. Ground-truth solutions are provided in two formats—Replace Format (GitHub merge-conflict style) and Patch Format (standard diff output)—to support both direct file editing and patch-based evaluation.

## Method

SWE-Flow's core mechanism is a runtime dependency analysis: a custom hook (SWE-Flow-Trace) instruments the function call stack during unit test execution to build a Runtime Dependency Graph (RDG) per test, capturing only intra-project function calls and filtering out external library invocations. From the RDGs, a development schedule is generated by merging test functions that cover the same core functions, sorting by core-function count, and iteratively absorbing already-covered functions to enforce topological dependency order. At each schedule step, the codebase is skeletonized and an LLM (Qwen2.5-Coder-32B-Instruct) generates a requirement document from the test function content using a two-shot prompt. The diff between the original and skeletonized codebase yields the ground-truth patch. The resulting dataset is used to fine-tune Qwen2.5-Coder-32B-Instruct via Megatron-LM (128 H800 GPUs, 32k max sequence length, batch size 1024, 32 training steps), producing SF-Coder-32B-Instruct, which substantially outperforms the base model on SWE-Flow-Bench (Lite) in both replace and patch formats.

## Results

On SWE-Flow-Bench (Lite), SF-Coder-32B-Instruct (fine-tuned from Qwen2.5-Coder-32B-Instruct with SWE-Flow data) achieves an average pass rate of 43.8% in Replace format and 32.5% in Patch format across 12 Python projects. This represents a substantial improvement over the base Qwen2.5-Coder-32B-Instruct (32.3% Replace, 12.7% Patch). In Replace format, SF-Coder-32B-Instruct ranks second only to DeepSeek-V3 (44.9%), while in Patch format it ranks second only to claude-3.5-sonnet (39.3%), outperforming all other models by a wide margin.

## Baselines & Comparisons

SF-Coder-32B-Instruct substantially outperforms its base model Qwen2.5-Coder-32B-Instruct in both formats: +11.5 pp in Replace (43.8% vs 32.3%) and +19.8 pp in Patch (32.5% vs 12.7%), confirming the effectiveness of SWE-Flow-synthesized training data. Against DeepSeek-V3, SF-Coder-32B-Instruct is narrowly behind in Replace (43.8% vs 44.9%) but dominates in Patch (32.5% vs 5.7%), where DeepSeek-V3's patch generation is nearly non-functional. Against claude-3.5-sonnet, SF-Coder-32B-Instruct wins decisively in Replace (43.8% vs 22.3%) but trails in Patch (32.5% vs 39.3%), suggesting claude-3.5-sonnet was trained on substantial patch-format data. SF-Coder-32B-Instruct also surpasses DeepSeek-R1 in both formats (43.8% vs 39.0% Replace; 32.5% vs 18.5% Patch) and gpt-4o by a large margin (43.8% vs 4.7% Replace; 32.5% vs 18.3% Patch). In agent evaluation (OpenHands), claude-3.5-sonnet remains the strongest (e.g., 98% accuracy on cryptography), but even it struggles on complex projects like transitions (8%) and pandas (48%), highlighting the difficulty of the benchmark.

## Relation to Prior Work

SWE-Flow departs from SWE-Bench's reliance on human-submitted GitHub issues and Commit0-Bench's single-shot full-implementation paradigm by grounding data synthesis in Test-Driven Development (Beck, 2002), where unit tests serve as executable specifications. The key methodological departure is the use of a Runtime Dependency Graph (RDG) constructed from actual test execution (via a custom tracing hook) rather than static code analysis or commit history mining, enabling automatic inference of incremental development schedules. The fine-tuning component builds on Qwen2.5-Coder-32B-Instruct using Megatron-LM, positioning the work within the broader trend of synthetic-data instruction tuning for code LLMs (WizardCoder, OSS-Instruct, CodeOcean).

## Why It Matters / Open Questions

SWE-Flow-Bench fills a gap between standalone function benchmarks (HumanEval, MBPP) and issue-resolution benchmarks (SWE-Bench) by evaluating incremental, multi-file development in a TDD structure, offering finer-grained interpretability of model failures. The automated synthesis pipeline is scalable to any Python project with passing unit tests, potentially enabling large-scale pre-training corpora and RL-based training with verifiable rewards. Key limitations include restriction to Python and synchronous programs (asynchronous/multi-process code is unsupported), a relatively small project pool (74 usable projects), and the Lite split's lower difficulty due to shallower dependency depths. Open questions include whether the RDG-based approach generalizes to other languages and whether the synthetic data quality degrades at scale.
