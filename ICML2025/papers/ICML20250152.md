## Problem

CPU-based DNN serving systems like TorchServe default to running a single model instance with all available threads for intra-operator parallelism, but this yields diminishing returns as thread count increases. Neither maximizing intra-op parallelism (one fat instance) nor maximizing inter-instance parallelism (one instance per core) minimizes inference latency, and the optimal configuration of instances, threads, and batch sizes is workload- and deployment-specific, making manual tuning impractical.

## Input / Output

Given a DNN model, a target batch size B (estimated online from request queue depth via two-level smoothing: EWMA followed by mode over recent estimates), and T available server threads, Packrat produces an <i,t,b> configuration specifying how many concurrent instances to run, how many threads each instance uses for intra-op parallelism, and what sub-batch size each processes, subject to the constraints Σi_j·t_j = T and Σi_j·b_j = B. The batch size B is rounded to the next lower power of two, and reconfiguration is triggered only when the smoothed batch size differs from the current one, avoiding unnecessary flip-flopping.

## Method

Packrat profiles single-instance configurations over a reduced space of <t,b> pairs (all t from 1 to T, but b restricted to powers of 2, cutting profiling from O(2^n·T) to O(n·T) configurations), recording average batch latency L_{t,b} for each. It then formulates a 2D multi-dimensional knapsack problem where the knapsack dimensions are (T, B), items are the profiled <t,b> configurations with latency as value, and the objective is to minimize the maximum latency across concurrently running instances (since end-to-end latency equals the slowest instance). The dynamic programming recurrence opt[t,b] = min over t'≤t, b'≤b of max(opt[t−t', b−b'], L_{t',b'}) exploits optimal substructure to find the configuration in pseudo-polynomial time. For online reconfiguration without downtime, Packrat uses active-passive scaling: it scales up a passive set of workers to the new configuration, redirects traffic, then scales down the old active set in the background, avoiding the overhead of modifying thread pools in operator libraries like MKL-DNN or ATen.

## Results

Packrat achieves an average inference latency speedup of 1.43× to 1.83× (and maximum speedup of 1.72× to 2.09×) over the default fat-instance baseline in end-to-end TorchServe serving, averaged across batch sizes for ResNet-50, Inception-v3, GPT-2, and BERT. In PyTorch microbenchmarks, the per-model mean speedups are 1.53× (ResNet-50), 1.52× (Inception-v3), 1.18× (GPT-2), and 1.13× (BERT). End-to-end gains exceed microbenchmark gains because multi-instance execution also parallelizes pre- and post-processing. Online reconfiguration via active-passive scaling takes ~5 s and reduces latency by 1.54× after a workload shift, with no serving downtime.

## Baselines & Comparisons

The primary baseline is the default TorchServe configuration: a single 'fat' model instance using all 16 threads for intra-op parallelism on the full batch. Packrat consistently outperforms this baseline by 1.43×–1.83× on average latency across all four models and batch sizes in end-to-end TorchServe, and by 1.13×–1.53× in PyTorch microbenchmarks. A secondary baseline of T single-threaded instances (one per core, no intra-op parallelism) performs worse than the fat instance due to cross-instance interference and inability to exploit intra-op parallelism; Packrat beats this baseline by up to 3.2× on GPT-2 and by 1.02×–1.75× on the other models. The paper does not include head-to-head comparisons with other serving systems (Triton, TensorFlow Serving) or with prior auto-tuning approaches (TensorTuner, McBench) in quantitative terms; those are discussed only qualitatively in Related Work. The gap between Packrat's expected speedup (from isolated profiling) and actual speedup is 12–15%, attributed to license-based CPU downclocking and increased memory bandwidth contention when instances run concurrently.

## Relation to Prior Work

Packrat builds directly on TorchServe's plugin architecture and worker scaling mechanisms, extending them with an automated configuration optimizer. Conceptually, it departs from the dominant paradigm in CPU-based DNN serving—maximizing intra-operator parallelism within a single 'fat' instance—by instead partitioning work across multiple 'thin' instances, a strategy inspired by observations of diminishing returns from OpenMP thread scaling. The optimization itself draws on the multi-dimensional knapsack formulation, while the adaptive batching and online reconfiguration mechanisms relate to prior work on batched request processing (Clipper, Nexus, InferLine) and preemptive scheduling (Shinjuku, Shenango), though Packrat is the first to frame the <i,t,b> configuration problem explicitly and solve it via dynamic programming in a serving context.

## Why It Matters / Open Questions

As CPU-based DNN serving becomes increasingly important (due to GPU cost, power, and underutilization), Packrat's 1.43×–1.83× latency improvement over the standard fat-instance baseline is practically significant for production deployments on existing server fleets. The online active-passive reconfiguration mechanism avoids serving downtime, making the approach deployable in real systems. Key limitations include evaluation on a single server with a specific Intel Xeon configuration, the ~12–15% gap between expected and actual speedup due to license-based downclocking and memory bandwidth contention, and the assumption that workloads for a given model are relatively stable. Open questions include how the approach generalizes to multi-server deployments, multi-model serving with shared resources, and whether the DP formulation extends naturally to SLO-constrained or heterogeneous hardware settings.
