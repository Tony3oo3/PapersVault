## Problem

Specializing small edge-side language models for domain-specific tasks typically requires task-specific LoRA fine-tuning, which suffers from catastrophic forgetting and cannot generalize to unseen tasks without retraining. Existing LoRA-MoE approaches add per-token routing overhead at inference, while LoRAHub requires a pre-trained library of task-specific LoRAs. No prior method can dynamically generate task-specific LoRA parameters at inference time from a large cloud model to specialize a small edge model, while simultaneously compressing lengthy system prompts (e.g., tool definitions) into the model weights.

## Input / Output

The cloud-side LM (LLaMA3-8B) receives a system prompt containing task description, few-shot samples, role specification, and conversation format, and produces L meta tokens in a single autoregressive forward pass, where L equals the number of transformer layers in the edge-side model. These meta tokens drive a routing module that composes a discrete pool of 8 LoRA experts into layer-specific LoRA weight matrices. The generated LoRA weights are merged into the edge model's FFN layers via reparameterization, after which the specialized edge model processes user queries with no additional parameters or routing overhead. In the agent scenario, this compresses ~26 tool definitions (constituting ~91% of input context) into LoRA weights, achieving a 10.1× context compression ratio.

## Method

LoRA-Gen decouples specialization into two stages: (1) online LoRA generation on the cloud side, and (2) reparameterized inference on the edge side. The cloud-side LLaMA3-8B (fine-tuned with LoRA on q/v projections) appends L special meta tokens after the system prompt and transfers task knowledge into them via causal masking. A layer-wise routing module (two linear projections + BatchNorm + SiLU) maps each meta token to a KeepTOP-K (K=2) gate over a pool of 8 discrete LoRA experts, each containing three LoRA blocks for the gate/up/down FFN layers. The gated expert combination yields task-specific LoRA weights per layer, which are merged into the edge model's FFN via standard LoRA reparameterization, eliminating all additional inference cost. Training uses a coefficient-of-variation auxiliary loss (α=0.01) to enforce balanced expert utilization alongside standard cross-entropy LM loss. The discrete expert pool (rather than continuous projection) and meta-token bottleneck are critical: direct generation overfits to seen tasks and loses 11.1% on unseen tasks, while Gumbel-Softmax routing degrades generalization compared to deterministic KeepTOP-K.

## Results

On eight commonsense reasoning benchmarks with 5-shot samples, LoRA-Gen achieves the best average accuracy (AVE) and harmonic mean (HAR) across all three edge-side models: 55.1%/49.8% on TinyLLaMA-1.1B, 59.8%/55.0% on Qwen-1.5B, and 63.9%/60.2% on Gemma-2B, while delivering the lowest inference latency (21.2 ms, 26.7 ms, 36.1 ms respectively). On the GPT4Tools agent benchmark, LoRA-Gen with Gemma-2B reaches a 91.5% average score with a 10.1× context compression ratio, surpassing the vanilla LoRA baseline (88.4%) that requires full tool definitions in the prompt. On unseen tasks (HellaSwag, Winogrande, PIQA) with OPT-2.7B, LoRA-Gen outperforms AutoCompressors by 1.5% in average accuracy (61.6% vs. 60.1%) while being 34% faster (7.54 ms vs. 11.4 ms).

## Baselines & Comparisons

Against vanilla LoRA fine-tuning, LoRA-Gen consistently wins on both AVE and HAR across all three edge-side models (e.g., +0.8% AVE and +1.3% HAR on TinyLLaMA-1.1B; +0.7% AVE and +1.1% HAR on Qwen-1.5B) while reducing inference latency by 2.1× (21.2 ms vs. 44.5 ms on TinyLLaMA). Compared to LoRAMoE, LoRA-Gen achieves higher AVE on TinyLLaMA (55.1 vs. 54.9) and Qwen (59.8 vs. 58.8), ties on Gemma (63.9 vs. 63.9), and is 2.5–3× faster at inference (21.2 ms vs. 55.9 ms; 36.1 ms vs. 101.8 ms). Against MixLoRA, LoRA-Gen matches or exceeds AVE on all models while being 4.7× faster on TinyLLaMA (21.2 ms vs. 100.1 ms) and 4.9× faster on Qwen (26.7 ms vs. 141.9 ms). On the GPT4Tools agent benchmark, LoRA-Gen (91.5% avg, 10.1× compression) outperforms the trained LoRA baseline with tool definitions (88.4% avg, 1× compression) by 3.1 points, and removing tool definitions from the LoRA baseline causes a 26.1% drop in successful rate, underscoring LoRA-Gen's advantage in context compression. On unseen tasks with OPT-2.7B, LoRA-Gen beats AutoCompressors by 1.5% in average accuracy (61.6% vs. 60.1%) with 34% lower latency (7.54 ms vs. 11.4 ms).

## Relation to Prior Work

This paper extends the LoRA fine-tuning paradigm (Hu et al., 2021) and the LoRA-MoE plugin approach (Dou et al., 2024) by reframing specialization as an online parameter generation problem: a large cloud-side model reads a task description and produces LoRA weights for a smaller edge-side model, rather than fine-tuning on task-specific data. The key architectural departure is the use of meta-tokens as a discrete bottleneck between the cloud model's causal LM output and the edge model's LoRA space, combined with layer-wise (rather than token-wise) KeepTOP-K routing over a shared expert pool. The reparameterization step, inherited from vanilla LoRA, ensures the specialized edge model incurs zero additional inference cost, distinguishing it from LoRA-MoE methods that retain routing overhead at inference time.

## Why It Matters / Open Questions

The practical significance lies in enabling edge-side model specialization without task-specific training data or fine-tuning—only a single forward pass of the cloud model on a system prompt is needed, which is attractive for deployment scenarios where per-task data is unavailable or expensive to collect. The 10.1x context compression on agent tasks (GPT4Tools) while maintaining competitive accuracy addresses a real bottleneck in tool-use pipelines where tool definitions dominate the prompt. However, the approach is validated only on small models (1.1B–2B) with a modest cloud model (LLaMA3-8B), and the reasoning-task gains over vanilla LoRA are modest (1–3%), leaving open whether the knowledge-transfer benefit scales to larger edge models or architecturally dissimilar cloud/edge pairs. The paper also notes future applicability to multimodal and unified understanding-generation systems.
