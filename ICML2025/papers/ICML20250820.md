## Problem

Repository-level code auditing with LLMs is fundamentally misaligned: code repositories form massive graphs (e.g., over one million data-flow edges in shadowsocks-libev) requiring path-sensitive reasoning across functions, while LLMs are designed for sequential text processing and suffer from hallucinations and context-window limits when prompted with large codebases. Existing LLM-driven approaches are restricted to small-scale codebases like smart contracts or single functions, and traditional static analyzers require compilation, limiting their applicability during development.

## Input / Output

The system takes a C/C++ source code repository (ranging from ~2K to 1.7M LoC) and a bug type definition (NPD, MLK, or UAF) as input, using tree-sitter pattern matchers to identify source values without any compilation step. It produces validated bug reports containing the complete inter-procedural trail of data-flow facts (e.g., NULL@s₄ → json@s₁₄ → field_json@s₇ → dereference@s₈), the corresponding feasible program path, and path conditions. Analysis is bounded to a calling context of K=4 functions, and the agent memory caches data-flow facts per (function, program value) pair to avoid redundant LLM queries.

## Method

REPOAUDIT is a three-component LLM agent that navigates program graphs externally, prompting the model one function at a time in a demand-driven fashion. The **initiator** identifies source values via tree-sitter pattern matching; the **explorer** traverses relevant functions by prompting the LLM with a structured template that enforces three sequential steps—pointer aliasing identification, program abstraction (extracting only propagation-relevant statements), and feasible path exploration with execution simulation to derive data-flow facts—storing results in agent memory and following the call graph only when values actually escape function boundaries; the **validator** applies two checks: a parsing-based control-flow order verifier for intra-function data-flow facts, and an LLM-prompted satisfiability check for inter-procedural path conditions to discard infeasible bug reports. The key insight is that LLMs can implicitly perform program abstraction and distinguish relevant from irrelevant paths within a single function, thereby mitigating path explosion without explicit path enumeration, while the demand-driven navigation and caching strategy keep token costs to an average of $2.54 per project.

## Results

REPOAUDIT (powered by Claude 3.5 Sonnet) detects 40 true bugs across 15 real-world benchmark projects (avg. 251 KLoC) with 78.43% precision, reproducing all 21 previously reported bugs and uncovering 19 new bugs (14 since fixed). On average, each project audit takes 0.44 hours (1,577 s) and costs $2.54, with 100.67 prompting rounds. In a separate real-world evaluation on 9 additional high-profile projects, REPOAUDIT detects 185 new bugs (85.71% precision), of which 95 are confirmed and 79 are fixed by developers.

## Baselines & Comparisons

REPOAUDIT substantially outperforms all five baselines. Against single-function CoT prompting (Ding et al., 2024), which detects only 1 intra-procedural NPD bug, and multiple-function CoT prompting / LLMSAN (Wang et al., 2024c), which detects 10 TPs, REPOAUDIT finds 40 TPs by performing path-sensitive, demand-driven exploration rather than end-to-end prompting. Against the agent-centric LLMDFA (Wang et al., 2024a), REPOAUDIT detects the same bugs but with 165× fewer prompting rounds and 123× fewer input tokens (PATHSCAN setting), or 1,737× fewer prompts and 1,193× fewer tokens (SRCSCAN setting), because LLMDFA exhaustively summarizes all data-flow facts per function while REPOAUDIT explores only on demand. Against Meta INFER, REPOAUDIT detects 40 TPs vs. 7 TPs at comparable precision (78.43% vs. 77.78%), while INFER cannot analyze 7 of 15 projects due to compilation failures or crashes. Against Amazon CODEGURU, REPOAUDIT finds 40 TPs versus 0 TPs and 18 FPs, demonstrating that CODEGURU's pattern-based approach is not robust to diverse buggy code styles.

## Relation to Prior Work

REPOAUDIT carves new ground at the intersection of LLM agent architectures and traditional program analysis. It departs from the compiler-based paradigm (symbolic execution, taint analysis, SMT-based path feasibility) by replacing these with LLM-intrinsic capabilities—program abstraction, intuitive pointer handling, and feasible path exploration—guided by structured prompts. Compared to prior LLM-driven auditors like LLMDFA (which exhaustively summarizes all data-flow facts per function in a compiler-like fashion) and end-to-end CoT prompting approaches (which feed entire programs to the model), REPOAUDIT introduces a demand-driven, function-by-function agent with persistent memory and a dedicated validator, explicitly motivated by cognitive science findings on how human auditors navigate code graphs. It also contrasts with compilation-dependent industrial tools (Meta INFER, Amazon CodeGuru) by operating directly on source code, enabling development-time auditing of non-compilable codebases.

## Why It Matters / Open Questions

This is the first purely LLM-driven auditor demonstrated on real-world repositories (average 251 KLoC) without any compilation step, achieving 78–88% precision at ~$2.54 per project—costs that make continuous, development-time auditing economically viable in a way compilation-dependent tools cannot. The finding that 185 new bugs were detected in actively maintained projects (174 confirmed/fixed) demonstrates tangible real-world impact beyond benchmark reproduction. Key open questions include: soundness for call chains longer than four functions, sensitivity to source density in large repositories, generalization beyond C/C++ and the three evaluated bug types, and whether fine-tuning or specialized RAG over control-flow structure can further reduce the residual ~20% false positive rate. The broader implication is that LLMs may eventually replace the entire compilation-and-IR infrastructure that classical static analysis depends on.
