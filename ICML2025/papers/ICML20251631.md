## Problem

Prior automated code review methods reduce the task to snippet-level code-to-text generation evaluated by text similarity metrics (BLEU/ROUGE), ignoring repository context, merge-request-level defect detection, and real-world developer workflows. This paper identifies four practical gaps in industry-scale C++ codebases: capturing sufficient code context beyond diff hunks, improving key bug inclusion (KBI), reducing false alarm rates from nitpicks and hallucinations, and integrating comments into human-centric DevOps workflows with precise line localization.

## Input / Output

The system consumes a merge request's code diff within a cloned C++ repository, processing it through AST-based static analysis to produce context-enriched code slices (via four slicing strategies: Original Diff, Parent Function, Left Flow, Full Flow). Code is formatted with inline line-number annotations (operation label + line number + content) to enable precise comment placement. The output is a set of filtered, line-localized review comments injected directly into the company's DevOps platform, each scored on a 1–7 scale across three dimensions (nitpick likelihood, fake-problem likelihood, and criticality), with only comments exceeding thresholds retained.

## Method

The framework is a four-stage pipeline operating at merge-request granularity without fine-tuning any LLM. Stage 1 applies AST-based code slicing (backward L-value tracing for Left Flow; forward R-value and callee tracing for Full Flow) to extract targeted context, avoiding the performance degradation from overly long inputs. Stage 2 employs a multi-role LLM system—multiple Reviewers generate scored comments with chain-of-thought prompts, a Meta-Reviewer merges and deduplicates across reviewers, a Validator re-scores and discards hallucinations, and a Translator localizes output—leveraging LLM non-determinism for recall and self-correction for precision. Stage 3 applies a sequential filtering mechanism (coarse Q1/Q2 thresholding, Top-k truncation by Q3 criticality, meta-reviewer consensus filtering, and validator re-scoring) to suppress false alarms. Stage 4 uses an Aider-inspired inline line-number format to anchor each comment to specific code lines. The system is evaluated on 45 real-world fault-induced merge requests from a 400M-DAU recommendation service, achieving up to 10× improvement in CPI over prior baselines using open-source LLMs (LLaMA-3.1-405B, Qwen2-72B, Command R+, Mistral-large).

## Results

On the 45-case C++ fault-report dataset (merge-request level), the best configuration (LLaMA3.1-405B with Full Flow slicing) achieves KBI of 28.89%, FAR₁ of 86.11%, and CPI₁ of 18.76, with CPI₂ reaching 30.68%. Qwen2-72B with Full Flow attains the highest KBI (42.22%) among all tested engines. Across all LLM engines, the framework achieves a 10× improvement in CPI₁ over the strongest baseline (CCT5 at 2.32) and a 2× improvement over the best single-LLM baseline (LLaMA-Reviewer at 2.30).

## Baselines & Comparisons

The proposed framework decisively outperforms all four baselines on every reported metric. CodeReviewer and DISCOREV achieve 0% KBI and 0% CPI₁, meaning they fail to recall any key bugs from the 45 real-world fault cases. CCT5 (KBI 2.22%, CPI₁ 2.32) and LLaMA-Reviewer (KBI 2.22%, CPI₁ 2.30) marginally recall one key bug but still produce a 97%+ false alarm rate. In contrast, the best framework configuration (LLaMA3.1-405B, Full Flow) reaches KBI 28.89% and CPI₁ 18.76, representing roughly a 10× gain in CPI₁ over the strongest baseline. Even the weakest framework configuration (Command R+ 103B, Full Flow, CPI₁ 8.43) still exceeds the best baseline by more than 3×. The gap is most dramatic on KBI, where the framework recalls 13–42× more key bugs than any baseline, confirming that the end-to-end pipeline (code slicing + multi-role LLM + filtering) is the primary driver of the improvement rather than any single LLM engine.

## Relation to Prior Work

This paper departs from the dominant snippet-level code-to-text formulation of automated code review (CodeReviewer, CCT5, LLaMA-Reviewer, DISCOREV) by reframing the task at merge-request granularity with repository-level context. It repurposes code slicing from static analysis (previously applied to vulnerability detection) as a context-extraction mechanism for LLM-based review, and combines it with a multi-role LLM pipeline (Reviewer, Meta-Reviewer, Validator, Translator) inspired by multi-agent collaboration frameworks. The evaluation paradigm shifts from BLEU/ROUGE text similarity to defect-oriented metrics (KBI, FAR, CPI, LSR) grounded in real fault reports, drawing on the Critique-Bug Inclusion concept from McAleese et al. (2024).

## Why It Matters / Open Questions

This is the first deployment of an end-to-end automated code review pipeline within a production DevOps system serving hundreds of millions of users, providing rare evidence of what works (and what doesn't) at industrial scale. The introduction of MR-level, defect-focused metrics (KBI, FAR, CPI, LSR) offers a more meaningful evaluation framework than text similarity, potentially reshaping how the field measures progress. Key limitations include the small evaluation set (~45 fault MRs), C++-only focus, heuristic filtering thresholds, and absence of formal user studies; open questions include whether combining slicing strategies, adaptive thresholds, and heterogeneous model assignments can close the remaining gap toward reliable defect recall.
