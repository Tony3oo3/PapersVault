## Problem

Existing LLM-based patching agents face a fundamental tradeoff: agent-based planning methods achieve high resolved rates but incur high costs and suffer from instability due to LLM randomness in workflow decisions, while rule-based planning methods are stable and cheap but are constrained by rigid workflows that limit patching performance. No prior method simultaneously balances patching efficacy, run-to-run stability, and per-instance cost for practical real-world deployment.

## Input / Output

PatchPilot takes as input a full Python code repository (multiple files with interdependent functionalities) and a natural-language issue description, and produces a code patch in git diff format. The system internally generates a Proof-of-Concept (PoC) test that triggers the bug and identifies three benign functionality test files from the repository; the final patch must pass both the PoC and all functionality tests to be considered successful. Patches are generated in Search/Replace edit format and converted to git diff, with a maximum of 12 patches (N_max) generated per instance across iterative refinement rounds.

## Method

PatchPilot employs a rule-based planning workflow with five sequential components: reproduction, localization, generation, validation, and refinement. Reproduction uses a Reflexion-style iterative loop to generate a working PoC and identifies relevant benign functionality tests. Localization follows a hierarchical file→function→line procedure augmented with codebase search tools and a review step that retrieves surrounding context beyond the minimal root cause. Generation is split into a planning phase (producing a multi-step patching plan, inspired by chain-of-thought) and a generation phase, with three prompt variants (comprehensive, minimal, standard) to encourage patch diversity. Validation ranks candidates by running both PoC and functionality tests, prioritizing PoC pass over functionality pass. The key novelty is the refinement component, which iteratively improves the top-ranked patch based on validation feedback rather than regenerating from scratch, and can re-run localization if no new tests are passed. An optional formal verification stage uses LLM-generated pre/post-conditions checked by the Z3 SMT solver via CrossHair.

## Results

On SWE-bench Lite (300 instances), PatchPilot resolves 45.33% of issues at a cost of $0.97 per instance, outperforming all open-source baselines. On SWE-bench Verified (500 instances), PatchPilot achieves 53.60% resolved rate at $0.99 per instance, again the best among open-source methods. In a stability comparison on 45 shared instances over 3 runs, PatchPilot resolves 30–35 instances (std dev 2.52) versus OpenHands' 15–21 (std dev 3.21), while costing ~$12.65 per run vs. OpenHands' ~$33.69.

## Baselines & Comparisons

PatchPilot outperforms all four open-source baselines on both benchmarks. Against the closest rule-based competitor Agentless, PatchPilot gains +4.66 pp on SWE-bench Lite (45.33% vs. 40.67%) and +2.80 pp on SWE-bench Verified (53.60% vs. 50.80%), while also being cheaper ($0.97 vs. $1.12 and $0.99 vs. $1.19 per instance). Against the SOTA agent-based method OpenHands, PatchPilot leads by +3.66 pp on Lite and +0.60 pp on Verified, at lower cost on Lite ($0.97 vs. $1.33). AutoCodeRover trails PatchPilot by a wide margin (−14.66 pp on Lite, −1.80 pp on Verified) and costs 4.5× more on Verified. Among closed-source methods, Globant edges out PatchPilot on Lite (48.33% vs. 45.33%) at comparable cost, while CodeStory achieves the highest Verified rate (62.20%) but at 20× the cost of PatchPilot ($20 vs. $0.99 per instance).

## Relation to Prior Work

PatchPilot builds directly on Agentless (Xia et al., 2024), adopting its hierarchical rule-based localization workflow (file → function → line) and fixed sequential pipeline, but departs in three key ways: it adds a self-reflection-based reproduction component, introduces a novel iterative refinement stage that improves partially-correct patches rather than regenerating from scratch, and splits generation into a planning-then-generation two-phase process inspired by chain-of-thought prompting. It positions itself explicitly against the agent-based planning paradigm (SWE-Agent, OpenHands, AutoCodeRover), arguing that rule-based planning offers superior stability and cost-efficiency at a modest resolved-rate cost. The formal verification component using CrossHair and Z3 has no direct precedent in prior patching agents, representing an early attempt at verifiable patching.

## Why It Matters / Open Questions

The paper makes a practical case that resolved rate alone is an insufficient metric for patching agents, demonstrating that rule-based planning achieves comparable accuracy at roughly half the cost and with measurably lower variance across runs — a critical consideration for production deployment. The ablation finding that PoC-only validation can actually *decrease* resolved rate (by admitting patches that fix the target bug but break other functionality) is a useful caution for practitioners. However, the formal verification component remains extremely preliminary (11 patches verified), the system is Python-only, and the overall resolved rate, while best among open-source methods, still trails top closed-source systems by 8–10 points. Open questions include whether hybrid agent/rule-based planning can close the accuracy gap without sacrificing stability, and whether fine-tuned patching models can overcome the tendency of general LLMs to produce overly simplistic fixes.
