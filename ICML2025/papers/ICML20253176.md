## Problem

When thousands of LoRA adapters are deployed simultaneously on a single server, standard LoRA's per-module trainable parameters create prohibitive memory overhead and task-switching latency. Existing parameter-sharing methods (VeRA, VB-LoRA, ShareLoRA) reduce stored parameters but capture either local or global redundancy, not both, and cannot handle the shape mismatch between attention modules (e.g., 4096×4096) and FFN modules (e.g., 4096×11008) that arises when extending sharing beyond same-shaped layers.

## Input / Output

The method takes a frozen LLM (Llama 1-7B, Llama 3-8B, or Llama 1-13B) and instruction-tuning data (Alpaca 52K or FLAN_V2), producing a compact set of adapter parameters applied to W_q, W_k, W_v, W_up, and W_down in every transformer block. The output is a text response generated by the frozen backbone plus the combined local, intra-layer, and inter-layer low-rank updates. A key constraint is that shared parameters must be reshaped to match modules of differing input/output dimensions (e.g., GQA changes the k-module shape in Llama 3), which the three transformation methods handle at inference time without additional storage.

## Method

BSLoRA decomposes each module's LoRA update ΔW = BA into three parallel sub-LoRA terms: a local term (rank r_local) capturing module-specific features, an intra-layer shared term (rank r_intra) shared across all modules within the same transformer block, and an inter-layer shared term (rank r_inter) shared across all layers, yielding f(x) = Wx + (BA)_local x + (BA)_intra x + (BA)_inter x. To reconcile the shape mismatch between shared parameters and target modules of varying dimensions, three transformation methods are proposed: Slice Sharing (slices a max-dimension shared matrix to each module's size), Gate Transformation (applies rank-1 input/output gate matrices to project between module and shared dimensions), and Kronecker Extension (expands a small shared matrix via Kronecker product with a module-specific kernel vector). Entropy-similarity analysis (via Relative Mutual Information) motivates the design by showing high redundancy both within layers and across layers, while ablation experiments confirm that combining all three components outperforms any single sharing strategy alone. With rank configuration r = {2, 4, 32} for SS, BSLoRA uses only ~44.6% of standard LoRA's parameters while improving average performance by 0.33% on commonsense reasoning and 2.08% on MMLU.

## Results

On the Commonsense Reasoning benchmark (zero-shot, Llama 1-7B), BSLoRA(SS) achieves 65.63% average with 7.03M trainable parameters (0.10% of model), outperforming standard LoRA (65.24%, 14.02M params) while using only ~50% of the parameters. On MMLU (zero-shot, Llama 1-7B), BSLoRA(SS) reaches 38.12% average versus LoRA's 35.62%, a 2.5% absolute gain. The most parameter-efficient variant, BSLoRA(KE), uses only 3.66M parameters (26% of LoRA) while still achieving 65.59% on Commonsense Reasoning and 36.42% on MMLU, outperforming all baselines. Across Llama 1-7B, Llama 3-8B, and Llama 1-13B, BSLoRA consistently matches or exceeds LoRA performance with roughly 44–56% fewer trainable parameters.

## Baselines & Comparisons

BSLoRA outperforms all five baselines on average across both Commonsense Reasoning and MMLU benchmarks on all three model sizes. Compared to standard LoRA (r=8), BSLoRA(SS) improves Commonsense Reasoning average by +0.39% (65.63 vs 65.24 on Llama 1-7B) and MMLU zero-shot by +2.50% (38.12 vs 35.62) while using only 50% of the trainable parameters (7.03M vs 14.02M). Against VeRA (r=64), which uses far fewer parameters (0.89M), BSLoRA(KE) at 3.66M parameters still achieves +1.50% on Commonsense Reasoning and +4.00% on MMLU, showing that extreme parameter reduction via random vectors comes at a significant performance cost. VB-LoRA (r=4) is the closest competitor on Commonsense Reasoning (65.51 vs 65.63 for BSLoRA(SS) on Llama 1-7B), but BSLoRA still leads on MMLU by +7.83% (38.12 vs 30.29). ShareLoRA (r=8) and Tied-LoRA (r=8) both underperform BSLoRA by 0.2–1.8% on Commonsense Reasoning and 2.4–5.4% on MMLU, with Tied-LoRA being the weakest baseline overall (63.85 avg on Commonsense, 32.13 on MMLU for Llama 1-7B). The Kronecker Extension variant (BSLoRA-KE) is the most parameter-efficient, using only 26% of LoRA's parameters (3.66M vs 14.02M) while still beating every baseline on both benchmarks.

## Relation to Prior Work

BSLoRA extends the LoRA framework by following the MultiLoRA principle of decomposing a single LoRA matrix into multiple smaller parallel LoRA modules, but introduces a structured three-way split (local, intra-layer shared, inter-layer shared) that no prior method combines. It departs from existing sharing approaches—VeRA and VB-LoRA (inter-layer only), Tied-LoRA (q/k/v only), ShareLoRA (same-shape only), and PRoLoRA (intra-layer only)—by simultaneously capturing both local module-specific features and global cross-layer patterns, and by introducing three shape-transformation mechanisms (Slice Sharing, Gate Transformation, Kronecker Extension) to handle the heterogeneous dimensions of attention and FFN modules that prior sharing methods could not address.

## Why It Matters / Open Questions

The practical significance lies in multi-adapter serving: BSLoRA's ~50% parameter reduction allows roughly 3× more LoRA adapters to fit in GPU memory (1095 vs. 341 on a V100-32G), directly addressing the bottleneck for deploying thousands of personalized adapters on a single server. The complementary relationship with S-LoRA's system-level scheduling suggests a path toward serving-scale efficiency. However, the evaluation is limited to the Llama family (7B/8B/13B), a single instruction-tuning dataset (Alpaca 52K), and one training epoch, leaving open whether the sharing strategy generalizes to other architectures, longer training, or more diverse task distributions. The authors themselves note that more intelligent, selective sharing across modules and layers remains future work.
