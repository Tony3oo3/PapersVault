## Problem

Grammar-constrained decoding (GCD) guarantees LLM outputs conform to a context-free grammar, but existing algorithms face a fundamental trade-off: either incurring >1 second per-token online masking overhead or >30 minutes of offline preprocessing to handle the misalignment between LLM subword tokens and grammar terminals. This makes GCD impractical for domains where grammars change frequently, such as program synthesis or grammar prompting.

## Input / Output

Offline, the method consumes the LLM's full subword vocabulary (e.g., 32K–151K tokens) and a CFG specified as regex-defined terminals plus production rules, producing a precomputed inverse token spanner table and parser preprocessing tables. Online, at each decoding step it takes the current token prefix, the lexer FSA state, the parser PDA state, and the PDA stack configuration, and outputs a binary mask over the vocabulary identifying exactly which tokens can lead to a grammar-conformant completion. The mask is applied to the LLM's logits to exclude invalid tokens from sampling.

## Method

The core contribution is a token spanner table that maps each (lexer state, LLM token) pair to the set of terminal sequences the lexer can produce, computed by composing a lexing transducer (built from the terminal regexes via a 1-lookahead maximal-munch FSA) with a detokenizing transducer (from Koo et al., 2024) that expands LLM tokens into character sequences. Crucially, the algorithm restricts attention to *realizable* terminal sequences—those actually producible by some LLM token from some lexer state—rather than all sequences in Γ*, which dramatically shrinks the table and enables 17.71× faster offline preprocessing. For the parser, a stack-invariance proposition and an FSA overapproximation (removing stack operations) partition terminal sequences into always-accepted and context-dependent sets, so the online decoder only consults the PDA for the smaller context-dependent subset. At decoding time, Algorithm 6 unions the always-accepted tokens with those recovered from the inverse token spanner table for context-dependent sequences accepted by the current PDA configuration, yielding the final allowed-token set in 5–32 ms per token.

## Results

GREATGRAMMA achieves a geomean 17.71× speedup in offline preprocessing over SYNCODE (e.g., 24.76s vs. 556.10s for Go/Llama) while maintaining the lowest online per-token masking overhead of 5–32 ms across all model–grammar combinations. Compared to OUTLINES, GREATGRAMMA is 30.01× slower offline but 550.57× faster online (e.g., 5.08 ms vs. 3,213 ms per token for Go/Llama). XGRAMMAR was excluded from the comparison because it failed to compile or crashed on all three grammars tested.

## Baselines & Comparisons

Against SYNCODE, GREATGRAMMA wins on both axes: 17.71× faster offline preprocessing (geomean) and 2.73× faster online masking, while SYNCODE additionally exhibited soundness bugs (incorrectly masking valid tokens) on the Go grammar. Against OUTLINES, GREATGRAMMA trades a 30.01× increase in offline preprocessing time for a 550.57× reduction in online per-token overhead, dropping from ~3–15 seconds per token to 5–32 ms. XGRAMMAR (Dong et al., 2024) was excluded entirely because it failed to compile the Java grammar and entered infinite loops or segmentation faults during decoding for Python and Go. The paper also notes that DOMINO (Beurer-Kellner et al., 2024) is not publicly available but reports comparable offline times only for a much smaller C grammar (~70 rules), whereas GREATGRAMMA handles 353–520-rule grammars in 25–35 s with the same Llama tokenizer.

## Relation to Prior Work

This paper extends the grammar-constrained decoding (GCD) framework introduced by Geng et al. (2023) and the detokenizing transducer construction of Koo et al. (2024), combining them with PDA composition techniques from Allauzen & Riley (2012) to address the token misalignment problem. The key departure from SYNCODE (Ugare et al., 2024) is the introduction of 'realizable terminal sequences'—a principled subset of all terminal sequences that can actually be produced by the LLM vocabulary from a given lexer state—rather than speculatively unrolling all sequences up to a fixed bound k. Unlike OUTLINES, which verifies token acceptability at runtime, and DOMINO, which traverses a full terminal-sequence tree per decoding step, GREATGRAMMA precomputes a compact inverse token spanner table and separates always-accepted tokens from context-dependent ones, avoiding PDA traversal in the common case.

## Why It Matters / Open Questions

The 17.71x reduction in offline preprocessing makes GCD practical for domains where grammars change per-query (program synthesis, grammar prompting), a setting where prior tools were infeasible. The discovery that published GCD implementations contain soundness bugs (SYNCODE masking valid tokens, XGRAMMAR crashing) underscores the need for simpler, more testable implementations. Key limitations remain: the approach assumes 1-lookahead maximal-munch lexing, which fails for context-dependent tokenization (e.g., Java generics), and handling k>1 lookahead or nondeterministic PDAs would significantly increase transducer size. Open directions include leveraging PDA stack information for more aggressive precomputation and GPU-native decoding.
