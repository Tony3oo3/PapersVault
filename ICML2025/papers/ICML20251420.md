## Problem

Smaller LMs (7B–8B parameters) deployed locally for code privacy lack the reasoning ability to correctly infer types when control and data flow matter, and existing LM-based approaches like TypeGen rely on in-context examples rather than genuine symbolic reasoning. The paper demonstrates that LMs do not truly understand type rules but pattern-match from demonstration examples, and that static tools like mypy fail on custom functions and third-party libraries.
![Teaser figure](../imgs/ICML20251420/cropped_page1_idx0.webp)

## Input / Output

The method takes an unannotated or partially annotated Python code snippet (within a 4,096-token context window) and produces ranked type annotations (Top-1/3/5) for argument, return, and local variable identifiers, along with a natural-language explanation of each inference step. An intermediate high-level program (a sequence of API calls like if_analysis, return_analysis, assignment_analysis) is generated as a transparent, inspectable reasoning trace that developers can view in a VSCode plugin.

## Method

NESTER decomposes type inference into two stages following the neuro-symbolic f = h ∘ g paradigm. First, an LM (Code Llama 7B or Llama 3 8B) translates the target code into a high-level program of predefined API calls that mirror the code's control-flow structure, with each conditional branch becoming an analysis unit. Second, a program interpreter executes each API by traversing a Coarse-Grained Dataflow Graph (CGDG) with Def, User, and Usee nodes per identifier, first applying regex-based symbolic parsing to recognize literal types, then falling back to a Condition Eval LM (for value-range reasoning) and a Type Infer LM (for type identification) when static rules are insufficient. A Combine module merges types across reachable execution paths to produce the final annotation (e.g., Optional[float]). The key insight is that dataflow-guided decomposition lets a 7B model reason about control flow step-by-step, achieving 70.7% Top-1 Exact Match—3.6% above TypeGen—without increasing model size.

## Results

On the ManyTypes4Py dataset, NESTER-CL (Code Llama 7B) achieves 70.7% Top-1 Exact Match overall, surpassing TypeGen-CL (67.1%) by 3.6% and the symbolic baseline HiTyper (52.4%) by 18.3%. For Match to Parametric, NESTER-CL scores 81.5% Top-1 overall, exceeding Type4Py (80.2%) by 1.3%. On complex type annotations, NESTER reaches 51.0% precision on typing.Optional and 16.7% on typing.Union, outperforming TypeGen by 28.3% and 5.8% respectively.

## Baselines & Comparisons

NESTER-CL (70.7% Top-1 EM) outperforms all LM-based baselines: TypeGen-CL (67.1%), TypeGen-L3 (59.0%), Naive-CL (31.7%), Naive-L3 (38.3%), CodeT5-large (48.4%), and InCoder-6.7B (21.9%). Against the strongest deep-learning baseline Type4Py (76.6% Top-1 EM), NESTER-CL actually trails on overall and local-variable Exact Match (70.7% vs 76.6%; 72.2% vs 82.0%) due to Type4Py's strength on short code segments, but wins on argument (70.3% vs 66.5%) and return (60.0% vs 56.1%) types, and surpasses Type4Py on Match to Parametric overall (81.5% vs 80.2%). The symbolic baseline HiTyper (52.4%) is far behind, confirming the benefit of combining LMs with symbolic rules. For complex typing categories, NESTER's advantage over TypeGen is most pronounced: 51.0% vs 22.7% on typing.Optional and 16.7% vs 10.9% on typing.Union, demonstrating the value of explicit control-flow reasoning. NESTER-L3 (Llama 3 8B backbone) underperforms NESTER-CL on Exact Match (67.8% vs 70.7%), suggesting Code Llama 7B is better suited for the code-specific sub-tasks in the pipeline.

## Relation to Prior Work

NESTER adapts the VISPROG neuro-symbolic paradigm (LM generates a high-level program of API calls, executed by a program interpreter) from visual reasoning to the type inference domain, a setting where prior work has been split between pure static analysis (HiTyper, mypy) and pure LM-based generation (TypeGen, InCoder, CodeT5). The key departure is the introduction of a Coarse-Grained Dataflow Graph (CGDG) as the symbolic substrate that the interpreter traverses, replacing the more granular Type Dependency Graph used by TypeGen. The paper also positions itself against the 'pre-train, prompt, and predict' paradigm by showing that in-context learning examples in TypeGen largely drive accuracy rather than genuine symbolic reasoning, motivating the explicit decomposition into condition evaluation and type inference sub-tasks.

## Why It Matters / Open Questions

The work addresses a practical gap: organizations needing local type inference for IP protection cannot rely on cloud-based 100B+ models, and 7B LMs alone lack the control-flow reasoning to handle conditional returns and complex type annotations. The preliminary study showing that ICL examples (not reasoning) drive TypeGen's accuracy is a useful diagnostic for the field. However, the approach is currently Python-specific, the gains over TypeGen (3.6% Top-1) are moderate, and the authors acknowledge that larger models (70B+) may close the neuro-symbolic gap without explicit symbolic scaffolding. Open questions include whether the CGDG-based decomposition generalizes to statically-typed languages and whether the interpretability benefits justify the added pipeline complexity as LM reasoning improves.
