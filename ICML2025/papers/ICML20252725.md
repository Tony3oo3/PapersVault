## Problem

Existing LLM guardrails (e.g., LlamaGuard) moderate textual harmfulness and cannot address the diverse, agent-specific safety guard requests—such as role-based database access control or user-attribute-dependent action policies—that LLM agents face in practice. Task-specific safety controls hardcoded into individual agents cannot generalize across different agent types and guard requests. This paper presents the first systematic study of guardrails designed specifically for LLM agents.

## Input / Output

GuardAgent receives four textual inputs: a set of safety guard requests (e.g., role-to-database access mappings or six web safety rules), a specification of the target agent's output format and log structure, the user's query to the target agent, and the target agent's full output log (reasoning steps, generated code, and final action/answer). It produces a binary guardrail label (0 = permitted, 1 = denied) obtained by executing generated Python code, plus a detailed violation explanation listing the specific inaccessible databases/columns or violated rules. The guardrail runs non-invasively in parallel to the target agent, so the target agent's task performance is unaffected (100% FRA across all settings).

## Method

GuardAgent is a two-step, training-free pipeline built on in-context learning. In step 1 (task planning), an LLM is prompted with the guard requests, agent specification, and target agent I/O, augmented by k demonstrations retrieved from a memory module via Levenshtein-distance similarity over past (input, output, plan, code) tuples; the LLM produces a four-step chain-of-thought action plan. In step 2 (guardrail code generation), the same LLM converts the plan into executable Python code constrained to a user-extensible toolbox of callable functions (e.g., CheckAccess, CheckRules), again guided by retrieved demonstrations; the code is then executed by an external engine to yield the final label and explanation. A debugging loop (up to 3 iterations) invokes the LLM to fix runtime errors, though in most cases the code is directly executable. The key design insight is that code-based guardrails are more reliable than natural-language guardrails because they deterministically encode the safety logic, avoiding the 'autonomy' failures where LLMs loosely interpret rules (e.g., incorrectly granting access to a database a role should not have).

## Results

GuardAgent achieves over 98% label prediction accuracy (LPA) on EICU-AC and over 83% LPA on Mind2Web-SC across four core LLMs (GPT-4, Llama3-70B, Llama3.1-70B, Llama3.3-70B), with explanation accuracy (EA) of 95.7–97.5% on EICU-AC and 68–94% on Mind2Web-SC. Critically, GuardAgent maintains 100% final response accuracy (FRA) in all settings, meaning it introduces zero degradation to the target agent's task performance. On the supplementary CSQA benchmark (Appendix P), GuardAgent with GPT-4 achieves 92.5% overall risk-level recall versus 82.5% for the model-guarding-agent baseline.

## Baselines & Comparisons

GuardAgent consistently outperforms the Model-Guarding-Agent baseline (which uses the same LLMs but relies on natural-language reasoning without code generation) on both LPA and EA across all four LLMs. On EICU-AC, GuardAgent gains 1.3–6.3 percentage points in LPA and 28–55 points in EA over the baseline; on Mind2Web-SC, the LPA gap is 1–12.5 points and the EA gap is 3–29 points. The Hardcoded Safety Rules baseline (safety instructions injected into the target agent's system prompt) achieves moderate LPA but catastrophically low FRA (3.2–71%), meaning it severely degrades the target agent's task performance, whereas GuardAgent maintains 100% FRA due to its non-invasive design. LlamaGuard, a content-moderation model, performs at near-random levels (~50% LPA) on both benchmarks, confirming its inability to handle agent-specific safety guard requests. The paper attributes GuardAgent's advantage over the model-guarding-agent baseline to code-based execution, which eliminates LLM 'autonomy' errors (e.g., incorrectly granting access to a database) and resolves ambiguities like shared column names across databases.

## Relation to Prior Work

This paper departs from the existing LLM guardrail literature (LlamaGuard, NeMo Guardrails, RigorLLM), which is designed to moderate textual harmfulness in LLM inputs/outputs, by reframing the problem for LLM agents that produce diverse action modalities (database queries, web clicks, trajectory predictions) governed by domain-specific safety policies. It builds on EHRAgent's code-execution debugging mechanism and adopts chain-of-thought prompting as the structural template for task planning, but the key conceptual departure is the 'agent guarding agents' paradigm: using an LLM agent with a memory module and extendable toolbox to generate and execute guardrail code, rather than relying on natural-language moderation or hardcoded rules. The paper also positions itself against the 'model guarding agents' approach (prompting an LLM to reason about safety) and shows that code-based guardrails are more reliable for structured access-control and rule-checking tasks.

## Why It Matters / Open Questions

This is the first systematic treatment of safety guardrails for LLM agents, a gap that becomes critical as agents are deployed in high-stakes domains (healthcare, autonomous driving, finance) where hardcoded safety controls cannot generalize across agent types. The two introduced benchmarks (EICU-AC, Mind2Web-SC) provide the first evaluation infrastructure for agent-level access control and safety policy compliance. Open questions include scaling to more complex multi-attribute access policies, automating toolbox construction, and extending to multi-agent guardrail architectures; the current system also relies on relatively simple Levenshtein-based retrieval and a single-agent pipeline, limiting its robustness on broader or more ambiguous guard requests.
