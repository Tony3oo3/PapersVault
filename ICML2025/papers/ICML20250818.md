## Problem

Existing coding agents are designed and evaluated in static environments where the workspace remains fixed, but real-world collaborative software engineering operates in dynamic settings where concurrent updates by other collaborators cause an agent's belief state to diverge from the actual codebase state. No prior framework or benchmark systematically measures how well LLM agents detect, diagnose, and recover from this out-of-sync condition, nor evaluates their collaboration willingness and resource-awareness during recovery.
![Teaser figure](../imgs/ICML20250818/cropped_page0_idx0.webp)

## Input / Output

Each task instance presents an agent with a Docker container containing a Python codebase where a specific function (Caller) or its imported dependency (Callee) has been rolled back to an older Git commit, causing unit tests to fail. The agent operates under explicit resource constraints (30-turn time limit, $1000 budget with $100 per solution-proposal or assistance-seeking action) and can take three action types: environment exploration via OpenHands, solution proposal, or proactive collaborator assistance. Recovery success requires a two-stage validation: the agent's updated code must pass all unit tests (exit code 0) AND produce parsed test outputs that exactly match the ground-truth commit's outputs.

## Method

SyncMind formally defines agent out-of-sync as a belief-state deviation (B_k ≠ S_k) arising from missed updates, and specifies two recovery pathways: independent recovery (environment interaction and solution proposal) and collaborative recovery (seeking LLM-simulated know-everything collaborator assistance). SyncBench constructs 24,332 out-of-sync instances from 21 GitHub Python repositories by tracing Git history backwards to identify commits where execution transitions from pass to fail, then applies multi-level quality filtering and weighted downsampling to yield a 300-instance evaluation set. Evaluation employs five complementary metrics—Success Rate, Localization Accuracy (file and function level), Conditional Success Rate, Assistance Seeking Rate, and Recovery Efficiency (time and expense)—to disentangle technical problem-solving ability from collaboration initiative and resource adaptability. The key finding is that agents with the highest technical CSR scores (e.g., Llama-3.1-70B) still achieve low overall SR due to poor localization and near-zero collaboration willingness (ASR ≤ 4.86% across all agents), while resource constraint variations produce negligible behavioral changes, revealing a fundamental lack of resource awareness in current LLM agents.

## Results

On SyncBench (300 instances from 21 GitHub repos), independent out-of-sync recovery success rates (SR) range from 0.33% (Llama-3.1-8B) to 28.18% (Claude-3.5-Sonnet), with collaborative SR reaching up to 33.70% for Claude-3.5-Sonnet. All agents exhibit extremely low collaboration willingness (Assistance Seeking Rate ≤ 4.86%), yet collaborator assistance consistently improves SR by 0.33–5.52 percentage points. Localization accuracy (LA_func) spans 4.67%–56.35% independently, and conditional success rates (CSR) reveal that even agents with strong technical repair ability (e.g., Llama-3.1-70B with CSR_func = 53.40%) fail to recover due to poor localization and minimal collaboration initiative.

## Baselines & Comparisons

Claude-3.5-Sonnet dominates all other agents on every metric, achieving 28.18% independent SR and 33.70% collaborative SR, outperforming the second-best Llama-3.3-70B (16.33%/19.00%) by over 12 percentage points in SR. GPT-4o benefits most from collaboration (Δ_collaborator SR = +4.00%, with LA_func jumping from 9.33% to 34.67%), suggesting its strong technical capacity is unlocked by proactive assistance-seeking. DeepSeek-V2.5 achieves the highest independent localization (LA_file = 47.67%) but the smallest collaboration gain (Δ_collaborator SR = +0.34%), reflecting its very low ASR of 1.21%. Llama-3.1-8B and Llama-3.1-70B trail all other agents on SR (≤ 3.33%) despite Llama-3.1-70B showing competitive conditional technical ability (CSR_func = 53.40%), confirming that localization failure and collaboration reluctance—not repair skill—are the primary bottlenecks. The oracle single-turn experiment (GPT-4o mini agent + GPT-4o collaborator with full instructions) reaches 86.33% SR, revealing a massive untapped collaboration potential across all evaluated agents.

## Relation to Prior Work

This paper carves new ground by formally defining the 'out-of-sync' problem in collaborative software engineering—a setting where a collaborator's belief state diverges from the actual codebase state due to concurrent updates by others. Prior coding-agent benchmarks (SWE-bench, R2E) and agent frameworks (OpenHands, Devin) evaluate agents in static environments where the workspace is fixed, while version control systems detect only syntactic conflicts rather than semantic inconsistencies. The theoretical framing draws on Theory of Mind research (modeling others' mental states) but applies it specifically to codebase-state synchronization, a connection not previously made in the SE-agent literature. The benchmark construction pipeline repurposes Git commit history traversal and Docker-based test execution, but the multi-level filtering for pass-to-fail divergence and the weighted downsampling strategy are novel contributions to benchmark design for collaborative scenarios.

## Why It Matters / Open Questions

The findings that LLM agents exhibit near-zero collaboration willingness (ASR ≤ 4.86%) and essentially no resource awareness (tripling budget shifts ASR by <1%) challenge the assumption that current agents can be dropped into dynamic collaborative workflows without fundamental redesign. The 86.33% oracle upper bound versus ≤33.70% actual performance reveals a massive untapped potential that could be unlocked through better communication protocols and resource-adaptive strategies. Key limitations include Python-only scope, single-collaborator simulation, and simplified resource modeling, leaving open questions about multi-agent out-of-sync cascades, real-time (non-historical) collaboration, and whether specialized training can close the collaboration-willingness gap. For practitioners building collaborative AI systems, the paper provides the first systematic evidence that technical coding ability alone is insufficient—localization, communication quality, and resource allocation are equally critical.
