## Problem

Prompt caching in LLM APIs introduces data-dependent timing variations that create side-channel vulnerabilities: if caches are shared across users, an attacker can infer other users' prompts from fast response times, and prefix caching can reveal model architecture details. However, there was no systematic, statistically rigorous method to audit whether real-world API providers actually cache prompts or to determine the precise level of cache sharing (per-user, per-organization, or global).

## Input / Output

The audit sends prompts consisting of PROMPTLENGTH (5000) random English letters separated by spaces—ensuring exactly PROMPTLENGTH tokens under any BPE tokenizer—to live LLM API endpoints, measuring time-to-first-token (TTFT) via client-side or server-side timing with max_tokens=1. It produces a one-sided p-value from a two-sample KS test, a determination of the highest cache-sharing level at which caching is detected, precision-recall curves for distinguishing cache hits from misses, and (for embedding models) evidence about decoder-only vs. encoder architecture. The audit is structured as four sequential levels of increasing cache sharing, where each level is only tested if the previous level detected caching.

## Method

The audit formulates caching detection as a statistical hypothesis test: H0 (no caching) implies the cache-hit and cache-miss timing distributions are identical, while H1 (caching) implies cache hits are faster. The cache-hit procedure has a victim user send a random prompt NUMVICTIMREQUESTS times to populate the cache, then an attacker user sends a prompt sharing a prefix of PREFIXFRACTION × PROMPTLENGTH tokens; the cache-miss procedure simply sends a fresh random prompt. A one-sided two-sample Kolmogorov-Smirnov test over NUMSAMPLES=250 randomized timing samples yields a valid p-value with controlled false-positive rate. To handle multiple testing across NUMVICTIMREQUESTS values and timing sources, Bonferroni corrections are applied. The four-level escalation (same-prompt per-user → prefix per-user → prefix per-org → prefix global) precisely localizes the cache-sharing boundary, and the PREFIXFRACTION < 1 setting specifically tests for prefix caching, which is only possible in decoder-only Transformers, thereby leaking architecture information.

## Results

The audit detected prompt caching in 8 out of 17 real-world LLM API providers, with global cache sharing (the highest-risk level) found in 7 providers including OpenAI, Azure, Fireworks, Deep Infra, Lepton, Perplexity, and Replicate. Average precision for distinguishing cache hits from cache misses ranges from 0.70 to 1.00, with most APIs clustering around 0.8, indicating that an attacker can reliably identify cached prompts from timing data. P-values for detected caching are often many orders of magnitude below the significance threshold of α = 10⁻⁸ (e.g., 10⁻¹⁵⁰ for Replicate), providing strong statistical evidence. Additionally, the audit revealed that OpenAI's text-embedding-3-small model uses a decoder-only Transformer architecture, which was previously undisclosed.

## Baselines & Comparisons

This is an empirical audit paper rather than a method comparison, so there are no traditional baselines. The key cross-provider comparison reveals a clear split: 7 providers (Azure, Deep Infra, Fireworks, Lepton, OpenAI embedding, Perplexity, Replicate) exhibit global cache sharing, while 2 providers (Anthropic Claude 3 Haiku, OpenAI GPT-4o mini) limit sharing to the per-organization level, consistent with their published documentation. The remaining 9 providers (Amazon, Cohere, DeepSeek, Google, Groq, Hyperbolic, Mistral, OctoAI, Together) showed no detectable caching. Detection precision varies by provider and timing source: Replicate achieves perfect 1.00 server-side precision, Perplexity reaches 0.90 client-side, while Lepton is the weakest at 0.70–0.71. The statistical test (one-sided KS test) rejects the null hypothesis of no caching with overwhelming significance in all 8 detected cases, with p-values ranging from 10⁻⁹ to 10⁻¹⁵⁰, far below the Bonferroni-corrected threshold.

## Relation to Prior Work

This paper builds on the well-studied tradition of cache timing attacks in computer security (Meltdown, Spectre, AES key extraction) and applies that conceptual framework to LLM API serving. The most directly related prior work—Song et al. (2024) and Zheng et al. (2024b)—studied prompt-caching timing side channels, but exclusively in simulated, controlled environments with local execution and explicit cache clearing. This paper departs by formulating the problem as a real-world statistical audit with valid p-values, multi-level cache-sharing detection (per-user, per-organization, global), and no assumptions about the provider's internal caching implementation. It also extends the scope beyond privacy to intellectual property leakage via model architecture inference, a dimension absent from prior timing-attack-on-LLMs work.

## Why It Matters / Open Questions

The practical impact is immediate: 7 of 17 major LLM API providers were found to share caches globally, meaning any user could in principle detect whether another user recently sent a prompt sharing a prefix. The responsible disclosure led at least five providers to patch vulnerabilities, demonstrating real-world security relevance. Open questions include whether prompt extraction attacks (token-by-token reconstruction of other users' prompts) are feasible in practice—the authors found them impractical with current techniques but did not rule them out—and whether the statistical audit methodology generalizes to other types of caching (semantic caching, approximate prefix matching). The architecture leakage finding (OpenAI's embedding model is decoder-only) raises the broader question of how much proprietary information can be extracted from API timing behavior.
