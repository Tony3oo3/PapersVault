## Problem

LLM serving workloads are increasingly heterogeneous in input/output token lengths, creating divergent compute (prefill) and memory (decode) demands that homogeneous GPU clusters cannot match efficiently. Existing heterogeneous serving systems (HexGen, Helix, M'elange) optimize within a predefined cluster but ignore real-time cloud GPU availability and user-defined price budgets, leaving a gap in how to jointly decide which GPUs to rent, how to configure them, and how to route workloads under practical cloud constraints.

## Input / Output

The method takes as input a set of LLM models to serve (e.g., Llama3-8B, Llama3-70B), a heterogeneous workload trace specifying per-type request counts and input/output token lengths, a user-defined hourly price budget, and a vector of real-time GPU availability per type from a cloud provider. It produces a complete serving plan: (1) a GPU composition vector specifying how many of each GPU type to rent, (2) per-replica deployment configurations encoding DP/TP/PP degrees, and (3) a fractional workload assignment matrix routing each workload type to activated replicas. The plan is validated by a one-time profiling step that estimates per-configuration throughput from prefill/decode layer latencies and inter-GPU communication costs.

## Method

The core contribution is a mixed-integer linear program (MILP) that jointly optimizes three coupled decisions—GPU composition, deployment configuration, and workload assignment—to minimize the overall makespan under budget, GPU-availability, memory, and connectivity constraints. Each feasible configuration is characterized by a GPU-type vector, a parallelism strategy (pipeline stages with per-stage TP degrees), a cost, and a throughput profile per workload type obtained via one-time profiling. The MILP uses integer activation variables y_c (number of replicas per configuration) and continuous fractional assignment variables x_{c,w} ∈ [0,1], with an activation-coupling constraint linking them. For scalability, the authors replace direct minimization of T with a binary-search-on-T procedure that performs feasibility checks (accelerated by knapsack approximation), achieving ~4× speedup with <1% performance loss. Additional heuristics restrict TP to intra-machine links, allow non-uniform PP layer partitioning based on memory allocation, and prune dominated configurations; the formulation extends to multi-model serving by adding a model-type dimension to all variables and constraints.

## Results

Across diverse workload traces, GPU availabilities, and price budgets ($15–$60/h), the proposed scheduling algorithm improves system throughput by up to 41% (25% on average) and reduces percentile latencies by up to 54% (20% on average) over the best homogeneous baseline. In the multi-model serving scenario (Llama3-8B + Llama3-70B), the method achieves up to 35% (average 23%) throughput gain. The binary-search acceleration reduces MILP solving time by approximately 4× with less than 1% performance deviation.

## Baselines & Comparisons

Against HexGen (ICML 2024), the proposed method wins in both tested setups: HexGen with a uniform GPU composition suffers up to 35% (average 29%) throughput degradation, and even when HexGen is given the optimal GPU composition, the proposed method still outperforms it by up to 18% (average 14%) due to workload-aware scheduling. Against Helix (arXiv 2024), the proposed method achieves 35% higher throughput on Llama-30B (11.43 vs. 8.49 req/s) and 25% higher on Llama3-70B (7.13 vs. 5.72 req/s) under a $15/h budget on Azure-Trace. Against homogeneous baselines (H100, A6000, RTX 4090), the method delivers up to 41% throughput improvement and up to 54% latency reduction, with the best homogeneous baseline varying by trace (H100 for compute-heavy traces, A6000 for memory-heavy traces, 4090 for Llama3-8B). Ablation confirms all three optimization targets (GPU composition, deployment configuration, workload assignment) contribute meaningfully, with removing any single one causing 20–34% throughput loss.

## Relation to Prior Work

This paper extends the heterogeneous LLM serving line (HexGen, Helix, M'elange) by adding a cloud resource-scheduling dimension: rather than optimizing within a fixed heterogeneous cluster, it jointly decides which GPUs to rent (GPU composition), how to configure each replica (deployment), and how to route workloads (assignment) under real-time availability and budget constraints. It builds on Vidur's one-time profiling methodology to obtain per-configuration throughput values that feed the MILP, and on vLLM as the serving engine. The key conceptual departure from prior work is treating GPU composition as a decision variable rather than a given, and explicitly modeling workload heterogeneity (varying input/output token lengths) in the assignment objective.

## Why It Matters / Open Questions

As LLM serving costs become a primary barrier to democratizing AI access, the finding that matching GPU types to workload characteristics (e.g., workstation GPUs for memory-intensive decoding, data-center GPUs for compute-intensive prefill) can yield up to 2.27× cost-efficiency gains is practically significant for cloud operators and cost-sensitive deployments. However, the approach assumes a quasi-static workload distribution and offline planning; the online replanning mechanism is only sketched (Appendix M) and not rigorously evaluated under truly dynamic, non-stationary traffic. Open questions include how the MILP scales to dozens of model types with hundreds of GPUs in production, whether the one-time profiling generalizes across model updates, and how multi-tenant fairness interacts with the cost-optimization objective.
