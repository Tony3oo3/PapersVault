## Problem

LLMs trained on static pre-training data generate code using outdated API signatures, leading to runtime errors when third-party libraries update their interfaces. Prior benchmarks for API-update knowledge rely on synthetic updates generated by GPT-4 rather than authentic library changes, leaving it unclear whether LLMs can truly synchronize with real-world code evolution. This paper asks whether existing knowledge-updating methods (SFT, DPO, ORPO, SimPO) can effectively and efficiently inject real-time API knowledge without degrading general model utility.

## Input / Output

The pipeline ingests legacy and current versions of six Python libraries (pandas, numpy, scipy, tensorflow, torch, flask), extracts API signature changes via Python's inspect module, retrieves real-world invocation snippets from GitHub Code Search, and validates them through AST parsing with alias resolution. The output is CODESYNCBENCH: 3,300 legacy-updated invocation pairs across 220 APIs (130 functions, 59 initializers, 31 methods), split into 1,100 test cases per task (CCT, ECT, MCQ) and a 2,200-sample update-aware instruction tuning set where each sample is a triple (instruction, legacy_output, updated_output) enabling token-level contrastive learning.

## Method

CODESYNC is a three-stage data engine: (1) Real-Time API Update Tracking uses Python's inspect module in versioned virtual environments to extract signatures and performs static parameter-level diffing (name, position, type, required/optional) to identify 6,063 updates; (2) Real-World API Invocation Retrieval designs multi-template GitHub Code Search queries accounting for import aliases, then parses results into ASTs to locate and validate genuine invocations (filtering to 220 APIs with ≥15 valid instances each); (3) Legacy-Updated API Invocation Synthesis prompts DeepSeek-V3 to rewrite each retrieved invocation against both legacy and updated signatures while preserving surrounding context, with manual verification of divergence. For evaluation, the benchmark defines three tasks—Code Completion (complete parameter list), Error Correction (fix a legacy invocation), and Multiple Choice (select correct invocation among four options with LLM-synthesized distractors)—and benchmarks 14 LLMs plus five updating methods (SFT-LoRA, DPO, ORPO, SimPO) on both CODESYNCBENCH and HumanEval to measure utility preservation.

## Results

On CODESYNCBENCH, all 9 evaluated LLMs struggle with API update tasks: GPT-4o achieves only 14.93 BLEU on Code Completion (CCT) and 38.98 Pass@3 on MCQ, while Claude-3.5-Sonnet reaches 19.29 BLEU (CCT) and 36.08 Pass@3 (MCQ). After applying knowledge updating methods (DPO, ORPO, SimPO) to 5 open-source 7B models, CCT BLEU improves from ~6–8 (original) to ~24–28, yet remains far below the upper bound of ~42–45 (Table 5). On HumanEval, most updating methods preserve >94% of original Pass@1 performance, with SimPO maintaining 100% for Llama-3.1-8B and Qwen2.5-Coder-7B.

## Baselines & Comparisons

Among the 9 LLMs benchmarked in Table 3, no model exceeds 20 BLEU on CCT or 40 Pass@3 on MCQ, confirming systemic knowledge obsolescence regardless of model scale or recency. In the knowledge updating comparison (Table 4), DPO, ORPO, and SimPO consistently outperform SFT-LoRA on CCT BLEU by roughly 12–15 points (e.g., Qwen2.5-7B: DPO 24.45 vs. SFT-LoRA 12.17; CodeLlama-7B: SimPO 27.78 vs. SFT-LoRA 17.24), while SFT-LoRA is the most training-efficient. The RAG baseline (Table 6) achieves 35.17 CodeBLEU on CCT for Qwen2.5-Coder-7B, outperforming SFT (31.17) but falling short of DPO (38.67), with a 60% retrieval hit rate limiting its effectiveness. On HumanEval, all preference-optimization methods (DPO, ORPO, SimPO) incur ≤10% Pass@1 degradation, whereas SFT-LoRA causes slightly larger drops (e.g., 96.26% ratio for Qwen2.5-7B). A notable anomaly: DeepSeek-Coder-6.7B-Instruct suffers severe MCQ score collapse after fine-tuning (Pass@1 drops from 31.25 to 6–7), attributed to degraded instruction-following rather than knowledge failure.

## Relation to Prior Work

This paper extends the software engineering tradition of tracking API evolution (Tao et al., 2012; Zhang et al., 2020) into the LLM evaluation domain, departing from the closest prior work CodeUpdateArena (Liu et al., 2024c), which relied on GPT-4-synthesized API updates rather than authentic library releases. The data pipeline repurposes existing tools—Python's inspect module for signature extraction, GitHub Code Search for real-world invocation retrieval, and AST parsing for validation—into a unified pipeline that had not previously been assembled for LLM benchmarking. On the updating side, the paper applies well-established preference optimization methods (DPO, ORPO, SimPO) and SFT-LoRA to a new domain (code API synchronization) without modifying the methods themselves, positioning the contribution as a rigorous empirical study rather than a methodological advance.

## Why It Matters / Open Questions

The benchmark exposes a practical gap that directly affects AI coding assistants (Copilot, Cursor): even models with recent knowledge cutoffs (DeepSeek-R1, Jul 2024) produce non-executable code when APIs have changed, and the finding that preference optimization methods yield only marginal absolute improvements (BLEU ~25–28% on CCT) is a sobering negative result for the knowledge-updating community. Open questions include how to scale beyond 6 Python libraries and 220 APIs, how to handle the significantly harder method-API category, and whether structural code understanding or continual learning paradigms can close the gap that fine-tuning leaves. The limited scope (single language, single ecosystem) and the 60% RAG hit rate suggest the problem is substantially harder than current methods assume.
