## Problem

Large-scale 3D parallel training of vision-language models suffers from severe computational imbalance across devices because the vision encoder and language model are structurally heterogeneous and their inputs (variable image counts, resolutions, and text lengths) cannot be trivially fixed as in LLM pretraining. This imbalance manifests as uneven forward times across pipeline stages and data-parallel replicas, excessive padding, and the need for overly aggressive activation checkpointing, collectively wasting GPU resources and slowing training by up to 1.8×.

## Input / Output

The method consumes VLM instruction-tuning samples (each containing a variable number of images at up to 3840×2160 resolution and variable-length text), a heterogeneous VLM (e.g., InternViT-6B + InternLM2-20B/34B), and a hardware configuration (TP/PP/DP sizes, GPU type). It produces three artifacts: balanced dynamic mini-batches with near-zero padding and low cross-device distribution ratio, an optimal pipeline partition strategy (which layers go to which stage), and a per-stage adaptive re-computation schedule. The final output is a trained VLM achieving comparable benchmark scores (MMBench, ChartQA, AI2D, MMVet, MME) in roughly half the GPU days.

## Method

OmniBal is a three-layer framework where each layer builds on the previous one. First, an Iterative Sampling and Filtering (ISF) algorithm groups variable-size samples into mini-batches whose total image count and text token length stay within tight bounds (Q_v, Q_t), simultaneously minimizing within-batch padding and cross-device input variance. Second, a search-based Balanced Model Partitioning (BMP) profiles per-layer forward times, constructs a greedy anchor partition, jitters it within a small radius to generate candidates, and ranks them by forward-time variance and point-to-point communication volume to select the optimal pipeline split. Third, with inputs and partitions now stable, a Balanced Adaptive Re-Computation step measures actual remaining GPU memory per stage and disables checkpointing on layers where memory permits, replacing the globally most-aggressive strategy with a per-stage optimal one. The three components are tightly coupled: data balance fixes input sizes so model partitioning can be deterministic, and both together stabilize memory so adaptive checkpointing becomes feasible.

## Results

On InternVL-Chat-1.5 (6+20B) with the Megatron-DeepSpeed backend, OmniBal reduces training time from 61.8 to 21.3 GPU days (1.83× speed-up) while maintaining comparable benchmark performance (e.g., MMB-EN 79.5→78.6, ChartQA 87.3→86.7, MME 1957.7→1956.3). Scaling to the larger 6+34B model, GPU days drop from 75.4 to 30.5 (1.80× speed-up). Under the DeepSpeed ZeRO-3 backend, speed-ups of 1.54× (6+20B) and 1.53× (6+34B) are achieved. Across all configurations, OmniBal outperforms the unbalanced 3D-parallel baseline and even surpasses the DeepSpeed-only baseline, demonstrating that balanced computation is essential for effective large-scale VLM training.

## Baselines & Comparisons

The primary baseline is the open-source InternVL-Chat training code (Chen et al., 2024), which uses standard 3D parallelism without computation balancing. Under the Megatron-DeepSpeed backend, the unbalanced baseline actually *slows down* training relative to DeepSpeed alone (61.8 vs. 38.9 GPU days for 6+20B), because the heterogeneous VIT/LLM architecture creates severe pipeline bubbles. OmniBal reverses this, achieving 21.3 GPU days — a 1.83× speed-up over the unbalanced Megatron baseline and even 1.83× faster than the DeepSpeed-only baseline. For the 6+34B model, the same pattern holds: 30.5 vs. 75.4 (unbalanced Megatron) and 35.5 (DeepSpeed). The second comparison is against PipeDream-style profile-based partitioning (Narayanan et al., 2019), which in Table 4 achieves VAR(fwd_time)=6.5 but incurs +16.6 MB extra communication overhead, yielding 30.9 GPU days. OmniBal's search-based Balanced Model Partitioning (BMP) achieves 29.0 GPU days with −21.0 MB less communication, demonstrating that jointly optimizing partition and communication volume outperforms pure profiling-based approaches.

## Relation to Prior Work

This paper extends the pipeline-parallelism optimization line (PipeDream, AdaPipe) from homogeneous LLMs to heterogeneous vision-language models, where the structural and computational disparity between ViT and LLM components invalidates standard equal-layer or parameter-based partitioning. It builds on the 3D-parallelism infrastructure of Megatron-DeepSpeed and DeepSpeed-ZeRO, and adapts the activation-checkpointing technique from Li et al. (2014) into an adaptive, per-stage strategy. The key departure is identifying that the multi-modal data's variable input sizes (images + text) compound the model heterogeneity to create a 'computation imbalance' problem that prior LLM-focused partitioning and re-computation methods do not address.

## Why It Matters / Open Questions

The finding that naively applying 3D parallelism to VLMs actually *increases* training time (61.8 vs. 38.9 GPU days) challenges the default assumption that more parallelism is always faster, and the systematic three-pronged fix (data, model, memory balance) recovers and surpasses the data-parallel baseline by ~1.8×. The method generalizes across model scales (8B–110B), datasets, hardware (A100/H100), and even pre-training tasks, making it broadly applicable to the growing VLM ecosystem. Open questions include whether the search-based partitioning scales gracefully to very large pipeline-parallelism sizes (N > 16) and whether the approach extends to even more heterogeneous architectures (video, audio, 3D) where input variability is greater.
