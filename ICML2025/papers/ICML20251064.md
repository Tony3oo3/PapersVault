## Problem

Prior attacks on LLM-based code completion engines required white-box access to model weights or training data, making them infeasible against deployed commercial services like GitHub Copilot. This paper asks whether an attacker with only black-box access—i.e., the ability to manipulate the engine's input—can stealthily bias a code completion engine to generate insecure code at a significantly higher rate while preserving functional correctness and response speed.

## Input / Output

The method takes a standard code completion query (prefix + suffix) and a pre-computed, fixed attack string σ of 5–15 tokens. At inference time, σ is indiscriminately inserted as a short comment on the line above the completion position in the prefix, producing an adversarial query that is forwarded to the black-box engine. The output is the engine's code completion, which is steered toward vulnerable implementations. Because σ is fixed and inserted into every query, the deployment adds negligible latency and requires no per-query computation.

## Method

INSEC combines three components: an attack template, a random optimization algorithm, and diverse initialization strategies. The template inserts a short adversarial comment string σ above the completion line, exploiting LLMs' instruction-following to steer toward vulnerable code while the comment format minimizes disruption to functional correctness. The optimization (Algorithm 1) iteratively mutates candidate strings by replacing random tokens with vocabulary samples and selects the top-n by vulnerability rate on a small training set, using a proxy tokenizer (CodeQwen) since the attacker has no access to the target model's tokenizer. Six initialization strategies—random, TODO, security-critical token, sanitizer, and inversion—seed the candidate pool, with security-critical token initialization (extracting tokens that distinguish secure from vulnerable completions) proving most effective. The resulting attack string is fixed at inference time, requiring less than $10 in API costs to develop and increasing the vulnerability rate by over 50% across 16 CWEs in 5 languages while maintaining near-original functional correctness.

## Results

INSEC increases the vulnerability rate of generated code by an absolute ~50% (up to 60%) across all tested engines while maintaining less than 22% relative decrease in functional correctness. On GPT-3.5-Turbo-Instruct, the vulnerability rate rises from 22% to 73%, and on StarCoder-3B and CodeLlama-7B it reaches 80% and 82% respectively. GPT-3.5-Turbo-Instruct and GitHub Copilot are attacked with virtually no impact on functional correctness. The total development cost is under $10 (e.g., $5.80 for GPT-3.5-Turbo-Instruct), and the attack generalizes across models: a string optimized for StarCoder-3B raises GPT-3.5-Turbo-Instruct's vulRate from 22% to 55%.

## Baselines & Comparisons

This is an attack paper, so the primary comparison is between the unattacked (baseline) engine and the INSEC-attacked engine, rather than against competing attack methods. INSEC consistently increases vulRate by ~50% absolute across all six tested engines (StarCoder-3B, CodeLlama-7B, StarCoder2-3B/7B/15B, GPT-3.5-Turbo-Instruct, and GitHub Copilot), with the strongest absolute gains on GPT-3.5-Turbo-Instruct (22%→73%) and CodeLlama-7B (~32%→82%). In terms of stealth, GPT-3.5-Turbo-Instruct and GitHub Copilot suffer virtually no functional correctness loss, while smaller open-source models (StarCoder-3B, StarCoder2-3B) lose up to ~22% relative passRatio@1. The attack also generalizes across architectures: a string optimized for StarCoder-3B transfers to GPT-3.5-Turbo-Instruct (22%→55%) and to CodeLlama-7B (22%→59%), though at lower effectiveness than model-specific optimization (73% and 82% respectively). For multi-CWE attacks, concatenating individually optimized strings for up to 16 CWEs simultaneously still achieves nearly 2× the baseline vulRate on GPT-3.5-Turbo-Instruct, demonstrating composability without explicit multi-target design.

## Relation to Prior Work

This paper adapts the random optimization paradigm from jailbreak attacks on LLMs (Zou et al., 2023) to the code completion domain, but under a fundamentally different threat model: instead of per-prompt, user-visible jailbreak strings, INSEC derives a single fixed, short (5–10 token) adversarial comment that is stealthily injected into all queries. It builds on He & Vechev's (2023) vulRate metric and their observation that secure and vulnerable completions differ only in a few critical tokens, which directly informs the security-critical token initialization strategy. The key departure from prior code-completion attacks (Schuster et al., 2021; Aghakhani et al., 2024; Yan et al., 2024) is the shift from white-box model poisoning to black-box input manipulation, making the attack feasible against deployed commercial services like GitHub Copilot and the OpenAI API.

## Why It Matters / Open Questions

The finding that a sub-$10, 5-token attack string can increase insecure code generation by over 50% on production services used by millions of developers has immediate practical security implications, and the demonstrated IDE-plugin deployment vector makes the threat concrete. A counterintuitive result is that more capable models (GPT-3.5-Turbo-Instruct, GitHub Copilot) suffer virtually no functional-correctness loss under attack, suggesting that future, stronger models may be *more* susceptible to this class of stealthy perturbation rather than less. Open questions include whether effective defenses exist without degrading completion utility (the paper shows comment scrubbing and perplexity filters are impractical), whether the attack extends to coding agents and novel undetectable vulnerabilities, and how to reconcile the tension between instruction-following capability and adversarial robustness in code LLMs.
