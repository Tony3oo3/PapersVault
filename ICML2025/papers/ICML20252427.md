## Problem

Repository-level coding benchmarks like SWE-Bench require substantial manual effort to construct historically accurate execution environments for each repository, limiting them to just 12 popular Python repositories. This small, popularity-biased selection creates distributional mismatch with real-world codebases, increases overfitting and training-data contamination risk, and prevents frequent updates. The paper asks whether the entire environment-setup pipeline—dependency installation, test execution, and result parsing—can be fully automated to enable large, diverse, and updatable benchmarks.

## Input / Output

SETUPAGENT consumes a GitHub repository at a specific historical commit along with its README, CI/CD configuration files, and referenced web pages, and produces a validated pair of bash installation and testing commands plus test-level pass/fail results. A key constraint is historical accuracy: the uv package manager is configured to exclude dependency versions released after the issue creation date, ensuring the environment faithfully reproduces the original bug. The final output is a SWE-Bench-compatible dataset instance (code patch, test patch, reference test behaviors) packaged with a pre-built Docker image, with a hard acceptance threshold of ≥95% of tests passing in the unpatched codebase.

## Method

SETUPAGENT operates in three LLM-driven phases. In Extraction, it identifies the correct Python version from setup.py/pyproject.toml or LLM-parsed constraints, heuristically selects relevant context files (README, CONTRIBUTING, CI/CD configs, linked web pages), and prompts an LLM to propose initial installation and testing commands under the uv historical-version constraint. In Iterative Improvement (up to 4 rounds), it executes the commands in a clean Ubuntu 22.04 Docker container, feeds error messages back to an LLM that classifies the failure cause (Python version, installation, testing, or undecidable) and proposes corrected commands, distinguishing between missing dependencies, wrong test flags, and actual codebase bugs. In Validation, an LLM judges overall setup success, the test framework is reconfigured for test-level granularity (e.g., pytest -rA), a pre-defined parser extracts per-test results, and the configuration is accepted only if ≥95% of tests pass. Validated commands are cached in a reference database so that subsequent versions of the same repository install faster, and the entire pipeline runs in ~30 s per repository on average, making it 60× faster than the concurrent ExecutionAgent.

## Results

SETUPAGENT achieves historically accurate environment setup for 21.6–28.6% of repositories and 58.5–71.5% of individual instances, taking ~30s per repository on average. On the generated benchmarks, AutoCodeRover v2 with GPT-4O-MINI achieves the highest resolution rate at 8.4% (SWA), 9.0% (SWEE), and 8.2% (SWE), showing surprisingly small cross-benchmark differences. However, with stronger models like GPT-4O and DeepSeek V3, performance on SWE-Bench inflates substantially (16.6% and 26% respectively) compared to SWA (10.2% and 8%), revealing up to 60% lower success rates on the more representative benchmarks. Correlation analysis confirms that fix complexity (lines/files modified) has a strong negative correlation with agent success (ρ = −0.28 to −0.40, p < 10⁻⁹), while issue-to-fix overlap has a strong positive correlation (ρ = 0.12–0.19, p < 10⁻³).

## Baselines & Comparisons

All five baselines are evaluated on the three benchmarks (SWA, SWEE, SWE) with GPT-4O-MINI. AutoCodeRover v2 is the strongest agent across all three benchmarks (8.4–9.0%), outperforming OpenHands (3.9–4.6%) by roughly 2× and SWE-Agent v1 (2.6–7.5%) by a wide margin, though SWE-Agent performs significantly worse on SWA (2.6%) than on SWEE/SWE (~7%). The ZeroShot baselines (Oracle: 0.9–2.8%, BM25: 1.3–2.8%) are consistently the weakest, confirming that agentic tool use is essential. The critical finding is that with GPT-4O-MINI, cross-benchmark differences are small, but when swapping to GPT-4O or DeepSeek V3, SWE-Bench accuracy inflates dramatically (GPT-4O: 16.6% SWE vs. 10.2% SWA; DeepSeek V3: 26% SWE vs. 8% SWA), indicating that SWE-Bench's popular, older repositories are contaminated in training data while the more diverse SWEE-Bench is not. This suggests that SWE-Bench overestimates real-world agent capability by up to 60% for certain models.

## Relation to Prior Work

This paper builds directly on SWE-Bench (Jimenez et al., 2024), which established repository-level code generation as a benchmark task but required manual environment setup, limiting it to 12 popular repositories. It departs from R2E (Jain et al., 2024b), which automated setup but aggressively filtered out complex installations, and from the concurrent ExecutionAgent (Bouzenia & Pradel, 2024), which was 60× slower and lacked historical accuracy. The key conceptual contribution is SETUPAGENT, which automates the full pipeline of historically accurate dependency resolution, iterative error diagnosis, and test-level result parsing, enabling scalable and updatable benchmark creation without manual labor.

## Why It Matters / Open Questions

The paper demonstrates that SWE-Bench's focus on popular, well-documented libraries creates a distributional mismatch with real-world coding tasks, with agent success rates dropping by up to 60% on more representative benchmarks. The statistically significant contamination signal (GPT-4o performing worse on post-knowledge-cutoff SWA instances) underscores the urgency of frequently updated, diverse benchmarks. Limitations include Python-only support, no Docker-in-Docker capability, and a 20–30% repository-level success rate for SETUPAGENT without reference commands, leaving open questions about generalization to other languages and more complex build systems.
