## Problem

Existing type inference benchmarks for Python rely on exact matching, which fails to capture semantic relationships between types (e.g., List vs. Sequence), and evaluate predictions in isolation on individual functions or files rather than assessing type consistency across entire codebases. This makes it difficult to determine whether LLM-predicted types are actually usable in practice, where both local accuracy and global coherence matter.
![Teaser figure](../imgs/ICML20250544/cropped_page1_idx0.webp)

## Input / Output

The benchmark provides 50 curated Python repositories (split into 20/10/20 train/validation/test) with all type annotations stripped via AST parsing, yielding untyped .py source files as input. LLMs are prompted to generate the corresponding .pyi stub file for each source file (file-by-file mode) or for the entire repository (full-repo mode for repos under 64k tokens). Evaluation produces two scores per repository: TYPE SIM (a continuous 0–1 semantic similarity between predicted and ground-truth types) and TYPE CHECK (the count of mypy consistency errors, where lower is better).

## Method

The core contribution is a two-metric evaluation framework. TYPE SIM computes a continuous similarity score by: (1) using a Jaccard index over the set of supported methods/operations for base types (excluding object-level methods), (2) recursively averaging root-type similarity with argument similarity for generic types (e.g., List[int] vs. Sequence[float] scores 0.65), and (3) finding an optimal bipartite matching between members for Union types. TYPE CHECK runs mypy on the predicted stub files integrated into the full codebase and counts specific error categories (attr-defined, assignment, arg-type, union-attr, index) as a proxy for repository-wide type coherence. The dataset curation selects repositories by a weighted quality score combining type coverage, popularity (GitHub stars + PyPI downloads), and annotation complexity, then removes types while preserving all other code structure. LLMs are evaluated via a prompt that provides the untyped file plus a .pyi example and requires syntactically valid stub output.

## Results

On TYPYBENCH (50 Python repositories), SOTA LLMs achieve TYPE SIM scores of 0.78–0.80, with GPT-4O leading at 0.804 and DEEPSEEK-V3 close behind at 0.795. However, TYPE CHECK (mypy error count, lower is better) reveals a stark consistency gap: CLAUDE-3.5-SONNET achieves the best score of 127.1 errors (vs. 141.8 for ground truth), while GPT-4O produces 366.0 errors and GPT-4O-MINI 310.6. Small local models (LLAMA-3-8B, LLAMA-3.1-8B, QWEN-2.5-7B) perform substantially worse, with TYPE SIM below 0.61 and TYPE CHECK errors exceeding 400. The missing rate for SOTA models ranges from 9.9% (GPT-4O) to 16.9% (DEEPSEEK-V2.5), indicating non-trivial failure to produce valid stub files.

## Baselines & Comparisons

The paper evaluates nine LLMs on TYPYBENCH, revealing a clear separation between API-based SOTA models and local-hosted small models. Among SOTA models, GPT-4O achieves the highest TYPE SIM (0.804) but the worst TYPE CHECK (366.0) among the top tier, while CLAUDE-3.5-SONNET achieves the best TYPE CHECK (127.1, even beating the ground truth of 141.8) despite a slightly lower TYPE SIM (0.788). DEEPSEEK-V3 strikes a balance with strong TYPE SIM (0.795) and moderate TYPE CHECK (214.6), and GROK-2 is competitive on both (0.787 / 190.1). GPT-4O-MINI underperforms GPT-4O on TYPE CHECK (310.6 vs. 366.0) while matching its TYPE SIM w/o missing (0.893). Small local models (LLAMA-3-8B, LLAMA-3.1-8B, QWEN-2.5-7B) are far behind, with TYPE SIM below 0.61 and TYPE CHECK errors 2–4× higher than SOTA models, and LLAMA-3-8B has a 50.8% missing rate. The key finding is that TYPE SIM and TYPE CHECK are largely decoupled: the model with the best similarity (GPT-4O) has the worst consistency, while the model with the best consistency (CLAUDE-3.5-SONNET) is mid-pack on similarity.

## Relation to Prior Work

This paper positions itself at the intersection of two research threads: (1) the long line of type inference methods from static analysis (Mypy, Pyright) through learning-based approaches (JSNice, Typilus, TypeT5) to recent LLM-based methods, and (2) the emerging trend of repository-level code benchmarks (RepoBench, SWE-bench, RepoTransBench). It departs from prior type inference benchmarks (Typilus, ManyTypes4Py, TypeEvalPy) by replacing exact-match and parametric-type metrics with two complementary measures—TYPE SIM (a Jaccard-based semantic similarity over type attributes) and TYPE CHECK (mypy error count as a proxy for cross-file consistency)—and by evaluating entire repositories rather than isolated functions. The benchmark construction (50 curated repos with type annotations stripped) follows the standard input/ground-truth paradigm but adds the repository-level scope that prior benchmarks lacked.

## Why It Matters / Open Questions

The central practical finding—that SOTA LLMs reach ~0.80 TYPE SIM yet produce 127–465 mypy errors versus 141.8 for ground truth—reframes the open problem from 'can the model predict the right type?' to 'can it predict a mutually consistent set of types across a codebase?' This shifts research attention toward context-aware, repository-level inference strategies. Key open questions include how to efficiently handle long inputs/outputs for whole-repo context (the paper shows full-repo context helps consistency but degrades similarity), how to mitigate data contamination from pre-2024 repositories, and whether the consistency gap can be closed without sacrificing local accuracy. The benchmark itself provides a standardized, reproducible evaluation harness that the type-inference community can adopt.
