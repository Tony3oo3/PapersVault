## Problem

Federated recommender systems (FedRec) require transmitting full embedding matrices between edge devices and servers, imposing prohibitive communication and computation costs on resource-constrained devices. While the sparsity of embedding updates (users rate only a tiny fraction of items) offers an opportunity for payload reduction, existing sparsity-aware federated protocols inevitably leak the indices of non-zero updates to the server, revealing which items a user has rated. The paper asks whether one can achieve succinct user communication and computation in FedRec while ensuring the server learns no information about rated item indices or individual gradient values beyond the aggregated model.

## Input / Output

Each user provides a private set of rated items with their ratings, along with user and item feature vectors, and downloads only the relevant item embeddings (m' rows out of m total) rather than the full embedding matrix. The user locally computes sparse gradient updates (non-zero only for rated items) and uploads FSS keys of size O(m'(λ log m + bd)) per server instead of the full O(mbd) gradient. The two non-colluding servers jointly reconstruct the aggregated item embedding gradient and dense parameter updates, which are used to update the public model; the final output is a trained recommender model producing rating predictions. A uniform m' (e.g., 200–500) is enforced across all users via padding/truncation to hide each user's actual number of rated items.

## Method

SecEmb consists of two correlated modules built on function secret sharing (FSS) for point functions over a two-server architecture. In the privacy-preserving embedding retrieval module, each user encodes their rated item indices as point functions, generates FSS key pairs, and sends them to two servers; each server evaluates its share to produce secret shares of the target embeddings, which the user sums to recover the full embedding without revealing which items were requested. In the secure update aggregation module, each non-zero gradient row is encoded as a point function whose value is the d-dimensional gradient vector; FSS keys are generated and sent to the servers, which sum their evaluations across all users to reconstruct the aggregated gradient. Two key optimizations reduce overhead: (1) row-wise encoding collapses d separate point functions per item into a single one, cutting key count from m'd to m'; and (2) sharing the binary tree path from the retrieval stage means the aggregation stage only transmits a single correction word CW^(n+1) instead of the full FSS key, eliminating n AES operations per item. The protocol is lossless (no quantization or dimension reduction), and FSS security guarantees that each server learns nothing about individual updates or rated item indices beyond the final aggregation.

## Results

SecEmb reduces upload communication cost by up to 91.22× (MF on Yelp, 93,386 items) and download cost by up to 93.39× compared to Secure FedRec, while decreasing user-side computation time by up to 70×. On utility, SecEmb achieves the lowest RMSE among all compared methods: e.g., 0.864±0.002 on ML25M (MF) vs. 0.870–0.874 for Bit8Quant/TernQuant/SVD/CoLR, and 1.050±0.001 on Yelp (MF) matching the best baseline. For sequential recommendation on Amazon (9.27M items), SecEmb achieves up to 2549× upload reduction with HR@10 of 0.629 (Caser) and 0.639 (SASRec), outperforming all lossy compression baselines.

## Baselines & Comparisons

Against Secure FedRec (two-server ASS, Xiong et al. 2020), SecEmb reduces upload communication by 5×–91× and download by 4×–116× depending on item size and model, with the largest gains on ML25M and Yelp where sparse embeddings dominate. Against lossy compression baselines (Bit8Quant, TernQuant, SVD, CoLR), SecEmb achieves strictly lower RMSE (e.g., 0.864 vs. 0.870–0.874 on ML25M/MF) while also delivering higher reduction ratios on large-item datasets (62×–91× vs. 4×–16×), confirming it is both lossless and more efficient. Against sparse aggregation protocols SecAggMask (Liu et al. 2023) and TopkSecAgg (Lu et al. 2023), SecEmb achieves lower upload cost (e.g., 0.51 MB vs. 9.60 MB and 1.17 MB on ML25M/MF) while being the only method that fully hides rated item indices from the server. Against Kvsagg (Gupta et al. 2021), SecEmb reduces upload cost by 2.4×–14× (e.g., 0.52 vs. 7.31 MB on Yelp/MF) and does not leak the number of users who rated each item. Overall, SecEmb is the only protocol that simultaneously achieves secure training, reduced model download, reduced gradient transmission, operation on a reduced local model, and lossless aggregation.

## Relation to Prior Work

This paper builds on Function Secret Sharing (FSS) for point functions (Boyle et al., 2015, 2016) as its core cryptographic primitive, repurposing it to exploit the row-wise sparsity of item embedding gradients in recommender systems. It departs from two lines of prior work: general-purpose secure aggregation protocols (two-server ASS, Bonawitz et al.) that are secure but scale linearly with model size, and sparsity-aware FL protocols (SecAggMask, TopkSecAgg) that reduce communication but leak non-zero indices or gradient values. The key conceptual contribution is showing that FSS point functions can simultaneously provide full index privacy and lossless sparsity-aware compression, resolving the privacy-efficiency tradeoff that prior sparse aggregation methods could not.

## Why It Matters / Open Questions

The 90x communication reduction and 70x computation savings are practically significant for edge devices serving large item catalogs (60k+ items), where full-model federated training is otherwise infeasible. The lossless guarantee distinguishes SecEmb from quantization and low-rank compression methods that degrade utility by 1.3–2%, making it attractive for production recommender systems where accuracy is critical. Open questions include scalability to very large user populations (the two-server assumption and per-user FSS key generation may not scale), applicability to models where dense parameters dominate (e.g., DeepFM on small datasets shows only ~1x savings), and whether the protocol can be adapted to single-server or multi-server settings without the non-collusion requirement.
