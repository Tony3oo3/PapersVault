## Problem

Writing efficient GPU kernels is a time-consuming, expertise-intensive bottleneck in ML systems, yet no systematic benchmark exists to evaluate whether language models can automate this task. Existing kernel-generation approaches (compilers, libraries like CUTLASS or Triton) either require human programming effort or apply fixed optimization policies, leaving open whether LLMs can generate correct, hardware-efficient kernels across a breadth of real-world ML workloads.

## Input / Output

Each task provides a PyTorch reference Model class (with __init__ and forward) plus get_inputs() and get_init_inputs() functions that fix tensor shapes and dtypes (e.g., BF16, FP8); the LM must output a ModelNew class that inlines custom CUDA kernels via torch.utils.cpp_extension.load_inline. Evaluation is fully automated: correctness is verified against the reference on 5 random inputs, and wall-clock speedup is measured over 100 timed trials on a bare-metal NVIDIA L40S GPU, yielding the fast_p score (fraction of tasks that are both correct and exceed a speedup threshold p over PyTorch Eager).

## Method

KernelBench is an evaluation-only framework of 250 tasks partitioned into three difficulty levels—single primitive operations (100), fused operator sequences of 3–6 ops (100), and full ML architectures from popular GitHub repos (50)—with no ground-truth kernels provided so results transfer across hardware. The key metric, fast_p, jointly captures correctness and performance by counting tasks where the generated kernel is functionally correct and achieves a speedup greater than adjustable threshold p over the PyTorch Eager baseline. The evaluation environment supports two test-time strategies: repeated sampling (drawing k parallel generations at elevated temperature) and iterative refinement (feeding back compiler errors, execution results, and PyTorch profiler output across N turns). The paper evaluates seven frontier and open-source models (GPT-4o, OpenAI o1, DeepSeek V3/R1, Claude 3.5 Sonnet, Llama 3.1-70B/405B) under one-shot, repeated-sampling, and iterative-refinement settings, and further probes hardware-awareness by conditioning on GPU specs and few-shot kernel examples demonstrating tiling, fusion, and shared-memory management.

## Results

On KernelBench (250 tasks across 3 difficulty levels), the best frontier reasoning models (OpenAI o1 and DeepSeek-R1) achieve fast₁ scores of only 10–12% (Level 1), 24–36% (Level 2), and 2–12% (Level 3) against PyTorch Eager, meaning they outperform the baseline in fewer than 20% of tasks on average. Iterative refinement with execution and profiler feedback improves DeepSeek-R1's Level 2 fast₁ from 36% to 72%, and repeated sampling (k=100) lifts DeepSeek-V3's Level 2 fast₁ from 4% to 37%. Non-reasoning models (GPT-4o, Llama 3.1, Claude 3.5 Sonnet) perform substantially worse, with fast₁ rarely exceeding 10% on any level.

## Baselines & Comparisons

Against PyTorch Eager (the primary baseline), DeepSeek-R1 is the strongest model, achieving fast₁ of 36% on Level 2 (operator fusion) but only 12% on Level 1 and 2% on Level 3; OpenAI o1 is competitive at 24% on Level 2 and 12% on Level 3. Against torch.compile (the secondary baseline), DeepSeek-R1 reaches 38% (Level 1) and 37% (Level 2), while OpenAI o1 reaches 28% and 19% respectively — both still far below parity. Non-reasoning models (GPT-4o, DeepSeek-V3, Claude 3.5 Sonnet, Llama 3.1) consistently trail the reasoning models by 10–30 percentage points on Level 2, where kernel fusion opportunities are most exploitable. The paper also compares test-time strategies: iterative refinement with execution + profiler feedback (G+E+P) outperforms repeated sampling in 5 of 6 model-level combinations, with DeepSeek-R1 Level 2 improving from 36% to 72% fast₁. Overall, no model achieves fast₁ above 50% on any level in the one-shot setting, confirming KernelBench as a challenging open benchmark.

## Relation to Prior Work

This paper carves new ground at the intersection of LLM code generation and high-performance computing. Prior HPC code generation work focused on narrow tasks like C++-to-CUDA translation or generating well-known kernels (e.g., GEMMs), while LLM code generation benchmarks (HumanEval, SWE-bench) emphasized functional correctness over wall-clock performance. KernelBench departs from both by curating 250 diverse real-world ML workloads and introducing the fast_p metric that jointly captures correctness and speedup, positioning the problem as one where LLMs must reason about hardware-specific optimizations (tiling, fusion, tensor cores) rather than merely produce syntactically valid code.

## Why It Matters / Open Questions

GPU kernel development is a critical bottleneck for ML performance, and the finding that even frontier reasoning models (o1, R1) match the PyTorch baseline in fewer than 20% of tasks underscores a significant gap. The benchmark's design—directly mapping to production value, supporting new hardware platforms, and evolving with new architectures—makes it a durable evaluation target. Key open questions include how to improve LLM performance in the low-resource CUDA data regime (only 0.073% of The Stack), whether alternative programming abstractions (Triton, ThunderKittens) simplify the generation problem, and how to effectively select from the rich set of hardware and profiling information to condition models on.
