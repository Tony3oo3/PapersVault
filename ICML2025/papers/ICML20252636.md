## Problem

Writing high-performance mappers for task-based parallel programs (e.g., Legion) requires days of expert tuning across processor selection, memory placement, layout, and index mapping decisions, creating a significant barrier for domain scientists. Existing automated approaches like OpenTuner rely on scalar reinforcement learning feedback and struggle with the large, discrete search space of mapping strategies, failing to find valid mappers for 8 out of 9 benchmarks even after 1000 iterations.
![Teaser figure](../imgs/ICML20252636/cropped_page1_idx0.webp)

## Input / Output

The agent receives server specifications (CPU/GPU counts, node topology) and application metadata (task names, data arguments per task) as structured inputs, then iteratively generates mapper code in a purpose-built declarative DSL that is compiled to low-level C++ Legion APIs. The output is a DSL mapper program specifying Task, Region, Layout, and IndexTaskMap statements; the best mapper across 5 independent runs of 10 iterations each is selected for deployment. Notably, the DSL is a low-resource language with zero representation in LLM training corpora, yet LLMs generate it far more reliably than the equivalent C++ code (80% vs. 0% single-trial success rate).

## Method

The core contribution is the Agent-System Interface (ASI), comprising a declarative Domain-Specific Language (DSL) that reduces mapper code by 14× and defines a structured search space over four orthogonal mapping axes, and AutoGuide, a keyword-matching mechanism that translates raw runtime errors and performance metrics into natural-language explanations and targeted modification suggestions. The optimization loop uses the Trace framework (Cheng et al., 2024) with GPT-4o as the generative optimizer: the mapper agent is decomposed into independent trainable code segments (least-to-most prompting), and at each iteration the LLM receives enriched textual feedback (execution output + error explanations + mapper suggestions) rather than a single scalar reward. This rich-feedback generative optimization outperforms OpenTuner's scalar-reward RL by 11× at 10 iterations and maintains a 3.8× advantage even when OpenTuner runs 1000 iterations, while matching or surpassing expert-written mappers by up to 1.34× across nine benchmarks.

## Results

Using normalized throughput relative to expert-written mappers, the best mappers found by Trace (generative optimizer) match or surpass expert performance across all 9 benchmarks, achieving up to 1.34× speedup on Circuit and 1.31× on COSMA. When compared against OpenTuner (RL-based autotuning), Trace achieves an 11× advantage at 10 iterations and maintains a 3.8× advantage even after OpenTuner runs 1000 iterations. OpenTuner fails to produce valid mappers for 8 out of 9 benchmarks entirely (0.00× throughput), while Trace's worst-case failures are limited to occasional invalid configurations in SUMMA, PUMMA, and Solomonik. The full optimization process completes in approximately 10 minutes per application, reducing mapper development time from days to minutes.

## Baselines & Comparisons

Against expert-written mappers, Trace's best mappers match or exceed expert performance on all 9 benchmarks, with the largest gains on Circuit (1.34×, attributed to superior GPU FrameBuffer memory placement) and COSMA (1.31×, attributed to more efficient index mapping that reduces inter-GPU communication). Against OpenTuner (RL-based autotuning), Trace dominates decisively: at 10 iterations Trace is 11× better, and even after OpenTuner runs 1000 iterations, Trace retains a 3.8× advantage. OpenTuner fails catastrophically on 8 of 9 benchmarks, producing zero throughput, while Trace only occasionally encounters invalid configurations in SUMMA, PUMMA, and Solomonik. Against OPRO (another LLM-based generative optimizer), Trace performs comparably, confirming that the gains come from the Agent-System Interface design rather than the specific search algorithm. Random mappers serve as a lower bound, with 82.2% producing runtime errors, underscoring the difficulty of the search space.

## Relation to Prior Work

This paper builds directly on the Trace generative optimization framework (Cheng et al., 2024), adapting its PyTorch-like optimizer loop (forward pass → execution feedback → backward update) to the domain of parallel program mapper generation. It departs from the RL-based autotuning lineage (OpenTuner, Ansel et al., 2014) by replacing scalar reward signals with rich textual feedback (error explanations, natural-language suggestions) via the AutoGuide mechanism, and from prior LLM-as-optimizer work (OPRO, Yang et al., 2023) by introducing a purpose-built Agent-System Interface—a Domain-Specific Language that structures the search space and a compiler that translates it to low-level C++ APIs. The paper positions itself as the first application of generative optimization to system-level code generation, carving out a new sub-problem within the broader task-based parallel programming literature (Legion, StarPU, Chapel).

## Why It Matters / Open Questions

The practical impact is significant for HPC domain scientists: reducing mapper tuning from days to minutes and surpassing expert-written mappers (up to 1.34×) lowers a major barrier to exploiting modern heterogeneous hardware. The ASI abstraction (DSL + AutoGuide) is a reusable design pattern that could generalize to other system code generation tasks beyond Legion. Key limitations include evaluation on a single node, a single parallel framework, a single LLM (GPT-4o), and only nine benchmarks; the 3.8× advantage over OpenTuner partly reflects an information asymmetry (rich textual feedback vs. scalar reward) rather than purely algorithmic superiority. Open questions include whether the DSL generalizes to other task-based frameworks, whether the approach scales to multi-node or exascale settings, and whether the gains persist with smaller or open-weight LLMs.
