## Problem

Static code benchmarks like HumanEval and MBPP are vulnerable to data contamination during LLM training, inflating Pass@K scores and obscuring true reasoning ability. Existing contamination-free approaches (LiveCodeBench, PPM) rely on substantial manual effort and produce problems whose semantic complexity is uncontrolled, making it impossible to attribute score changes to model capability versus benchmark difficulty. No automated method exists that generates semantically diverse yet complexity-preserving programming problems at scale.

## Input / Output

The system consumes a seed programming problem consisting of a natural language prompt, a canonical Python solution, and a set of test cases (from HumanEval or MBPP Sanitized). It produces a new problem prompt rewritten under a randomly selected real-world scenario with contextualized input variables, while the canonical solution and test cases remain unchanged. A type inference algorithm (Algorithm 1) extracts input variable types from ASSERT statements and concrete values in the canonical solution, handling both basic types (int, float) and composite types (List[int], Tuple[int|str]) via recursive abstraction. The generation parameters are 50 scenarios × 50 contexts per scenario, with LLM temperature 0.8 for generation and 0 for validation.

## Method

DyCodeEval exploits a metamorphic relationship: a programming problem decomposes into a complexity-related algorithmic abstraction and a complexity-unrelated context description, and modifying only the latter preserves both the canonical solution and problem difficulty. Four LLM agents (powered by Claude-3.5-Sonnet) execute sequentially: a Scenario Proposer iteratively expands a pool of real-world domains, a Context Generator assigns scenario-specific meaning to each input variable using the inferred types, a Prompt Rewriter reformulates the seed prompt into 1–3 sentences under the new context (a rewriting task rather than generation), and a Validator performs two LLM-based consistency checks (prompt equivalence and solution alignment) before accepting the variant. The paper further introduces DyPass@K, a metric that generates n semantic prompt variants of a seed problem rather than n solution candidates for a fixed prompt, expanding the input space and making memorization-based shortcuts ineffective. Theoretical collision analysis (Theorems 3.1–3.3) bounds the probability of generating duplicate problems, showing that with M ≪ |S|×|C| the collision probability is negligible.

## Results

On the diversity evaluation (Table 1), DyCodeEval achieves substantially lower BLEU-4 and semantic similarity scores than all baselines, indicating far greater problem diversity. For example, on HumanEval external diversity, DyCodeEval scores BLEU-4 of 0.17 and SemSim of 0.59, compared to PPM's 0.69 and 0.89. Under simulated data contamination (Table 2), Pass@K for Llama-3.2-1B inflates from 0.22 to 0.82 at k=3, while DyPass@K remains stable at 0.17→0.13, confirming that DyPass resists contamination-induced score inflation. Across 10 random generation runs, the standard deviation of Pass@1 scores is minimal relative to the mean, demonstrating benchmarking stability.

## Baselines & Comparisons

DyCodeEval is compared against two families of baselines: PPM (Chen et al., FSE 2024) and Recode robustness mutations (Wang et al., ACL 2023). On all eight diversity metrics (internal and external, BLEU-4 and SemSim, across HumanEval and MBPP), DyCodeEval dramatically outperforms every baseline. Against PPM, the closest competing method, DyCodeEval reduces external BLEU-4 from 0.69 to 0.17 on HumanEval and from 0.57 to 0.02 on MBPP, and reduces external SemSim from 0.89 to 0.59 and 0.84 to 0.59 respectively. Against the Recode mutations (Token, Char, Func, Insert Line, CommSyntax), the gap is even more pronounced: most mutations score near 1.0 on both metrics (indicating almost no diversity), while DyCodeEval scores 0.17–0.27 on BLEU-4 and 0.59–0.74 on SemSim. The paper also demonstrates that under contamination, the proposed DyPass@K metric (0.13–0.29 for contaminated models) remains far more stable than Pass@K (0.82–0.89), whereas on uncontaminated models both metrics align closely, confirming DyPass does not introduce bias in clean settings.

## Relation to Prior Work

This paper adapts metamorphic testing principles from software engineering (Chen et al., 2018) to the domain of code LLM benchmarking, defining a metamorphic relationship that separates complexity-related algorithmic abstraction from complexity-unrelated context description in programming problems. It departs from prior contamination-free benchmarking efforts—LiveCodeBench (crawling new human-authored problems), PPM (manually defined operator combinations), and DyVal/TreeEval (dynamic generation via DAGs or tree planning)—by automating problem variation through a multi-agent LLM pipeline that modifies only contextual framing while preserving canonical solutions and test cases. The key conceptual departure is that rather than generating entirely new problems (which risks uncontrolled complexity shifts), DyCodeEval performs a controlled rewriting task guided by type inference and scenario assignment, making the generation process both scalable and complexity-preserving.

## Why It Matters / Open Questions

Data contamination in code LLM evaluation is an increasingly urgent concern as training corpora grow and public benchmarks like HumanEval and MBPP become ubiquitous in pretraining data. The paper's demonstration that static Pass@K scores can be inflated to near-ceiling levels under even partial contamination, while DyPass remains stable, provides a practical diagnostic tool for model developers and benchmark curators. However, the approach's reliance on a large foundation LLM (Claude-3.5-Sonnet) for generation introduces significant computational cost, and the 83% consistency rate with smaller models limits accessibility. Open questions include whether the collision analysis holds under non-uniform sampling in practice, whether the method generalizes beyond Python to other languages, and how to handle problems where context and algorithm are more tightly coupled than the assumed separation allows.
