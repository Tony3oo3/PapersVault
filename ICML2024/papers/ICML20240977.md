## Problem

Current LLM agent frameworks like ReAct execute function calls sequentially, invoking the LLM repeatedly for each reasoning and action step, which inflates latency, token cost, and can degrade accuracy through repetitive calls or premature early stopping. No existing framework could automatically identify which function calls are parallelizable, manage their inter-task dependencies, and execute them concurrently while also supporting dynamic replanning when intermediate results are needed to determine subsequent actions.
![Teaser figure](../imgs/ICML20240977/cropped_page1_idx0.webp)

## Input / Output

The system takes a natural language query, user-supplied tool definitions (descriptions and argument specifications), and optional in-context examples that demonstrate expected task decomposition patterns for the Planner. The Planner outputs a directed acyclic graph of tasks where inter-task dependencies are expressed via placeholder variables (e.g., $1, $2) that are later substituted with actual tool outputs. The final output is a single answer to the user query, assembled by a finish/join function that collects all task observations. A streamed Planner variant dispatches each task to the Executor as soon as it is generated rather than waiting for the full plan, analogous to instruction pipelining.

## Method

LLMCompiler decomposes the function-calling pipeline into three components inspired by classical compiler design: (1) a Function Calling Planner that uses an LLM with a pre-defined prompt to decompose the query into a DAG of atomic tasks with explicit dependencies, using placeholder variables for inter-task data flow; (2) a Task Fetching Unit that applies a greedy dispatch policy, replacing placeholder variables with actual outputs from completed tasks and sending ready tasks to the Executor without requiring a dedicated LLM; and (3) an Executor that asynchronously runs dispatched tasks in parallel using user-provided tools (search, math, LLM agents, etc.), each with dedicated memory for intermediate results. A key differentiator is the dynamic replanning loop: when intermediate results are a priori unknown (e.g., Game of 24 with Tree-of-Thoughts), the Executor feeds results back to the Planner, which generates a new set of tasks for the next iteration. The streamed Planner further reduces latency by emitting tasks incrementally, allowing the Executor to begin work before planning is complete. The framework is model-agnostic, working with both closed-source GPT models and open-source LLaMA-2 via vLLM, and requires no fine-tuning—only in-context examples and tool definitions from the user.

## Results

LLMCompiler achieves up to 3.74× latency speedup and 6.73× cost reduction compared to ReAct on embarrassingly parallel workloads (Movie Recommendation with GPT-3.5-turbo). On the more complex ParallelQA benchmark with dependency patterns, it delivers 2.15×–2.27× speedup, 4.65× cost reduction, and up to ~9% accuracy improvement over ReAct. On the Game of 24 (dynamic replanning), LLMCompiler achieves 2.09×–2.89× speedup over Tree-of-Thoughts with comparable success rates. On WebShop, it reaches up to 101.7× speedup over LATS and 25.7% higher success rate over ReAct.

## Baselines & Comparisons

Against ReAct (the primary baseline), LLMCompiler consistently wins on all three axes: latency (1.40×–3.74× speedup), cost (3.37×–6.73× token/cost reduction), and accuracy (up to ~9% improvement on ParallelQA with LLaMA-2, driven by eliminating ReAct's repetitive function calls and premature early stopping). Against ReAct† (ReAct with anti-looping prompts), LLMCompiler still achieves clear latency and cost advantages while matching or slightly exceeding accuracy, confirming that prompting alone cannot fully resolve ReAct's failure modes. Against OpenAI's parallel function calling (OAI Parallel Func.), LLMCompiler is up to 35% faster in latency and up to 2.57× cheaper in cost, while matching or slightly exceeding accuracy; the cost advantage stems from LLMCompiler planning the entire dependency graph in a single LLM call versus OAI's per-step planning. On Game of 24, LLMCompiler outperforms Tree-of-Thoughts by 2.09×–2.89× in latency with equal or slightly better success rates (75.33% vs. 74.00% with GPT-4). On WebShop, LLMCompiler dramatically outperforms LATS (101.7× speedup, 44.0% vs. 38.0% success rate with GPT-3.5) and LASER (2.69× speedup, 55.6% vs. 50.0% success rate with GPT-4), while being slightly slower than ReAct in latency but achieving 20–28% higher success rates.

## Relation to Prior Work

LLMCompiler draws its core metaphor from classical compiler optimization—specifically instruction scheduling, DAG-based dependency management, and pipelining—and applies these principles to LLM function calling. It departs from ReAct's sequential reason-act-observe loop and from ReWOO's static plan-then-execute separation by introducing a three-component architecture (Planner, Task Fetching Unit, Executor) that supports both parallel execution and dynamic replanning. The paper positions itself against concurrent work (OpenAI's 1106 parallel function calling, Skeleton-of-Thought) by emphasizing generality across open-source and closed-source models, support for non-trivial dependency graphs, and the replanning capability absent in those systems.

## Why It Matters / Open Questions

The framework offers a practical, model-agnostic solution to a growing bottleneck in LLM agent systems: sequential tool invocation inflates latency, cost, and—less obviously—accuracy by polluting context with intermediate observations. The ParallelQA benchmark fills a gap in evaluating non-trivial dependency patterns beyond embarrassingly parallel workloads. Open questions include how the Planner overhead scales with very large task graphs, whether the accuracy gains from avoiding intermediate-observation concatenation persist in more complex multi-turn agent settings, and how the framework handles failures or partial tool unavailability at runtime.
