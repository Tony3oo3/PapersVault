## Problem

Existing retrieval-augmented generation (RAG) methods for repository-level code completion invariably perform retrieval, yet the paper shows that up to 80% of retrievals fail to improve code LM performance and roughly 20% actively degrade it by introducing irrelevant cross-file information. This invariable retrieval also introduces significant latency overhead, with sparse retrieval alone being as time-consuming as generation with a 3B code LM. The paper challenges the assumption that retrieval should always be performed and asks whether a system can learn to selectively abstain.

## Input / Output

The system takes the current file's left context (X_l, truncated to 1024 tokens) and right context (X_r, truncated to 512 tokens) as input, along with the repository's other files F for potential retrieval. After a single forward pass over X_l and X_r, the model emits a retrieval decision (a special <cc> token to trigger retrieval or an empty token to abstain). If retrieval is triggered, top-k cross-file code chunks (k=10, retrieved via Jaccard similarity with chunk size 20 or 50) are concatenated into the prompt. The final output is one or more consecutive lines of completed code, generated in a single left-to-right pass modeled as an extension of fill-in-the-middle.

## Method

REPOFORMER fine-tunes StarCoderBase (1B/3B/7B/16B) with a self-supervised multi-task objective that jointly trains the model to (1) self-evaluate whether retrieval would help by predicting a <cc> token after an <eof> marker, and (2) robustly generate code with or without retrieved contexts. Training data is constructed by sampling blanks from permissively licensed Python repositories, retrieving cross-file contexts, and labeling each instance by contrasting the LM's edit similarity with and without retrieval augmentation. The training loss is a weighted combination of a cross-entropy loss on the retrieval decision (L_eval) and a cross-entropy loss on code generation conditioned on the appropriate context (L_gen). At inference, the entire process—self-evaluation, optional retrieval, and generation—is executed in a single left-to-right pass as an extension of fill-in-the-middle, with two selectable policies: greedy selection (retrieve if <cc> is the argmax token) and threshold selection (retrieve if P(<cc>) exceeds a tunable threshold T). This design yields up to 70% inference speedup while improving accuracy over always-retrieving baselines.

## Results

REPOFORMER-16B with threshold selection achieves state-of-the-art repository-level code completion, outperforming StarCoder-16B (Always Retrieving) by an average of ~3 points across all tasks (e.g., API completion ES: 77.93 vs. 74.50; Chunk completion ES: 75.50 vs. 71.90). The 3B REPOFORMER outperforms the 5× larger StarCoder-16B on API and chunk completion ES (74.96 and 72.23 vs. 74.50 and 71.90). Selective retrieval also yields up to 70% inference speedup in online serving settings (greedy selection) or ~25–33% speedup with threshold selection, without sacrificing accuracy.

## Baselines & Comparisons

REPOFORMER consistently outperforms same-size StarCoderBase with always-retrieving across all model sizes (1B–16B) and all tasks, with the largest gains on function completion (e.g., 1B: UT 28.79 vs. 25.71; 16B: UT 44.18 vs. 42.86). The 16B REPOFORMER surpasses the strongest StarCoder-16B baseline by 3.43 ES on API completion and 3.60 ES on chunk completion, establishing new state-of-the-art. In the plug-and-play setting (Table 4), REPOFORMER-1B as a selective policy improves accuracy and reduces latency for larger generation models: Code Llama-16B gains +1.02 ES on API completion with 32% speedup, ChatGPT gains +0.63 ES with 28% speedup, and CodeGen25-7B gains +0.30 ES with 20% speedup. CodeGen-Mono (16B and 2B) is used in the analysis (Table 1) to demonstrate that retrieval helps on fewer than 25% of instances, motivating the selective approach rather than serving as a direct performance baseline. Code Llama (7B/16B) and CodeGen25 (7B) are evaluated solely as generation models under REPOFORMER's selective policy, where REPOFORMER's decisions improve their accuracy over always-retrieving in every case.

## Relation to Prior Work

This paper builds on the fill-in-the-middle inference paradigm (Bavarian et al., 2022) and the StarCoder/StarCoderBase model family (Li et al., 2023), extending them with a self-selective retrieval mechanism for repository-level code completion. It departs from the dominant 'always retrieve' RAG formulation (Zhang et al., 2023; Ding et al., 2024) and from adaptive RAG heuristics based on retrieval scores or generation uncertainty (Drozdov et al., 2022; Jiang et al., 2023), instead training the code LM itself to self-evaluate retrieval necessity via contrastive self-supervision. The approach is conceptually closest to Self-RAG (Asai et al., 2024) and SKR (Wang et al., 2023), but avoids oracle-LM labeling and extra modules by deriving labels from the LM's own with/without-retrieval performance gap.

## Why It Matters / Open Questions

The finding that up to 80% of standard RAG retrievals fail to improve (and ~20% actively harm) code LM performance challenges a core assumption in the repository-level code completion literature and has direct practical implications: selective retrieval yields up to 70% inference speedup with no accuracy loss. Open questions remain around function completion labeling (ES-based signals are suboptimal for long-form generation), calibration of selective decisions for longer targets, and whether personalized per-repository retrieval policies can further improve the uniform selective strategy. The plug-and-play nature of REPOFORMER as a retrieval policy for larger black-box LMs (including ChatGPT) broadens its applicability beyond the StarCoder family.
