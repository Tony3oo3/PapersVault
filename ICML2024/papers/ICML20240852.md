## Problem

Existing code-generation benchmarks (HumanEval, MBPP, ODEX) evaluate LLMs on short, isolated functions with primitive-type I/O pairs, failing to capture the complexity of real-world software engineering where code must integrate with existing codebases, manage dependencies, and interact with interpreters. No scalable, execution-based testbed exists for evaluating programming agents on repository-level problems, largely because high-quality test suites are unavailable at scale on GitHub.

## Input / Output

The framework consumes a GitHub repository and selects functions with docstrings, extracting a dependency slice (transitively called functions and accessed global variables) as minimal context. It produces a problem instance tuple (D, R, T): a refined natural-language docstring, the repository code context, and an equivalence test harness containing setup code (file creation, environment configuration) plus test cases that check functional equivalence against the ground-truth implementation. R2E-Eval1 instantiates 246 such problems from 137 repositories, averaging 127.2 code tokens, 11.5 tests, and 3.7 dependencies per problem, with 92.2% average branch coverage.

## Method

R2E combines program analysis with LLM prompting to synthesize equivalence test harnesses for arbitrary GitHub functions. The key insight is decoupling test outputs from inputs: rather than predicting expected outputs, the harness executes the ground-truth function at runtime to obtain reference outputs, then checks whether the generated function produces equivalent results. Dependency slicing (computed via PyCG call graphs plus bytecode analysis for global variable access) extracts the minimal repository context needed for test generation, striking a balance between the Naive (no context) and Full (entire file) strategies. Generated harnesses are validated by execution in per-repository Docker containers, with validity requiring all equivalence tests to pass and quality measured by branch coverage (~83% achieved). Docstrings are further refined via a self-instruct-like prompting procedure that incorporates the synthesized test harness, argument types, and serialized I/O examples to improve specification clarity.

## Results

On R2E-Eval1, GPT-4 achieves a PASS@1 of approximately 50%, while GPT-3.5-Turbo and CodeLlama models (7B/13B/34B) achieve only ~30%, all significantly below their HumanEval scores. Self-repair with test harness feedback improves performance substantially: GPT-4 reaches a 33% self-repair rate and GPT-3.5-Turbo reaches 20% after 5 iterations on previously-failing problems. Chain-of-Thought prompting (0-shot and 2-shot) does not improve over direct prompting for either GPT-4 or GPT-3.5-Turbo. The R2E test harness generation pipeline (Equivalence + Sliced context) produces ~52% valid harnesses with ~88% branch coverage, outperforming output-prediction approaches by ~20% in validity.

## Baselines & Comparisons

R2E-Eval1 is the only benchmark that simultaneously supports execution-based evaluation, repository context, and fully automated construction, distinguishing it from all five compared baselines. Compared to HumanEval and ODEX, R2E-Eval1 introduces real-world repository dependencies (avg. 3.7 per problem) and 11.5 tests per function versus 6.6 and 1.9 respectively, making it substantially harder (models drop from HumanEval-level accuracy to ~30–50% PASS@1). CrossCodeEval and RepoBench provide repository context but lack execution-based functional correctness checks, relying instead on exact-match or BLEU metrics. RepoEval-Func supports execution and repository context but depends on human-written tests (not automated), limiting scalability to 12 repositories versus R2E-Eval1's 137. The paper's key empirical finding is that even SOTA models (GPT-4) struggle on R2E-Eval1 (~50% PASS@1) compared to their near-ceiling performance on HumanEval, and that interactive self-repair with test harness feedback (33% repair rate) far outperforms static prompting techniques like CoT, which show no improvement.

## Relation to Prior Work

This paper extends the code generation benchmarking lineage from isolated single-function problems (HumanEval, ODEX) and repository-level but execution-free benchmarks (CrossCodeEval, RepoBench, RepoEval) to a setting that combines repository context with automated, execution-based evaluation. The key methodological departure is the synergy of program analysis (dependency slicing via call graphs) with LLM prompting to synthesize equivalence test harnesses, where the original function serves as a reference implementation rather than requiring the LLM to predict outputs. For specification refinement, the paper adapts the self-instruct paradigm (Wang et al., 2022a) by augmenting it with synthesized test harnesses, argument types, and serialized I/O examples. Unlike SWE-bench, which depends on human-written tests from pull requests and limits scalability to 12 repositories, R2E's automated test generation enables problem collection from 137 repositories with minimal human supervision.

## Why It Matters / Open Questions

R2E-Eval1 fills a clear gap as the first executable, repository-level, fully automated code generation benchmark, enabling scalable and contamination-free evaluation of both static and interactive code generation systems. The finding that GPT-4 achieves only ~50% PASS@1 on real-world repository problems (versus much higher on HumanEval) and that chain-of-thought prompting provides no benefit while execution-based self-repair yields a 33% improvement underscores a practical shift toward interactive programming paradigms. Limitations include the relatively small scale (246 problems), reliance on observational equivalence rather than mutation testing for correctness, and residual docstring ambiguity. Open questions include whether the framework scales to larger repositories, whether the dependency-slicing context strategy generalizes beyond Python, and how to handle the inherent ambiguity in natural language specifications for complex functions.
