## Problem

Existing code-based reasoning approaches (e.g., Program of Thoughts) require all intermediate reasoning steps to be executable by a code interpreter, making them inapplicable to semantic sub-tasks like detecting sarcasm or classifying whether an object is a fruit. Conversely, pure language-based reasoning (Chain of Thought) struggles with precise arithmetic and symbolic computation. The paper asks whether these two paradigms can be unified so that LMs can 'think in code' while still handling semantic reasoning that cannot be expressed as executable code.

## Input / Output

The method takes a reasoning question in natural language along with three few-shot examples (either from the same task family or from different task families for cross-task prompting) that provide the response format. The LM generates a code or pseudocode program, which is then executed line-by-line with a shared program state. The final answer is extracted from a variable named 'answer' or, in case of irrecoverable errors, from the LM outputting 'A: answer'. The program state is maintained as a Python dictionary that is updated by both the interpreter and the LMulator, enabling arbitrary interweaving of execution modes including within control-flow structures like for-loops and if-statements.

## Method

Chain of Code (CoC) operates in two phases: Generation, where the LM writes a program mixing executable code and flexible pseudocode for semantic sub-tasks, and Execution, where the program is run line-by-line using Python's try/except. If a line executes successfully in Python, the program state is updated normally; if it raises an exception (e.g., calling an undefined function like is_sarcastic()), the LMulator—a language model acting as a code emulator—simulates the execution by generating the next program state given the question, prior lines, and state history. This shared program state interweaves the Python interpreter and LMulator in an arbitrary pattern, so a single program can alternate between precise computation (e.g., arithmetic, sorting) and semantic reasoning (e.g., commonsense classification) within the same loop or conditional. The key distinction from prior work is that CoC does not require all code to be executable (unlike Program of Thoughts) nor does it require the LM to simulate all execution (unlike ScratchPad), instead dynamically routing each line to whichever executor is appropriate.

## Results

On BIG-Bench Hard (BBH) with text-davinci-003, Chain of Code (CoC) achieves 84% average accuracy under single-task few-shot prompting, a 12-point gain over Chain of Thought (72%) and 29 points over Direct answering (55%), surpassing the human average of 68%. Under cross-task prompting, CoC reaches 61% vs. 55% for CoT and 50% for Direct. When combined with gpt-4, CoC achieves 91% on BBH single-task. On GSM8K, CoC (Interweave) scores 71% vs. 63% for CoT and 16% for Direct.

## Baselines & Comparisons

The primary baseline is Chain of Thought (CoT) prompting (Wei et al., 2022), which decomposes problems into natural-language intermediate steps. CoC outperforms CoT by 12 points on BBH single-task (84% vs. 72%) and by 6 points on cross-task (61% vs. 55%) with text-davinci-003. CoC also substantially outperforms Direct answering (55% single-task, 50% cross-task). On algorithmic tasks specifically, CoC reaches 95% average vs. 71% for CoT, while on NLP/semantic tasks CoC (74%) is roughly on par with CoT (74%), confirming that the LMulator preserves semantic reasoning capability. The paper also ablates against Python-only execution (48%, comparable to Program of Thoughts) and LM-only execution (57–63%, comparable to ScratchPad), showing that the interweaving of both interpreters is critical for the full performance gain.

## Relation to Prior Work

Chain of Code sits at the intersection of three prior lines of work: Chain of Thought (Wei et al., 2022) decomposes reasoning into natural-language substeps, Program of Thoughts (Chen et al., 2022) generates executable code for a Python interpreter, and ScratchPad (Nye et al., 2021) has an LM simulate code execution by tracking intermediate program state. CoC's key departure is the 'LMulator' — a line-by-line interweaving where the Python interpreter handles executable lines while the LM simulates non-executable semantic lines (e.g., `is_sarcastic(sentence)`), sharing a unified program state. This lifts the hard requirement in PoT that all intermediate reasoning must be executable code, and goes beyond ScratchPad by letting the interpreter handle the algorithmic portions precisely.

## Why It Matters / Open Questions

The LMulator concept provides a practical, low-overhead mechanism for LMs to 'think in code' on problems that mix algorithmic and semantic reasoning — a regime where neither pure CoT nor pure code execution suffices. The finding that CoC benefits even small models (where CoT gains only emerge at scale) suggests structured code output is a more accessible intermediate format than free-form text. Limitations include additional context/compute overhead, inability to modify custom Python objects during simulation, and marginal gains on purely semantic tasks like Ruin Names. Open directions include a unified code-and-language interpreter, finetuning dedicated LMulators, and extending the framework to external modalities (vision, databases) as demonstrated in the robotics experiments.
