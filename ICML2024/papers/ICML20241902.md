## Problem

Distributed LLM serving suffers from three interrelated challenges: pipeline bubbles caused by the bimodal latency gap between compute-bound prompt processing and memory-bandwidth-bound token generation (up to 106× difference), GPU memory overprovisioning from preallocating KV caches for all in-flight microbatches in pipeline-parallel configurations, and the absence of fault-tolerance mechanisms that preserve KV cache state across failures, forcing full request restarts and inflating end-to-end latency by up to 1.9×.

## Input / Output

The system accepts user-submitted text prompts (500–1000 tokens in evaluation) and autoregressively generates tokens until an EOS token or a prespecified limit is reached. In the distributed pipeline-parallel setting, the prompt KV cache must be streamed from dedicated prompt-processing machines to token-generation machines, while the evolving KV cache is continuously replicated to peer workers and swapped between GPU and CPU memory at microbatch granularity. The key intermediate artifact is the per-layer key-value cache, whose footprint scales with model depth, hidden dimension, batch size, and sequence length, often exceeding single-GPU capacity for models above ~13B parameters.

## Method

DéjàVu builds on FasterTransformer and introduces DéjàVuLib, a modular KV cache streaming library whose three low-level optimizations—buffered copies to coalesce non-contiguous token updates, layer-by-layer pipelining of prompt cache streaming with computation, and parallelization of token streaming with subsequent token generation—keep streaming overhead under 2%. On top of DéjàVuLib, the system implements three higher-level mechanisms: (1) prompt-token disaggregation with a closed-form resource allocation formula (Eq. 1) that partitions machines between prompt and token pipelines to equalize their throughputs and eliminate pipeline bubbles; (2) microbatch-level KV cache swapping that keeps only the active microbatch's cache in GPU memory while prefetching the next, enabling up to 2× larger batch sizes and up to 1.8× throughput gains; and (3) ring-based KV cache replication where each worker asynchronously streams its cache to the next pipeline stage, supporting a four-step recovery protocol that resumes inference from the last replicated token rather than restarting the entire request.

## Results

DéjàVu improves LLM serving throughput by up to 2× (BLOOM-176B) and 1.88× (OPT-66B) over the FasterTransformer baseline in pipeline-parallel configurations without failures. Microbatch swapping enables up to 1.8× throughput gains by accommodating 2× larger batch sizes within the same GPU memory budget. Under a single pipeline-stage failure, DéjàVu limits the latency increase to 1.24× versus 1.91× for the non-fault-tolerant baseline (a 1.54× reduction in added latency), and with three sequential failures, DéjàVu achieves 1.16× shorter overall runtime. The DéjàVuLib streaming overhead is within 2% of no-streaming performance, with buffered copies alone providing a 95× speedup over naive non-contiguous transfers.

## Baselines & Comparisons

The sole baseline is a modified FasterTransformer (with microbatch-level scheduling enabled to allow early-stopped microbatches to be replaced, which the paper shows outperforms the original FasterTransformer). DéjàVu wins on all three evaluated dimensions: (1) Throughput — DéjàVu sustains up to 2× higher throughput than FasterTransformer on BLOOM-176B and 1.88× on OPT-66B at high request rates, primarily because prompt-token disaggregation eliminates pipeline bubbles caused by the bimodal prompt/decode latency gap. (2) Memory efficiency — microbatch swapping allows DéjàVu to run 2× larger batch sizes on the same hardware, yielding up to 1.8× throughput gains for models that already fit in GPU memory (e.g., OPT-30B on V100s). (3) Fault tolerance — FasterTransformer has no fault-tolerance mechanism and must restart all in-flight requests from scratch upon failure (1.91× latency increase), while DéjàVu's KV cache replication and four-step recovery protocol limit the penalty to 1.24× for a single failure and 1.16× shorter runtime across three failures. The paper does not compare against vLLM, Orca, Splitwise, or DistServe experimentally, noting that vLLM and Orca do not support pipeline parallelism and that Splitwise/DistServe are concurrent work with different design goals.

## Relation to Prior Work

DéjàVu builds directly on FasterTransformer's pipeline-parallel and tensor-parallel infrastructure, extending it with a general-purpose KV cache streaming library (DéjàVuLib) that underpins three distinct optimizations. It departs from concurrent prompt-token disaggregation work (Splitwise, DistServe) by targeting pipeline-parallel settings specifically and providing a principled, closed-form resource allocation planner rather than simulation-based heuristics. Compared to vLLM's PagedAttention, which manages KV cache at the individual-request level in non-pipeline-parallel settings, DéjàVu operates at the microbatch level across pipeline stages. For fault tolerance, it goes beyond SpotServe's grace-period migration by implementing continuous token-level KV cache replication with a four-step recovery protocol.

## Why It Matters / Open Questions

The paper addresses three production-critical challenges in distributed LLM serving simultaneously—pipeline bubbles, GPU memory overprovisioning, and failure recovery—within a unified framework, making it directly relevant to teams operating large-scale inference clusters. The DéjàVuLib streaming primitives are a reusable component that could be integrated into other serving frameworks (the authors note TensorRT-LLM has the same issues). Key limitations include evaluation on small clusters (2–4 machines), a narrow set of models (GPT2, OPT, BLOOM), and a 20 Gbps network bandwidth floor for disaggregation to be beneficial. Open questions include dynamic reconfiguration under shifting workloads, integration with PagedAttention for further memory savings, and scaling to the hundreds-of-nodes deployments where these effects would be most pronounced.
