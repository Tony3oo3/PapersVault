## Problem

Existing LLM-based tool-use systems like ToolLLM require training a separate API retriever and lack a feedback mechanism when initial solutions fail, making them brittle at the scale of 16K+ real-world APIs. Additionally, the evaluation protocol in ToolBench artificially inflates pass rates by counting queries classified as 'non-solvable' (often due to irrelevant API candidates) as solved, masking true system performance.

## Input / Output

The system takes a natural-language user query and a pool of 16K+ APIs from RapidAPI, organized in a three-tier hierarchy (categories → tools → individual APIs), each with documented parameters and outputs. It produces a natural-language solution to the query, generated by orchestrating calls to a subset of APIs (typically ~14 candidates) selected from the pool. The entire pipeline is capped at 200K tokens and a maximum of 10 API calls per solver invocation, with GPT-4's function-calling interface serving as the sole interaction mechanism—no external retriever model or trained module is invoked.

## Method

AnyTool is a zero-shot, plug-and-play agent built entirely on GPT-4's function-calling feature, comprising three components. First, a hierarchical API retriever mirrors RapidAPI's category→tool→API structure with three tiers of agents (meta-agent, category agents, tool agents) that operate in parallel threads: the meta-agent dynamically spawns category agents, which spawn tool agents that add relevant APIs to a global candidate pool, thereby overcoming GPT-4's context-length limit through divide-and-conquer. Second, a solver (using DFSDT or CoT) attempts to resolve the query by calling functions from the candidate pool, with explicit 'Give Up' and 'Try Backtrack' options. Third, a self-reflection mechanism re-activates the system in ascending order (tool agents → category agents → meta-agent) with the failure reason injected into each agent's context, expanding the candidate pool and re-running the solver with cleaned history; this closed loop iterates up to a fixed number of rounds, improving pass rates by up to 20% with 4–6 reflections.

## Results

On the filtered ToolBench (using the revised pass rate metric from Eq. 2), AnyTool achieves a 58.2% average pass rate across six subsets, outperforming the best ToolLLM variant (GPT-4 w/DFSDT, 31.8%) by +26.4 points and the best GPT-4-with-reference-APIs baseline (DFSDT, 38.9%) by +19.3 points. On AnyToolBench, which requires the agent to retrieve APIs from the full 16K+ pool without reference APIs, AnyTool reaches 73.8% pass rate versus 36.6% for ToolLLM with GPT-4 and 14.0% for GPT-4 with a plain agent. Ablation studies confirm that both the hierarchical structure and the self-reflection mechanism contribute substantially: removing either drops the pass rate on G2-I from 58.9% to 22.4% or 19.6%, respectively.

## Baselines & Comparisons

AnyTool outperforms all ToolLLM variants by a wide margin: against the original ToolLLM (ToolLLaMA w/DFSDT, 22.9% avg), AnyTool gains +35.3 points; against the strongest ToolLLM variant (GPT-4 w/DFSDT, 31.8%), the gap is +26.4 points. Against GPT-4 baselines that use reference APIs (bypassing retrieval), AnyTool still leads by +19.3 points over the best configuration (GPT-4 w/DFSDT, 38.9%), demonstrating that its hierarchical retriever adds value even when the solver is the same model. The GPT-4 variants that attempt retrieval without a hierarchical structure (Plain Agent at 15.2%, AutoGen-RAG at 13.1%) perform far worse, confirming that the hierarchical divide-and-conquer design is critical for navigating 16K+ APIs within GPT-4's context window. On AnyToolBench, where no reference APIs are provided, AnyTool (73.8%) more than doubles the best ToolLLM variant (36.6%) and outperforms GPT-4 with a plain agent (14.0%) by nearly 60 points, underscoring the advantage of the self-reflective hierarchical retrieval in realistic settings.

## Relation to Prior Work

This paper builds directly on ToolLLM's dual-phase framework (API retrieval followed by query resolution) for leveraging 16K+ RapidAPI endpoints, but departs from it in three key ways: replacing the trained API retriever with GPT-4's native function-calling capability organized in a three-tier hierarchical agent structure, introducing a self-reflection loop that re-activates both retriever and solver upon failure, and revising the evaluation protocol to eliminate an artificial pass-rate inflation. It also situates itself within the broader LLM-agent literature (AutoGen, RAG-based retrieval) and the emerging self-reflection line of work (RAIN, self-play, self-rewarding LMs), arguing that whether GPT-4 can serve as a self-reflective agent for API calling was an open problem prior to this work.

## Why It Matters / Open Questions

The demonstration that ToolLLM's evaluation protocol yields a 99% pass rate with randomly selected APIs is a significant methodological finding that should prompt the field to re-examine how tool-use systems are benchmarked. AnyTool's plug-and-play design (no trained modules, relying solely on GPT-4 function calling) offers a practical path to large-scale API utilization, though its heavy dependence on GPT-4's availability, cost, and server stability limits immediate deployment. Open questions include whether the hierarchical structure and self-reflection mechanism transfer to open-source LLMs (the paper shows substantial drops with GPT-3.5 and ChatGLM), how to optimize API organization for efficiency, and whether performance holds on genuinely complex multi-step scenarios that current benchmarks do not capture.
