## Problem

Tokenization is an understudied and often neglected component of modern LLMs, with most works borrowing a single tokenizer from a base model without performing ablations or domain-specific optimization. When fine-tuning pre-trained LLMs for specialized domains like code generation, the original tokenizer is typically kept unchanged, leaving models sub-optimally compressed and limited by decisions made during unrelated pre-training. This paper asks whether and how the tokenizer can be specialized or swapped during fine-tuning without sacrificing downstream performance.
![Teaser figure](../imgs/ICML20240387/cropped_page0_idx0.webp)

## Input / Output

The tokenizer takes raw text or source code sequences and produces variable-length token sequences via BPE, with compression measured as Normalized Sequence Length (NSL) relative to the Llama tokenizer baseline. The downstream LLMs consume code prompts (from HumanEval and MBPP) and generate code completions, evaluated via Pass@1, Pass@100, and Compile@1 with n=200 samples per example at temperature 0.6 and top-p 0.95. A key practical detail is that higher-compression tokenizers reduce the number of tokens per sequence, directly increasing effective context length and reducing inference FLOPs and KV-cache memory, but the trade-off with per-token compute cost depends on model size and hardware.

## Method

The paper conducts a systematic empirical study of three tokenizer design levers—training data distribution, pre-tokenization regular expression, and vocabulary size—on BPE code tokenizers evaluated with 1.5B (GPT-2 XL) and 7B (Llama 2) models. They train tokenizers on 10B characters with varying code/English/multilingual mixes, test multiple pre-tokenization regexes (Identity, Punct, GPT-4, Llama), and sweep vocabulary sizes from 10k to 256k, deriving closed-form expressions for inference-optimal and memory-optimal vocabulary sizes that account for embedding parameters and KV-cache costs. For adapting pre-trained models, they use Fast Vocabulary Transfer (FVT) to initialize new embedding weights and show that switching tokenizers during fine-tuning on ≥50B tokens recovers downstream performance to near-baseline levels. They also compare tokenizer extension (merging domain-specific tokens into the existing vocabulary) against full tokenizer replacement, and ablate token healing as a decoding trick to mitigate prompt-boundary biases, finding it critical for high-compression tokenizers like Identity but negligible for well-bounded ones.

## Results

On 1.5B code-fine-tuned models (500B tokens), the Llama^C baseline achieves 22.8% HumanEval Pass@1 and 30.1% MBPP Pass@1. Switching to the GPT-4 tokenizer (GPT-4^C) yields 21.2% and 28.9% respectively, while Punct^C achieves 22.2% and 29.8%—all within ~1.5% of the Llama baseline despite 25%+ compression gains. On 7B Llama 2 models fine-tuned for 500B code tokens, GPT-4 80k achieves 30.8% HumanEval Pass@1 and 42.6% MBPP Pass@1, matching or exceeding Code Llama 7B (32.1% / 41.9%) on MBPP while using ~25% fewer tokens. The Identity tokenizer, despite achieving the highest compression (0.69 Code NSL), drops HumanEval Pass@1 to 18.8%, confirming that maximal compression comes at a significant performance cost.

## Baselines & Comparisons

Against Code Llama 7B (the primary real-world baseline), the paper's GPT-4 80k tokenizer achieves 30.8% HumanEval Pass@1 vs. 32.1% for Code Llama, but exceeds it on MBPP Pass@1 (42.6% vs. 41.9%) and Pass@100 (83.4% vs. 81.8%), while compressing code ~25% more efficiently. The Merged 80k tokenizer (Llama + code-specific tokens) achieves 31.2% HumanEval Pass@1 and 42.0% MBPP Pass@1, also matching Code Llama on MBPP. Against the Llama tokenizer baseline at 1.5B scale, Punct^NL actually surpasses Llama^NL on HumanEval Pass@1 (21.1% vs. 20.5%) and MBPP Pass@1 (28.6% vs. 28.0%), demonstrating that a tokenizer switch can simultaneously improve both compression and performance. The Identity tokenizer, despite achieving the best code compression (0.69 NSL vs. Llama's 1.00), underperforms all other tokenizers by 4+ points on HumanEval Pass@1, confirming that unbounded compression is counterproductive. In the broader tokenizer comparison (Table 1), the paper's GPT-4 100k tokenizer (0.74 Code NSL) matches the published GPT-4 tokenizer's compression while the Identity 100k (0.59 Code NSL) achieves the highest compression of any evaluated tokenizer, exceeding InCoder (0.74) and StarCoder (0.87) by 20%+ on code. Vocabulary size ablations (Table 3) show no statistically significant effect on performance (Pearson r = -0.13, p = 0.87), and FVT initialization (Table 4) provides a consistent 2-3 point improvement over random embedding initialization when switching tokenizers.

## Relation to Prior Work

This paper extends prior tokenizer research (Gowda & May, 2020; Chirkova & Troshin, 2023; Rust et al., 2021) from small-scale or multilingual settings to modern code LLMs of 1.5B and 7B parameters, and builds directly on Fast Vocabulary Transfer (Gee et al., 2022) as the mechanism for initializing new embedding weights when swapping tokenizers. It departs from prior tokenizer-adaptation work (Mosin et al., 2023; Gee et al., 2023) by operating at substantially larger model and vocabulary scales, and by continuing pre-training with the masked language model objective rather than fine-tuning directly on a downstream task. The paper positions itself against the common practice exemplified by Code Llama (Rozière et al., 2023), which inherited the Llama tokenizer unchanged, arguing that this leaves significant efficiency on the table.

## Why It Matters / Open Questions

The practical implication is significant: a widely-deployed model like Code Llama could have achieved 25%+ compression (faster inference, larger effective context) at no cost to code-generation quality by switching to a GPT-4-regex tokenizer during fine-tuning, provided >50B tokens of additional training. The finding that vocabulary size has negligible impact on coding performance (Pearson r = -0.13, p = 0.87) simplifies the design space for practitioners. Open questions include whether the 50B-token threshold generalizes to other domains or model architectures, whether the compression-vs-effective-FLOPs trade-off becomes more pronounced at larger scales, and whether the Identity tokenizer's catastrophic failure without token healing reveals a broader fragility in unconstrained BPE for structured generation tasks.
