## Problem

Hardware accelerator architecture and distributed device placement strategy for deep learning training have historically been optimized in isolation: architecture search assumes a fixed placement, while placement search assumes a fixed accelerator. This paper identifies that neither approach can find the globally optimal configuration, as the two dimensions are tightly coupled through memory footprint, compute utilization, and communication overhead.

## Input / Output

PHAZE consumes DNN training scripts (from which operator graphs are extracted via Torch.fx for each supported TMP width and microbatch size), an architecture template bounding the search to tensor/vector/fused cores with on-chip and HBM memory, and an area constraint set to TPUv4's footprint. It produces a complete co-optimized design: the accelerator's compute configuration (core counts, PE dimensions, vector lane width), memory hierarchy (global buffer, L2 buffers, HBM size), a per-layer operator schedule with intra-operator parallelism decisions, a multi-dimensional device placement (pipeline depth, data-parallel width, TMP width), and the microbatch size with activation recomputation vs. stashing choice. The ILP formulation uses only O(|V|²) variables per layer, avoiding time-indexed variables that cause exponential blowup in prior work.

## Method

PHAZE co-optimizes architecture and placement through a feedback loop: an architecture generator iterates feasible configurations in decreasing area order (with hysteresis-based early stopping), and for each configuration a solver computes end-to-end throughput. The solver has two stages: (1) a novel ILP per layer/layer slice that minimizes makespan by jointly deciding operator-to-core assignment, start times, and whether each operator uses intra-operator parallelism (all cores) or branches across cores, using continuous time variables and a strict-partial-order encoding that keeps the formulation at O(|V|²) variables; (2) a dynamic program over downsets that partitions layers into pipeline stages, assigns accelerators per stage, and selects data-parallel width and TMP width, modeling PipeDream-Flush/1F1B schedules, per-stage memory (weights, gradients, optimizer state, stashed activations), and AllReduce gradient-sync costs. The throughput from the DP feeds back to the architecture generator to select the next configuration or converge, enabling the architecture search to be guided by actual distributed-training performance rather than single-device metrics.

## Results

PHAZE-Per Model and PHAZE-Common architectures achieve 3.6× and 2.9× higher throughput, respectively, compared to TPUv4 with an expert device placement strategy across 8 LLM workloads (OPT, BERT-Large, GPT-2, LLaMA-2-7B, and Megatron variants up to GPT-3 175B). Even when TPUv4 is augmented with PHAZE's own ILP scheduler and dynamic programming device placement, PHAZE-Common still delivers 1.8× higher throughput, demonstrating the value of co-optimization. The PHAZE-Common architecture ({2,512,256,256,256} compute, {32,4096,1,4KB} memory, 64GB HBM) stays within 91% of the TPUv4 area constraint while outperforming it, and requires less area than TPUv4 overall.

## Baselines & Comparisons

Against TPUv4 (Jouppi et al., 2023) with expert device placement, PHAZE-Common achieves 2.9× higher geometric-mean throughput and PHAZE-Per Model achieves 3.6×. When TPUv4 is given PHAZE's own ILP scheduler and dynamic programming device placement (removing the placement advantage), PHAZE-Common still leads by 1.8×, confirming that the architecture co-optimization loop—not just the placement algorithm—drives the gains. Against Spotlight (Sakhuja et al., 2023), a Bayesian-optimization-based architecture search, PHAZE-Common delivers 2× higher throughput; Spotlight is structurally limited to a single tensor core, producing very wide but bandwidth-starved cores (e.g., {1,1,8192,2,8192} for LLaMA-2) with significantly smaller global buffer bandwidth than PHAZE's multi-core designs. Both baselines also benefit from PHAZE's solver (TPUv4+Phaze Solver, Spotlight+Phaze Solver), but neither matches the full co-optimized PHAZE configuration, underscoring that fixing the architecture before placement search leaves performance on the table.

## Relation to Prior Work

PHAZE unifies two previously isolated research threads: hardware accelerator architecture search (WHAM, Spotlight, Fast, Prime) and distributed device placement (Piper, Alpa, FlexFlow, PipeDream). Prior architecture search works either target inference only or assume a fixed memory-based placement strategy, while prior device placement works assume a fixed accelerator. PHAZE departs from both by jointly optimizing architecture, per-chip operator scheduling (via a novel ILP that avoids time-indexed variables, unlike WHAM), and cross-device placement (via a DP that extends Piper with flushing schedules, faithful memory modeling, and branching support). The ILP additionally explores intra-operator parallelism across cores, a dimension absent from both prior architecture and placement formulations.

## Why It Matters / Open Questions

PHAZE provides the first algorithmic framework for co-optimizing accelerator design and distributed training strategy, which is practically important as AI supercomputer design increasingly requires workload-specific hardware. Key limitations include the assumption of a homogeneous flat network (no hierarchical topologies), no modeling of compute-communication overlap across unfused operators, and globally fixed parallelism degrees across all layers. Open questions include whether the simulation-based estimates (Sunstone, Accelergy, Tandem) transfer faithfully to real silicon, how the framework scales to non-transformer architectures with more complex branching, and whether integrating novel TMP strategies (MoE, sequence parallelism) would further improve the co-optimization landscape.
