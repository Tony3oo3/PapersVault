## Problem

Automatically optimizing Linux kernel configurations (15,000+ interdependent options) for AIoT scenarios remains unsolved: the combinatorial space exceeds 2^15,000 possibilities, each evaluation costs 1–2 hours, and error-prone options can cause boot-up failure. Existing neural network and Bayesian optimization approaches fail due to the lack of training data, the high dimensionality, and their inability to handle boot-critical constraints.
![Teaser figure](../imgs/ICML20240292/cropped_page1_idx0.webp)

## Input / Output

AutoOS consumes the OS kernel configuration tree (accessed level-by-level via kconfiglib atomic APIs), a user-specified optimization goal (e.g., maximize UnixBench total score), and the target hardware platform. It produces a set of modified kernel configuration options that yield a bootable, performance-optimized OS kernel. The tree structure is essential because the full configuration (~100,000 words) exceeds LLM context limits (~32K tokens), so options are processed sequentially per tree level rather than as a monolithic prompt.

## Method

AutoOS formulates kernel configuration as optimization on a dynamic tree and navigates it via a five-stage state machine: observe (gather node semantics at the current level), prune (LLM-guided random pruning of irrelevant subtrees), propose (LLM selects and configures options with a two-round self-explanation mechanism to ensure reasoning consistency), act (apply modifications and handle newly appeared/disappeared options in a loop until the tree stabilizes), and correct (closed-loop LLM debugging of boot-up failures, falling back to binary search if needed). Randomness in pruning and proposing broadens exploration across multiple search trials, while the self-explanation mechanism raises LLM decision consistency from 28.6% to 93.4% and eliminates boot-up failure options, reducing correction overhead from O(|M∩K|) to O(1) in most cases.

## Results

AutoOS achieves up to 25.6% UnixBench total score improvement over vendor-provided default configurations (Fedora on RISC-V: 260 vs. 207), 8.4% on PolyOS (335 vs. 309), and 9.0% on Ubuntu (4238 vs. 3885). On PolyOS, AutoOS also outperforms the expert-manually-optimized default, and on LMbench (54 sub-metrics), the PolyOS configuration optimized for UnixBench still achieves better performance on 37/54 metrics (10–30% gains) without overfitting. The LLM-Vanilla baseline (directly prompting GPT-3.5-Turbo) actually degrades performance by 8.5% on PolyOS and 6.3% on Fedora, confirming that naive prompting is insufficient for this task.

## Baselines & Comparisons

The paper compares AutoOS against two baselines: (1) the vendor-provided default kernel configuration, and (2) LLM-Vanilla, which directly prompts GPT-3.5-Turbo to recommend ~10–20 configuration options without structured interaction. AutoOS outperforms the default on all three platforms: +8.4% on PolyOS (notably surpassing an expert-manually-optimized baseline), +25.6% on Fedora, and +9.0% on Ubuntu. LLM-Vanilla consistently underperforms the default on AIoT scenarios (−8.5% on PolyOS, −6.3% on Fedora) because it cannot handle inter-option dependencies or the full 15,000+ option space within its token limit. On Ubuntu, LLM-Vanilla barely matches the default (+0.3%), while AutoOS achieves a clear +9.0% gain, with particularly strong improvements in file I/O (File 256: +15.8%) and system calls (+23.5%). The ablation study further confirms that both pruning and self-explanation are essential: removing them increases modified options from 17 to 230 and introduces 5 boot-up failures requiring 26.7 hours of correction.

## Relation to Prior Work

This paper departs from the two dominant prior approaches to OS kernel configuration optimization—neural network methods (which require large labeled datasets that do not exist for kernel configs) and Bayesian optimization (which is limited to low-dimensional continuous spaces)—by instead exploiting the expert prior knowledge embedded in pre-trained LLMs. It builds on the self-explanation prompting mechanism of Rajani et al. (2019) to enforce reasoning consistency, and on the kconfiglib library to abstract the kernel's directory-structured configuration space into a programmatically traversable dynamic tree. The key conceptual departure is formulating the 15,000+-option optimization as a state-machine-guided tree traversal (observe-prune-propose-act-correct) rather than a flat combinatorial search, which naturally respects inter-option dependencies and keeps each LLM prompt within context-length limits.

## Why It Matters / Open Questions

AutoOS demonstrates that LLMs can replace expert manual tuning for a task that previously required hours of specialist knowledge, achieving 8–25% UnixBench improvements over vendor defaults and even surpassing the 'exhaustively manually optimized' PolyOS baseline. However, the evaluation is limited to a single LLM (GPT-3.5-Turbo), two hardware platforms, and 24 search trials, leaving open whether the approach generalizes across LLM families, kernel versions, and non-Linux systems. The authors themselves note that integration with Bayesian optimization for the pruned sub-space and extension to energy-consumption objectives are natural next steps, and the lack of kconfig-like APIs for non-Linux kernels remains a practical barrier to broader adoption.
