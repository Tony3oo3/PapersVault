## Problem

Existing UE-based simulators (AirSim, CARLA, UnrealCV+) expose only hundreds of handcrafted Python functions, incur 20–35× communication overhead when returning high-resolution images to Python, and are distributed as monolithic applications requiring custom forks of the 10+ million-line UE codebase. This limits both the programmable functionality available to researchers and the rendering throughput achievable when delivering photorealistic observations to embodied agents.
![Teaser figure](../imgs/ECCV20260138/cropped_page1_idx0.webp)

## Input / Output

The user writes Python code structured as transactions (begin_frame/end_frame contexts) that call any reflection-visible UE function or property as though it were a native Python attribute. The system renders 1920×1080 photorealistic beauty images directly into the user's NumPy array at 73 FPS via interprocess shared memory (zero-copy), alongside ground truth modalities unavailable in any existing UE simulator: non-diffuse intrinsic image decomposition, material IDs, physically based shading parameters, depths, surface normals, and instance/semantic IDs. The client and server can run on different machines over TCP/IP, and the same interface controls standalone applications, the Unreal Editor, and UE's path tracer.

## Method

The key technical insight is to hook directly into UE's runtime reflection system, exposing over 14K unique UE functions and 53K properties to Python via string-keyed dynamic dispatch without hand-crafted wrappers for each class or function. The architecture is a client-server design: a Python client (built on nanobind) transforms user transactions into typed command streams sent over rpclib to a C++ server running on a dedicated thread within the UE application, which queues tasks onto the game thread at frame boundaries. Every UE operation has an asynchronous variant that returns a future object, allowing the Python thread to run ahead of the game thread without blocking it, enabling native frame-rate execution. For large data transfer, a shared-memory mechanism maps GPU-rendered images directly into user NumPy arrays with no intermediate copying, and SPFUNCTIONS (custom C++ functions bound to UE objects at runtime) provide an efficient dispatch path for NumPy array arguments and return values. Only 193 hand-crafted server entry points are needed (versus thousands in existing simulators), with roughly 75% dedicated to exposing the reflection system itself, yielding an order-of-magnitude increase in programmable functionality at a modest 27K-line code footprint.

## Results

SPEAR exposes 14,485 unique UE functions and 53,537 UE properties to Python, an order-of-magnitude increase over existing UE-based simulators (AirSim: 0, CARLA: 0, UnrealCV+: 747 functions), while maintaining a modest 27,193-line code footprint. In rendering performance, SPEAR delivers 1920×1080 photorealistic images to a user's NumPy array at 73.4 FPS (2-frame latency), which is 9–21× faster than UnrealCV+ (3.5 FPS) and 12× faster than AirSim (2.6 FPS at 0-frame latency). Under matched rendering-latency conditions, SPEAR is 10% faster than CARLA (27.0 ms vs. 30.6 ms at 2-frame latency).

## Baselines & Comparisons

SPEAR decisively outperforms AirSim in rendering throughput: at 0-frame latency, SPEAR delivers images in 31.0 ms (32.3 FPS) versus AirSim's 379.4 ms (2.6 FPS), a 12× speedup attributable to lower communication overhead. Against CARLA at matched 2-frame latency, SPEAR is 10% faster (27.0 ms / 37.1 FPS vs. 30.6 ms / 32.7 FPS). Compared to UnrealCV+ under identical project settings, SPEAR with async + shared memory achieves 17.8 ms (56.2 FPS) versus UnrealCV+'s 286.9 ms (3.5 FPS), a 9–21× improvement depending on configuration. On programmable functionality, SPEAR exposes 14,485 UE functions and 53,537 UE variables through its reflection interface, whereas AirSim and CARLA expose zero underlying UE functions (only 92 and 465 hand-crafted wrappers respectively), and UnrealCV+ exposes 747 UE functions and 8,721 variables. SPEAR also achieves this with far less code (27,193 lines) than AirSim (144,536) or CARLA (150,502), and provides ground-truth modalities (intrinsic decomposition, material IDs, PBR parameters) unavailable in any of the baselines.

## Relation to Prior Work

SPEAR builds directly on Unreal Engine's runtime reflection system, which prior UE-based simulators (AirSim, CARLA, UnrealCV+) largely bypassed in favor of hand-crafted Python wrappers exposing only hundreds of functions. The key architectural departure is using UE's reflection system as the primary interface layer, exposing 14K+ functions and 53K properties to Python with only 27K lines of code, compared to 144K–150K lines in AirSim and CARLA. The transaction-based programming model with asynchronous operations and interprocess shared memory represents a novel client-server design that avoids the 20–35× communication overhead observed in existing UE plugins when returning large data blocks like rendered images.

## Why It Matters / Open Questions

SPEAR positions itself as a foundational data engine for computer vision, robotics, and embodied AI, and its order-of-magnitude gains in both programmable functionality and rendering throughput (73 FPS at 1080p vs. 3.5 FPS for UnrealCV+) make it a compelling default choice for UE-based research. The ground-truth modalities it provides (non-diffuse intrinsic decomposition, material IDs, physically based shading parameters) are unavailable in any existing UE simulator, enabling new types of training data for holistic scene understanding. Open questions include how well the reflection-based approach scales to very large or heavily modified UE projects, whether the 2-frame rendering latency required for peak throughput is acceptable for all interactive applications, and how the system performs on non-Windows platforms or with non-RTX GPUs.
