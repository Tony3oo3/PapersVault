## Problem

Sampling-based view transformation (Sampling-VT) enables dense, continuous BEV aggregation ideal for high-resolution and long-range perception, but its standard tensorized execution explicitly materializes height- and camera-dependent intermediate tensors whose size scales as O(BNCXYZ), causing peak GPU memory and latency that grow linearly with vertical discretization and camera count. This memory-traffic bottleneck, rather than arithmetic throughput, limits deployment on memory-constrained devices and prevents scaling BEV range, resolution, or height bins within fixed budgets.

## Input / Output

FlashBEV consumes the same inputs as the tensorized baseline: per-camera image feature maps (e.g., 56×100×128 after backbone downsampling of 448×800 images) and camera projection matrices of shape (B,N,3,4). It produces a dense BEV feature map of shape (B,X,Y,C) (e.g., 1×200×200×128) computed as the sum over height bins of the per-bin valid camera mean, with no precomputed lookup tables, no discretized pixel indices, and no additional indexing structures beyond the projection matrices.

## Method

The core insight is that Sampling-VT is a gather-reduction operator: each BEV element (x,y,c) independently accumulates contributions across cameras n and height bins z with no cross-location dependencies, so the height-expanded tensor need never be materialized. FlashBEV launches a single fused CUDA kernel assigning one thread per output element (b,x,y,c); each thread iterates over z and n, performing voxel-center computation, camera projection, validity masking, and bilinear feature sampling entirely in registers, accumulating per-bin numerator and denominator before computing the valid mean and adding to a running sum. All intermediates are discarded immediately, reducing peak memory to O(BCXY) (output only), independent of Z and N. The approach trades increased arithmetic—channel-independent quantities like projection and validity are recomputed per channel—for eliminated HBM traffic, shifting execution from memory-bound to compute-bound. The result is mathematically equivalent to Tensorized Sampling-VT (max forward error ~3×10⁻⁴, cosine similarity 1.00), and the same execution principle extends to BEVFormer's deformable-attention SCA as FlashSCA.

## Results

On the SimpleBEV reference config (X=Y=200, Z=8, C=128, batch 1), FlashBEV reduces VT peak GPU memory from 1971.9 MB to 52.8 MB (~37×) and achieves 5.2× forward speedup (1.77 ms vs 9.18 ms) and 5.5× backward speedup (3.27 ms vs 17.90 ms) over Tensorized Sampling-VT, while preserving detection accuracy (46.8±0.1 vs 46.9±0.3 mIoU on nuScenes). End-to-end, peak memory drops from 2211.3 MB to 876.8 MB (~2.5×) and latency from 67.2 ms to 59.9 ms (~11% faster). Critically, FlashBEV's memory is independent of the number of height bins Z, enabling up to 10× larger BEV grids under the same memory budget (1992×1992 vs 200×200).

## Baselines & Comparisons

Against SimpleBEV (the reference pipeline), FlashBEV matches detection accuracy on nuScenes (46.8±0.1 vs 46.9±0.1 mIoU, within variance) while reducing VT peak memory by 37× and forward latency by 5.2×, confirming that the execution redesign preserves operator semantics exactly. Against BEVFormer's spatial cross-attention (SCA), the analogous FlashSCA kernel reduces peak memory by 2.5–3.2× and latency by 1.7–2.1× (e.g., at P=32 sampling points: 3708 MB → 1168 MB, 29.27 ms → 13.90 ms in TensorRT), with outputs matching to FP32 round-off (max |Δ| = 7×10⁻⁷ forward). In both comparisons FlashBEV/FlashSCA wins decisively on memory and latency while tying or matching on accuracy, demonstrating that the gather-reduction fusion strategy generalizes across different VT operator formulations.

## Relation to Prior Work

FlashBEV applies the IO-awareness principle from FlashAttention—reordering computation and selectively recomputing intermediates to minimize HBM traffic—to the view-transformation operator in BEV perception. It departs from the standard Tensorized Sampling-VT baseline by recognizing the operator's gather-reduction structure (each BEV element independently accumulates over cameras and height bins), enabling a single fused kernel with thread-local accumulation instead of materializing O(BNCXYZ) intermediate tensors. Unlike LUT-based methods (FastBEV, DualBEV) that trade exactness for speed via discretized coordinates, and unlike sparse-sampling approaches (PointBEV, HV-BEV) that sacrifice dense coverage, FlashBEV preserves exact continuous Sampling-VT semantics with no precomputed tables and no sparsification.

## Why It Matters / Open Questions

By reducing VT peak memory by over 37× and making it independent of the number of height bins, FlashBEV removes a fundamental scalability barrier that previously forced practitioners to choose between BEV range/resolution, vertical discretization, and deployment feasibility on memory-constrained hardware. The cross-framework transfer to BEVFormer's spatial cross-attention (FlashSCA) and clean TensorRT plugin deployment suggest the execution pattern generalizes beyond SimpleBEV-style pipelines. Open questions include whether the compute-bound trade-off (recomputing channel-independent quantities per channel) remains favorable at very large channel counts, and whether the approach extends to multi-resolution or temporal-gathering variants of Sampling-VT.
