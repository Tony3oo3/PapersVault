## Problem

Existing agentic coding benchmarks like SWE-bench are dominated by bug-fixing tasks (only ~18–22% are feature requests) and rely on PR-based collection that cannot capture complete feature patches spanning multiple commits and PRs. This limits evaluation to narrow, single-PR scenarios and prevents automated, scalable generation of feature-level tasks. FeatureBench addresses this by targeting end-to-end, feature-oriented software development with an execution-based evaluation protocol and a test-driven pipeline that automatically derives tasks from code repositories.

## Input / Output

Each task provides the agent with a problem statement containing a high-level functional description, explicit interface definitions (function signatures, import paths, input/output types with annotations), a blacklist of prohibited URLs, and a Dockerfile for the execution environment. For L1 tasks the agent receives an existing codebase with the target feature surgically removed; for L2 tasks the entire repository is absent and the agent must implement from scratch. The agent must produce a directly callable code module (a git patch) whose invocation path and signature exactly match the specified interface; success is determined by passing all F2P tests while maintaining P2P test integrity, with metrics reported as resolved rate, average F2P passed rate, and token I/O.

## Method

The core contribution is a test-driven, automated collection pipeline that isolates feature-level coding tasks from real repositories. It executes F2P and P2P test cases under Python's dynamic tracing facility to construct a function-level object dependency graph, then uses an LLM classifier to identify top-level tested objects versus utility imports in each test file. A breadth-first traversal from those entry points classifies graph nodes as 'remained' (encountered during P2P execution, i.e., shared infrastructure) or 'extracted' (exclusive to the target feature); the extracted nodes' source code is removed to produce an undeveloped codebase and a complementary patch. A rigorous post-verification step confirms the modified codebase passes all P2P tests, fails all F2P tests, and that reapplying the patch restores full functionality. Problem statements are then auto-synthesized from the extracted code's signatures and docstrings (with LLM-generated descriptions when docstrings are absent), requiring only ~3 minutes of manual environment configuration per repository.

## Results

On the Full set of FeatureBench (200 tasks), the best-performing configurations achieve only 11.0% resolved rate (Claude Code + Claude Opus 4.5) and 12.5% (Codex + GPT-5.1-Codex, medium reasoning), with passed rates of 43.29% and 41.66% respectively. On the Lite set (30 tasks), the top resolved rates reach 20.0% for both Claude Opus 4.5 and GPT-5.1-Codex. All evaluated models consume over 1 million input tokens per task on average, reflecting extremely low computational efficiency for real-world feature development. The L2 (from-scratch) setting is substantially harder than L1 (incremental), with resolved rates dropping by roughly half across all models.

## Baselines & Comparisons

The primary comparison is against SWE-bench (Table 4), using a FeatureBench subset restricted to repositories shared with SWE-bench for a fair head-to-head. Claude Opus 4.5 resolves 74.40% of SWE-bench Verified tasks but only 5.2% of the corresponding FeatureBench subset, a gap of nearly 70 percentage points. GPT-5.1-Codex similarly drops from 16.7% resolved on FeatureBench subset versus its SWE-bench performance. The paper also positions FeatureBench against other agentic coding benchmarks (Table 1): unlike SWE-bench (bug-fixing focused, 500 instances), PaperBench (20 handcrafted tasks, no execution-based eval), or GitTaskBench (54 expert-designed tasks), FeatureBench is the only benchmark that simultaneously supports feature-oriented tasks, execution-based evaluation, scalable automated collection, and continual updatability. The ablation in Table 5 confirms that manual verification of auto-generated instances does not materially change model performance (e.g., GPT-5.1-Codex: 16.7% → 20.0% resolved), validating the automated pipeline's quality.

## Relation to Prior Work

FeatureBench extends the SWE-bench evaluation paradigm (F2P/P2P execution-based testing) from bug-fixing to feature-level development, addressing a gap the authors identify as underrepresented in existing benchmarks. It departs from PR-based collection methods (SWE-bench, SWE-Gym, R2E-Gym) by introducing a test-driven pipeline that uses dynamic runtime tracing to construct object dependency graphs, enabling automatic extraction of feature-level code patches that span multiple commits and PRs. Unlike other feature-oriented benchmarks (PaperBench, MLE-Bench, GitTaskBench) that rely on expert curation or lack execution-based evaluation, FeatureBench combines automated, scalable instance generation with rigorous post-verification to ensure codebase integrity.

## Why It Matters / Open Questions

The stark performance gap—Claude Opus 4.5 resolving 74.4% of SWE-bench tasks but only 11.0% of FeatureBench tasks—reveals that current agentic coding systems have not generalized from bug-fixing to the multi-file, long-horizon feature development that dominates real-world software engineering. The automated, test-driven collection pipeline enables continual benchmark updates to mitigate data contamination, a practical advantage over static handcrafted benchmarks. Open questions include how to address the identified failure modes (cross-file dependency resolution, LLM 'laziness' in hallucinating interfaces rather than reading source), whether the L2 from-scratch setting is realistic enough to guide training, and how token efficiency (millions of input tokens for <15% success) can be improved.
