## Problem

Existing repository-level benchmarks (SWE-bench, RepoBench) do not require full reasoning over runtime execution and can be solved via heuristic shortcuts or localized patch retrieval, leaving a gap in evaluating whether coding LLMs truly understand codebase-level execution flow. This paper introduces GISTIFY, a task that demands an agent trace the complete execution path of a given command through a codebase and compress all essential logic into a single self-contained file, directly probing structural understanding, runtime modeling, and the ability to produce large code patches.

## Input / Output

The agent receives a full codebase (e.g., pylint, scikit-learn, flask) inside a Docker image plus a specific entrypoint command such as a pytest invocation on a particular test. It must produce a single Python file that is self-contained (no imports from the original repository), execution-faithful (identical stdout/stderr and test pass/fail behavior), minimal (only lines actually executed are retained), and grounded (all code copied verbatim from the original codebase, no hallucination). Evaluation integrates the original test function into the generated file before running it to prevent the model from modifying the test, and scores via three metrics: binary Execution Fidelity, Line Execution Rate (fraction of executable lines actually run), and Line Existence Rate (block-level line matching against the source repository).

## Method

GISTIFY is framed as an agentic code-generation task evaluated across three scaffolding frameworks (mini-SWE-agent with bash-only access, SWE-agent with a full tool suite, and GitHub Copilot with 25+ tools) and four frontier models (GPT-5-mini, GPT-5, Claude-3.7-Sonnet, Claude-Sonnet-4), each capped at 50 steps and 128K context. The core mechanism requires the agent to start from the entrypoint test, recursively follow imports and function calls to identify every module and dependency on the execution path, then inline all necessary code into one file while pruning unused branches. The paper's key empirical contributions include: (1) showing that even the best model (Claude-4) achieves only ~55–61% execution fidelity, with performance dropping to 21% on a GISTIFY-hard subset selected by long execution traces and high file coverage; (2) demonstrating that faithfully copying the test function (Test F₁ score) is the strongest predictor of success (correlation 0.76), and that explicitly providing the test body in the prompt lifts fidelity from 42% to 60%; (3) finding that global-context tools (RepoGraph code graph, gold execution traces) and prompt-based tracing/reading strategies yield consistent gains over the base setup; and (4) showing that agentic multi-step search outperforms a static single-shot LLM even when the latter is given all gold files, while a restricted 'Edit-and-Execute' tool outperforms full bash access by reducing trajectory length and step-limit failures.

## Results

On the GISTIFY task (25 tests × 5 repositories), the best-performing configuration—Claude-Sonnet-4 with Copilot—achieves 58.7% execution fidelity without execution tools and 61.3% with them, while the weakest (GPT-5-mini with mini-SWE-agent) reaches only 17.1%. GPT-5 produces the most concise outputs, with Line Execution rates of 81–83%, compared to 69–76% for Claude models. On a curated GISTIFY-hard subset (tests with the longest execution traces), performance drops sharply to 21% versus the 43% baseline, confirming that long, multi-file execution traces remain a major bottleneck for current coding LLMs.

## Baselines & Comparisons

The paper evaluates 12 model–framework combinations on GISTIFY rather than proposing a single method against baselines. Claude-Sonnet-4 is the most robust performer, achieving the highest execution fidelity (54–61%) and Line Existence (66–70%) across all three frameworks (mini-SWE-agent, SWE-agent, Copilot). GPT-5, while competitive on execution fidelity (51–61%), stands out for producing the most minimal files, with Line Execution rates 5–10 points above Claude models. SWE-agent (the listed baseline framework) shows mid-range performance: Claude-4 reaches 56.7% fidelity on SWE-agent versus 58.7% on Copilot, while GPT-5-mini drops from 58.0% on Copilot to 30.9% on SWE-agent, highlighting that scaffolding quality matters more for smaller models. Enabling execution tools (bash, pytest) yields only small, consistent gains of 2–15 points, and a restricted 'Edit and Execute' tool actually outperforms full bash access by reducing trajectory length and step-limit failures. On the hardest subset (longest execution traces), even the best configuration drops to 21% fidelity, indicating that no current framework–model pairing reliably solves GISTIFY for complex, multi-file codebases.

## Relation to Prior Work

GISTIFY carves new ground at the intersection of codebase-level understanding benchmarks (SWE-bench, RepoBench) and runtime execution reasoning (CRUXEval, Traced). Unlike SWE-bench-style tasks that can be solved via localized patch retrieval or heuristic shortcuts, GISTIFY requires the model to trace full execution paths across files and compress the result into a single self-contained program. The paper also departs from prior runtime-execution benchmarks, which test whether models can *predict* traces or intermediate states, by requiring them to *reformulate* the program itself. The agentic frameworks evaluated (SWE-agent, mini-SWE-agent, Copilot) were originally designed for issue-resolution tasks and are repurposed here for a fundamentally different objective: program distillation under execution-fidelity constraints.

## Why It Matters / Open Questions

GISTIFY provides a lightweight, automatically constructible evaluation axis for codebase-level understanding that does not depend on GitHub issues or pull requests, making it applicable to arbitrary (including private) repositories. The finding that even frontier models (GPT-5, Claude-4) plateau around 55–60% execution fidelity, and that performance drops sharply on tests with long execution traces, highlights a concrete gap in current coding agents. The gistified files themselves are practical artifacts for debugging, refactoring, and code review. Key limitations include reliance on existing test suites as entrypoints and the unaddressed challenge of non-deterministic execution, both of which the authors flag for future work.
