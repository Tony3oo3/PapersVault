## Problem

Large-scale MoE inference under Expert Parallelism suffers from expert load imbalance, where a few hot experts cause straggler GPUs that determine end-to-end latency. Existing system-level solutions either rely on ineffective heuristics that leave substantial imbalance (EPLB, Lina) or achieve good balance but introduce new bottlenecks because their load-balancing algorithms run synchronously on the GPU critical path (HarMoEny). No prior system simultaneously achieves near-optimal balance and hides its own overhead.

## Input / Output

At runtime, Libra consumes the current layer's hidden states to speculatively execute the next layer's gating function, producing predicted expert IDs for upcoming tokens. Combined with actual routing results, these predictions drive two outputs: a binary expert-placement matrix M_next ∈ {0,1}^{E×G} specifying which experts to replicate to which GPUs, and a rebalanced remote-token assignment that maps each remote token to a specific destination GPU hosting a replica of its assigned expert. The token sharding operates only on remote tokens (those routed to experts not resident on the token's home GPU), while local tokens are processed in-place.

## Method

Libra's core innovation is Two-Stage Locality-Aware Execution, which splits each MoE layer into MoE_local (tokens routed to experts on the same GPU) and MoE_remote (tokens requiring cross-GPU dispatch), then runs MoE_local first to create a time window in which all load-balancing overhead is hidden. For expert replication, a lookahead predictor speculatively executes the next layer's gating on current-layer hidden states (achieving 70–90% accuracy vs. Lina's 11–47%), and a two-phase planning algorithm first duplicates local hot experts to extend the MoE_local window, then iteratively replicates global hot experts from overloaded to underloaded GPUs. For token sharding, an iterative greedy algorithm runs on the CPU, selecting the most overloaded GPU's hottest remote expert and transferring tokens to the least-loaded GPU hosting a replica, re-evaluating global balance after each transfer. Dispatch uses AllGather rather than All2All so that data movement also proceeds in parallel with token sharding, and double-buffered P2P copies via PyTorch SymmetricMemory pipeline expert replication with Grouped-GEMM computation.

## Results

On 8 H200 GPUs, Libra reduces the total MoE layer latency to 9.07 ms (Qwen3MoE, seq len 1024, batch 32), compared to 11.33 ms for Lina and 13.61 ms for vanilla SGLang, yielding up to 19.2% prefill throughput improvement. Libra's speculative-execution predictor achieves 70–90% expert-activation accuracy across datasets, versus 11–47% for Lina's offline lookup table. Under dynamic mixed workloads, Libra maintains an imbalance ratio near 1.0 while baselines see throughput drop sharply as imbalance spikes. End-to-end TTFT reductions reach 27% for Qwen3MoE and 12.7% for GLM-4.5 in large-batch, long-context settings.

## Baselines & Comparisons

Libra outperforms all three baselines across every evaluated dataset and model. Against vanilla SGLang (no load balancing), Libra cuts total MoE layer time from 13.61 ms to 9.07 ms (−33%) by reducing the MoE computation from 10.99 ms to 7.32 ms (local+remote) through effective load balancing. Against Lina, Libra's key advantage is prediction accuracy (70–90% vs. 11–47%), which translates into a much smaller MoE computation time (7.32 ms vs. 8.11 ms) and a lower total (9.07 ms vs. 11.33 ms); Lina also incurs 0.40 ms visible prediction latency that Libra hides. Against EPLB (evaluated only in Figure 8), Libra wins on prefill throughput across all four stress-test datasets, even though EPLB was given a favorable static placement of 8 hot experts profiled on the same dataset. In the dynamic-workload experiment (Figure 9), Libra maintains stable throughput near its peak while Lina's throughput fluctuates and drops sharply as the imbalance ratio spikes, confirming Libra's robustness to shifting token distributions.

## Relation to Prior Work

Libra sits at the intersection of two prior lines of work on MoE load balancing: Lina's proactive expert replication (using offline expert-selection-path lookup tables to prefetch experts for the next layer) and HarMoEny's reactive approach (using exact routing results to drive both replication and a sophisticated token-sharding algorithm). Libra departs from Lina by replacing its offline lookup-table predictor with a runtime speculative-execution mechanism that reuses the current layer's hidden states to predict the next layer's gating decisions, and departs from HarMoEny by offloading its token-sharding algorithm to the CPU and hiding it under a newly introduced Two-Stage Locality-Aware Execution that splits MoE computation into local and remote phases. The net effect is a system that combines Lina's prefetching spirit with HarMoEny's sharding quality while eliminating the critical-path overhead that plagues both.

## Why It Matters / Open Questions

As state-of-the-art MoE models (Qwen3MoE, GLM-4.5, DeepSeek-V3) increasingly forgo auxiliary load-balancing losses to maximize expert specialization, inference-time load imbalance is projected to worsen, making system-level solutions like Libra more critical. The paper's practical impact is demonstrated by a 19.2% prefill throughput gain on 8 H200 GPUs with an imbalance ratio near 1.0, and the open-sourced implementation on SGLang lowers the adoption barrier. Key limitations include evaluation restricted to a single 8-GPU node and the prefill phase only; short-sequence workloads show comparable or slightly degraded performance because the MoE_local window is too short to fully mask CPU overhead. Open questions include multi-node scaling (where AllGather communication volume grows), interaction with decode-phase serving, and whether the speculative-execution predictor degrades under highly non-stationary workloads.
