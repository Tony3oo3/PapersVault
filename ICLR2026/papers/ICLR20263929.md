## Problem

Existing LLM benchmarks evaluate tool calling in simplified, domain-isolated settings or assess single-agent performance, failing to capture the hierarchical orchestration capabilities required for service-ready deployments where a main LLM must decompose multi-domain user requests into coordinated workflows and delegate to specialized sub-LLMs. No prior benchmark explicitly disentangles workflow planning quality from constraint-aware tool execution in realistic, multi-domain service environments with dynamic user revisions and business-rule validation.
![Teaser figure](../imgs/ICLR20263929/cropped_page1_idx0.webp)

## Input / Output

The system receives a natural-language user request within a multi-turn conversation, along with agent capability descriptions (A2A-style agent cards) defining available sub-LLMs and their tool inventories across 17 domains (~100 virtual tools). The main LLM outputs a workflow DAG specifying execution states (pending/running/completed/paused), dependency types (independent/dependent), and step-level agent assignments with refined queries; sub-LLMs then produce either a JSON function call (tool name + typed arguments), an AWAIT_FOR_USER_INPUT signal, or a TOOL_CONSTRAINT_VIOLATION rejection. Evaluation yields three scores: a planning score (1 − normalized Graph Edit Distance over workflow topology and component assignments), call/reject classification accuracy, and function-calling F1 (tool selection, key, and argument sub-scores).

## Method

OrchestrationBench formalizes orchestration as a structured workflow schema represented as a DAG, where each node encodes execution state, dependency relations, and agent assignment, enabling fine-grained structural comparison via Graph Edit Distance (GED) with hierarchical scoring that weights sub-LLM selection errors (0.8) more heavily than status errors (0.2). Tool execution is evaluated in two sequential stages: first, call/reject classification accuracy measures whether the model correctly decides to invoke a tool, request clarification, or flag a constraint violation; second, function-calling F1 (tool name, key, and argument) is computed only over correctly-decided calls, with semantic argument validation performed by an ensemble of three LLM judges (GPT-4.1, Claude Sonnet 4, Gemini 2.5 Flash) achieving Cohen's Kappa 0.63 against human annotators. The dataset is entirely manually annotated by trained annotators with cross-validation by at least three independent reviewers, covering single-domain tasks, multi-domain orchestration, constraint violations with correction, clarification requests, and dynamic mid-conversation revisions. The benchmark is bilingual (English: 219 sessions/706 tool calls; Korean: 222 sessions/730 tool calls), with cultural adaptation for domain-specific services, and is designed as a living, extensible benchmark for new domains and real-world tool integration via MCP.

## Results

On the English dataset, Claude-Sonnet-4 and Qwen3-235B-A22B achieve the highest overall scores (0.842), while Gemini-2.5-Pro leads in planning (0.850) and Claude-Sonnet-4 leads in function calling (0.885). On the Korean dataset, Gemini-2.5-Pro achieves the best overall score (0.839), with Claude-Sonnet-4 maintaining the strongest function calling (0.898). Planning scores exhibit the widest inter-model spread (0.057 for EXAONE-4.0 to 0.850 for Gemini-2.5-Pro in English), whereas function calling scores are relatively compressed (0.534–0.885), confirming that workflow planning is the primary discriminative capability among evaluated models.

## Baselines & Comparisons

The benchmark evaluates 16 LLMs across three orthogonal metrics, revealing distinct model specializations. Gemini-2.5-Pro dominates planning (0.850 English, 0.828 Korean) but trails in call/reject classification (0.724 English), while Claude-Sonnet-4 excels in function calling (0.885 English, 0.898 Korean) and call/reject accuracy (0.868 English). Qwen3-235B-A22B, an open-source MoE model, matches Claude-Sonnet-4's overall score (0.842 English) and surpasses it in C/R accuracy (0.876 vs. 0.868), demonstrating competitive open-source viability. GPT-5 underperforms its predecessors on planning (0.583 vs. GPT-4.1's 0.744) despite comparable function calling, suggesting reasoning-mode configurations may hinder structured workflow generation. Korean open-source models (A.X-4.0, Kanana, EXAONE) show substantially degraded C/R classification (0.48–0.78) compared to their English performance, highlighting language-specific weaknesses in constraint-aware decision-making. Correlation analysis (Table 5) shows planning and C/R are only weakly correlated (r=0.58 English, r=0.45 Korean), confirming that strong planning does not guarantee correct execution decisions.

## Relation to Prior Work

This paper positions itself at the intersection of tool-use benchmarks (BFCL, API-Bank, ToolBench), single-agent task benchmarks (τ-bench, GAIA, UltraTool), and multi-agent coordination evaluations (MultiAgentBench, REALM-Bench), but carves out a distinct niche: hierarchical 'LLM-to-LLM' orchestration where a main LLM decomposes user requests into workflow DAGs and delegates to specialized sub-LLMs, as opposed to the prevailing 'LLM-to-API' paradigm in prior work. It adapts the Agent2Agent (A2A) protocol from Google for its agent-card schema and introduces Graph Edit Distance as a structural planning metric, building on the graph-editing literature. The explicit disentanglement of workflow planning from constraint-aware tool execution (with call/reject classification as an intermediate layer) is a methodological departure from prior benchmarks that typically conflate these or evaluate only end-to-end success.

## Why It Matters / Open Questions

The key practical finding—that function calling performance is relatively consistent across models while planning capability shows substantial variation (e.g., GPT-5 scoring 0.583 vs. GPT-4.1's 0.744 on English planning)—suggests that current training pipelines adequately optimize tool invocation but under-address structured multi-step planning, a gap that would limit real-world agentic deployment. The bilingual (English/Korean) design and 17-domain coverage address a scarcity of evaluation resources for non-English orchestration. However, acknowledged limitations temper the impact: the turn-by-turn evaluation assumes successful execution at each step (potentially inflating scores), tools are virtual rather than real, and the predefined workflow structure limits exploration of fully open-ended planning. Open questions include whether end-to-end evaluation with error propagation would substantially change model rankings, and whether MCP-based real tool integration would reveal additional failure modes.
