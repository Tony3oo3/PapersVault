## Problem

Existing Table-Text QA benchmarks (HybridQA, OTT-QA, TAT-QA, FinQA, MultiHiertt) suffer from three critical flaws: shallow reasoning depth (rarely exceeding two hops, with no support for GROUP BY, HAVING, or aggregation), substantial annotation noise (21–30% error rates across 100-sample audits), and toy-scale tables averaging ~15 rows. These limitations prevent meaningful evaluation of deep multi-hop, tree-structured reasoning over realistic, large-scale heterogeneous data.

## Input / Output

The benchmark presents a QA system with a natural-language question, a set of source tables (e.g., NBA player stats with 45,640 rows, movie metadata with 25,617 rows), and accompanying textual passages (game reports, descriptions). The system must return a free-form answer. During construction, the pipeline consumes a relational database schema plus sample rows and produces executable nested SQL queries whose number of nested predicates equals the target hop count; each query is then paired with its execution result and verbalized into a fluent question, yielding a <question, answer> pair. The reference fact database unifies source tables with grounding tables that store atomic propositions extracted from text as SQL-addressable tuples, so a single query can freely join across structured and unstructured evidence without span-level pointers.

## Method

SPARTA is a three-stage automated construction framework. Stage 1 builds a reference fact database by merging source tables with grounding tables populated via validated corpora (ROTOWIRE) or deterministic table-to-text templates, enforcing primary-foreign key constraints so every text-derived tuple is joinable to at least one source table. Stage 2 generates nested SQL queries using an LLM (Llama-3.1-70B-Instruct) under two novel safeguards: (i) realistic-structure enforcement, which constrains generation to post-order traversal of the query graph so each intermediate subquery is validated before higher-level predicates are composed, and (ii) provenance-based refinement, which, upon an empty result, peels predicates in reverse order, samples a surviving tuple, runs a why-not provenance tool to identify the blocking predicate, and feeds that diagnosis back to the LLM for targeted clause repair. Stage 3 verbalizes each validated query into a natural-language question via AST-ICL (graph-aware few-shot in-context learning over the SQL AST), followed by lightweight human validation (~1,493 minutes for 3,300 queries vs. ~6,600 minutes for HybridQA's equivalent). The pipeline supports four nesting patterns (Type-N, A, J, JA) and explicitly controls query shape (depth/breadth) and analytical operator coverage (WHERE, GROUP BY, HAVING, ORDER BY, LIMIT, aggregation).

## Results

On SPARTA (Oracle), the best-performing method HProPro with GPT-5 achieves an average F1 of 40.4 across NBA, Movie, and Medical domains, while ODYSSEY with GPT-5 reaches 35.6 F1. Both methods suffer dramatic drops compared to their performance on HybridQA: HProPro falls from 70.5 to 40.4 F1 (−30.1 points) and ODYSSEY from 69.5 to 35.6 F1 (−33.9 points). In the harder retrieval setting (SPARTA Retrieval), the best system HELIOS+HProPro w/ GPT-5 attains only 22.6 F1, a 33.4-point drop from its 56.0 F1 on OTT-QA, while the fine-tuned FiE Reader drops from 65.2 to 11.6 F1.

## Baselines & Comparisons

SPARTA is a benchmark, so the 'baselines' are the SOTA Table-Text QA methods evaluated on it. HProPro (Shi et al., ACL 2024) outperforms ODYSSEY (Agarwal et al., NAACL 2025) on SPARTA Oracle by 4.8 F1 (40.4 vs. 35.6 with GPT-5), particularly on large-table domains like NBA and Movie where its program-execution approach handles thousands of rows better than ODYSSEY's graph traversal. However, both methods drop 30+ F1 points relative to their HybridQA scores, exposing that neither handles deep multi-hop tree-structured queries or analytical operations (GROUP BY, HAVING, aggregation) well. In the retrieval setting, HELIOS (Park et al., ACL 2025) paired with HProPro achieves 22.6 F1, substantially outperforming the fine-tuned FiE Reader (Ma et al., ACL 2023) at 11.6 F1 on SPARTA, yet FiE Reader still leads on OTT-QA (65.2 vs. 56.0 F1), showing that fine-tuned readers fail to generalize to SPARTA's more complex, out-of-domain queries. The GPT-5 vs. GPT-3.5-turbo gap (35.6 vs. 20.6 for ODYSSEY; 40.4 vs. 20.3 for HProPro) underscores that even the strongest LLM backbones struggle with SPARTA's depth and scale.

## Relation to Prior Work

SPARTA extends the Table-Text QA task established by HybridQA and OTT-QA, but departs fundamentally from their manual-annotation paradigm by replacing human question construction with an automated SQL-centric pipeline. Its two key technical building blocks are borrowed from distinct literatures: why-not provenance (Dietrich et al., 2022) is repurposed as a query-repair mechanism, and AST-ICL (Al Lawati et al., 2025) handles SQL-to-text verbalisation. The post-order construction strategy draws on classical nested-query optimisation (Kim, 1982), and the grounding-table design leverages the ROTOWIRE text-to-table corpus. Compared to other synthetic benchmark generators (ERBench, TDBench, InPars), SPARTA is distinguished by its cross-modal scope, support for analytical operators (GROUP BY, HAVING, aggregations), and tree-structured multi-hop reasoning rather than linear chains.

## Why It Matters / Open Questions

SPARTA provides the first large-scale, low-noise Table-Text QA benchmark that meaningfully tests deep multi-hop reasoning, analytical operations, and cross-modal integration over tables with thousands of rows—addressing three concrete gaps (shallow questions, 21–30% annotation error rates, toy-scale tables) that have limited the field's ability to diagnose model weaknesses. The 30+ F1-point drop for SOTA systems, combined with fine-grained failure analyses (negation scoping, range reasoning, cross-modal alignment), gives the community actionable diagnostic signals. Open questions include whether the SQL-centric construction captures the full diversity of natural question patterns, how the benchmark scales to truly massive databases, and whether the planned multimodal extension (images/video → grounding tables) preserves the same guarantees.
