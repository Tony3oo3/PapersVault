## Problem

While code data has been shown to improve LLM reasoning, it remains unclear which specific properties of code—syntactic regularity, structural abstractions, or linguistic style—are actually responsible for these gains. This paper addresses that gap by asking: can we causally disentangle the structural and semantic contributions of code to reasoning performance through controlled, data-centric perturbations?

## Input / Output

The framework consumes 120K parallel instruction-response pairs in natural language and in each of ten programming languages (Java, JavaScript, PHP, Python, C#, TypeScript, C, C++, Go, Rust), with code responses generated by GPT-4o-mini and validated via per-language syntax/compilation checks (82.59% average pass rate). Perturbed variants modify only the response side while keeping instructions fixed, so the model always sees the same task prompt but learns from structurally or semantically altered solutions. Evaluation outputs span accuracy/exact-match scores on NL and math benchmarks and LLM-as-judge Likert scores (1–10) on code generation, with the judge first generating an instance-specific rubric before scoring.

## Method

The paper constructs a systematic perturbation framework with two families of transformations applied to code responses: rule-based edits (whitespace removal, variable renaming to var_i placeholders, keyword replacement with nonsense or non-English tokens, comment removal, and local/global comment swapping) and generative rewrites via GPT-4o-mini (pseudocode, Mermaid flowcharts, step-by-step natural-language procedures, code in a fictional language, comment enhancement, and comment obfuscation). These 13 perturbations are then analyzed along four orthogonal axes—structural vs. semantic disruption, explicitness of code structure, relative information density (token count ratio), and human interpretability—to isolate which code properties drive reasoning gains. Models from five families (Qwen3, LLaMA-3, Gemma3, OLMo2, SmolLM2) at eight scales (0.36B–8B) are fine-tuned via SFT (BF16, 2 epochs, batch 64, lr 1e-5, cosine schedule, DeepSpeed ZeRO-3) on each dataset variant, yielding 3,331 experiments. Key findings include that structural perturbations hurt math and code tasks more than semantic ones, that pseudocode and flowcharts can match or exceed raw code for non-generation tasks, that token-reduced encodings retain performance, and that lower-level languages (Java, Rust, C, C++) disproportionately benefit mathematical reasoning.

## Results

Across 14 model bases (5 families, 8 scales), code fine-tuning (code-ft) or mixed fine-tuning (mixed-ft) achieves the best performance on 64% of natural language tasks, 86% of math and code understanding tasks, and all code generation tasks. On the LLM-as-judge code generation evaluation (Qwen3-4B, Python), code-ft scores 8.51/10 mean versus 7.57 for zero-shot and 7.19 for NL-only fine-tuning. Structural perturbations (e.g., whitespace removal, pseudocode) degrade performance more severely than semantic perturbations (e.g., comment swapping, variable renaming), with the gap widening as model scale increases. Lower-level languages (Java, Rust, C, C++) consistently outperform high-scripting languages (Python, PHP, JavaScript, TypeScript) on math tasks, while Python leads on NL tasks.

## Baselines & Comparisons

The paper's primary comparison is across four training configurations: zero-shot (no fine-tuning), NL-only fine-tuning, code-only fine-tuning, and 50-50 mixed fine-tuning. Code-ft consistently outperforms nl-ft across all task categories, with the largest gaps on math and code generation (e.g., 8.51 vs. 7.19 mean judge score on code generation). Mixed-ft is competitive with code-ft on NL tasks but generally trails on math and code, suggesting that higher code proportions are beneficial. Among perturbations, structural edits (whitespace removal, pseudocode, flowcharts) cause larger performance drops than semantic edits (comment swapping, variable renaming, keyword replacement), particularly on math and code tasks. Notably, low-interpretability variants (comment obfuscation, imaginary language) often match or even surpass medium-interpretability ones, indicating models exploit surface-level regularities rather than true semantic understanding. For language-specific ablations, Python leads on NL tasks while Java and Rust rank among the top for math, and multi-language code-ft outperforms any single-language fine-tuning on code generation.

## Relation to Prior Work

This paper extends the established finding that code data improves LLM reasoning (Fu & Khot, 2022; Ma et al., 2023; Zhang et al., 2024b) by introducing a systematic, data-centric perturbation framework to causally isolate which specific code properties drive those gains. It draws on the data-impact literature (Longpre et al., 2024; Li et al., 2023) for its controlled experimental design, and is closest in spirit to Lam et al. (2025, CodeCrash), which stress-tests LLMs under code perturbations but focuses on model robustness rather than training-data design. The 'structure over content' hypothesis from Li et al. (2025) on demonstrations informs the paper's central structural-vs-semantic axis, but this work generalizes that insight to code-specific training data across ten programming languages and five model families.

## Why It Matters / Open Questions

The paper provides actionable, fine-grained guidance for practitioners designing training data to enhance reasoning: structural integrity matters more than semantic fidelity, compact abstractions (pseudocode, flowcharts) can substitute for full code, and lower-level languages disproportionately benefit math reasoning. Key limitations include the restriction to small-to-mid-size base models (≤8B), a perturbation suite that does not cover code complexity or data diversity, and a relatively small-scale human verification (390 samples). Open questions include whether these trends persist in larger instruction-tuned models, whether the findings transfer to chain-of-thought or preference-optimization settings, and whether the observed robustness to corrupted code reflects genuine understanding or mere exploitation of surface regularities.
