## Problem

Existing benchmarks for tool-augmented LLMs suffer from two critical limitations: they are vulnerable to data contamination through pretraining overlap and test-time web search, and they offer little fine-grained control over task difficulty dimensions such as function dependency depth, the number of required calls, and the type-compatibility of irrelevant distractor functions. This makes it difficult to isolate which structural factors most impact model performance in multi-step function calling.

## Input / Output

The LLM agent receives a list of function schemas (each with a randomly generated name, input parameters annotated with type and subtype, a single output variable, and a natural-language description), a set of initial input variables with known 3-digit integer values, and a target variable name. Functions are linked by type-and-subtype matching rather than variable names, so the agent must infer dependencies from signatures alone. The agent iteratively issues function calls (multiple per step allowed) and receives outputs until it stops; the final parsed output is checked against the ground-truth target value. Each function returns the correct output only when given exact expected inputs, otherwise returning a random incorrect value to simulate realistic API failures.

## Method

FuncBenchGen casts multi-step function calling as traversal over a hidden function-dependency DAG and generates all function sets and tasks at evaluation time to guarantee contamination-free evaluation. Difficulty is controlled via four parameters: the number of core nodes (required functions), the dependency depth d, the number of connected irrelevant nodes (CINs, which share type-compatible variables with core functions), and the number of disconnected irrelevant nodes (DINs). Graph generation proceeds in two stages: first, a valid path of length d is created and remaining core nodes are added while preserving acyclicity and depth constraints; second, CINs are attached as children of random core nodes and DINs are added as isolated nodes with at most ⌊n_dis/2⌋ internal edges. The paper also identifies that the dominant failure mode across all models is state-tracking errors (using unknown or stale variable values), and proposes a lightweight mitigation that appends the full list of currently known variable values to each function's return, yielding substantial success-rate gains (e.g., 62.5% → 81.3% for GPT-5).

## Results

GPT-5 achieves the highest success rates across all settings: 72.5% with 5 core nodes, 38.2% with 10, and 15.0% with 20, substantially outperforming the next-best model Gemini-2.5-Pro (46.5%, 14.4%, 6.0%). General-purpose models (GPT-4.1, GPT-4.1-mini) drop to near-zero success rates at 10+ core nodes. The most common failure mode across all models is 'Value Not Yet Known' (66.8%–81.3% of errors), and a simple mitigation that restates all known variable values after each function call improves GPT-5's success rate from 62.5% to 81.3% on 5-core-node tasks.

## Baselines & Comparisons

This is a benchmark paper, so the primary comparisons are among seven LLMs evaluated on the same generated tasks. Reasoning-optimized models (GPT-5, GPT-5-mini, Gemini-2.5-Pro, Gemini-2.5-Flash, Qwen3) consistently outperform general-purpose models (GPT-4.1, GPT-4.1-mini) at every core-node size; for example, with 5 core nodes GPT-5 reaches 72.5% versus 12.0% for GPT-4.1, and with 20 core nodes GPT-5 still achieves 15.0% while GPT-4.1 drops to 0.2%. Among reasoning models, GPT-5 leads by a wide margin (72.5% vs. 46.5% for Gemini-2.5-Pro at 5 core nodes), but all models degrade sharply as sequence length grows. The paper also compares a baseline prompting setup against a mitigation strategy (restating all known variable values after each call): this simple change lifts GPT-5 from 62.5% to 81.3% on 5-core-node tasks and yields similar gains for GPT-5-mini and Gemini-2.5-Pro, while smaller models (Gemini-2.5-Flash, Qwen3) see only marginal or slightly negative effects. Connected irrelevant functions (CINs) degrade performance for all models more than disconnected ones, and lower dependency depth (star-like graphs) yields substantially higher success rates than deeper chain-like structures.

## Relation to Prior Work

This paper carves new ground in function-calling evaluation by combining two ideas that had not been jointly applied to this domain: contamination-free synthetic task generation (inspired by LiveBench and GSM-Symbolic) and DAG-based controllability of task structure. Unlike prior benchmarks (API-Bank, BFCL, ToolBench, ComplexFuncBench, LongFuncEval) that rely on static, hand-curated API sets with limited difficulty knobs, FuncBenchGen formulates multi-step function calling as traversal over a generated function-dependency DAG, enabling independent control over graph size, dependency depth, and the type/connectivity of distractor functions. The conceptual departure is treating the evaluation problem as a graph-construction problem rather than a curation problem, which simultaneously solves contamination and controllability in one mechanism.

## Why It Matters / Open Questions

The framework provides the first systematic way to isolate which structural factors (depth, branching, distractor connectivity) most degrade LLM function calling, yielding actionable insights for both model developers and agent-system designers. The finding that a trivially simple mitigation—restating known variable values after each call—recovers ~19 percentage points for GPT-5 suggests that much of the observed failure is a context-management problem rather than a reasoning deficit, which refracts on how agent scaffolds should be designed. Open questions include whether these findings transfer to tasks with conditional logic, iteration, or non-deterministic tool outputs, and whether the synthetic DAG abstraction captures the semantic ambiguity of real-world API ecosystems.
