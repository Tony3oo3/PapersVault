## Problem

Existing prompt-program interoperability systems use isolated program state, where prompts are evaluated in a separate environment and programmers must manually serialize program data, define output schemas, reify LLM responses, and implement control-flow bridging code. This manual work obscures core program logic and is error-prone (e.g., asking the LLM to regenerate entire data structures invites hallucination). The paper asks whether a programming abstraction can eliminate this intermediary by letting prompts directly read, write, and manipulate the host program's live state.

## Input / Output

The system consumes a Python source file in which natural-language prompts are embedded as triple-quoted strings tagged with the 'prompt' language identifier; prompts reference in-scope variables via <var> (read) and <:var> (write) syntax. At runtime, the LLM agent inspects the live program state (variable values, object types, attributes) and issues a sequence of effects—eval (evaluate a Python expression), exec (execute a Python statement block), and control-flow primitives (break, continue, return, raise, done)—which the handler executes against the actual Python interpreter's scope, heap, and control state. The output is the mutated program state itself: updated variables, in-place object mutations (e.g., adding an edge to a graph dictionary), and control-flow transitions (e.g., breaking out of a loop), with no serialized intermediate representation.

## Method

The paper formalizes a general schema called the Natural Function Interface (NFI), built on algebraic effects and handlers, that specifies three components: NFI values (data types crossing the prompt-program boundary), NFI effects (distinguished requests the prompt emits to the host), and NFI handlers (host-side implementations that fulfill or cancel those requests). Shared program state is then specified as a particular NFI with effects for shared scopes (Lookup, Assign), shared heap (Deref, Ref, Set), and shared control state (Goto to program labels), where the Goto handler notably does not resume prompt evaluation, thereby implementing control flow. NIGHTJAR implements this NFI in Python by specializing the general effects into Eval/Exec (replacing the fine-grained scope/heap effects) and Python control-flow primitives (replacing Goto), and performs a source-code transformation that installs try-except blocks as program labels so the LLM can trigger break/continue/return/raise. An LLM agent evaluates each prompt by issuing a trace of effects; the handler enforces safety constraints (only <var>-denoted variables are readable, <:var>-denoted variables must be defined before termination) and applies optimizations including eager variable loading and effect-trace caching to reduce runtime overhead.

## Results

On SPSBench (25 programs), NIGHTJAR achieves 0.85±0.03 average pass rate with Claude-Sonnet-4 and 0.78±0.03 with GPT-4.1, outperforming Manual Implementation (0.78±0.03 and 0.74±0.03 respectively) by +4–19%. Shared program state programs use 25.1 lines of code on average versus 42.0 for manual implementations, a 39.6% reduction. The runtime tradeoff is 25.9s (Sonnet-4) and 19.6s (GPT-4.1) for NIGHTJAR versus 8.0s and 4.5s for Manual Implementation, a 0.4–4.3× overhead.

## Baselines & Comparisons

NIGHTJAR outperforms all three baselines on pass rate for both LLMs. Against Manual Implementation (isolated program state with Pydantic schemas), NIGHTJAR gains +7 points (0.85 vs 0.78) on Sonnet-4 and +4 points (0.78 vs 0.74) on GPT-4.1. Against Manual Implementation with Code Interpreter tools, NIGHTJAR gains +19 points (0.85 vs 0.66) on Sonnet-4 and +6 points (0.78 vs 0.72) on GPT-4.1, while also running 1.4× faster (25.9s vs 36.8s on Sonnet-4). The language-agnostic NIGHTJAR (Baseline) without Python specialization underperforms Manual Implementation on both LLMs (0.60 vs 0.78 on Sonnet-4; 0.61 vs 0.74 on GPT-4.1), confirming that Python-specific features (first-class functions, abstract methods) are necessary for competitive accuracy. The key tradeoff is runtime: NIGHTJAR is ~3× slower than Manual Implementation but ~1.4–2.6× faster than Manual Implementation (Code Interpreter) and ~2× faster than NIGHTJAR (Baseline).

## Relation to Prior Work

This paper builds on the algebraic effects and handlers formalism (Bauer & Pretnar 2015; Plotkin & Pretnar 2013) to define a language-agnostic schema called the Natural Function Interface (NFI), which formalizes how prompts interact with host program state. It departs from the dominant 'isolated program state' design used by most prior prompt-program interoperability systems (LangChain, DSPy, Guidance, TypeChat, etc.), where programmers must manually serialize data to the LLM and reify outputs back into program objects. The paper also situates itself in the long history of language interoperability and literate programming, but is the first to formalize a 'shared program state' abstraction in which prompts directly read/write variables, mutate heap objects in-place, and manipulate control flow via a Goto effect that the handler fulfills without resuming prompt evaluation.

## Why It Matters / Open Questions

The shared program state abstraction eliminates ~40% of boilerplate serialization/reification code while achieving comparable or higher task accuracy, suggesting that delegating state-management reasoning to an LLM agent is a viable alternative to hand-written glue code. However, the safety implications are significant: prompts gain direct read/write access to program memory, blurring the isolation boundary that prior systems maintain, and the paper acknowledges its partial safety mechanisms are incomplete. Open questions include developing richer safety mechanisms (drawing on OS-level isolation and ownership literature), reducing the 0.4–4.3× runtime overhead through better effect scheduling and caching, and building debugging/testing tooling for a programming model where natural-language instructions have side effects on live program state. The evaluation is limited to 25 programs and two LLMs, so generalizability remains to be established.
