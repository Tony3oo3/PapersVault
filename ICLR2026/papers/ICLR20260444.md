## Problem

Existing code benchmarks (SWE-bench, SWT-bench, HumanEval) evaluate AI agents on isolated development tasks—primarily Python code generation and issue resolving—while the operational stages of the DevOps cycle (build/configuration, runtime monitoring, and cross-stage pipeline coordination) remain entirely unbenchmarked. No prior benchmark provides real-world repositories, dynamic execution environments with tool-calling interfaces, and sequential multi-stage workflows that mirror how DevOps engineers actually work across the full software lifecycle.

## Input / Output

Each task provides a containerized Docker environment containing a Java or Go repository at a specific commit state (git metadata stripped to prevent solution leakage), a natural language task description, and terminal access to stage-specific tools (e.g., Maven/Gradle for build, top/free/ps/netstat for monitoring, git/grep/sed for issue resolving). Outputs are stage-specific: unified diff patches for issue resolving, structured single-line diagnostic reports naming the anomaly type for monitoring, complete build configuration files for implementation tasks, and regression test files in JUnit/pytest format for test generation. Evaluation is binary per task (pass/fail via automated pytest scripts checking fail-to-pass test transitions or exact anomaly-type matching), aggregated into stage-level success rates across 704 tasks and 18 end-to-end pipeline tasks.

## Method

DEVOPS-GYM is constructed through a semi-automated pipeline combining real-world GitHub issue mining (following BugSwarm and Multi-SWE-bench protocols) with expert-injected synthetic anomalies, yielding 704 tasks across 30+ Java and Go repositories. A key technical contribution is the contamination prevention protocol: 20 code snippets per repository are sampled and subjected to prefix-completion analysis using five similarity metrics (Levenshtein distance, token matching, first-mismatch position, longest common substring, BLEU), with repositories exceeding 20% high-risk snippet rate excluded. Task reproduction for monitoring and build stages required 10+ hours of expert engineering per task to reconstruct environments, dependencies, and trigger conditions. The evaluation environment is standardized in terminal-bench format with tool-calling interfaces, and the benchmark is evaluated by running three agentic frameworks (OpenHands, mini-SWE-Agent, Claude Code) paired with five LLMs (Claude-4-Sonnet, o4-mini, Gemini-2.5-Pro, DeepSeek-V3.1, Qwen3-Coder-30B) across all four stages plus 14 end-to-end pipeline tasks that chain build→monitor→resolve→test sequentially, where failure at any stage terminates the pipeline.

## Results

On DEVOPS-GYM, the best-performing agent (Claude Code with Claude-4-Sonnet) achieves 51.85% on Build & Configuration, 20.56% on Monitoring, 23.87% on Issue Resolving, and 13.87% on Test Generation. Within the OpenHands framework, Claude-4-Sonnet leads all other models (o4-mini, Gemini-2.5-Pro, DeepSeek-V3.1, Qwen3-Coder-30B) across every stage, with the largest gap on Build & Config (42.59% vs. 24.07% for o4-mini). All agents achieve 0% success on the 14 end-to-end pipeline tasks that chain all four DevOps stages sequentially, revealing a complete inability to maintain context across cascading workflows.

## Baselines & Comparisons

Claude Code with Claude-4-Sonnet dominates all other agent-framework combinations across every DevOps stage, achieving 51.85% on Build & Config versus 42.59% for OpenHands+Claude-4-Sonnet and 29.62% for mini-SWE-Agent+Claude-4-Sonnet. The framework gap is especially stark on Monitoring (20.56% vs. 14.70% vs. 2.91%) and Test Generation (13.87% vs. 11.61% vs. 0.98%), indicating that sophisticated tool-calling architecture matters more than the underlying LLM for agentic DevOps tasks. On Issue Resolving, OpenHands+Claude-4-Sonnet and Claude Code tie at 23.87%, both far exceeding mini-SWE-Agent (5.16%) and Aider (9.67%). Within OpenHands, Claude-4-Sonnet outperforms o4-mini by 18.52 points on Build & Config and 15.05 points on Issue Resolving, while Gemini-2.5-Pro leads on Monitoring (11.76%) among non-Claude models. The paper also highlights a cross-language gap: the same OpenHands+Claude-4-Sonnet configuration achieves 70.4% on SWE-bench-Verified (Python) but drops to 23.87% on DEVOPS-GYM's Java/Go tasks, suggesting Python-centric training data limits generalization to compiled-language ecosystems.

## Relation to Prior Work

This paper extends the SWE-bench/Multi-SWE-bench line of work on issue resolving and the SWT-bench line on test generation by (1) shifting from Python to Java and Go, (2) adding two previously unbenchmarked DevOps stages—build/configuration (drawing on BugSwarm's CI-log mining methodology) and runtime monitoring—and (3) chaining all four stages into end-to-end pipeline tasks. Unlike prior benchmarks that evaluate isolated coding or testing tasks in synthetic or single-language settings, DEVOPS-GYM provides a tool-augmented dynamic execution environment with standardized terminal-bench interfaces, explicitly designed for agentic systems that must perform multi-step planning and tool calling across a full DevOps workflow.

## Why It Matters / Open Questions

The benchmark reveals that even the strongest current agents (Claude Code + Claude-4-Sonnet) achieve only ~14–52% on individual stages and 0% on end-to-end pipeline tasks, exposing a fundamental gap between LLM coding capabilities and real-world DevOps automation. The dramatic cross-language performance drop (70.4% on SWE-bench-Verified Python → 23.87% on Java/Go) and near-zero monitoring success challenge the assumption that strong code-generation ability transfers to operational tasks requiring dynamic system observation and domain-specific tool use. Open questions include whether specialized training on DevOps tool-use trajectories can close the monitoring gap, whether the cross-language deficit is purely a data-coverage issue, and how agents can maintain coherent context across multi-stage pipelines. Limitations include coverage of only two languages and 30+ projects, and the reliance on expert-injected synthetic anomalies for monitoring.
