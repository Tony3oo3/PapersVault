## Problem

Automated GPU kernel optimization remains difficult because the design space is highly irregular and architecture-dependent, yet existing LLM-based approaches treat models as single-shot generators or naive linear-refinement tools that get trapped in local optima. The paper identifies three specific gaps: (1) no exploration-exploitation balance over prior attempts, (2) a monolithic agent that conflates planning, coding, and debugging, and (3) a planning-implementation gap where LLMs propose correct high-level strategies but fail to produce valid low-level CUDA code.

## Input / Output

The system takes a PyTorch reference model as the root of a search tree and iteratively consumes profiling feedback (compile status, unit-test correctness, CUDA-event wall-clock runtime) from each evaluated candidate. At each step, a node is selected for expansion and agent-specific context windows are assembled from subsets of the tree (children, siblings, cousin nodes, and a global top-r leaderboard). The final output is a functionally equivalent CUDA kernel (compiled via torch.utils.cpp_extension.load_inline) that minimizes wall-clock runtime; intermediate outputs include grounded instructions with explicit <<IMPROVE BEGINS>>/<<IMPROVE ENDS>> span anchors marking the exact code regions to modify.

## Method

STARK decomposes kernel optimization into three specialized LLM agents—plan (Claude Sonnet 4, τ=0.8), code (τ=0.1), and debug (τ=0.1)—that operate over a persistent search tree T. The plan agent emits grounded instructions that wrap target code spans in machine-checkable anchors, forcing the code agent to resolve each anchor into concrete CUDA rather than free-form editing; this tightens plan-code alignment and reduces hallucinated guidance. Each agent receives a dynamically rebuilt context window tailored to its role: the plan agent sees its own children plus top-r global leaders for ambition calibration and capability estimation, the code agent additionally sees cousin nodes (children of siblings) to transfer micro-optimizations and avoid repeated failures, and the debug agent is restricted to siblings for local structural fixes. Node selection uses an adapted ε-greedy policy (ε=0.3) with root throttling (max 5 direct children), dead-branch pruning (ineligible after 3 consecutive failing children), and leaf-biased exploration to counteract the root-dominance and frequent-failure characteristics of kernel optimization. The entire loop is implemented in LangGraph and runs for a fixed budget B=30 attempts per task.

## Results

On KernelBench (B=30 attempts, Claude Sonnet 4), STARK achieves 100% success rate across all three difficulty levels, compared to 57.1–100% for the Sampling Agent and 67.5–100% for the Reflexion Agent. Against Torch Eager, STARK delivers 3.03×, 2.69×, and 1.58× average speedup on Levels 1, 2, and 3 respectively, while the Reflexion Agent actually produces kernels *slower* than the baseline at Level 2 (0.88×) and Level 3 (0.79×). Relative to the baseline agents themselves, STARK achieves up to 16× wall-clock speedup over Reflexion (L2) and 10.7× over Sampling (L1).

## Baselines & Comparisons

STARK dominates both baselines on every metric across all three KernelBench levels. Against the Sampling Agent (best-of-K single-shot generation), STARK improves success rate from 57.1%→100% (L1) and 87.5%→100% (L2), and boosts speed from 0.81×→3.03× (L1) and 1.06×→2.69× (L2) relative to Torch Eager; the Sampling Agent's kernels are actually *slower* than the unoptimized baseline at L1 and L3. Against the Reflexion Agent (iterative self-refinement), STARK closes the correctness gap (100% vs 67.5% success at L3) and, more critically, reverses the performance deficit: Reflexion produces kernels that run slower than Torch Eager at L2 (0.88×) and L3 (0.79×), while STARK achieves 2.69× and 1.58× speedups respectively. In wall-clock terms, STARK's best kernels are up to 16× faster than Reflexion's best (L2) and 10.7× faster than Sampling's best (L1). Even when given 4× more attempts to match STARK's API budget, neither baseline recloses the gap (Table 6), confirming that the multi-agent workflow and strategic search—not raw compute—are the key differentiators.

## Relation to Prior Work

STARK extends the LLM-agent paradigm for GPU kernel optimization established by KernelBench (Ouyang et al., 2025), which introduced the benchmark and two baseline agents (Sampling and Reflexion) that treat the LLM as either a single-shot generator or a linear iterative refiner. The paper departs from this monolithic-agent design by decomposing the workflow into specialized plan/code/debug roles with distinct temperature settings, and introduces grounded instruction (span-anchored edits) and dynamic context windows as coordination mechanisms not present in prior kernel-optimization agents. The strategic search over a persistent tree memory with an adapted ε-greedy policy replaces both best-of-K sampling and myopic iterative refinement, drawing conceptually on MCTS and evolutionary search but finding that a simpler adapted rule performs best under the domain-specific challenges of root dominance and frequent compilation failures.

## Why It Matters / Open Questions

GPU kernel optimization is a bottleneck for AI infrastructure efficiency, and STARK demonstrates that structured multi-agent LLM workflows can produce kernels up to 16× faster than prior LLM-based approaches while maintaining 100% correctness on evaluated tasks. However, the evaluation is limited to a representative subset of KernelBench with a single base LLM (Claude Sonnet 4), and correctness rates remain moderate (35–61%), indicating that code-synthesis fidelity is still the dominant bottleneck. Open questions include whether the framework generalizes to diverse hardware architectures, broader operator classes, and cross-kernel scheduling, and whether agent-specific post-training (e.g., fine-tuning the code agent) can close the remaining gap between high-level planning and low-level CUDA implementation.
