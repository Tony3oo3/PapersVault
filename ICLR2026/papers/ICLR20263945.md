## Problem

State-of-the-art LLM-based retrievers employ symmetric dual-encoders that run full LLM forward passes on both queries and documents. While documents can be pre-encoded and indexed offline, queries arrive in real-time, making the deeply parameterized query encoder a severe bottleneck for online serving throughput and resource consumption. No prior work has specifically addressed this online efficiency challenge for LLM-based retrievers, leaving a gap between retrieval quality and deployment feasibility.

## Input / Output

At inference, the method consumes a raw search query (tokenized into token IDs) and a pre-built document index consisting of dense vectors (served via Faiss) and sparse vectors (served via Anserini/Lucene). The query side requires only a single [V, H] embedding lookup matrix in RAM for dense encoding and simple token counting for sparse encoding—no GPU or Transformer forward pass is needed. The output is a ranked document list scored by linearly interpolated dense and sparse similarity scores, with the dense query vector computed as the mean of looked-up token embeddings.

## Method

LightRetriever breaks the symmetry between query and document encoders by retaining a full-sized LLM on the document side while reducing query encoding to at most an embedding lookup. For dense retrieval, during training each query token is independently passed through the full LLM (with a task instruction prefix) to obtain token-level representations via last-token pooling, and the query vector is the average of these token vectors; these per-token embeddings are then cached into a single [V, H] matrix so that online inference is just a lookup-and-average operation. For sparse retrieval, the query vector is simply the token count vector (no learnable encoder), while the document vector is produced by projecting the LLM's final-layer hidden states through its own language modeling head, applying ReLU and log-saturation, then max-pooling over the sequence dimension, with a FLOPs regulator for sparsification. Both dense and sparse branches are trained end-to-end with listwise contrastive loss, and their normalized scores are linearly interpolated for the final hybrid retrieval score.

## Results

LightRetriever-Llama3.1-8b achieves 54.4 nDCG@10 on BeIR (15 English datasets) and 63.0 nDCG@10 on CMTEB-R (8 Chinese datasets), retaining ~95% of the full symmetric Llama3.1-8b retriever (56.8 / 67.6). On the efficiency side, query encoding drops from 109.5 s (full Llama-8b) to 0.041 s (LightRetriever), a ~2,650× speedup, while end-to-end throughput rises from 549 QPS to 6,999 QPS (~12.7×) on a single A800 GPU. Across all six backbone LLMs tested (Llama-1B/3B/8B, Qwen-1.5B/3B/7B), the average performance retention relative to the full symmetric counterpart is approximately 95%.

## Baselines & Comparisons

LightRetriever-Llama3.1-8b (54.4 BeIR) substantially outperforms all non-LLM baselines: BGE-m3 dense+sparse (49.6, +4.8), SPLADE-v3 (50.2, +4.2), USTAD (44.2, +10.2), and BM25 (41.7, +12.7). Against the two strongest LLM-based retrievers, LightRetriever trails E5-Mistral-7b (56.9) by 2.5 and LLM2Vec-Llama8b (56.6) by 2.2 on BeIR, but reverses the gap on CMTEB-R, where LightRetriever-Llama3.1-8b (63.0) beats both LLM2Vec (54.4, +8.6) and E5-Mistral (61.8, +1.2). The largest remaining gap is to the full symmetric dual-encoder of the same backbone (−2.4 BeIR, −4.6 CMTEB-R for Llama-8b; −2.8 BeIR, −3.6 CMTEB-R for Qwen-7b), which the paper attributes to the removal of deep token interactions on the query side. On category-wise BeIR analysis, retention stays above 93% for general relevance tasks (Bio-Medical IR, Argument Retrieval, Fact Checking, Duplicate QA, Passage Retrieval) but drops to 87–89% on reasoning-intensive tasks (Domain-specific QA, Entity Retrieval, Citation Prediction). In speed, LightRetriever's 0.041 s query encoding is ~2,650× faster than full Llama-8b (109.5 s) and even ~57× faster than a single-layer Llama-8b query encoder (2.34 s), while the 1st-layer baseline underperforms LightRetriever by 4.3 (BeIR) and 8.6 (CMTEB-R) in nDCG@10.

## Relation to Prior Work

This paper extends the line of asymmetric dual-encoder retrieval (KALE, USTAD, Wang & Lyu) that distills or prunes query encoders, but pushes the asymmetry to an extreme: instead of retaining a few Transformer layers on the query side, LightRetriever eliminates all deep modeling at inference time, reducing query encoding to a single embedding lookup. It builds on LLM-based symmetric retrievers (E5-Mistral, LLM2Vec, NV-Embed) for the document-side encoder and on SPLADE-style sparse retrieval for the complementary sparse signal. The key conceptual departure from prior asymmetric work is the hypothesis—motivated by Mackenzie et al.'s finding that semantic capacity can reside entirely on the document side—that queries need no Transformer computation at all at serving time, while still requiring full LLM modeling during training to learn effective token embeddings.

## Why It Matters / Open Questions

The practical impact is substantial: a 1000× speedup in query encoding and 10× end-to-end throughput with only ~5% average performance loss makes LLM-based retrieval deployable in latency-sensitive, high-throughput production settings that were previously infeasible. The approach is simple (one [V,H] matrix in RAM) and generalizes across Llama and Qwen families at multiple scales, suggesting broad adoptability. However, the paper clearly delineates its limits: reasoning-intensive retrieval (BRIGHT, CoIR) and complex compositional queries (e.g., Git operations) degrade noticeably, and the method has not been validated on non-LLM backbones like BERT. Open questions include whether intermediate query-side computation (e.g., a single attention layer) could recover the remaining 5% without sacrificing most of the speedup, and whether the approach transfers to multilingual or code retrieval settings.
