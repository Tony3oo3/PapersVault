## Problem

Existing environment configuration benchmarks for software engineering agents only report end-to-end build/test success, making it impossible to identify which specific capabilities (planning, perception, feedback, action) an agent lacks or at which stage it fails. Additionally, constructing high-quality task instances is bottlenecked by the scarcity of reliably buildable repositories and the heavy manual effort required for annotation, limiting the scale and rigor of evaluation.
![Teaser figure](../imgs/ICLR20263867/cropped_page1_idx0.webp)

## Input / Output

Each task instance provides a README with 1–10+ synthetically injected errors, the repository directory structure, and a base Docker image with minimal prerequisites (Python, Conda). The agent must output a structured JSON error analysis (type, description, fix suggestion per detected error) followed by a corrected bash shell script. Evaluation compares the JSON predictions against gold-standard annotations (error type, description, candidate fixes, golden answer) using precision/recall/F1 and an LLM-as-judge for description and fix accuracy, while the shell script is executed in Docker to measure end-to-end Pass@1 (build success + unit test pass + clean exit).

## Method

EnConda-Bench introduces an automated data construction pipeline that selects high-quality Python repositories (≥10 stars, ≥1000 commits, ≥10 closed issues, manually verified buildable), then uses Claude-4-sonnet and Gemini-2.5-pro to minimally edit each README by injecting exactly two errors from a six-category taxonomy (dependency, syntax, file path, logical order, version compatibility, other) with structured JSON annotations. Injected errors are validated by having GPT-4.1-mini generate a shell script strictly following the erroneous README and executing it in Docker; errors that do not cause failure are discarded, followed by LLM-assisted filtering and human review (98.5% agreement), yielding 4,201 READMEs with 9,471 errors across 323 repositories. The evaluation suite performs process-level trajectory analysis by extracting error type judgments, descriptions, and fix suggestions from the agent's output and scoring them against gold labels, complemented by end-to-end executability testing. This design decouples the four agent capabilities—planning (devising configuration steps), perception (localizing error causes), feedback (analyzing and formulating repairs), and action (executing corrections into a working shell script)—enabling targeted diagnosis of where agents break down rather than only reporting aggregate pass rates.

## Results

On EnConda-Bench (4,201 task instances), the best end-to-end Pass@1 is 22.9% (Repo2Run + Claude-4), while the best error-type F1 is 66.4% (SWE-Agent + GPT-5-Codex). Zero-shot LLMs achieve high recall (65.8–90.6%) but low precision (33.2–40.5%) and very poor Pass@1 (1.5–6.3%), indicating broad but noisy error perception. The persistent gap between fix-suggestion accuracy (up to 47.3%) and Pass@1 (up to 22.9%) reveals that agents struggle to translate correct diagnoses into valid execution actions.

## Baselines & Comparisons

Zero-shot LLMs serve as the weakest baseline: they achieve high recall (up to 90.6% for GPT-4.1) but low precision (33.4%) and Pass@1 of only 1.5–6.3%, confirming that raw language modeling without agentic scaffolding is insufficient for environment configuration. SWE-Agent and OpenHands (code agents) improve F1 by ~8–12 points over zero-shot and raise Pass@1 to 7–11.5%, with SWE-Agent + GPT-5-Codex achieving the best error-type F1 (66.4) and description accuracy (58.7). INSTALLAMATIC, despite being purpose-built for Python environment setup, underperforms both code agents on all metrics (best Pass@1: 7.9%), suggesting its curated-context approach does not generalize well to multi-error READMEs. Repo2Run delivers the largest end-to-end gains, with Repo2Run + Claude-4 reaching 22.9% Pass@1 and 47.3% fix accuracy—roughly 2× the Pass@1 of the next-best code agent—demonstrating the value of its dual-environment architecture and rollback mechanism for failure recovery.

## Relation to Prior Work

This paper extends the environment-configuration evaluation line (InstallMatic, ExecutionAgent, EnvBench, SetupBench) by shifting from end-to-end build/test success to process-level trajectory assessment decomposed into planning, perception, feedback, and action capabilities. It also departs from the manual curation paradigm of prior benchmarks by introducing an automated error-injection pipeline (LLM-edited READMEs validated in Docker) that scales instance generation from tens to thousands. The agent frameworks evaluated (SWE-Agent, OpenHands, Repo2Run, InstallMatic) represent the current SWE-agent landscape, but none prior to this work provides a structured, multi-dimensional capability breakdown of where in the configuration trajectory an agent fails.

## Why It Matters / Open Questions

The benchmark reveals a concrete and actionable bottleneck: agents achieve high recall in error localization (~90%) but their fix accuracy lags far behind description accuracy (~30–47% vs ~50%), and end-to-end Pass@1 remains low (≤23%), indicating the critical gap is translating perceived feedback into valid execution actions. The automated data-construction pipeline also addresses the scalability bottleneck that has limited prior environment-configuration research to 40–994 instances. Open questions include whether process-level evaluation generalizes beyond Python/README-based setup, whether the perception-to-action gap can be closed with better environment-interaction loops, and whether the LLM-injected error distribution fully captures the long tail of real-world configuration failures.
