## Problem

Existing LLM memory systems introduce substantial computational overhead and consistency issues: they process raw dialogue without filtering redundant tokens, segment memory at rigid turn or session boundaries that entangle unrelated topics, and perform expensive update operations synchronously during inference. This results in high token consumption, many API calls, and long test-time latency without proportional gains in reasoning quality.

## Input / Output

LightMem consumes raw dialogue turns incrementally (one turn at a time, reflecting realistic multi-turn interaction) and a user query at retrieval time. Each turn is first compressed by LLMLingua-2 (a lightweight BERT-based model under 2 GB GPU memory), buffered in a 512-token sensory memory, then grouped into topic-constrained segments. The system outputs structured memory entries of the form {topic, {summary, user_turn, model_turn}} with associated embeddings stored in a vector database, and ultimately produces QA responses by retrieving relevant entries and prompting the backbone LLM.

## Method

LightMem organizes memory into three stages inspired by the Atkinson-Shiffrin human memory model. Light1 (Sensory Memory) applies token-level pre-compression via LLMLingua-2's binary retain/discard classification, then performs hybrid topic segmentation by intersecting attention-based boundaries (local maxima in the sub-diagonal of a turn-level attention matrix from LLMLingua-2's upper layers) with embedding-similarity boundaries to identify topic transitions. Light2 (Topic-Aware STM) buffers compressed topic segments until a token threshold is reached, at which point the backbone LLM generates concise summaries, producing topic-constrained memory entries that minimize API calls while preserving summarization accuracy. Light3 (LTM with Sleep-Time Update) decouples maintenance from inference: at test time, new entries are inserted directly with timestamps (soft update), and during offline 'sleep' periods, each entry's update queue (top-k semantically similar entries with later timestamps) is processed in parallel, eliminating the sequential read-after-write bottleneck that causes cumulative latency in prior systems.

## Results

On LongMemEval-S with GPT-4o-mini, LightMem (r=0.7, th=512) achieves 68.64% ACC, surpassing the strongest baseline A-MEM (62.60%) by 6.04 points while using only 28.25k total tokens vs. A-MEM's 1,605.81k (a 57× reduction) and 18.43 API calls vs. 986.55 (a 53× reduction). On LoCoMo with GPT-4o-mini, LightMem (r=0.8, th=768) reaches 72.99% ACC, outperforming A-MEM (64.16%) by 8.83 points with 85.19k total tokens vs. 1,149.43k. In terms of pure online test-time cost, LightMem reduces token usage by up to 105.9× (GPT) and 117.1× (Qwen), and API calls by up to 159.4× and 309.9× respectively.

## Baselines & Comparisons

LightMem consistently outperforms all four memory-system baselines on both accuracy and efficiency across both datasets and both LLM backbones (GPT-4o-mini and Qwen3-30B). Against A-MEM (the strongest baseline), LightMem improves ACC by 2.09%–6.40% with GPT and up to 7.67% with Qwen on LongMemEval, and by 6.10%–18.12% (GPT) / 4.41%–29.29% (Qwen) on LoCoMo, while reducing total token consumption by 10×–38× (GPT) and 6.9×–21.8× (Qwen) on LongMemEval. Against MemoryOS, LightMem achieves substantially higher accuracy (e.g., 68.64% vs. 44.80% on LongMemEval-GPT) with roughly 27× fewer total tokens and 20× fewer API calls. Against Mem0, LightMem gains 5–15 ACC points on LongMemEval and 10–30 points on LoCoMo while using 10×–20× fewer tokens. Against LangMem, the accuracy gap is even larger (31+ points on LongMemEval-GPT), and LightMem uses an order of magnitude fewer API calls. The efficiency advantage is most dramatic in the online-only setting, where LightMem's decoupled sleep-time update eliminates all update-phase LLM calls from the critical path.

## Relation to Prior Work

LightMem repurposes ideas from prompt compression (LLMLingua-2), attention-based text segmentation, and the Atkinson-Shiffrin cognitive memory model to address efficiency limitations in existing LLM memory systems (A-MEM, MemoryOS, Mem0, LangMem). Rather than building on a single prior architecture, it restructures the standard memory pipeline by inserting a lightweight pre-compression and topic-segmentation stage before summarization, and by decoupling memory updates from online inference via an offline 'sleep-time' parallel update mechanism. The paper explicitly positions itself against the three inefficiencies it identifies in prior work—redundant sensory processing, fixed-granularity short-term memory, and sequential online updates—making it a systems-level redesign rather than an incremental extension of any one baseline.

## Why It Matters / Open Questions

The practical impact is significant for production LLM agents: reducing token consumption by up to 38× and API calls by up to 30× while simultaneously improving accuracy makes memory-augmented generation far more economically viable for long-horizon dialogue. The sleep-time update concept—treating memory consolidation as an offline, parallelizable process analogous to human sleep—offers a generalizable design principle that could be adopted by other memory frameworks. Open questions include whether the approach generalizes beyond dialogue to other incremental information streams, how the compression ratio and buffer threshold interact at scale, and whether the offline 'sleep' period is realistic in always-on production settings. The paper also notes limitations in relying on a single compression model (LLMLingua-2) and the absence of structured multi-hop reasoning, pointing toward future integration with knowledge graphs and multimodal inputs.
