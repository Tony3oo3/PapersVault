## Problem

Despite JSON being the de facto standard for structured data exchange and jq being a widely used tool for querying and transforming it, no existing benchmark jointly evaluates language models on generating executable jq expressions from natural language instructions and/or input-output examples. This gap leaves the community without a standardized way to measure how well models handle the expressive yet relatively uncommon jq language over diverse, variably nested real-world JSON structures.
![Teaser figure](../imgs/ICLR20260290/cropped_page2_idx0.webp)

## Input / Output

Each JQSTACK instance provides a natural-language instruction plus two or more JSON input-output example pairs; each JQSPIDER instance provides an instruction, a JSON Schema, and a jq expression validated against a large JSON database (with the full file omitted when too large, forcing schema-based reasoning). The model must produce a single jq expression (or, in comparison experiments, a Python function accepting one JSON argument). Evaluation executes the expression via the jq Python binding's jq.all() call, which wraps all results in a list, so a prediction is correct if jq.all(e, i) equals [o] or o equals [jq.all(e, i)] for every held-out test; on JQSPIDER, record keys and (unless ORDER BY is specified) ordering are ignored.

## Method

JQBENCH is built by two fully automated pipelines. The JQSTACK pipeline extracts intent, candidate jq expressions, and examples from Stack Overflow posts tagged jq using GPT-5, then runs an agentic conversion loop (GPT-5 or Opus 4.6) equipped with add_test and run_tests tools to synthesize and validate multiple test cases; a filtering step removes the 11,066+1,913 tasks solvable in one shot by GPT-5 or Opus 4.1 at temperature 0, leaving 1,496 challenging instances. The JQSPIDER pipeline converts Spider's relational schemas to nested JSON Schemas, transforms SQL databases into conforming JSON files via iterative Python-function generation with execution feedback, and derives equivalent jq programs from the original SQL queries, yielding 859 tasks. Baseline evaluation follows a Self-Debug-style iterative protocol (up to 8 iterations, temperature 0) that feeds back compilation errors, execution results, and value-match outcomes after each attempt; the paper further ablates explicit tool use (run_code, search_docs, print_docs), compares jq against Python as the target language, and studies the effect of omitting the natural-language instruction to create a pure programming-by-example setting.

## Results

On JQSTACK, the best jq baseline (Opus 4.1 with implicit execution feedback) achieves 76% value-match, while the best overall configuration (Opus 4.1 generating Python) reaches 83%. On JQSPIDER, Opus 4.1 with jq and implicit feedback scores 81%, with all non-Phi-4 models clustering in the 72–81% range. Smaller models struggle dramatically with jq: Phi-4 drops to 10% on JQSTACK (vs. 54% for Python), and GPT-5-mini reaches only 59% (vs. 79% for Python).

## Baselines & Comparisons

The paper does not compare against external methods but instead ablates model, language, and feedback configuration. Python consistently outperforms jq across all models, with the gap largest for smaller models: Phi-4 drops from 54% (Python) to 10% (jq) on JQSTACK, and GPT-5 from 82% to 68%. Implicit execution feedback (SELF-DEBUG-style) substantially outperforms explicit tool use: giving Opus 4.1 the run_code tool drops JQSTACK from 76% to 31%, and GPT-5 from 68% to roughly 35%. Access to jq documentation further hurts the strongest model (Opus 4.1: 76% → 31%), attributed to the model getting stuck in documentation-retrieval loops rather than solving the problem. Removing the natural-language instruction (converting to pure PBE) causes a moderate drop (Opus 4.1: 76% → 71%; GPT-5: 68% → 63%), confirming that the instruction provides a meaningful signal beyond examples alone.

## Relation to Prior Work

This paper positions itself at the intersection of NL-to-code benchmarks (ODEX, BigCodeBench), NL-to-SQL work (Spider, DocSpider), and programming-by-example (PBE) research, but carves out a distinct niche: generating jq expressions for JSON querying and transformation from natural language and/or input-output examples. The evaluation protocol builds directly on SELF-DEBUG's iterative compilation/execution feedback loop, while the data pipeline repurposes Spider's relational databases into nested JSON with schemas. Unlike DocSpider (which targets MongoDB) or NL2Bash (which contains only 2 jq commands), JQBENCH is the first benchmark to jointly capture NL prompts with executable jq programs over diverse, organically-shaped JSON, and it explicitly supports both NL and PBE task formulations in a low-resource language setting.

## Why It Matters / Open Questions

JQBENCH provides the first systematic testbed for studying how LLMs handle an uncommon but expressive query language over structured data, revealing that language novelty is a major bottleneck (Phi-4 drops from 54% Python to 10% jq) and that the best model still plateaus at 76–81%. The finding that documentation access actively harms the strongest model (76%→31%) and that explicit tool-based feedback underperforms implicit SELF-DEBUG-style feedback (−53% for GPT-5) has direct practical implications for designing agentic coding workflows. Open questions include whether fine-tuning on the released 13K training cases can close the jq gap for smaller models, whether the documentation trap generalizes beyond jq, and how multi-input or multi-file jq programs would further challenge current systems.
