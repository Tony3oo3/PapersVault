## Problem

While LLMs achieve over 90% Pass@1 on single-language code generation benchmarks, their ability to generate cross-programming-language (CPL) interoperating code—encompassing Inter-Process Communication (IPC) and Foreign Function Interface (FFI)—remains entirely unexplored. No existing benchmark evaluates whether LLMs can produce correct code that enables heterogeneous languages to communicate or invoke each other, despite over 80% of real-world software systems involving multiple languages.
![Teaser figure](../imgs/ICLR20263974/cropped_page1_idx0.webp)

## Input / Output

Each task provides a natural language instruction (median ~1,200 characters) describing a specific IPC or FFI functionality, along with metadata specifying the target language, IPC technique, and key procedural steps. For IPC tasks, the LLM generates code in one of six languages (Java, Python, Go, JavaScript, PHP, C++) that must satisfy a predefined finite state machine's protocol compliance. For FFI tasks, the LLM generates Python ctypes wrapper code that must compile and execute correctly against precompiled GNU Scientific Library (.so) shared objects, validated by automatically generated assertion test cases. The benchmark comprises 2,534 tasks: 1,982 IPC tasks across seven technologies and 522 Python-C FFI tasks.

## Method

CrossPL is constructed via two LLM-based workflows (powered by DeepSeek-V3) built atop 156 scenario-specific finite state machines (FSMs) derived from official IPC documentation, which model the state-transition logic of each communication protocol. For CrossPL-IPC, the pipeline mines 19,169 multi-language GitHub repositories using FSM-based pattern detection, then applies a Judger→Extractor→FSM-validation→Instructor chain to extract minimal code snippets and generate task instructions, with up to five extraction retries at increasing temperature. For CrossPL-FFI, the pipeline compiles GSL C source into .so files, prompts an LLM to generate Python ctypes wrappers and reference solutions, and iteratively refines failures via error-revision prompts until execution succeeds. Evaluation uses FSM state-transition matching for IPC (checking protocol compliance without execution) and controlled compilation plus assertion-based execution for FFI, reporting unbiased Pass@1 (greedy) and Pass@5 (temperature 0.2, top-p 0.95) across 20 state-of-the-art LLMs.

## Results

On CrossPL-IPC (1,982 tasks across 6 languages and 7 IPC techniques), GLM4-plus achieves the highest mean Pass@1 of 75.88%, followed by GPT-4o at 73.81% and DeepSeek-V3 at 73.51%. On CrossPL-FFI (522 Python-C tasks), performance drops dramatically: even the best model, GPT-4o, reaches only 19.54% Pass@1 and 26.46% Pass@5, while Llama3-8b-instruct achieves a mere 0.77% Pass@1. This stark contrast with >90% Pass@1 on single-language benchmarks underscores the fundamental inadequacy of current LLMs for CPL interoperating code generation.

## Baselines & Comparisons

On CrossPL-IPC, GLM4-plus leads with 75.88% mean Pass@1, narrowly ahead of GPT-4o (73.81%) and DeepSeek-V3 (73.51%), while Llama3-8b-instruct trails at 40.67%. Code-specialized models are competitive at matched scale: Qwen2.5-coder-32b-instruct (72.50%) outperforms the general Qwen3-32b (65.69%) by 6.81 points, and Qwen2.5-coder-7b-instruct (68.92%) beats CodeLlama-7b-instruct (50.15%) by 18.77 points. On CrossPL-FFI, GPT-4o dominates with 19.54% Pass@1, but no model exceeds 26.46% Pass@5; the best code model, Qwen2.5-coder-32b-instruct, reaches only 7.28% Pass@1, well below GPT-4o. Think mode (Qwen3 series) improves FFI performance but degrades or has no effect on IPC, indicating that IPC's rigid protocol patterns do not benefit from additional reasoning. Overall, the gap between IPC (best ~76%) and FFI (best ~20%) Pass@1 highlights that FFI remains the critical bottleneck for LLM-based CPL code generation.

## Relation to Prior Work

This paper extends the FSM-based approach of PolyFax (Li et al., 2022a), which first proposed using finite state machines to identify interoperating patterns in multi-language projects but defined only 8 coarse FSMs, to a suite of 156 fine-grained FSMs with semantic descriptions and comment-skipping. It departs fundamentally from existing multilingual code generation benchmarks (HumanEval-X, MultiPL-E, CRUXEVAL-X, Multi-SWE-bench), which evaluate each language in isolation or focus on code translation, by introducing the distinct task of generating interoperating code that bridges heterogeneous languages via IPC or FFI mechanisms. The LLM-based construction and evaluation workflows (Judger, Extractor, Instructor) draw on multi-agent prompting patterns but are specifically designed around FSM-validated protocol compliance rather than execution-based testing.

## Why It Matters / Open Questions

CrossPL is the first benchmark to systematically evaluate LLMs on cross-language interoperating code generation, revealing a stark capability gap: the best model achieves only 19.5% Pass@1 on FFI tasks versus >90% on single-language benchmarks, underscoring that current LLMs are far from ready for real-world multi-language software development. The finding that think mode improves FFI but degrades IPC performance challenges the assumption that additional reasoning universally benefits code generation. Key limitations include FFI coverage restricted to Python-C, IPC limited to six languages and seven techniques, and uneven sample distribution across sub-tasks, leaving open questions about whether specialized fine-tuning, expanded language-pair coverage, or architectural innovations can close the FFI gap.
