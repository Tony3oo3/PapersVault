## Problem

Existing tool-use benchmarks (ToolBench, BFCL v3, τ-Bench, MCP-RADER, MCPEval) rely on isolated APIs with poor input-output alignment, explicit tool specifications, shallow few-step workflows, and limited domain coverage, failing to capture the complexity of real-world multi-domain tool orchestration. In particular, none test an agent's ability to infer appropriate tools from fuzzy, underspecified instructions, plan multi-hop trajectories across complementary tool sets, ground responses in intermediate outputs, or coordinate cross-server workflows with multiple concurrent goals.

## Input / Output

The agent receives a single fuzzy natural-language instruction (e.g., a researcher asking about BRAF V600E melanoma resistance) with no explicit tool names or execution steps, plus access to 28 MCP servers exposing 250 tools and 10 distractor servers adding 100+ irrelevant tools per task. The agent produces a multi-turn execution trajectory (up to 20 rounds, each containing a plan and parallel tool invocations) and a final synthesized answer. Evaluation yields three rule-based rates (valid tool name, schema compliance, execution success) and six LLM-judge sub-scores normalized to [0,1] across task fulfillment, information grounding, tool appropriateness, parameter accuracy, dependency awareness, and parallelism efficiency.

## Method

MCP-BENCH is built on a POMDP formalization where the agent iteratively plans, executes tools, compresses observations, and updates state over up to 20 rounds (Algorithm 1). Tasks are synthesized via a three-stage pipeline: (1) dependency chains are discovered from tool I/O signatures across servers, (2) an LLM (o4-mini) generates natural-language tasks grounded in those chains, filtered by solvability (≥9/10) and practical utility (≥5/10), and (3) passing tasks are rewritten into fuzzy variants that omit tool names and step-by-step instructions while preserving all numerical parameters. The evaluation combines rule-based execution checks with a rubric-driven LLM-as-a-Judge (o4-mini) that scores six sub-dimensions using the concrete (pre-fuzzing) task description and dependency analysis as hidden references, with five random prompt shuffles per task to mitigate ordering bias. The benchmark comprises 104 tasks (56 single-server, 30 two-server, 18 three-server) spanning 11 functional domains, and is evaluated on 20 state-of-the-art LLMs.

## Results

On MCP-BENCH (104 tasks, 28 MCP servers, 250 tools), GPT-5 achieves the highest overall score of 0.749, followed by O3 (0.715) and GPT-oss-120b (0.692). Schema understanding has largely converged, with top models exceeding 98% on valid tool naming and schema compliance, while the sharpest separations appear in planning effectiveness: GPT-5 scores 0.649 on dependency awareness and 0.339 on parallelism, whereas smaller models like Llama-3-1-8B-instruct (overall 0.428) rarely exceed 0.22 on either dimension. Moving from single-server to multi-server settings, weaker models degrade noticeably (e.g., Llama-3-1-8B drops from 0.438 to 0.415), while frontier models remain stable (GPT-5: 0.749 → 0.750).

## Baselines & Comparisons

As a benchmark paper, MCP-BENCH evaluates 20 LLMs rather than proposing a new method, so the 'comparisons' are cross-model performance gaps. GPT-5 leads all models by a clear margin (0.749 overall), outperforming O3 (0.715) by 3.4 points and GPT-oss-120b (0.692) by 5.7 points, with the largest advantage in information grounding (0.828 vs. 0.706 for O3). The gap between frontier and mid-tier models is most pronounced in planning effectiveness: GPT-5 scores 0.649 on dependency awareness while Llama-3-1-70B manages only 0.287, a 2.3× difference. In the multi-server setting, weaker models degrade more sharply—Llama-3-1-8B drops from 0.438 to 0.415 and Nova-Micro-v1 from 0.520 to 0.471—while GPT-5 and O3 remain nearly flat, indicating that cross-server orchestration is the key differentiator. On rule-based metrics (schema compliance, valid tool naming), all models above ~70B parameters cluster above 97%, confirming that basic execution fidelity is no longer a distinguishing factor. Efficiency also varies: Llama-3-1-8B requires 17.3 rounds and 155.6 tool calls per task on average, whereas Qwen3-235B-A22B completes tasks in just 4.0 rounds and 16.4 calls while scoring 0.678 overall.

## Relation to Prior Work

This paper extends the tool-use benchmarking lineage from ToolBench and BFCL v3 (which aggregate isolated APIs) and τ-Bench (which uses a small set of compatible APIs) by leveraging the Model Context Protocol (MCP) as a standardized substrate for tool invocation. It departs from the closest MCP-based predecessors—MCP-RADER (42 tools) and MCPEval (19 tools)—by scaling to 28 servers and 250 tools, introducing fuzzy task descriptions that omit explicit tool names and execution steps, and adding cross-server dependency chains with information-grounding evaluation. The POMDP formalization follows ReAct (Yao et al., 2023), and the LLM-as-a-Judge evaluation with prompt shuffling builds on recent work addressing judge bias (Li et al., 2025).

## Why It Matters / Open Questions

MCP-BENCH provides the first large-scale, ecosystem-based benchmark that systematically exposes the gap between execution fidelity (largely solved, >98% schema compliance for frontier models) and higher-order agentic reasoning (planning effectiveness, dependency awareness, parallelism), where even GPT-5 scores only ~0.34 on parallelism efficiency. The finding that weaker models degrade non-monotonically across server counts, and that the 104-task suite still yields only ~0.75 for the best model, suggests that long-horizon, cross-domain orchestration remains a fundamental open challenge. Limitations include the relatively small task count (104), reliance on LLM-as-a-Judge for strategic quality assessment, and the fact that MCP server availability and rate limits may affect reproducibility over time.
