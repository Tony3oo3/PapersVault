## Problem

Existing RL methods for LLMs on verifiable rewards (e.g., GRPO) train on single-turn outcome rewards, but GPU kernel generation is inherently iterative: engineers write code, execute it, inspect timing profiles, and refine over many turns. This paper asks how to explicitly incorporate successive turns of code generation, execution, and feedback into each RL training step so the model learns multi-turn refinement strategies rather than optimizing for a single-shot answer.

## Input / Output

Each training/inference turn takes as input the PyTorch reference implementation (the KernelBench task) plus, for subsequent turns, the history of previously generated kernels, their summarized chain-of-thoughts, and evaluation feedback (compilation errors, correctness failures, or achieved speedup). The model outputs three components per turn: a full chain-of-thought, a complete CUDA kernel wrapped in a `torch.utils.cpp_extension.load_inline` block (pure inline CUDA, no PyTorch functional operators), and a short summary of the reasoning. Prior-turn CoTs are discarded from context and replaced by their summaries to keep the context window manageable over 8+ refinement turns.

## Method

Kevin is trained with a multi-turn GRPO recipe on 180 KernelBench Level 1/2 tasks using QwQ-32B as the base model. Within each training step, the model generates m=16 parallel trajectories of n=4 sequential refinement turns; each turn is treated as an individual training sample (not the full trajectory), enabling per-turn credit assignment. The reward for turn t is a discounted sum of its own kernel score and all subsequent scores (R_t = Σ γ^(i−t) r_i with γ=0.4), where the score S = 0.3·1{correct} + (T_baseline/T_kernel)·1{correct} balances correctness and speedup. To prevent context explosion, prior-turn CoTs are replaced by model-generated summaries. The GRPO loss uses Clip-Higher (ε_high=0.28), zero KL penalty, and constant-length normalization with gradient-norm clipping at 0.05 to maintain training stability. Strict rule-based checks (rejecting any PyTorch functional calls, try-except fallbacks, or inheritance from the reference) prevent reward hacking.

## Results

On a 100-task unseen KernelBench evaluation set (16 parallel trajectories, 8 refinement turns), Kevin (multi-turn RL on QwQ-32B) achieves 82% best@16 correctness and 1.10× best@16 mean speedup over PyTorch Eager, compared to 56% and 0.53× for the base model. Kevin also outperforms frontier models o4-mini (38% correctness, 0.78× speedup) and o3-mini (27%, 0.30×). In test-time scaling experiments, sequential refinement (16 trajectories × 8 turns) consistently outperforms parallel sampling (128 trajectories × 1 turn) under the same 128-kernel inference budget, with Kevin achieving 1.10× vs. 0.65× speedup.

## Baselines & Comparisons

Kevin (multi-turn RL) substantially outperforms its base model QwQ-32B on both correctness (82% vs. 56% best@16) and speedup (1.10× vs. 0.53× best@16), demonstrating that multi-turn RL training nearly doubles the base model's kernel generation capability. Against the single-turn RL baseline (same QwQ-32B base, trained with GRPO on single-turn rollouts), Kevin ties on correctness (82% vs. 82%) but achieves a 29% relative speedup improvement (1.10× vs. 0.85×), with the gap widening further under more refinement turns. Kevin also surpasses frontier closed-source models: o4-mini (38% correctness, 0.78× speedup) and o3-mini (27%, 0.30×), despite being built on a smaller open-weights base model. In the parallel-vs-sequential scaling comparison (Table 2), Kevin's multi-turn inference configuration (16 traj × 8 turns) yields 1.10× speedup, outperforming its own single-turn configuration (128 traj × 1 turn) at 0.65×, confirming that iterative refinement is more effective than parallel sampling for kernel optimization.

## Relation to Prior Work

This paper extends the GRPO-based RLVR (Reinforcement Learning with Verifiable Rewards) framework from single-turn outcome rewards to a multi-turn credit-assignment setting, where each refinement turn in a trajectory receives a discounted sum of current and future kernel scores. It departs from RLEF, which assigns a single binary pass/fail reward only at the final turn, by training on every turn and optimizing for continuous performance (speedup) beyond correctness. The work also positions itself against agentic test-time-compute systems (WarpDrive, AlphaEvolve) that improve inference but leave the base model unchanged, and against supervised fine-tuning or imitation learning for code optimization, arguing that RL with execution feedback is the natural paradigm for iterative kernel engineering.

## Why It Matters / Open Questions

Kevin demonstrates that a multi-turn RL recipe can close a substantial gap between a 32B open-weights model and frontier closed models on a practically important task (CUDA kernel generation), and that the recipe's components—turn-wise reward with discounting, CoT summarization to manage context, and strict anti-hacking checks—are generalizable to other iterative optimization domains with verifiable rewards. Key limitations include the small task pool (250 KernelBench problems), H200-specific speedup measurements, and the high compute cost (650 H200-hours per run). Open questions include whether learned value networks or PPO can further improve baseline estimation, whether the multi-turn recipe transfers to other hardware architectures or kernel DSLs (Triton, ThunderKittens), and how it scales as more robust kernel environments become available.
