## Problem

Existing code-generation benchmarks for LLMs suffer from two intertwined limitations: static problem sources that become contaminated through training corpora (turning evaluation into memorization), and superficial example-based testing that creates an 'illusion of correctness' by missing subtle edge-case failures. No prior benchmark simultaneously addresses both the dynamic sourcing of novel, real-world problems and the systematic scaling of test rigor to deep, verifiable coverage.

## Input / Output

The framework ingests raw source functions from recent GitHub commits (post-May 2025, from repositories with ≥500 stars across 10 stratified domains) and produces executable benchmark instances, each comprising a natural-language instruction, a ground-truth implementation, and a PBT-generated test suite of ~500 input-output pairs. Evaluation consumes LLM-generated code solutions and produces Pass@1 scores alongside a 'diagnostic fingerprint' — a multi-stage outcome distribution (SyntaxErr → RuntimeErr → LogicErr → partial pass tiers → Perfect) that reveals *how* and *why* models fail, not just whether they pass.

## Method

CODE2BENCH operationalizes a 'Dual Scaling' philosophy through an end-to-end automated pipeline. For scaling the source, it applies temporal filtering (extracting only code committed after each model's knowledge cutoff), Scope Graph-based dependency analysis to classify functions as Self-Contained (pure algorithmic logic) or Weakly Self-Contained (API application within an allowed library set), CFG-based testability checks, Cyclomatic Complexity filtering ([2,10]), and LLM-as-a-Judge semantic filtering (Cohen's κ=0.95 vs. human experts). For scaling the rigor, it employs a PBT engine (Hypothesis/jqwik) to synthesize diverse, structured inputs and enforces a 'Great Filter' quality gate mandating 100% branch coverage on the ground-truth function — discarding both inadequate test suites and inherently untestable functions. The resulting CODE2BENCH-2509 suite (217 SC-Python, 194 WSC-Python, 249 SC-Java tasks) is evaluated via zero-shot greedy decoding with differential testing against ground truth, and the paper introduces a diagnostic fingerprint visualization that decouples algorithmic synthesis failures (dominant LogicErr in SC tasks) from API application failures (dominant RuntimeErr in WSC tasks) and quantifies how Java's static type system acts as 'performance scaffolding' suppressing error rates relative to Python.

## Results

On CODE2BENCH-2509, the top-performing model Claude-4-Sonnet achieves 40.1% Pass@1 on SC-Python, 38.7% on WSC-Python, and 47.4% on SC-Java, while the best open-source model DeepSeek-V3 reaches 34.4%, 37.6%, and 47.8% respectively. The benchmark reveals a systematic performance gap: all models score 50+ percentage points lower than on HumanEval (e.g., Claude-4-Sonnet drops from ~97% to 40.1%). Additionally, 6.94% of SC-Python submissions exhibit 'near-perfect' failures (passing ≥98% of ~500 PBT test cases but failing on subtle edge cases), a phenomenon invisible to conventional sparse test suites.

## Baselines & Comparisons

CODE2BENCH-2509 is compared against three prior benchmarks: HumanEval (164 tasks, ~7.8 test cases, avg CC 2.8), MBPP (974 tasks, ~3.0 test cases, avg CC 2.3), and EvalPlus (mutation-enhanced HumanEval/MBPP). The head-to-head comparison in Figure 4 shows that all 10 evaluated models score dramatically lower on CODE2BENCH-2509 than on HumanEval/EvalPlus — for instance, Claude-4-Sonnet achieves ~97% on HumanEval but only 40.1% on SC-Python-2509, a drop of over 50 percentage points. This gap is attributed to both the dynamic, contamination-resistant sourcing (code committed after May 2025) and the order-of-magnitude increase in test rigor (~500 PBT test cases with 100% branch coverage vs. ~7.8 example-based tests). The paper positions CODE2BENCH-2509 as the only benchmark simultaneously achieving dynamic sourcing, dependency handling, rigorous testing, and multi-language design (Table 1), whereas prior methods like LiveCodeBench lack dependency handling and BigCodeBench lacks dynamic sourcing and rigorous testing.

## Relation to Prior Work

This paper operationalizes two established techniques—Property-Based Testing (PBT, Claessen & Hughes 2000) and Scope Graph-based name resolution (Néron et al. 2015)—into a unified benchmark construction pipeline, a combination no prior code-generation benchmark has attempted. It departs from static benchmarks (HumanEval, MBPP) on the contamination axis and from dynamic benchmarks (LiveCodeBench, EvoCodeBench) on the testing-rigor axis, while also extending repository-level benchmarks (BigCodeBench, DevEval) by adding the 100% branch-coverage PBT quality gate and multi-language native instantiation. The 'Dual Scaling' framing is the paper's conceptual contribution: treating source dynamism and test rigor as two independent, simultaneously scalable dimensions rather than addressing one at the expense of the other.

## Why It Matters / Open Questions

The benchmark directly addresses two widely acknowledged but rarely jointly solved limitations of code-LLM evaluation, and the 'illusion of correctness' finding (~7% near-perfect failures on SC-Python) provides concrete evidence that current benchmark scores systematically overestimate model robustness. The first systematic quantification of how language paradigms (static typing in Java vs. dynamic typing in Python) reshape LLM failure modes opens a new axis of analysis for the field. Key open questions include whether the framework extends to repository-level (Project-Dependent) tasks, whether non-functional properties (efficiency, security) can be incorporated into the PBT quality gate, and whether the SC/WSC gap persists as models improve.
