## Problem

Evaluating formally verifiable code generation is bottlenecked by reliance on manually-written ground-truth specifications, which limits existing Dafny benchmarks to a few hundred simple problems and introduces reliability issues (10–28% of expert-written specs contain errors or ambiguities). The paper asks: how can we rigorously assess the quality of generated specifications and code without depending on any ground-truth annotation?
![Teaser figure](../imgs/ICLR20264956/cropped_page1_idx0.webp)

## Input / Output

For the end-to-end task, the model receives a natural-language algorithmic problem and must produce both a Dafny implementation and its formal specification; for auxiliary tasks, it receives either annotated-but-unverified Dafny code (refinement) or a Dafny implementation alone (spec generation). The evaluation yields two scores: a binary equivalence score determined by the Dafny verifier checking bidirectional implication between code and spec (no false positives), and a 0–100 exact matching score from an LLM judge comparing the spec's NL translation against the original query. Each of the 2,389 benchmark problems ships with a strong auto-formalized spec (complete but often unverifiable) and a weaker verifiable-but-incomplete spec, plus Python and Dafny implementations and unit tests.

## Method

The core technical contribution is the equivalence score, which proves bidirectional implication between code and specification using the Dafny verifier: direction 1 (spec → code) is checked by standard verification of the annotated program, while direction 2 (code → spec) is checked by constructing a helper method that assumes all pre/post-conditions and asserts the spec-determined outputs equal the actual method outputs. This eliminates false positives and removes the need for ground-truth specs. The benchmark is built by auto-formalizing 2,174 LeetCode problems into Dafny (using Claude-4 with iterative syntax repair and first-order-logic-only constraints) and synthesizing 215 novel problems via a tag-composition pipeline that randomly combines 3–8 tags from a 500+ tag ontology spanning domain, data structure, and algorithm categories. Evaluation is two-step: the equivalence score gates formal correctness, then Grok-4 translates the spec back to NL and Claude-4 judges intent alignment. For auxiliary tasks, they RL-train (GRPO) a 14B SFT model from Veri-Code Series I, using verifier pass/fail as reward for refinement and spec-superior-score for spec generation.

## Results

The headline finding is that the best-performing model, Claude-4-sonnet, which achieves 75.81% pass@4 on CloverBench, fails on all instances of the contamination-free TagComp subset (0% exact matching score), even under pass@4. GPT-5 achieves the highest mutual-equivalence rate at 2.65%, but these solutions often provide simplified implementations that hack the reward. Claude-4-sonnet produces syntactically correct Dafny code at 73.79%, yet all three proprietary models (Claude-4-sonnet, GPT-5, Gemini-2.5-flash) fail to generate verifiable solutions that are both mutually equivalent and aligned with user intent. The average Cyclomatic Complexity of VeriEquivBench is 5.63, more than double the 2.44 of DafnySynthesis, confirming substantially harder problems.

## Baselines & Comparisons

The paper validates its equivalence score metric against three existing Dafny benchmarks. DafnySynthesis (Misu et al., 2024) achieves 76.22% equivalence, but the authors identify an additional 18% of specifications with errors or ambiguities beyond the 10% already reported by Clover, meaning roughly 28% of its ground-truth labels are unreliable. CloverBench (Sun et al., 2024) scores 61.29%, with a large fraction of specifications failing to establish true equivalence with their code. DafnyBench (Loughridge et al., 2025) scores lowest at 43.09%, as it was not designed to check specification completeness. On the model-performance side, the key comparison is between CloverBench and TagComp: Claude-4-sonnet drops from 75.81% to 0% pass@4, demonstrating that prior benchmarks are too simple to evaluate advanced formal reasoning. The paper also shows that its synthetic TagComp data is slightly more complex than the LeetCode-derived portion (5.63 vs. 5.38 Cyclomatic Complexity), and that the RL-trained baselines score only 17.68% on verifiable code refinement and 54% on spec generation, with almost no generated specifications achieving a full equivalence score.

## Relation to Prior Work

This paper extends the verifiable code generation line initiated by Clover (Sun et al., 2024), DafnyBench (Loughridge et al., 2025), and DafnySynthesis (Misu et al., 2024), all of which rely on manually-written ground-truth specifications for evaluation. The key departure is replacing ground-truth matching with an automated equivalence score that checks bidirectional implication between code and specification via the Dafny verifier, eliminating the need for expert-annotated reference solutions. The paper also builds on the spec-superior-score from Yan et al. (2025) and the auxiliary task formulations from DafnyBench, while introducing a tag-composition synthesis pipeline for scalable data generation that has no direct precedent in prior formal-verification benchmarks.

## Why It Matters / Open Questions

The finding that Claude-4-sonnet (75.81% on CloverBench) achieves 0% pass@4 on VeriEquivBench reveals a stark capability gap in formal reasoning on complex algorithmic problems, suggesting that prior benchmarks were too simple to expose true model limitations. The discovery that 10–28% of expert-written ground-truth specifications in existing benchmarks contain errors undermines confidence in prior evaluations and motivates the ground-truth-free equivalence metric. Open questions include whether the benchmark is appropriately calibrated (the 0% result may indicate the task is beyond current model capabilities rather than merely difficult), whether the tag-composition pipeline produces problems that are genuinely novel versus recombining known patterns, and whether the LLM-as-judge step (Claude-4) introduces its own biases in the second evaluation stage.
