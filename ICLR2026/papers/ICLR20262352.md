## Problem

Existing tool planning methods either treat tools as isolated components in prompts or rely on predefined complete dependency structures, both of which fail when tool dependencies are incomplete—a common real-world scenario since dependencies are collected from limited historical trajectories. No prior work explicitly models the incompleteness of tool dependency graphs while enhancing LLM-based planning, leading to invalid or suboptimal plans especially with large toolsets.

## Input / Output

The method takes a user request (natural language text), a tool set with formal description documents, and historical tool trajectories (ordered tool invocation sequences) as input. It produces an ordered tool trajectory (the planned sequence of tool invocations) and a single graph token vector that compactly encodes request-specific dependency structure. Notably, the graph token replaces verbose tool descriptions in the LLM prompt, reducing pre-task token consumption by over 95%, and the LLM is invoked only once per request rather than iteratively.

## Method

GTool constructs a request-specific tool graph by adding a request node (embedded via BERT) connected to all tool nodes (also BERT-embedded from their descriptions), then encodes this graph with a 3-layer TransformerConv GNN whose request-node output serves as the graph token. A Missing Dependency Prediction with LLMs (MDPL) module masks existing edges with probability ρ and trains the GNN encoder via autoregressive loss on LLM-generated edge-existence predictions, making the model robust to incomplete graphs. During planning, the graph token, tool names, and user request are fed to a frozen LLM in a single prompt, with supervised fine-tuning on ground-truth trajectories. The final loss jointly optimizes tool planning (L_TL) and dependency prediction (L_MDPL) weighted by λ, and only the GNN encoder parameters are trained, enabling seamless integration with any LLM backbone without retraining the language model.

## Results

GTool achieves over 29.6% average n-F1 improvement over the strongest baseline (GNN4Plan) using a lightweight LLaMA-2-7B backbone. On the HuggingFace dataset, GTool reaches n-F1=0.7913, l-F1=0.5403, NED=0.2537 (LLaMA-2-7B), substantially outperforming GNN4Plan (n-F1=0.4853) and HuggingGPT (n-F1=0.4457). On the large-scale ToolBench dataset (16,000+ APIs), GTool achieves n-F1=0.6126 and l-F1=0.3018 while reducing inference time to 2.02s per request—approximately one-tenth of SOTA baselines. GTool also reduces pre-task token consumption by over 80% compared to prompt-based methods like HuggingGPT and TaskBench.

## Baselines & Comparisons

GTool outperforms all eight baselines across nearly all datasets and LLM backbones. Against the strongest tuning-based baseline GNN4Plan, GTool achieves a 26.7% n-F1 improvement on average (e.g., 0.7913 vs. 0.4853 on HuggingFace with LLaMA-2-7B), and a 63% n-F1 gain on that specific dataset. Among tuning-free methods, HuggingGPT is the closest competitor, but GTool still leads by 76% in n-F1 on HuggingFace (0.7913 vs. 0.4457). The only marginal exception is on the ToolE dataset with Vicuna-13B and Qwen3-14B, where HuggingGPT slightly edges out GTool on l-F1 and NED (due to ToolE's short tool sequences favoring HuggingGPT's concise reasoning), while GTool still wins on n-F1. On the large-scale ToolBench (16,000+ APIs), GTool surpasses the best baseline (HuggingGPT) by 2.28% in n-F1 and 9.46% in l-F1, while running ~6× faster (2.02s vs. 12.77s per request). Naive retrieval methods (BM25, COLT, GRTF) and graph-traversal methods (ToolNet, Tool-Planner) are consistently far behind, confirming that explicit dependency modeling via GNNs is critical for tool planning.

## Relation to Prior Work

GTool sits at the intersection of two research threads: LLM-based tool planning (HuggingGPT, TaskBench, GNN4Plan, ToolNet, Tool-Planner) and graph-based link prediction (GCN, GAT, hyperbolic GNNs). It departs from prior tuning-free methods that encode tool descriptions in long prompts, and from tuning-based methods (GNN4Plan, ToolNet) that assume complete dependency structures, by introducing a request-specific tool graph with a GNN-produced 'graph token' and an explicit missing-dependency-prediction loss (MDPL) that trains the GNN encoder via LLM autoregressive supervision. The request-specific node design and the joint training objective (planning loss + edge-prediction loss) are novel architectural choices not present in any single prior work.

## Why It Matters / Open Questions

Tool planning is a bottleneck for deploying LLM agents in real-world settings where tool dependency graphs are inevitably incomplete; GTool's robustness to up to 90% missing edges and its 95% token reduction (replacing verbose tool descriptions with a single graph embedding) make it practically attractive for large-scale tool ecosystems. Key limitations include degraded performance under extreme sparsity (90% missing on Qwen3-14B), sensitivity to overlapping tool functionalities (bad cases in Appendix C.5), and reliance on a single LLM interaction that precludes iterative refinement. Open questions include whether the graph-token approach scales to truly massive tool sets (beyond ToolBench's ~16K APIs), whether multi-turn LLM interaction could recover from the identified failure modes, and whether the MDPL objective generalizes to dynamic tool graphs where dependencies shift over time.
