## Problem

Existing code generation methods rely on supervised next-token prediction, which cannot optimize for execution efficiency since multiple semantically correct CUDA programs exist but only a few achieve optimal performance for a given sparse matrix. Additionally, prior approaches ignore execution-time rewards during training and fail to bridge the modality gap between structured sparse matrix inputs and CUDA code generation, resulting in sub-optimal performance for low-latency sparse computation scenarios.
![Teaser figure](../imgs/ICLR20261013/cropped_page1_idx0.webp)

## Input / Output

The method takes the row and column indices of all non-zero elements in a sparse matrix as structured input (not text), encoded via sinusoidal positional embeddings that capture multi-scale positional relationships and relative proximity of non-zero entries. The output is a complete, compilable CUDA kernel for the target sparse operation (SpMV or SpMM) that must satisfy both functional correctness and minimal execution time on GPU. Because the optimal kernel depends on the specific sparsity pattern, the same model generates different CUDA code for different input matrices at inference time.

## Method

SparseRL employs a three-stage pipeline: (1) pre-training a CodeT5-based LM augmented with high-performance CUDA code, (2) supervised fine-tuning where the text prompt is replaced entirely by sinusoidal embeddings of sparse matrix indices mapped through a linear layer, and (3) PPO-based reinforcement learning where the LM acts as a stochastic policy generating tokens autoregressively. The key innovation is a hierarchical reward function combining compilation success (±0.5), functional test pass/fail (±0.5), a per-matrix z-score-normalized efficiency reward measuring speedup over cuSPARSE, and a memory-usage penalty, all evaluated by an external compiler-and-executor environment that provides non-differentiable feedback. The sinusoidal embedding of row/column indices enables the model to directly perceive sparse matrix structure and generate input-adaptive kernels (e.g., DIA format for diagonal matrices vs. block-CSR for clustered non-zeros), while the RL stage fine-tunes the policy to discover hardware-specific optimizations like shared memory tiling and warp-shuffle instructions that supervised learning alone cannot capture.

## Results

On the SpMV task (400 test matrices from SuiteSparse), SparseRL+Qwen2.5-14B achieves a pass@1000 of 49.25 and a Compilation Rate of 57.50%, outperforming all open-source baselines. In terms of execution efficiency, SparseRL achieves average speedups of 3.27× and 3.42× over CodeRL and PPOCoder on V100 (3.50× and 3.29× on A100), and 1.42× and 1.82× over cuSPARSE and TVM-S on V100. For SpMM, SparseRL achieves 6.80×/4.50× average speedup over CodeRL at 8/32 columns and 6.39×/4.38× over cuSPARSE on A100. The generated code runs approximately 30% faster on average compared to existing methods.

## Baselines & Comparisons

SparseRL consistently outperforms all open-source RL-based code generation baselines: it achieves 3.27× and 3.42× average GFLOPS speedups over CodeRL and PPOCoder on V100, while also improving pass@1000 from 36.50/35.50 to 49.25. Against the NVIDIA cuSPARSE library, SparseRL achieves 1.42× (V100) and 1.44× (A100) speedup on SpMV, and 6.39×/4.38× on SpMM at 8/32 columns; against TVM-S, the speedups are 1.82× (V100) and 1.86× (A100) on SpMV. Compared to general-purpose LLMs (Qwen3-8B, DeepSeek-R1-671B), SparseRL+Qwen3-14B achieves comparable or higher pass@1 (16.25 vs. 8.00/15.00) and, critically, a +34.5% speedup over cuSPARSE where DeepSeek-R1-671B actually underperforms cuSPARSE by 27.5%. Against closed-source models (GPT-5, Claude-sonnet-4), SparseRL trails on pass@5 (21.00 vs. 36.50/36.75) but achieves a +34.5% speedup over cuSPARSE where these models show −18.0%/−19.2%, confirming that correctness does not translate to performance optimization. Against LLM4EFFI (a concurrent general-purpose code efficiency method), SparseRL+Qwen3-14B achieves pass@1 of 16.00 vs. 10.00 and +32.5% speedup vs. −25.1% on SpMV.

## Relation to Prior Work

SparseRL sits at the intersection of three research threads: (1) pre-trained code generation models (CodeT5, CodeBERT, StarCoder), (2) RL-based code optimization (CodeRL, PPOCoder, StepCoder), and (3) decades of manual SpMV kernel engineering (CSR → CSR5 → DASP). It departs from prior RL-for-code work by replacing the natural-language input with a non-text modality (sparse matrix row/column indices via sinusoidal embeddings) and by incorporating actual GPU execution time into a hierarchical reward, rather than relying solely on correctness or proxy metrics. The authors explicitly position this as the first application of deep RL to sparse computation code generation, distinguishing it from general-purpose code synthesis and dense-kernel optimization.

## Why It Matters / Open Questions

The paper exposes a critical gap: even frontier closed-source LLMs (GPT-5, Claude-sonnet-4) that outperform SparseRL on pass@k generate code 17–20% *slower* than cuSPARSE, while SparseRL is ~30% *faster*—demonstrating that correctness and performance are decoupled objectives in GPU code generation. This has direct practical impact for pruned-LLM inference and GNN workloads where SpMV/SpMM latency is a bottleneck. Key limitations include the high compute cost of RL training (5 days on 8 GPUs per run), the requirement that generated code be reused repeatedly to amortize generation time, and the current restriction to NVIDIA CUDA. Open questions include extension to other hardware backends (AMD, custom ASICs), broader sparse operations beyond SpMV/SpMM, and whether the sinusoidal-embedding + RL recipe transfers to other structured-input code generation tasks.
