## Problem

Existing code generation benchmarks rely on costly manual annotation, focus predominantly on Python, and suffer from imbalanced language distributions and insufficient difficulty as LLMs rapidly saturate simpler tasks. The paper asks whether high-quality, high-difficulty, multilingual code generation benchmarks can be constructed fully automatically without any human annotation while guaranteeing correctness and completeness of test cases.
![Teaser figure](../imgs/ICLR20262672/cropped_page2_idx0.webp)

## Input / Output

The pipeline consumes multilingual code snippets (function-level, class-level, and file-level) extracted from Stack-Edu as seeds, along with a target programming language specification. Each generated benchmark instance is a structured tuple of <programming problem, code solution, public test function (≤3 basic cases), private test function (7+ cases including edge cases)>, with correctness verified by sandbox execution. The final AutoCodeBench contains 3,920 problems across 20 languages (averaging 498.2 characters per problem and 9.6 test cases per problem), and the companion AutoCodeInstruct training set contains 37K verifiable problems with pass rates filtered to the 40–80% range.

## Method

AutoCodeGen is a fully automated workflow centered on LLM-sandbox interaction that inverts the typical data synthesis paradigm. Instead of prompting LLMs to generate both test inputs and expected outputs (where LLMs frequently produce incorrect outputs on hard problems), the LLM generates only test inputs, which are then executed in a multilingual sandbox to obtain ground-truth outputs; the LLM subsequently integrates these verified input-output pairs into coherent test functions. A reverse-generation step then prompts the LLM to synthesize the programming problem description from the already-verified code solution and test function, ensuring the problem is solvable and well-specified. A three-stage filtering pipeline follows: (1) difficulty control via 10-sample pass-rate filtering with DeepSeek-Coder-V2-Lite (discarding problems solved in all attempts), (2) quality control via DeepSeek-R1-0528 as a critic checking problem-test alignment, and (3) diversity-based cyclic sampling across 14 task categories. For 14 low-resource languages lacking sufficient seed data, an approximate language translation step converts problems from high-resource languages (Python, Java, C++, JavaScript, Shell) before re-filtering.

## Results

On AutoCodeBench (3,920 problems, 20 languages), no model exceeds 55.5% average Pass@1, with Claude Opus 4.1 (reasoning) leading at 55.4% and GPT-5 at 53.5%. The union upper bound across all evaluated models reaches 75.3%, indicating substantial complementary strengths. Over 60% of problems are classified as hard (zero correct solutions from DeepSeek-Coder-V2-Lite in 10 samplings), and multi-logic problems (1,622 total) cause significant performance drops for all models. On low-resource languages, the inter-model performance gap widens to Δ6.3 compared to Δ3.1 on popular languages, underscoring uneven multilingual capability.

## Baselines & Comparisons

AutoCodeBench is positioned against five prior benchmarks along five axes: multilingual coverage, multi-logic tasks, human-free construction, balanced language distribution, and difficulty. Compared to HumanEval (164 Python problems, 1-star difficulty) and MBPP (378 Python problems, 1-star), AutoCodeBench is dramatically harder (5-star) and spans 20 languages with balanced distribution. Against LiveCodeBench (1,100 Python-only problems, 5-star difficulty), AutoCodeBench matches the difficulty level but adds multilingual and multi-logic coverage. Versus FullStackBench (1,687 problems, 12 languages, 2-star difficulty) and McEval (2,007 problems, 9 languages, 2-star), AutoCodeBench is substantially harder (5-star vs. 2-star), covers more languages (20 vs. 12/9), and uniquely includes multi-logic problems and a fully human-free pipeline. In the training experiments (Table 6), AutoCodeInstruct + two-stage GRPO improves Qwen2.5-Coder-32B from 35.8 to 41.6 on ACB-Full and from 57.1 to 59.7 on FullStackBench, while also gaining 5.0 points on McEval, demonstrating cross-benchmark transfer beyond the in-domain benchmark.

## Relation to Prior Work

This paper departs from the dominant paradigm of manually annotated code benchmarks (HumanEval, MBPP, LiveCodeBench, FullStackBench, McEval) by introducing a fully automated LLM-sandbox pipeline for benchmark construction. Conceptually, it extends the data synthesis line (Evol-Instruct, OSS-Instruct, KodCode) from training-data augmentation to benchmark creation, but introduces two key methodological departures: (1) LLMs generate test *inputs* while a sandbox produces *outputs*, avoiding the well-known failure mode of LLMs hallucinating incorrect expected outputs on hard problems, and (2) a reverse-generation paradigm where code solutions and test functions are synthesized first and the natural-language problem is derived afterward, guaranteeing verifiable correctness. The multi-logic problem category (requiring multiple independent functional units in a single task) has no direct analogue in prior benchmarks, which almost exclusively target single-functionality tasks.

## Why It Matters / Open Questions

AutoCodeBench provides the first large-scale, human-free, balanced multilingual code benchmark (3,920 problems, 20 languages, >60% hard), addressing the scalability and coverage limitations that have constrained prior evaluations. The finding that even the best model (Claude Opus 4.1) reaches only ~55% while the collective upper bound is 75% underscores substantial headroom, and the widening performance gap in low-resource languages (Δ6.3 vs. Δ3.1 in popular languages) highlights an under-addressed dimension of model capability. The accompanying AutoCodeInstruct training set and multilingual sandbox service make the contribution immediately actionable for both evaluation and RL training. Open questions include whether the LLM-as-Critic stage fully guarantees test completeness, how bias from using DeepSeek models throughout the pipeline affects cross-family fairness, and whether the approach extends to repository-level (SWE-Bench-style) tasks.
