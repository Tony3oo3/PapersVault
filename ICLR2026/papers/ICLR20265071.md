## Problem

LLM API providers promise version-pinned, consistent models, but users have no practical way to verify this, and existing change-detection methods are prohibitively expensive for continuous monitoring. This leaves model updates, quantization swaps, and potential backdoor injections largely unmonitored in production. The paper asks whether the log probabilities returned by LLM APIs—typically underutilized—contain enough signal to detect even tiny model changes at a fraction of the cost of token-based benchmarks.

## Input / Output

The method consumes a single-token prompt (e.g., the letter 'x') sent to two LLM APIs, requesting only the top-k logprobs (k=5–20 depending on provider) of the first output token, repeated N times per API. Missing tokens in a sample's top-k list are conservatively imputed with that sample's minimum logprob value. The output is a p-value from a permutation test, with the underlying test statistic being the mean absolute distance between per-token average logprobs across the two APIs; a p-value below a chosen significance level α indicates the APIs are not serving the same model.

## Method

Logprob tracking (LT) treats each returned logprob as a noisy sample from an underlying distribution, accounting for the well-known non-determinism of LLM inference (batch-level effects, GPU routing, kernel variability). For each token observed across both APIs, it computes the empirical mean logprob over N samples, then defines the test statistic as the mean absolute distance between these per-token means. A two-sample permutation test on the pooled 2N samples yields a p-value under the null hypothesis that both APIs share the same logprob distribution, requiring no parametric assumptions about the logprob distribution shape. The key insight is that even a single input token and single output token suffice: because model modifications (fine-tuning, pruning, quantization) shift all weights, the first-token logprob distribution is sensitive to changes as small as one fine-tuning step, while the permutation test absorbs the run-to-run noise. This makes LT roughly 1,000× cheaper than token-based baselines (28 tokens per test vs. ~21,000–29,000) while achieving higher ROC AUC (0.915 vs. 0.878 and 0.670) on the TinyChange benchmark.

## Results

On the TinyChange benchmark (5 open-weight LLMs, 290 variants), logprob tracking (LT) achieves an overall ROC AUC of 0.915 (95% CI: 0.864–0.958), compared to 0.878 for MMLU-ALG and 0.670 for MET. LT requires only 28 input + 20 output tokens per hypothesis test, versus 2.1×10⁵ + 9.9×10³ for MMLU-ALG and 2.9×10⁴ + 2.0×10⁴ for MET, yielding an annual monitoring cost of $0.14 versus $332 and $146 respectively at GPT-4.1 pricing. In terms of sensitivity, LT detects weight-pruning changes as small as 2⁻¹⁰ fraction of weights removed, compared to 2⁻⁴ for MMLU-ALG and 2⁻¹ for MET. In a 4-month real-world deployment across 189 API endpoints from 10 providers, LT identified 37 suspected changes across 29 endpoints and 7 providers.

## Baselines & Comparisons

LT outperforms both baselines on every metric. Against MET (Gao et al., ICLR 2025), which uses MMD with a Hamming distance kernel over 25 prompts and 50-token responses, LT achieves a substantially higher AUC (0.915 vs. 0.670) while using roughly 1,000× fewer tokens per test (28 vs. ~49,000), making it 2–3 orders of magnitude more sensitive to small changes (e.g., detecting pruning at 2⁻¹⁰ vs. 2⁻¹ fraction of weights). Against MMLU-ALG (adapted from Chen et al., 2023), which evaluates 100 multiple-choice questions with 5 output tokens each, LT achieves a modest AUC gain (0.915 vs. 0.878) but at a dramatically lower cost (28 tokens vs. ~220,000 tokens per test, a ~7,500× reduction), and is 1–2 orders of magnitude more sensitive. The one area where LT does not clearly dominate is LoRA fine-tuning detection, where all three methods struggle, though LT still maintains the highest AUC. The cost advantage is the most striking: at GPT-4.1 pricing, hourly monitoring costs $0.14/year with LT versus $146–$332/year for the baselines.

## Relation to Prior Work

This paper departs from the dominant paradigm in LLM API change detection, which relies on comparing output tokens across many prompts (Chen et al. 2023, Gao et al. 2025, Cai et al. 2025), by instead exploiting the top-k log probabilities returned alongside tokens. While logprobs have previously been studied for information leakage (Finlayson et al. 2024, Carlini et al. 2024) and prompt recovery (Morris et al. 2023), their use as a change-detection signal under inference non-determinism is new. The TinyChange benchmark also carves new ground: prior evaluation used ad-hoc model pairs, whereas this paper systematically generates 58 variants per model across five modification axes (fine-tuning, LoRA, pruning, noise) at graduated magnitudes, enabling sensitivity measurement rather than binary detection.

## Why It Matters / Open Questions

The 1,000× cost reduction (from ~$332/year to ~$0.14/year per endpoint at GPT-4.1 pricing) makes continuous third-party monitoring of LLM APIs practically feasible for the first time, and the real-world deployment across 189 endpoints confirmed 37 undisclosed changes—34 of them on open-weight models—demonstrating that the problem is not hypothetical. Key limitations remain: the method requires logprob API support (currently only ~23% of endpoints), cannot distinguish the source of a change (model update vs. infrastructure), and is vulnerable to provider evasion via caching or output-length enforcement. Open questions include whether more sophisticated sequential methods (e.g., CUSUM) can further improve sensitivity, and whether the single-token-of-output constraint can be relaxed to catch changes that only manifest in later tokens.
