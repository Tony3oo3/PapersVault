## Problem

Existing Lean search engines are trained on LLM-generated informalizations of formal statements, which occupy a different embedding subspace than the queries real mathematicians actually type (demonstrated via PCA). This domain gap means retrieval systems are over-tuned to a neutral, paraphrase-like distribution that misses the diverse intents, motivations, and perspectives working mathematicians bring to their queries, resulting in poor alignment with user needs.
![Teaser figure](../imgs/ICLR20265253/cropped_page1_idx0.webp)

## Input / Output

Lean Finder accepts five input modalities: free-form natural language queries (synthesized to mimic real user intents), informalized natural-language statements, raw Lean proof states (subgoals with context and target), augmented proof states (proof states enriched with a GPT-4o-generated natural-language description of the intended proof transition), and formal Lean statements (declaration without proof body, optionally with 20% token corruption to simulate noisy recall). The output is a ranked list of formal Lean statements from a corpus spanning mathlib4, research-linked GitHub repositories, and domain-specific libraries, with the top results displayed alongside their informalizations in the web interface.

## Method

The core innovation is a reverse query-synthesis pipeline: rather than annotating scarce real queries with answers, the authors cluster 693 real Zulip/GitHub discussions into five intent categories (lemma search, metaprogramming, type-class issues, proof engineering, library design), then prompt GPT-4o to generate 582K synthetic queries from formal Lean statements conditioned on each applicable intent cluster. Training proceeds in two stages: first, contrastive learning (InfoNCE with in-batch negatives, temperature 0.01) on 1.4M query-code pairs across all four modalities, fine-tuning DeepSeek-Prover-V1.5-RL 7B via LoRA (rank 64) and extracting the final-token hidden state as the embedding; second, DPO fine-tuning on 1,154 preference triplets collected from user up/downvotes, blinded pairwise comparisons against Lean Search, and GPT-4o-judged Zulip queries, where the standard DPO objective is adapted to retrieval by substituting sequence log-likelihoods with cosine-similarity differences between chosen and rejected statements, jointly optimized with the contrastive loss (λ=0.01) to prevent retrieval degradation.

## Results

On informalized statements, Lean Finder achieves 64.2% Recall@1 and 0.75 MRR, surpassing Lean Search (49.2% R@1) by over 30% relatively and GPT-4o stem-match (21.1% R@1) by 3x. On synthetic user queries, it reaches 54.4% R@1 vs. 47.1% for Lean Search. On augmented proof states, Lean Finder achieves 24.6% R@1, outperforming Lean State Search (4.99%) and Real Prover Search (8.0%) by 5–3x. In a user study with 5 participants on 128 real GitHub queries, Lean Finder is preferred in 81.6% of top-3 rankings (vs. 56.9% for Lean Search and 54.1% for GPT-4o).

## Baselines & Comparisons

Lean Finder outperforms all five baselines across every input modality tested. Against Lean Search (Gao et al., 2024a), it gains +15.0 R@1 on informalized statements (64.2 vs. 49.2), +7.3 on synthetic user queries (54.4 vs. 47.1), and +23.5 on augmented statements (82.7 vs. 59.2). On proof states, Lean Finder dominates Lean State Search (Tao et al., 2025b) by ~5x on augmented states (24.6 vs. 4.99 R@1) and ~2.5x on raw states (8.3 vs. 3.3), and beats Real Prover Search (Shen et al., 2025) by 3x on augmented states (24.6 vs. 8.0) and marginally on raw states (8.3 vs. 7.1). Against the larger Qwen3-Embedding-8B (Zhang et al., 2025), Lean Finder leads by +6.5 R@1 on informalized statements and +13.2 on synthetic queries, while on augmented statements the gap narrows to +6.5. Lean Explore (Asher, 2025) is the closest competitor on augmented statements (86.8 vs. 85.8 R@1) but is far behind on informalized (65.7 vs. 35.0) and synthetic query (57.3 vs. 26.3) inputs. GPT-4o with web search performs worst overall, achieving only 21.1% R@1 (stem match) on informalized statements, confirming that general-purpose LLMs struggle with precise Lean statement retrieval.

## Relation to Prior Work

This paper extends the line of Lean/mathlib semantic search engines (Lean Search, Lean State Search, Real Prover Search) by identifying and addressing a domain gap: prior systems are trained on LLM-generated informalizations that do not match the distribution of real user queries, as evidenced by PCA analysis. The key methodological departure is a two-stage pipeline combining contrastive learning on intent-synthesized queries (derived from clustering real Zulip/GitHub discussions into five semantic intent categories) with DPO-based preference alignment, adapting the DPO objective from sequence generation to retrieval over candidate statements. The base model is DeepSeek-Prover-V1.5-RL 7B, fine-tuned with LoRA, positioning the work at the intersection of dense retrieval, code search, and preference optimization for formal mathematics.

## Why It Matters / Open Questions

The 1.4M-pair Lean code search dataset and the user-intent-aware retrieval framework address a first-order pain point in formal mathematics: locating the right lemma among 230k+ theorems in mathlib4. The finding that GPT-4o with web search achieves only 14.8% Recall@1 (vs. 64.2% for Lean Finder) underscores that general-purpose LLMs cannot substitute for domain-specific retrieval, reinforcing the need for specialized tools. Limitations include a modest 'alignment tax' from DPO (slight degradation in retrieval metrics), only marginal gains when integrated as a RAG backbone for LLM provers, and reliance on GPT-4o for data synthesis. Open questions include whether the five-cluster intent taxonomy generalizes across proof assistants or mathematical domains, and whether the approach can be extended to multi-turn interactive search.
