## Problem

Numpy-like tensor notation is difficult to read and write, and prone to shape errors, because it relies on a large, inconsistent collection of operations each with its own vectorization rules (broadcasting, axis parameters, advanced indexing, function-specific conventions). Existing alternatives such as einsum and einops address readability but are inherently restricted to a limited set of operations (dot-product, reduction, rearrangement) and lack the generality needed for a universal model of tensor programming.

## Input / Output

The method takes one or more n-dimensional tensor arguments plus a declarative vectorization string that specifies how the elementary operation is applied across axes. The string uses symbolic axis names, square brackets to mark argument sub-tensor axes passed to the elementary operation, parentheses for flattened axis compositions, the plus operator for concatenated axes across multiple tensors, and generalized ellipses for variable-length axis groups. The output is the resulting tensor(s) computed by the backend framework, and optionally an inspectable compiled Python code snippet showing the exact sequence of framework calls (reshape, transpose, vmap, etc.) that implements the operation.

## Method

The core insight is that all tensor operations in Numpy-like frameworks decompose into a small set of elementary operations (scalar, reduction, dot-product, identity, indexing) differing only in their vectorization pattern. Einx represents this vectorization using declarative, pointful expressions defined by direct analogy with loop notation: the user writes the loop that would apply the elementary operation to individual sub-tensors, and the einx string encodes which axes are vectorized versus which form the argument sub-tensor. The implementation compiles each einx expression into an isolated Python code snippet via a three-stage pipeline (AST parsing with ellipsis expansion and axis-length solving, computational graph construction, and topological code generation), supporting both Numpy-like and vmap backends with zero runtime overhead after initial compilation. Key notational innovations over einsum/einops include generalized ellipses that expand per-axis, axis concatenation for representing stack/concatenate as vectorized identity maps, implicit output inference, and separation of elementary operations into individual entry-points that catch silent failures from expression typos.

## Results

einx achieves full support (P, F, R, C) for all six operation classes (identity, scalar, reduction, dot-product, indexing, and any other), whereas no existing ein*-notation covers all classes. In the multi-head attention case study, einx requires only 3 lines of code versus 7+ lines in the einsum/einops/Numpy-like implementation. The compiled einx operations incur less than 0.1 ms of cache-retrieval overhead after initialization, and the overhead disappears entirely under just-in-time compilation (e.g., jax.jit). Table 1 demonstrates that 20+ distinct Numpy-like function calls (torch.take, torch.gather, np.outer, np.kron, np.matmul, np.tensordot, np.transpose, np.broadcast_to, np.concatenate, np.meshgrid, etc.) all reduce to just 4 einx elementary operations (get_at, multiply, dot, id) differing only in their vectorization expression.

## Baselines & Comparisons

Against einsum, einx extends coverage from 4 operation classes (identity, scalar, reduction, dot-product) to all 6, adding full indexing and arbitrary-operation support, and introduces axis concatenation (C) and repetition (R) that einsum lacks entirely. Against einops (reduce/repeat/rearrange/einsum), einx adds indexing and arbitrary-operation support, and supports concatenation (C) for identity operations where einops only offers it via the separate pack/unpack entry-point. Against einops.pack/unpack, einx expresses concatenation and splitting as special cases of the vectorized identity map with a unified notation, supporting more vectorization patterns (e.g., transposed concatenation, multi-tensor stacking) that have no single entry-point in einops. Against eindex, einx generalizes indexing to the same notation as all other operations (rather than requiring a dedicated entry-point with the coordinate axis fixed as the first axis), and supports additional vectorization patterns (e.g., broadcasting the coordinate tensor) that eindex cannot express. In the MHA case study, einx's explicit bracket notation makes it immediately visible which axes are contracted (e.g., only k is summed), whereas einsum's implicit convention obfuscates this; einx also self-documents axis names in the softmax call, eliminating the need for a positional axis argument.

## Relation to Prior Work

This paper extends the ein* notation family (einsum, einops) by identifying vectorization as the universal mechanism underlying all tensor operations, thereby generalizing from the limited set of operations those notations support to an arbitrary, open set. It draws on the vmap transformation from Jax as a formalization of vectorization and on loop notation as the interpretive foundation for its declarative expressions, while departing from einops by introducing axis concatenation, generalized ellipses, and a strict separation of elementary operations into individual entry-points. The paper also positions itself against named tensor frameworks and other pointful notations (Tensor Comprehensions, Dex), arguing that einx's universality and seamless integration with existing positional-tensor ecosystems give it a practical advantage.

## Why It Matters / Open Questions

The 'it's all just vectorization' framing offers a genuinely unifying mental model that could reduce the cognitive load of writing tensor programs and eliminate a large class of shape errors by replacing dozens of function-specific rules with one consistent notation. However, the paper's contribution is primarily notational and conceptual rather than algorithmic; its practical impact hinges on community adoption, and the benchmark evidence (Table 3) only shows negligible overhead rather than performance gains. Open questions include whether the notation scales well to highly dynamic or data-dependent shapes, how it interacts with automatic differentiation and higher-order transformations beyond vmap, and whether the added expressiveness (axis concatenation, generalized ellipses) introduces its own learning curve that offsets the simplicity gains.
