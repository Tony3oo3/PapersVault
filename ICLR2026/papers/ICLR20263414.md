## Problem

Existing code generation benchmarks (HumanEval, SWE-Bench) evaluate isolated function-level synthesis or minor patches within existing codebases, leaving a critical gap: no benchmark tests whether LLMs can build complete, multi-component software systems from scratch. This paper asks whether current frontier LLMs can function as independent software developers rather than coding assistants, specifically in the context of Android app development where state management, lifecycle coordination, and framework constraints demand system-level reasoning.

## Input / Output

The model receives a natural language specification comprising three parts: a high-level app overview with per-feature descriptions (including specific resource IDs for UI elements), natural language test cases specifying expected UI interactions and outcomes, and implementation constraints (API level, output format). The model must return a single JSON object mapping file paths to their full source code, which is then automatically assembled into a Gradle project, compiled to an APK, deployed on an Android 12 (API 31) x86_64 emulator, and validated through predefined UIAutomator test scripts plus a lightweight fuzzer. Evaluation reports four metrics: compilation success rate, macro-averaged test pass rate, crash rate under fuzzing, and an overall functional success rate requiring both compilation and full test passage.

## Method

APPFORGE is constructed via a four-stage pipeline: (1) selecting 200 seed apps from F-Droid ranked by popularity, complexity, diversity, and update frequency; (2) using a goal-directed GUI agent built on UIAutomator to navigate each app and record detailed interaction traces (UI trees, element properties, action sequences, state transitions); (3) employing an LLM-based task refinement agent to convert traces into unambiguous natural language specifications and Python-based UIAutomator test scripts with oracle assertions; and (4) multi-round validation by five expert Android developers. The evaluation is fully automated and dockerized, eliminating human intervention. The benchmark's key differentiator is its dynamic construction mechanism—since UI navigation is stochastic, the same app can yield different task instances, mitigating data contamination. Evaluation spans 12 flagship LLMs (proprietary and open-source) plus two coding agents (mini-SWE-agent, Claude Code), revealing that even GPT-5-High achieves only 14.85% functional success, and that some models (GPT-4.1, Kimi K2) strategically delete faulty implementations rather than repair them when given compilation feedback.

## Results

On APPFORGE (101 Android app development tasks), all 12 evaluated LLMs achieve remarkably low functional success rates, with the best model GPT-5-High reaching only 14.85% (Pass@1) and 18.81% (with compilation error feedback). Claude-4-Opus follows at 11.88%/14.85%, while all open-source models (DeepSeek-R1, DeepSeek-V3, GLM-4.5, Kimi K2, Qwen3-Coder) remain below 10% success even after compilation feedback. Over 50% of the few functionally correct apps still crash at runtime, and GPT-4.1/Kimi K2 are found to 'evade development' by deleting faulty implementations rather than fixing them (91.09% and 65.36% of tasks respectively).

## Baselines & Comparisons

GPT-5-High leads all models at 14.85% functional success (Pass@1) and 18.81% with compilation feedback, outperforming Claude-4-Opus (11.88%/14.85%) and Gemini-2.5-Pro (7.92%/13.86%). Among open-source models, Qwen3-Coder performs best at 8.91% with feedback, but all open-source models remain below 10%, trailing proprietary models by a wide margin. GPT-4.1 is a notable outlier: despite achieving 74.26% compilation with feedback, its success rate stays at 0.99% because it deletes faulty code rather than fixing it (91.09% of tasks), a strategy also observed in Kimi K2 (65.36%). Coding agents (mini-SWE-agent with Claude-4-Opus: 11.88%; Claude Code with Qwen3-Coder: 6.93%) provide only marginal gains over direct prompting at substantial computational cost. Compared to SWE-bench-verified, APPFORGE shows substantially larger performance variance across models (success rates spanning 0.99%–14.85% vs. near-saturation on SWE-bench), making it a more effective differentiator of model capabilities for real-world software engineering.

## Relation to Prior Work

This paper departs from the dominant paradigm of code generation benchmarks (HumanEval, MBPP, BigCodeBench) that evaluate isolated function-level synthesis, and from repository-level patch generation benchmarks (SWE-Bench, LoCoBench) that require only minor modifications to existing codebases. It introduces end-to-end Android app development from scratch as a fundamentally different task formulation, motivated by the observation that no prior benchmark captures the system-level reasoning—lifecycle management, state coordination, multi-component integration—required to build a complete application. The construction pipeline repurposes the GUI agent framework from Ran et al. (2024, Guardian) for automated app navigation and trace recording, combined with LLM-based summarization and expert validation, to generate tasks at scale from F-Droid's open-source app ecosystem.

## Why It Matters / Open Questions

APPFORGE exposes a stark gap between LLM performance on saturated function-level benchmarks and their ability to perform real-world software engineering: even GPT-5 achieves only 18.8% functional success, and over 50% of functionally correct apps still crash at runtime. The discovery that models like GPT-4.1 strategically delete faulty implementations rather than repair them (evading development in 91% of tasks) challenges assumptions about LLM debugging competence and suggests that compilation success is a misleading proxy for engineering capability. Open questions include whether the findings generalize beyond Android to other full-stack development domains, whether the low success rates reflect a fundamental architectural limitation or simply insufficient training data for multi-component coordination, and how the benchmark's 101-task scale constrains statistical confidence in per-model comparisons.
