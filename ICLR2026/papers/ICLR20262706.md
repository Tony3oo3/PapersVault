## Problem

LLMs perform well on high-resource languages like Python but struggle on low-resource languages (Fortran, Julia, R, OCaml, Lua) that remain essential in science and engineering. Beyond pre-training data scarcity, post-training itself is a per-language bottleneck: each new language traditionally requires bespoke datasets, test translators, and RL infrastructure. The paper asks whether a single, language-agnostic RL environment can eliminate this per-language engineering tax.

## Input / Output

The pipeline takes (1) language-agnostic programming problems specified purely as stdin/stdout I/O pairs, (2) a 4–5 line YAML configuration that specifies the target language's prompt prefix, install command, filename, and execute (and optionally compile) shell commands, and (3) a base LLM checkpoint. It produces a fine-tuned model that emits code in the target language within a Markdown block, which the verifier extracts, compiles if needed, and tests against the I/O examples. The verifier's own implementation language is independent of the target language, and the I/O convention (plain-text stdin/stdout with explicit formatting rules) is what makes a single verifier universal across all languages.

## Method

The core insight is that for a large class of coding tasks, correctness is a property of the program's externally observable I/O behavior rather than of internal function signatures, so a single verifier can test solutions in any language. Data preparation uses an LLM to reformulate existing unit-test datasets (MBPP, Codeforces, LiveCodeBench) into this uniform I/O format, eliminating the need for per-language test translators. Training applies GRPO with verifiable rewards (RLVR): the model samples a group of candidate programs, each is executed in a language-agnostic OCI container sandbox that compiles, runs, and checks I/O correctness, and binary pass/fail rewards are converted into group-relative advantages for policy updates. The sandbox maintains a pool of warm containers with timeouts on compilation and execution, a fixed-size output buffer to prevent memory blowups, and a RAM disk for faster compilation; Ray distributes generation (GPU nodes) and execution (CPU nodes) across heterogeneous hardware. Notably, the authors omit the KL-divergence term and reject partial-credit rewards after observing that models exploit them by producing trivial or hard-coded outputs.

## Results

On Ag-LiveCodeBench-X (pass@1), Qwen3-4B-CF-X achieves 23/22/15 on Lua/Julia/R, and Qwen3-8B-CF-X achieves 25/25/19, matching or exceeding the 16B DeepSeek Coder v2 Lite Instruct (13/12/9) and approaching the 70B Llama 3.3 (25/22/13). On the harder OCaml and Fortran languages, the 4B model improves from near-zero base accuracy to 7% and 15% respectively, outperforming even Sonnet 4 (6%/6%). On MultiPL-E, Qwen3-8B-CF-X reaches 68/61/52 on Lua/Julia/R, a 1.5–2× improvement over its base model.

## Baselines & Comparisons

Against Llama 3.3 70B Instruct, Qwen3-8B-CF-X matches on Lua (25 vs 25), exceeds on Julia (25 vs 22), and beats on R (19 vs 13) on Ag-LiveCodeBench-X. Against Qwen3 32B, the 8B model wins on Lua (25 vs 22) and R (19 vs 17) but trails slightly on Julia (25 vs 26). Against the 16B DeepSeek Coder v2 Lite Instruct, both 4B and 8B Agnostics models substantially outperform it across all three languages (e.g., 23 vs 13 on Lua). Against the smaller non-Qwen baselines (SmolLM3 3B, Phi 4 Mini, DeepSeek Coder 6.7B), Agnostics-trained models achieve 2–3× higher Ag-LiveCodeBench-X scores (e.g., 23 vs 1 for SmolLM3, 23 vs 8 for Phi 4 Mini on Lua). On MultiPL-E, Qwen3-8B-CF-X improves over its base by 5/8/8 points on Lua/Julia/R, confirming gains generalize beyond the I/O training format.

## Relation to Prior Work

This paper builds on the GRPO reinforcement learning algorithm (Shao et al., 2024) and the RLVR paradigm popularized by DeepSeek-R1 (DeepSeek-AI et al., 2025), applying efficiency tweaks from DAPO (Yu et al., 2025). It departs from MultiPL-T (Cassano et al., 2024), which requires per-language test translators and rejection sampling, by reframing code correctness as externally observable I/O behavior so that a single language-agnostic verifier works for any target language. The key conceptual departure is that the verifier's implementation language is independent from the language being learned, eliminating the need for language-specific compilers or type-mapping expertise that prior approaches demanded.

## Why It Matters / Open Questions

The practical impact is significant: adapting the pipeline to a new language requires only a 4–5 line YAML configuration (under an hour of work), making RL post-training for low-resource languages accessible to practitioners without deep language expertise. The new Ag-LiveCodeBench-X benchmark is challenging even for frontier models as of early 2026, filling a gap left by MultiPL-E which is saturated. Limitations include experiments capped at 8B parameters due to compute constraints, and the approach is restricted to tasks expressible as standard I/O programs (no interactive or multi-turn tasks). Open questions include whether the method scales to larger models, whether it extends to non-I/O task formulations, and how it performs on languages without a simple command-line toolchain.
