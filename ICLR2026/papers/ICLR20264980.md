## Problem

LLM agents deployed for software engineering tasks frequently receive underspecified instructions, yet current benchmarks like SWE-Bench Verified only evaluate well-specified issues and prior underspecificity work considers at most a single missing detail. This paper asks whether agents can (a) detect when information is missing, (b) ask targeted clarification questions, and (c) leverage the resulting interaction to recover performance—capabilities that are critical for safe, resource-efficient deployment but remain unmeasured in existing evaluations.

## Input / Output

The agent receives a synthetically summarized GitHub issue (generated by GPT-4o to strip code snippets, error messages, and file references while preserving key terminology) alongside a live code repository inside an OpenHands sandbox. In the Interaction setting, a GPT-4o user proxy holds the full issue plus file-location hints and responds to at most three clarification turns, answering only from the original issue text or replying 'I don't have that information.' The agent produces a git patch verified against SWE-Bench unit tests, and the evaluation additionally records the agent's interaction decision (ask vs. proceed), the specific questions posed, and per-turn information gain measured by embedding cosine distance and a GPT-4o LLM-as-judge score.

## Method

Ambig-SWE extends SWE-Bench Verified (500 issues) with GPT-4o-generated underspecified variants and introduces a three-setting interactive evaluation protocol—Full (complete issue, no interaction), Hidden (summarized issue, no interaction), and Interaction (summarized issue plus a GPT-4o user proxy holding the full specification)—all run within the OpenHands agentic framework. The core methodological contribution is decomposing underspecificity resolution into three independently measurable capacities: detection (measured via FPR/FNR across three prompt-encouragement levels on randomly mixed full/hidden issues), question quality (measured via cosine-distance information gain and LLM-as-judge specificity scores), and task-level leverage (measured via resolve-rate deltas with Wilcoxon Signed-Rank tests between settings). Six models spanning proprietary (Claude Sonnet 4, Sonnet 3.5, Haiku 3.5) and open-weight (Llama 3.1 70B, DeepSeek-V2, Qwen 3 Coder) families are evaluated, with the user proxy constrained to prevent hallucination by restricting responses to information explicitly present in the full issue. The framework further distinguishes informational queries (expected behavior, error nature) from navigational queries (file paths), enabling analysis of how each information type differentially affects resolve rates across models.

## Results

On Ambig-SWE (500 issues from SWE-Bench Verified), interaction with a user proxy improves resolve rates by up to 74% over the non-interactive Hidden setting across all models. Claude Sonnet 4 achieves the highest relative recovery (89% of Full-setting performance), followed by Claude Sonnet 3.5 and Haiku 3.5 (~80%), while DeepSeek-V2 and Llama 3.1 70B recover only 59% and 54%, respectively. For underspecificity detection, Claude Sonnet 4 reaches 89% accuracy with strong prompting, while Qwen 3 Coder fails entirely (100% false-negative rate across all prompt conditions).

## Baselines & Comparisons

Claude Sonnet 4 outperforms Claude Sonnet 3.5 in both absolute resolve rate (67.24% vs. 59.52% in Interaction) and detection accuracy (89% vs. 84% at best prompt), confirming gains from model scaling. Qwen 3 Coder matches or exceeds Claude Sonnet 4 in raw information extraction (cosine distance 0.179 vs. 0.171) but achieves a lower Interaction resolve rate (52.38% vs. 67.24%) due to rigid protocol-following that wastes turns re-discovering file locations. Among open-weight models, DeepSeek-V2 and Llama 3.1 70B trail proprietary models by a wide margin (13.19% and 6.34% Interaction resolve vs. 59–67% for Claude models), with Llama 3.1 also showing the poorest question quality (2.61 avg. questions, 0.101 cosine distance). Notably, Qwen 3 Coder is the only model that completely refuses to interact under any detection prompt (100% FNR), while Claude Haiku 3.5, despite fewer parameters, recovers a similar fraction of Full-setting performance (80%) as Claude Sonnet 3.5, suggesting interaction leverage is not strictly tied to model scale.

## Relation to Prior Work

This paper extends SWE-Bench Verified by constructing underspecified variants of its GitHub issues and wrapping them in an interactive evaluation framework (Ambig-SWE) where agents can query a GPT-4o user proxy holding the full specification. It builds on prior underspecificity/ambiguity detection work (Kim et al., 2024; Zhang & Choi, 2023; Chen et al., 2025), which typically isolates a single missing detail in simpler settings, by studying multiple interdependent specification gaps that emerge dynamically over multi-step agentic trajectories. The interactive evaluation design draws on LLM-as-user simulation (Li et al., 2024; Xu et al., 2024) and the OpenHands agentic framework (Wang et al., 2024b), but departs from prior work by decomposing underspecificity resolution into three independently measurable capabilities—detection, question quality, and information integration—rather than treating it as a single end-to-end task.

## Why It Matters / Open Questions

The paper provides the first systematic decomposition of how LLM agents handle underspecified instructions in realistic software engineering workflows, revealing that even top-performing models (Qwen 3 Coder, Llama 3.1 70B) fail to detect missing information or default to non-interactive behavior without explicit prompting. The finding that interaction recovers up to 74% of the performance gap yet yields no efficiency gains, and that coding ability does not predict interaction integration ability (Haiku 3.5 ≈ Sonnet 3.5 in relative recovery), challenges the assumption that stronger models will naturally handle underspecificity better. Open questions include whether dedicated training (beyond prompt engineering) can close the detection gap, whether the simulated user proxy adequately captures real user behavior, and whether the three-step decomposition generalizes to non-code agentic domains.
