## Problem

Running 30-70B LLMs on consumer home clusters (mixed CPUs/GPUs, insufficient RAM/VRAM, slow disks, Wi-Fi, heterogeneous OSs) remains impractical: existing distributed systems require sufficient aggregate memory to hold the full model, disk offloading inflates TPOT to tens of seconds, and heuristic layer partitioning ignores OS-specific memory reclamation and disk heterogeneity. The paper asks how to relax memory constraints while hiding disk latency, and how to design heterogeneity-aware layer partitioning that identifies bottleneck devices.

## Input / Output

The system consumes a text prompt and Q4K/IQ1-quantized LLM weights stored on local disks across a Wi-Fi-connected cluster of 4+ heterogeneous consumer devices (Mac, Linux PC, Android phone, etc.), with inter-device bandwidth of 320-610 Mbps and 3-7 ms latency. It produces generated text tokens at sub-second TPOT (674 ms/token for 70B, 26 tokens/s for 32B with speculative decoding) while maintaining <6% memory pressure per device. Halda additionally outputs a per-device layer window size (w_m) and GPU layer count (n_m) partitioning plan, plus an optimal device subset, recomputable whenever the task queue is empty to adapt to environmental changes.

## Method

Prima.cpp introduces Pipelined-Ring Parallelism (PRP), which connects devices end-to-end in a ring and processes a model in multiple rounds per token using small layer windows, so that prefetching of the next segment overlaps with other devices' compute and communication, resolving the prefetch-release conflict that causes mmap-based offloading to reload all layers twice. To determine optimal window sizes and GPU/CPU layer splits, the paper formulates the Layer-to-Device Assignment (LDA) problem as an NP-hard integer linear fractional program whose objective decomposes into per-device compute (FLOPs/FLOPS per quantization format), memory access, OS-specific disk loading (macOS with/without Metal, Linux, Android), and communication latencies. Halda solves this by enumerating the ≤11 valid integer factors k of the layer count L to convert the fractional program into standard ILPs solved by HiGHS, combined with an iterative calibration loop that reassigns devices to four OS-specific memory sets (M1–M4) until convergence, plus a forced-reassignment step to prevent GPU underutilization. The scheduler also automatically removes weak devices assigned only one layer, reducing to single-device llama.cpp for small models.

## Results

On a 4-device consumer home cluster (Mac M1, Linux laptop, Linux desktop, Android phone) with only 37 GiB aggregated RAM+VRAM, prima.cpp achieves 674 ms/token TPOT and 1793 ms TTFT for a 70B Q4K model, with <6% memory pressure on every device. With speculative decoding, a 32B model reaches 26 tokens/s and the 70B model drops to 442 ms/token. Compared to llama.cpp on the same hardware, prima.cpp reduces TPOT by up to 17× (10120→674 ms at 70B) and TTFT by up to 8×, while exo and dllama both OOM at 65–70B.

## Baselines & Comparisons

Against llama.cpp (single-device, run on the strongest node D3), prima.cpp matches TPOT and TTFT exactly on 8B and 14B models (Halda collapses to single-device), then pulls ahead sharply: at 70B, llama.cpp degrades to 10120 ms/token due to repeated mmap page faults, while prima.cpp stays at 674 ms/token (15× faster). Against exo (pipeline parallelism, memory-ratio partitioning), prima.cpp achieves at least 18× lower TPOT and 42× lower TTFT on every model size where exo does not OOM; exo fails entirely at 70B because it pins weights in RAM and cannot offload to disk. Against dllama (tensor parallelism over Wi-Fi), prima.cpp is at least 18× faster in TPOT; dllama's 64–160 all-reduce operations per token add ~24 s of communication latency at 70B, and it OOMs at 65B. In terms of memory pressure, exo and dllama pin model weights in RAM causing >50% pressure on some devices (and OOM at 65–70B), whereas prima.cpp keeps pressure below 6% on all devices by using mmap with OS-managed page reclamation.

## Relation to Prior Work

This paper extends pipeline parallelism (PP) for distributed LLM inference by introducing pipelined-ring parallelism (PRP), which connects devices in a ring and runs multiple rounds per token to overlap disk I/O with compute and communication. It builds directly on llama.cpp's mmap-based weight loading but departs from prior distributed systems (exo, dllama, Galaxy, Hepti, EdgeShard) in three key ways: (1) it handles insufficient aggregate RAM/VRAM via OS-managed page-cache offloading rather than requiring the full model to reside in memory, (2) it models OS-specific memory reclamation and disk behavior in a formal ILP-based scheduler (Halda) rather than relying on memory-ratio or compute-power heuristics, and (3) it identifies and resolves the prefetch-release conflict that silently negates the benefit of naive prefetching in mmap-based offloading.

## Why It Matters / Open Questions

This is the first system to deliver sub-second TPOT for 70B models on consumer-grade home hardware with under 6% memory pressure, making local embodied AI (surveillance, assistants, companion robots) feasible without cloud dependency or specialized hardware. The prefetch-release conflict is a non-obvious failure mode that likely affects other mmap-based offloading systems, and the ILP formulation for heterogeneity-aware layer partitioning provides a principled alternative to ad-hoc heuristics. Open questions include scalability beyond ~32 devices, robustness to dynamic network conditions (Wi-Fi congestion, device sleep), whether the analytical latency model holds for 100B+ models or MoE architectures, and practical deployment friction (cross-OS build complexity, 20K lines of code). The evaluation is limited to 4–6 devices and a handful of model families, so generalizability to larger, more diverse home clusters remains to be validated.
