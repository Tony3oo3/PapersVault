## Problem

While LLM-based coding assistants are widely assumed to act as a 'Great Equalizer' that flattens the programming landscape, no large-scale empirical study has tested whether they instead reinforce existing popularity hierarchies. This paper investigates the long-term ecosystem-level consequences of AI-assisted programming, asking whether data-rich languages and frameworks receive systematically superior AI support in a self-reinforcing Matthew Effect that could reduce software ecosystem diversity.

## Input / Output

For algorithmic tasks, the input is a LeetCode problem statement (title, description, constraints) paired with a target language specification, formatted into a standardized prompt that explicitly suppresses chain-of-thought reasoning; the output is a single executable code submission judged by LeetCode's online system, yielding a Pass@1 binary plus a six-category error label (Accepted, Compile Error, Wrong Answer, Runtime Error, TLE, MLE). For framework tasks, the input is a set of functional requirements plus a designated technology stack, and the output is a complete multi-file application whose success is measured by the number of iterative error-feedback rounds needed to reach a runnable state under a strict Vibe Coding protocol where no manual code edits are permitted.

## Method

The paper constructs a two-tier benchmark: (1) 3,011 LeetCode problems × 9 languages (spanning TIOBE ranks 1–46) × 5 LLMs (GPT-4o-mini, DeepSeek-V3, Gemini-2.0/2.5-Flash, Qwen3-Turbo) producing 135,495 code generations submitted via a distributed 15-account system with exponential backoff, and (2) 17 general-purpose CRUD tasks plus 8 divergent-technology-pathway tasks evaluated across 6 full-stack combinations using Cursor, CodeBuddy, and Copilot in Agent/Auto modes. A key design choice is selecting newly released 2025 LeetCode problems to use 'data contamination' as a direct signal of training-data coverage, establishing a clearer causal chain from language popularity → training corpus representation → AI performance. A multi-stage code-extraction pipeline (Markdown block detection, language-specific regex comment stripping, debugging artifact removal) ensures clean, directly submittable code. Statistical significance is confirmed via paired t-tests across all 3,011 problems, and the framework tier measures the number of human-free error-feedback iterations required, revealing that mainstream stacks converge in 1–2 rounds while niche stacks demand 5–10.

## Results

Across 135,495 code generation requests (3,011 LeetCode problems × 9 languages × 5 models), the best model (DeepSeek-V3) achieves 79.81% Pass@1 on Python but only 24.31% on Erlang and 20.82% on Racket, a gap of ~55 percentage points. The mean Pass@1 difference between popular languages (Python, C++, C, Java, JavaScript) and less popular ones (Go, Rust, Erlang, Racket) ranges from +28.9% (Qwen3-Turbo) to +44.8% (DeepSeek-V3), all statistically significant (p < 0.001). For framework tasks, mainstream stacks (Vue+Spring Boot, React+Express, Django) resolve most of 17 CRUD tasks in 1–3 iterations, while niche stacks (SolidJS+Actix, Svelte+FastAPI) require 5–10+ iterations or fail entirely.

## Baselines & Comparisons

This is an empirical study rather than a method-vs-baseline comparison, so the key contrasts are across models and across languages/frameworks. Among the five LLMs, DeepSeek-V3 dominates on every language (e.g., 79.81% Python vs. 41.98% for GPT-4o-mini), while Qwen3-Turbo is consistently weakest, particularly on Rust (2.19%) and Erlang (0%). The central finding is that no model can close the popularity gap: even DeepSeek-V3 shows a 55.5-point Pass@1 drop from Python to Erlang, and the gap widens on Hard problems (50–63% for popular languages vs. 0–6% for niche ones). At the framework level, mainstream stacks (Vue+Spring Boot, React+Express, Django) converge in 1–3 correction rounds, middle-ground stacks (Preact+Gin, Svelte+FastAPI) need 2–3 rounds, and niche/emerging stacks (SolidJS+Actix, Elixir/Phoenix, Haskell) require 5–10+ rounds or fail, confirming the Matthew Effect operates at both the language and framework tiers.

## Relation to Prior Work

This paper departs from the dominant line of LLM code-generation evaluation (HumanEval, XCodeEval, Copilot studies) that measures aggregate accuracy on narrow, single-language benchmarks, and instead repurposes the well-studied task of algorithmic code generation as a controlled instrument for measuring ecosystem-level popularity bias. It draws on prior observations of training-data skew (StarCoder's ~40% Python share, CodeGen's acknowledged quality variance, Twist et al.'s 58% Python preference) but elevates them from anecdotal evidence to a large-scale, statistically tested empirical finding across 135,495 submissions. The framework-selection tier extends the analysis beyond languages to full-stack technology choices, a dimension largely absent from prior code-generation benchmarks, and connects to the programming-ecosystem-evolution literature (Meyerovich & Rabkin, Swacha & Kulpa) by introducing AI assistance as a new adoption variable.

## Why It Matters / Open Questions

The paper quantifies a concrete 'AI Productivity Tax' (up to ~55 percentage points Pass@1 gap between Python and Erlang/Racket) that, if left unaddressed, could systematically reduce programming-language and framework diversity as developers gravitate toward AI-friendly stacks. A key open question the authors themselves flag is disentangling AI-specific amplification from pre-existing structural biases in training data—i.e., whether the Matthew Effect is genuinely *caused* by LLMs or merely *revealed* by them. The framework-level results (niche stacks requiring 5–10 correction rounds vs. 1–2 for mainstream) suggest the bias extends beyond syntax to architectural reasoning, but the study's correlational design and single-platform (LeetCode) evaluation limit causal claims. Future work on diversity-aware training, multi-agent collaborative coding, and broader domain coverage would be needed to move from measurement to mitigation.
