## Problem

Traditional virtual machine protection (VMP) relies on rigid, rule-based transformations that produce highly regular instruction patterns vulnerable to automated reverse engineering, yet no learning-based framework has been designed to generate, compare, or reason over VMP-protected code. Large language models have transformed code generation but have not been adapted to the polymorphic, multi-level protection structure of virtualized machine code, leaving a gap between LLM capabilities and software defense needs.
![Teaser figure](../imgs/ICLR20260805/cropped_page2_idx0.webp)

## Input / Output

For code generation, the model receives a structured prompt containing C source code and a target protection level (L0–L3) and produces a corresponding VMP-protected assembly function using virtual instructions marked with [VINST-X] tokens and virtual registers (e.g., %veax, %vreg0). For binary similarity detection and protection effectiveness optimization, the model consumes disassembled VMP code at different protection levels and outputs cosine-similarity-based rankings over a candidate pool of K functions, identifying the variant derived from the same source. The VMP code undergoes four canonicalization steps (debug symbol removal, whitespace normalization, symbolic address substitution, and canonical instruction labeling) before tokenization.

## Method

ShieldedCode introduces a three-level hierarchical attention mask (intra-instruction, preceding-instruction, and inter-instruction) applied to half of the transformer heads, enabling the model to capture local token interactions, short-range register/operand flow, and long-range polymorphic control-flow dependencies simultaneously. Training jointly optimizes a language modeling loss with two contrastive objectives: Functionality Contrastive Learning (FCL) pulls same-function embeddings together with exponentially decaying weights across protection levels, while Protection Contrastive Learning (PCL) enforces linearly-scaled distance separation proportional to protection-level differences via a soft-margin constraint. A Protection Effectiveness Optimization (PEO) task with hard-negative mining further trains the model to rank the correct same-source variant as most similar among K candidates at a different protection level. The full pipeline consists of continual pre-training on CodeLlama-34B over paired (source, normalized VM) data from AnghaBench and The Stack, followed by fine-tuning on 2.5M VMP pairs, with theoretical analysis proving that the joint FCL+PCL objective yields embeddings with weighted functional clustering and proportional protection-level stratification.

## Results

On the primary VM code generation task (HumanEval_compile), ShieldedCode achieves 26.95% Pass@1 at L0 protection, outperforming GPT-4o (22.58%) and all open-source code LLMs (best: DeepSeekCoder-7B at 10.28%). At higher protection levels, ShieldedCode maintains a consistent lead: 19.23% vs. 15.26% (GPT-4o) at L2 and 14.71% vs. 11.89% at L3. On binary code similarity detection (BinaryCorp-VirtualAssembly), ShieldedCode achieves 0.488 Recall@1 and 0.575 MRR on the O0+L1 setting, surpassing jTrans (Linear Probe) by 15.5 percentage points in Recall@1, though it trails jTrans on O1/O2 optimization settings.

## Baselines & Comparisons

On VM code generation (Table 1), ShieldedCode outperforms all 7 baselines across every protection level, with the largest margins over open-source 7B models (e.g., 26.95% vs. 10.28% Pass@1 over DeepSeekCoder-7B at L0) and a 4.37-point advantage over GPT-4o at L0. On binary code similarity detection (Table 2), ShieldedCode dominates all GNN-based and transformer-based baselines (Gemini, GNN, OrderMatters, GraphEmb, Asm2Vec, PalmTree, Trex, jTrans Zero-Shot, DeGPT, BinDiff, CodeBERT-Binary) across all optimization-protection settings. However, against the strongest baseline jTrans (Linear Probe), ShieldedCode wins only on O0 settings (0.488 vs. 0.333 Recall@1 at O0+L1; 0.397 vs. 0.309 MRR at O0+L3) but loses on O1 and O2 settings (e.g., 0.306 vs. 0.573 Recall@1 at O1+L1). For long-input handling (Table 3), ShieldedCode's polymorphic generation improves Pass@1 from 12.84% (Granite + standard fine-tuning) to 17.91% average, and outperforms LongCoder's window attention design (19.8% vs. 25.2% average Pass@1). In the ablation (Table 4), ShieldedCode surpasses recent binary code representation methods (ContraBin, CLAP, CEBin) and the xVMP reproduction by 10–20+ points on Pass@1, confirming the contribution of both contrastive learning and polymorphic generation.

## Relation to Prior Work

This paper carves new ground at the intersection of LLM-based code generation and virtual machine protection (VMP), a domain previously addressed only by rule-based commercial tools (VMProtect, Themida). Conceptually, it repurposes contrastive learning (à la SimCSE) and hierarchical attention (cf. Nova for compiler assembly) to the substantially harder regime of polymorphic VMP bytecode with virtual registers and dispatcher-based control flow. It departs from prior binary similarity detection work (jTrans, Trex, Asm2Vec) by extending the task from unprotected binaries to VMP-protected code, and from standard code LLMs (CodeLlama, DeepSeekCoder) by introducing protection-aware objectives (FCL, PCL, PEO) that have no analogue in prior code-generation literature.

## Why It Matters / Open Questions

The paper opens a genuinely new research direction—using learned representations to generate, compare, and reason about protected code—which could shift software defense from static rule-based transformations to adaptive, data-driven protection. However, several open questions limit near-term impact: the reverse-engineering resistance claim rests on a small user study (15 participants, 20 functions) without adaptive or ML-based attacks; no formal correctness guarantees are provided (acknowledged in Appendix G); and the evaluation is confined to x86-64 C programs with a single (unspecified) commercial VMP tool. Whether the learned protection generalizes to adaptive adversaries who can query the model or who exploit the specific [VINST] tokenization remains untested.
