## Problem

Training LLMs on long contexts is bottlenecked by GPU memory, not compute time: activations and the KV cache scale linearly with sequence length, so even a 256K context can exhaust an A100 before other tensors are allocated. Existing remedies—ZeRO3, tensor parallelism, and context parallelism—require multi-GPU clusters with high-bandwidth interconnects, making million-token training inaccessible to most labs.
![Teaser figure](../imgs/ICLR20263785/cropped_page1_idx0.webp)

## Input / Output

The system consumes pre-trained LLM weights (Qwen2.5-7B or GPT-OSS) and long text sequences constructed by concatenating arXiv samples up to 8M tokens. Sequences are partitioned into fixed-size chunks (default 4K tokens) that are processed serially, so the GPU only ever holds one chunk's activations plus the accumulated KV cache. The output is a fine-tuned model whose context window has been extended, validated by training loss convergence at 256K and 1M token lengths.

## Method

OOMB processes a long sequence chunk-by-chunk in a recurrent fashion: each chunk's forward activations are discarded immediately and recomputed on-the-fly during backpropagation, yielding a constant O(1) activation footprint regardless of total sequence length. This shifts the memory bottleneck to the KV cache, which OOMB manages through three synergistic mechanisms: (1) a paged memory manager with a custom Triton kernel that handles both forward and backward passes in-place, bypassing PyTorch autograd to avoid storing the KV cache as an activation and to accumulate gradients via atomic_add; (2) asynchronous CPU offloading using pinned memory and dedicated CUDA streams, where the next layer's KV pages are pre-fetched during the current layer's computation (or, for sparse attention, overlapped with key/value projections); and (3) page-level sparse attention that retrieves only the top-K most relevant KV pages per query page, reducing both compute and offload volume. The combined system adds only ~10 MB of peak memory per additional 10K context tokens, enabling 4M-token training of Qwen2.5-7B on a single H200 GPU.

## Results

OOMB achieves a near-constant memory footprint for long-context training: for every additional 10K context tokens, end-to-end training memory increases by only ~10 MB for Qwen2.5-7B, enabling a 4M-token context on a single H200 GPU. In per-device throughput (tokens/sec), OOMB with dense attention on 1×H200 reaches 936.22 at 64K and 266.13 at 256K, outperforming Ring Flash Attention on 4×H200 (872.51 and 218.41 respectively). With sparse attention, OOMB on 1×H200 further boosts throughput to 1560.38 (64K) and 1301.60 (256K), yielding speedups of ~3.7× at 64K and up to 13.5× at 256K over the dense-attention baseline.

## Baselines & Comparisons

Against the standard parallel FlashAttention baseline, OOMB with dense attention already achieves lower peak memory at 32K (39.8 GB vs. 65.0 GB) and avoids OOM at 128K and 256K where the baseline fails entirely; with CPU offloading, OOMB keeps memory nearly flat (~34 GB) across all context lengths. Compared to Ring Flash Attention (RFA) on 4×H200, OOMB on a single H200 delivers higher per-device throughput at every tested context length (e.g., 936 vs. 872 tokens/sec at 64K; 266 vs. 218 at 256K), and the sparse-attention variant widens this gap to ~6× at 256K. Against SeCO (the prior chunk-wise training method), OOMB extends the maximum trainable context from 128K to 4M tokens on the same single-H200 hardware, a >10× improvement. Relative to ZeRO3 Offload and Tensor Parallelism (both requiring 8×H200 for 128K–256K), OOMB achieves 4M-token training on 1×H200 with O(1) activation memory versus their O(N) or O(N/8) complexity. The paper does not report a direct head-to-head accuracy comparison against these baselines, as the focus is on system-level memory and throughput efficiency rather than downstream task performance.

## Relation to Prior Work

OOMB extends the chunk-recurrent training paradigm introduced by SeCO (Li et al., 2025), which demonstrated O(1) activation memory but lacked operator-level and memory-management optimizations, limiting it to 16K contexts on consumer hardware. The paged memory design is adapted from PagedAttention (Kwon et al., 2023), originally an inference-time technique, and repurposed here with custom Triton kernels that support backpropagation and bypass PyTorch's autograd. The sparse attention component draws on query-aware page retrieval (Quest, Tang et al., 2024) and block-level sparse attention (MOBA, Lu et al., 2025), while the overall system is positioned as a single-GPU alternative to context parallelism methods like Ring Attention and DeepSpeed Ulysses that require multi-GPU clusters.

## Why It Matters / Open Questions

By reducing the per-10K-token memory overhead to ~10MB, OOMB makes 4M-token context training feasible on a single H200 GPU—a task that previously demanded 256-GPU clusters—potentially democratizing long-context model development for resource-constrained labs. Key open questions include whether the sparse attention approximation degrades performance on tasks requiring dense global reasoning (the paper acknowledges this needs further investigation), whether the serial chunk-processing latency becomes prohibitive at even longer contexts, and how the system scales to models with different attention patterns beyond Qwen2.5 and GPT-OSS. The CPU-GPU interconnect bandwidth dependency also limits portability across hardware configurations.
