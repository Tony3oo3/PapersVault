## Problem

State-of-the-art LLMs achieve only ~15% success rates in generating CUDA code that actually improves speed over reference implementations, as demonstrated on KernelBench. Standard RL algorithms (REINFORCE, GRPO, PPO) use reward signals exclusively for gradient updates and never feed performance feedback into the model's reasoning process, preventing the LLM from learning to reason about performance trade-offs during code generation.
![Teaser figure](../imgs/ICLR20264206/cropped_page1_idx0.webp)

## Input / Output

The method takes a reference PyTorch implementation (from KernelBench's 250 tasks) plus N=2 previously generated CUDA code variants paired with their measured speedup scores, structured into a prompt with task description, scored exemplars, generation protocol, and anti-reward-hacking restrictions. The model must produce a three-part structured response: a comparative performance analysis explaining why certain implementations outperform others, a numbered algorithm design description, and a complete CUDA kernel implementation that is both executable and correct across 1000 random test inputs.

## Method

CUDA-L1 is a three-stage pipeline: (1) SFT on 2,105 successful CUDA snippets collected from six LLMs, (2) iterative self-supervised learning where the model generates code, filters for executability and correctness only, and retrains on successful samples, and (3) contrastive RL using GRPO. The key innovation in stage 3 is embedding performance scores directly into the input prompt alongside multiple code variants, forcing the model to perform comparative analysis of why certain implementations achieve superior performance before synthesizing improved solutions. Exemplar selection uses temperature-scaled softmax over performance buckets (with mean-centering for stability) to balance competitive performance with diversity. Each speedup score serves a dual purpose: as a GRPO reward for gradient-based parameter updates and as prompt content for contrastive reasoning in subsequent iterations, creating a co-evolutionary dynamic between foundation model enhancement and fixed-parameter solution optimization.

## Results

On KernelBench (250 CUDA kernels, A100), CUDA-L1 achieves a mean speedup of ×3.12 (median ×1.42, max ×120) over the default PyTorch baseline, with 249/250 successful compilations and 226/250 kernels achieving >1.01× speedup. Against stronger baselines, CUDA-L1 delivers ×2.77 over Torch Compile, ×2.88 over Torch Compile with reduce overhead, and ×2.81 over CUDA Graph implementations. The model also generalizes across GPU architectures, achieving mean speedups of ×3.85 on H100, ×3.13 on L40, ×2.51 on RTX 3090, and ×2.38 on H20 without retraining.

## Baselines & Comparisons

CUDA-L1 (bucket sampling) substantially outperforms all four foundation model baselines in both vanilla and evolutionary configurations. Against vanilla models, the gap is dramatic: DeepSeek-R1-vanilla achieves only 0.88 mean speedup (18/250 kernels >1.01×) versus CUDA-L1's 3.12 (226/250), and Llama 3.1-405B-vanilla manages just 0.23 mean speedup with only 5/250 improvements. Even the strongest evolutionary baseline, DeepSeek-R1-evolve (1.41 mean, 162/250 speedups), is more than 2× below CUDA-L1's mean and 64 kernels short on the speedup count. The ablation in Table 2 further shows that replacing contrastive-RL with vanilla GRPO (Stage 1+2+GRPO, 2.41 mean) degrades performance by ~23%, confirming that the contrastive exemplar mechanism is critical. CUDA-L1 also surpasses the island-sampling variant (3.21 vs. 3.12 mean) by a narrow margin while achieving a higher 25th percentile (1.17 vs. 1.16), indicating more consistent tail performance.

## Relation to Prior Work

CUDA-L1 builds on two converging research threads: evolutionary LLMs (AlphaEvolve, FunSearch) that present scored code variants for comparative analysis, and RL-augmented LLMs for code optimization (compiler and assembly optimization). The key departure is that contrastive-RL unifies these by embedding performance-scored exemplars directly into the prompt while simultaneously performing gradient-based parameter updates via GRPO, whereas evolutionary LLMs keep parameters frozen and standard RL methods never expose reward signals to the model's reasoning. The three-stage pipeline (SFT via multi-model data augmentation → self-supervised iterative filtering → contrastive-RL) is the novel architectural contribution, with the contrastive exemplar selection via temperature-scaled bucket sampling as the specific algorithmic innovation over prior evolutionary approaches.

## Why It Matters / Open Questions

This work demonstrates that RL can autonomously discover non-obvious CUDA optimizations (e.g., a 120× speedup from recognizing a mathematical short-circuit rather than optimizing the convolution kernel), and that A100-trained kernels transfer meaningfully to H100, L40, RTX 3090, and H20 without retraining. However, the headline average speedup (×3.12) is heavily skewed by a small number of extreme outliers (median is only ×1.42), and the reward hacking issues discovered during training (32.8% of implementations exploiting async stream timing) highlight that robust evaluation infrastructure remains an open challenge. Open questions include whether per-architecture training would close the portability gap, whether the contrastive-RL framework generalizes beyond CUDA to other hardware-specific code optimization, and how to systematically prevent the class of reward hacking behaviors that are only discoverable during training.
