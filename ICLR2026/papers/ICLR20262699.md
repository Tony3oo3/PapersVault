## Problem

Existing MCP benchmarks remain narrow in scope, focusing on read-heavy tasks or shallow interactions with limited interaction depth (averaging only 3.2–6.8 turns), and fail to capture the complex, multi-step CRUD workflows typical of real-world MCP usage. This makes it difficult to probe whether current models possess the reasoning, planning, and tool-use capabilities needed for realistic agentic tasks, and to assess robustness under repeated execution.

## Input / Output

Each task provides a natural-language instruction (~289 words average) paired with a curated initial state in one of five MCP environments (Notion, GitHub, Filesystem, PostgreSQL, Playwright), drawn from 38 realistic starting configurations such as template databases, repositories with development histories, and live webpages. The agent operates within a sandboxed, state-tracked environment with a 100-turn / 3600-second budget, and outputs are evaluated by a programmatic verification script (~210 lines of code average) that checks the final environment state against all required conditions. Performance is reported via three complementary metrics: pass@1 (single-run success), pass@4 (success within 4 independent attempts), and pass^4 (all 4 runs must succeed), the last being a strict consistency measure.

## Method

MCPMark comprises 127 tasks (20–30 per MCP server) constructed through a four-step human-AI collaborative pipeline (Exploration → Evolvement → Verification → Iteration) involving 10 domain experts and two agents (task creation and task execution), with each task requiring 3–5 hours of expert effort. Evaluation uses MCPMark-Agent, a deliberately minimal tool-calling loop built on LiteLLM and the MCP Python SDK that exposes server tools in OpenAI function-call format and routes to native provider APIs, avoiding task-specific heuristics or model-specific scaffolding. The benchmark's distinguishing design choices are: (1) diverse CRUD coverage across all five environments rather than read-only queries, (2) fully programmatic verification with explicit state tracking and environment reset for reproducibility, and (3) substantially longer interaction chains (16.2 turns, 17.4 tool calls on average) that stress-test planning, long-context handling, and consistent multi-step execution. The paper further benchmarks MCP server implementations and agent scaffolds (ReAct, Codex) to isolate model capability from infrastructure choices.

## Results

On MCPMark's 127 tasks across five MCP environments, the best-performing model gpt-5-medium achieves only 52.56% pass@1, 68.50% pass@4, and 33.86% pass^4, while the strongest open-source model qwen3-coder-plus reaches 24.80% pass@1 and 12.60% pass^4. Most proprietary models cluster between 15% and 30% pass@1, and several open-source models fall below 10%. On average, tasks require 16.2 execution turns and 17.4 tool calls, with kimi-k2-instruct exceeding 26 turns per task, underscoring the benchmark's stress-testing nature.

## Baselines & Comparisons

The paper benchmarks MCPMark-Agent (a minimal iterative tool-calling loop) against two structured agent scaffolds: ReAct and Codex. For gpt-5-medium, MCPMark-Agent achieves 52.6% pass@1, substantially outperforming ReAct (37.8%) and Codex (36.2%), suggesting that structured scaffolds introduce redundant constraints in MCP settings. For gpt-5-mini-medium, MCPMark-Agent narrowly edges out ReAct (27.4% vs. 26.6%), while for grok-4-fast, ReAct actually surpasses MCPMark-Agent (26.0% vs. 24.0%), indicating the advantage is model-dependent. The paper further shows that MCP server implementation choice matters significantly: for GitHub tasks with claude-sonnet-4, the KlavisAI server reaches 31.5% pass@1 versus only 16.3% for the official server, and for Notion, 34.8% vs. 21.4%, with higher-performing servers also consuming fewer tokens. These results collectively demonstrate that both agent scaffold design and server-side engineering (schema exposure, error messaging) materially influence MCP task success.

## Relation to Prior Work

This paper carves new ground in MCP benchmarking by departing from prior efforts (MCP-Universe, LiveMCP-101, MCPEval, LiveMCPBench) that rely on read-heavy tasks, LLM-as-judge verification, or short interaction chains. Rather than building on a specific prior method, MCPMark repurposes the human-AI collaborative task-creation paradigm and the programmatic verification approach from broader agent benchmarks (AppWorld, WebArena) but grounds them in official MCP servers with curated initial states, enabling CRUD-diverse, multi-step workflows that prior MCP benchmarks did not capture. The evaluation framework (MCPMark-Agent) is deliberately minimal, positioning the benchmark as a model-capability probe rather than a scaffold comparison, though it does include scaffold ablations against ReAct and Codex.

## Why It Matters / Open Questions

MCPMark provides the first comprehensive, programmatically-verified stress test for MCP-based agent workflows, revealing that even frontier models achieve only ~52% pass@1 and ~34% pass^4, with a stark local-vs-remote environment gap that points to training data scarcity as a key bottleneck. The finding that naive iterative tool-calling outperforms structured scaffolds (ReAct, Codex) challenges the assumption that more elaborate agent architectures are necessary in MCP settings. Open questions include whether the labor-intensive task-creation pipeline (3–5 hours per task) can be scaled, whether a finer difficulty gradient would better serve smaller models, and whether ambiguous-intent tasks would further probe real-world agent robustness.
