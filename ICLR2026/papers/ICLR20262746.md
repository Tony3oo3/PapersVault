## Problem

LLM agents applied naively to Fully Homomorphic Encryption code generation consistently produce programs that compile and pass functional tests yet violate cryptographic security constraints—generating plaintext implementations, hallucinating APIs, or misconfiguring LWE security parameters. Existing code-generation evaluation metrics like Pass@k measure only functional correctness, making them misleading proxies for secure cryptographic programming where the entire privacy guarantee depends on parameter correctness and ciphertext-only computation.

## Input / Output

The framework takes a natural-language FHE task description (e.g., 'implement matrix-vector multiplication on encrypted data using TFHE') and a target scheme specification (TFHE or CKKS) as input, and produces a complete, compilable C++ program that uses only homomorphic APIs with Lattice-Estimator-derived security parameters. The output is validated through a four-stage pipeline (compile, functional unit tests, security invariant checks, latency comparison) with up to 10 iterative correction rounds. A novel Pass@1(func_sec) metric is introduced, requiring both functional correctness and cryptographic security (exclusive TFHE/CKKS API usage, correct parameter bounds, and proper input encryption) to be satisfied simultaneously.

## Method

FHE-Coder is a three-phase agentic framework built on ReAct prompting that addresses the distinct failure modes of FHE code generation. The FHE Prompt Formalizer extracts user intent and invokes a Lattice Estimator to mathematically solve for the security parameter λ (rather than letting the LLM guess), then generates Dafny pseudocode with formal ensure/assert constraints that guide the agent toward valid ciphertext structures. The FHE API RAG Retriever supplies scheme-specific, expert-annotated documentation (Doxygen @objective tags encoding cryptographic purpose and noise constraints) retrieved by intent rather than keyword, with a one-time offline annotation pass making cross-scheme adaptation plug-and-play. The FHE Security Verifier enforces LWE-based parameter bounds and mandates exclusive homomorphic API usage through an automated four-stage feedback loop (Compile → Functional → Security → Latency), generating structured Formal Error Reports that drive iterative correction. For complex compositional tasks (e.g., Transformers, CNNs), a structured decomposition strategy first generates and verifies secure primitives, then a composer agent assembles them into the final program.

## Results

On the TFHE benchmark with GPT-5, FHE-Coder achieves pass@1(func_sec) of 1.00 on MatMul and Softmax, 0.80 on Attention, and 0.80 on Transformer, while both baselines (BAS and COT) yield pass@1(func_sec) of 0.00 across all tasks. On CKKS with GPT-5, FHE-Coder reaches 1.00 on Attention and 0.60 on MatMul, Softmax, and Transformer, again with baselines at 0.00. The ablation on Vector Addition shows a clear cumulative hierarchy: BAS ≈ 0.0, +Prompt Formalizer 0.6, +RAG 0.8, full FHE-Coder 1.0. Structured decomposition extends FHE-Coder to compositional tasks, achieving 0.70 on Mat-Vec Mult and 0.60 on CNN where direct generation yields near-zero success.

## Baselines & Comparisons

The paper compares FHE-Coder against two baselines: BAS (single-shot generation with no formalizer, RAG, or verification loop) and COT (zero-shot Chain-of-Thought with a worked TFHE example). Both baselines universally fail the security check (pass@1(func_sec) = 0.00) across all four LLMs (GPT-5, Gemini-2.5-Pro, DeepSeek-V3.1, Qwen3-Coder) and all TFHE and CKKS tasks, even when they occasionally pass functional tests (e.g., BAS achieves 0.80 pass@1(func) on Softmax but 0.00 on security). FHE-Coder is the only method that produces verifiably secure code, achieving pass@1(func_sec) of 1.00 on MatMul and Softmax (TFHE, GPT-5) and 1.00 on Attention (CKKS, GPT-5). The security gap is model-agnostic: swapping the base LLM does not rescue the baselines, confirming that the failure stems from the absence of structured parameter derivation, API grounding, and iterative security verification rather than from any single model's limitations. On the hardest task (Transformer), FHE-Coder still leads with 0.80 pass@1(func_sec) versus 0.00 for both baselines, though performance is partially constrained by the base model's reasoning depth.

## Relation to Prior Work

This paper sits at the intersection of LLM-based code generation (CodeGen, CodeX, CodeT5) and specialized cryptographic programming, drawing on ReAct-style agentic loops for iterative refinement and the Lattice Estimator (Albrecht et al., 2015) for mathematically grounded parameter derivation. It departs from prior LLM code-generation work in two key ways: (1) it introduces cryptographic security as a first-class, verifiable constraint rather than treating it as an implicit property of correct code, and (2) it replaces heuristic parameter selection with a deterministic lattice-based solver, eliminating the probabilistic guesswork that causes baseline agents to produce insecure configurations. The expert-enriched RAG module and structured decomposition strategy extend ideas from adjacent LLM-agent work in HLS/RTL synthesis, where circuit-oriented reasoning has shown promise, into the FHE domain.

## Why It Matters / Open Questions

The paper's central empirical finding—that even state-of-the-art LLMs (GPT-5, Gemini-2.5-Pro) consistently produce functionally correct but cryptographically insecure FHE code—exposes a fundamental gap in how code-generation quality is measured for security-critical domains, motivating the new Pass@k(func_sec) metric. The modular, scheme-agnostic design (demonstrated by TFHE→CKKS transfer) offers a practical blueprint for extending agentic code generation to other niche cryptographic or safety-critical libraries. However, performance on the deepest circuits (Transformer blocks) remains constrained by base-model reasoning limits (~0.4 pass rate), and the evaluation is limited to 10 tasks per scheme with a single library implementation per scheme, leaving open whether the framework generalizes to more complex real-world FHE applications or alternative libraries (e.g., OpenFHE, SEAL).
