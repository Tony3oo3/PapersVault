## Problem

Traditional Inverse Reinforcement Learning methods recover reward models as opaque neural networks that are difficult to interpret, verify, or debug. While recent code-based reward approaches (EUREKA, Reward-As-Code) improve interpretability, they require ground-truth reward signals or explicit task descriptions. GRACE addresses the open question of whether a reward function can be recovered purely from expert demonstrations in an IRL-style setting, with no task description or domain-specific assumptions, while remaining fully interpretable as executable code.

## Input / Output

GRACE consumes a small set of expert trajectories (as few as 8) and random trajectories, along with environment state representations that vary by domain: (h,w,3) integer arrays for BabyAI, numerical state vectors for MuJoCo, and XML view hierarchies for Android. The LLM also receives pixel images in-context for visual environments. The output is a self-contained Python Reward class with reward_fn(state)→float and an optional debug_fn, which is then used to train a PPO policy. In multi-task settings, the evolved code naturally decomposes into a modular library of reusable helper functions and sub-rewards.

## Method

GRACE operates as a three-phase iterative loop. Phase 1 prompts a code LLM (GPT-4o or Qwen3-Coder-30B) with expert and random trajectories to generate an initial population of reward programs. Phase 2 performs evolutionary search: a fitness function based on the AIRL discriminator loss (D_r(s)=exp(r(s))/(exp(r(s))+π(a|s))) scores each reward, and the LLM mutates low-fitness parents by receiving their source code, specific failure states, and reward values in-context, producing corrected variants; the top-N rewards are retained each generation. Phase 3 trains a PPO agent under the best reward to collect new trajectories, which are added to the negative dataset to expose edge cases in the next iteration. The key distinction from prior work is that the entire pipeline is driven by LLM code generation and mutation rather than gradient-based optimization, and no ground-truth reward or task description is required—only demonstrations.

## Results

On BabyAI, GRACE (using only 8 expert trajectories per task) achieves a success rate of 1.00 on 5 out of 10 evaluated tasks, matching the PPO oracle with ground-truth rewards, while GAIL (trained on 2,000 trajectories) drops to 0.35–0.37 on the same tasks. On the multi-task BabyAI setting, GRACE reaches 0.92 success rate versus 0.95 for PPO and 0.31 for GAIL. On MuJoCo, GRACE with GPT-4o achieves 2143±80 on Hopper and 5707±210 on Ant, within ~3–9% of the PPO oracle (2212±54 and 6239±237) while substantially outperforming GAIL (2056±92 and 5521±674) and AIRL (2028±82 and 4308±306).

## Baselines & Comparisons

Against the PPO oracle (ground-truth sparse reward), GRACE matches or nearly matches performance on most BabyAI tasks (1.00 vs 1.00 on five tasks; 0.92 vs 0.95 on multi-task) and stays within 3–9% on MuJoCo continuous control (e.g., 2143 vs 2212 on Hopper), indicating the recovered code-based rewards are nearly as effective as the true reward. Against GAIL (the primary IRL baseline), GRACE wins decisively: on BabyAI, GRACE reaches 1.00 where GAIL scores 0.35–0.37 on GoToRedBall and OpenTwoDoors, and 0.92 vs 0.31 on the multi-task setting, all while using 250× fewer expert trajectories (8 vs 2,000). On MuJoCo, GRACE outperforms GAIL on Hopper (2143 vs 2056), Walker (2072 vs 1982), and Ant (5707 vs 5521), though GAIL slightly edges GRACE on Humanoid (6521 vs 5809). Against AIRL, GRACE with GPT-4o achieves higher returns on Hopper (2143 vs 2028) and Ant (5707 vs 4308), confirming that the evolutionary code-search approach yields more transferable rewards than the gradient-based AIRL objective.

## Relation to Prior Work

GRACE sits at the intersection of two research threads: inverse reinforcement learning (IRL) and code-as-reward. It adopts the AIRL discriminator formulation (Fu et al., 2018) as its fitness function but replaces the gradient-based neural reward with an LLM-driven evolutionary search over Python programs. This departs from prior code-reward work (EUREKA, Reward-As-Code) that required either ground-truth reward signals or explicit task descriptions; GRACE recovers rewards purely from expert and random trajectories in a classical IRL setting, with no domain-specific prompting or oracle feedback. The evolutionary search mechanism draws on AlphaEvolve-style program mutation, but is applied here to reward synthesis rather than algorithmic discovery.

## Why It Matters / Open Questions

The key practical contribution is that interpretable, inspectable reward functions can be recovered from as few as 8 expert trajectories—25× fewer than GAIL—while matching or exceeding oracle PPO on several BabyAI tasks. This opens a path toward debuggable RL in safety-critical or multi-task settings where black-box neural rewards are unacceptable. However, the approach has clear limitations: it struggles with high-dimensional perceptual state spaces (e.g., MuJoCo Humanoid, raw pixels), and the authors acknowledge that code-based rewards are brittle compared to neural networks. Open questions include whether hybrid code+NN reward architectures can retain interpretability while handling perception-heavy inputs, and whether the evolutionary search scales effectively when large datasets are available.
