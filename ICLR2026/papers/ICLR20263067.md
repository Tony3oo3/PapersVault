## Problem

The dominant 'one-token-per-tool' paradigm for generative tool use in LLMs suffers from two fundamental limitations: vocabulary size grows linearly with the number of tools (requiring ~47,000 new tokens for ToolBench), and each tool is assigned a semantically isolated token that prevents the model from learning collaborative relationships between tools, since it must infer them from sparse co-occurrences of monolithic IDs in a vast library.

## Input / Output

The method takes a natural language query and a tool corpus of ~47,000 APIs (each with name and description text) as input. Tool documentation is first encoded into 768-dimensional dense embeddings via a pretrained text encoder (all-mpnet-base-v2), then projected to 64 dimensions before quantization. The output is a hierarchical code sequence of L=2 discrete tokens (e.g., <T1_1><T2_1>) drawn from 2×1024=2048 new vocabulary tokens, followed by generated tool parameters and a final answer. At inference, a constrained beam search guided by a precomputed trie of all valid code sequences ensures only legitimate tool identifiers are produced.

## Method

ToolWeaver represents each tool as a compositional sequence of L discrete codes learned via a collaborative-aware Residual Quantized VAE (RQ-VAE). The key innovation is a graph Laplacian regularization term (L_collab) added to the standard RQ-VAE reconstruction and quantization losses, which uses a pre-computed tool-tool cosine similarity matrix derived from co-occurrence counts in usage trajectories to pull frequently co-used tools toward shared codebook centroids. This weaves collaborative semantics directly into the tokenization process rather than relying on post-hoc alignment. A Sinkhorn-Knopp optimal transport step enforces uniform assignment on the final codebook to resolve index collisions while preserving learned structure. The resulting codes are integrated into an LLM (Llama-3-8B) through a two-stage generative alignment: first fine-tuning on 489,702 query-to-code-sequence pairs for retrieval, then on 183,336 full interaction trajectories for multi-step tool orchestration.

## Results

On the ToolBench multi-domain retrieval benchmark (46,985 tools), ToolWeaver achieves NDCG@1 of 91.16 (I1), 89.76 (I2), and 88.00 (I3), outperforming the strongest generative baseline ToolGen (88.50/84.00/81.00) by 2.66/5.76/7.00 points respectively. In end-to-end task completion, ToolWeaver reaches a Solvable Pass Rate of 52.19% on complex multi-tool I3 tasks versus 36.34% for ToolGen and 24.86% for GPT-4o-mini, with a Solvable Win Rate of 59.02% against the GPT-4o-mini reference. Critically, ToolWeaver preserves general language capabilities far better than ToolGen: WikiText-2 perplexity is 25.36 vs. 104.54, and the average BERTScore drop on summarization is only 0.57 vs. 2.47.

## Baselines & Comparisons

ToolWeaver consistently outperforms all five baselines across every complexity level. Against the retrieval-based methods, the gap is largest on I3: ToolWeaver (NDCG@1 = 88.00) surpasses ToolRetriever (28.00) by 60 points, EmbSim (18.00) by 70 points, and BM25 (10.00) by 78 points, confirming that generative selection with structured codes far exceeds external retrievers at scale. Against the primary generative baseline ToolGen (one-token-per-tool), ToolWeaver leads by 2.66/5.76/7.00 NDCG@1 points on I1/I2/I3 respectively, with the advantage growing as task complexity increases—directly validating the collaborative-semantics hypothesis. In end-to-end evaluation, ToolWeaver's I3 SoPR of 52.19% exceeds ToolGen's 36.34% by 15.85 points and GPT-4o-mini's 24.86% by 27.33 points, while also beating ToolGen on SoWR (59.02 vs. 49.18). In the In-Domain setting (Table 4), ToolWeaver also outperforms the multi-stage IterFeedback pipeline (90.70 NDCG@1 on I1) with a single end-to-end model (93.76), highlighting the efficiency of the generative approach. On general capability preservation, ToolWeaver's WikiText-2 PPL of 25.36 is 4× lower than ToolGen's 104.54, and its average benchmark accuracy drop is 8.4 points versus ToolGen's 22.9 points, demonstrating that logarithmic vocabulary expansion is far less disruptive to pretrained knowledge.

## Relation to Prior Work

ToolWeaver departs from the dominant 'one-token-per-tool' generative paradigm (ToolGen, ToolKenGPT) by representing each tool as a compositional sequence of discrete codes learned via RQ-VAE, reducing vocabulary expansion from linear to logarithmic. It builds on the structured-identifier idea from LC-Rec (Zheng et al., 2024), which applies RQ-VAE to recommendation, but introduces a key conceptual shift: rather than performing post-hoc alignment of collaborative semantics onto semantically isolated identifiers, ToolWeaver injects a graph-Laplacian collaborative regularization directly into the quantization training, so that co-usage patterns shape the code structure from the ground up. The Sinkhorn-Knopp optimal-transport step for collision mitigation follows the formulation in Zheng et al. (2024), and the two-stage generative alignment (retrieval then trajectory) mirrors the training recipe of ToolGen.

## Why It Matters / Open Questions

The logarithmic vocabulary scaling (2,048 tokens for ~47,000 tools vs. ~47,000 for ToolGen) makes large-scale tool integration practically feasible on memory-constrained deployments, and the 4× lower perplexity degradation (25.36 vs. 104.54) shows the approach preserves general language capabilities far better. The 16-point SoPR gap on complex multi-tool I3 tasks (52.19 vs. 36.34) suggests that explicitly encoding collaborative co-usage patterns is a critical ingredient for tool orchestration that flat token representations cannot capture. Open questions include whether the collaborative signal remains informative when co-occurrence data is extremely sparse (very large or rapidly growing tool libraries), whether reinforcement learning can autonomously discover new collaborative patterns beyond what is observed in training trajectories, and how the approach behaves when tools are added or removed dynamically without retraining the codebooks.
