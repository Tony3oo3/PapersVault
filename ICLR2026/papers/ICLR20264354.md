## Problem

Existing model watermarking methods are ill-suited for publicly released code generation LMs: backdoor-based watermarks target classification tasks and struggle with code's strict syntactic/semantic constraints, while output-based watermarks assume black-box API access and cannot protect models whose parameters are openly distributed. Code LMs further demand that watermarks preserve code functionality, resist parameter-level removal attacks (fine-tuning, distillation), and remain stealthy against adaptive adversaries who know a watermark exists but not its exact pattern.

## Input / Output

The method takes a raw Python code corpus (CodeSearchNet-Python, 200K samples), a pretrained code LM (CodeGen-350M or DeepSeek-Coder-1B), a chosen SPT pattern from four categories (EDP, SSR, LNA, TPF), and an 8-token discrete trigger prompt optimized via PEZ. It produces a fully merged watermarked model (LoRA weights absorbed into the base) and, at verification time, a p-value from an independent-samples t-test comparing the target SPT pattern frequency in trigger-conditioned versus untriggered outputs. Verification is strictly black-box, requiring only input-output pairs from the suspect model without access to its internals.

## Method

CodeGenGuard embeds a backdoor watermark where an optimizable discrete trigger, when prepended to code, causes the model to generate a specific semantic-preserving transformation (SPT) pattern. Three key mechanisms distinguish it: (1) a dead-code-based data augmentation pipeline that inserts PCFG-generated dead code blocks containing SPT-applicable structures to boost the frequency of rare SPTs, enabling near-infinite watermark diversity; (2) a dual-LoRA shadow training scheme where the watermarked model F_wm and a shadow model F_shd are implemented as two LoRA adapters sharing a frozen base model, trained alternatingly so the trigger is co-optimized against a distilled surrogate to survive extraction attacks; (3) auxiliary semantic prompts inserted as comments during verification to disambiguate contexts where expression-level SPTs (e.g., list vs. dict initialization) would otherwise yield false negatives. The trigger is optimized via PEZ (continuous embedding-space gradient descent with nearest-neighbor projection onto the vocabulary), and the watermarked model is trained with a three-term loss balancing watermark activation, normal generation fidelity, and suppression under random triggers.

## Results

On CodeSearchNet-Python, CodeGenGuard achieves p-values ranging from 1.10×10⁻²⁶ to 7.28×10⁻³³ across four SPT patterns on CodeGen-350M and DeepSeek-Coder-1B, consistently outperforming CodeMark (p-values of 1.49×10⁻⁴ to 2.17×10⁻²⁶). For fidelity, watermarked models retain near-clean Pass@1 scores on MBPP and HumanEval, while CodeMark causes an ~10% Pass@1 drop on MBPP for DeepSeek-Coder-1B. Against model extraction attacks, CodeGenGuard maintains p-values below 0.01 in all 8 pattern-model combinations, whereas CodeMark fails verification (p > 0.01 or NaN) in 5 out of 8 cases.

## Baselines & Comparisons

Against CodeMark (fixed-trigger backdoor watermark), CodeGenGuard achieves substantially lower p-values across all four SPT patterns on both models, e.g., 1.45×10⁻³¹ vs. 4.02×10⁻¹⁴ for PFlush on CodeGen, and 7.28×10⁻³³ vs. 6.28×10⁻⁵ for DInit. CodeGenGuard also preserves model fidelity better: CodeMark causes a ~10% Pass@1 drop on MBPP for DeepSeek-Coder-1B, while CodeGenGuard shows negligible degradation. Under model extraction attacks, CodeGenGuard survives in all 8 pattern-model combinations (p < 0.01), whereas CodeMark fails in 5 of 8 (p > 0.01 or NaN), demonstrating the benefit of the optimizable trigger with shadow training. Against ToSyn (post-processing watermark), ToSyn achieves lower p-values (e.g., 3.50×10⁻⁴¹ vs. 1.45×10⁻³¹ for PFlush on CodeGen), but this comparison is not apples-to-apples since ToSyn unconditionally transforms all outputs via rule-based SPTs rather than embedding a trigger-activated backdoor. Critically, after extraction followed by fine-tuning on clean data, ToSyn's watermark vanishes within a few epochs, while CodeGenGuard's backdoor-based watermark remains detectable, highlighting its superior resilience to iterative removal attacks.

## Relation to Prior Work

CodeGenGuard sits at the intersection of three prior research threads: backdoor-based model watermarking (Adi et al., 2018; Cong et al., 2022), which has focused almost exclusively on classification and embedding models; LLM output watermarking (Kirchenbauer et al., 2023; Li et al., 2023b/ToSyn), which assumes the model is guarded behind a black-box API and thus inapplicable to publicly released parameters; and code dataset watermarking (Sun et al., 2023/CodeMark; Yang et al., 2024a/SrcMarker), which protects data provenance rather than model ownership. The paper departs from all three by formulating a backdoor watermark specifically for auto-regressive code generation models with publicly available weights, using semantic-preserving transformations as the watermark target, an optimizable discrete trigger (via PEZ), and a dual-LoRA shadow-training scheme borrowed from robustness literature (Cong et al., 2022; Tan et al., 2023) but made memory-efficient through shared-base LoRA modules.

## Why It Matters / Open Questions

This is the first watermarking framework purpose-built for the threat model of publicly released code LMs, filling a gap where prior methods either require white-box access, assume API-only deployment, or target datasets rather than models. The dual-LoRA shadow training and dead-code augmentation are practical techniques that could transfer to other generative watermarking settings. However, the paper acknowledges significant open questions: the optimized trigger remains unnatural and potentially detectable by human inspection, weight-merging attacks (WAG) can eliminate the watermark entirely for discrete triggers, no theoretical guarantees exist, and the method is vulnerable to token-based extraction if the adversary invests sufficient resources. Scaling beyond 1B-parameter models and to multi-language settings remains largely untested.
