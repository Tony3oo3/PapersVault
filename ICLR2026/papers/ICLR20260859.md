## Problem

Writing CodeQL queries that capture security vulnerability patterns requires deep expertise in both program analysis and security, yet existing query suites cover only a fraction of known CVEs with low precision. CVE databases contain rich metadata about vulnerability patterns and their fixes, but this information has remained largely untapped for automated query construction, leaving a gap between vulnerability reports and practical static analysis detection.
![Teaser figure](../imgs/ICLR20260859/cropped_page1_idx0.webp)

## Input / Output

The system takes as input a CVE's natural-language description, the vulnerable and patched source code versions (from which inter-procedural dataflow graphs are derived), and the patch diff identifying modified program points. The output is a syntactically valid CodeQL taint-tracking path query that must satisfy three criteria: it compiles without errors, it produces at least one dataflow path traversing the patched region in the vulnerable version, and it produces no such path in the fixed version. The query is structured with explicit source, sink, sanitizer, and additional taint-step predicates connected via CodeQL's TaintTracking::Global path graph.

## Method

QLCoder embeds an LLM agent (Claude Sonnet 4 via the Claude Code framework) in an iterative refinement loop of up to 10 rounds, where each round the agent proposes a candidate query and a CodeQL-based validator executes it against both code versions, returning compilation status, match counts, recall/coverage statistics, and prioritized repair recommendations. The agent's reasoning is constrained by a custom MCP interface exposing two tools: a CodeQL Language Server (providing completion, diagnostics, and definition lookup for version-specific syntax guidance) and a ChromaDB vector database (storing CWE definitions, CodeQL API documentation, curated sample queries, and AST snippets from the target repository for semantic retrieval). Conversation histories are kept local to each iteration to prevent context bloat, and the agent is limited to 50 tool interactions per round. This structured, execution-guided synthesis with demand-driven retrieval avoids the pitfalls of naive LLM approaches—producing ill-formed queries, hallucinating deprecated constructs, or missing inter-procedural taint propagation—yielding queries with 53.4% success rate and F1 of 0.700 versus 0.048 for IRIS and 0.073 for CodeQL's built-in suites.

## Results

On CWE-Bench-Java (176 CVEs across 111 Java projects), QLCoder successfully synthesizes correct CodeQL queries for 53.4% of CVEs (94/176), achieving 100% compilation success and an average F1 score of 0.700. The synthesized queries achieve 80% recall and 0.672 average precision on the shared 130-CVE subset. The average synthesis time is 3,712 seconds per query at a cost of $2.90 USD, with 97% success rate for queries completing within 3,000 seconds.

## Baselines & Comparisons

QLCoder substantially outperforms both static analysis baselines on all metrics. Against CodeQL's built-in security query suite (F1 = 0.073), QLCoder achieves a 9.6× improvement in F1 (0.700), driven primarily by a 4× higher recall (80% vs. 20%) and a 12× higher precision (0.672 vs. 0.055). Against IRIS, a recent LLM-assisted static analyzer (F1 = 0.048), QLCoder achieves a 14.6× F1 improvement, with IRIS's lower precision (0.031) stemming from its inability to generate sanitizer or taint-step predicates. In agent framework comparisons (Table 5, 20 CVEs from 2025), QLCoder boosts Claude Code's success rate from 10% to 35% and Codex (GPT-5 Medium) from 0% to 20%, while Gemini CLI remains at 0% success regardless of QLCoder. Figure 5 further shows that CodeQL, IRIS, and QLCoder all achieve significantly higher vulnerability recall than Snyk and SpotBugs across CWE types, confirming CodeQL's superior detection capability as the underlying engine.

## Relation to Prior Work

QLCoder extends the line of LLM-assisted static analysis work (IRIS, MocQ, KNighter) by synthesizing *complete* CodeQL queries—including sources, sinks, sanitizers, and custom taint-propagation steps—rather than only identifying sources/sinks (IRIS) or working in a restricted DSL subset (MocQ). Architecturally, it builds on the Claude Code agentic framework and introduces a structured MCP interface that combines a CodeQL Language Server (for syntax-aware completion and diagnostics) with a RAG vector database (for semantic retrieval of queries, CWE definitions, and AST snippets), all governed by an execution-feedback refinement loop. This departs from prior agentic code-generation work (SWE-agent, LSPAI, Hazel) by targeting a low-resource, highly expressive query language where naive LLM generation produces syntactically valid but semantically useless queries, and by enforcing a discriminative success criterion (alarm on vulnerable, silence on patched) that prior query-synthesis efforts did not formalize.

## Why It Matters / Open Questions

The 10×+ F1 improvement over CodeQL's and IRIS's general query suites (0.70 vs. 0.073/0.048) demonstrates that targeted, CVE-specific query synthesis can dramatically outperform broad CWE-categorized queries, with direct practical value for regression testing, variant analysis, and patch validation in CI pipelines. Key limitations include the 53.4% success ceiling (Java-only, ~$2.90 and ~1 hour per query), the self-referential evaluation (queries are validated against the same CVE they were synthesized for), and the dependence on a single LLM (Claude Sonnet 4) whose training cutoff affects 2025 CVEs. Open questions include generalization to other CodeQL-supported languages, integration with dynamic analysis for exploitability confirmation, and whether the discriminative criterion can be relaxed to improve recall without sacrificing the precision gains.
