## Problem

Interpretability research on large-scale AI is constrained by two barriers: commercial APIs lack the transparency needed to inspect model internals, and open-weight frontier models (e.g., Llama 3.1 405B) require multi-node GPU clusters and complex deployment engineering that most research groups cannot afford. A survey of 184 interpretability papers reveals that 60.6% of research since February 2023 still targets models below 40% MMLU, far behind the capabilities of leading open-weight models, indicating that engineering and infrastructural costs—not just model availability—drive this gap.

## Input / Output

The user writes standard PyTorch code inside a Python tracing context (e.g., `with model.trace(input):`), specifying interventions on module inputs/outputs and marking tensors for retrieval via `.save()`. Upon exiting the context, the traced operations are compiled into a serializable intervention graph in a custom JSON format, which can be executed locally or transmitted to a remote NDIF server. The returned results include saved intermediate activations, modified model outputs, computed intervention metrics (e.g., logit differences), and gradients, all inserted back into the local graph for the research code to consume.

## Method

The core contribution is the intervention graph, a portable, serializable representation of an experiment that decouples experimental design from model deployment. Formally, an intervention is defined as a subgraph C' with getter edges (connecting model variable nodes to intervention apply nodes) and setter edges (connecting intervention variable nodes back to model apply nodes), with an acyclicity constraint ensuring valid interleaving. NNsight implements this by wrapping all PyTorch modules in Envoy objects that expose deferred `.input` and `.output` attributes; operations on the resulting Proxy objects build the intervention graph without executing the model. NDIF then executes these graphs on preloaded, sharded model instances using tensor parallelism across GPU nodes, with safe co-tenancy achieved by simulating interventions without permanently modifying the computation graph and restricting parameter access to copies. This design avoids the costly hidden-state transfers required by peer-to-peer systems like Petals, since all intervention computation runs server-side within the high-performance cluster.

## Results

On HPC (4× H100 82GB), NNsight achieves setup times of 3.53s (GPT2-XL), 6.35s (Gemma-7B), and 5.99s (Llama-3.1-8B), comparable to baukit and pyvene but 2–3× faster than TransformerLens (8.99s, 21.56s, 20.63s respectively). Activation patching runtimes are within 0.01–0.03s of the fastest baseline across all three models. When executed remotely via NDIF, model loading time drops to near zero (models are preloaded), and remote execution becomes faster than local HPC for models with ≥3B parameters, with only a roughly constant communication overhead during activation patching.

## Baselines & Comparisons

Against **baukit** and **pyvene** on HPC, NNsight ties or is within noise on both setup time and activation patching across GPT2-XL, Gemma-7B, and Llama-3.1-8B (e.g., 3.53s vs. 3.15s setup on GPT2-XL; 0.073s vs. 0.073s patching), confirming no performance penalty for the added expressiveness of the intervention graph. Against **TransformerLens**, NNsight is 2.5–3.4× faster on model setup (e.g., 6.35s vs. 21.56s on Gemma-7B) and 2–3× faster on activation patching for GPT2-XL (0.073s vs. 0.205s), though TransformerLens is slightly faster on Llama-3.1-8B patching (0.332s vs. 0.335s). Against **Petals** for standard remote inference, both systems show comparable latency. However, for remote activation patching, NDIF significantly outperforms Petals because NDIF executes interventions server-side and returns only scalar metrics (e.g., logit difference), whereas Petals must transfer full hidden states to the client for local modification and back to the server, incurring multiple costly data transfers per forward pass.

## Relation to Prior Work

This paper builds on PyTorch's deferred computation graph idiom (used for autograd) and Theano's formal bipartite computation graph definition to introduce the intervention graph, a serializable representation that decouples experimental design from model deployment. It departs from local hook-based frameworks (TransformerLens, pyvene, baukit) that require researchers to host and shard models themselves, and from Petals' peer-to-peer architecture that incurs costly hidden-state transfers for interventions. The key conceptual departure is treating an experiment as a portable, optimizable graph that can be transmitted to a shared inference service (NDIF) for co-tenant execution, rather than as bespoke code tied to a specific model instance.

## Why It Matters / Open Questions

The paper documents a growing and quantified gap: 60.6% of interpretability papers since February 2023 still study models below 40% MMLU, while the best open-weight model (Llama 3.1 405B) far exceeds that, and the size disparity between studied and released models grew from 2.7× to 10.3× between 2019 and 2024. By enabling community-shared, co-tenant execution of intervention graphs on preloaded 400B+ parameter models, NNsight/NDIF removes the primary engineering and financial barriers that have kept interpretability research on smaller, less capable models. A key limitation is that the system cannot access closed-weight proprietary models (GPT-4, Claude), and whether commercial providers will adopt this structured-access paradigm remains an open question. The intervention graph's expressiveness (full PyTorch semantics, training loops, gradient interventions) and the demonstrated performance parity with local HPC for models ≥3B parameters make this a practical tool, though its long-term impact depends on sustained community infrastructure investment.
