## Problem

Automated proof generation for Rust code via Verus is severely hampered by multi-level data scarcity: fewer than 500 Verus-verified Rust files exist on GitHub, far too few to fine-tune LLMs as was done for Lean or F*. Prior prompt-based approaches to proof synthesis generalize poorly, while data-driven fine-tuning requires tens of thousands of human-written proofs that simply do not exist for Verus. The paper addresses how to bootstrap and scale proof generation when no large corpus of verified programs, specifications, or proofs is available.

## Input / Output

For proof generation, the model receives a complete Rust function annotated with Verus specifications (preconditions in `requires` blocks and postconditions in `ensures` blocks) and must produce proof annotations—loop invariants, assert statements, proof blocks, and lemma functions—inserted into the code so that Verus's Z3-based SMT solver can verify the function. For self-debugging, the input additionally includes an incorrect proof and the specific verification error messages reported by Verus (e.g., 'postcondition not satisfied', 'possible arithmetic underflow/overflow'), and the model must output a corrected proof. The output is always a complete Verus-annotated Rust program that passes the Verus compiler's verification check.

## Method

SAFE is a self-evolving framework with two coupled procedures. First, self-evolving specification synthesis bootstraps with GPT-4o, then iteratively fine-tunes an open-source LLM (DeepSeekCoder-33B) on previously accepted specifications, filtering candidates via a quantitative Correctness/Completeness metric that uses Verus to symbolically evaluate specifications against test cases (≥80% correctness, ≥60% completeness thresholds). Second, self-evolving proof synthesis bootstraps with a month of GPT-4o invocations yielding ~3,673 verified programs, then runs three rounds where the fine-tuned model generates proofs and Verus acts as an automatic quality oracle—only proofs that pass verification are retained for the next round's training. Crucially, the model is jointly trained on two objectives: a sequence-to-sequence proof generation loss and a self-debugging loss that maps (incorrect proof, Verus error messages) → corrected proof, re-purposing the large volume of failed proofs from early rounds as training signal. This self-evolving loop, where data synthesis and fine-tuning co-evolve with the SMT verifier as the sole quality gate, allows the model to accumulate capability without any human labeling.

## Results

On VerusBench, SAFE with DeepSeekCoder achieves 43.17% Accuracy@1 and 53.96% Accuracy@10 via direct proof generation, far surpassing GPT-4o's 11.51% and 24.46% respectively. With the self-debugging mechanism (SAFE+), accuracy reaches 70.50% at Accuracy@100 (10 initial proofs + 10×10 debugged proofs). On the larger, more diverse CodeNet-Test benchmark, SAFE achieves 43.83% Accuracy@1 versus GPT-4o's 0.28%, demonstrating strong generalization beyond the training distribution. The LLaMa3.1-8B backbone also benefits substantially, reaching 52.52% Accuracy@2 with self-debugging on VerusBench.

## Baselines & Comparisons

SAFE is compared against four baselines: GPT-4o (raw and with a long hand-crafted prompt), LLaMa3.1-8B-Instruct (raw), and DeepSeekCoder-33B-Instruct (raw). SAFE wins decisively on every comparison. On VerusBench, DeepSeekCoder+SAFE achieves 43.17% Accuracy@1, outperforming GPT-4o raw (11.51%) by 3.7× and GPT-4o with the elaborate prompt (25.90%) by 1.7×; the gap widens further with self-debugging (70.50% at @100 vs. GPT-4o's 43.88%). On CodeNet-Test, the advantage is even more dramatic: SAFE reaches 43.83% Accuracy@1 while GPT-4o raw scores only 0.28% and even GPT-4o with the prompt manages just 2.86%, indicating that prompt-based approaches have severely limited generalizability. The raw open-source models (LLaMa3.1 at 3.60%, DeepSeekCoder at 9.35% on VerusBench) are essentially non-functional for this task, confirming that the self-evolving fine-tuning is what drives the capability gain. Statistical significance testing (paired t-tests) confirms all improvements are significant (p < 5×10⁻⁷) except for GPT-4o vs. SAFE on CodeNet-Test @1 (p = 0.08), where the absolute numbers are so low that the difference, while large in relative terms, is not statistically significant at the 0.05 level.

## Relation to Prior Work

This paper adapts the self-evolving/expert-iteration paradigm from mathematical proving (Polu et al., 2022, for Lean) and self-training (Gulcehre et al., 2023) to the fundamentally different setting of SMT-based code verification with Verus/Rust. Unlike prior proof-automation work that relies on elaborate prompt engineering or in-context learning (Misu et al., 2024; Sun et al., 2024a), SAFE bootstraps from a small GPT-4o seed and iteratively fine-tunes open-source models, using the Verus verifier as an automated quality filter. A key departure from Lean-based work is the shift from step-wise tactic search to whole-proof generation and debugging, necessitated by Verus's SMT-solver architecture, and the introduction of a self-debugging training objective that repurposes incorrect proofs as repair data.

## Why It Matters / Open Questions

SAFE addresses a critical bottleneck in Rust formal verification: the near-total absence of training data (fewer than 500 verified Rust files on GitHub). By synthesizing 19K specifications and 9.7K verified programs through self-evolution, it creates the largest Verus training dataset to date and demonstrates that a 33B open-source model can outperform GPT-4o by 3–4× on proof generation. Key limitations include the focus on small algorithmic functions (not large projects with cross-function dependencies), the Verus-specific tooling, and the finding that certain proof features (e.g., `reveal`) remain unsynthesizable due to training-data gaps. Open questions include scaling to real-world Rust codebases, fine-grained multi-round debugging, and generalizing the framework to other verification tools.
