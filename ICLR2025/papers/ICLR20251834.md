## Problem

Existing tool-learning frameworks (e.g., DFSDT, ToolChain*) treat each planning node as a single API, so when a tool call fails they discard the entire planning path and generate a new, often more complex plan that is itself prone to further errors. This leads to redundant error correction, unstable planning, and high computational cost, while ignoring the availability of alternative tools with identical or similar functionality that could resolve the failure without altering the overall plan.

## Input / Output

The method consumes a natural-language task query, the full set of API documentation and descriptions (e.g., 16,464 APIs from RapidAPI in ToolBench), and pre-computed toolkit functionality descriptions generated via in-context learning. Rather than feeding individual API docs into the planning prompt (which creates excessively long contexts), Tool-Planner first has an LLM produce a brief one-sentence functionality summary per API, clusters these into toolkits, and then generates a single toolkit-level description per cluster. The output is a chained toolkit-based plan, a sequence of intermediate reasoning states produced by actual API calls, and a final natural-language answer.

## Method

Tool-Planner introduces a two-level planning architecture built on tool clustering. First, LLM-generated API functionality summaries are embedded with SimCSE and clustered via k-means++ (k=1800 for ToolBench, k=65 for APIBench) into 'toolkits'—groups of APIs with similar or identical functionality. The LLM then plans at the toolkit level, selecting a sequence of toolkits rather than individual APIs, which shortens the planning context and keeps the plan stable. During execution, if an API call fails, the framework first attempts all remaining APIs within the same toolkit (intra-toolkit recovery) without modifying the plan; only when every API in the toolkit has failed does it trigger cross-toolkit replanning, where the LLM generates a new plan on the subgraph with the failed node removed. This design ensures thorough exploration of each planning path before branching, reducing the number of replanning cycles and the overall execution time compared to API-level search methods like DFSDT.

## Results

On ToolBench (GPT-4), Tool-Planner achieves an average Pass Rate of 77.3% and Win Rate of 77.5%, outperforming the strongest baseline DFSDT (68.5% / 68.4%) by +8.8% and +9.1% respectively. On APIBench (GPT-4), Tool-Planner reaches 76.9% Pass Rate, 82.2% Win Rate, and 9.4% Hallucination Rate, improving over DFSDT by +6.6% pass, +14.5% win, and −2.1% hallucination. The method also reduces average running time to roughly 2× that of ReACT/AdaPlanner, compared to 6–8× for DFSDT.

## Baselines & Comparisons

Tool-Planner outperforms all five baselines across both ToolBench and APIBench with GPT-4, GPT-3.5, and Claude-3. Against DFSDT (the strongest baseline), Tool-Planner gains +8.8% pass rate and +9.1% win rate on ToolBench (GPT-4), with the largest margin on G3-Inst (83.0% vs. 71.0% pass). On APIBench, the win-rate improvement over DFSDT reaches +14.5% (82.2% vs. 67.7%), while hallucination rate drops from 11.5% to 9.4%. Compared to ReACT, Tool-Planner improves average pass rate by +23.5% (GPT-4, ToolBench), and versus AdaPlanner by +11.4%. ToolChain* (evaluated in Appendix D) shows significantly degraded performance as tool count grows, with GPT-4 win rates dropping to 38.5% on G1-Inst versus Tool-Planner's 75.5%, confirming that heuristic A* search does not scale to large API collections.

## Relation to Prior Work

Tool-Planner builds directly on DFSDT (ToolLLM, Qin et al., 2024), which performs deep first-search over API-level nodes in a planning tree, but departs from it by replacing individual API nodes with clustered 'toolkits' of functionally similar tools. This shifts the error-recovery granularity from the API level to the toolkit level: when a tool call fails, the system first exhausts alternatives within the same toolkit before triggering a full replan. The clustering pipeline (SimCSE embeddings + k-means++) is borrowed from sentence-representation and clustering literature, and the overall tree-search framing connects to ToolChain* (A* search) and Tree-Planner (path merging), though Tool-Planner avoids their heuristic-search overhead by operating on coarser-grained nodes.

## Why It Matters / Open Questions

The toolkit abstraction offers a practical, low-overhead mechanism for tool-failure recovery that reduces replanning frequency and computational cost compared to API-level search, which is relevant to anyone deploying LLM agents over large API collections. The ablation showing that simply injecting toolkit clustering into ReACT or AdaPlanner nearly closes the gap to DFSDT suggests the clustering itself is the primary driver of improvement, an insight that could inform future tool-learning architectures. Open questions include how to select the optimal tool within a cluster (currently random), how clustering quality degrades as API catalogs grow, and whether causal-inference-based tool-combination selection (sketched in Appendix G) can further optimize multi-tool planning.
