## Problem

Despite LLMs' strong performance on NLP tasks, their string processing capability—character-level operations like indexing, substring searching, and counting—remains largely unexplored. Existing studies are limited to a handful of case-study tasks without comprehensive benchmarks, in-depth analysis of failure causes, or effective remedies. This paper provides the first systematic evaluation of LLMs on string processing, identifies the root causes of their limitations, and proposes a fine-tuning solution.

## Input / Output

Each question is a natural-language instruction (e.g., 'Retrieve the first 29 characters from string ...') paired with a target string drawn from one of three categories: multilingual text sampled from Flores-200 (200 languages), cryptographic hash outputs (10 functions, 32–128 alphanumeric characters), or random printable-character strings. The expected output is a single deterministic answer (a substring, index, count, or boolean) obtained by executing the corresponding Python expression, so evaluation uses exact-match accuracy rather than fuzzy or LLM-judged scoring.

## Method

StringLLM constructs its benchmark by (1) manually curating 49 atomic string tasks from Python built-in documentation and hand-designed operations, (2) prompting GPT-4o to compose 1,462 composite tasks via Program-of-Thought code generation, (3) generating three paraphrased question templates per task through GPT-4o's code summarization, and (4) substituting three string types into templates and executing the Python code to produce guaranteed ground-truth answers, yielding 61,761 question-answer pairs across StringBench. For evaluation, ten LLMs are tested under Raw Instruction, Chain-of-Thought, and Program-of-Thought prompting. The paper then diagnoses the failure mode—tokenization splits strings into subwords rather than characters, depriving the model of character-level information—and addresses it by fine-tuning three open-source 7–9B LLMs (Llama-3.1-8B, Gemma-2-9b, Mistral-7B-v0.3) with LoRA via LlamaFactory on the 80% training split, augmented with general-purpose (Alpaca-GPT-4, Dolly-15k) and code (Code Alpaca, OpenCoder) datasets to preserve foundational and coding capabilities. Fine-tuning raises average PoT accuracy by 38.80–56.51% while degrading MMLU/Hellaswag/ARC by at most 1.35%.

## Results

On StringBench, the best-performing LLM (GPT-4o) achieves only 45.31% average accuracy with raw instructions and 62.08% with Program of Thought (PoT), far below the 98.24% average achieved by humans using Python. Random strings are the most challenging subset, with GPT-4o peaking at just 49.06% (PoT) versus 69.19% on Multilingual. After supervised fine-tuning with LoRA, Mistral-7B-v0.3 improves its average PoT accuracy by +56.51% (from 26.06% to 82.57%), while foundational capabilities degrade by at most 1.35% on MMLU/Hellaswag/ARC.

## Baselines & Comparisons

All 10 evaluated LLMs fall substantially short of human performance: GPT-4o (62.08% avg with PoT) and GPT-4-Turbo (62.08% avg with PoT) are the strongest, yet both remain ~36% below the 98.24% human Python baseline. Among open-source models, DeepSeek-Coder (47.24% PoT avg) and Gemma-2-9b (40.85% PoT avg) lead, while DeepSeek-Chat (5.76% PoT avg) and Mistral-7B-v0.3 (26.06% PoT avg) are the weakest. PoT consistently outperforms raw instructions by 15–30% across models, with the largest gains seen in DeepSeek-Coder (+29.54%) and GPT-3.5 (+24.21%). After fine-tuning with StringBench data, Mistral-7B-v0.3 jumps from 26.06% to 82.57% average PoT accuracy (+56.51%), surpassing GPT-4o's 62.08% on string processing while losing only 1.35% on general benchmarks (MMLU, Hellaswag, ARC). Notably, 8 out of 10 LLMs perform worst on Random Strings, suggesting an out-of-distribution issue rather than a general reasoning deficit.

## Relation to Prior Work

This paper carves new ground by providing the first systematic, large-scale benchmark (StringBench, 1,511 tasks) for evaluating LLMs on string processing, departing from prior case-study-level work (Shin & Kaneko 2024, Zhou et al. 2023, Tan et al. 2024) that examined only a handful of string operations. Methodologically, it repurposes GPT-4o's strong coding ability (rather than its string processing ability) to generate guaranteed ground-truth answers via Python execution, a clever workaround that avoids the very limitation being studied. The fine-tuning approach builds on standard parameter-efficient techniques (LoRA via LlamaFactory) and draws on the practice of mixing general-purpose and code datasets during training, as seen in Code Llama and DeepSeek-Coder.

## Why It Matters / Open Questions

The finding that even frontier LLMs (GPT-4o) achieve only ~45–62% accuracy on string tasks that humans solve at ~98% has direct practical implications for any production system relying on LLMs for text manipulation, data cleaning, or search. The tokenization-based explanation (subword tokens lack character-level information) points toward a concrete architectural fix—finer-grained tokenizers—that could be pursued by model developers. Open questions include whether retraining with character-level tokenizers would close the gap, whether the fine-tuning gains transfer to unseen string operations, and whether the limitation extends to other discrete-symbol manipulation tasks beyond strings.
