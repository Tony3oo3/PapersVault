## Problem

Existing code benchmarks like HumanEval and MBPP are no longer reliable for evaluating modern LLMs because they suffer from data contamination, overfitting, and saturation, and they measure only code generation while ignoring broader capabilities (self-repair, code execution, test generation) essential for building programming agents. The paper asks whether a contamination-free, holistic evaluation framework can be constructed that detects and avoids these issues while providing meaningful model differentiation.

## Input / Output

Each problem instance consists of a natural language problem statement with example input-output pairs, sourced from LeetCode, AtCoder, or Codeforces contests and tagged with a release date. For the self-repair scenario, the model additionally receives error feedback (exception message or failing test case) alongside its initial incorrect program; for code execution, it receives a function snippet and a test input; for test output prediction, it receives the problem statement and a fixed test input. Evaluation uses PASS@1 computed over 10 nucleus-sampled completions (temperature 0.2, top_p 0.95), with each problem graded against ~18–20 private tests (including adversarial and stress tests) to ensure functional correctness.

## Method

LiveCodeBench is a continuously updated benchmark of 612 competition problems (May 2023–Aug 2024) from three platforms, organized into four evaluation scenarios: code generation, self-repair (multi-turn with execution feedback), code execution (predicting program output), and test output prediction (generating expected outputs from problem statements alone). The key anti-contamination mechanism is time-segmented evaluation: each problem carries a release date, and models are only scored on problems published after their training cutoff, which empirically reveals sharp performance drops for contaminated models (e.g., DeepSeek, GPT-4o, Claude-3) on pre-cutoff LeetCode problems. Test inputs are generated via LLM-constructed random and adversarial input generators (using GPT-4-Turbo with in-context learning) rather than direct LLM sampling, and problems are filtered to exclude those accepting multiple correct outputs or requiring interactive input. Difficulty ratings from the source platforms are used to curate problems into Easy/Medium/Hard tiers, avoiding problems too hard for current models (e.g., high-rated Codeforces problems where PASS@1 tends to zero).

## Results

On LiveCodeBench code generation (PASS@1, Sep 2023–May 2024 window), GPT-4O-2024-05-13 leads with 41.9% overall (88.3% Easy, 33.2% Medium, 4.2% Hard), followed by GPT-4-Turbo-2024-04-09 (41.1%) and GPT-4-0613 (33.9%). Among open-access models, DSCoder-33b-Ins achieves 21.8% overall and LLama3-70b-Ins reaches 26.0%, while smaller models like DSCoder-1.3b-Ins score only 8.1%. Across the four holistic scenarios, correlations in PASS@1 exceed 0.88 between all scenario pairs, yet relative rankings shift: e.g., Claude-3-Opus outperforms GPT-4-Turbo on test output prediction, and the gap between closed and open models widens on self-repair and code execution.

## Baselines & Comparisons

Against HumanEval+ (Liu et al., 2023b), LiveCodeBench reveals significant overfitting: the correlation between PASS@1 on HumanEval+ and LCB-Easy is only 0.72, and fine-tuned open models (e.g., DS-INS-1.3B scores 60 on HumanEval+ but only 26 on LCB-Easy; DS-INS-6.7B and CodeQwen outperform Claude-3-Sonnet on HumanEval+ yet trail by >20 points on LCB-Easy) form a distinct cluster that does not transfer. Compared to prior competition benchmarks (APPS, Code-Contests, CodeScope, xCodeEval, TACO, USACO-Bench), LiveCodeBench is the only one that simultaneously provides contamination prevention via time-segmented evaluation, robust test-based grading (avg. 18+ tests per problem), varied difficulty levels, non-saturation, and multiple evaluation scenarios (Table 1). The code execution scenario builds on CRUXEval (Gu et al., 2024) but uses live, human-produced functions from LeetCode rather than synthetic ones, and the self-repair scenario extends Olausson et al. (2023) by integrating it into a multi-scenario holistic framework. The test output prediction scenario adapts CODET (Chen et al., 2022) by fixing test inputs and only requiring output prediction, enabling straightforward automated evaluation. On contamination detection, time-segmented evaluation on LeetCode problems shows stark performance drops for DeepSeek (post-Aug 2023), GPT-4O (post-Nov 2023), and Claude-3s (post-Apr 2024), confirming that prior static benchmarks are unreliable for these models.

## Relation to Prior Work

This paper extends the code LLM evaluation landscape by combining three previously separate threads: (1) time-segmented 'live' benchmarking inspired by Dynaboard and LatestEval, (2) holistic multi-scenario evaluation drawing on self-repair (Olausson et al., 2023), code execution (CRUXEval, Gu et al., 2024), and test output prediction (CodeT, Chen et al., 2022), and (3) competition programming problem curation from LeetCode, AtCoder, and Codeforces. Unlike prior competition benchmarks (APPS, Code-Contests, CodeScope, xCodeEval) that are static and already contaminated, LiveCodeBench introduces release-date-tagged problems with a 'scrolling through time' mechanism to isolate post-cutoff performance. The paper departs from the dominant single-task (code generation) evaluation paradigm by treating programming as a multi-faceted capability requiring repair, execution reasoning, and test generation skills.

## Why It Matters / Open Questions

LiveCodeBench addresses the most pressing practical concern in code LLM evaluation—data contamination—by providing a scalable, continuously updated benchmark with built-in contamination detection via time-segmented evaluation. The finding that fine-tuned open models systematically overfit to HumanEval (performing well there but poorly on LCB) while base and closed models do not has important implications for how the community interprets benchmark scores and designs post-training data. Limitations include the narrow domain of competition programming (which may not reflect practical software engineering), evaluation noise from small per-time-window problem counts, and sensitivity to prompt formatting. Open questions include whether the contamination detection generalizes to non-competition code tasks and how the benchmark evolves as models close the gap on easy/medium problems.
