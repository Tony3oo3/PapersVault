## Problem

Existing LLM code evaluation frameworks focus almost exclusively on functional correctness, leaving code efficiency—an equally critical quality dimension—largely unmeasured. The few recent efficiency benchmarks suffer from fundamental methodological gaps: they ignore right-censored execution times (overestimating efficiency when code times out), fail to characterize the relationship between efficiency and sample size k, rely on non-expert reference solutions that are themselves inefficient, and use weak test cases that cannot filter wrong code or differentiate suboptimal algorithms on worst-case inputs.

## Input / Output

The benchmark consumes 142 programming problem prompts (selected from HumanEval and HumanEval+, excluding Θ(1)-complexity problems) and evaluates LLM-generated code samples against expert-written reference solutions and multi-level test case generators. Each problem is evaluated across L levels of increasing input scale (plus a level-0 correctness filter), with each test case repeated R=6 times and execution times estimated via the Hodges-Lehmann estimator for robustness. The output is a continuous efficiency score e_{i,j} per code sample (weighted average of per-level scores normalized by reference execution time) and the aggregate eff@k metric per problem, alongside the standard pass@k correctness metric.

## Method

ENAMEL introduces a level-based evaluation framework where each problem has multiple input-scale levels sharing a common time limit T_i = α·max(t*_ref), enabling fine-grained differentiation of algorithms with different complexities (e.g., 2^Θ(n) vs. Θ(n) vs. Θ(log n) for Fibonacci). The core metric eff@k generalizes pass@k from Boolean correctness to continuous efficiency scores by defining eff_i@k as the expected maximum efficiency over k i.i.d. code samples, with the (·)^+ operator ensuring the score is invariant to right-censored execution times. An unbiased, variance-reduced estimator is derived via Rao-Blackwellization of a bootstrap estimator, yielding a closed-form weighted sum over order statistics with coefficients C(r-1,k-1)/C(n,k), and a numerically stable iterative algorithm avoids overflow in binomial coefficient computation. The benchmark sets a high standard through expert-written reference solutions (involving advanced algorithms like KMP, suffix automata, digit DP, and implementation tricks like str.translate) and expert-curated test case generators that include non-trivial corner cases (e.g., Carmichael numbers for primality) and worst-case inputs to expose suboptimal algorithms.

## Results

Across 30 LLMs evaluated on the ENAMEL benchmark (142 problems from HumanEval/HumanEval+), even the strongest commercial model GPT-4 Turbo achieves only eff@1=0.470 (greedy) despite pass@1=0.796, and GPT-4 reaches eff@1=0.454 with pass@1=0.831. The gap between eff@k and pass@k is substantial across all models: for example, Llama 3 70B Instruct has eff@100=0.575 vs. pass@100=0.880. Notably, open-source models are closing the gap—Phind Code Llama V2 achieves eff@100=0.723, exceeding ChatGPT's eff@100=0.690. On the algorithm design subset (20 hard problems), even ChatGPT's eff@100 is only 0.483, indicating LLMs fundamentally struggle with advanced algorithm design.

## Baselines & Comparisons

The paper compares ENAMEL's expert-written reference solutions against HumanEval canonical solutions (eff@1=0.455, pass@1=0.908) and HumanEval+ canonical solutions (eff@1=0.513, pass@1=0.972), showing that even these 'correct' solutions are far from expert-level efficiency (ENAMEL reference: eff@1=1.000). Against the classic speedup metric, ENAMEL's eff@1 produces materially different rankings: under speedup, Mixtral 8x22B Instruct and Llama 3 70B Instruct appear to outperform GPT-4, but under eff@1 (which properly handles right-censored execution time), GPT-4 Turbo and GPT-4 rank first and second. Compared to other efficiency benchmarks, ENAMEL is more challenging: Code Llama 34B Python scores eff@1=0.268 on ENAMEL versus 0.336 on EffiBench and 0.424 on Mercury, because LLMs have seen public LeetCode solutions in pretraining but never the expert-written ENAMEL solutions. The paper also shows that prompting engineering (encouraging 'most efficient algorithm' or revealing the algorithm) barely improves efficiency, confirming the gap is a fundamental capability limitation rather than a prompting issue.

## Relation to Prior Work

This paper extends the HumanEval/HumanEval+ line of code generation benchmarks by generalizing the pass@k correctness metric to a continuous efficiency metric (eff@k) that properly handles right-censored execution time via a Rao-Blackwellized bootstrap estimator. It departs from recent efficiency benchmarks (EffiBench, Mercury, Niu et al.) by addressing five fundamental gaps: right-censoring, sample-size characterization, expert-level reference solutions, strong correctness-filtering test cases, and worst-case input coverage. The statistical machinery (Hodges-Lehmann estimation, U-statistic variance bounds) is borrowed from classical statistics and repurposed for the novel setting of LLM code evaluation.

## Why It Matters / Open Questions

The benchmark reveals a large and previously unquantified gap between code correctness and code efficiency: GPT-4 achieves pass@1=0.831 but only eff@1=0.454, and even 100 samples per problem barely close the gap on algorithm-design problems. This suggests that the field's focus on correctness has masked a fundamental capability limitation in LLMs' understanding of advanced algorithms and implementation optimization. Open questions include whether this gap can be closed via better training data or prompting, how to extend evaluation to space efficiency and multi-file codebases, and whether reference-solution optimality can be theoretically guaranteed.
