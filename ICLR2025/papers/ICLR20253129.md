## Problem

Existing language-guided 3D scene editing methods either require manual intervention to select target objects and specify edit types, or only modify object appearance without supporting comprehensive layout changes (translation, rotation, scaling, addition, removal, replacement). Additionally, no large-scale dataset exists for training and evaluating language-guided 3D scene layout editing, constraining both model development and benchmarking.
![Teaser figure](../imgs/ICLR20253129/cropped_page0_idx0.webp)

## Input / Output

The system takes a source 3D scene (from 3D-FRONT, represented as a semantic graph with object categories, 1280-dim OpenShape features, and spatial-relation edges, plus a layout matrix of positions, sizes, and rotations) and a free-form natural language command. GPT-4o first decomposes the command into structured breakdown operations (e.g., [Translate, 'the red sofa', 'left', 0.5m]), which are then encoded via CLIP-ViT-B-32. The output is a target scene graph (categories, VQ-VAE-compressed feature indices, relation edges) and a target layout (M×8 matrix), from which object meshes are retrieved from 3D-FUTURE to reconstruct the edited scene.

## Method

EditRoom is a two-stage pipeline: a GPT-4o-based Command Parameterizer decomposes natural language into sequences of six atomic operations, and a Scene Editor executes them via two graph transformer-based conditional diffusion models. The Target Graph Diffusion uses a discrete denoising process (DiGress-style with KL-divergence loss) to generate the target scene graph, where high-dimensional OpenShape features are first compressed into low-dimensional VQ-VAE codebook indices to make discrete diffusion tractable. The Target Layout Diffusion then performs continuous denoising to produce the final M×8 layout (position, size, rotation), conditioned on the generated graph, source graph, source layout, and text. A key architectural choice is concatenating source scene information directly into the noisy target as self-attention context rather than using cross-attention, which ablations show significantly improves layout accuracy. The entire system is trained end-to-end on EditRoom-DB (83k editing pairs) generated by an automated pipeline that applies collision-checked edits to 3D-FRONT scenes and uses LLaVA-1.6 captions plus GPT-4o to produce natural language commands.

## Results

On the EditRoom-DB test set, EditRoom achieves the best performance across all room types and editing types. For bedrooms, EditRoom reaches 0.7342 IOU and 0.7236 S-IOU, outperforming SceneEditor-N (0.7055 / 0.6942) and DiffuScene-N (0.6220 / 0.6125). On the more challenging living room scenes, EditRoom scores 0.4710 IOU vs. 0.4618 (SceneEditor-N) and 0.4332 (DiffuScene-N). EditRoom also achieves the lowest LPIPS (0.1090 bedroom, 0.1616 living room) and highest CLIP scores (0.9597 bedroom, 0.9446 living room) among all methods.

## Baselines & Comparisons

EditRoom is compared against two baselines: DiffuScene-N (a UNet-based diffusion model adapted from DiffuScene with source scene as context) and SceneEditor-N (the same graph diffusion architecture as EditRoom but trained directly on GPT-4o-generated natural language commands instead of template commands). EditRoom outperforms both baselines on every metric (IOU, S-IOU, LPIPS, CLIP) across all three room types and all six editing types. The margin over DiffuScene-N is substantial (e.g., +0.112 IOU on bedrooms), confirming that the graph-based diffusion architecture is significantly more effective than the UNet-based approach for scene editing. The gap over SceneEditor-N is smaller but consistent (e.g., +0.029 IOU on bedrooms), demonstrating that the LLM-based command parameterizer (converting natural language to structured template commands) provides a meaningful advantage over directly conditioning on free-form text. The ablation in Table 4 further confirms that concatenating source scene information into self-attention (EditRoom's design) substantially outperforms using it as cross-attention context (−0.149 IOU on bedrooms).

## Relation to Prior Work

EditRoom sits at the intersection of two lines of work: (1) language-guided 3D scene synthesis via diffusion models (DiffuScene, EchoScene, InstructScene), which generate scenes from text but cannot accept an external source scene or support all layout operations, and (2) discrete graph diffusion (DiGress) for structured generation, previously applied to molecules and proteins but not to scene editing. The key departure is the two-stage architecture: an LLM (GPT-4o) decomposes free-form natural language into atomic template commands, and a unified graph diffusion editor (combining a discrete graph diffusion for scene-graph semantics and a continuous layout diffusion for poses/sizes) executes them. This contrasts with prior editing works that either modify only object appearance (ReplaceAnything3D, FreeEditor) or require manual object selection and single-step commands (GaussianEditor, Gaussian Grouping).

## Why It Matters / Open Questions

EditRoom-DB (83k editing pairs) is the first large-scale dataset purpose-built for language-guided 3D scene layout editing, filling a gap that has constrained both training and evaluation in this area. The framework's ability to generalize to multi-operation commands without explicit multi-operation training data suggests the LLM decomposition is a robust planning layer, but performance remains dependent on GPT-4o's 3D spatial reasoning and is limited to the 3D-FRONT scene distribution (bedrooms, dining rooms, living rooms). Open questions include scaling to more complex or outdoor scenes, handling out-of-distribution commands that deviate from training distributions (e.g., extreme translations), and reducing the LLM dependency through learned planners. The collision-avoidance trade-off—where the model may silently deviate from commands to stay within collision-free training data—raises questions about faithfulness in safety-critical applications.
