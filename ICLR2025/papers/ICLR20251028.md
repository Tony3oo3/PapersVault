## Problem

Existing text-to-SQL benchmarks (Spider 1.0, BIRD) use small, single-dialect databases with few columns and short SQL queries, falling far short of real-world enterprise complexity. In practice, enterprise SQL workflows involve databases with over 1,000 columns, multiple SQL dialects (BigQuery, Snowflake, SQLite, DuckDB), project-level codebases, external documentation, and multi-step data transformation pipelines. This paper introduces Spider 2.0 to evaluate whether LLMs can handle these realistic enterprise text-to-SQL workflows.

## Input / Output

In the full Spider 2.0 (code agent) setting, the model receives a natural language question, a live database interface, and a project codebase, then iteratively executes SQL/Python commands until producing a final answer (string, table, or transformed database file). In the Spider 2.0-lite/snow (text-to-SQL) setting, the model receives a preprocessed database schema, the question, and auxiliary documentation, and must output a single SQL query. Ground-truth SQLs average 144–162 tokens with 6.5–7.1 advanced dialect-specific functions per query, and databases average ~800 columns with nested and multi-schema structures. Evaluation uses execution-based focused scoring (EX for lite/snow, Success Rate for full Spider 2.0) that checks whether essential columns/values appear in the output rather than requiring exact table matches.

## Method

The benchmark is constructed through a six-step annotation pipeline: collecting 213 databases from cloud warehouses and local systems (requiring 200+ columns or nested schemas), gathering 1,021 complex SQL queries and 157 DBT projects (filtered to 547 SQL + 78 DBT), rewriting each SQL at surface and semantic levels to prevent data leakage, setting up project codebases and external documentation, writing natural language instructions, and creating per-example execution-based evaluation scripts. For evaluation, the authors propose Spider-Agent, a code agent framework inspired by ReAct and Intercode that enables multi-turn interaction with databases via command-line interfaces, and compare it against Reflexion, CodeR, and AutoEval. They also adapt existing text-to-SQL methods (DIN-SQL, DAIL-SQL, CHESS, SFT CodeS-15B) to the lite/snow settings. The key finding is that even o1-preview achieves only 21.3% success rate on Spider 2.0 and 23.4% on Spider 2.0-lite, compared to 91.2% on Spider 1.0, with major failure modes including schema linking in large databases, dialect function usage, intricate multi-CTE query planning, and grounding external documentation into SQL.

## Results

On Spider 2.0 (the full agentic benchmark), the best configuration (Spider-Agent + o1-preview) achieves a success rate of only 21.36%, compared to 91.2% on Spider 1.0 and 73.0% on BIRD. On Spider 2.0-lite, o3-mini achieves the highest execution accuracy at 23.40% overall (32.03% Easy, 26.02% Medium, 13.87% Hard), while on Spider 2.0-snow, o1-preview leads at 23.77%. Traditional text-to-SQL methods perform dramatically worse: DAIL-SQL + GPT-4o drops from 86.6% EX on Spider 1.0 to just 5.68% on Spider 2.0-lite, and SFT CodeS-15B achieves only 0.73%.

## Baselines & Comparisons

Among code agent frameworks on Spider 2.0, Spider-Agent with o1-preview (21.36% SR) substantially outperforms CodeR (7.91%), Reflexion (7.28%), and AutoEval (5.70%), all using GPT-4o, indicating that the purpose-built database agent architecture is critical. Among LLMs, o1-preview and o3-mini consistently lead across all difficulty levels on both Spider 2.0-lite and Spider 2.0-snow, with o1-preview achieving 23.77% on Snow (vs. 19.20% for o3-mini) and o3-mini slightly edging ahead on Lite (23.40% vs. 23.22%). The gap between frontier and open-source models is stark: DeepSeek-V3 (8.78%) and Qwen2.5-Coder (5.30%) trail o1-preview by roughly 15–18 percentage points on Spider 2.0-lite. Traditional text-to-SQL methods (DIN-SQL, DAIL-SQL, CHESS, SFT CodeS) all collapse on Spider 2.0-lite/snow, with the best (DAIL-SQL + GPT-4o) reaching only 5.68% EX on Lite and 2.20% on Snow, compared to their 86.6% and 57.4% on Spider 1.0 and BIRD respectively. Even with oracle function documentation, DAIL-SQL + o1-preview improves only marginally (12.60% without oracle vs. 9.51% with), and few-shot prompting yields negligible gains (5.68% → 6.76% from 0-shot to 3-shot), suggesting the bottleneck is not syntax knowledge but complex multi-step reasoning and schema navigation.

## Relation to Prior Work

This paper extends the text-to-SQL evaluation lineage (Spider 1.0, BIRD, WikiSQL) by introducing an enterprise-scale, agentic benchmark that departs fundamentally from the traditional text-input-to-SQL-output paradigm. While prior benchmarks use small, single-dialect databases with ~27–54 columns, Spider 2.0 sources real industrial databases (BigQuery, Snowflake, DuckDB, etc.) with 800+ columns, nested schemas, and diverse SQL dialects, and wraps tasks in a code-agent setting where models must navigate project codebases, documentation, and database interfaces. The agentic framing draws on interactive coding benchmarks (Intercode, SWE-Bench) and agent frameworks (ReAct, Reflexion, CodeR), but applies them specifically to data engineering workflows including DBT project-level transformations, a setting absent from all prior text-to-SQL work.

## Why It Matters / Open Questions

The benchmark exposes a stark capability gap: the best model (o1-preview) achieves only 21.3% success on Spider 2.0 versus 91.2% on Spider 1.0, and traditional text-to-SQL parsers drop to 5.7% on Spider 2.0-lite, revealing that current LLMs are far from enterprise-ready for data engineering. The error analysis identifies concrete, actionable bottlenecks—nested schema linking, SQL dialect function usage, multi-step CTE planning, and document-to-SQL grounding—that give the community clear targets for improvement. Open questions include whether scaling context length or reasoning depth can close the gap, how to effectively integrate project-level codebase understanding, and whether the agentic interaction loop (execution feedback, iterative debugging) is sufficient or requires fundamentally new architectures for enterprise SQL workflows.
