## Problem

LLMs frequently fail to generate correct solver programs for complex vehicle routing problems (VRPs) with composite constraints, because their internal training knowledge is insufficient to accurately model diverse constraint types and integrate heterogeneous constraints within a single program. Existing RAG approaches for code generation retrieve documents for the entire problem at once, which often misses critical individual constraints (e.g., retrieving CVRP documents while neglecting the open-route constraint). The paper addresses this by proposing a constraint-decomposed retrieval mechanism that retrieves and filters external knowledge per constraint.

## Input / Output

The input is deliberately minimal: the name of a VRP variant (e.g., 'CVRPTWMD') plus a Python function signature with docstrings describing each parameter (distance matrix, capacities, time windows, etc.), rather than a full natural-language problem description. The output is a complete Python 'solve' function that invokes a designated solver (OR-Tools or Gurobi) and returns the objective value. Because the input is a function signature rather than instance-specific data, a single successfully generated program generalizes to all instances sharing the same constraint structure, and the framework is evaluated on 48 VRP variants each paired with a small expert-crafted instance.

## Method

DRoC is a multi-step pipeline that first attempts code generation using only the LLM's internal knowledge, then executes the code to obtain a traceback. An LLM router then dynamically selects between self-debugging (fixing syntax/logic errors) and decomposed retrieval (RAG). In the decomposed retrieval step, an LLM decomposer extracts individual constraint keywords from the VRP name; for each constraint, a dense-retrieval query ('Python code of <constraint>') retrieves top-k documents from solver documentation and example code repositories. A two-stage LLM-based filter first assesses per-document relevance and extracts code snippets with explanations, then comparatively selects the single most relevant document per constraint. The per-constraint contexts are concatenated into a merged generation context that guides either a retrieval-augmented generator (producing a new program) or a retrieval-augmented debugger (refining the existing one). The entire process iterates up to I=4 attempts, and the framework requires no additional training of the LLM.

## Results

On 48 VRP variants, DRoC with gpt-4o achieves 45.83% Accuracy Rate (AR) and 20.83% Runtime Error Rate (RER), improving AR by 25 percentage points over Standard Prompting (20.83%) and reducing RER by 37.5 percentage points. With gpt-3.5-turbo, DRoC reaches 20.83% AR and 47.92% RER, outperforming all six baselines on both metrics. The framework also generalizes to the Gurobi solver, where DRoC lifts gpt-4o's AR from 2.08% to 31.25% on 10 VRP variants requiring MIP modeling.

## Baselines & Comparisons

DRoC outperforms all six baselines on both AR and RER for both gpt-3.5-turbo and gpt-4o. Against the strongest internal-knowledge baselines (Standard Prompting, CoT, PHP), DRoC gains 6.25–12.5 percentage points in AR with gpt-3.5-turbo and 22.9–25 percentage points with gpt-4o. Among RAG-based baselines, Vanilla RAG actually degrades gpt-3.5-turbo performance (10.42% AR vs. 14.58% for Standard Prompting), while Self-RAG offers only marginal improvement; DRoC's decomposed retrieval and two-stage filtering consistently surpass both. For the LLM+EC comparison on PCTSP, DRoC achieves a better objective value (6.352) than EoH (6.436) and ReEvo (6.984) while consuming far fewer tokens (EoH and ReEvo each require over 0.1M tokens for iterative evolution). The ablation confirms each component contributes: removing the filter, decomposed retrieval, or router each causes a 2–8 percentage point AR drop.

## Relation to Prior Work

This paper extends the RAG paradigm (Lewis et al., 2020) from monolithic document retrieval to a decomposed, constraint-specific retrieval strategy tailored for VRP code generation. It departs from prior LLM-for-OR work (Xiao et al., 2023; AhmadiTeshnizi et al., 2024) that relies on mathematical formulation as an intermediate step, instead directly generating solver API code. The divide-and-conquer decomposition draws on CoT (Wei et al., 2022) and DaC prompting (Zhang et al., 2024b), while the dynamic routing between self-debugging and retrieval distinguishes it from static RAG pipelines like Self-RAG (Asai et al., 2024) or Vanilla RAG. Unlike LLM+EC approaches (Liu et al., 2024; Ye et al., 2024) that evolve heuristics, DRoC leverages existing solvers, shifting the LLM's role to constraint-aware program generation rather than algorithm design.

## Why It Matters / Open Questions

The framework demonstrates that even frontier LLMs (GPT-4o) solve fewer than 21% of complex VRP variants without external knowledge, highlighting a significant gap between LLM capability and real-world optimization needs. The decomposed retrieval technique is broadly applicable to any domain where composite constraints require specialized API knowledge, and the solver-agnostic, LLM-agnostic design increases practical relevance. Limitations include reliance on simple evaluation instances, a fixed set of 48 variants, and the still-modest absolute accuracy (~46% for GPT-4o). Open questions include scaling to larger and more heterogeneous constraint sets, integrating solver selection, and whether the Bootstrap mechanism can close the remaining performance gap without manual curation of external knowledge.
