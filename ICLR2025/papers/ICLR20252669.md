## Problem

Existing smartphone app agents rely on large foundation models (e.g., GPT-4o) that are prohibitively slow (~1–2 min per task) and expensive (~$1 per task) for everyday on-device use, or on fine-tuned VLMs that still demand substantial compute. There is no architecture that balances natural-language understanding for text-heavy actions with the low latency and memory footprint required for real-time mobile deployment.
![Teaser figure](../imgs/ICLR20252669/cropped_page3_idx0.webp)

## Input / Output

LiMAC consumes a natural-language goal string, a sequence of past observations (each comprising a phone screenshot and a UI element tree where each element is a triplet of cropped image, text label, and attributes), and the history of prior actions. It outputs a structured action tuple: an action type from an 11-class vocabulary (click, scroll, input-text, open-app, etc.) plus a specification — either a target UI element (for clicks, selected via contrastive similarity) or a generated text string (for input-text/open-app, produced by the VLM). For AitW, where no UI tree is provided, elements are extracted via OCR, and the system remains robust to the resulting imprecision.

## Method

LiMAC is a gated two-stage architecture. The first stage, AcT (a 520M-parameter GPT-2-based transformer), encodes each UI element as a concatenated embedding of a fine-tuned CLIP image vector, a BERT text vector, and an attribute vector, then processes the full episode sequence to predict the action type via a classification head and, for clicks, the target element via a contrastive InfoNCE objective that scores the transformer's hidden state against all UI-element embeddings in the episode using cosine similarity with a learnable temperature. The second stage is a fine-tuned VLM (Florence2 820M or Qwen2-VL 2B with LoRA) that is invoked only when AcT predicts a text-requiring action (input-text or open-app, <15% of steps); AcT's predicted action type is prepended to the VLM prompt to constrain generation to the correct JSON format. This division of labour eliminates the need for autoregressive generation on the majority of actions, yielding 30× faster inference (~0.34 s per step) and up to 19% higher overall accuracy than standalone fine-tuned VLMs.

## Results

On Android-in-the-Wild (AitW), LiMAC with Florence2 achieves 72.2% overall action accuracy and LiMAC with Qwen2-VL achieves 70.9%, compared to 70.8% and 51.0% for the standalone fine-tuned VLMs respectively. On AndroidControl, LiMAC with Florence2 reaches 63.1% and LiMAC with Qwen2-VL reaches 62.5%, versus 57.0% and 52.2% for the standalone VLMs. Inference time drops to 0.34 s per action (LiMAC + Florence2) and 0.63 s (LiMAC + Qwen2-VL), compared to 0.50 s, 3.03 s, 4.87 s, and 10.64 s for Florence2, Qwen2-VL, T3A, and M3A baselines respectively.

## Baselines & Comparisons

Against the GPT-4o prompt-engineering baselines from Rawles et al. (2024), LiMAC with Florence2 outperforms T3A by 45.3 points on AitW (72.2 vs 26.9) and by 10.0 points on AndroidControl (63.1 vs 53.1); over M3A the margins are 36.6 points on AitW (72.2 vs 35.6) and 5.6 points on AndroidControl (63.1 vs 57.5), while also reducing inference time from 4.87–10.64 s to 0.34 s. Against the SeeAct variants from Zheng et al. (2024), LiMAC with Florence2 leads by 34.5 points on AitW (72.2 vs 37.7 for SeeAct_choice) and by 33.2 points on AndroidControl (63.1 vs 29.9). Against the fine-tuned Florence2 baseline (Xiao et al., 2024), LiMAC adds 1.4 points on AitW (72.2 vs 70.8) and 6.1 points on AndroidControl (63.1 vs 57.0) while halving inference time. Against the fine-tuned Qwen2-VL baseline (Bai et al., 2023), LiMAC achieves a 19.9-point gain on AitW (70.9 vs 51.0) and a 10.3-point gain on AndroidControl (62.5 vs 52.2), with inference time reduced from 3.03 s to 0.63 s.

## Relation to Prior Work

This paper departs from the dominant paradigm of mobile app control agents that rely on a single large model (GPT-4o prompt engineering à la T3A/M3A/SeeAct, or fine-tuned VLMs like CogAgent's 18B model) for every action decision. LiMAC introduces a gated hybrid architecture where a compact 520M-parameter Action Transformer (AcT) handles the majority of actions—type prediction and click targeting via a contrastive InfoNCE objective over UI element embeddings—while a fine-tuned VLM (Florence2 or Qwen2-VL) is invoked only for the <15% of actions requiring text generation. The contrastive click-targeting mechanism, which treats all UI elements in the episode as negatives, repurposes the CLIP-style alignment objective from vision-language pretraining into a sequential decision-making context, drawing on the Decision Transformer's sequence-modelling framing but with a fundamentally different (non-autoregressive) prediction head.

## Why It Matters / Open Questions

The 30× reduction in inference time (to ~3 s per task) and the elimination of per-action API costs make on-device app agents practically viable for the first time, addressing a key bottleneck that has kept prior GPT-4o-based agents out of everyday use. The ablation showing that removing text embeddings has negligible impact (63.0 vs. 63.1 overall accuracy) is practically important: it means LiMAC remains robust when UI trees are missing or noisy, as in AitW. However, the method is trained on only 13K–18K episodes with no pretraining or reinforcement learning, and the authors themselves flag error recovery, online learning, and safety with sensitive data as open problems that limit real-world deployment.
