## Problem

Scaling inference-time compute (search) for LLM code generation has not yielded gains comparable to training-time scaling, because post-trained models produce highly similar yet incorrect generations when sampled repeatedly, making search inefficient. The paper identifies this lack of high-level diversity in model outputs as the core bottleneck and asks: what is the right axis of diversity to search over to make inference-time compute effective for code generation?
![Teaser figure](../imgs/ICLR20250088/cropped_page1_idx0.webp)

## Input / Output

The method takes a competitive programming problem statement in natural language (with associated public and hidden test cases) and produces Python code solutions that must pass all tests. Internally, PLANSEARCH generates intermediate natural language artifacts—first- and second-order observations, solution sketches, and pseudocode—before the final code is produced. The pipeline generates a variable number of code completions (typically 300–400) per problem, compared to a fixed n for baselines like repeated sampling.

## Method

PLANSEARCH searches over natural language plans rather than directly over code, operating in a two-level observation tree. Starting from the problem, it prompts the LLM for first-order observations, forms all subsets of size ≤ 2, then for each subset prompts for second-order observations derived from the combination. Each leaf node (a combination of observations) is used to generate a natural language solution sketch, which is further diversified by asking the model to critique its own sketch and produce an alternative. Sketches are then translated through pseudocode into Python code in a granular multi-step process to reduce translation error. The key insight, validated empirically, is that conditioning on a correct sketch polarizes solve rates toward 0% or 100%, so maximizing diversity over the idea space (measured via LLM-as-a-judge pairwise similarity) is the dominant factor determining pass@k gains.

## Results

PLANSEARCH achieves a pass@200 of 77.0% on LiveCodeBench with Claude 3.5 Sonnet, nearly doubling the best pass@1 score (41.4%) and substantially outperforming standard repeated sampling at pass@200 (60.6% for GPT-4o). Across all four non-search models and three benchmarks (LiveCodeBench, HumanEval+, MBPP+), PLANSEARCH consistently achieves the highest pass@200, with gains of 10–15 points over repeated sampling on LiveCodeBench and 3–10 points on HumanEval+ and MBPP+. On HumanEval+, PLANSEARCH reaches 99.5% pass@200 with GPT-4o, and on MBPP+ it reaches 93.7% with Claude 3.5 Sonnet.

## Baselines & Comparisons

Against OpenAI's o1-mini (a model that already performs internal inference-time search), PLANSEARCH applied on top of o1-mini achieves 91.3% pass@200 on LiveCodeBench versus o1-mini's own 90.8% pass@200, a marginal 0.5-point gain reflecting diminishing returns when stacking search on a model already optimized for it. Against Chain-of-Thought prompting (Wei et al., 2022), IDEASEARCH (and by extension PLANSEARCH) shows non-negligible improvements, which the authors attribute to splitting the solution sketch into a separate model response rather than generating reasoning and code in a single pass. More broadly, PLANSEARCH outperforms the standard repeated sampling baseline across every model–benchmark combination: on LiveCodeBench the gap ranges from +11.6 points (GPT-4o-mini: 64.9 vs. 53.3) to +21.4 points (Claude-Sonnet-3.5: 77.0 vs. 55.6), and on HumanEval+ and MBPP+ the gains are smaller (3–10 points) due to near-saturation of those benchmarks. The intermediate IDEASEARCH method also beats repeated sampling on all settings, confirming that the key driver is diversity in idea space rather than the specific tree structure of PLANSEARCH.

## Relation to Prior Work

This paper extends the line of work on inference-time search for LLMs (repeated sampling, best-of-n, Tree of Thoughts, Reasoning via Planning) by arguing that the correct axis to search over is not tokens, code lines, or full programs, but natural-language 'idea space'—high-level observations and solution sketches. It builds directly on chain-of-thought prompting (Wei et al., 2022) as the conceptual foundation for IDEASEARCH, and borrows the backtranslation idea from machine translation (Sennrich et al., 2016) to validate that correct sketches are sufficient for correct code. The key departure from prior search-in-LLM work (ToT, RAP) is that those methods were demonstrated on contrived, small-step problems (game of 24, Blocksworld), whereas PLANSEARCH targets the complex, open-ended domain of competitive programming where the 'steps' are not obvious and the search space is vast.

## Why It Matters / Open Questions

The paper identifies a concrete, measurable bottleneck for inference-time compute—lack of diversity in model outputs—and shows that post-training (RLHF/DPO) actively reduces this diversity, causing instruct models to underperform base models at high k. This has direct implications for how future models should be trained: the current paradigm of optimizing for a single correct response is misaligned with the goal of maximizing search effectiveness. Open questions include whether the observation-tree approach can be made deeper via MCTS-style pruning, whether the diversity-search correlation generalizes beyond code generation to domains without executable verifiers, and whether distilling successful plans back into the model (as the authors suggest) can convert pass@k gains into pass@1 without inference-time overhead.
