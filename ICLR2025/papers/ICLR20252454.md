## Problem

As LLM vocabularies grow (up to 256K tokens), the cross-entropy loss layer becomes the dominant memory consumer during training, accounting for up to 90% of total memory footprint because it materializes an N×|V| logit matrix in global memory. Existing mitigations (chunking, torch.compile) reduce memory but introduce latency trade-offs, and no prior method achieves both negligible memory and competitive speed for the loss computation.
![Teaser figure](../imgs/ICLR20252454/cropped_page1_idx1.webp)

## Input / Output

The method consumes the backbone's output embeddings E (D×N in bfloat16), the classifier weight matrix C (D×|V|), and the ground-truth token index vector x (length N). It produces a per-token scalar loss vector, plus gradients ∇E (D×N) and ∇C (D×|V|) in bfloat16. Crucially, the intermediate N×|V| logit matrix is never written to global GPU memory; all intermediate computation occurs in on-chip SRAM, so the only global memory allocated beyond the required output buffers is O(N+|V|) for the LSE vector and a temporary vocabulary-ordering buffer (~1 MB).

## Method

CCE decomposes the cross-entropy loss into two operations computed entirely in on-chip SRAM via custom Triton kernels: (1) an indexed matrix multiplication that computes only the logit for the ground-truth token per position, and (2) a blockwise linear-log-sum-exp that accumulates the log-partition function over the full vocabulary without ever storing the full logit matrix. For the backward pass, CCE recomputes logits in SRAM and exploits the inherent sparsity of softmax by skipping gradient computation for any block whose entries all fall below a bfloat16 precision threshold (2⁻¹²), yielding a 3.5× speedup. A vocabulary sorting step (ordering tokens by average logit computed during the forward pass) concentrates non-trivial gradients into fewer blocks, further reducing wasted computation. For pretraining where numerical precision matters, a Kahan-summation variant (CCE-Kahan-FullC) removes gradient filtering on ∇C to avoid suppressing gradients for low-frequency tokens.

## Results

On Gemma 2 (2B) with a batch of 8,192 tokens and vocabulary size 256,000, CCE reduces the peak memory for loss+gradient computation from 28,000 MB (Baseline) to 1,164 MB — a 24× reduction — while achieving a total time of 145 ms. CCE computes the loss 5% faster than torch.compile (46 ms vs. 49 ms) and is within 2 ms on the combined loss+gradient pass (145 ms vs. 143 ms). For fine-tuning four models (Gemma 2 2B, Phi 3.5 Mini, Qwen 2.5 7B, Mistral NeMo) on Alpaca, CCE produces loss curves indistinguishable from torch.compile, and for pretraining on 5% of Open WebText, CCE-Kahan-FullC matches torch.compile's validation perplexity exactly.

## Baselines & Comparisons

CCE dominates all four baselines on memory: it uses 1,164 MB for loss+gradient versus 1,474 MB (Liger Kernels), 9,631 MB (Torch Tune), 16,000 MB (torch.compile), and 28,000 MB (Baseline PyTorch). On speed, CCE (145 ms) is 2.1× faster than Liger Kernels (304 ms), 1.2× faster than Torch Tune (169 ms), and 1.4× faster than Baseline (208 ms), while essentially matching torch.compile (143 ms, a 2 ms difference). The memory advantage is most dramatic against the standard PyTorch baseline (24× less) and torch.compile (14× less), directly enabling 1.5×–10× larger batch sizes across frontier models. On training quality, CCE ties torch.compile exactly: fine-tuning loss curves are indistinguishable across four models, and pretraining validation perplexity (using the CCE-Kahan-FullC variant) matches torch.compile on all four models tested.

## Relation to Prior Work

CCE directly extends the FlashAttention paradigm—materializing intermediate matrices in on-chip SRAM rather than global DRAM—from the attention layer to the cross-entropy loss computation. It departs from chunking-based approaches (Liger Kernels, Torch Tune) that create an inherent memory-latency tradeoff by using only on-chip SRAM and exploiting the mathematical structure of cross-entropy (only one logit plus a log-sum-exp are needed per token). The gradient filtering step is a novel contribution that leverages the inherent sparsity of softmax in bfloat16, a property not previously exploited for loss computation. The paper also contrasts with vocabulary-reduction methods (hierarchical softmax, byte-level models) and parallelism strategies, positioning CCE as orthogonal to and composable with those approaches.

## Why It Matters / Open Questions

CCE eliminates what has become the dominant memory bottleneck in modern LLM training (up to 90% of total memory for large-vocabulary models), enabling 1.5×–10× larger batch sizes without sacrificing speed or convergence. This has immediate practical impact: models like Gemma 2 (2B) that previously required an entire 80 GB GPU just for the loss layer can now train with negligible overhead. Open questions include whether a CUDA-native implementation (vs. Triton) could close the small remaining speed gap, whether the approach extends to other large-classification problems (image classification, contrastive learning), and how CCE interacts with pipeline parallelism for very large models where the classifier head is currently a memory-to-computation outlier. A limitation is that pretraining requires the Kahan-FullC variant, which is slower than the fine-tuning variant, though the larger batch sizes it enables often offset this in wall-clock time.
