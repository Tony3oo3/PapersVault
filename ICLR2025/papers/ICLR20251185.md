## Problem

Traditional file systems manage files by attributes (size, timestamps) and require users or agents to recall exact file names and navigate complex directory hierarchies through cryptic commands. While LLM-based agents have advanced rapidly, their file management interactions remain stuck in this command-driven paradigm, and no general-purpose semantic file system exists to serve as a shared infrastructure layer for diverse LLM agents.
![Teaser figure](../imgs/ICLR20251185/cropped_page1_idx0.webp)

## Input / Output

The system accepts free-form natural language prompts (e.g., 'Locate the 3 papers showing the highest correlation with reinforcement learning in LLM-training') and file content in multiple text formats (TXT, PDF, DOCX). The LSFS parser converts prompts into structured JSON containing API function names and arguments, which are then executed against a vector database indexed by all-MiniLM-L6-v2 embeddings. Outputs include retrieved file contents with LLM-generated summaries, before/after change summaries, shareable cloud links with configurable expiration, rolled-back file versions (by date or version number), and newly created grouped directories.

## Method

LSFS is a layered architecture operating on top of traditional file systems, comprising three tiers: (1) atomic and composite syscalls that perform CRUD operations, keyword/semantic retrieval, grouping, and file joining over a LlamaIndex-backed vector store; (2) higher-level APIs (Retrieve-Summary, Change-Summary, Rollback, Link) that compose syscalls with LLM-powered summarization and a version recorder for rollback; and (3) an LLM-based parser (default GPT-4o-mini) that translates natural language prompts into executable API calls via structured JSON schemas. A supervisor process continuously monitors the underlying file system and synchronizes changes to the semantic index in real time, while a process-lock mechanism and user-confirmation step guard against irreversible operations. The key design insight is offloading file retrieval from LLM long-context reasoning to deterministic keyword matching plus embedding-based semantic similarity search, which avoids accuracy degradation as file counts grow and yields 2.1× faster retrieval with ≥15% accuracy improvement over LLM-only baselines.

## Results

In semantic file retrieval, LSFS achieves at least 15% accuracy improvement (up to 45.6% with GPT-4o-mini at 120 files) and 2.1× higher retrieval speed (up to 92.4% time reduction) compared to using LLM directly on a traditional file system. In keyword-based retrieval, LSFS achieves 89.1–90.9% F1-score across 10–40 files, outperforming TFS search window and TFS-grep while remaining competitive with the enhanced TFS-grep*. For file sharing, LSFS achieves a 100% final success rate in generating valid shareable links, compared to 5–10% for LLM-based baselines. The LSFS parser achieves 90% average first-pass accuracy, rising to 100% on a second pass for most LLM backbones.

## Baselines & Comparisons

In the file sharing task, LSFS achieves a 100% final success rate (code generation, link generation, and link validity all at 100%), dramatically outperforming Gemini-1.5-flash (10% final success) and GPT-4o-mini (5% final success), which struggle to produce valid shareable links despite generating code. In semantic file retrieval, LSFS consistently outperforms the LLM-without-LSFS baseline by 14–58 percentage points in accuracy while reducing retrieval time by 50–92%, with the gap widening as file count increases (e.g., 35.2% → 92.9% accuracy at 120 files with Gemini-1.5-flash). In keyword-based retrieval, LSFS (89.1–90.9% F1) surpasses TFS search window (81.7–84.0% F1) and TFS-grep (33.7–40.2% F1) but trails the manually enhanced TFS-grep* (100% F1), which requires complex multi-step commands and manual binary-to-text conversion. LSFS also outperforms AutoGPT (5% final success) and Code Interpreter (0% final success) in file sharing, demonstrating that a structured system-level approach is more reliable than ad-hoc LLM code generation for file operations.

## Relation to Prior Work

This paper extends the lineage of semantic file systems (Gifford et al. 1991; Hua et al. 2009, 2013; Leung et al. 2009) by replacing rule-based or ontology-driven semantic indexing with LLM-generated embedding vectors stored in a vector database (LlamaIndex + all-MiniLM-L6-v2). It also builds on the semantic parser tradition (Lin et al. 2018 NL2Bash; Kamath & Das 2018) but departs from prior work by using an LLM (GPT-4o-mini) with structured JSON schemas rather than trained sequence-to-sequence models. Crucially, while prior LLM-based file management efforts (OS-Copilot, Mobile-Agent, AgentLite) operate at the application level with task-specific agents, LSFS positions itself as a system-level infrastructure layer within AIOS, providing reusable syscalls and APIs that any agent can call.

## Why It Matters / Open Questions

LSFS offers a practical infrastructure layer that could reduce the cognitive and operational burden on LLM agents performing file operations, with the 100% file-sharing success rate (vs. 5–10% for LLM-code-generation baselines) and 2.1× retrieval speedup being practically useful. However, the evaluation is limited to ≤120 text files on a single machine, the semantic retrieval gains (15–24%) are moderate, and the system's reliance on an LLM parser introduces a hallucination bottleneck that the authors mitigate only with user confirmation. Open questions include scaling to multi-modal files (images, audio, video), privacy guarantees when file content is sent to external LLM APIs, and whether the embedding-based semantic index remains effective at enterprise-scale file counts.
