## Problem

Natural language prompts for LLMs suffer from inherent ambiguity, lack of modularity, and no mechanism for static verification, making them unreliable as the 'APIs' for human-AI interaction. Existing remedies either extend programming languages (LangChain, DSPy, Semantic Kernel), which tightly couple prompts to code and exclude non-technical users, or apply simple NL templates (RISEN, RODES) that only offer micro-level stylistic improvements without addressing expressive limits or state management. The paper asks whether a controlled natural language can integrate software engineering principles at a macro level to produce structured, lintable, and accessible prompts.

## Input / Output

The system accepts free-form natural language requirement statements (e.g., 'I need an agent that can customize personalized exercise plans') and produces structured CNL-P prompts organized into BNF-defined modules (PERSONA, CONSTRAINTS, DATA_TYPE, VARIABLES, WORKER with MAIN_FLOW/IF_BLOCK/COMMAND, CALL_API, INPUTS/OUTPUTS) delimited by 'keyword Like' identifiers such as DEFINE_PERSONA and END_PERSONA. For evaluation, CNL-P prompts are fed as system prompts to LLMs on classification tasks, producing task responses scored against ground-truth answers. The linting tool additionally outputs AST-Like JSON representations and semantic diagnostics (error location, type, and explanation) by traversing the parsed structure with Pydantic-based type checking.

## Method

CNL-P is a controlled natural language whose syntax is formally specified in BNF and whose design embeds four SE first principles (modularity, abstraction, encapsulation, separation of concerns) alongside PE best practices (persona, constraints, chain-of-thought). Two supporting tools operationalize the framework: (1) an NL-to-CNL-P transformer agent that extracts role, objective, variables, data types, and workflow steps from free-form NL and maps them into the CNL-P grammar, and (2) a two-stage linting tool that first performs syntactic analysis (Parser_Like) to build an AST-Like JSON using keyword-Like delimiters, then performs semantic analysis (NodeVisitor_Like) by traversing the JSON to check variable declarations, type conformance via Pydantic, and API parameter validity. This is the first application of static analysis techniques to natural language, and the paper validates it through three empirical studies: conversion quality assessment across five dimensions (RQ1), LLM comprehension without few-shot or language specification on six classification tasks across five models (RQ2), and linting accuracy versus GPT-4o on 47 error-injected instances (RQ3, achieving 100% accuracy vs. 76.6% for the LLM baseline).

## Results

In RQ3 (static checking), the CNL-P linting tool achieves 100% accuracy and 0% redundancy across 47 task instants, compared to GPT-4o's 76.60% accuracy and 19% redundancy. In RQ1 (conversion quality), CNL-P demonstrates clear advantages over RISEN and RODES on Modularity, Extensibility/Maintainability, and Process Rigor across all three evaluation groups (LLM, technical, non-technical). In RQ2 (LLM comprehension), CNL-P prompts achieve performance comparable to natural language prompts across 5 LLMs and 6 classification tasks without requiring any language specification, few-shot examples, or fine-tuning.

## Baselines & Comparisons

The paper compares CNL-P against two NL template baselines (RISEN and RODES) and GPT-4o as a direct static-checking baseline. On RQ1 (conversion quality, 93 prompts from Awesome ChatGPT Prompts), CNL-P outperforms both RISEN and RODES on Modularity, Extensibility/Maintainability, and Process Rigor across all three evaluator groups; the technical group showed the strongest preference for CNL-P, while RISEN scored notably lower on Adherence to Original Intent due to its 'Expectation' module narrowing agent scope. On RQ2 (6 Natural Instructions classification tasks, 5 LLMs), CNL-P achieves performance on par with plain NL prompts without any additional language specification or few-shot examples, confirming that its structured syntax does not degrade LLM comprehension. On RQ3 (47 error-detection instants), the CNL-P linting tool achieves 100% accuracy with 0% redundancy, substantially outperforming GPT-4o (76.60% accuracy, 19% redundancy), which produced 11 incorrect or redundant error reports. CNL-P's advantage is most pronounced on structural dimensions (modularity, process rigor) where its grammar-driven design provides inherent benefits over free-form NL templates.

## Relation to Prior Work

This paper carves new ground by applying software engineering principles (modularity, abstraction, encapsulation, separation of concerns) at the macro level to natural language prompts, going beyond the micro-level NL template approaches (RISEN, RODES) and the implementation-oriented PL-based frameworks (LangChain, DSPy, Semantic Kernel, Guidance, LMQL). It draws on the Controlled Natural Language (CNL) literature (Kuhn, 2014; PENS framework) and prompt engineering best practices (persona, constraints, CoT) to define a BNF-specified grammar (CNL-P) that treats prompts as structured, lintable 'APIs' for AI interaction. The linting tool adapts static analysis techniques from traditional SE (inspired by TypeChat and Pydantic) to NL for the first time, and the NL-to-CNL-P transformer agent bridges the gap between free-form user input and the structured format.

## Why It Matters / Open Questions

The paper proposes a concrete path toward a NL-centered programming paradigm where non-technical stakeholders can define, validate, and maintain AI agent specifications using structured natural language, with SE tooling (linting, eventual compilation) ensuring correctness. Key open questions include whether the CNL-P compiler backend (translating to DSPy/LangChain/Semantic Kernel code) will work reliably at scale, whether the approach generalizes beyond the six classification tasks and 93 prompts evaluated, and how requirement clarification (explicitly out of scope) will be automated. The assumption that users provide well-defined requirements limits near-term practical impact, and the small evaluation datasets (47 linting instances, 50 instances per task) leave robustness questions open.
