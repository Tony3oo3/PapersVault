## Problem

Fine-tuned LLMs for Verilog code generation suffer from two critical weaknesses: poor performance on problems containing non-textual representations (Karnaugh maps, FSM state-transition diagrams, waveforms) and high variability across training checkpoints where models make small, seemingly trivial errors on otherwise solvable problems. Existing synthetic data generation methods (Self-Instruct, OSS-Instruct) cannot reliably produce correct solutions for these non-textual formats or target the specific minor errors that cause pass-rate degradation.

## Input / Output

The model receives a natural language problem description (either machine-generated line-by-line instructions or human-written high-level descriptions) that may embed non-textual representations—Karnaugh maps as tabular grids with Gray-coded rows/columns, FSM diagrams as edge lists or transition tables, and waveforms as tables recording signal values at discrete time steps—followed by a Verilog module header specifying port names and widths. The output is a complete Verilog RTL module, evaluated for syntax and functional correctness using Icarus Verilog testbenches with the unbiased pass@k metric (20 samples per problem at temperatures 0.2 and 0.8).

## Method

The paper introduces a three-component data curation pipeline (SDG-CC-Repair, ~110k total samples) for instruction-tuning code LLMs. First, 80.1k synthetic examples are generated via Self-Instruct, OSS-Instruct, Docu-Instruct, and non-textual prompting using nemotron-4-340b-instruct, filtered by deduplication, benchmark decontamination, syntax checks, and self-verification. Second, 28.5k correct-by-construction (CC) examples guarantee solution accuracy for non-textual representations: Karnaugh maps are built from random minterm/don't-care assignments converted to SOP Verilog; FSMs are constructed via random tree-based state-transition graphs (ensuring reachability and out-degree 2^w) rendered as Moore or Mealy Verilog; waveforms are produced by simulating the CC code and parsing VCD dumps into signal tables. Third, 1.4k targeted repair examples are created by prompting an LLM to generate detailed error reports from checkpoint-varying benchmark failures, categorizing errors into types (vector concatenation, latch hazards, timing violations, etc.), then injecting those specific error patterns into correct open-source code snippets; quality is enforced via a self-consistency check confirming the LLM can fix the injected errors using only the report's hints. Models (Starcoder2-15B, CodeLlama-7B, DeepSeek-Coder-6.7B) are fine-tuned for one epoch with full-parameter Adam updates and cross-entropy loss masked to response tokens only.

## Results

The fine-tuned Starcoder2-15B (SDG-CC-Repair) achieves 81.9% pass@1 on VerilogEval-Machine and 68.0% pass@1 on VerilogEval-Human, surpassing the prior SOTA (CodeV CodeQwen 7B at 77.6% and 53.2%) by 3.8% and 14.8% respectively. On RTLLM v1.1, the same model reaches 49.0% functional pass@1, outperforming the previous best (CodeV CodeLlama 7B at 39.4%) by 9.6%. The paper reports overall improvements of 3.8%, 10.9%, and 6.6% in pass@1 over prior SOTA on VerilogEval-Machine, VerilogEval-Human, and RTLLM respectively. Ablations confirm that correct-by-construction (CC) data primarily boosts Human/NonText performance (54.7%→62.0% pass@5), while targeted Repair data lifts all benchmarks (e.g., Machine pass@1 from 73.9% to 81.9%).

## Baselines & Comparisons

The paper's fine-tuned Starcoder2-15B (SDG-CC-Repair) outperforms all 12 baselines on both VerilogEval subsets and RTLLM. On VerilogEval-Machine, it leads CodeV CodeQwen 7B (77.6%) by 4.3 points and GPT-4o (65.9%) by 16 points. On VerilogEval-Human, the gap is largest: 68.0% vs. OriGen (54.4%), CodeV CodeQwen (53.2%), and GPT-4o (57.1%), reflecting the benefit of correct-by-construction non-textual data. On RTLLM v1.1 functional pass@1, the model reaches 49.0%, beating CodeV CodeLlama 7B (39.4%), DeepSeek-Coder-V2 236B (34.5%), and GPT-4o (33.8%). Notably, even the 7B CodeLlama fine-tuned with the same data (78.1% Machine, 63.1% Human) surpasses the unfine-tuned 236B DeepSeek-Coder-V2 (68.2% Machine, 56.4% Human), demonstrating that data quality matters more than raw model scale for Verilog generation. The paper also observes that recent frontier models (GPT-4o, Llama-3.1 405B) have closed the gap with prior Verilog-specific efforts on Machine descriptions but still lag significantly on Human descriptions, where the proposed method's advantage is most pronounced.

## Relation to Prior Work

This paper extends the synthetic data generation pipeline for Verilog code (building on Self-Instruct and OSS-Instruct) by identifying two specific failure modes of LLM-generated data: poor handling of non-textual representations (Karnaugh maps, FSM diagrams, waveforms) and uncontrolled 'minor' errors that cause pass-rate variability across training checkpoints. Rather than relying on LLMs to verify solution correctness (as in prior Verilog-specific work like CodeV, BetterV, and OriGen), the authors introduce a correct-by-construction data generation pipeline inspired by AlphaGeometry's symbolic deduction approach, combined with a novel targeted code repair strategy that injects identified error patterns into verified open-source code. This represents a conceptual shift from 'LLM generates and self-verifies' to 'deterministic construction plus targeted error injection' for low-resource HDL domains.

## Why It Matters / Open Questions

The targeted code repair approach—using model checkpoint error reports to create a small (1.4k) but highly effective repair dataset—is a transferable data curation strategy that could apply to other low-resource code domains where automated verification is difficult. The finding that pass-rate variability across checkpoints stems from unverified synthetic data noise rather than catastrophic forgetting reframes how practitioners should think about fine-tuning data quality for HDL. Open questions include whether the correct-by-construction template approach generalizes beyond the three non-textual representation types studied, whether iterative repair (shown to saturate after one iteration) can be extended with more diverse error sources, and whether the reduced code diversity on NonText problems (due to template-based generation) limits real-world applicability.
