## Problem

Existing tool documentation is authored for human developers and suffers from incompleteness, redundancy, and inaccuracy that obstruct LLMs from correctly understanding and invoking external tools. Manually revising documentation to align with LLM comprehension is labor-intensive, does not scale to large tool collections, and cannot keep pace with evolving tool functionalities. The paper asks whether LLMs can autonomously refine tool documentation through their own trial-and-error interactions with the tools.
![Teaser figure](../imgs/ICLR20252004/cropped_page1_idx1.webp)

## Input / Output

The method consumes raw API documentation (natural-language descriptions of tool names, parameters, and return values) together with live access to the actual tool API for execution, and an LLM backbone (e.g., GPT-4o) that both generates exploratory queries and evaluates documentation quality. The output is a revised natural-language tool description per tool, iteratively updated over up to 5 rounds, where each revision incorporates real execution feedback (success responses, error messages, and returned data structures) rather than relying solely on the original text. The revised documentation is model-agnostic and generalizes across different LLMs at inference time.

## Method

DRAFT is a three-phase iterative loop: (1) an Explorer synthesizes diverse user queries, invokes the tool, and captures execution results, with a diversity-promoting strategy that enforces a cosine-similarity threshold (φ=0.9) between new and prior queries and triggers self-reflection when the constraint is violated; (2) an Analyzer compares the current documentation against actual tool outputs to identify inconsistencies, gaps, and redundancies, producing natural-language revision suggestions; (3) a Rewriter integrates these suggestions to produce an updated documentation and proposes the next exploration direction. A tool-adaptive termination mechanism computes a combined BLEU + embedding-similarity score between consecutive documentation versions and halts iteration once the change falls below a threshold (τ=0.75), preventing overfitting from excessive rounds. The entire process is fully automated, requires no gradient updates, and operates purely through in-context prompting of the LLM backbone.

## Results

DRAFT achieves the highest Correct Path Rate (CP%) across all three datasets and all three LLMs. For GPT-4o, DRAFT reaches 88.00% CP% on RestBench-TMDB, 70.17% on RestBench-Spotify, and 51.00% on ToolBench, compared to 71.00%, 28.07%, and 37.00% for the ReAct baseline. A particularly notable finding is that GPT-4o-mini enhanced with DRAFT (47.00% CP% on ToolBench) surpasses GPT-4o without DRAFT (37.00%), demonstrating strong cross-model generalization of the refined documentation. Win Rate improvements are also consistent, with DRAFT achieving 71.00% Win% on TMDB and 84.21% on Spotify for GPT-4o.

## Baselines & Comparisons

DRAFT consistently outperforms all three baselines (ReAct, DFSDT, EasyTool) on CP% across every dataset and LLM combination. Against ReAct, the most direct baseline, DRAFT improves CP% by 17 points on TMDB (88 vs. 71) and 14 points on ToolBench (51 vs. 37) for GPT-4o. Against DFSDT, which uses depth-first search for error correction, DRAFT gains 14 CP% points on TMDB and 10 on ToolBench for GPT-4o, while also achieving substantially higher Win% (71% vs. 61% on TMDB). Against EasyTool, which rewrites documentation in a single pass without iterative feedback, DRAFT achieves 9 CP% higher on TMDB (88 vs. 79) and 6 on ToolBench (51 vs. 45) for GPT-4o, and is the only method evaluated on Spotify where EasyTool was not implemented. The cross-model generalization is a key differentiator: documentation refined using GPT-4o's feedback also improves Llama-3-70B and GPT-4o-mini performance, and GPT-4o-mini with DRAFT even exceeds GPT-4o without DRAFT on ToolBench (47% vs. 37% CP%).

## Relation to Prior Work

DRAFT extends the tuning-free tool learning paradigm (ReAct, DFSDT) and the documentation-quality line of work initiated by EasyTool, which performs a single-pass ChatGPT rewrite of tool descriptions. The key departure is making documentation refinement iterative and grounded in actual tool execution feedback, drawing on self-reflection (Reflexion) for the diversity-promoting exploration strategy and on learning-from-feedback literature for the analyzer-rewriter loop. Conceptually, the paper reframes tool documentation as a living artifact that should co-evolve with the LLM's demonstrated understanding, rather than a static human-authored artifact.

## Why It Matters / Open Questions

The finding that documentation refined by a single model (GPT-4o) transfers effectively to other architectures (Llama-3-70B, GPT-4o-mini) suggests that the 'LLM-readable' properties of good tool documentation are somewhat model-agnostic, which could reduce the cost of maintaining documentation across model fleets. However, the approach is limited to API-style tools with clear input/output contracts, requires multiple LLM calls per iteration (expensive at scale), and has only been validated on three relatively small benchmarks. Open questions include scalability to the 16,000+ APIs in ToolBench, handling of tools with side effects or stateful interactions, and whether the iterative process can be parallelized across tools without quality degradation.
