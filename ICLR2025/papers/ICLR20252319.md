## Problem

Existing LLM-based planning systems face a fundamental trade-off: zero-shot planners (e.g., ReAct, SayCan) handle only simple single-objective tasks, while frameworks for complex multi-constraint or long-horizon planning require task-specific in-context examples, PDDL domain files, pre-defined critics, or existing MILP codebases. No prior system can solve diverse complex planning problems from scratch using only a natural language task description, background data, and a user query.

## Input / Output

The method consumes three user-supplied inputs: a natural language task description (domain setup and objective), structured background information or API definitions (numeric parameters, cost tables, availability matrices), and a user query (a what-if constraint modification or a new initial/goal state specification). No task-specific examples, PDDL files, or pre-existing solver code are required. The output is a guaranteed-optimal plan rendered in a fixed JSON format: decision variable values (e.g., units shipped per supplier-destination pair) for multi-constraint tasks, or a step-by-step action sequence for multi-step tasks, accompanied by a brief commonsense evaluation of the result.

## Method

LLMFP's core insight is that diverse planning problems share a common structure as constrained optimization problems, and that LLMs can reliably *formulate* such problems even when they cannot *solve* them. The framework is a five-stage pipeline: (1) a Definer prompts the LLM to extract the goal, decision variables, and constraints (including implicit ones, guided by a three-step relation-reasoning instruction); (2) a Formulator produces a structured JSON representation with six fields per variable (name, SMT_variable flag, cardinality, data_source, value, specific_requirement), extended to five semantic stages (objects, predicates, actions, update, goal) for multi-step tasks; (3) a Code Generator writes executable Python code using the Z3 SMT solver syntax from that representation; (4) a Result Formatter converts solver output into a fixed schema and performs a commonsense sanity check; (5) a Self-Assess-and-Modification loop evaluates each stage, identifies the first incorrect one, and regenerates from that point (up to 5 iterations). The Z3 SMT solver guarantees completeness and soundness, so correct encodings yield provably optimal plans. Only two task-agnostic example input-output pairs appear in the Formulator prompt; no task-specific examples or external verifiers are used.

## Results

LLMFP achieves an average optimal rate of 83.7% (GPT-4o) and 86.8% (Claude 3.5 Sonnet) across 9 diverse planning tasks, significantly outperforming the best baseline (Direct o1-preview) by 37.6% and 40.7% respectively. On 5 multi-constraint problems, LLMFP reaches 79.1% (GPT-4o) and 80.7% (Claude), while on 4 multi-step problems it reaches 87.5% (GPT-4o) and 91.8% (Claude). The framework also demonstrates robustness to obfuscated problems, maintaining 77.7% (GPT-4o) and 98.0% (Claude) on Mystery Blocksworld where baselines drop to near zero.

## Baselines & Comparisons

LLMFP outperforms all baselines across all 9 tasks. On multi-constraint problems, the strongest baselines are Code (GPT-4o, 31.1%) and Code_SMT (Claude 3.5, 62.4%); LLMFP surpasses them by 48.0% and 18.3% respectively. On multi-step problems, Direct o1-preview is the strongest baseline at 68.1%; LLMFP (GPT-4o) exceeds it by 19.4%, and LLMFP (Claude 3.5) at 91.8% beats CoT (Claude 3.5, 45.9%) by 45.9%. Code and Code_SMT baselines nearly fail on multi-step tasks (0.1% and 0.0% average for GPT-4o), as they struggle to generate correct PDDL or SMT encodings without task-specific scaffolding. Notably, LLMFP remains robust to obfuscated problem names (Mystery Blocksworld: 77.7%/98.0%) where Direct and CoT baselines collapse to under 3%, demonstrating that the formal optimization encoding is insensitive to surface-level naming.

## Relation to Prior Work

This paper departs from two main lines of work on LLM-based planning. First, zero-shot LLM planners (Huang et al., Ahn et al.) can handle simple single-objective tasks but fail on multi-constraint or long-horizon problems. Second, LLM+Solver approaches (LLM+P, LLM-Modulo, Li et al. for supply chain) combine LLMs with external planners but require task-specific PDDL domain files, pre-existing MILP code templates, or hand-crafted critics/verifiers, limiting cross-task generalization. LLMFP carves new ground by treating the LLM's role as *formulating* the optimization problem from scratch (goal, variables, constraints) rather than solving it, then delegating the search to a general-purpose SMT solver (Z3). The multi-stage pipeline (Definer → Formulator → Code Generator → Result Formatter → Self-Assess) with task-agnostic examples is the key architectural departure from prior LLM+Solver work that relied on domain-specific scaffolding.

## Why It Matters / Open Questions

The paper demonstrates that the flexibility-vs-complexity trade-off in LLM planning can be largely resolved by separating problem formulation (LLM's strength) from problem solving (solver's strength), achieving 83.7–86.8% optimal rates across 9 diverse tasks with no task-specific examples. This has direct practical implications for deploying LLM-based planners in logistics, workforce scheduling, and robotics where task descriptions vary but the underlying structure is always constrained optimization. Key limitations include dependence on clear, unambiguous task descriptions (confusing what-if queries still cause failures), solver runtime scaling for large combinatorial spaces (e.g., Sokoban with many positions), and the current restriction to problems expressible as SMT-encodable optimization. Open questions include whether the approach extends to stochastic or partially observable planning, how to handle problems where the optimization formulation itself is ambiguous, and whether lighter-weight solvers or learned heuristics can reduce the runtime bottleneck for large-scale instances.
