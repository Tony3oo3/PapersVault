## Problem

Existing tool learning research assumes a static environment where the APIs provided in the prompt match those deployed on the server, yet real-world APIs undergo frequent version updates, renamings, and deprecations. This tool variability causes LLMs to invoke outdated APIs and suffer severe performance degradation, a problem that has been largely overlooked in the literature. The paper is the first to systematically investigate the impact of API name, parameter, and response format changes on LLM tool-use performance.

## Input / Output

The model receives a task description and a set of collected API usage descriptions (P_c) in the prompt, which may be outdated relative to the server-deployed APIs. It produces a sequence of REACT-format actions (thought, API invocation with parameters, and observation from the environment), and may additionally emit UpdateTool calls that rewrite the API descriptions in the prompt to reflect newly discovered tools. Critically, the prompt never reveals that APIs have changed; the model must discover new API names and parameters solely through deprecation error messages and invocation errors returned by the dynamic environment.

## Method

TOOLEVO customizes Monte Carlo Tree Search to drive active exploration of a dynamic tool environment. The four MCTS phases are adapted as follows: Selection uses PUCT to balance exploration and exploitation; Expansion samples k candidate REACT-format actions from the LLM policy; Simulation employs a cached rollout strategy that stores subtrees to avoid redundant rollouts while keeping them invisible to the selection phase; and Backpropagation updates Q-values and visit counts from the terminal reward. Two key modules are integrated into the tree: a self-reflection module that, upon encountering an invocation or deprecation error, generates corrective reflective actions appended to the error state rather than backtracking, and a tool-update module (implemented as a system tool UpdateTool) that, after a successful new-API invocation, summarizes the new tool's usage and updates P_c in the prompt, acting as a memory mechanism. The collected successful trajectories (~30k) from MCTS exploration are then used for supervised fine-tuning, teaching the model to adapt to tool variability through trial-and-error rather than memorizing static invocation patterns.

## Results

On the OOD dynamic environment (Table 4), TOOLEVO (Llama3-8B) achieves 61.6% (Easy) and 28.3% (Hard) average accuracy, outperforming Static-SFT (Llama3-8B) by +41.2 and +19.3 points respectively, and surpassing the much larger Llama3-70B-Instruct (43.1/16.3) by a wide margin. On the in-domain dynamic environment (Table 3), TOOLEVO (Qwen2-7B) reaches 68.7% (Easy) and 32.1% (Hard), beating Qwen2-72B-Instruct (54.1/18.4) and Static-SFT (Qwen2-7B) (40.8/17.3). In the static environment (Table 2), TOOLEVO remains competitive without any fine-tuning on the static APIs, achieving 70.7% (Easy) with Qwen2-7B versus 68.8% for Static-SFT, confirming that adaptability training does not sacrifice static performance.

## Baselines & Comparisons

Against the key methodological baseline Static-SFT, TOOLEVO achieves dramatic gains in dynamic settings: +41.2 Easy / +19.3 Hard points on OOD (Llama3-8B) and +27.9 Easy / +14.8 Hard points on in-domain dynamic (Qwen2-7B), while remaining competitive in the static setting (within ~3.5 points). Against proprietary models, TOOLEVO (Llama3-8B) surpasses GPT-4o (56.0/24.4) and GPT-4 (40.3/23.2) on OOD Easy/Hard, and narrowly beats Claude-3.5-Sonnet on Easy (61.6 vs 60.2) but trails on Hard (28.3 vs 32.1). Against larger open-source models, TOOLEVO (Llama3-8B) outperforms Llama3-70B-Instruct by +18.5 Easy / +12.0 Hard on OOD, and TOOLEVO (Qwen2-7B) outperforms Qwen2-72B-Instruct by +24.2 Easy / +9.9 Hard, demonstrating that adaptability training in a dynamic environment is more effective than simply scaling model size. The base open-source models without fine-tuning (Llama3-8B-Instruct, Qwen2-7B-Instruct) perform poorly under tool variability (10.7/8.0 and 42.4/11.1 on OOD), confirming that neither raw capability nor static fine-tuning alone suffices for handling evolving APIs.

## Relation to Prior Work

This paper extends the tool-learning line of work (ToolLLM, Toolformer, ReAct) by introducing the previously unaddressed problem of tool variability—where APIs change names, parameters, or response formats over time. It repurposes MCTS (with PUCT selection) as an active exploration mechanism to generate trial-and-error trajectories in dynamic environments, departing from prior approaches that rely solely on static supervised fine-tuning or in-context learning. The self-reflection and tool-update modules build on the ReAct action format but add a memory-like mechanism (UpdateTool) that lets the model rewrite its own prompt-level API descriptions based on environmental feedback, a capability absent from prior tool-learning frameworks.

## Why It Matters / Open Questions

This is the first systematic study quantifying how tool variability degrades LLM performance, and the ToolQA-D benchmark provides a reusable evaluation platform for future work on dynamic tool adaptation. The finding that static SFT induces 'stereotypes' causing severe performance collapse in dynamic settings (e.g., Static-SFT Llama3-8B drops from 70.2 to 20.4 Easy average) highlights a practical risk for deployed LLM agents that prior work has overlooked. Open questions include whether the approach scales beyond 12 tools, whether preference learning (DPO/RLHF) on the collected trajectories would further improve adaptability, and how well the method handles more realistic, gradual API evolution rather than the discrete GPT-4-generated changes used here.
