## Problem

SWE-bench, the dominant benchmark for autonomous software engineering agents, covers only Python repositories with predominantly text-based problem statements, leaving unexplored how these systems perform on visual, user-facing software domains such as front-end web development, data visualization, and interactive mapping. The paper asks whether existing agent systems generalize to JavaScript codebases where bugs are frequently described through screenshots, diagrams, and videos rather than pure text, and where codebases employ diverse programming paradigms (object-oriented, functional, declarative) that break Python-centric tooling.

## Input / Output

Each task instance provides a JavaScript/TypeScript codebase (median 549K non-test lines across 1,799 files), a GitHub issue containing text plus at least one image or video (median resolution 262K pixels, aspect ratio 5:3), and a set of fail-to-pass and pass-to-pass unit tests. The system must produce a code patch that makes all F2P tests pass without breaking P2P tests. Notably, 83.5% of instances require the image to solve the task, 69 instances verify correctness via pixel-level visual testing (rendering webpages and comparing screenshots), and 28% of reference solutions edit multiple file types (JS, TS, HTML, CSS, Lua, SCSS).

## Method

The paper introduces SWE-bench M, a dataset of 619 task instances from 17 user-facing JavaScript repositories (e.g., carbon, openlayers, bpmn-js, Chart.js), collected by scraping 135K PRs, filtering for visual assets in issue text or test patches, building per-repository Docker environments with Node.js and Chrome, removing inconsistent tests via 10-run validation, and performing human annotation to confirm image necessity. For evaluation, the authors adapt four existing SWE-bench systems: SWE-agent (with Base, JS, and M configurations adding ESLint linting and a web browser with screenshot capability), Agentless (replacing Python's ast module with a custom JavaScript parser), and a BM25-based RAG baseline; AutoCodeRover and Moatless proved infeasible to adapt due to deep Python-specific AST dependencies. The key empirical finding is that SWE-agent's language-agnostic, interaction-focused agent-computer interface (12.2% resolved with GPT-4o) substantially outperforms workflow-oriented localize-then-repair systems (Agentless JS: 3.1–6.2%), revealing that offloading problem-solving to manually engineered, language-specific pipelines is a critical generalization bottleneck.

## Results

On SWE-bench M (517 test instances), the best system achieves 12.2% resolved (SWE-agent M with GPT-4o), while the next-best system (Agentless JS with Claude 3.5 Sonnet) reaches only 6.2%. SWE-agent configurations (Base, JS, M) cluster tightly around 11.4–12.2% resolved regardless of the underlying LM, whereas Agentless JS and RAG average 3.9% and 5.5% respectively. Per-task inference cost ranges from $0.15 (RAG) to $3.11 (SWE-agent M/JS with Claude 3.5 Sonnet), with SWE-agent M using GPT-4o at $2.94.

## Baselines & Comparisons

SWE-agent (Yang et al., 2024), adapted into three configurations (Base, JS, M), dominates all comparisons, resolving 11.4–12.2% of instances regardless of whether GPT-4o or Claude 3.5 Sonnet is used as the backbone LM. Agentless (Xia et al., 2024), adapted as Agentless JS with a custom JavaScript parser replacing the Python ast module, achieves only 3.1% (GPT-4o) and 6.2% (Claude 3.5 Sonnet) resolved—roughly half the SWE-agent rate—largely because its Python-centric localization pipeline fails to recognize JavaScript's declarative and functional patterns (e.g., arrow functions). The RAG baseline inherited from SWE-bench (Jimenez et al., 2024a), using BM25 retrieval with a JavaScript-adapted prompt, scores 6.0% (GPT-4o) and 5.0% (Claude 3.5 Sonnet), confirming that retrieval alone cannot compensate for the lack of interactive code navigation. Two additional SWE-bench leaders—AutoCodeRover and Moatless—could not be benchmarked at all because their localization tools are irreparably tied to Python AST structures, underscoring the paper's central finding that generalizability across languages and modalities remains an unsolved design challenge for agent-based software engineering systems.

## Relation to Prior Work

This paper directly extends SWE-bench (Jimenez et al., 2024a) by replacing its Python-only, text-only task instances with JavaScript, multimodal ones, while preserving the issue→patch→test-verification formulation. It also positions itself at the intersection of two previously separate research threads: repository-level software engineering agents (SWE-agent, Agentless, AutoCodeRover, Moatless) and multimodal code generation (MMCode, Design2Code, Plot2Code), which prior work has studied in isolation. The key conceptual departure is from the Python-centric, pipeline-based agent design (AST-based localization, code graphs) toward an LM-first, interaction-focused paradigm, motivated by the observation that rigid Python-specific tooling breaks entirely on JavaScript repositories.

## Why It Matters / Open Questions

The benchmark reveals a stark generalization gap: systems achieving 43% on SWE-bench Lite drop to 12% on SWE-bench M, exposing that current agent systems are overfit to Python and text-only inputs. The finding that a simple LM-first framework (SWE-agent) substantially outperforms elaborate pipeline-based systems (Agentless, AutoCodeRover) on the new domain challenges the field's assumption that hand-engineered localization modules are necessary, suggesting future agent design should prioritize flexible, language-agnostic interaction over fixed procedural workflows. Open questions include whether the gap will narrow as multimodal LMs improve, how to build truly language-agnostic code analysis tooling, and whether visual testing (pixel-level comparison) can be automated at scale for broader benchmark coverage.
