## Problem

Existing LLM research in software engineering overwhelmingly targets early SDLC stages (code generation, testing, debugging), leaving the post-deployment phase—where on-call engineers must diagnose live failures—largely unexplored. No public benchmark exists to evaluate whether LLMs can perform root cause analysis over the massive, heterogeneous telemetry data (metrics, traces, logs) that real-world distributed systems produce, making it impossible to measure progress or identify specific failure modes in LLM-based RCA.

## Input / Output

Each task instance pairs a natural language query (specifying a 30-minute time window, the target system, and the number of failures) with the full telemetry corpus for that system—metrics as CSV time series, traces as hierarchical span graphs, and logs as semi-structured text—totaling ~20 GB per case. The model must output a structured JSON containing a subset of three root cause elements (originating component, start time in '%Y-%m-%d %H:%M:%S' format, and failure reason), with seven task types covering all non-empty combinations. All candidate components and reasons are provided in the prompt to eliminate textual-variation ambiguity during evaluation.

## Method

The paper contributes two main artifacts. First, OpenRCA, a benchmark of 335 curated failure cases from three real-world systems (Telecom, Bank, Market) built via a four-stage pipeline: system selection from AIOps Challenge data, downsampling for balance, manual calibration by three SREs who verified each label against telemetry anomalies, and GPT-4-synthesized natural language queries covering seven goal-driven task types. Second, RCA-agent, a multi-agent system that avoids feeding raw telemetry into the LLM context by having a Controller agent (which follows a fixed diagnostic workflow: anomaly detection → fault identification → root cause localization, in metric → trace → log order) iteratively instruct an Executor agent to synthesize and execute Python code in a stateful IPython kernel. This program-synthesis approach keeps the LLM focused on reasoning over execution results rather than parsing 68 GB of data, enabling scalability while revealing that model error-tolerance during code execution becomes the new bottleneck.

## Results

On the OpenRCA benchmark (335 failure cases, 68.5 GB telemetry), the best-performing model Claude 3.5 Sonnet achieves only 11.34% correct accuracy using the RCA-agent method, with 17.31% partial accuracy. Under oracle sampling (which reduces KPIs by 95% using ground-truth information), the best result is GPT-4o at 6.27% correct accuracy. Under balanced sampling, Gemini 1.5 Pro leads at 6.27% correct accuracy. No model achieves any correct answer on Hard tasks (requiring all three root cause elements: component, time, and reason), and accuracy drops by at least half when moving from 1-element to 2-element tasks.

## Baselines & Comparisons

The paper evaluates six LLMs (three proprietary: Claude 3.5, GPT-4o, Gemini 1.5 Pro; three open-source: Mistral Large 2, Command R+, Llama 3.1) across three methods (balanced sampling, oracle sampling, RCA-agent). Proprietary models consistently outperform open-source models across all methods; for example, Claude 3.5 achieves 11.34% correct with RCA-agent versus Llama 3.1's 3.28%. RCA-agent outperforms both sampling strategies for Claude (11.34% vs. 5.37% oracle) and GPT-4o (8.96% vs. 6.27%), confirming that code-based data processing is more effective than feeding sampled telemetry directly into context. Oracle sampling outperforms balanced sampling across all models, as expected since it uses ground-truth KPI selection. A notable finding is that Gemini 1.5 Pro, the best sampling-based model (6.27% balanced), performs worst as an agent (2.69%), with a 68.4% accuracy drop on failed-execution cases, revealing that agent-based methods impose additional error-tolerance requirements beyond raw reasoning ability.

## Relation to Prior Work

This paper carves new ground at the intersection of LLMs and post-deployment software engineering, a phase largely overlooked by prior LLM-for-SE work (MetaGPT, SWE-agent, OpenDevin) that focuses on code generation and debugging. It departs from learning-based RCA methods (causal discovery, dependency graph analysis) by treating LLMs as general-purpose reasoners over heterogeneous telemetry rather than training specialized models. The RCA-agent builds on the code-first multi-agent paradigm (TaskWeaver, UFO) but is the first to apply program synthesis and execution as the primary mechanism for handling massive telemetry in an RCA setting, avoiding the context-window bottleneck of sampling-based approaches. The goal-driven task formulation (7 combinations of 3 root-cause elements) generalizes prior single-goal RCA benchmarks (Nezha, Eadro, MicroRank) into a unified evaluation framework.

## Why It Matters / Open Questions

OpenRCA fills a critical gap by providing the first open, real-world benchmark for evaluating LLMs on post-deployment root cause analysis, a task that costs service providers billions in incident response. The extremely low best-case accuracy (11.34%) and complete failure on 3-element tasks reveal a substantial capability gap that will anchor future research in AI-driven software reliability. The finding that CoT prompting actually degrades performance and that agent-based approaches impose an additional error-tolerance requirement (Gemini's 68.4% accuracy drop) challenges straightforward assumptions about how to deploy LLMs in operational settings. Open questions include whether architectural changes (longer context, better error recovery, specialized training) can close the gap, and whether the benchmark generalizes beyond distributed microservice architectures.
