## Problem

Language models are trained to autoregressively generate entire programs in a single pass, but software engineers write code by iteratively editing existing programs. Sequential edit data is even scarcer than instruction data for code synthesis, leaving LMs without a reliable trade-off between generation quality and test-time compute—outputs degrade in quality with length and exhibit limited diversity across samples, particularly for smaller models.

## Input / Output

At inference, the model receives a natural language instruction and produces a sequence of Unix-style insertion-only diffs interleaved with special <|diff|> tokens, which are then resolved into an executable Python program by applying each diff's line insertions to the growing file. For data generation, LintSeq takes a complete source code file and decomposes it into s synthetic edit sequences (s=5 in experiments), where each edit consists solely of line insertions whose content reflects the syntactic dependencies identified by pylint. The training format is instruction + concatenated edit-sequence strings, with instruction-conditioned cross-entropy loss computed over the full sequence.

## Method

LintSeq is a parameter-free, CPU-only synthetic data generation algorithm with two phases: (1) a backward sampling phase that starts from the full program and iteratively deletes a uniformly random line, runs pylint, and removes all lines whose deletion would introduce new linter errors, continuing until the file is empty; and (2) a forward edit computation phase that reverses the resulting sequence of intermediate program states and applies the Unix diff operator between consecutive states to yield insertion-only edit sequences. The linter ensures each edit chunk reflects genuine syntactic and semantic dependencies in the source code rather than arbitrary line groupings. Models are trained via teacher-forced supervised fine-tuning on these edit sequences, and at test time they generate code by iteratively predicting insertion edits. Ablating the linter (replacing it with fully random line sampling, 'RandSeq') reduces HumanEval pass@1 by ~30% and MBPP pass@1 by ~25–28%, confirming that linter-guided structure is essential. The approach is validated across TinyCodeLM (150M/400M), Gemma 2 (2.6B), Phi-3 (3.8B/14B), and Llama 3.1 (8B), showing consistent gains in pass@1 and improved test-time scaling (pass@k vs. total FLOPs) compared to standard instruction fine-tuning.

## Results

On HumanEval, TinyCodeLM-LintSeqInstruct (150M) achieves 12.8% pass@1, a 41% relative improvement over its baseline (9.1%), and matches or exceeds several larger models including CodeT5+ (220M, 12.0%) and Codegen-Mono (350M, 12.8%). On MBPP(+), the 400M LintSeq variant reaches 19.4% pass@1 (25% improvement over baseline 15.5%) and 29.9% pass@10. Across larger models (Gemma 2 2.6B, Phi-3 3.8B/14B, Llama 3.1 8B), LintSeq fine-tuning yields average absolute gains of +2.3 (HumanEval), +4.3 (MBPP), +3.1 (DS-1000), and +1.1 (BigCodeBench) in pass@1 over standard instruction tuning, with the gap widening substantially at higher pass@k values.

## Baselines & Comparisons

The 150M TinyCodeLM-LintSeqInstruct (12.8% HumanEval pass@1) outperforms AlphaCode 89M (4.3%), Codex 85M (8.2%), SmolLM-Instruct 135M (7.7%), and CodeT5+ 220M (12.0%), while matching Codegen-Mono 350M (12.8%) and approaching Codex 300M (13.2%)—all with fewer parameters. The 400M LintSeq variant (13.4% pass@1) surpasses AlphaCode 302M (11.6%) and Codex 300M (13.2%) on HumanEval, and achieves 19.4% MBPP(+) pass@1, exceeding SmolLM-Instruct 360M (19.4%) and Codegen-Mono 350M (9.4%). On the larger-model comparisons (Gemma 2, Phi-3, Llama 3.1), LintSeq consistently wins at higher pass@k: for example, Phi-3-Mini-LintSeqInstruct reaches 87.3% HumanEval pass@50 vs. 62.2% for the baseline, and Llama-3.1-LintSeqInstruct achieves 82.7% vs. 64.2%. The one exception is BigCodeBench Instruct greedy pass@1, where Llama-3.1-LintSeqInstruct (20.53) slightly trails the baseline (21.46), though all other models show gains. Ablating the linter (RandSeq) degrades HumanEval pass@1 by ~30% and MBPP pass@1 by ~25–28%, confirming that linter-guided edit structure is essential for the observed improvements.

## Relation to Prior Work

This paper repurposes the Unix diff operator and linter-based static analysis to create a new training data representation for code synthesis, drawing conceptual inspiration from discrete diffusion methods for text generation (Li et al., 2022a) where decoding is non-autoregressive. It departs from prior edit-generation work (Yin et al., 2018; Gu et al., 2019; Guo et al., 2021) and commit-based instruction tuning (Muennighoff et al., 2023; Cassano et al., 2023) by training models to *synthesize* programs as sequences of insertion-only edits rather than editing existing code in response to prompts or error messages. Unlike Self-Instruct-style synthetic data generation, LintSeq requires no LLM for data creation—only a linter and the diff operator—making it parameter-free and CPU-only. The test-time scaling analysis connects to the broader line of work on inference-time compute (Brown et al., 2024; Snell et al., 2024) by showing that the edit-sequence reparameterization improves the pass@k vs. FLOPs trade-off.

## Why It Matters / Open Questions

The finding that a simple, parameter-free data reparameterization (linter-guided backward deletion + forward diff) consistently improves both pass@1 quality and test-time scaling across six model families from 150M to 14B parameters suggests that the current single-pass autoregressive code synthesis paradigm may be suboptimal for smaller models, and that the data-level structure of training examples matters as much as model architecture. The linter ablation (30% degradation) and the counterintuitive result that LintSeq models produce *more* syntactic errors yet higher pass@1 indicate the gains come from improved logical diversity rather than surface correctness. Key limitations include restriction to insertion-only edits (no deletion capability), Python-only evaluation, and instruction fine-tuning scale rather than pretraining; open questions include whether LintSeq can be applied at pretraining scale (e.g., on The Stack), whether combining it with RL or search in edit space yields further gains, and whether the approach transfers to other languages with appropriate linters.
