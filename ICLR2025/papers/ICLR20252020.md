## Problem

Running large Mixture-of-Experts (MoE) LLMs in resource-constrained environments is challenging because GPU memory cannot hold all model parameters, yet existing CPU-GPU systems either incur heavy PCIe transfer overhead (offloading approaches) or ignore the fundamentally different batching behaviors of CPUs and GPUs (CPU-based frameworks like llama.cpp). No prior system dynamically orchestrates expert execution across CPU and GPU to achieve good performance simultaneously across single-batch inference, long prefill, and beam search workloads.

## Input / Output

Fiddler takes text prompt tokens (up to 4096 tokens for long prefill) and produces generated text tokens, operating on 16-bit MoE models (e.g., Mixtral-8x7B with 47B parameters) that exceed available GPU memory. The model is partitioned at initialization: non-expert layers and a popularity-ranked subset of expert layers reside in GPU memory, while remaining expert weights stay in CPU memory. At runtime, the gating network determines which experts each token activates, and the system handles variable batch sizes ranging from single-token decoding to multi-thousand-token prefill or beam search with widths up to 16.

## Method

Fiddler's core mechanism is a per-expert, per-layer execution strategy that exploits the observation that CPU computation latency scales linearly with input size while GPU latency remains approximately constant (bounded by memory bandwidth for weight loading). At runtime, for each activated expert, Fiddler compares the predicted CPU latency against GPU latency plus the fixed weight-transfer latency, choosing CPU execution for small input sizes (where transferring activations is cheaper than transferring weights) and GPU execution for larger input sizes. During initialization, Fiddler places the most frequently-used experts on the GPU based on offline popularity profiling from calibration data, maximizing the probability that a needed expert is already resident. The system also employs a custom AVX512_BF16 kernel for CPU-side expert computation, which outperforms native PyTorch. This dynamic, input-size-aware scheduling allows Fiddler to integrate the strengths of both offloading-based and CPU-based approaches, achieving balanced performance across all evaluated scenarios.

## Results

On the Mixtral-8x7B model (16-bit) across two hardware environments, Fiddler achieves 1.26× average speedup over the best baseline (llama.cpp) in single-batch end-to-end inference (tokens/s), 1.30× speedup in long-prefill TTFT (outperforming DeepSpeed-MII by 1.07× and Mixtral-Offloading by 1.65×), and 11.57× speedup in beam-search inference over llama.cpp. The gains are consistent across both a 24 GB (Quadro RTX 6000, PCIe Gen3) and a 49 GB (RTX 6000 Ada, PCIe Gen4) GPU environment, with 56/256 and 125/256 experts resident on the GPU respectively.

## Baselines & Comparisons

Fiddler is compared against three baselines: DeepSpeed-MII (ZeRO-Infinity offloading), Mixtral-Offloading (expert-level CPU offloading with caching), and llama.cpp (CPU-based inference with partial GPU layer offload). In single-batch end-to-end inference, Fiddler beats llama.cpp by 1.26× on average across 15 input/output length configurations; the offloading-based baselines are not competitive here due to PCIe transfer overhead. In long-prefill TTFT, the offloading methods (DeepSpeed-MII and Mixtral-Offloading) outperform llama.cpp, but Fiddler still leads, beating DeepSpeed-MII by 1.07× and Mixtral-Offloading by 1.65×, because its dynamic CPU/GPU routing avoids unnecessary weight transfers when the input batch is small. In beam search (widths 4–16), Fiddler achieves a dramatic 11.57× speedup over llama.cpp, the only other baseline that supports beam search, because the larger effective batch size triggers Fiddler's GPU execution path while llama.cpp's fixed layer split leaves most computation on the CPU. Overall, Fiddler wins in all three scenarios, integrating the strengths of both offloading-based and CPU-based approaches.

## Relation to Prior Work

Fiddler synthesizes two previously separate lines of work on resource-constrained LLM inference: offloading-based systems (DeepSpeed-MII, Mixtral-Offloading) that transfer expert weights from CPU to GPU on demand, and CPU-based frameworks (llama.cpp) that statically partition layers between devices. Rather than committing to one strategy, Fiddler introduces a dynamic per-expert decision that exploits the distinct batching behaviors of CPUs (linear latency growth with input size) and GPUs (near-constant latency), a distinction prior systems did not formally model. The expert-popularity-based GPU placement and the AVX512_BF16 CPU kernel are incremental optimizations layered on top of this core scheduling insight.

## Why It Matters / Open Questions

As MoE models grow to hundreds of billions of parameters, running them on a single consumer or workstation GPU becomes a practical necessity for privacy-sensitive and edge deployments, and Fiddler provides a principled way to do so without quantization or model modification. However, the evaluation is limited to a single model (Mixtral-8x7B) at 16-bit precision on two specific hardware configurations, leaving open how the approach generalizes to larger MoE models, multi-GPU setups, or quantized weights. The paper also notes orthogonality to compression techniques, suggesting future work could combine Fiddler's scheduling with quantization or sparsity for further gains.
