## Problem

Static taint analysis tools like CodeQL suffer from false negatives due to missing manually-crafted taint specifications for third-party APIs, and false positives due to lack of context-sensitive reasoning over detected dataflow paths. While LLMs have shown promise on code tasks, they cannot perform the complex whole-repository dataflow reasoning required for vulnerability detection. The paper asks whether LLMs can be systematically combined with static analysis to address both specification gaps and imprecision simultaneously.

## Input / Output

The method operates on whole Java repositories (averaging 300K SLOC, with 10 projects exceeding 1M SLOC) rather than individual methods, requiring the LLM to reason over project-level context including README files and JavaDoc. The output is not a binary vulnerability label but a set of concrete unsanitized dataflow paths from source to sink, each accompanied by a natural-language explanation of why the path is exploitable. Taint specifications are structured as 3-tuples (node type, API descriptor with package/class/method/signature/argument position, and role) that are directly translatable into CodeQL predicates.

## Method

IRIS is a four-stage neuro-symbolic pipeline: (1) CodeQL extracts all candidate external API calls and public internal function parameters from the project; (2) LLMs label these candidates as CWE-specific sources or sinks using few-shot prompting for external APIs and zero-shot prompting (augmented with project README and JavaDoc) for internal APIs; (3) the inferred specifications are converted into CodeQL predicates and a CWE-specific taint query is executed to enumerate unsanitized source-to-sink paths; (4) a contextual analysis stage encodes each detected path with ±5 lines of surrounding code into a structured prompt, asking the LLM to classify it as true or false positive with a JSON-formatted verdict and explanation. The key insight is that LLMs' pre-training exposure to library API usages enables them to infer relevant taint specifications on-the-fly per project, while static analysis provides the systematic inter-procedural dataflow tracking that LLMs alone cannot perform, and the contextual filtering step leverages path-sensitive code context to elicit more reliable reasoning than method-level classification.

## Results

On CWE-Bench-Java (120 vulnerabilities across 4 CWE classes in real-world Java projects), IRIS with GPT-4 detects 55 vulnerabilities (45.83%), more than double CodeQL's 27 (22.50%), while also reducing the average false discovery rate from 90.03% to 84.82% and improving average F1 from 0.076 to 0.177. Smaller open-source LLMs also substantially outperform CodeQL: DeepSeekCoder 7B detects 52 and Llama-3 70B detects 54. IRIS with GPT-4 additionally discovers 4 previously unknown vulnerabilities in the latest versions of 30 Java projects that CodeQL alone cannot find.

## Baselines & Comparisons

IRIS with GPT-4 decisively outperforms CodeQL, the strongest baseline, detecting 55 vs. 27 vulnerabilities (+103.7%) while simultaneously reducing the average false discovery rate by 5.21 percentage points (84.82% vs. 90.03%) and more than doubling the average F1 score (0.177 vs. 0.076). The other static analysis baselines are far weaker: Snyk detects only 23 vulnerabilities, SpotBugs detects 4, and Facebook Infer detects 0 across all four CWE classes. Per-CWE, IRIS's gains are most dramatic on CWE-94 (Code Injection), where CodeQL detects 0 out of 21 vulnerabilities while IRIS+GPT-4 detects 8, and on CWE-22 (Path Traversal), where IRIS+GPT-4 detects 31 vs. CodeQL's 22. The one exception is CWE-78 (OS Command Injection), where all methods struggle (IRIS+GPT-4 detects only 3 of 13), attributed to complex gadget-chain patterns that are inherently difficult for static taint analysis.

## Relation to Prior Work

IRIS builds on CodeQL's static taint analysis engine but departs fundamentally from prior specification inference approaches (MERLIN, Seldon, InspectJS) that required expensive analysis of third-party library code or probabilistic modeling. Instead of mining specifications from library internals, IRIS leverages LLMs' pre-trained knowledge of API semantics to infer taint specifications on-the-fly per project, and introduces a novel contextual analysis stage where LLMs triage static analysis alerts using code-path and natural-language context. This positions IRIS at the intersection of neuro-symbolic programming and program analysis, extending prior work showing LLMs are effective at method-level tasks but fail at whole-repository reasoning by offloading the structural dataflow tracing to the symbolic engine while using LLMs for the semantic judgments that static tools lack.

## Why It Matters / Open Questions

The paper addresses two persistent, well-documented pain points in practical static analysis—missing third-party API specifications and high false-positive rates—by showing that LLMs can fill both gaps without requiring human-crafted specifications. The CWE-Bench-Java dataset (120 manually validated vulnerabilities in real-world, compilable Java projects averaging 300K SLOC) is a significant practical contribution that fills a gap no existing dataset addresses. Key limitations remain: the approach is Java-only, incurs substantial LLM API costs, still misses over half of vulnerabilities (45.83% detection rate), and cannot handle vulnerabilities not modelable as simple taint dataflows (e.g., side-effect-mediated flows, gadget chains). Open questions include whether the neuro-symbolic pattern generalizes to other languages, whether tighter LLM-analyzer integration can close the remaining detection gap, and how to reduce the cost of per-project specification inference.
