## Problem

Current LLM-based software agents follow linear, sequential processes that prevent backtracking and exploration of alternative solutions, causing them to become trapped in repetitive patterns on complex, long-horizon tasks. Software engineering is inherently non-linear and iterative—engineers explore multiple approaches, backtrack, and refine strategies based on feedback—yet existing agents lack mechanisms to reconsider their course when initial approaches prove ineffective.
![Teaser figure](../imgs/ICLR20252322/cropped_page3_idx0.webp)

## Input / Output

The system takes a repository codebase and a GitHub issue description as input, operating within a git-like commit tree where each state references a specific commit and the agent can revert to earlier versions. The agent works with file context organized into 'spans' (sections, classes, functions) to manage prompt size, and can execute any pre-existing tests in the repository at its discretion, though the specific fail-to-pass tests required to resolve the instance are not revealed. The output is a code patch (git diff) that fixes the issue, selected from up to five candidate solutions generated by the search process.

## Method

SWE-Search is a multi-agent framework built on the moatless-tools base agent, integrating a modified Monte Carlo Tree Search with three specialized components. The Action Agent operates in a flexible state space where the Plan state can transition to any other state type (unlike the rigid Search→Identify→Plan→Edit sequence of the baseline), enabling dynamic backtracking. The Value Agent is an LLM-based hybrid value function that outputs both a numerical utility score (−100 to 100) and a qualitative natural-language explanation, which serves as hindsight feedback to guide re-expansion from parent nodes. The MCTS selection uses a modified UCT criterion with an early-depth bonus (αe^{−β(d−1)}) to encourage wide exploration and a late-depth penalty (−γ√d) to promote convergence, plus a heuristic rule to abandon nodes with consecutive low rewards. Finally, a Discriminator Agent conducts a structured multi-agent debate (5 agents, 3 rounds) among up to five candidate solutions to select the final patch, improving selection accuracy from 73% (value function alone) to 84%.

## Results

On SWE-bench Lite (300 instances), SWE-Search achieves a mean 23% relative improvement in resolve rate (Pass@1) over the Moatless-Adapted baseline across five models. The best absolute performance is 31.0% resolve rate with GPT-4o, while the largest relative gain (+27%) comes from Qwen-2.5-72B-Instruct (18.0% → 24.7%). Pass@5 scores range from 22.3% (GPT-4o-mini, Llama-3.1-70B) to 34.0% (GPT-4o), indicating the search process surfaces additional correct solutions beyond the top-1 pick.

## Baselines & Comparisons

SWE-Search is compared against two baselines built on the moatless-tools framework: the original Moatless-v0.0.2 (rigid state transitions, no test execution) and Moatless-Adapted (adds tree structure, test execution, and flexible Plan→any-state transitions). SWE-Search wins on every model against Moatless-Adapted, with relative gains ranging from +17% (GPT-4o: 25.7→31.0) to +27% (Qwen-2.5-72B: 18.0→24.7). Against the original Moatless-v0.0.2, SWE-Search with GPT-4o improves from 24.3% to 31.0% (+6.7 absolute points). Notably, SWE-Search with Qwen-2.5-72B-Instruct (24.7%) exceeds the original Moatless-v0.0.2 with GPT-4o (24.3%), showing that the search framework enables smaller open-source models to approach or match closed-source performance. The Moatless-Adapted baseline itself only marginally improves over Moatless-v0.0.2 (+1.4% for GPT-4o), confirming that the primary gains come from the MCTS search and value-feedback loop rather than the state-flexibility modifications alone.

## Relation to Prior Work

SWE-Search extends the moatless-tools agent framework by wrapping it in a Monte Carlo Tree Search loop with a modified UCT selection criterion inspired by AlphaZero, deliberately avoiding LLM-based node selection in favor of heuristic-driven exploration. The Value Agent's hybrid output (numerical reward plus natural-language explanation) and the hindsight feedback mechanism for iterative re-expansion depart from prior MCTS-for-LLM work (e.g., Koh et al., 2024; Zhang et al., 2024b), which typically uses language models for both selection and evaluation. The Discriminator Agent's multi-agent debate for final solution selection draws on recent persuasive-debate frameworks (Du et al., 2023; Khan et al., 2024) but applies them to code patch comparison rather than factual QA.

## Why It Matters / Open Questions

The paper demonstrates that inference-time compute scaling via deeper search can close the gap between smaller open-source models and GPT-4o on repository-level bug fixing, offering a practical pathway to improve software agents without retraining. However, the computational cost is prohibitive in practice (e.g., ~$576 per instance for GPT-4o vs. ~$41 for the baseline), and the value function's 73% accuracy in identifying the correct solution limits the ceiling of the approach. Open questions include whether the search depth can be made more adaptive per-instance, whether the multi-agent debate overhead is justified over simpler selection heuristics, and how the framework generalizes beyond SWE-bench-style bug fixes to broader software engineering tasks like feature development or refactoring.
