## Problem

Current grammar-guided LLM generation tools enforce only syntactic constraints via context-free grammars but cannot detect or correct semantic violations (e.g., invalid column names in SQL, leaked private data, incorrect field types in Vega-Lite). When a semantic error occurs, users must restart generation from scratch because existing tools lack the ability to pause, inspect, or backtrack through the output at a meaningful structural granularity. The token-level abstraction provided by LLM libraries is not tied to the syntax of the target language, making precise navigation to the source of a violation impractical.

## Input / Output

The method takes a text prompt, a context-free grammar specified in Lark EBNF (defining terminals and non-terminals for the target language), and an autoregressive LLM. The user program controls generation through three API calls—forward(stop_symbol, count), backward(symbol, count), and view(symbol)—that operate on grammar symbols rather than raw tokens. The output is a grammar-constrained structured text (SQL query, natural language passage, or Vega-Lite JSON) that satisfies both the syntactic grammar and user-defined semantic predicates checked between forward/backward steps.

## Method

ITERGEN's core mechanism is a dynamically maintained symbol position map that maps each occurrence of a grammar symbol to its character span in the partially generated output, updated incrementally via an LR parser's reduce operations. This map bridges the misalignment between LLM vocabulary tokens and grammar-level lexical tokens, enabling precise forward generation (stop after n occurrences of a symbol) and backward navigation (remove the last n occurrences of a symbol). A decoding trace stored as a token tree, combined with a recurrence penalty γ that multiplicatively dampens probabilities of previously backtracked tokens, encourages the model to explore alternative paths during iterative resampling. The LLM's key-value cache is cropped coherently with backward calls to avoid expensive re-prefilling. The framework builds on SYNCODE's incremental parser-guided constrained decoding for syntax enforcement, extending it with the bidirectional grammar-symbol navigation that enables targeted semantic correction without regenerating valid portions of the output.

## Results

On the Spider text-to-SQL benchmark, ITERGEN achieves 41.63% average overall execution accuracy and 75.84% execution success rate across nine LLMs, compared to 28.90%/50.28% for unconstrained STANDARD generation and 35.22%/63.72% for SYNCODE. On the DecodingTrust privacy benchmark (Enron emails), ITERGEN eliminates all privacy leaks (0 out of 100 prompts), whereas STANDARD generation leaks 45–67 emails depending on the model. On the NLV Corpus for Vega-Lite specification generation, ITERGEN improves exact-match accuracy by 17.8% over SYNCODE (e.g., 30.47% vs. 24.69% with Llama-3-8B).

## Baselines & Comparisons

ITERGEN is compared against two baselines: STANDARD (unconstrained LLM generation) and SYNCODE (state-of-the-art grammar-guided generation). On the Spider SQL benchmark, ITERGEN outperforms both baselines across all nine models in overall execution accuracy and execution success rate, with the largest gains observed on smaller and instruct-tuned models (e.g., Qwen2.5-1.5B-Instruct: 50.7% vs. 32.7% for SYNCODE and 0.0% for STANDARD). On the DecodingTrust privacy benchmark, ITERGEN achieves 0 leaked emails across all models, while STANDARD leaks 45–67 out of 100 prompts; the overhead is modest (4–7 extra tokens on average and ~0.1–0.2s additional time). On the NLV Vega-Lite benchmark, ITERGEN surpasses SYNCODE in both exact-match accuracy (e.g., 30.47% vs. 24.69% for Llama-3-8B) and execution success (92.51% vs. 89.56%), with a small time increase (~0.8s). ITERGEN's advantage is most pronounced when the base model is weaker or when semantic constraints (valid table/column names, field types) are critical, since SYNCODE enforces only syntactic correctness.

## Relation to Prior Work

ITERGEN builds directly on SYNCODE's incremental LR-parser infrastructure for grammar-constrained decoding, extending the line of grammar-guided generation work (GCD, OUTLINES, DOMINO, SYNCODE, AICI) that ensures syntactic correctness. The key conceptual departure is introducing grammar symbols (terminals and non-terminals) as first-class navigational abstractions, enabling bidirectional iteration (forward and backward) through the generation process—something no prior grammar-guided tool supported. Unlike GUIDANCE's stop_at (which halts at regex patterns but cannot backtrack) or SYNCHROMESH's token-level rejection sampling, ITERGEN operates at the grammar-symbol level with a symbol position map, allowing users to programmatically inspect, validate, and selectively resample specific structural units of the output.

## Why It Matters / Open Questions

ITERGEN addresses a practical gap in structured LLM generation: the inability to correct semantic errors (invalid column names, privacy leaks, wrong field types) without regenerating the entire output from scratch. The 100% privacy leak elimination and consistent 17–18% accuracy gains over SYNCODE across SQL and Vega-Lite demonstrate that mid-generation backtracking is both feasible and effective. Key limitations include single-sequence-only operation (no batch backtracking), a recurrence penalty heuristic that can skew the token distribution at the first backtracked position, and dependence on LR-parseable grammars. Open questions include whether the approach scales to deeply nested or ambiguous grammars, how it interacts with larger models where semantic errors are rarer, and whether the symbol-position-map overhead becomes prohibitive for very long generations.
