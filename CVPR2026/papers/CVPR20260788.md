## Problem

State-of-the-art MLLMs exhibit severe brittleness to trivial image corruptions such as rotation and flipping, with performance dropping up to 80% on simple orientation changes, yet existing 'thinking with images' methods rely on narrow, hand-specified tool registries (mostly crop/zoom) that offer only marginal gains and do not scale to new tools or multi-turn, multi-tool composition. The paper argues that current benchmarks fail to create scenarios where tools are genuinely necessary, and that fixed tool-name/argument interfaces are too rigid to support flexible, real-world visual reasoning.

## Input / Output

The model receives an RGB image that may have been rotated (90°/180°/270°) or flipped (horizontal/vertical) along with a text question, and produces a multi-turn dialogue of Python code snippets that invoke arbitrary image operations (rotation, cropping, contrast adjustment, edge detection, etc.), interleaved with reasoning traces and a final text answer. Unlike fixed-API tool calling, the model writes executable code in a controlled runtime, receives updated images or error messages as tool returns, and can revise its code across turns. During training, only assistant-side tokens (reasoning and code) contribute to the loss; user prompts and tool-return outputs are masked out.

## Method

CodeVision treats code generation as a universal tool interface, eliminating fixed tool registries so the model can invoke any image operation from an effectively unbounded library. Training proceeds in two stages: (1) a cold-start SFT phase on ~6K GPT-5-generated multi-turn trajectories covering single-tool, multi-tool, multi-crop, error-handling, and no-tool scenarios, with metadata-conditioned image transformations making tool use necessary; and (2) RL via GRPO on ~40K difficulty-filtered samples using a dense multi-component reward that combines terminal accuracy, a strategy reward (must-use tool bonuses with IoU-based crop scoring and rollout-comparison-based suggested-tool discovery), and constraint penalties (turn-limit, poor-reasoning, and inappropriate-tool-use) to prevent reward hacking. The code-as-tool design yields three emergent capabilities: the model calls tools never seen in training data, chains multiple operations within a single execution, and recovers from runtime errors by reading error logs and revising code.

## Results

On the new multi-tool benchmark MVToolBench, CodeVision-7B achieves 60.1, nearly doubling the next-best model Gemini2.5-Pro (32.6), and CodeVision-32B reaches 65.4. On orientation-robustness benchmarks (Table 1), CodeVision models show dramatic improvements over their base models: CodeVision-7B improves OCRBench average from 56.0 to 73.4 (+17.4) and CodeVision-32B from 55.7 to 79.5 (+23.8). On single-tool cropping benchmarks (V*, HRBench), CodeVision-32B achieves 86.2/84.3/76.1, matching or exceeding the much larger Qwen3-VL-235B-Thinking (85.9/84.3/76.6) while using 7× fewer parameters.

## Baselines & Comparisons

Against its direct base models, CodeVision delivers the largest gains on MVToolBench: CodeVision-7B scores 60.1 vs. Qwen2.5-VL-7B's 18.1 (+42.0), CodeVision-8B scores 62.7 vs. Qwen3-VL-8B-Thinking's 19.7 (+43.0), and CodeVision-32B scores 65.4 vs. Qwen3-VL-32B-Thinking's 28.6 (+36.8). Against Gemini2.5-Pro, CodeVision-32B wins on V* (86.2 vs. 83.8) and MVToolBench (65.4 vs. 32.6) but loses on HRBench4k (84.3 vs. 85.0) and HRBench8k (76.1 vs. 85.1), indicating that Gemini retains an edge on pure high-resolution cropping. Against GPT-4o, CodeVision-32B dominates across all four benchmarks (86.2 vs. 67.9 on V*, 65.4 vs. 8.5 on MVToolBench). Against Thyme, the closest prior tool-use method, CodeVision-32B leads on every benchmark, with the gap most pronounced on MVToolBench (65.4 vs. 24.2), confirming that multi-tool composition is where the code-as-tool paradigm provides the clearest advantage.

## Relation to Prior Work

This paper extends the 'thinking with images' paradigm introduced by OpenAI o3, where MLLMs interactively manipulate visual inputs via tools. Prior follow-ups (GRIT, Mini-o3, OpenThinkImg, Thyme) largely focus on a single crop/zoom tool with hand-specified API interfaces, and evaluate on benchmarks where tool use yields only marginal gains. CodeVision departs by replacing fixed tool registries with a 'code-as-tool' interface—the model writes Python to invoke any image operation—inspired by o3's code-execution capability, and by shifting the evaluation to scenarios (orientation correction, multi-tool composition) where tools are genuinely necessary rather than optional.

## Why It Matters / Open Questions

The finding that even frontier models (GPT-5, Gemini 2.5 Pro) suffer up to 80% accuracy drops from simple rotation/flip is a concrete, well-evidenced vulnerability that motivates robust tool-augmented reasoning beyond the crop-centric framing of prior work. The code-as-tool paradigm and the observed emergent tool use (model discovering and chaining operations never seen in training) suggest a path toward scalable, open-ended visual manipulation, though it remains unclear whether this advantage persists as the set of required operations grows or whether a sufficiently rich fixed API would close the gap. Open questions include the computational overhead of runtime code execution at scale, generalization to truly novel image operations, and whether the dense process-reward design transfers to other tool-augmented domains.
