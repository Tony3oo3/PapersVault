## Problem

UI-to-Code generation has been extensively studied for web pages and mobile screens, but app widgets remain unexplored due to their unique challenges: they are compact, context-free micro-interfaces with dense iconography, embedded data visualizations, and strict spatial constraints, yet they lack accessible source code, layout metadata, or publicly available (image, code) pairs. This paper formalizes Widget2Code as a distinct task and shows that both specialized UI2Code methods and general-purpose MLLMs fail to produce reliable, visually faithful widget reconstructions.
![Teaser figure](../imgs/CVPR20263837/cropped_page0_idx1.webp)

## Input / Output

The method takes a single RGB widget image as input (no markup, bounding boxes, or structural annotations) and produces executable front-end code (HTML/CSS or React) that reconstructs the widget at its original dimensions. A key constraint is that the output must preserve the exact aspect ratio and size class of the input widget without content overflow or occlusion, which is enforced by an adaptive rendering module that iteratively adjusts layout dimensions using browser feedback. The intermediate representation is a compact, human-readable WidgetDSL rather than raw framework code, enabling deterministic compilation to multiple targets.

## Method

The framework operates at two levels. At the perceptual level, a Perceptual Agent decomposes the input into atomic components (icons, charts, text, buttons) and applies three auxiliary modules: a two-stage icon retrieval system over a 50k SVG library using SigLIP visual and textual embeddings (coarse visual filtering followed by caption-based re-ranking), reusable DSL-encoded component templates that the MLLM populates with input-specific data and style, and K-means color palette extraction to preserve the original color distribution. At the system level, WidgetFactory defines a framework-agnostic WidgetDSL and compiles it via a two-phase DSL→AST→target-code pipeline into HTML/CSS or React. An adaptive rendering module then performs feedback-guided binary search on the layout width, using a violation function that aggregates content overflow and boundary excess from the browser engine, to find the minimal width that satisfies the target aspect ratio without occlusion.

## Results

On the Widget2Code benchmark (1,000 test widgets), the proposed baseline (built on Qwen3-VL with the Perceptual Agent and WidgetFactory) achieves a perfect Geometry score, accurately reproducing input widget dimensions, while all other methods fail to match the original size even when explicitly prompted. Among generalized MLLMs, GPT-4o and Gemini 2.5-Pro lead on visual fidelity metrics (Layout, Style, Perceptual), outperforming specialized UI2Code methods such as ScreenCoder, DCGen, and Design2Code, which exhibit pronounced degradation on compact widget structures. The proposed method further improves over the best generalized MLLM baseline across Layout, Legibility, and Style metrics by integrating icon retrieval, reusable visualization templates, and color extraction, with the adaptive rendering module eliminating content overflow and occlusion.

## Baselines & Comparisons

The paper benchmarks 11 baselines across two groups. Generalized MLLMs (GPT-4o, Gemini 2.5-Pro, Seed1.6-Thinking, Qwen3-VL, Qwen3-VL-235B) consistently outperform all seven specialized UI2Code methods (ScreenCoder, UI-UG, DCGen, UICopilot, LatCoder, Design2Code, WebSightVLM-8B) on the widget test set, with GPT-4o and Gemini 2.5-Pro achieving the highest visual fidelity among the MLLM group. The specialized methods, optimized for web or mobile layouts, show pronounced degradation on compact, context-free widget structures, failing to reproduce input appearance in qualitative comparisons (Fig. 3). The proposed Widget2Code baseline (Qwen3-VL + Perceptual Agent + WidgetFactory) surpasses the best generalized MLLM (GPT-4o) on Layout, Legibility, and Style metrics by leveraging icon retrieval, reusable visualization templates, and K-means color extraction, while achieving a perfect Geometry score that no other method matches. All baselines, including the strongest MLLMs, still exhibit content overflow, structural misalignment, and color inconsistencies, which the proposed adaptive rendering module and constraint-guided DSL generation specifically address.

## Relation to Prior Work

This paper carves new ground by formalizing widget-to-code generation as a distinct task separate from the well-studied web-page and mobile-screen UI2Code literature. It repurposes retrieval-augmented generation (SigLIP-based icon retrieval), introduces a widget-specific domain-specific language (WidgetDSL) with a multi-target compiler, and adds an adaptive rendering loop—none of which appear in prior UI2Code pipelines. Conceptually, it sits at the intersection of MLLM-driven code generation and structured output control, but the widget-specific constraints (compactness, iconography density, absence of markup) motivate all architectural choices.

## Why It Matters / Open Questions

As the first systematic study of widget-to-code, this paper establishes a benchmark, evaluation protocol, and baseline infrastructure for a UI modality that is growing in importance (Apple/Android widgets) but has been entirely unaddressed. Key open questions remain: whether the approach generalizes to interactive or dynamic widgets, whether stronger fine-grained visual grounding can handle dense micro-visualizations (sparklines, pie charts), and whether the modest 1,000-sample test set is sufficient for robust conclusions. The single-model baseline (Qwen3-VL via API) and the absence of trained/fine-tuned comparisons limit the generality of the empirical claims.
