## Problem

LLM-based agents currently interact with web services through static API endpoints designed for single-shot queries, forcing procedural workflows with loops, conditionals, and retries into brittle sequences of endpoint calls interleaved with multi-round reasoning. This stepwise interface inflates network round trips, causes systematic over- and under-fetching, and makes recovery fragile because partial failures trigger cascading retries that can duplicate state-modifying operations and corrupt service state.

## Input / Output

The agent receives a natural-language task intent and MCP-style tool endpoint specifications, then synthesizes a compact Rust tool program (median 70 non-empty lines, ~4 endpoint calls) constrained to a surface of structured control flow, a unified CALL(e,a,eff) stub, and explicit READ/WRITE effect annotations at each call site. The program is compiled to a Wasm module and executed server-side, producing workflow results and updated service state; on failure, the system falls back to stepwise endpoint calling with diagnostics.

## Method

TOOLPRO represents tool intent as an executable, effect-typed tool program and operationalizes it through a synthesize-project-compile-execute pipeline with three key mechanisms. First, constraint-guided construction combines lightweight client-side structural checks with server-side projection into a constrained Wasm surface, then uses compiler diagnostics and runtime traces for bounded in-place repair within a fixed attempt budget. Second, effect-aware replay enforces exactly-once semantics for WRITE calls by maintaining per-intent-instance history (H) and working (W) logs, matching each re-execution's WRITE to the earliest unused committed entry and replaying cached outcomes rather than re-emitting calls. Third, a profile-driven consolidation policy uses moving averages of RTT, per-step decision time, and build cost to predict whether program execution saves net latency (ΔT = (N−1)(T_RTT + T_DEC) − T_BUILD) versus stepwise calling, selecting the mode per instance and falling back to stepwise calling when the build cost is not amortized.

## Results

TOOLPRO reduces end-to-end latency by up to 53.4% and client-side traffic by up to 96.1% compared to stepwise MCP calling. On the complex supplemental benchmarks (cbench1–cbench3), TOOLPRO cuts average latency from 30.16 s to 17.91 s (40.6%) and improves task accuracy from 0.60 to 0.93; on the cross-service benchmark (cbench4), latency drops from 52.68 s to 24.54 s (53.4%) and accuracy rises from 0.20 to 0.80. A 15-run no-replay ablation confirms that disabling effect-aware replay increases latency by 19.7% and triggers 3/15 fallbacks, validating the retry-safety mechanism.

## Baselines & Comparisons

The primary baseline is MWS (stepwise MCP Web Service), where the agent replans the next endpoint call at every step, incurring N round trips and N LLM decision rounds. TOOLPRO consistently outperforms MWS across all workflows and network conditions, with the gap widening as RTT and workflow length increase (e.g., at 2000 ms RTT, TOOLPRO-prog achieves 17.51 s vs. 30.50 s for stepwise). The TOOLPRO-step variant (intent-structured guidance without consolidation) improves over MWS by reducing per-step decision overhead but still pays N rounds, while TOOLPRO-prog (always program mode) dominates at high RTT but pays a one-time build cost that is unprofitable at low RTT (1–100 ms). The full TOOLPRO policy with profile-driven consolidation tracks the empirically better mode across the RTT sweep, staying within 0.14 s of the best variant at every tested latency. On the supplemental realistic benchmarks, TOOLPRO also substantially improves task accuracy over MWS (0.60→0.93 on cbench1–3; 0.20→0.80 on cbench4), indicating that consolidating control flow into a single program reduces cascading errors from partial failures.

## Relation to Prior Work

This paper departs from the dominant stepwise endpoint paradigm for agent tool use (REST, MCP-style APIs) by introducing tool programs as a first-class, effect-typed interface object. It is conceptually adjacent to ORFA (Wasm as a Turing-complete query language for web APIs) and CodeAct (executable code as agent action space), but distinguishes itself by targeting the agentic service boundary: the submitted program is an enforceable interface contract with explicit READ/WRITE effect annotations and retry-safe replay semantics, rather than an internal reasoning representation. The constrained-surface projection and bounded in-place repair pipeline draw on compiler-feedback-driven program synthesis, while the WebAssembly sandboxing substrate follows established Wasmtime-based isolation patterns. The profile-driven consolidation policy is a lightweight online decision rule rather than a learned policy, keeping the system practical without additional training.

## Why It Matters / Open Questions

The paper addresses a concrete and growing bottleneck in agentic web services: stepwise endpoint sequences scale poorly in latency, traffic, and failure recovery as workflows grow longer. The 53.4% latency and 96.1% traffic reductions, together with the accuracy improvement on complex workflows (0.20→0.80 on cbench4), suggest that the interface representation itself—not just the execution substrate—matters for both efficiency and correctness. Open questions include how the constrained surface generalizes to highly dynamic or cross-service workflows, whether the Rust/Wasm choice is optimal versus lighter DSLs or IRs, and how the system interacts with evolving MCP standards and multi-tenant service environments. The reliance on LLM coding capability (qwen3-coder-flash at 80% vs. 100% for stronger models) highlights that executability remains a model-dependent bottleneck.
