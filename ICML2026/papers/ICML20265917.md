## Problem

LLM-based code translation has achieved strong functional correctness but largely ignores runtime efficiency, with translated programs often running significantly slower than human-written equivalents. Prompt engineering strategies that emphasize efficiency (e.g., adding optimization instructions or post-hoc acceleration steps) consistently degrade correctness, creating an unresolved correctness–efficiency trade-off that existing training-based methods also fail to resolve.
![Teaser figure](../imgs/ICML20265917/cropped_page0_idx0.webp)

## Input / Output

The framework takes a source code snippet in one of five languages (C, C++, Go, Java, Python) and produces a single translated program in a target language. During inference, MpTranslator generates m=10 candidate translations in parallel, each conditioned on a distinct set of 0–3 in-context demonstrations sampled from a curated library; DiffSelector then performs n−1 pairwise comparisons to select the final output. Evaluation uses efficiency-critical test cases with explicit maximum runtime constraints derived from conservative baseline translations, executed via the Judge0 sandbox five times per sample.

## Method

SWIFTTRANS comprises two trained components. MpTranslator generates diverse candidates via parallel in-context learning, where each candidate is conditioned on a different random subset of demonstrations; it is trained with hierarchical guidance that links the number of demonstrations in context to an optimization level (0 = correctness-only, n = fully optimized), teaching the model to produce conservative-to-efficient translations depending on context richness. DiffSelector acts as a pairwise LLM-as-a-judge that explicitly highlights token-level differences between two candidates using unified diff format, then selects the best via a bubble-sort-inspired O(n) sequential comparison strategy rather than O(n²) all-pair evaluation. DiffSelector is trained with ordinal guidance using a bi-judge loss that enforces consistent quality judgments regardless of candidate order, reducing order sensitivity from 64.2% to 6.4%. Both components are fine-tuned on ~15k instances per language pair using full-parameter training on lightweight open-source LLMs (Qwen2.5-3B/7B, StarCoder-7B).

## Results

On the extended CodeNet, F2SBench, and SWIFTBENCH benchmarks (averaged over 5 languages × 3 benchmarks), SWIFTTRANS with Qwen2.5-7B achieves 90.2% Computational Accuracy (CA) and 292 ms average Execution Time (ET), outperforming F2STrans with Qwen2.5-7B (84.6% CA, 731 ms ET) by 5.6% CA and 439 ms ET. Even the 3B variant (86.9% CA, 339 ms ET) surpasses F2STrans-7B in both metrics. Against the strongest prompt-based baseline, GPT-5 with Correctness-Only prompting (86.4% CA, 528 ms ET), SWIFTTRANS-7B gains 3.8% CA and 236 ms ET while using a 7B open-source model instead of a proprietary one.

## Baselines & Comparisons

Against F2STrans (Zhang et al., ICML 2025), the primary training-based baseline, SWIFTTRANS wins decisively on both metrics: the 3B variant (86.9% CA, 339 ms ET) beats F2STrans-7B (84.6% CA, 731 ms ET) by 2.3% CA and 392 ms ET, and the 7B variant extends the gap to 5.6% CA and 439 ms ET. Against Qwen3-Next-80B prompt-based baselines, SWIFTTRANS-7B achieves 90.2% CA versus 73.3% for Correctness-Only prompting (a 16.9% gap) while also reducing ET from 776 ms to 292 ms; notably, the efficiency-oriented prompts (Cor.+Eff., Cor.→Eff.) on Qwen3-Next-80B drop CA to 68.6% and 59.3% respectively, confirming the correctness-efficiency trade-off that SWIFTTRANS avoids. Against GPT-5, SWIFTTRANS-7B (90.2% CA, 292 ms ET) surpasses GPT-5 Correctness-Only (86.4% CA, 528 ms ET) by 3.8% CA and 236 ms ET, and also outperforms GPT-5's best efficiency-oriented prompt (Cor.→Eff.: 62.7% CA, 399 ms ET) on both metrics. On real-world class-level and repository-level benchmarks (ClassEval-T, AlphaTrans, RepoTrans), SWIFTTRANS leads on ClassEval-T (28.4% vs. 25.7% for GPT-4o) and RepoTrans (7.3% vs. 4.0%), though GPT-4o edges ahead on AlphaTrans (29.1% vs. 27.5%) due to very long source programs (>5,000 tokens) where the 7B backbone is at a disadvantage.

## Relation to Prior Work

This paper extends the LLM-based code translation line (F2STrans, CoTran, prompt-based RAG/CoT) by explicitly targeting runtime efficiency alongside functional correctness, a dimension prior work largely ignores. Methodologically, it repurposes two established ideas—repeated sampling (Brown et al., 2024) and LLM-as-a-judge (Zheng et al., 2023)—into a generate-then-select pipeline, but introduces two novel training strategies: hierarchical guidance that links demonstration count to optimization level for the generator, and ordinal (bi-judge) guidance with explicit diff highlighting for the selector. The bubble-sort-inspired O(n) selection is a practical departure from the O(n²) all-pair comparison common in candidate selection literature.

## Why It Matters / Open Questions

The paper fills a genuine gap: runtime efficiency is an ISO/IEC 25010 quality criterion that code translation research has systematically neglected, and the finding that prompt engineering cannot resolve the correctness-efficiency trade-off (efficiency prompts consistently degrade correctness even for GPT-5) is a useful negative result for practitioners. SWIFTBENCH, with its intentionally inefficient source programs, provides a much-needed evaluation axis beyond pass@k correctness. Open questions include whether the framework scales to repository-level translation (where results are notably weaker), whether the hierarchical data construction pipeline generalizes to language pairs with very different paradigms (e.g., functional vs. imperative), and whether the 15k training instances per scenario are sufficient for broader language coverage.
