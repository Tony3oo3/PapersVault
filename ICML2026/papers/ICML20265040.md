## Problem

Existing MLLM-based UI-to-code generation methods focus almost exclusively on HTML/CSS, leaving multi-framework generation for React, Vue, and Angular underexplored. Naively switching the generation target by modifying prompts produces substantial compilation success gaps and highly framework-specific error modes, because multi-framework differences involve joint changes in language rules, component boundary conventions, and project scaffolding constraints that cannot be captured by prompt-level instructions alone.

## Input / Output

The method takes a single UI screenshot (RGB image) and a target framework label (React, Vue, Angular, or Vanilla) as input, and produces a complete, compilable front-end project in the target framework's engineering form (e.g., TSX components for React, SFC files for Vue, component.ts + component.html pairs for Angular). Internally, the screenshot is first processed by a UI element detector (UIED) and OCR to produce structured element and content tables, which then condition all downstream generation. The output is constrained to a permission window defined by a framework-specific file contract, restricting which files are writable and which engineering units each subtask must materialize.

## Method

MulFCoder decomposes UI-to-code generation into four cooperating agents: a Grounder that builds an ElementTable, ContentTable, and macro-layout partition from detected UI elements; a Planner that constructs a DOM-like hierarchical layout tree with geometric layout primitives, schedules tasks in a local-first-then-assemble order, and derives a three-part framework contract (policy invariants, permission window, and task-to-artifact binding); a Writer that generates code incrementally in FILE mode (structure-first, content-backfilling) or performs minimal repairs in PATCH mode; and a Judger that applies a four-stage gated pipeline (structural form → parse feasibility → dependency/scope consistency → contract compliance) without invoking full compilation. The key insight is collapsing multi-framework differences into an explicit, decidable rule space via the file-level contract, so that framework-specific engineering conventions are enforced as hard constraints rather than left to implicit model knowledge. A bounded repair budget with failure-signature tracking prevents deadlocks during iterative Judger–Writer repair loops.

## Results

On Design2Code, MulFCoder improves Compilation Success Rate (CSR) by ~10.2% on Angular, ~6.6% on Vue, and ~3.8% on React (averaged across five MLLM backbones), with the largest absolute gain being +0.13 CSR for LLaVA-v1.5-7B on Angular (0.65→0.78). On the more challenging DesignBench, gains are ~9.0% (Angular), ~8.2% (Vue), and ~6.2% (React). CLIP visual similarity shows consistent 3–7% relative improvements in the Vanilla setting, while under strict engineering frameworks (React/Vue/Angular) CLIP remains roughly stable or slightly regressed, reflecting an engineering trade-off where MulFCoder prioritizes compilation correctness over maximal visual fidelity.

## Baselines & Comparisons

The paper does not compare against other named multi-agent or UI-to-code methods; the sole baseline is direct prompting (prompt transfer), where the same MLLM backbone is simply asked to generate code in a target framework in one shot. MulFCoder consistently outperforms this baseline on CSR across all five backbones (Gemini-2.5-Pro, GPT-4o, Doubao-Seed-1.6, Qwen2.5-VL-7B, LLaVA-v1.5-7B), all four frameworks, and both datasets, with no regressions. The advantage scales with framework strictness: Angular sees the largest CSR gains (+0.06 to +0.13), followed by Vue (+0.04 to +0.11) and React (+0.01 to +0.09), while Vanilla CSR is already saturated at 1.00 for most backbones. Weaker backbones benefit disproportionately—LLaVA-v1.5-7B gains +0.13 CSR on Angular (DesignBench) versus +0.06 for Gemini-2.5-Pro—indicating that MulFCoder externalizes framework knowledge that smaller models lack. On CLIP, MulFCoder achieves small but consistent visual gains in Vanilla (+0.02 to +0.08) while remaining roughly neutral under strict engineering frameworks, confirming the stated engineering trade-off between compilation correctness and visual richness.

## Relation to Prior Work

This paper extends the MLLM-based UI-to-code generation line (Laurençon et al., 2024; Gui et al., 2025b,c; Wan et al., 2025) from single-target HTML/CSS output to multi-framework (React/Vue/Angular) generation, where prior work has been largely absent. Conceptually, it repurposes the multi-agent decomposition pattern seen in ScreenCoder (Jiang et al., 2025) and UI-CoPilot (Gui et al., 2025c) but introduces a key departure: a framework-conditioned file Contract and FastGate rule system that encodes engineering constraints (standalone components, SFC structure, TSX exports) as explicit, decidable checks rather than relying on prompt-level instructions. The Grounder's use of UIED + OCR for structured element extraction follows established CV pipelines (Wu et al., 2021; Nguyen & Csallner, 2015), while the Planner's geometric layout-primitive heuristics are a lightweight alternative to learned layout models.

## Why It Matters / Open Questions

The paper identifies and quantifies a practical gap: prompt-only framework transfer produces large, framework-specific compilation failures that no amount of prompt engineering resolves, making multi-framework UI-to-code generation unreliable in production. The observed 'engineering trade-off'—where fixing build errors forces simplification of complex UI components, capping visual fidelity—is an important and underappreciated limitation that future work must address. Angular remains the hardest case (CSR fix ratio drops to ~31% on DesignBench), suggesting that global project-level coherence (cross-file imports, module wiring) is still an open problem that local, task-scoped repair cannot fully solve. The backbone-agnostic design and the finding that weaker models benefit disproportionately suggest the constraint-externalization approach could be a practical complement to model scaling.
