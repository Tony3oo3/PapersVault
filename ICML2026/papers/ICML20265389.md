## Problem

Evaluating the quality of LLM-generated formal program specifications at scale remains an open problem. Existing pipelines either check whether an implementation satisfies a specification (conflating proof difficulty with specification quality) or require full semantic equivalence proofs (which are extremely difficult and yield sparse, hard-to-interpret signals). This makes it fundamentally unclear whether a verification failure reflects a defective specification or merely a limitation of the prover.

## Input / Output

The method takes a natural language problem description and Python reference implementation from HumanEval, and the LLM produces a Rocq specification as a Prop over input-output pairs. Evaluation instantiates each specification against approximately 756 positive test cases (from HumanEval+) and 10 negative test cases (generated via mutation testing on canonical implementations), producing a multi-stage score culminating in REJECT_all — the proportion of specifications that provably accept all positive cases while not being provably overly permissive on any negative case.

## Method

COINS (COq-based INstantiated Specification evaluation) assesses specification quality by instantiating specifications on concrete test cases and checking whether the resulting proof obligations can be discharged in Rocq, exploiting the asymmetry of formal reasoning where successful proofs provide reliable positive evidence while failures are inherently ambiguous. The evaluation pipeline proceeds through four progressive stages — syntactic validation, first-case acceptance, full positive test acceptance (PASS_all), and negative test rejection (REJECT_all) — with the final stage serving as the core discriminative metric. To anchor the evaluation and break the specification-prover duality, the authors manually construct human-written Rocq specifications for all 164 HumanEval problems and use them to calibrate and select the strongest verifier (Gemini 3 Pro Preview). Negative test cases are generated through a two-stage mutation strategy (AST-based deterministic mutations followed by LLM-guided semantic mutations) applied to canonical implementations, yielding 1,640 negative cases across the benchmark.

## Results

On the COINS benchmark (164 HumanEval problems in Rocq), the core metric REJECT_all (specifications that pass all positive tests and reject all negative tests) ranges from 28.05% for Gemini 3 Pro Preview to 1.22% for DeepSeek-V3.1, revealing a substantial capability gap. Syntax correctness—the first bottleneck—spans from 78.05% (Gemini 3 Pro Preview) to 7.93% (DeepSeek-V3.1). Even the strongest verifier (Gemini 3 Pro Preview) achieves only 29.88% PASS_all on human-crafted specifications, highlighting that verification difficulty itself obscures specification quality. Compared to CLEVER's end-to-end equivalence approach (0.621% correctness), COINS provides meaningful discriminative power across all six models.

## Baselines & Comparisons

The paper does not compare against a single prior method but instead benchmarks six LLMs (Gemini 3 Pro Preview, GPT-5, Claude 4.5 Opus, GPT-4o, Claude 3.7 Sonnet, DeepSeek-V3.1) on the new COINS framework. Gemini 3 Pro Preview leads on every metric, achieving 28.05% REJECT_all versus 15.24% for GPT-5 and 14.63% for Claude 4.5 Opus—a roughly 2× gap over the next-best models. Earlier-generation models (GPT-4o, Claude 3.7 Sonnet, DeepSeek-V3.1) cluster near the bottom (1.22%–4.27% REJECT_all), with DeepSeek-V3.1's 7.93% syntax rate being the dominant failure mode. Against the prior CLEVER benchmark (which requires full equivalence proofs and achieves only 0.621% correctness), COINS's test-case-based approach yields 28× higher top-model scores and meaningful variance across models. An ablation shows that improving specification quality (human vs. LLM specs) contributes +5.01% while upgrading the verifier (self vs. Gemini) contributes +3.05%, confirming both factors matter but specification quality is the larger bottleneck.

## Relation to Prior Work

This paper departs from the dominant paradigm in LLM-for-verification benchmarks (CLEVER, VeriBench, VERINA, VeriEquivBench), which evaluate specifications indirectly by checking implementation conformance or requiring full semantic equivalence proofs. COINS instead repurposes the proof-assistant verification loop to evaluate the specification itself by instantiating it on concrete test cases, drawing on mutation-testing ideas from software engineering but applied to Python implementations rather than formal artifacts. It also complements the growing line of LLM-based specification synthesis work (AutoSpec, SpecGen, nl2spec) by providing the missing evaluation infrastructure to measure the quality of their outputs, and positions itself as a diagnostic methodology for the autoformalization pipelines studied in theorem-proving work (DeepSeek Prover, APOLLO, Lemur).

## Why It Matters / Open Questions

The paper exposes a fundamental blind spot in how the field measures specification quality: the 'Evaluation Duality' means that failed proofs conflate specification errors with prover limitations, making it impossible to attribute failures correctly without a more granular evaluation protocol. The finding that even the strongest model achieves only ~28% on the core metric, and that formal specification generation correlates more with mathematical reasoning (AIME) than with code generation (SWE-bench), reframes where the bottleneck lies and suggests that scaling code-generation capability alone will not solve the specification problem. Key limitations include the restriction to 164 HumanEval problems in Rocq, the incompleteness of test-case-based evaluation (candidate specs may still be semantically wrong on untested inputs), and the dependence on a single best-performing verifier (Gemini 3 Pro Preview) whose own 30% PASS_all rate on human specs introduces residual uncertainty. Open questions include whether the methodology transfers to richer proof assistants or industrial-scale specifications, and whether the Fixpoint-vs-Inductive design choice generalizes beyond algorithmic problems.
