## Problem

Current LLM agent safety mechanisms focus almost exclusively on preventing failures in advance (model alignment, runtime guards, trajectory monitoring), leaving agent systems without structured capabilities to detect, contain, recover from, or prevent recurrence of incidents that inevitably arise during multi-step execution. No prior work provides a dedicated incident response framework that operates within the agent's execution loop to manage the full incident lifecycle.
![Teaser figure](../imgs/ICML20265136/cropped_page2_idx0.webp)

## Input / Output

AIR consumes the agent's generated plan, the tool invocation just executed, the current environment state (queried via inspection tools), a selected portion of recent execution context, and a set of AIR rules written in a natural-language DSL. It produces an incident detection flag, executes containment and recovery actions through the agent's existing tool interface, and synthesizes a new plan-level guardrail rule that is appended to a growing rule set. The DSL's check conditions are natural-language semantic descriptions (e.g., 'a sensitive file has been copied into an unprotected directory') rather than syntactic API-match constraints, and guardrail rules evaluate plan intent before any tool invocation occurs.

## Method

AIR defines a domain-specific language with three components per rule—trigger (selects rules by matching the tool used in the current step), check (a natural-language condition the agent evaluates against environment state and context), and remediate (structured containment-then-recovery actions executed via the agent's tools)—and interposes two lightweight hooks into the agent's execution loop: one after each tool invocation for detection and remediation, and one before each step for plan-level guardrail enforcement. After containment and recovery, AIR enters an eradication phase where it extracts incident context (plan, tool call, environment state, triggering check condition) and guides the agent to synthesize a new guardrail rule that blocks similar plans in future executions. This creates a self-reinforcing safety loop: each incident generates a guardrail rule that accumulates into a growing rule set, progressively reducing incident frequency across rounds without manual intervention. The framework is implemented on the OpenAI Agent SDK using ANTLR4 for DSL parsing and is framework-agnostic, with the same two integration hooks mappable onto other agent frameworks.

## Results

AIR achieves incident detection, remediation, and eradication success rates all exceeding 90% across three agent types (code, embodied, computer-use). On the embodied agent (SafeAgentBench), detection matches execution in every hazard category (e.g., 21/21 for Poisoning, 19/19 for Slip Hazard), with remediation and eradication at 87–100%. Zero false positives are observed across 85 safe tasks (50 embodied + 35 CUA). LLM-generated AIR rules attain 84.6–96.0% detection, 84.6–88.8% remediation, and 89.7–91.0% eradication, approaching developer-authored rule performance.

## Baselines & Comparisons

No direct baselines exist, as AIR is explicitly the first incident response framework for LLM agent systems; the paper therefore does not benchmark against prior methods. Instead, the paper positions AIR as complementary to three existing safety categories (model-centric alignment, runtime enforcement, and trajectory monitoring), arguing that all three are inherently incomplete and leave systems vulnerable to incidents that require post-hoc response. The closest internal comparison is between developer-authored and LLM-generated AIR rules: LLM-generated rules achieve 84.6–96.0% detection versus near-100% for hand-written rules, with the gap attributed to overly specific or overly abstract check conditions. Ablation results further quantify the contribution of each component: removing structured remediation degrades remediation success and response efficiency, while removing guardrail rule generation causes incident counts to remain high across rounds (e.g., code agent incidents stay elevated versus dropping from 54→6→0 with guardrails active).

## Relation to Prior Work

AIR repurposes the traditional incident response lifecycle (detection → containment → recovery → eradication) from networked systems (NIST CSF, SOAR platforms) into the LLM agent execution loop, where no prior work has addressed post-incident response. It departs from the dominant agent-safety literature—model-centric alignment, runtime enforcement (AgentSpec, GuardAgent, Progent), and trajectory monitoring (Pro2Guard, TraceAegis)—which all focus on preventing unsafe actions before they occur, by instead providing a structured mechanism for detecting, containing, recovering from, and eradicating incidents after they inevitably arise. The DSL design draws on AgentSpec's runtime rule concept but extends it with natural-language semantic checks and a full remediation/eradication chain, while the guardrail-rule synthesis step borrows the plan-level blocking idea from prior runtime enforcement work and repurposes it as an automatic, incident-driven learning mechanism.

## Why It Matters / Open Questions

By establishing incident response as a first-class mechanism alongside prevention, AIR addresses a gap that becomes increasingly critical as agents are deployed in safety-critical or user-facing settings where failures are inevitable. Key open questions include: how well the framework scales to multi-agent or long-horizon settings where incidents span many steps and agents; whether the reliance on the agent's own reasoning for check interpretation and remediation execution remains reliable under distribution shift; and how to reduce the ~40% overhead on safe tasks without sacrificing detection quality. The finding that LLM-generated rules approach developer-authored rules is encouraging for practical adoption but still requires human-in-the-loop validation, particularly for remediation actions that may be infeasible in practice.
