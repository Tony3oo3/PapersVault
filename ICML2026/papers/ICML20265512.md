## Problem

Existing Text-to-SQL and SQL-debugging benchmarks focus on short, simple queries far removed from enterprise ETL workloads, and no systematic benchmark exists for evaluating LLMs on iterative debugging of long, complex, schema-heavy SQL scripts. The paper asks whether current LLMs can realistically debug enterprise-level ETL SQL, where scripts average over 140 lines with deeply nested subqueries and dozens of table references, and where bugs range from explicit syntax errors to subtle semantic mismatches with user intent.
![Teaser figure](../imgs/ICML20265512/cropped_page1_idx0.webp)

## Input / Output

The task takes a buggy SQL script (b), auxiliary context C (an explicit error message for syntax errors or a natural-language intent specification for semantic errors), and the database schema DDL (σ), and produces a corrected SQL query (q̂) that is both syntactically valid and faithful to the encoded intent. Scripts are highly complex—averaging 140–160 lines, 420+ tokens, AST width >11, depth >8.7, and 15+ functions per script—making long-range context and dependency tracking essential. Evaluation is execution-free, using three complementary metrics: Exact Match (string identity), Graph Match (isomorphism of Apache Calcite-optimized ASTs), and Modify Better (whether the AST edit distance to the reference decreases relative to the original buggy query).

## Method

The Squirrel Benchmark is constructed via an automated reverse-engineering pipeline: seed enterprise SQL scripts are curated and complexity-filtered, a three-level hierarchical bug taxonomy is derived from 268 annotated production logs, and minimal-change bugs are injected by LLMs guided by structural profiling and taxonomy selection, followed by an attack-defense validation loop that discards trivial instances solvable by most models. For evaluation, the paper introduces an execution-free framework built on Apache Calcite's canonical intermediate representation, performing graph isomorphism to capture semantic equivalence without running queries against production databases. On the solution side, the paper explores four strategies: vanilla SFT on parallel debugging pairs, DM-SFT (masking loss on unchanged tokens to focus learning on diffs), Diff-SFT (framing repair as search-and-replace to halve inference time), and a two-agent architecture where a main agent plans fixes and a sub-agent implements them iteratively with TQS static-analysis feedback. Across nearly 30 LLMs, the best model (Claude-4-Sonnet) achieves only 36.46% GM on syntax and 32.17% on semantic tasks, while most models score below 20%.

## Results

On Squirrel-Syntax, the best-performing model Claude-4-Sonnet achieves 36.46% Graph Match (GM) score, while on Squirrel-Semantic it reaches 32.17% GM. Most evaluated models score below 20% GM on both subsets, with the best open-source model DeepSeek-V3 reaching 30.28% GM on Squirrel-Syntax. The Modify Better (MB) score, measuring whether a model's output moves closer to the correct solution, is substantially higher (50–68%) for reasoning-oriented LLMs, indicating models can partially improve buggy code but rarely fix it completely in one pass.

## Baselines & Comparisons

Claude-4-Sonnet dominates all other models, achieving 36.46% GM on Squirrel-Syntax and 32.17% GM on Squirrel-Semantic, outperforming the next-best closed-source model (Doubao-Seed-1.6 at 30.92%/20.93% GM) by 5.5 and 11.2 points respectively. Among open-source models, DeepSeek-V3 leads with 30.28% GM on Squirrel-Syntax, while Qwen-2.5-Coder-32B is strongest on Squirrel-Semantic (23.45% GM), both trailing Claude-4-Sonnet by 6+ points. The Text-to-SQL-specialized OmniSQL model collapses to just 6.40% GM on both subsets, confirming a large gap between SQL generation and SQL debugging capabilities. GPT-4o and GPT-4o-mini perform poorly (4.69% GM on Squirrel-Syntax), while GPT-5 (18.55%) and GPT-4.1 (17.70%) are more competitive but still well below Claude-4-Sonnet. Reasoning-oriented models (GPT-5, O3-mini, Gemini-2.5-Pro, Kimi-K2) consistently achieve MB scores above 50%, showing they can partially improve buggy code even when failing to produce a fully correct fix. The DM-SFT fine-tuning of Qwen-2.5-Coder-7B reaches 33.18% GM on Squirrel-Syntax, surpassing the 32B base model (20.26%) by 12.9 points, demonstrating that targeted in-domain SFT can close much of the size gap.

## Relation to Prior Work

This paper extends the SQL debugging task introduced by BIRD-Critic (Li et al., 2026) from short, simplified StackOverflow-style queries to enterprise-scale ETL scripts averaging 140+ lines with deep ASTs. It builds on the DM-SFT dynamic masking technique (Duan et al., 2025) for fine-tuning baselines and draws on the SWE-Bench paradigm of iterative code repair, but departs from both by introducing an automated reverse-engineering pipeline for bug injection and an execution-free evaluation framework (Graph Match via Apache Calcite, Modify Better Score) that avoids the practical infeasibility of running production SQL. The positioning is explicitly against Text-to-SQL benchmarks (Spider, BIRD) and their enterprise extensions (Spider 2.0), arguing that generation and debugging are fundamentally different capabilities.

## Why It Matters / Open Questions

The benchmark reveals that even the strongest LLMs (Claude-4-Sonnet at 36.46% GM) struggle substantially with enterprise SQL debugging, and the gap between SQL generation (OmniSQL: 87.6% on Spider) and SQL debugging (6.4% GM on Squirrel) is stark, suggesting that code-generation-optimized models are poorly suited for iterative repair. Open questions include whether the execution-free metrics (particularly GM, which agrees with human judgment in only ~68% of cases) adequately capture correctness for semantic tasks with multiple valid solutions, and whether the Hive/Spark SQL dialect limitation generalizes. The automated reverse-engineering pipeline also offers a reusable template for synthesizing debugging training data at scale, which could accelerate future work beyond this specific benchmark.
