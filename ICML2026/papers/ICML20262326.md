## Problem

On-device personal AI agents must ground responses in device-resident personal context, but indiscriminate storage of all incoming data is infeasible under strict memory budgets. Prior RAG personalization work focuses on how to use personal signals at retrieval time (query rewriting, memory-side organization) rather than the upstream question of what to store in the first place. This paper tackles that gap: constructing compact, preference-aligned on-device memory from raw heterogeneous data so that retrieval is both query-relevant and consistent with user preferences.
![Teaser figure](../imgs/ICML20262326/cropped_page0_idx0.webp)

## Input / Output

At indexing time, EPIC consumes raw text chunks (segmented to ~100 words) from heterogeneous sources (Wikipedia, Common Crawl, LMSYS-Chat) together with an explicit user preference set, and produces an instruction-centric memory where each entry stores a raw item, a preference-conditioned usage instruction, the associated preference, and the instruction's embedding. At query time, a single user query is steered toward the most relevant preference direction and matched against instruction embeddings via FAISS kNN, returning the linked raw items as retrieval context. The memory is indexed by instruction embeddings rather than raw item embeddings, making the index explicitly preference-aware at the text level while remaining compact (under 1 MB on-device).

## Method

EPIC (Efficient Preference-aligned Index Construction) is a three-stage, zero-shot pipeline that integrates user preferences into both memory construction and retrieval. Stage 1 (Semantic-Based Coarse Filtering) embeds all items and preferences with a shared sentence encoder (Contriever) and retains only items whose cosine similarity to at least one preference exceeds a threshold τ, achieving high-recall pruning with no LLM calls. Stage 2 (Preference-Aligned Fine Verification) applies an LLM-based Decision Module to confirm or discard each coarse-filtered candidate and an Instruction Generator to synthesize concise preference-conditioned usage directives; the final memory is indexed by these instruction embeddings rather than raw text. Stage 3 (Preference-Guided Query Steering) selects the preference most similar to the incoming query and shifts the query embedding toward that preference via vector addition and ℓ₂-normalization before FAISS retrieval, adding negligible overhead (0.03–0.55 ms) while improving preference-aligned recall. The entire pipeline is plug-and-play and has been validated as a drop-in layer for structured RAG systems such as HippoRAG 2.

## Results

Across four benchmarks (PrefWiki, PrefRQ, PrefELI5, PrefEval) and three LLM backends, EPIC consistently achieves the highest preference-following accuracy. Under the primary Llama-3.1-8B-Instruct backend, EPIC scores 54.07%, 83.00%, 87.95%, and 65.61% respectively, outperforming the best standard RAG baseline (NV-Embed-v2) by 18.79 percentage points on average. In terms of efficiency, EPIC reduces on-disk indexing memory by 2,404× (0.27 MB vs. 648.96 MB for NV-Embed-v2 on PrefWiki) and achieves 32.17× lower retrieval latency (3 ms vs. 96.5 ms average). On-device, EPIC maintains under 1 MB memory and 5.21–29.35 ms/query retrieval latency across Jetson Orin Nano, MacBook Pro M4, and Galaxy Z Flip 6.

## Baselines & Comparisons

EPIC outperforms all 11 baselines across every benchmark and LLM backend. Against the strongest standard RAG retriever (NV-Embed-v2), EPIC gains +9.54 to +34.73 pp depending on the dataset, with the largest margin on PrefEval (conversation) where preference alignment is most critical. Indexing-enhanced methods (RAPTOR, HippoRAG, HippoRAG 2) improve retrieval structure but remain preference-agnostic; EPIC surpasses the best of these (HippoRAG 2) by +11.16 to +32.63 pp. Preference-conditioned query-rewriting baselines (Pref-QR, PBR) condition the query but still index all raw data indiscriminately; EPIC beats them by +14.35 to +35.40 pp while also eliminating the per-query LLM rewriting cost (PBR incurs ~13,327 ms average retrieval latency vs. EPIC's 3 ms). In the appendix comparisons, EPIC also dominates MemoryBank (64.0% vs. 25.61% on PrefEval) and high-compression retrieval methods BPR/RaBitQ (55.2% vs. 41.33%/40.77% on PrefWiki), confirming that content-level preference filtering is orthogonal to and more effective than post-hoc index compression.

## Relation to Prior Work

This paper carves out a distinct sub-problem within personalized RAG: rather than improving retrieval quality over a fixed index (RAPTOR, HippoRAG) or conditioning queries at retrieval time (Pref-QR, PBR), EPIC addresses the upstream question of *what to store* from raw, heterogeneous on-device data under tight memory budgets. It repurposes standard components—Contriever embeddings for coarse filtering, an LLM for fine-grained verification and instruction generation, and a simple vector-averaging trick for query steering—into a three-stage pipeline that has not been previously assembled for this purpose. The paper explicitly positions itself as orthogonal to both index-compression methods (BPR, RaBitQ) and memory-side personalization methods (MemoryBank, EMG-RAG), which assume content is already retained.

## Why It Matters / Open Questions

As personal AI agents move to on-device deployment for privacy and latency reasons, the memory-construction bottleneck becomes the limiting factor, and this paper provides a concrete, well-evaluated answer with sub-1 MB footprints and single-digit-ms retrieval across edge and consumer hardware. The four constructed benchmarks (PrefWiki, PrefRQ, PrefELI5, plus PrefEval) fill a gap in preference-centric RAG evaluation beyond conversational memory. Open questions remain: the preference set is assumed available at indexing time (extraction is out of scope), long-term memory eviction policies are only sketched, and the streaming evaluation is limited to a single device and one corpus. The plug-and-play integration with HippoRAG 2 suggests the components could compose with structured retrieval pipelines, but broader validation across architectures and real user data is needed.
