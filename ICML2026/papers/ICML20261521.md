## Problem

Prior work treats LLM inference optimizations (sparse attention, RAG, compressed contextual memory) as isolated techniques without a unified understanding of their computational characteristics or hardware efficiency implications. This paper shows that these methods share a common four-stage memory processing pipeline accounting for 22%–97% of inference latency, and that the strong computational heterogeneity across stages (varying arithmetic intensity, access patterns, and data dependencies) is systematically underexploited by homogeneous GPU-only deployments.

## Input / Output

The system consumes long-context text sequences (up to 1M tokens), document corpora (up to 20M documents for RAG), and pre-computed KV cache or memory embeddings, producing generated tokens, retrieved document indices, and retrieved memory embeddings. A key operational detail is that inputs are partitioned across devices: the GPU receives the full model weights and dense computation inputs, while the FPGA receives compressed key vectors, query vectors, or BM25 token-frequency dictionaries via PCIe P2P DMA (under 1 KB for indices, up to MB-scale for embeddings). The FPGA returns only lightweight outputs (top-k indices or retrieved embeddings) back to the GPU, keeping cross-device transfers negligible relative to end-to-end latency.

## Method

The paper unifies sparse attention, RAG, synthesized memory, and memory-as-context under a four-stage pipeline (Prepare Memory → Compute Relevancy → Retrieval → Apply to Inference) and profiles each stage's arithmetic intensity, access regularity, and data dependencies to guide hardware mapping. On a GPU-FPGA system (AMD MI210 + Alveo U55C over PCIe), compute-intensive and regular stages (linear projections, attention, prefilling) remain on the GPU, while memory-bound, irregular, and data-dependent stages (inner-product scoring, top-k selection, BM25) are fused into a single streaming dataflow kernel on the FPGA. The FPGA kernel exploits a three-level on-chip memory hierarchy (BRAM at 21.8 TB/s, URAM at 10.4 TB/s, HBM at 460 GB/s) with a write arbiter that places recent key vectors in faster tiers, and a parallel reduction tree for running top-k maintenance. Mapping strategy varies by method: a general setup for sparse attention and RAG, prefill-decode disaggregation for MemAgent (FPGA decodes, GPU prefills), and a recurrent-loop data placement for Memory as Context that keeps all memory on the FPGA to enable deeper kernel fusion. The system achieves 1.04–2.2× end-to-end speedup and 1.11–4.7× energy reduction over GPU-only baselines, with speedups growing with batch size for sparse attention and RAG due to the FPGA's sustained HBM bandwidth advantage on non-shareable retrieval workloads.

## Results

The GPU-FPGA heterogeneous system (AMD MI210 + Alveo U55C) achieves 1.04–2.2× end-to-end speedup and 1.11–4.7× geomean energy reduction over the GPU-only baseline across six LLM inference optimization categories. Memory processing accounts for 22%–97% of total inference latency, with the largest gains in RAG (up to 2.2× end-to-end, 5.2–7.7× memory-processing speedup) and MemAgent (1.8× end-to-end, 4.66× energy reduction). At batch size 1, all methods show speedup; sparse attention and RAG speedups grow with batch size (e.g., LServe reaches 1.83× at BS=32), while MemAgent degrades beyond BS=2 due to GPU weight-reuse advantages in dense decoding.

## Baselines & Comparisons

The paper compares the GPU-FPGA heterogeneous system against a GPU-only baseline (same MI210) for each of six LLM inference optimization methods. The system wins on all methods at batch size 1: sparse attention methods (DeepSeek Attention 1.02×, SeerAttention-R 1.07–1.12×, LServe 1.19×), RAG methods (DRAGIN 1.14×, FLARE 1.19×, FS-RAG 1.26×, Two-stage RAG 1.16×), MemAgent (1.85×), and Memory as Context/HMT-Titans (1.48×). At larger batch sizes, sparse attention and RAG speedups increase (FLARE reaches 2.11× at BS=32) because retrieval operations do not benefit from GPU weight reuse, while MemAgent loses beyond BS=2 (dropping to 0.13× at BS=32) because GPU decoding benefits from batched weight reuse that the FPGA cannot match. The system also achieves 1.11–4.66× geomean energy reduction, with the largest gain (4.66×) on MemAgent where FPGA decoding power (44.2 W) is less than half the GPU's (99 W). For sequences exceeding 1M tokens, LServe and DeepSeek Attention dynamically fall back to GPU-only execution to avoid FPGA HBM-access degradation.

## Relation to Prior Work

This paper builds on the line of GPU-FPGA heterogeneous LLM inference work (GLITCHES, FlightLLM, LUT-LLM, FlexLLM), which demonstrated that FPGAs can accelerate specific LLM operations. However, those prior efforts focused on the full model forward pass or prefill-decode disaggregation, whereas this paper identifies a more targeted opportunity: the memory processing pipeline (Prepare Memory, Compute Relevancy, Retrieval, Apply to Inference) that underlies sparse attention, RAG, and compressed memory methods. The key conceptual departure is the unification of these previously isolated algorithmic optimizations under a single four-stage pipeline, revealing that their shared computational heterogeneity (irregular, memory-bound, data-dependent operations) is what makes them amenable to FPGA offloading rather than GPU execution.

## Why It Matters / Open Questions

The finding that memory processing accounts for 22%–97% of inference latency across diverse LLM optimizations provides a concrete, actionable target for hardware designers and system architects, and the four-stage pipeline offers a reusable analytical framework for evaluating future memory-centric LLM methods. The 4.7× energy reduction for MemAgent and consistent 1.1–1.6× savings across other methods have direct implications for serving cost at scale. Key limitations include the reliance on a 16nm FPGA (U55C) connected via PCIe, performance degradation beyond 1M tokens for some sparse attention methods, and MemAgent's slowdown at larger batch sizes. Open questions include whether a purpose-built heterogeneous ASIC could eliminate the PCIe bottleneck, whether design automation can reduce the kernel development effort for new memory processing algorithms, and how the approach scales to next-generation FPGA platforms like the Versal V80.
