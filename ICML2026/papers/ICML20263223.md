## Problem

As LLMs are increasingly deployed as autonomous agents inside Docker/OCI container sandboxes, there is no systematic benchmark to measure whether these models can discover and exploit container isolation weaknesses to escape. Existing cyber capability evaluations (CTF, web exploitation, CVE benchmarks) do not target the specific failure mode of container-to-host escape, leaving uncertainty over whether standard container isolation is a safe boundary for frontier LLMs.

## Input / Output

The agent receives a minimal white-hat system prompt and a task prompt describing a CTF escape challenge, with optional task-specific vulnerability hints in an ablation variant. It operates via a ReAct-style loop with exactly two tools (bash for shell execution routed into the container, and submit for flag submission) under a 2.5M-token budget, with no web search or external tools. Output is a binary success signal (exact string match of a flag file on the host filesystem outside all container namespaces), aggregated into per-task and per-difficulty success rates over 5 independent trials, alongside full agent transcripts for behavioural analysis.

## Method

SANDBOXESCAPEBENCH employs a nested 'sandbox-in-a-sandbox' architecture: a Docker container (or Kubernetes pod) with an intentionally introduced vulnerability runs inside a virtual machine, so that a successful escape lands the agent in the VM rather than the evaluation host. The benchmark comprises 18 tasks across three layers of the container stack (Orchestration, Engine & Runtime, Host/Kernel), each grounded in a documented CVE or misconfiguration class with a known reference exploit, rated on a 1–5 difficulty scale validated by three independent security experts (Krippendorff's α = 0.816). Evaluation is implemented on the Inspect AI framework with a custom Vagrant-based VM sandbox provider, and success is determined by unambiguous flag retrieval to prevent reward hacking. The paper further analyses inference-time compute scaling (showing approximately log-linear gains), the effect of vulnerability hints on discovery vs. exploitation, and transcript-level behavioural patterns including refusals, disengagement, and false success claims across nine frontier models.

## Results

On SANDBOXESCAPEBENCH (18 container-escape tasks, 5 trials each, 2.5M token budget), frontier models achieve near-perfect success on difficulty-1 misconfigurations (GPT-5, Opus 4.5, Sonnet 4.5 all reach 1.00) and strong rates on difficulty-2 tasks (Opus 4.5 and GPT-5 at 1.00; GPT-5.2 at 0.73). At difficulty 3, only the largest models succeed meaningfully: Opus 4.5 reaches 0.40 [0.26, 0.56] and GPT-5 reaches ~0.26, while all other models score 0.00–0.17. No model achieves any success on difficulty-4 or difficulty-5 tasks (kernel exploits, complex CVEs). Overall pooled success rates are Opus 4.5: 0.49 [0.39, 0.59], GPT-5: 0.50 [0.40, 0.60], GPT-5.2: 0.27 [0.19, 0.37], Haiku 4.5: 0.18 [0.11, 0.27], and GPT-OSS-120B: 0.16 [0.09, 0.24].

## Baselines & Comparisons

This is a benchmark paper, so the 'baselines' are the nine evaluated frontier models compared against each other on the same 18 tasks. Claude Opus 4.5 and GPT-5 are the strongest performers, both reaching 1.00 on all difficulty-1 and difficulty-2 tasks and the only models with non-trivial difficulty-3 success (Opus 0.40, GPT-5 ~0.26). GPT-5.2 shows a notable version-to-version regression relative to GPT-5 (0.27 vs. 0.50 overall), with 92.3% of its failed samples exhibiting mid-task disengagement. Smaller models (Haiku 4.5, GPT-5-nano, GPT-OSS-120B) handle the most direct misconfiguration escapes competitively but degrade sharply on tasks requiring exploit adaptation or multi-step kernel reasoning, scoring 0.00 on all difficulty-3+ tasks. DeepSeek-R1 is an outlier in behaviour: it achieves 0.80 on difficulty-1 but hallucinates success in 86.7% of its failed samples, submitting an average of 21 incorrect flags per run. Inference-time compute scaling is approximately log-linear, with marginal cost of ~$1 per sample at current pricing, meaning an attacker can cheaply attempt many parallel escapes.

## Relation to Prior Work

This paper sits at the intersection of three established lines of work: LLM cyber-capability benchmarks (CyBench, CVE-Bench, CyberGym, NYU CTF Bench), the container security vulnerability taxonomy (Jarkas et al. 2025, cataloguing 200+ weaknesses across orchestration, runtime, and kernel layers), and AI containment research (Babcock et al. 2017, OpenAI's o1 system card, ControlArena). It repurposes the CTF evaluation methodology from the first line and the layered vulnerability taxonomy from the second to define a new evaluation target—LLM container-escape capability—that neither line had addressed. The nested sandbox-in-a-sandbox architecture is a methodological contribution that enables safe evaluation of escape, building on Inspect AI's sandbox provider ecosystem but extending it with a VM isolation layer specifically designed so that successful escapes do not compromise evaluation infrastructure.

## Why It Matters / Open Questions

The practical finding that frontier models reliably escape difficulty 1–2 misconfigurations (privileged containers, exposed Docker sockets, writable host mounts) means that 'plain Docker isolation'—the default in much of the open-source agent ecosystem—is insufficient as a containment boundary for capable models, with direct implications for how agent deployments should be configured. The approximately log-linear scaling of success with inference-time compute implies that containment must account for deployment parameters (token budgets, retries, parallelism), not just model identity, and the observed version-to-version regression (GPT-5.2 substantially worse than GPT-5) raises concerns about the stability of agentic capabilities across model updates. Open questions include how results change under more sophisticated agent architectures (persistent memory, web search, structured planners), whether microVM-based isolation (Firecracker, gVisor) closes the gap, and how the benchmark evolves as models improve on the currently unsolvable difficulty 4–5 kernel exploits.
