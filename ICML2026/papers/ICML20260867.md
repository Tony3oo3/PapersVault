## Problem

Existing coding benchmarks like SWE-Bench are vulnerable to data contamination because they draw from public open-source repositories that are likely present in LLM training corpora, and they underrepresent the complexity of real enterprise software engineering—SWE-Bench Verified contains 161 of 500 problems requiring only 1–2 line fixes. SWE-Bench Pro addresses both gaps by constructing a contamination-resistant benchmark from copyleft-licensed and proprietary startup codebases, with tasks that demand multi-file, substantial code modifications comparable to professional engineering work.

## Input / Output

Each task provides the agent with the full repository codebase, a human-augmented problem statement (rewritten from original commits/PRs/issues), a list of grounded requirements specifying expected behavior, and an optional interface specification defining exact class/function names and signatures expected by the test suite. The agent must produce a single code patch that passes both fail2pass tests (verifying the fix) and pass2pass tests (preserving existing functionality) within a 50-turn budget in a containerized, language-specific environment. The benchmark comprises 1,865 problems across 41 repositories, partitioned into a public set (731 instances, GPL-licensed repos), a commercial set (276 instances, proprietary startup repos), and a held-out set (858 instances) for future overfitting checks.

## Method

The benchmark is constructed by mining consecutive commit pairs from 41 actively maintained repositories, extracting test patches and gold patches, then filtering to retain only problems requiring ≥10 lines of change across multiple files (average 107.4 LOC across 4.1 files). Contamination resistance is achieved through two complementary mechanisms: exclusively using GPL/copyleft-licensed repositories for the public and held-out sets (creating legal barriers to inclusion in commercial training corpora), and sourcing 18 proprietary repositories from early-stage startups for the commercial set. A three-stage human-in-the-loop augmentation process rewrites problem statements, adds requirements grounded in unit tests, and specifies interfaces to eliminate false negatives from test verifiers while preserving implementation flexibility. Evaluation uses the SWE-Agent scaffold with a unified prompt and 50-turn limit across frontier and open-weight models hosted on 8×H100 GPUs via vLLM. A GPT-5-based LLM-as-a-judge pipeline classifies unresolved trajectories into failure-mode buckets (wrong solution, syntax error, tool-use failure, context overflow, etc.) using the last 20 turns of each rollout.

## Results

On the public set of SWE-Bench Pro (N=731), GPT-5 (High) achieves the highest Pass@1 resolve rate at 25.9%, followed by GPT-5 (Medium) at 23.3% and Claude Opus 4.1 at 22.7%. Smaller models show dramatically lower performance: Claude Sonnet 4 reaches 17.6%, GPT-OSS 20B 16.2%, Gemini 2.5 Pro Preview 13.5%, SWE-Smith-32B 6.8%, GPT-4o 4.9%, and Qwen3 32B 3.4%. On the harder commercial set (N=276), the best model (Claude Opus 4.1) drops to 17.8%, and GPT-5 (High) to 15.7%, highlighting the additional difficulty of enterprise codebases. These scores contrast sharply with the ~70% these frontier models achieve on SWE-Bench Verified.

## Baselines & Comparisons

This benchmark paper evaluates nine models under a unified SWE-Agent scaffold rather than proposing a new method, so the key comparison is between frontier and smaller models. GPT-5 (High) leads at 25.9% Pass@1, outperforming Claude Opus 4.1 (22.7%) by 3.2 points and Claude Sonnet 4 (17.6%) by 8.3 points. The gap widens dramatically for open-weight models: GPT-OSS 20B (16.2%) and Gemini 2.5 Pro Preview (13.5%) trail the frontier by 10+ points, while SWE-Smith-32B (6.8%), GPT-4o (4.9%), and Qwen3 32B (3.4%) fall below 7%. On the commercial set, Claude Opus 4.1 edges out GPT-5 (High) (17.8% vs. 15.7%), suggesting different strengths on proprietary enterprise code. The ablation (Table 3) shows that removing human augmentations (requirements and interface) drops GPT-5 from 25.9% to 8.4% and Claude Opus 4.1 from 22.7% to 8.2%, confirming that the benchmark's task specification is critical for fair evaluation.

## Relation to Prior Work

This paper extends SWE-Bench and SWE-Bench Verified by constructing a substantially harder benchmark of multi-file, enterprise-level issues, while introducing a contamination-resistant curation strategy (copyleft-licensed public repos plus purchased commercial codebases) that prior benchmarks lacked. It builds on the SWE-Agent scaffold and the fail2pass/pass2pass verification paradigm, but adds a novel three-stage human augmentation workflow (problem statement, requirements, interface specification) to ensure task resolvability and reduce false negatives. The failure-mode taxonomy follows Yang et al.'s LLM-as-a-judge approach but applies it to a new, more complex task distribution.

## Why It Matters / Open Questions

The ~25% ceiling for frontier models (vs. 70%+ on SWE-Bench Verified) provides a much more honest calibration of current agent capabilities against professional software engineering, and the ablation showing a 3× performance drop when removing human augmentations reveals that ambiguity resolution—not just code generation—is a major bottleneck. The contamination-resistant design (legal barriers via copyleft + private commercial repos) addresses a credibility concern that has plagued prior benchmarks. Open questions include whether the test-suite-dependent verification can be replaced with more flexible evaluators, whether the held-out set will reveal overfitting to the public set, and how performance changes when requirements are removed entirely (the under-specified setting the authors note is 'potentially interesting' but do not fully explore).
