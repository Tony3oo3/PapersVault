## Problem

Existing formal mathematics benchmarks (miniF2F, FATE, miniCTX) evaluate isolated theorem proving—synthesizing a proof term for a given statement—while real formal mathematics development in production libraries like Mathlib involves repository-scale proof engineering: coordinating auxiliary results across files, managing library evolution, and performing maintenance under change. No systematic evaluation framework exists for these repository-scale engineering activities, leaving a gap between what AI systems actually do in practice and what benchmarks measure.

## Input / Output

Each task provides a natural-language instruction describing modification objectives (admitting multiple valid implementations), a pinned Mathlib commit hash and Lean4 toolchain version, and a target file that is blocked (read-only) while full library access is preserved for compilation context. The agent produces modified Lean source code, which undergoes dual verification: syntactic compilation against the pinned environment AND semantic validation via a 3-judge LLM-as-judge panel (majority vote) assessing requirement alignment, scope control, and mathematical correctness—compilation alone is explicitly insufficient since type-checking does not guarantee the stated objectives were met.

## Method

The core infrastructure is APE-Harness, built on a task contract abstraction that declaratively specifies environment bindings, objectives, boundaries (read-only/blocked paths), and verification protocols while remaining execution-agnostic, enabling scaffold interchangeability across APE-Agent (a ReAct-style scaffold with integrated edit-and-compile verification), Claude Code, and Codex CLI. APE-Bench automates task extraction from Mathlib commit histories through a three-stage pipeline (commit filtering for 10–300 line diffs, instruction synthesis executed as a task contract through APE-Harness itself, and solvability validation), producing 100 tasks from 67 commits with zero training-data contamination. Multi-version support across 67 library versions is achieved through content-addressable storage that deduplicates identical files by cryptographic hash, reducing execution storage from 480 GB to 71 GB and retrieval annotation cost by 98.5%. The key design insight is that contracts compose through nested execution—proof engineering tasks invoke judgment tasks as semantic validation sub-components—making the infrastructure self-hosted and extensible beyond evaluation to functional workflows like instruction synthesis and library annotation.

## Results

On APE-Bench (100 repository-scale proof engineering tasks), Gemini 3 Flash achieves 47% success rate, substantially outperforming GPT-5.2 (27%) and Gemini 3 Pro (24%) under a fixed $3 budget per task. On traditional theorem proving benchmarks, Gemini 3 Flash reaches 86% on miniF2F and 87.1% on miniCTX, while GPT-5.2 lags at 73% and 71.9% respectively. A critical finding is that GPT-5.2's 73 failures include 36 'hidden successes' that passed both compilation and semantic verification before exhausting budget, implying a potential 63% pass rate—revealing that cost-efficiency, not raw reasoning, determines model rankings under fixed budgets. APE-Agent scaffold outperforms Claude Code and Codex CLI by 15–23 percentage points across all models.

## Baselines & Comparisons

The paper compares three agent scaffolds (APE-Agent, Claude Code, Codex CLI) executing identical tasks under the same APE-Harness contracts. APE-Agent outperforms Claude Code by 15–23 percentage points across all three models (e.g., 47% vs. 27% for Gemini 3 Flash on APE-Bench), primarily due to integrated verification (5.6% execute calls vs. 16.9% for Claude Code) and a leaner 16.5K-character system prompt versus Claude Code's 65K. Codex CLI performs worst, with 26.6% of calls spent on execute and 60.3% on retrieval, reflecting a conservative information-gathering strategy that consumes budget. Among models, Gemini 3 Flash dominates APE-Bench (47%) over GPT-5.2 (27%) and Gemini 3 Pro (24%), but this advantage is economic rather than cognitive: per-turn progress is comparable, and GPT-5.2's higher per-turn cost causes premature budget exhaustion. Notably, GPT-5.2 shows anomalous resilience at high-complexity tasks (29% at 100+ diff lines vs. 12% for Gemini 3 Flash), consistent with a reasoning-heavy, low-iteration strategy that amortizes cost when fewer attempts suffice.

## Relation to Prior Work

This paper adapts SWE-bench's repository-scale evaluation paradigm (real commits, natural-language instructions, dual verification) to formal mathematics, replacing unit tests with LLM-as-judge semantic validation since proof tasks lack preexisting test coverage. It departs from existing formal math benchmarks (miniF2F, FATE, miniCTX) that evaluate isolated theorem proving by introducing repository-scale code modification with pinned environments and semantic requirement checking. The task contract abstraction is positioned architecturally between progress-tracking patterns (Claude Code) and execution-encapsulation patterns (LangGraph), adding programmatic enforcement while remaining execution-agnostic.

## Why It Matters / Open Questions

This is the first systematic infrastructure for evaluating repository-scale proof engineering, a gap the authors identify as critical given that production formal math libraries span millions of lines and AI systems already perform this work in practice. The finding that cost-efficiency rather than reasoning capability determines model rankings under fixed budgets (GPT-5.2's potential 63% vs. Gemini 3 Flash's 47% actual) reframes evaluation from capability-limited to budget-limited. Key limitations include restriction to single-file modifications in Lean/Mathlib, reliance on LLM judges whose scope-control assessment (89% accuracy) remains the weakest dimension, and the need for multi-file engineering and other formal ecosystems to validate generality.
