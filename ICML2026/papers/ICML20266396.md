## Problem

Mathematical benchmarks built around formal domain-specific languages (DSLs) such as JGEX for Euclidean geometry ship formal instances without the executable environment needed to rerun, audit, and extend them. Documented predicate vocabularies are not uniformly supported by the underlying solver backends, nontrivial encoding choices silently affect solver behavior, and cross-tool discrepancies (e.g., predicates recognized by Newclid but not Yuclid) fragment interoperability. The paper argues that without an executable interface contract—versioned, runnable, and conformance-tested—these benchmarks are not fully reproducible.

## Input / Output

The NL→JGEX pipeline consumes a natural-language geometry problem statement alongside a compact JGEX reference card (supported predicates, canonical constructor signatures, minimal examples) and k=20 in-context NL-to-JGEX example pairs, all fed to GPT-5.4 Pro via the Chat Completions API at temperature 0. The extracted JGEX candidate is validated by building and running it under pinned Newclid v3.0.1, producing one of three outcome labels: Executable, API-truncated (finish_reason=length with no program text), or Other failure. The broader release also includes a 33-predicate support matrix generated from minimal executable test cases and per-instance run-status annotations across the 137-problem JGEXDiv corpus.

## Method

The paper's core contribution is the 'executable interface contract,' a four-component bundle: (i) released executable formal instances with validator scripts, (ii) explicit toolchain versioning, (iii) executable support evidence for the benchmark-used interface fragment, and (iv) documented nontrivial curation decisions (reformulations, helper constructions, exclusions, alternative encodings). To instantiate this, the authors build JGEXDiv (137 Euclidean geometry problems with JGEX formalizations, NL rewrites, and pinned Newclid v3.0.1 run-status annotations) and conduct a predicate-level audit using minimal JGEX test instances that categorize all 33 documented goal predicates as supported (26), unsupported (4), or unstable (3) under the pinned backend. The NL→JGEX baseline employs a propose-validate pipeline: the LLM is prompted with the reference card and 20 in-context examples to generate a JGEX program, which is then extracted and validated end-to-end by Newclid's JGEXProblemBuilder and GeometricSolverBuilder. The key insight is that for a low-resource, version-sensitive DSL, the effective interface is not recoverable from scattered public examples alone; a compact, version-pinned reference card and executable conformance evidence are necessary to make the benchmark auditable and the DSL learnable by both humans and models.

## Results

On the NL→JGEX formalization task (107 dataset rows, 105 unique problems), the GPT-5.4 Pro pipeline achieves 49.5% pass@1 end-to-end executability overall, rising to 89.8% (53/59) conditional on non-truncated API responses. The dominant failure mode is API truncation (44.9%), not formalization error: IMO problems show the lowest raw executability (9.4%) but also the highest truncation rate (87.5%), while Euclid problems reach 72.4% executability with only 20.7% truncation. The JGEXDiv corpus itself covers 137 problems spanning 51.4% of admissible construction-pattern bins, all 26 supported goal predicates, and 85/89 (≈95.5%) construction definitions under pinned Newclid v3.0.1.

## Baselines & Comparisons

This is a position paper with a single NL→JGEX baseline pipeline rather than a multi-method comparison, so no competing baselines are benchmarked head-to-head. The closest comparative evidence is the cross-tool predicate audit: four documented JGEX predicates (DIFFERENT, N_COLLINEAR, N_PERPENDICULAR, N_PARALLEL) execute end-to-end under pinned Newclid v3.0.1 but are not recognized by Yuclid, while four predicates (A_COMPUTE, L_COMPUTE, LENGTH_EQUATION, ANGLE_EQUATION) are unsupported under Newclid itself and three (R_COMPUTE, PYTHAGOREAN_PREMISES, PYTHAGOREAN_CONCLUSIONS) are classified as unstable due to lack of accessible minimal examples. A limited truncation-mitigation probe (setting reasoning.effort='low') recovered only 9/48 previously truncated rows, with zero recovery on IMO problems, indicating that the formalization bottleneck for long statements is robust to modest decoding changes. The paper positions its contribution as infrastructure (executable interface contract, predicate support matrix, conformance suite) rather than a state-of-the-art solver, and explicitly notes that the 49.5%/89.8% numbers measure the NL→formal translation bottleneck, not geometry-solving ability.

## Relation to Prior Work

This paper carves new methodological ground by proposing an 'executable interface contract'—a four-component standard (executable formalizations, version pinning, predicate-level conformance evidence, and documented curation decisions) for benchmarks built around formal DSLs. It draws on the JGEX language (Ye et al., 2008), the Newclid prover (Sicca et al., 2024), and the reproducibility-infrastructure tradition in data science (Donoho, 2024), but departs from prior geometry benchmarks (AlphaGeometry, TongGeometry, GenesisGeo) and Lean benchmarks (LeanEuclid, LeanGeo, miniF2F) by making executable conformance evidence and systematic curation provenance first-class release requirements rather than implicit assumptions. The NL→JGEX baseline repurposes standard few-shot LLM prompting with a compact reference card, but the key departure is validating outputs against a pinned solver backend rather than comparing to a reference string.

## Why It Matters / Open Questions

The paper identifies a concrete, underappreciated failure mode in formal-DSL benchmarking: documented predicates that silently fail or behave differently across solver backends (e.g., four JGEX predicates executable in Newclid but unrecognized by Yuclid), which can bias what is actually being measured. The finding that API truncation—not formalization errors—dominates NL→JGEX failures (44.9% vs. 5.6%) reframes the bottleneck for low-resource DSL generation and suggests that prompt-budget management may matter more than model capability in this regime. Limitations include version-dependent executability, only 51.4% construction-pattern coverage, and an evaluation that measures executability rather than semantic faithfulness; open questions include whether the executable-interface-contract framework generalizes beyond geometry to other formal DSLs and how to maintain conformance evidence across rapid tool evolution.
