## Problem

Existing code security benchmarks like BAXBENCH require security experts to manually design scenarios, write functional tests, and craft reproducible end-to-end exploits, making them slow to extend, vulnerable to training-data contamination, and unable to scale in difficulty as LLMs improve. This paper asks whether the entire benchmark-construction pipeline can be automated while preserving the soundness guarantees of expert-written tests and exploits.
![Teaser figure](../imgs/ICML20260129/cropped_page1_idx0.webp)

## Input / Output

The pipeline takes a target number of API endpoints, a list of existing scenario names (for novelty enforcement), and a list of vulnerability names as input, and produces a complete BAXBENCH-style task: a natural-language description, a full OpenAPI 3.0 specification, a suite of functional tests, and a set of end-to-end security exploits classified by CWE. All outputs are validated through execution: functional tests must pass on at least one reference solution, and each exploit must be confirmed via a contrastive pair (one vulnerable, one patched solution) before acceptance. The resulting scenario is framework-agnostic, with tests and exploits interacting only through the REST API, file system, database, and resource monitors inside an isolated Docker container.

## Method

AUTOBAXBUILDER is a three-step agentic pipeline driven by an orchestration LLM (GPT-5) that iteratively refines outputs using execution feedback from multiple solution LLMs. Step 1 generates a novel OpenAPI scenario and initial reference solutions. Step 2 constructs functional tests, then alternates between REFINESOLUTIONS (fixing reference solutions using only execution logs, hiding test code to prevent overfitting) and REFINETESTS (producing per-solution correctness verdicts merged into a global consensus to decide whether to refine tests or solutions), looping until convergence. Step 3 identifies target vulnerabilities, generates exploits, and validates each via REFINEEXPLOIT: the orchestration LLM executes the exploit on a reference solution, judges correctness, then constructs a contrastive solution by patching or introducing the vulnerability from its natural-language description alone (without seeing exploit logic); the exploit is accepted only if it correctly flags the vulnerable solution as insecure and the patched solution as secure. Guardrails include YAML/Python compilation checks, regex validation, pseudorandom flags for programmatic exploit verification, and self-criticism loops, with a maximum of 5 refinement iterations per phase.

## Results

On AUTOBAXBENCH (40 scenarios across EASY/MEDIUM/HARD splits), the strongest model CLAUDE-4.5 SONNET achieves only 36% sec_pass@1 overall and 25% on the HARD split, while reaching 82.7% pass@1, revealing a large gap between functional correctness and security. GEMINI 3 PRO, GROK 4, and CLAUDE-3.7 SONNET follow with ~28% overall sec_pass@1. Validation against BAXBENCH shows 80.9% agreement on functional tests and the same model ranking, while AUTOBAXBUILDER-generated exploits flag more than twice as many solutions as insecure compared to the original human-written exploits, with only 1 unsound exploit found out of 71 manually audited.

## Baselines & Comparisons

The primary comparison is between AUTOBAXBUILDER-generated tests/exploits and the original expert-written tests/exploits of BAXBENCH on the same 28 scenarios. On functional correctness (pass@1), the two test suites show high agreement (80.9% match) and produce nearly identical model rankings, confirming that AUTOBAXBUILDER faithfully reproduces expert-level functional testing. On security (sec_pass@1), AUTOBAXBUILDER-generated exploits flag more than twice as many solutions as insecure compared to BAXBENCH's human-written exploits, primarily because they cover additional CWEs (e.g., OS Injection in FileSearch, FrameExtract, ZipToTxt where BAXBENCH only tests Path Traversal) and use more diverse attack vectors (e.g., multiple SVG payloads for XSS vs. a single HTML payload). Manual auditing of all 71 generated exploits found only 1 unsound exploit (98.6% soundness rate). The main gap is 164 false negatives out of 2227 correct solutions, mostly attributable to AUTOBAXBUILDER not probing for plaintext password storage (CWE-522), a check that BAXBENCH performs via direct database inspection. Overall, AUTOBAXBUILDER tightens the security upper bound reported by BAXBENCH while maintaining equivalent functional test quality.

## Relation to Prior Work

This paper directly extends BAXBENCH (Vero et al., 2025a), which established the paradigm of jointly evaluating functional correctness and security of LLM-generated web backends via end-to-end exploits, by automating the previously manual process of constructing new benchmark scenarios. Methodologically, it draws on LLM-based test generation (Kang et al., 2023; Chen et al., 2022) and LLM-driven exploit construction (Zhang et al., 2024; Deng et al., 2024), but departs from repository-mining approaches (Jimenez et al., 2024; Mei et al., 2024) by generating scenarios entirely from scratch, avoiding contamination from disclosed CVEs. The iterative refinement loop with contrastive verification (building both vulnerable and patched solutions to validate exploits) is a key methodological contribution not present in prior benchmark-generation work.

## Why It Matters / Open Questions

This work addresses a critical scalability bottleneck: security benchmarks inevitably contaminate training data and must be continuously extended, yet manual construction costs ~3 hours per scenario. By reducing this to ~15 minutes of verification at under $4 per task, AUTOBAXBUILDER enables ongoing, contamination-free evaluation as LLMs improve. The finding that even the strongest model (Claude 4.5 Sonnet) achieves only 25% sec_pass@1 on the HARD split, while maintaining 83% pass@1, underscores that the security gap in LLM code generation remains substantial and is not an artifact of benchmark difficulty. Open questions include extending beyond REST-based web backends to other API paradigms, reliably handling CWE-400 (resource exhaustion), and whether the pipeline can generate tasks that challenge even future SOTA agents on long-horizon security reasoning.
