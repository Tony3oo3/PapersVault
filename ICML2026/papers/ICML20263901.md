## Problem

Existing sub-agent-as-tools systems degenerate into two limited patterns: context-isolated threads that lack on-demand specialization, or static pre-defined roles that require heavy human engineering and cannot cover the dynamically emerging variety of subtasks in open environments. This paper addresses the absence of a dynamic, unified abstraction that allows sub-agents to be created and tailored at runtime to match the specific capabilities and context needs of each subtask.
![Teaser figure](../imgs/ICML20263901/cropped_page1_idx1.webp)

## Input / Output

The system receives a user goal (a GAIA question, a SWE-Bench GitHub issue, or a Terminal-Bench shell task) and interacts with an environment exposing actions such as shell commands, web operations, or code edits. The orchestrator's action space is restricted to two structured outputs: Delegate(Φ), which instantiates a sub-agent parameterized by a four-tuple of instruction, curated context, tool subset, and model, and Finish(y), which terminates with a final answer. Sub-agents return structured observations (concise result summaries, relevant artifacts, and error logs) that are integrated into the orchestrator's evolving state for the next decision step.

## Method

AORCHESTRA introduces a unified four-tuple agent abstraction Φ = (Instruction, Context, Tools, Model) that explicitly separates working memory from capabilities, treating every agent as a dynamically instantiable unit rather than a static entity. A dedicated orchestrator operates exclusively over Delegate(Φ) and Finish(y) actions—never directly executing environment actions—by decomposing the overall goal into subtasks and synthesizing the appropriate tuple for each delegation, including curating task-relevant context (neither empty nor full-history), selecting tool subsets, and routing to different models per subtask. The orchestration policy is learnable along two complementary axes: supervised fine-tuning via behavior cloning on expert trajectories improves subtask decomposition and tuple synthesis, while iterative in-context learning optimizes the orchestrator's instruction prompt for cost-aware model routing, yielding Pareto-efficient performance-cost trade-offs. Sub-agents are fully pluggable, supporting diverse execution backends (ReAct-style, Mini-SWE-style) without modifying the orchestrator, making the system framework-agnostic.

## Results

On GAIA, AORCHESTRA with Gemini-3-Flash achieves 80.00 pass@1 and 86.06 pass@3, surpassing the strongest baseline (OpenHands at 66.06) by 13.94 points. On Terminal-Bench 2.0, it reaches 52.86 pass@1, an 18.57-point gain over the best baseline (Mini-SWE at 34.29). On SWE-Bench-Verified, it attains 82.00 pass@1, competitive with Mini-SWE (84.00) while outperforming all other baselines. Overall, AORCHESTRA achieves a 16.28% relative improvement over the strongest baseline when paired with Gemini-3-Flash, with an average pass@1 of 71.62 versus 49.49 for the best competing framework.

## Baselines & Comparisons

AORCHESTRA consistently outperforms all four baselines on GAIA and Terminal-Bench 2.0 with Gemini-3-Flash. Against ReAct (49.09 GAIA, 28.57 TB, 64.00 SWE), AORCHESTRA gains +30.91, +24.29, and +18.00 points respectively. Against OpenHands (66.06, 31.43, 48.00), the gains are +13.94, +21.43, and +34.00. Against Mini-SWE (58.18, 34.29, 84.00), AORCHESTRA leads on GAIA (+21.82) and Terminal-Bench (+18.57) but trails by 2.00 points on SWE-Bench-Verified (82.00 vs. 84.00), the only benchmark where a baseline edges it out. Against Claude Code (32.86 TB, 22.00 SWE; not evaluated on GAIA), AORCHESTRA achieves +19.99 and +60.00 points. The advantage is most pronounced on GAIA and Terminal-Bench, where dynamic sub-agent creation with curated context and tailored tool sets provides the largest benefit over fixed-workflow or context-isolation designs.

## Relation to Prior Work

This paper carves new ground within the sub-agent-as-tools paradigm by introducing a unified four-tuple abstraction (Instruction, Context, Tools, Model) that treats each sub-agent as a dynamically instantiable unit rather than a fixed role or isolated context thread. It departs from context-isolation approaches (THREAD, Context-Folding) that lack specialization, and from static-role systems (Claude Code, Chain-of-Agents) that require heavy human engineering, by having a dedicated orchestrator concretize the tuple at runtime. The learnable-orchestrator component draws on behavior cloning (SFT) and iterative prompt optimization (ICL), but applies them specifically to the structured delegation interface rather than to end-to-end agent policies.

## Why It Matters / Open Questions

The four-tuple interface offers a clean, framework-agnostic compositional recipe for agent capabilities that could become a standard abstraction for multi-agent system design, and the demonstration that orchestration quality is learnable via SFT on a small model (Qwen3-8B) lowers the barrier to deploying specialized orchestrators. The Pareto cost-performance results from ICL-based model routing are practically relevant for production deployments where token budgets matter. Open questions include whether the four-tuple is expressive enough for deeply nested or adversarial multi-agent settings, how the approach scales beyond the three tested benchmarks, and whether the orchestrator's learned policies transfer across domains without retraining.
