## Problem

Agentic batch inference causes sustained, cumulative KV cache pressure that triggers a previously under-characterized pathology called middle-phase thrashing, where cache hit rates collapse and throughput degrades severely long before GPU memory is physically exhausted. Existing request-level cache management (LRU eviction, prefix caching, CPU offloading) is reactive and stateless, failing to account for the long-lived, asynchronous nature of agent execution where paused agents' KV cache is aggressively evicted and must be expensively recomputed upon resumption.

## Input / Output

CONCUR operates as a lightweight middleware between agent execution frameworks and LLM serving engines (e.g., SGLang), consuming real-time KV cache usage (U_t) and cache hit rate (H_t) signals from the serving engine alongside incoming agent generation requests. It produces a regulated concurrency window W_t and per-agent admit/pause/resume decisions that gate which agents may issue generation steps. Critically, the control operates at agent granularity rather than request granularity, preserving execution state for paused agents and treating the agent's accumulated KV cache footprint as the unit of resource accounting.

## Method

CONCUR adapts the Additive Increase Multiplicative Decrease (AIMD) algorithm from TCP congestion control to agent-level admission, drawing an analogy between GPU-resident KV cache and network bandwidth as a shared finite resource whose overcommitment degrades efficiency before physical exhaustion. The control law (Eq. 1) uses two feedback signals: KV cache usage as a proactive congestion indicator and cache hit rate as a reactive failure indicator. When usage is below a low threshold, the window additively increases (α=2) to probe available capacity; when usage exceeds a high threshold AND hit rate drops below a threshold, the window multiplicatively decreases (β=0.5) to rapidly exit the thrashing regime. The multiplicative decrease is specifically motivated by the O(L²) recomputation cost of cache thrashing, which imposes a convex penalty that demands exponential recovery. The controller exposes three minimal primitives—admit, pause, resume—that operate on agent lifecycles at well-defined boundaries between generation steps and tool execution, avoiding interruption of in-flight computation while bounding aggregate KV cache pressure.

## Results

CONCUR achieves up to 4.09× end-to-end latency reduction on Qwen3-32B (1480s → 362s at batch 256, TP=8) and up to 1.90× on DeepSeek-V3 (3877s → 2043s at batch 40, TP=16) compared to the SGLang baseline. Across all six model/parallelism configurations tested, CONCUR consistently achieves the lowest latency, with gains widening as effective per-GPU concurrency increases. KV cache hit rates under CONCUR remain substantially higher than SGLang (e.g., 73.36% vs. 35.41% at batch 40 on DeepSeek-V3), confirming that the throughput gains stem from preventing middle-phase thrashing rather than from offloading.

## Baselines & Comparisons

CONCUR outperforms all three baselines across every configuration tested. Against vanilla SGLang (request-level batching with LRU eviction), CONCUR reduces latency by up to 4.09× on Qwen3-32B and 1.90× on DeepSeek-V3, with the gap widening at higher effective concurrency where SGLang suffers severe middle-phase thrashing. Against SGLang with fixed request-level admission control, CONCUR wins by a large margin (e.g., 362s vs. 2049s on Qwen3-32B TP=8), because request-level caps lack visibility into accumulated agent-level KV cache footprints and delay execution until cached state is already evicted. Against SGLang + HiCache (CPU offloading), CONCUR also wins in all configurations (e.g., 362s vs. 976s on Qwen3-32B TP=8; 2043s vs. 2320s on DeepSeek-V3 batch 40), as PCIe contention under high concurrency negates HiCache's higher hit rates. The paper further shows that no fixed admission level (30, 32, 64, or 128) matches CONCUR's adaptive policy, which achieves 1.5–2.9× lower latency than the best static setting.

## Relation to Prior Work

CONCUR draws a direct conceptual lineage from TCP congestion control (AIMD, Chiu & Jain 1989; Floyd 2003), repurposing a 35-year-old networking algorithm to regulate agent admission in LLM serving. It departs from the dominant request-level scheduling paradigm in engines like SGLang (Zheng et al. 2024) by elevating the scheduling unit to the agent, and from reactive KV cache management (LRU eviction, CPU offloading via HiCache/Mooncake) by introducing proactive admission control. The paper also positions itself against application-centric serving systems (Parrot, Teola, Autellix) that reorder requests but still assume eviction can handle memory pressure, arguing that in agentic batch inference, over-admission causes thrashing regardless of scheduling order.

## Why It Matters / Open Questions

The identification of middle-phase thrashing as a distinct, dominant pathology (consuming ~49% of end-to-end latency) reframes how practitioners should think about agentic batch inference: the bottleneck is not peak memory but the temporal dynamics of asynchronous agent progress. The 4.09× speedup on Qwen3-32B is practically significant for agentic RL rollouts, which dominate end-to-end training time. Open questions include whether the fixed AIMD parameters generalize across vastly different agent workloads (varying tool-call frequencies, context growth rates), how CONCUR interacts with disaggregated memory architectures (e.g., TokenLake), and whether the approach extends to online (latency-sensitive) agentic serving where pausing agents is less acceptable.
