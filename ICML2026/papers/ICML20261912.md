## Problem

Existing LLM serving systems assume spatially uniform and temporally stable workloads, deploying homogeneous, static model configurations across all replicas. Real-world workloads, however, exhibit substantial spatial heterogeneity (mixed compute-intensive short-output and memory-intensive long-output requests) and temporal heterogeneity (shifting composition and arrival rates over time), causing significant performance degradation when a single static deployment must serve all workload types simultaneously.
![Teaser figure](../imgs/ICML20261912/cropped_page0_idx0.webp)

## Input / Output

The system consumes historical workload traces (input/output sequence lengths and arrival rates from the Azure Public Dataset), cluster GPU topology (e.g., 8×H100 servers with NVLink 400 GB/s intra-machine and InfiniBand 200 GB/s inter-machine), and model configuration to produce a per-replica serving strategy specifying GPU count, parallelism strategy (TP/PP), and per-workload-type request routing fractions. Workload types are defined by k-means clustering on (input_len, output_len) pairs, and the LSTM predictor outputs per-type request counts for the next 1-minute window using a 50-minute lookback. The switch planner outputs a GPU-to-GPU parameter transfer plan that specifies which source device sends which shard to which target device, prioritizing intra-machine NVLink paths.

## Method

OSERVE's core is a two-level workload-aware scheduling algorithm. The lower level formulates workload assignment as a max-flow problem on a directed flow network where edge capacities are normalized via the least common multiple of per-workload-type processing rates, solved with the preflow-push algorithm to maximize throughput under workload-demand, edge-capacity, and node-capacity-sharing constraints. The upper level performs flow-network-guided generation: it iteratively identifies bottleneck (saturated) and under-utilized replicas from the flow solution, reallocates GPUs between them, and enumerates parallelism strategy combinations to find the highest-throughput configuration, terminating when no further improvement is found over 20 iterations. For temporal adaptation, an LSTM predictor (trained on k-means-differentiated per-type arrival counts) forecasts the next minute's workload, and an ad hoc model switching mechanism transfers parameters between GPUs over NVLink/InfiniBand using a greedy load-balancing algorithm that prioritizes intra-machine sources, reducing switch time from ~50 s (reload) to ~10 s.

## Results

OSERVE improves P99 tail latency and system throughput by up to 2.0× (average 1.5×) over vLLM (static) and by up to 1.5× (average 1.3×) over vLLM (reload) across OPT-30B/66B and Llama-30B/70B on 8–32 H100 GPUs. Against Llumnix, OSERVE achieves 1.32–1.51× gains in P99 latency and throughput, and outperforms Dynamo+vLLM by 12–20% in end-to-end performance. The ad hoc model switching mechanism reduces switching overhead from >50 s (naive reload) to ~10 s, cutting P99 latency by up to 17% under highly fluctuating workloads. The LSTM workload predictor achieves a 5.045% RRMSE with <30 ms inference time over 1-minute prediction horizons.

## Baselines & Comparisons

OSERVE consistently outperforms all four baselines across every evaluated configuration. Against vLLM (static), which uses a fixed parallelism strategy, OSERVE gains up to 2.7× at specific time spans (e.g., P1/P6 in Trace 1 where optimal DP/TP ratios shift), with an average 1.5× improvement in both P99 latency and throughput. Against vLLM (reload), which can switch deployments but uses homogeneous replicas, OSERVE's heterogeneous deployment and workload-aware assignment yield up to 1.5× (avg 1.3×) gains, with the largest gap at P5 in Trace 2 where OSERVE deploys four differently-configured replicas (TP=4/PP=2, TP=2/PP=2, TP=2/PP=1, TP=2/PP=1) versus a uniform (DP=4, TP=2, PP=2). Against Llumnix, which migrates requests but does not reconfigure parallelism, OSERVE wins by 1.32–1.51× because it co-optimizes deployment and scheduling. Against Dynamo+vLLM, which autoscales prefill/decode workers but fixes per-worker parallelism, OSERVE improves end-to-end performance by 12–20% by dynamically adjusting tensor and pipeline parallelism to match the workload mix.

## Relation to Prior Work

OSERVE builds on the LLM serving infrastructure established by vLLM (PagedAttention), AlpaServe (model parallelism), and Splitwise (phase splitting), and borrows the one-time profiling methodology from Vidur for capacity estimation. It departs from prior systems (vLLM, Llumnix, Dynamo) that assume homogeneous, static model deployments by introducing heterogeneous replica configurations with per-replica parallelism strategies, formulated as a two-level flow-network optimization. The temporal adaptability component draws on LSTM-based time-series forecasting and k-means workload clustering, while the ad hoc model switching leverages GPU interconnects (NVLink/InfiniBand) for parameter transfer rather than disk reloading—a practical departure from the reload-from-scratch paradigm used by vLLM (reload).

## Why It Matters / Open Questions

The 2× end-to-end improvement over state-of-the-art serving systems addresses a real and growing gap as LLM workloads become increasingly heterogeneous in both composition and temporal dynamics. The clean ablation decomposing gains into heterogeneous deployment (34% P99 improvement) and workload assignment (additional 64%) provides actionable guidance for practitioners. Open questions remain around extension to heterogeneous GPU types, MoE models with expert parallelism, disaggregated prefill/decode architectures, and fault tolerance under heterogeneous replica management—limitations the authors acknowledge but leave for future work.
