## Problem

Locating the files and functions that need modification in large software repositories is difficult because existing LLM agents rely on multiple high-level retrieval tools (e.g., SearchClass, SearchMethods, GetImports) that do not reflect actual code execution semantics and amplify error propagation across tool chains. Moreover, prior localization agents require distillation from closed-source teacher models as a warmup before reinforcement learning, limiting accessibility and scalability.
![Teaser figure](../imgs/ICML20265776/cropped_page0_idx0.webp)

## Input / Output

The agent receives a repository, a natural-language issue description, and an explicit entry point (file path plus entry function) that serves as the starting context for navigation. It outputs a discrete set of file::function pairs identifying the code regions requiring modification, which enables verifiable string-level evaluation compatible with scalable RL training. The agent interacts with the repository exclusively through a single 'jump' tool that resolves a symbol's definition via a language server (Pyright), returning the definition code snippet and its file path.

## Method

RepoNavigator replaces multi-tool pipelines with a single execution-aware 'jump' tool that resolves symbol definitions using a language server's static analysis (AST parsing, LEGB scope resolution, MRO-based attribute lookup, and import dependency graph traversal), reflecting how code actually executes rather than high-level abstractions like classes or inheritance. The agent follows a ReAct-style loop (reason → act → observe), where at each step it either generates natural-language reasoning or emits a JSON-formatted jump call, constrained by grammar-enforced decoding. Training uses GRPO (Group Relative Policy Optimization) directly from the pretrained Qwen2.5 model without any distillation or SFT cold-start, with a hybrid reward combining DICE score on predicted locations (λ=0.5) and tool-calling success rate to provide dense intermediate supervision. The single-tool design reduces the action space branching factor, narrows the agent's access scope to the transitive closure of symbol references from the entry point, and empirically outperforms multi-tool baselines at every model size (7B, 14B, 32B) on both SWE-bench_Verified and SWE-bench_Pro.

## Results

On SWE-bench_Verified, RepoNavigator trained with GRPO achieves function-level Sample-F1 of 27.49 (7B), 29.23 (14B), and 34.09 (32B), with corresponding IoU scores of 26.43, 26.84, and 32.30. The 7B model outperforms all 14B baselines (best: OrcaLoca at 22.77 Sample-F1), the 14B model surpasses all 32B baselines (best: OrcaLoca at 28.72), and the 32B model exceeds GPT-5 (31.17 Sample-F1) and Claude 4.5-Sonnet (43.62) on IoU. On SWE-bench_Pro, the same pattern holds, with the 32B GRPO model reaching 20.72 function-level Sample-F1 and 57.57 file-level Sample-F1.

## Baselines & Comparisons

RepoNavigator (GRPO) outperforms all five baselines on both Sample-F1 and IoU across all model sizes. Against Agentless, the gap is largest at 7B (27.49 vs. 15.31 function-level Sample-F1, +12.2 points) and 32B (34.09 vs. 27.33, +6.8 points). Against CoSIL, RepoNavigator leads by 14.6 points in function-level Sample-F1 at 7B (27.49 vs. 12.90). Against LocAgent, the advantage is 14.8 points at 7B (27.49 vs. 12.71) and 12.6 points at 32B (34.09 vs. 21.48). Against OrcaLoca (the strongest training-free baseline), RepoNavigator+GRPO leads by 5.8 points at 7B (27.49 vs. 21.70) and 5.4 points at 32B (34.09 vs. 28.72). Against RepoSearcher (Distillation+GRPO), RepoNavigator wins on Sample-F1 and IoU at all sizes (e.g., 34.09 vs. 29.11 at 32B) but trails on recall (33.71 vs. 69.50), which the authors attribute to RepoSearcher's multi-tool design producing more (but less precise) predictions.

## Relation to Prior Work

This paper builds on the ReAct reason-act-observe loop and the GRPO reinforcement learning algorithm, but departs sharply from prior repository-level localization agents (LocAgent, CoSIL, OrcaLoca, RepoSearcher) in two key ways. First, it replaces the 3–5 heterogeneous retrieval tools (SearchClass, SearchFunction, GetImports, etc.) with a single execution-aware 'jump' tool grounded in language-server symbol resolution, arguing that high-level abstractions like classes and inheritance disappear at runtime and do not reflect actual code execution flow. Second, it is the first localization agent trained end-to-end with RL directly from a pretrained open-source model, eliminating the distillation-from-closed-source-teacher warmup that both RepoSearcher and LocAgent require.

## Why It Matters / Open Questions

The finding that a single, structurally grounded tool outperforms multi-tool pipelines challenges the prevailing assumption in agent design that more tools yield more capability, and the demonstrated cost efficiency (2.68K average tokens vs. 8–49K for baselines) makes the approach practically attractive for large-scale deployment. However, the work is limited to Python repositories and a single language server (Pyright), leaving open whether the single-tool principle generalizes to languages with more complex runtime semantics (dynamic dispatch, monkey-patching, metaprogramming). Extending RepoNavigator beyond localization to full issue resolution, and validating the approach across multiple programming languages, are the most natural next steps.
