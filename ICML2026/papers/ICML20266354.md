## Problem

Compound agentic AI systems have outgrown monolithic foundation models, yet the supporting software stack remains fragmented: each orchestration framework embeds its own implicit runtime for state, memory, budgets, and guardrails, making behavior non-portable and governance brittle. Protocol efforts like MCP and A2A standardize connectivity but do not define system-layer contracts for reliable, governable execution. The paper argues the field needs a Foundation Model Operating System (FMOS) that virtualizes FM interactions, analogous to how virtual machines abstract physical hardware.

## Input / Output

The FMOS intercepts agent requests (prompts, tool calls, memory operations) at virtual model endpoints, MCP services, and framework hooks, consuming application-level context policies (e.g., offload thresholds, retention rules) alongside physical FM resources and trust/safety budgets. By default, requests traverse a lightweight fast path with minimal interception; learned 'traps' (triggered by uncertainty, policy sensitivity, or budget pressure) escalate to a deliberative slow path that activates targeted knowledge augmentation, model routing, or verification. Outputs include virtualized FM responses, system-level routing and scheduling decisions, context management actions, verification outcomes, and immutable causal traces with checkpoint/replay support for deterministic debugging.

## Method

FMOS introduces a Virtual Foundation Model (VFM) as a stable interface that presents applications with the illusion of a dedicated, trustworthy FM with effectively unbounded capabilities, while three cooperating subsystems mediate access to physical FMs: a Data Agent managing hierarchical context/memory with learnable paging and retrieval policies, an FM Composition Optimizer performing runtime model routing, caching, and composition under quality-latency-cost constraints, and a Trust & Reasoning Agent governing escalation between fast heuristics and deliberative verification. The architecture is grounded in a formal virtualizability condition (A_sen ⊆ A_priv) derived from Popek & Goldberg, where sensitive operations (those affecting shared budgets, memory, or trust state) must trap to the FMOS control plane while innocuous operations execute natively on the fast path. Self-evolution operates through non-parametric adaptation: the FMOS learns from longitudinal interaction traces to update prompts, routing policies, memory schemas, and verification strategies, with improvements propagated safely via versioning, canary deployments, and rollback. A global constrained optimization (formalized via Lagrangian shadow prices) coordinates coupled resource budgets and risk constraints across applications, enabling co-optimization that fragmented stacks cannot achieve.

## Results

As a position paper, FMOS does not report main experimental results or a primary comparison table. The only quantitative evidence appears in Appendix B, where τ-bench (Retail) success rates (Pass^1) are plotted against reasoning-token budgets for four LLMs to motivate the need for a system-level reasoning knob. Key findings: gemini-2.5-flash improves from 0.49 (no reasoning) to 0.61 at a 4096-token budget but drops to 0.57 at 16,384 tokens; Qwen3-235B-A22B degrades from 48.3% to 43.1% when reasoning is enabled; and o4-mini's 'high' effort setting raises cost by 50% without improving performance. These results illustrate that uncontrolled reasoning budgets are a system-level problem that FMOS's Trust & Reasoning hierarchy aims to solve.

## Baselines & Comparisons

This is a position paper and does not benchmark FMOS against competing methods; no direct performance comparisons are made. Instead, the paper positions FMOS relative to existing systems by identifying their gaps: AIOS (Mei et al., 2024) and MemGPT (Packer et al., 2023) address scheduling or memory virtualization in isolation but lack a unified virtualization boundary governing knowledge, reasoning, verification, and trust jointly. MCP and A2A protocols standardize tool/agent connectivity but intentionally stop short of specifying execution semantics, state persistence, resource governance, or trust enforcement. Agent frameworks (LangChain, AutoGen, Claude Code) embed framework-specific runtimes that fix execution semantics, making behavior non-portable across harnesses. The paper argues that no single existing system provides the stable VFM interface, learned trap-based escalation, and cross-application co-evolution that FMOS would offer, but it does not quantify these gaps with head-to-head experiments.

## Relation to Prior Work

This paper formalizes the 'LLM as OS' metaphor (popularized by Karpathy) into a concrete system architecture by adapting the Popek–Goldberg virtualizability condition (sensitive ⊆ privileged operations) to foundation-model operations, proposing a Foundation Model Operating System (FMOS) that exposes Virtual Foundation Models (VFMs) to applications. It extends and unifies prior partial efforts—MemGPT's memory virtualization, AIOS's agent scheduling, Llumnix's serving-level orchestration, and agent filesystems (AgentFS, Nexus)—arguing that none provides the missing unified virtualization boundary jointly governing knowledge, reasoning, verification, and trust. It positions itself as complementary to (not a replacement for) MCP and A2A protocols, which handle connectivity but deliberately stop short of execution semantics and governance.

## Why It Matters / Open Questions

If the field converges on this framing, FMOS could become the infrastructure standard for compound agentic systems, enabling portable agent logic, shared governance, and system-level self-evolution without per-framework reimplementation. Key open questions include: how to learn and validate trap policies (the sensitive/innocuous partition is 'adaptive at runtime' but the learning mechanism is underspecified), how to ensure self-evolution doesn't introduce uncontrolled nondeterminism in safety-critical deployments, and whether the virtualization analogy holds when FM 'instructions' are far less rigid than hardware ISAs. As a position paper with no prototype or benchmark, its impact depends on whether the community adopts the VFM abstraction and builds reference implementations.
