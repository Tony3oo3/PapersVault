## Problem

Self-play for LLM code generation has been blocked by the brittleness of unit-test-based verification: tests cover only a limited set of cases, allowing incorrect programs to pass and propagate errors across training iterations. This paper asks whether formal verification, which provides a sound (though incomplete) correctness guarantee over all inputs, can serve as the reliable reward signal needed to make proposer-solver self-play work in a realistic, Turing-complete coding language.

## Input / Output

The solver receives a Verus formal specification — a Rust function signature with preconditions (requires) and postconditions (ensures) that mathematically describe all permitted inputs and the required output behavior — and must produce a Rust implementation plus proof annotations (e.g., loop invariants) that the SMT-backed Verus verifier accepts. The proposer takes difficulty-labeled example specs sampled from the growing dataset and outputs new specs at a target difficulty class (Easy/Medium/Hard/Impossible), which are then parsed, deduplicated, and filtered through a spec-compiler check before entering the training pool.

## Method

PSV is an iterative self-play loop alternating between a difficulty-aware proposer and a solver trained by rejection fine-tuning (RFT). At each iteration, the solver samples k_trn=10 candidate solutions per spec at temperature 0.8; only solutions that pass the Verus SMT verifier are retained for SFT (cross-entropy loss on verified solutions only, re-initialized from the base model each iteration). The proposer uses in-context learning: it samples 12 problems from the cumulative dataset, labels each by the solver's current pass rate into four difficulty bins, and is prompted to generate B new specs at uniform difficulty targets (3 per class). The key design choices — formal verification as a sound reward signal, difficulty-aware conditioning of the proposer, and dynamic refreshing of the proposer's in-context examples for diversity — are each shown to be essential via ablations, with removing verification causing ~50% relative drops and removing diversity causing ~11% drops in average pass@k.

## Results

In the test-time training setting, PSV-VERUS achieves 65.63% pass@1 on Dafny2Verus, 36.78% on MBPP, and 19.07% on HumanEval, substantially outperforming both AlphaVerus (24.06%, 6.48%, 7.24%) and iterative RFT (34.46%, 3.83%, 5.56%). In the transfer learning setting (training on Dafny2Verus, evaluating on held-out benchmarks), PSV-VERUS reaches 25.25% pass@1 on MBPP and 16.18% on HumanEval, a 3.9× and 2.2× improvement over AlphaVerus respectively. Averaged across all benchmarks and metrics in the TTT setting, PSV-VERUS obtains 48.12% versus 25.43% for RFT and 25.55% for AlphaVerus (≈1.9× mean improvement).

## Baselines & Comparisons

PSV-VERUS outperforms both baselines across all three benchmarks and all pass@k metrics in both the transfer learning and test-time training settings. Against AlphaVerus (the previous SOTA for verified code generation, re-implemented on the same Qwen2.5-Coder-3B base model), PSV-VERUS achieves a 2.73× improvement on Dafny2Verus pass@1 (65.63% vs. 24.06%), a 5.68× improvement on MBPP pass@1 (36.78% vs. 6.48%), and a 2.63× improvement on HumanEval pass@1 (19.07% vs. 7.24%) in the TTT setting. Against iterative RFT (expert iteration without proposing new problems), the gains are even larger on the harder benchmarks: 9.61× on MBPP pass@1 (36.78% vs. 3.83%) and 3.43× on HumanEval pass@1 (19.07% vs. 5.56%), while on Dafny2Verus the improvement is 1.90× (65.63% vs. 34.46%). In the transfer learning setting, PSV-VERUS beats AlphaVerus by 3.90× on MBPP and 2.24× on HumanEval pass@1, and beats RFT by 2.30× and 1.47× respectively. The consistent wins across all settings indicate that the self-play loop (proposing new specifications + difficulty-aware curriculum) provides a substantial advantage over both static prompting and fixed-corpus expert iteration.

## Relation to Prior Work

This paper extends the proposer-solver self-play paradigm (from AlphaZero-style game playing and recent LLM self-play work like Absolute Zero and STP) to verified code generation, where the critical enabler is replacing brittle unit-test-based verification with SMT-backed formal verification (Verus). The solver training algorithm is rejection fine-tuning (RFT) from Singh et al. (2024), and the seed corpus and evaluation setup follow AlphaVerus (Aggarwal et al., 2024). The key departure from prior verified-code-generation work (AutoVerus, SAFE) is the introduction of a difficulty-aware, diversity-preserving proposer that co-evolves with the solver, creating a true self-play loop rather than one-shot data synthesis on a fixed problem set.

## Why It Matters / Open Questions

This work demonstrates that self-play can succeed in a realistic, Turing-complete code generation setting by leveraging the soundness guarantee of formal verification to prevent error propagation and reward hacking—addressing the central obstacle that has limited self-play to toy or easily-verifiable domains. The clean scaling behavior with both question budget and iteration count, plus the transfer of verified solutions to models up to 10× larger, suggests a viable path toward data-free curriculum expansion. Open questions include whether the approach generalizes beyond Verus/Rust to other verification frameworks, whether on-policy RL (e.g., GRPO) can replace RFT given the verifier's incompleteness, and whether the 3B-scale results hold at the frontier model scale where self-play gains might be smaller relative to already-strong base capabilities.
