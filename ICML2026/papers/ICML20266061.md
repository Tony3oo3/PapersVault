## Problem

Vibe coding—where users prompt LLM agents to implement features with minimal code review—is increasingly adopted in production, yet no benchmark systematically measures whether agent-generated code is secure. Existing coding benchmarks (SWE-bench, HumanEval) evaluate functional correctness only, ignoring the implicit security requirements that real-world feature implementations must satisfy. This paper asks: when agents implement security-sensitive features in real repositories, how often do they introduce exploitable vulnerabilities?

## Input / Output

Each task provides a natural-language feature request (deliberately omitting any security guidance, mirroring how real users describe desired functionality), a repository codebase with the target feature's implementation masked out, and a Docker execution environment where the agent can run tests and iterate. The agent produces a code patch; evaluation applies two independent sets of human-written dynamic tests—functional tests (T_func, averaging 66.9 per task) and security tests (T_secure, averaging 3.5 per task)—yielding FuncPass (functional correctness) and SecPass (joint functional-and-security correctness) as pass@1 metrics.

## Method

SUSVIBES is constructed via an automated pipeline that mines 20,000+ vulnerability fix commits from ReposVul and MoreFixes, filters to Python ≥3.7 projects with test modifications, and for each commit: (i) reverts to the vulnerable predecessor C_{-1}, (ii) uses SWE-Agent to generate a minimal deletion mask removing the feature implementation, (iii) uses a second SWE-Agent instance to write a feature-request description from the masked code, and (iv) iteratively verifies the description covers the secure canonical implementation, enlarging the mask when gaps are found. Execution-based validation confirms that the masked repo fails all tests, the vulnerable repo passes functional but fails security tests, and the secure repo passes both. A final human verification step (5 experts) decouples security tests from the ground-truth implementation. The benchmark comprises 186 tasks across 100 repositories, 10 application domains, and 79 CWE types, with target patches averaging 175 lines across 1.8 files. Evaluation spans 12 agentic settings (3 frameworks × 4 frontier LLMs), revealing that even the best configuration (SWE-Agent + Claude 4 Sonnet) achieves only 11.8% SecPass despite 57% FuncPass.

## Results

On SUSVIBES (186 security-sensitive feature-request tasks), the best-performing agentic system, SWE-Agent with Claude 4 Sonnet, achieves 57.0% FuncPass but only 11.8% SecPass, meaning 79.3% of its functionally correct solutions contain exploitable vulnerabilities. Across all 12 agent-framework/LLM combinations, the average SecPass is only ~10%, with the highest being SWE-Agent + Gemini 3 Pro at 12.9%. When isolating security capability (SecPass⊥FuncPass on the intersection of correctly solved tasks), Gemini 2.5 Pro is the most secure LLM (30.4%) and SWE-Agent the most secure framework (23.3%), while Claude 4 Sonnet is the least secure LLM (18.3%).

## Baselines & Comparisons

The paper evaluates 12 agentic settings (3 frameworks × 4 LLMs) rather than comparing a single method against baselines. In terms of functional correctness, SWE-Agent + Claude 4 Sonnet leads at 57.0% FuncPass, followed by OpenHands + Claude 4 Sonnet (53.2%) and OpenHands + Gemini 3 Pro (50.5%); Claude Code consistently trails the other two frameworks. On security, Gemini 2.5 Pro is the most secure backbone (SecPass⊥FuncPass = 30.4% averaged across frameworks), while Claude 4 Sonnet is the least secure (18.3%); SWE-Agent is the most secure framework (23.3%) versus Claude Code (17.4%). Notably, Gemini 3 Pro more than doubles Gemini 2.5 Pro's FuncPass (37.1% vs. 18.3% on SWE-Agent) but only improves SecPass⊥FuncPass by 1.3×, indicating that reasoning-oriented post-training helps functionality far more than security. Preliminary mitigation strategies (CWE self-selection and oracle CWE hints) raise SecPass by only 2.7–3.3 pp while dropping FuncPass by 1.6–7.0 pp, confirming that simple prompting cannot close the security gap.

## Relation to Prior Work

This paper extends the SWE-bench paradigm (which evaluates coding agents on repository-level bug-fixing tasks for functionality alone) by introducing security-sensitive feature-request tasks where agents must implement new features without introducing vulnerabilities. It also builds on the line of secure code generation benchmarks (CWEval, SecCodePLT, BaxBench, SecureAgentBench) but departs from them in three key ways: evaluating agentic systems rather than single-turn model outputs, operating at repository scale with multi-file edits (~175 lines vs. 8–42 in prior work), and covering 79 CWE types rather than 11–45. The curation pipeline repurposes vulnerability-fix commits from ReposVul and MoreFixes as feature-request tasks, inverting the typical vulnerability-fixing task formulation used by ASE and SecureAgentBench.

## Why It Matters / Open Questions

The finding that ~80% of functionally correct agent-generated solutions contain exploitable vulnerabilities, consistent across 12 agentic settings and four frontier LLMs, directly challenges the assumption that passing functional tests is sufficient for production deployment of vibe-coded software. The failure of even oracle CWE hints to close the gap (while degrading functionality by 7 points) suggests that security in agentic code generation requires fundamentally different training or architectural approaches, not just better prompting. Open questions include whether reinforcement learning with security rewards, multi-agent verification, or dedicated security-specialist sub-agents can close the functionality-security trade-off, and whether the benchmark's Python-only scope limits generalizability to other languages.
