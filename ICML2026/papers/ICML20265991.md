## Problem

Dynamic LLM workloads (elastic KV caches, multi-LoRA, Tree-of-Thoughts branching, position-independent caching) demand tensors that grow, fork, and share memory flexibly, yet current systems force a trade-off: PyTorch's contiguous abstraction fragments under dynamic loads, while software-paged systems (vLLM, SGLang) sacrifice kernel transparency and impose 20–30% performance penalties from bespoke paged-aware kernels. The GPU's native MMU could resolve this tension, but standard CUDA VMM APIs incur millisecond-scale, size-linear mapping latency that is orders of magnitude too slow for the inference critical path.

## Input / Output

The system consumes tensor shape specifications (for virtual address reservation), physical GPU memory pages (for on-demand materialization), and LLM inference requests with associated LoRA adapter IDs or branching topologies. It produces Elastic Tensors that are byte-for-byte indistinguishable from standard contiguous PyTorch tensors to upper-layer kernels (FlashAttention, cuBLAS GEMM), while internally backing them with fragmented, on-demand physical pages. The key constraint is that all virtual-to-physical remapping must complete in microseconds to remain invisible to token-level decoding loops, and the 2 MB page granularity is fixed by the CUDA VMM hardware interface.

## Method

CONTINUUM modifies the NVIDIA open-source GPU driver to replace the serialized, lock-heavy VMM control plane with a three-stage transactional pipeline: (1) Eager Virtual Reservation physically instantiates the full page-table hierarchy (PML4 through leaf directories) in GPU memory at reservation time, (2) Offline PTE Pre-calculation computes hardware-specific Page Table Entry bit patterns in a host-side buffer at page-allocation time, and (3) Batched Transactional Mapping injects all pre-computed PTEs into GPU page tables via a single vectorized DMA write, collapsing O(N) serialized kernel transitions into one hardware transaction. This reduces mapping cost from ~40 ms (2 GB, standard cuMemMap) to ~60 µs (32 MB, CONTINUUM on H20), a 671× speedup. Built atop this backend, the Elastic Tensor PyTorch extension exposes four operations—elastic (reserve VA), materialize (bind physical pages), share (zero-copy alias via additional PTE mappings), and release (batched PTE invalidation + TLB flush)—that unify model-level structural elasticity (KV growth, LoRA/Engram stitching) and sequence-level topological aliasing (branching, prefix/position-independent caching) under a single contiguous-tensor interface requiring no kernel modification.

## Results

CONTINUUM reduces GPU memory mapping latency by up to 671.3× compared to standard CUDA VMM, collapsing millisecond-scale control-plane costs to the microsecond level. In Multi-LoRA serving on Llama-2-7B, CONTINUUM achieves up to 3.29× higher throughput than vLLM and 1.16–1.32× over S-LoRA. For Tree-of-Thoughts decoding (batch size 1), CONTINUUM delivers up to 7.65× end-to-end latency speedup over vLLM at branch factor K=8 and step size L_step=4, while matching vLLM (≈1×) at L_step=1 where per-step computation is too small to amortize remapping overhead.

## Baselines & Comparisons

Against standard CUDA VMM (Perry & Sakharnykh), CONTINUUM's driver extension achieves a 671.3× mapping speedup, reducing 2 GB remapping from 40.4 ms to the microsecond range. Versus vLLM (Kwon et al.), CONTINUUM wins decisively: up to 3.29× throughput in Multi-LoRA serving (where vLLM stalls on CPU-GPU adapter swapping) and up to 7.65× latency reduction in Tree-of-Thoughts branching, though it ties vLLM (0.97×–1.03×) at L_step=1 where per-token branching is too frequent to amortize any control-plane cost. Against S-LoRA (Sheng et al.), CONTINUUM achieves a 1.16–1.32× speedup in Multi-LoRA, attributed to dispatching to cuBLAS rather than custom Triton scatter-gather kernels. In context caching (Figure 9), CONTINUUM substantially outperforms vAttention (Prabhu et al.) for both position-dependent and position-independent reuse, because vAttention's reliance on unmodified cuMemMap places millisecond-scale mapping on the TTFT critical path. For the Engram sparse-retrieval workload (Cheng et al.), CONTINUUM achieves significantly higher throughput than the official copy-based PyTorch implementation by eliminating monolithic pre-allocation and enabling virtual stitching of sparse physical blocks.

## Relation to Prior Work

This paper builds directly on the CUDA VMM hardware mechanism (Perry & Sakharnykh) but departs fundamentally from prior VMM-based systems (GMLake, vAttention) that use the vendor control plane as-is and merely hide its latency through overlap scheduling or pre-mapping. It also contrasts with the dominant software-paging paradigm (vLLM/PagedAttention, SGLang) by arguing that the contiguous tensor abstraction should be restored via hardware virtualization rather than sacrificed for fragmentation management. The key conceptual departure is identifying the serialized driver control plane—not the MMU remapping mechanism itself—as the true bottleneck, and solving it through a driver-level modification that collapses O(N) serialized operations into a single batched DMA transaction.

## Why It Matters / Open Questions

If the Elastic Tensor abstraction gains traction, it could become a standard runtime layer that decouples algorithmic innovation from memory-management engineering, letting researchers express dynamic workloads (elastic KV, multi-LoRA, zero-copy branching) without writing bespoke paged-aware kernels. However, the approach requires modifying the NVIDIA open-source driver, which creates a significant adoption barrier and limits immediate cross-vendor portability. Open questions include whether the transactional mapping model extends to multi-GPU and disaggregated serving, whether host-memory oversubscription can be layered on top, and whether the 2 MB page granularity is optimal for all workload regimes (the paper shows near-parity with vLLM at L_step=1, suggesting the control-plane overhead is not fully eliminated for extremely fine-grained branching).
