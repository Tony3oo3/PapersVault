## Problem

Existing automated validation and repair tools for repository-level code translation (e.g., OXIDIZER, ALPHATRANS, SKEL) are tied to a single language pair, require thousands of lines of language-interoperability engineering, and rely on incomplete source test suites that produce false equivalence claims. Moreover, their repair strategies—simple reprompting or manual fixing—barely work on real-world projects with long call-chain dependencies. No prior approach is simultaneously language-agnostic, effective at validation, and capable of automated repair.

## Input / Output

MATCHFIXAGENT consumes a translation pair (source function and its translated counterpart) together with both full source and target projects, an LLM, an agent toolset (file I/O, shell execution, web search), and a timeout (default 1,000 s). It first builds Tree-Sitter ASTs to extract CFGs and DFGs, then feeds textual graph representations and code fragments to LLM sub-analyzers. The output is a structured validation report: a 6-tuple of JSON semantic-analysis verdicts, a set of generated differential tests in both PLs with execution results, an optional repair patch, and a final natural-language equivalence verdict (EQ, NEQ, or VF).

## Method

MATCHFIXAGENT is a three-stage multi-agent pipeline. The Semantic Analyzer runs six parallel LLM sub-analyzers—control flow, data flow, I/O mapping, library API, exception handling, and specifications—each prompted with a focused equivalence definition and aided by Tree-Sitter-derived CFG/DFG textual representations; the control-flow and data-flow analyzers additionally compute Jaccard-similarity scores on abstracted graph structures and short-circuit to an 'equivalent' verdict when similarity ≥ 0.7, skipping ~25–35% of LLM calls. The Test Generator & Repair Agent (an off-the-shelf coding agent such as Claude Code or Codex) receives the six semantic reports and writes executable differential tests in both source and target languages, runs them, and—if inequivalence is confirmed—iteratively generates a repair patch. Finally, the Verdict Agent consolidates all semantic and test-execution evidence into a single equivalence decision and a condensed user-facing summary. The entire system is ~1,650 LoC, depends only on Tree-Sitter for language support (~280 LoC per new PL), and is agnostic to the underlying LLM or agent framework.

## Results

MATCHFIXAGENT produces an equivalence verdict for 99.2% of 2,219 translation pairs across 6 PL pairs, compared to only 71.6% for the best existing tool. On the 1,571 pairs where both MATCHFIXAGENT and a competing tool produce verdicts, they agree in 72.8% of cases; in the remaining disagreements, manual investigation confirms MATCHFIXAGENT is correct 60.7% of the time. For translation repair, MATCHFIXAGENT fixes 50.6% of 265 buggy translations, compared to 18.5% for prior techniques. The entire system requires only 1,650 lines of code versus 3,843–19,052 LoC for competing tools, and adding a new PL costs ~280 LoC.

## Baselines & Comparisons

Against OXIDIZER (Zhang et al., PLDI 2025), MATCHFIXAGENT agrees in only 63.7% of cases but wins 84.1% of disagreements, largely because OXIDIZER's ASCII-only test inputs miss Unicode-related inequivalences (e.g., Go's len() vs Rust's .len()). Against ALPHATRANS (Ibrahimzada et al., FSE 2025), agreement is 69.3% with MATCHFIXAGENT winning 73.5% of disputes; ALPHATRANS's GraalVM-based validation system fails to validate many correct LLM-generated patches, inflating its NEQ rate. Against SKEL (Wang et al., PLDI 2025), agreement is highest at 79.3%, but MATCHFIXAGENT still wins 53.5% of disagreements, as SKEL's string-replacement test conversion misses edge cases. Against RUSTREPOTRANS (Ou et al., ASE 2025), the picture reverses: MATCHFIXAGENT agrees 80.2% but loses 87.5% of disagreements, because RUSTREPOTRANS's human-written idiomatic Rust translations intentionally deviate from 1:1 source semantics, making MATCHFIXAGENT's equivalence definition overly strict. For repair, MATCHFIXAGENT fixes 50.6% of 265 bugs versus 18.5% for prior work (only RUSTREPOTRANS's tool produced any patches; OXIDIZER, ALPHATRANS, and SKEL repaired zero).

## Relation to Prior Work

This paper departs from the dominant paradigm in repository-level translation validation, where tools like OXIDIZER, ALPHATRANS, and SKEL each require 4K–19K lines of language-specific engineering to support a single PL pair, by replacing that heavy interoperability layer with a lightweight Tree-Sitter-based static analysis (CFG/DFG with Jaccard similarity short-circuiting) plus LLM-driven semantic reasoning. Conceptually, it repurposes the recent success of LLMs on same-language equivalence checking (Wei et al. 2025a, Maveli et al. 2025) for the cross-language setting, and introduces a three-stage multi-agent decomposition (parallel semantic sub-analyzers → test generator/repair agent → verdict agent) that has no direct analogue in prior translation-validation tools, which typically use monolithic reprompting loops. The repair component extends simple feedback-driven reprompting (used by ALPHATRANS, SKEL, OXIDIZER) by feeding structured semantic diagnoses (e.g., library API mismatches, exception-handling gaps) into an agentic coding loop that can execute and iterate on patches.

## Why It Matters / Open Questions

The practical impact is substantial: a 1,650-LoC system that supports 6 PL pairs and can be extended to new languages with ~280 additional lines, versus 10K–19K LoC per single pair in prior tools, directly addresses the quadratic scaling problem of language-pair engineering in software modernization. The 50.6% repair rate (vs. 18.5% for prior work) and the ablation showing near-random (47.7%) standalone-agent accuracy on disputed cases provide strong evidence that the multi-agent semantic-analysis architecture is not merely helpful but essential for hard translations. Open questions include whether the approach generalizes to concurrent or systems-level code (the paper explicitly avoids aliasing, concurrency, and context sensitivity in its data-flow analysis), how it performs on translations with intentional refactoring (as in RUSTREPOTRANS, where MATCHFIXAGENT's accuracy drops to 12.5% on disagreements), and whether the 3.6% false-positive rate on agreed-equivalent cases is acceptable for production deployment.
