## Problem

Existing LLM serving systems treat concurrent multi-tenant workflows as independent instances, overlooking cross-workflow computational redundancy (e.g., multiple queries embedding or retrieving the same document chunks) and failing to coordinate scheduling globally. This request-level isolation causes wasted computation, head-of-line blocking for short tasks, and starvation for long tasks under heterogeneous workloads, degrading both average and tail latency.
![Teaser figure](../imgs/ICML20262574/cropped_page0_idx0.webp)

## Input / Output

The system ingests concurrent text queries, each represented as a DAG of fine-grained task nodes (embedding, retrieval, reranking, LLM prefill/decode, tool calls) with per-node attributes including estimated workload, compatible resource types, reverse topological depth, and splittability bounds. It produces LLM-generated responses while internally emitting scheduling decisions: priority-ordered execution sequences, batch sizes, resource share allocations, and pipeline decomposition factors. The DAG structure is the key unusual aspect—queries are not flat request-response pairs but multi-step graphs whose nodes can be merged, split, or reordered across query boundaries.

## Method

HeraSys employs a dual-layer optimization architecture. The Pre-Execution Graph Fuser computes a semantic signature for each node (a hash over operator type, result-affecting parameters, input data summary, and ordered predecessor signatures) to detect computationally equivalent nodes across concurrent queries, then performs DAG edge redirection to fuse them into a single execution instance or asynchronously reuses completed results. The Runtime Load-Aware Joint Scheduler assigns each ready node a composite priority π_v = α/(Ŝ_q+ε) + γ·φ_v + δ·y_v, combining dynamic SRTF (via online remaining-time estimation with PLAS-style correction at decoding sub-node boundaries), topological contribution (downstream workload and path length), and an anti-starvation boost for heavy nodes in long queries. Resource skewing enforces a minimum fraction ρ of each resource type reserved for long-query heavy nodes, while adaptive batching and pipeline decomposition (k_v) are modulated by a load-dependent λ: high load increases batch sizes and reduces splits for throughput, low load decreases batches and increases splits for latency.

## Results

HeraSys reduces P99 tail latency by up to 2.17× (Mixed Workload at concurrency 300) and increases serving throughput by up to 1.85× under strict latency guarantees compared to state-of-the-art baselines. Average end-to-end latency is reduced by 35.2% (RAG w/ Rerank), 30.7% (RAG w/o Rerank), and 41.8% (Web Search) relative to baselines. P95 and P99 latencies are reduced by 48.5% and 53.9% respectively, demonstrating the effectiveness of the resource skewing mechanism in preventing long-task starvation.

## Baselines & Comparisons

HeraSys outperforms all three baselines across every workload and concurrency level on both P95 and P99 latency. Against Ayo (the strongest baseline, a fine-grained task-primitive orchestration system), HeraSys achieves 1.44–2.17× P99 speedup, with the largest gains at high concurrency (C=300) where cross-workflow fusion opportunities are most abundant. Against LangGraph and LlamaIndex (modular frameworks that treat each request in isolation), HeraSys achieves up to 1.94× and 1.83× P99 speedup respectively, as these systems suffer severe head-of-line blocking under load. Notably, in the Web Search workflow at C=6, HeraSys's P95 (5.35s) is slightly higher than Ayo's (5.20s), but it pulls ahead dramatically at higher concurrency (32.03s vs. 43.77s at C=100), indicating that the graph fusion and load-aware scheduling mechanisms become increasingly beneficial as system pressure grows. Throughput under latency constraints reaches up to 1.50× Ayo and nearly 2× the modular frameworks, driven primarily by the Graph Fuser's deduplication of redundant embedding and retrieval operations.

## Relation to Prior Work

HeraSys extends the fine-grained task-primitive orchestration paradigm introduced by Ayo (Tan et al., 2025), which decomposes modular LLM applications into standardized computational nodes, by adding a cross-workflow dimension: a pre-execution graph fuser that identifies and merges semantically redundant subgraphs across concurrent queries. For runtime scheduling, it adapts the PLAS-inspired attained-service-time heuristic from Autellix (Luo et al., 2025) to handle LLM decoding unpredictability via sequential sub-node decomposition, while departing from prior intra-workflow-only schedulers (DistServe, Sarathi-Serve, Splitwise) by introducing a joint priority function that simultaneously accounts for remaining-time (SRTF), topological contribution, and long-query resource skewing. The paper positions itself against modular frameworks (LangGraph, LlamaIndex) that treat each request as an isolated execution graph, arguing that this request-level isolation obscures exploitable structural redundancy and prevents global load balancing.

## Why It Matters / Open Questions

The cross-workflow graph fusion mechanism addresses a practical gap in multi-tenant LLM serving where concurrent queries over shared corpora or tools generate substantial redundant computation; the 1.16× throughput gain from fusion alone (ablation) confirms this is not merely a scheduling artifact. However, the evaluation is limited to a single 4-GPU node with a fixed 8B model, and the semantic signature matching relies on exact operator-type and input-data hashing, which may underperform for semantically similar but textually distinct queries. Open questions include scalability to distributed multi-node clusters, robustness of the remaining-time estimator under highly variable LLM generation lengths, and whether the greedy per-event scheduling can be improved with lookahead without incurring prohibitive modeling overhead.
