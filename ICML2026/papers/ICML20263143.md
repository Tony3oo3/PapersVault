## Problem

Existing file-reasoning benchmarks rely on a 'parse-then-reason' paradigm that flattens documents into text or JSON before reasoning, offloading structural parsing to preprocessing and stripping away layout cues essential for correct answers. This masks a critical capability gap: LLMs cannot reliably navigate raw, unprocessed files (multi-sheet spreadsheets with merged cells, slide decks with embedded objects, formatted reports) where evidence is scattered across irregular, stateful structures. The paper formalizes File Reasoning as an interactive setting requiring agents to act directly on native files within a persistent, executable sandbox.

## Input / Output

The agent receives a raw file (XLSX, PDF, DOCX, or PPTX) pre-loaded into a containerized sandbox working directory, along with a natural-language question. It must issue executable tool calls (Python code via ExecuteCode with 60s timeout, or Bash via ExecuteShell) over up to 15 interaction rounds, interpreting stdout/stderr feedback at each step. The sandbox is stateful: file modifications (e.g., unzipping archives, writing intermediate CSVs) persist across turns within a trajectory. The final output is a single answer (text or numeric) extracted from the last turn, verified for correctness via an LLM-as-a-Judge (GPT-5-mini) comparing semantic equivalence against a ground-truth answer.

## Method

FIRE is trained in two stages. First, a cold-start SFT phase bootstraps basic tool-invocation syntax using verified question-solution trajectories generated by an asymmetric pipeline (teacher model sees structured data to produce unambiguous Q/A pairs; agent sees only the raw file at inference). Second, a stateful RL phase using GRPO optimizes the policy over full trajectories in a persistent sandbox, where each action modifies a latent environment context (e.g., creating intermediate files, altering directory state) that subsequent actions must account for. The reward is sparse and outcome-oriented: +1 for correct final answer (judged by GPT-5-mini), 0 for incorrect but valid, and −0.2 for structural format violations, deliberately avoiding step-level penalties to encourage exploration and error recovery. The data pipeline preserves native file irregularities (merged cells, inconsistent headers, embedded objects) and enforces solvability via an Auditor Agent that must programmatically reproduce the ground truth, followed by consensus filtering across three frontier models to retain only tasks that are solvable but non-trivial.

## Results

On the FIRE benchmark (410 verified questions across XLSX, PDF, PPTX, and DOCX), Qwen3-32B-FIRE(RL) achieves 50.33% overall accuracy with 6.49 average tool calls, substantially outperforming its base Qwen3-32B (11.14%) and approaching frontier proprietary models GPT-5 (60.16%) and Grok-4 (60.89%). RL training consistently reduces tool calls while increasing accuracy (e.g., Qwen3-32B-FIRE drops from 7.43 to 6.49 tool calls while gaining 7.57 accuracy points over SFT), indicating more strategic planning. The strongest open-source baseline, GLM-5, reaches 63.33% overall accuracy, remaining ahead of all FIRE models. Across file types, XLSX and PPTX tasks are notably harder than PDF and DOCX for all models, confirming the benchmark captures structural reasoning difficulty beyond reading comprehension.

## Baselines & Comparisons

Qwen3-32B-FIRE(RL) (50.33%) outperforms all open-source baselines except GLM-5 (63.33%), beating Kimi-K2-Thinking (47.97%) by 2.36 points and DeepSeek-V3.1 (44.55%) by 5.78 points, despite using a substantially smaller 32B backbone. Against proprietary models, it trails GPT-5 (60.16%) by ~10 points and Grok-4 (60.89%) by ~10.6 points, but surpasses Gemini-2.5-Pro (33.25%) and GPT-4.1 (24.15%) by wide margins. The base Qwen3-32B without FIRE training scores only 11.14%, demonstrating that the stateful RL framework contributes ~39 accuracy points over the untrained backbone. Among smaller open-source models, Qwen2.5-72B-Instruct (12.76%) and Qwen3-8B (6.67%) remain far below FIRE models, highlighting that scale alone without file-specific agentic training is insufficient. On the cross-benchmark comparison (Table 3), even GPT-5 drops from 77.8% on GAIA to 60.2% on FIRE, confirming the benchmark's higher difficulty relative to prior file-based datasets.

## Relation to Prior Work

This paper departs from the dominant 'parse-then-reason' paradigm in document and table QA (TabFact, SSTQA, GAIA, MeetBench), where files are pre-flattened into clean text or structured formats before reasoning. It also extends the tool-use literature (ReAct, Gorilla, ToolBench) by replacing stateless, single-shot API calls with a persistent, stateful sandbox where file-system modifications accumulate across turns. The training recipe builds on GRPO (from DeepSeekMath) and the verl/vLLM infrastructure, but applies them to a novel multi-turn file-interaction environment rather than math or code reasoning.

## Why It Matters / Open Questions

The benchmark exposes a substantial capability gap: even GPT-5 and Grok-4 score only ~60% here versus 77–87% on GAIA/SSTQA, suggesting that real-world file structure (merged cells, embedded objects, temporal references) remains a significant unsolved challenge. The finding that RL simultaneously improves accuracy and reduces tool-call count challenges the assumption that more interaction rounds are needed for better performance. Open questions include whether the 15-round budget artificially caps performance for some models, whether LLM-as-a-Judge reward introduces enough noise for stable training at scale, and whether the gains transfer to truly novel file formats beyond the four tested.
