## Problem

Existing Text-to-SQL systems commit to a single static workflow at inference time, assuming one fixed pipeline generalizes across heterogeneous query distributions. This fundamentally limits scalability to out-of-distribution and long-tail scenarios: simple queries suffer unnecessary latency from complex pipelines, while difficult queries with multiple challenges cannot be solved by any single method. The paper asks whether adaptively constructing workflows per query can close this gap, and how to learn such a policy from sparse execution feedback.

## Input / Output

The policy model receives a natural language question, database schema, optional external knowledge, and a pool of available actor implementations (e.g., parsers, generators, optimizers, selectors from methods like DIN-SQL, CHESS, MAC-SQL, RSL-SQL, LinkAlign). Rather than generating SQL directly, the LLM outputs a workflow specification—a Python list string of actor names (e.g., list['LinkAlignParser', 'MACSQLGenerator'])—which is parsed and executed by the Squrve backend to produce the final SQL query. At inference, five workflows are sampled and the final SQL is selected via majority voting over execution results.

## Method

SquRL decomposes policy learning into two stages. First, supervised fine-tuning constrains the model to generate structurally valid workflows by deriving workflow-level supervision from existing Text-to-SQL benchmarks (SynSQL, Spider, BIRD), progressively exploring templates from simple to complex and using the first correct workflow as the label. Second, reinforcement learning via GRPO refines workflow selection using a five-component rule-based reward (format, timeout penalty, execution, result correctness, and time efficiency) that evaluates workflows at multiple execution stages. Two training mechanisms address key challenges: dynamic actor masking randomly removes actors from the pool with probability r to prevent over-concentration on a small set of high-reward workflows, and pseudo rewards replace a fraction p of expensive execution-based rewards with LLM-judged pairwise comparisons against a baseline workflow. Theoretically, the paper proves that the optimal dynamic policy's expected accuracy is always at least that of the best static workflow, with the gap equal to the probability mass of the union of all workflows' success regions minus the best single workflow's success region.

## Results

SquRL-7B achieves 86.27% execution accuracy on Spider-Dev, 86.58% on Spider-Test, and 67.60% on BIRD-Dev, outperforming the best static baseline (RSL-SQL) by 1.97, 2.84, and 1.78 points respectively. On the SynSQL benchmark, SquRL-7B reaches 64.42% overall execution accuracy (vs. 57.42% for RSL-SQL), with the gap widening to +7.97 points on Highly Complex queries (46.51% vs. 38.54%). On the challenging Spider 2.0-Lite enterprise benchmark, SquRL-7B+DeepSeek-R1 achieves 49.18% accuracy, surpassing the best static method (33.09%) by 16.09 points.

## Baselines & Comparisons

SquRL-7B outperforms all five static workflow baselines (DIN-SQL, MAC-SQL, LinkAlign, RSL-SQL, CHESS) across every benchmark. The strongest static competitor is RSL-SQL, which SquRL-7B surpasses by 1.97 points on Spider-Dev, 2.84 on Spider-Test, 1.78 on BIRD-Dev, and 7.00 on SynSQL overall. The advantage scales with query difficulty: on SynSQL Highly Complex queries, SquRL-7B leads RSL-SQL by 7.97 points (46.51% vs. 38.54%), while on Easy queries the gap is a more modest 4.05 points. On Spider 2.0-Lite, SquRL-7B+DeepSeek-R1 (49.18%) beats the best static methods (LinkAlign and RSL-SQL, both at 33.09%) by 16.09 points, and substantially outperforms GPT-4o-based pipelines (DIN-SQL at 1.46%, CHESS at 3.83%, DAIL-SQL at 5.68%). Notably, even the smallest SquRL variant (1.5B) already surpasses the best static workflow on Spider-Dev (85.10% vs. 84.30%), suggesting dynamic workflow selection can partially compensate for limited model capacity.

## Relation to Prior Work

SquRL builds directly on the Squrve modular framework, which abstracts heterogeneous Text-to-SQL components (schema linking, generation, refinement) into a unified actor interface, and on GRPO as the RL training algorithm. It departs from prior RL-based Text-to-SQL methods (SQL-R1, Arctic-Text2SQL-R1, ReasoningSQL) that optimize token-level policies generating SQL directly, by instead learning a policy over a structured combinatorial workflow space—separating 'how to reason' from 'what to generate.' All prior Text-to-SQL systems (DIN-SQL, CHESS, MAC-SQL, RSL-SQL, LinkAlign) commit to a single fixed pipeline at inference time; SquRL is the first to make workflow selection itself a learned, query-conditioned decision.

## Why It Matters / Open Questions

The paper provides both a clean theoretical guarantee (dynamic selection dominates the best static workflow, with the gap governed by workflow heterogeneity) and a practical open-source system that achieves a 16-point gap over the best static baseline on the very difficult Spider 2.0 benchmark. The finding that a 1.5B policy model with dynamic workflows surpasses larger static pipelines suggests that adaptive orchestration can partially compensate for limited model capacity. Open questions include how the approach scales as the actor pool grows combinatorially, whether the learned policy transfers to new actor sets without retraining, and whether the dynamic workflow paradigm generalizes beyond Text-to-SQL to other multi-step reasoning tasks.
