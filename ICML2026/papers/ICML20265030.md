## Problem

Training terminal-based AI agents requires large-scale, execution-grounded trajectories, but existing methods face a fundamental trade-off: approaches like Nex-N1 scale task diversity through LLM-generated data and rule-based heuristics but remain decoupled from real execution, while SWE-bench-style datasets provide realistic Docker environments but are constrained in scale by heuristic repository filtering (e.g., high-star repos). No prior pipeline simultaneously achieves environment diversity, realistic execution grounding, and execution-based verification at scale.

## Input / Output

The pipeline consumes ~900K GitHub repositories across eight programming languages, prioritizing those containing Dockerfiles and explicit build configurations, along with external assets (images, CSVs, videos, model checkpoints, web links) for domain-specific tasks. It produces 32,325 Docker images and 50,733 verified multi-turn agent trajectories (averaging 15.1 turns and ~6,531 tokens each), where each trajectory is paired with instance-specific pytest validation code that checks filesystem side effects, process states, and output correctness rather than matching exact command sequences. The verified trajectory rate is only ~4.9%, reflecting a high-precision executable filtering regime.

## Method

TerminalTraj Pipeline operates in three stages: (1) a lightweight ScoreModel (Qwen2.5-Coder-0.5B with a sigmoid regression head, distilled from a Qwen2.5-Coder-32B teacher via MSE on 160K pseudo-labeled files) scores each code file for completeness and executability, enabling automated repository filtering at ~1/100th the inference cost of direct teacher scoring; (2) Qwen3-Coder-480B reverse-engineers task queries from shell/markdown file pairs within each Docker image and simultaneously generates executable pytest validation suites that verify state-based side effects; (3) Qwen3-Coder-480B rolls out trajectories via the Terminus-2 scaffold (4 attempts per query for diversity), and only trajectories whose final environment state passes the generated validation code are retained. The key differentiator from prior work is the end-to-end executable verification loop—replacing LLM judges and hand-crafted rules with task-specific pytest execution—combined with model-based (rather than heuristic) repository scoring that enables continuous, automated scaling of Docker environments.

## Results

TerminalTraj-32B achieves 35.30% on TerminalBench 1.0 and 22.00% on TerminalBench 2.0, representing absolute gains of +30.3 and +17.5 points over its Qwen2.5-Coder-32B backbone (5.00% and 4.49%). Across all model sizes, training on TerminalTraj data yields gains exceeding +20 points on TB 1.0 and +10 points on TB 2.0. In test-time scaling, TerminalTraj-32B reaches 63% pass@16 on TB 1.0, surpassing the substantially larger Qwen3-Coder-480B across all k values except k=4.

## Baselines & Comparisons

Against the three largest open-source baselines, TerminalTraj-32B trails: DeepSeek-V3.2 (685B) scores 56.25/46.40, GLM-4.7 (358B) scores 48.75/41.00, and Kimi-K2-Instruct (1T) scores 44.59/27.80 on TB 1.0/TB 2.0, all substantially above TerminalTraj-32B's 35.30/22.00. However, TerminalTraj-32B decisively outperforms the closest same-scale competitor, Qwen3-32B-Nex-N1 (28.75/16.70), by 6.55 and 5.30 points on TB 1.0 and TB 2.0 respectively, despite using a weaker backbone (Qwen2.5-Coder-32B vs. Qwen3-32B) and fewer training trajectories (50,733 vs. 69,008). TerminalTraj-32B also surpasses the much larger Qwen3-235B-A22B-Instruct (15.00 on TB 1.0) by 20.30 points and DeepSeek-V3.1-Nex-N1 (31.56 on TB 1.0) by 3.74 points. Most notably, TerminalTraj-32B achieves performance comparable to Qwen3-Coder-480B-A35B-Instruct (37.50/23.90) while using more than an order of magnitude fewer parameters, and in test-time scaling (pass@16) it exceeds Qwen3-Coder-480B at 63% vs. ~55%.

## Relation to Prior Work

This paper positions itself at the intersection of two existing but incompatible lines of work: SWE-bench-style datasets (SWE-Gym, SWE-Factory, SWE-Mirror) that provide realistic Dockerized execution environments but are constrained in scale by heuristic repository filtering, and Nex-N1, which scales task diversity but relies on LLM judges and rule-based heuristics rather than grounding trajectories in actual execution. TerminalTraj departs from both by reformulating repository selection as a model-based scoring problem (using a distilled 0.5B reward model) to enable automated construction of 32K Docker images, and by replacing LLM-based trajectory verification with instance-specific executable pytest validation. The reward-model distillation approach (Qwen2.5-Coder-32B teacher → Qwen2.5-Coder-0.5B student) borrows from knowledge distillation literature but applies it to a novel domain: code-file quality scoring for environment buildability prediction.

## Why It Matters / Open Questions

The 50,733 verified trajectories and 32K Docker images constitute a major open resource for terminal-agent research, and the pipeline's modular design (score → build → generate → verify) is directly reusable for scaling to more languages or domains. However, several limitations temper the impact: training is restricted to SFT on a single backbone family (Qwen2.5-Coder, up to 32B), the 4.92% verified trajectory rate means most generated data is discarded, and the paper explicitly defers RL integration to future work. The finding that environment diversity (32K vs. SETA's 400) dramatically improves test-time scaling (pass@8: 45% vs. 12.5%) suggests a promising but underexplored axis of scaling for agentic models. Open questions include whether the gains transfer to non-Qwen backbones, whether RL on these environments compounds the SFT gains, and whether the pipeline's quality ceiling is bounded by the LLM used for trajectory rolling (Qwen3-Coder-480B).
