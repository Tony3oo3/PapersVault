## Problem

Open-source LLMs significantly lag behind proprietary models in generating interactive frontend mini-games, and the core bottleneck is the absence of an evaluation mechanism that balances reliability with scalability. Static judges (code analysis or single-frame screenshots) systematically miss runtime errors and unresponsive controls, while GUI agents—though accurate—incur prohibitive token costs and latency that make them infeasible for synthesizing large training datasets or computing online RL rewards.

## Input / Output

The ALIVE evaluation framework takes a user prompt (game description) and the generated frontend code as input, then renders the page in a headless browser and processes the DOM, Accessibility Tree, and raw source code to plan interactions. It outputs a normalized ALIVE-Score (0–1) computed as the fraction of satisfied binary checklist items (8–20 per task, combining a fixed universal checklist with a prompt-driven checklist). For canvas-based games lacking explicit DOM nodes, the planner infers click coordinates by parsing rendering logic (e.g., fillRect, drawImage calls) from the source code. The trained ALIVE-Coder model takes a text prompt and produces complete HTML/CSS/JS mini-game code.

## Method

ALIVE operates on a Plan-Execute-Evaluate cycle whose key innovation is a verification-oriented one-shot planning mechanism: a multimodal model analyzes the page structure (DOM, Accessibility Tree, raw code) and synthesizes a complete Action List of interactions in a single inference pass, decoupling reasoning from execution to avoid the O(N) cost of iterative observe-think-act loops. A Playwright headless browser executes the planned actions, capturing sequential screenshots and execution logs as an interaction trace. A Judge Model then scores the trace against the binary checklists, with a replanning mechanism (up to 3 attempts for SFT, 1 for RL) that regenerates the Action List if the plan is deemed infeasible. This scalable signal is used twice: first to curate SFT data by selecting the highest-scoring candidate from 5 Gemini-3-Pro generations per query, and second as the reward function for GRPO-based RL on Qwen3-Next. At performance parity with a GUI agent running 11–12 serial steps, ALIVE achieves ~12× lower token consumption and ~22× lower latency, reducing RL-scale evaluation cost from $4,800 to $396 for 72,000 samples.

## Results

ALIVE-Coder-RL achieves a score of 40.5 on ALIVE-Eval, surpassing the strongest proprietary model GPT-5.2 (40.3) and all open-source baselines. On the static ArtifactsBench-Game benchmark, it reaches 61.2, slightly edging out Qwen3-Coder-Plus (60.9). The SFT stage alone lifts the base model Qwen3-Next from 25.4 to 29.1 on ALIVE-Eval (+3.7) and from 49.2 to 58.4 on ArtifactsBench (+9.2), while RL further amplifies gains to the final 40.5/61.2. In terms of evaluation efficiency, ALIVE reduces token consumption by ~12× and end-to-end latency by ~22× compared to a GUI-agent judge at performance parity (11–12 agent steps), cutting RL-scale API cost from $4,800 to $396 for 72,000 samples.

## Baselines & Comparisons

ALIVE-Coder-RL outperforms all proprietary baselines on ALIVE-Eval: it beats GPT-5.2 (40.5 vs. 40.3), Gemini-3-Pro (40.5 vs. 39.2), and Claude-4.5-Sonnet (40.5 vs. 37.7), with the largest margin over Claude. On ArtifactsBench-Game, it also leads all proprietary models (61.2 vs. 58.4 for GPT-5.2, 57.1 for Gemini-3-Pro, 56.7 for Claude-4.5-Sonnet). Against open-source baselines, the advantage is substantial on ALIVE-Eval (40.5 vs. 27.7 for DeepSeek-V3.2, 28.1 for GLM-4.7, 25.9 for Qwen3-Coder-Plus), while on ArtifactsBench it narrowly surpasses Qwen3-Coder-Plus (61.2 vs. 60.9) and clearly leads DeepSeek-V3.2 (61.2 vs. 57.6) and GLM-4.7 (61.2 vs. 56.2). Compared to its own base model Qwen3-Next, the full SFT+RL pipeline yields a +15.1 point gain on ALIVE-Eval and +12.0 on ArtifactsBench. Human evaluation corroborates these automated results, with ALIVE-Coder-RL achieving a >90% win rate over the base model and a substantial margin over DeepSeek-V3.2 in blinded pairwise comparisons.

## Relation to Prior Work

This paper carves out a middle ground between two existing paradigms for evaluating LLM-generated code: static judges (code analysis, single-frame screenshot inspection, as in ArtifactsBench) and iterative GUI agents (Observe-Think-Act loops, as in VideoGameBench and UI-TARS-2). The key architectural departure is the 'one-shot planning' mechanism, which decouples reasoning from execution by synthesizing an entire interaction trajectory in a single VLM inference pass over the DOM/Accessibility Tree, then offloading execution to a lightweight Playwright engine. This repurposes ideas from accessibility-tree-based web testing and code-to-geometry inference (for canvas games) into a scalable evaluation-and-reward pipeline, positioning ALIVE as a 'pre-flight' verification layer rather than a replacement for exhaustive human or agent-based testing.

## Why It Matters / Open Questions

The paper addresses a practical bottleneck that has stalled open-source progress in interactive frontend generation: the absence of an evaluation signal that is both reliable enough to filter functional failures and cheap enough to serve as an RL reward at scale. The demonstrated 12× token and 22× latency reduction over GUI agents, combined with the reward-hacking mitigation (verbosity trap, hallucination trap), makes interactive-verification-based RL training economically feasible for the first time. Open questions include whether one-shot planning generalizes to highly stochastic or real-time genres (parkour, fighting), whether the Playwright concurrency bottleneck (~30 parallel instances per container) limits further scaling, and whether the approach transfers beyond mini-games to full interactive web applications.
