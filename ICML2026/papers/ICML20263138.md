## Problem

Existing benchmarks for LM-based software engineering agents focus on what gets fixed (bug resolution, feature implementation) rather than how code is optimized for performance. While a few benchmarks probe code efficiency, they operate on isolated functions or synthetic tasks rather than real-world, end-to-end workloads on actual repositories. SWE-FFICIENCY targets the open question of whether LM agents can investigate an unfamiliar codebase, localize performance bottlenecks and relevant correctness tests, and produce a patch that matches or exceeds expert speedup while preserving existing behavior.

## Input / Output

The agent receives a complete Python codebase (one of nine repositories: numpy, pandas, scipy, matplotlib, astropy, dask, scikit-learn, sympy, xarray) at a pinned commit, along with a performance workload script containing a setup() function and a workload() function timed via timeit.repeat(). The agent must produce a code patch to non-test files that reduces workload runtime while keeping a set of covering unit tests (identified via dynamic line coverage and jedi-based symbol resolution) passing. Evaluation computes a per-instance speedup ratio SR = Speedup_LM / Speedup_gold, aggregated across all 498 tasks via harmonic mean with a per-instance floor of 0.001; patches that fail tests or are empty are clamped to max(1/Speedup_gold, 0.001).

## Method

The benchmark is built through a five-stage data collection pipeline: (1) scraping merged PRs from nine performance-sensitive Python repositories, (2) attribute filtering for performance keywords, exclusion of test-modifying PRs, and meaningful AST changes via tree-sitter, (3) coverage-guided test selection combining coverage.py dynamic line coverage with jedi cross-file symbol resolution to identify unit tests whose executed lines or transitively-referenced symbols intersect the expert patch, (4) manual annotation of performance workloads from PR descriptions and discussion threads, and (5) execution-based filtering retaining only instances with speedups exceeding 2× the post-edit standard deviation. The evaluation metric, speedup ratio, normalizes LM speedup against the expert's gold-patch speedup and is aggregated via harmonic mean to reward expert parity and beyond. Agents run within OpenHands or SWE-agent harnesses with a 3-hour time limit, 100-action cap, 4 pinned vCPUs, and 16 GB RAM per worker, with CPU-affinity and NUMA-node binding to achieve <0.5% measurement variance across independent runs.

## Results

On SWE-FFICIENCY (498 tasks across 9 repositories), the best-performing agent, CLAUDE 4.5 OPUS (OpenHands), achieves a Speedup Ratio (SR) of 0.225×, meaning it captures only 22.5% of the expert's speedup. Across all 15 frontier models evaluated, agents achieve less than 0.23× expert speedup on average, with the weakest (CLAUDE 3.7 SONNET) reaching only 0.024×. A striking capability transfer gap is observed: GPT-5 MINI scores 62.6% on SWE-bench Verified but only 0.019× expert speedup on SWE-FFICIENCY, indicating that bug-fixing ability does not transfer to performance optimization.

## Baselines & Comparisons

As a benchmark paper, SWE-FFICIENCY evaluates 15 frontier LM agents (from OpenAI, Anthropic, Google, Z.ai, Moonshot AI, and DeepSeek) rather than comparing a single method against baselines. The top three agents—CLAUDE 4.5 OPUS (0.225×), GPT-5 (0.157×), and GPT-5.2 (0.148×)—all remain well below expert parity (1.0×), with a 5–9× gap to human performance. A key comparison is the capability transfer gap: GPT-5 MINI achieves 62.6% on SWE-bench Verified yet only 0.039× SR on SWE-FFICIENCY, demonstrating that issue-resolution skill does not translate to performance optimization. In terms of correctness, even the best agents fail unit tests on 9–45% of instances (Table 3), and fewer than 50% of patches that pass correctness tests actually outperform the expert's speedup. The paper also notes that LMs achieve strong performance on easier tasks (shorter workloads, smaller expert speedups) but degrade sharply on harder instances, with over 68% of expert-achievable speedup occurring in functions the LM never edits.

## Relation to Prior Work

This paper re-engineers the SWE-bench scraping and evaluation infrastructure to target performance optimization rather than bug fixing, inverting SWE-bench's test-change filter to exclude behavior-altering PRs. It departs from function-level efficiency benchmarks (MERCURY, EFFIBENCH, PIE, KernelBench) by operating at the full repository level with a fixed user workload, and from the closest repo-level predecessors (GSO, SWE-Perf) by requiring agents to autonomously localize both bottlenecks and relevant unit tests rather than being told which functions to optimize or given oracle correctness scripts. The pass-to-pass formulation (speeding up already-correct code) and the separation of correctness tests from performance workloads mirror real-world performance engineering practice, which prior benchmarks conflated.

## Why It Matters / Open Questions

SWE-FFICIENCY provides the first large-scale (498 tasks, 9 repos) benchmark for the full investigative performance-engineering workflow, and its speedup-ratio metric offers a long runway for progress that percentage-solved metrics cannot. The finding that even the best agents (Claude 4.5 Opus at 0.225×) achieve less than a quarter of expert speedup, driven primarily by function-level mislocalization rather than edit complexity, identifies a concrete and actionable gap for future agent research. Limitations include Python/Cython-only scope, single-workload evaluation, and nine repositories; extending to lower-level languages, multi-objective optimization, and heterogeneous hardware are natural next steps that the authors outline.
