## Problem

Standard speculative decoding executes drafting and verification strictly sequentially, placing the draft model's latency directly on the critical path and fundamentally capping achievable speedups. Existing parallel speculative decoding methods either require substantial additional GPU/memory resources or a dedicated training stage for the draft model, and scaling single-request parallelism to batched multi-request settings remains challenging. MINEDRAFT addresses this gap by proposing a batch-parallel design that hides drafting latency behind verification using only one additional GPU.

## Input / Output

The system takes a batch of m text prompts (requests) along with a small draft model and a large target model, and produces verified text tokens identical in distribution to standard autoregressive decoding. Internally, the Batch Manager maintains 2m concurrent requests partitioned into two batches of size m; the draft model runs on a dedicated GPU and communicates draft tokens to the target model via direct GPU-to-GPU transfers. The framework is agnostic to the specific drafting strategy (e.g., EAGLE, TETRIS, PEARL) and integrates as a plug-and-play vLLM plugin compatible with PagedAttention and continuous batching.

## Method

MINEDRAFT's core mechanism is a two-batch alternation scheme: at each speculative decoding step, the Drafter generates draft tokens for one batch (the draft batch) while the Verifier simultaneously verifies previously drafted tokens from the other batch (the target batch), with roles swapping at each synchronization point. The draft model is placed on a separate GPU to avoid VRAM contention with the target model, and a patched vLLM scheduler skips KV block allocation for requests in the draft batch to prevent redundant memory usage. A theoretical analysis under a Pareto-frontier model of draft quality shows that PSD achieves a guaranteed ~37.9% reduction in inference time over standard SD (with a 50% upper bound), maximized when the expected number of accepted tokens per verification step is approximately 2.23. The framework also includes a fallback to standard SD when one batch becomes empty, and a load-balancing mechanism (balance variable) to maintain equal batch sizes across request arrivals and terminations.

## Results

MINEDRAFT achieves average throughput improvements of 38.62%–65.02% over the best baseline (PEARL or standard SD) and up to 75.68% over standard SD across Settings 1–4 (Qwen3-32B target with 0.6B–8B draft models). End-to-end latency is reduced by up to 28.97% relative to the best baseline and up to 39.51% relative to standard SD (Setting 2, Qwen3-32B + Qwen3-1.7B). On the larger Llama-3.3-70B setting, throughput gains reach 37.06% over standard SD, and on EAGLE-based settings (Vicuna-33B/13B), gains over standalone EAGLE reach 22.09% in throughput and 16.30% in latency. All gains are achieved at the cost of only one additional GPU dedicated to the draft model.

## Baselines & Comparisons

Against **standard SD** (Leviathan et al., 2023), MINEDRAFT consistently wins on both throughput and latency across all seven model settings, with throughput gains ranging from 18.87% (Setting 7, small Vicuna-13B) to 75.68% (Setting 3, Qwen3-32B + Qwen3-4B) and latency reductions up to 39.51%. Standard SD also fails entirely on Setting 4 (Qwen3-8B draft) and the Qwen3-235B MoE setting due to VRAM exhaustion, whereas MINEDRAFT's dedicated-GPU architecture avoids this. Against **PEARL** (Liu et al., 2025a), MINEDRAFT outperforms it across all Settings 1–3, with the best-baseline gap (which includes PEARL) reaching 65.02% in throughput; PEARL is omitted from later comparisons due to its substantially lower efficiency. Against **standalone EAGLE** (Li et al., 2024a), MINEDRAFT achieves up to 22.09% throughput improvement and 16.30% latency reduction on the Vicuna-33B/13B settings, though the margin narrows for the smaller Vicuna-13B model (only 6.06% throughput gain). In normalized per-GPU comparisons, MINEDRAFT still leads standard SD by up to 40.55% in throughput, though it marginally underperforms at very small k (k=1–2) due to inter-GPU communication overhead accounting for 50–58% of latency in that regime.

## Relation to Prior Work

MINEDRAFT builds directly on the speculative decoding paradigm (Leviathan et al., 2023) but departs from prior parallel SD approaches (Wang et al., 2024; Timor et al., 2025; Xiao et al., 2024) that broke the draft-verify dependency at the cost of substantial extra GPU memory or dedicated training stages. Its key conceptual contribution is 'Batch Parallelism'—maintaining two request batches so that drafting for one overlaps with verification for the other—which is orthogonal to all existing drafting-quality improvements (EAGLE, TETRIS, PEARL, Medusa) and composes with them. Unlike PEARL (Liu et al., 2025a), which parallelizes within a single request using pre/post-verify strategies, MINEDRAFT operates at the batch level and scales to multi-request serving, though it inherits a tail-effect limitation when batches become unbalanced.

## Why It Matters / Open Questions

The practical impact is significant: MINEDRAFT ships as a plug-and-play vLLM plugin compatible with PagedAttention and continuous batching, making batch PSD immediately deployable in production inference stacks. The theoretical guarantee (37.9% latency reduction under a mild exponential acceptance model) provides a principled upper bound, and the finding that draft model size has a non-monotonic effect on PSD performance (too large a drafter makes drafting slower than verification, negating the overlap benefit) offers actionable guidance for model pairing. Open questions include whether the mandatory extra GPU can be eliminated (e.g., via weight-padding), how to handle chunked prefill and adaptive batch sizing, and whether request-difficulty-aware draft selection can further close the gap to the 50% theoretical ceiling.
