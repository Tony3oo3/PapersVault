## Problem

Frontier LLMs that achieve high correctness on data-rich platforms like CUDA (e.g., GPT-5.2 at 92% on CUDA L1) suffer catastrophic performance drops on data-scarce Domain-Specific Architectures such as Ascend C for NPU programming (14% on L1, 2% on L2). Standard remedies—supervised fine-tuning, parametric RL, and similarity-based RAG—are infeasible or ineffective in this extreme data-scarcity regime, leaving an open question: how can an agent autonomously bootstrap and master a rigorous, binary-correctness kernel synthesis task from scratch without expert demonstrations or weight updates?

## Input / Output

The method takes a PyTorch reference operator with metadata (input shapes, hyperparameters) and a frozen frontier LLM as the generator, and produces a complete Ascend C operator project comprising kernel source, host tiling code, C++ PyTorch binding, and a Python model wrapper. Verification is multi-gate: an anti-hacking screen (rule-based + LLM auditor) rejects semantic bypasses, followed by compilation under the Ascend C toolchain, numerical correctness against the PyTorch reference (atol=rtol=1e-2), and on-device latency profiling via msprof. A persistent, self-evolving memory bank with learned Q-values is maintained across operators and can be transferred to different generator backbones.

## Method

EvoKernel formulates kernel synthesis as a Memory-based MDP where a frozen LLM generator is guided by a learned retrieval policy over a heterogeneous, self-evolving memory bank. The pipeline has two stages: (1) Cold-Start Drafting, which uses a binary feasibility reward (+1/−1) to bootstrap the first correct kernel, and (2) Continual Refining, which optimizes latency using a bounded tanh(log-ratio) reward against the best-so-far baseline with online z-score normalization. The key mechanism is Value-Driven Retrieval: stage-specific Q-values (Q₁ for drafting, Q₂ for refining) are updated via a unified Monte-Carlo rule from verifier feedback, so the agent learns which memory items (API templates, optimization traces, past kernels) are genuinely useful for the current objective rather than merely semantically similar. Cross-task memory sharing allows patterns learned on simpler L1 operators to transfer to harder L2 operators, and the memory bank itself transfers across generator backbones (e.g., GPT-5.2-built memory improves DeepSeek-V3.2 correctness from 6% to 58%). No model weights are updated; all adaptation occurs through the non-parametric memory and its learned value estimates.

## Results

On the NPU KernelBench (Ascend C), EvoKernel with GPT-5.2 achieves 98.5% compilation rate and 83.0% overall correctness, substantially outperforming Codex (83.0% CR, 46.0% Acc) and the Refinement baseline (71.5% CR, 22.0% Acc). On the harder Level 2 operators, EvoKernel reaches 100% compilation and 76% correctness, while all other baselines remain below 22%. Conditioned on reaching a correct draft, iterative refinement yields a median within-operator speedup of 3.60× (IQR 1.38–10.05×) over the first feasible kernel, with top performers exceeding 200×.

## Baselines & Comparisons

EvoKernel is compared against three in-paper baselines (Pass@k, Refinement, Codex) and one external trained model (AscendKernelGen / KernelGen-LM-32B-RL). With GPT-5.2, EvoKernel outperforms Codex by 15.5 points in compilation rate (98.5% vs. 83.0%) and 37.0 points in correctness (83.0% vs. 46.0%), despite Codex having autonomous shell and file-system access. Against the Refinement baseline, EvoKernel gains 27.0 points in CR and 61.0 points in Acc overall, with the gap widening dramatically on Level 2 (76% vs. 3% correctness). Pass@k, the stateless baseline, trails by 74.5 points in overall correctness (83.0% vs. 11.0%). The trained AscendKernelGen model (Appendix E, Table 6) achieves only 5.0% overall correctness and 0% on Level 2 under a matched 30-candidate budget, confirming that value-driven memory retrieval substantially outperforms domain-specific fine-tuning in this data-scarce setting. On weaker backbones (DeepSeek-V3.2, Qwen3-Coder-30B), EvoKernel still leads in correctness (9.5% and 5.5% respectively) but the margins are smaller, and Level 2 accuracy remains 0% for all methods, indicating that generator capacity is a hard bottleneck for the hardest operators.

## Relation to Prior Work

EvoKernel sits at the intersection of memory-augmented generation (MemGPT, Voyager, Memento, MemRL) and automated kernel synthesis (KernelBench, MultiKernelBench, QiMeng-Kernel, STARK). It departs from prior self-evolving agents (Reflexion, AlphaEvolve, EvolveR) by replacing textual reflection or implicit ranking with learned stage-specific Q-values for retrieval, and from training-based kernel generators (Kevin, TritonRL, AscendKernelGen) by keeping the LLM entirely frozen and updating only a non-parametric retrieval policy via Monte-Carlo value iteration. The two-stage drafting-then-refining formulation with a shared, cross-task memory bank is the paper's core architectural contribution, building on the M-MDP formalism from Memento and MemRL but specializing it to a binary-correctness, latency-optimization setting.

## Why It Matters / Open Questions

The work provides a practical pathway for deploying LLMs on emerging DSAs (NPUs, TPUs, neuromorphic chips) where the 'Data Wall' makes SFT and parametric RL infeasible, and it introduces a reusable NPU KernelBench benchmark for Ascend C. A key open question is the method's dependence on frontier-model in-context learning: weaker backbones (Qwen3-Coder-30B, DeepSeek-V3.2) see only marginal gains, suggesting the framework amplifies rather than compensates for generator capacity. Future directions include extending to other DSLs, reducing reliance on large commercial models via distillation, and incorporating denser reward signals to improve sample efficiency in the refining stage.
