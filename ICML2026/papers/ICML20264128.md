## Problem

Cross-tool description poisoning allows an adversary to corrupt the metadata of non-critical tools so that the LLM planner is steered into invoking safety-critical tools with malicious parameters, even when the poisoned tool is never selected. Existing prompt-injection defenses (tool filtering, repeated prompts, system-level guards) transfer poorly to this threat because poisoned descriptions persist in the planning context across steps, enabling continuous influence over subsequent tool choices. The paper identifies this gap and proposes a dedicated system-level defense.

## Input / Output

Tool-Guard consumes the user's original intent, the full tool set with their (potentially poisoned) natural-language descriptions, and the agent's running state (dialogue history, previously validated actions, and tool outputs). At each step it produces a single validated tool call (tool name + arguments) or a natural-language response, while internally maintaining a dynamic binary partition of the tool set into an Influenced list and an Others list. Notably, the validation checks deliberately exclude poisoned tool descriptions from their context, relying only on the original user query and previously validated actions/observations, which limits the adaptive attack surface.

## Method

Tool-Guard applies the security principle of isolation to agentic planning by dynamically partitioning the tool set into an Influenced list and an Others list, then querying the LLM planner twice under strictly isolated description subsets (isolated planning) so that a poisoned description in one partition cannot steer tool selection in the other. The two candidate actions are merged via a selection rule that picks the valid tool call (or terminates if neither is viable). Before execution, each candidate is validated by two complementary LLM-based checks: an alignment check (task consistency given only the user intent and validated progress) and a suspicion check (argument grounding in the user request or prior tool outputs, flagging unprovenanced sensitive entities). On validation failure, the implicated tool is moved into the Influenced list and the planner replans under the updated partition, progressively cutting cross-tool contamination paths while preserving utility because the union of both partitions always equals the full tool set. The design extends naturally to MCP server-level grouping by lifting the partition to server granularity.

## Results

On the AgentDojo benchmark (GPT-4o), Tool-Guard reduces the attack success rate (ASR) from 43.30% (no defense) to 2.06%, while preserving benign utility at 72.16% (vs. 76.29% without defense) and maintaining attack utility at 58.76%. Token overhead is approximately 1.45×/1.39× the no-defense baseline (1.22M/2.24M vs. 0.84M/1.61M tokens), and wall-clock latency is ~3.7× no-defense, compared to 1.2× for Progent and 7.3× for Drift. On the ASB benchmark, Tool-Guard similarly drives ASR to negligible levels across five LLMs while preserving utility. Under adaptive attacks (PAIR, TAP, semantic variants), ASR remains at or near 0%, with PAIR producing the highest residual ASR of 2.06%.

## Baselines & Comparisons

Tool-Guard decisively outperforms all four baselines on ASR: it achieves 2.06% vs. 19.59% (System Prompt), 10.31% (Tool Filter), 43.30% (Repeat User Prompt), 24.74% (Drift), and 19.59% (Progent). On benign utility, Tool-Guard (72.16%) trails Repeat User Prompt (85.57%) and System Prompt (76.29%) but exceeds Tool Filter (69.07%), Drift (68.04%), and Progent (43.30%). Progent is the most notable contrast: while it matches Tool-Guard's ASR on some suites, it catastrophically degrades benign utility (43.30% vs. 72.16%) and attack utility (13.40% vs. 58.76%), indicating severe over-kill. Drift achieves the lowest no-defense ASR (20.62%) among baselines but still yields 24.74% ASR under defense, far above Tool-Guard. In terms of efficiency, Tool-Guard uses ~1.45× tokens (vs. 3.5× for Drift, 3.7× for Progent) and ~3.7× latency (vs. 7.3× for Drift), making it the best security–utility–efficiency trade-off among all evaluated defenses.

## Relation to Prior Work

This paper carves new ground at the intersection of LLM agent security and tool metadata integrity. It departs from the dominant prompt-injection defense literature (Drift, Progent, tool filtering, sandwich defense) by identifying cross-tool description poisoning as a distinct threat where poisoned metadata on one tool steers selection of entirely different tools, a vector that prior defenses were not designed to address. Conceptually, it repurposes the classical security principle of isolation (quarantining untrusted components) and applies it to the planning loop of an LLM agent, rather than to execution-time outputs. The work also builds on the emerging MCP security line (Guo et al., Wang et al. 2025b) but avoids their reliance on internal model states or static scanning, instead operating purely at the system level through dynamic partitioning and pre-execution validation.

## Why It Matters / Open Questions

As MCP and similar tool-ecosystem standards proliferate, tool descriptions become a de facto trusted channel that attackers can exploit without ever invoking a malicious tool, making this a practically urgent vulnerability. The paper's demonstration that state-of-the-art prompt-injection defenses (Drift, Progent) fail against cross-tool poisoning is an important negative result that should reshape how agent security is evaluated. Key limitations include the ~3.7× latency overhead, validator failures when benign tasks are semantically close to attack targets (e.g., 'send to Alice' vs. 'forward to attacker'), and the open question of whether the isolation principle scales gracefully to thousands of MCP tools or to multi-agent settings where tool sets are dynamically composed. Future work could explore learned validators, lighter-weight partitioning heuristics, and formal security guarantees for the isolation mechanism.
