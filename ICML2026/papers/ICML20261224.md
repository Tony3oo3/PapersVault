## Problem

LLMs struggle to detect malicious code in large Python packages because their attention is diluted across vast amounts of benign code, and they cannot effectively track malicious behaviors fragmented across files with complex interdependencies. Performance degrades sharply as package size increases, and direct LLM analysis of entire projects incurs prohibitive computational costs compared to specialized detection tools.

## Input / Output

The method takes a Python package's source code, parses it into an AST-derived code graph where nodes are classes, functions, and modules (annotated with their source code) and edges encode definition, inheritance, decorator, and call relationships. Node features are multi-hot vectors indicating matches against a set of LLM-generated sensitive behavior rules. The output is a binary malicious/benign verdict accompanied by a natural-language description of the malicious behavior's location and characteristics, plus per-node and per-edge attention scores that identify which code regions drove the detection.

## Method

GMLLM is a two-stage pipeline. First, a lightweight two-layer GCN is trained with binary cross-entropy on code graphs whose node features are multi-hot vectors derived from LLM-auto-generated sensitive behavior rules (common rules plus data-derived rules sampled from 10% of training data). Second, at inference, an explainability module optimizes trainable edge and feature masks on the target graph using a loss that maximizes the GNN's malicious-class probability while penalizing mask size (L1) and encouraging binary determinacy (entropy). The resulting attention scores identify a small subgraph of high-influence nodes and edges, which is then serialized into a structured natural-language description (node names, call edges, and source code snippets) and fed to an LLM for targeted malicious-behavior analysis. A budgeted top-K edge strategy (K=20) controls the subgraph size, bounding token consumption and preventing the LLM from being overwhelmed by irrelevant code.

## Results

On the proposed MalCP dataset (All split), GMLLM with ChatGPT 4o achieves 95.62% accuracy, 95.30% recall, and 95.07% precision, outperforming the strongest baselines Ea4mp (91.03% acc) and MPHunter (93.56% acc). On Large packages—where LLM baselines degrade most severely—GMLLM (ChatGPT 4o) reaches 90.41% accuracy versus 88.10% for Ea4mp and 83.83% for MPHunter, while the Llama 3-based variant achieves 94.36% recall on Large. The method also attains 95.89% benign specificity, exceeding all baselines except Ea4mp (92.37%) and MPHunter (91.57%).

## Baselines & Comparisons

GMLLM (ChatGPT 4o) outperforms all 11 baselines on overall accuracy on MalCP (95.62%), with the closest competitors being MPHunter (93.56%) and Ea4mp (91.03%). Against the strongest LLM baseline, ChatGPT 4o used directly, GMLLM improves accuracy by 5.2 points (95.62 vs. 90.39) and recall by 6.0 points (95.30 vs. 89.33), while also raising benign specificity from 91.27% to 95.89%. On Large packages, where direct LLM prompting degrades sharply (ChatGPT 4o drops to 77.98% acc), GMLLM maintains 90.41%, a 12.4-point advantage. Against rule-based tools, GMLLM dominates OSSGadget (95.62 vs. 69.66 acc) and Bandit4Mal (95.62 vs. 52.77 acc), while also surpassing Virustotal (95.62 vs. 79.24 acc) primarily through superior recall (95.30 vs. 69.86). The Llama 3-based GMLLM variant achieves the highest recall (97.71%) but at the cost of lower precision (71.88%), indicating that the LLM backbone quality significantly affects the precision-recall tradeoff.

## Relation to Prior Work

GMLLM carves new ground by combining three previously separate threads: (1) GNN-based code representation (AST-derived graphs with GCN), (2) LLM-based malware detection (Fang et al. 2024, Yu et al. 2024, Akinsowon & Jiang 2024), and (3) graph explainability via trainable edge/feature masks (conceptually similar to GNNExplainer-style attribution). The key departure from prior LLM-for-malware work is that instead of feeding entire codebases to an LLM, the paper uses GNN interpretability as an attention mechanism to extract a minimal suspicious subgraph, which the LLM then analyzes in depth. The rule-generation component repurposes LLMs to automate what was previously a manual expert task in tools like Bandit and OSSGadget, while the GNN itself is trained with only binary package-level labels, avoiding the need for fine-grained node annotations.

## Why It Matters / Open Questions

The paper addresses a practical bottleneck: LLMs degrade sharply on large Python packages because attention is diluted across benign code, and the GNN-guided subgraph extraction directly targets this failure mode with orders-of-magnitude token reduction on large packages. The MalCP dataset, with its size-stratified splits and MITRE ATT&CK-aligned behavior labels, fills a gap in public benchmarks for package-level detection. Open questions include generalization beyond Python (the AST and rule pipeline is language-specific), robustness to obfuscated or dynamically-constructed malicious code, and whether the ~10-second-per-package explainability overhead is acceptable at PyPI-scale scanning. The paper also acknowledges dual-use risk: the explainability output could help adversaries understand detection patterns.
