## Problem

Existing cloud-edge collaborative speculative decoding frameworks suffer from two key limitations: (1) they execute token generation, communication, and cloud verification sequentially, leaving both edge and cloud resources idle and underutilizing bandwidth; and (2) they use inflexible NAV triggering—either fixed draft lengths or single-signal confidence thresholds—that cause premature verification or excessive speculation with costly rollbacks.
![Teaser figure](../imgs/ICML20261449/cropped_page1_idx0.webp)

## Input / Output

The system takes a text prompt and operates with a small draft model (e.g., DeepSeek-Coder-1.3B or TinyLlama-1.1B) deployed on the edge device and a large target model (e.g., DeepSeek-Coder-6.7B or Llama-2-7B) in the cloud. The edge autoregressively generates draft tokens and transmits them in optimized batches over a cloud-edge link (20 Mbps uplink in the testbed), while the cloud performs a single non-autoregressive verification pass and returns accepted tokens. The output is a generated text sequence that exactly preserves the target model's output distribution, with the draft length per speculative round dynamically determined by confidence thresholds rather than fixed in advance.

## Method

PipeSD introduces two core mechanisms. First, a token-batch pipeline scheduling mechanism overlaps draft token generation with cloud-edge communication by deciding how to partition tokens into transmission batches; this is formulated as an optimization problem over batch boundaries and solved optimally via a dynamic programming algorithm with O(N̂²) complexity, where N̂ is a sliding scheduling window. Second, a dual-threshold NAV triggering mechanism jointly monitors cumulative sequence confidence (product of all token probabilities) and individual token confidence, triggering cloud verification when either threshold is crossed; a lightweight Bayesian optimization autotuner (Gaussian process with Matérn kernel, EI acquisition) automatically adapts the two thresholds to minimize time-per-token using only ~16 samples. The system is implemented with llama-cpp-python for edge-side GGUF inference, PyTorch for the cloud target model, and FastAPI for the communication interface, with an environment monitor that triggers DP re-scheduling or BO re-tuning only when hardware parameters shift beyond a 20% relative change threshold.

## Results

On HumanEval and GSM8K across four cloud-edge scenarios, PipeSD achieves average TPT of 108–186 ms, yielding 1.33×–2.16× speedup over Vanilla, 1.19×–1.61× over HSL, and 1.16×–1.32× over EdgeLLM. The largest gains appear on resource-constrained edge devices (Scenarios 2–3), where pipelining hides more communication latency. PipeSD also reduces cloud energy consumption (ECS) by 14.3%–25.3% compared to baselines in Scenario 1, primarily due to fewer unnecessary verification requests from the dual-threshold NAV triggering mechanism.

## Baselines & Comparisons

PipeSD consistently outperforms all three baselines across every scenario and dataset. Against Vanilla (fixed-length draft, no pipelining), PipeSD achieves the largest speedups (1.33×–2.16×), with the gap widening as edge compute becomes more constrained (Scenario 3: 2.01×–2.16×), because token-batch pipelining hides more communication time relative to slower generation. Against HSL (single-token confidence triggering), PipeSD gains 1.19×–1.61×, benefiting from the dual-threshold mechanism that avoids both premature verification and over-speculation; HSL's overly conservative triggering (verification frequency 0.2558 vs. PipeSD's 0.1733) leads to shorter draft sequences and lower acceptance rates (0.9148 vs. 0.9616). Against EdgeLLM (cumulative sequence confidence only), PipeSD achieves 1.16×–1.32× speedup; EdgeLLM's single sequence-level signal can mask individual low-confidence tokens, causing delayed error detection, whereas PipeSD's joint token-level and sequence-level thresholds produce a higher acceptance rate (0.9616 vs. 0.8917) at a comparable draft length (4.96 vs. 4.74). Under dynamic bandwidth (Scenario 4), PipeSD maintains consistent improvements, confirming robustness to network fluctuations.

## Relation to Prior Work

This paper extends the cloud-edge collaborative speculative decoding line initiated by HSL, HAT, and SpecEdge, which all adopt a sequential compute-then-transmit pattern and single-signal NAV triggering. PipeSD departs from these by introducing a token-batch pipeline scheduling mechanism (formulated as a DP-optimized batching problem) that overlaps draft generation with communication, and a dual-threshold NAV triggering mechanism that jointly monitors cumulative sequence confidence and per-token confidence. The BO autotuner for adaptive threshold selection draws on Gaussian-process-based Bayesian optimization (Alipourfard et al., 2017), while the linear communication model follows the classical Hockney formulation. The system is built on llama-cpp-python for edge inference and FastAPI for cloud serving, keeping the cloud side minimal and compatible with existing optimization frameworks.

## Why It Matters / Open Questions

Cloud-edge LLM inference is becoming practically important as edge devices gain sufficient compute for small draft models, and PipeSD provides a clean, implementable framework that addresses two concrete bottlenecks (idle time from sequential execution and inflexible verification timing) with measurable energy savings on the cloud side. However, the evaluation is limited to two model pairs (≤7B target), CPU-only edge inference, and a single metropolitan network testbed; generalization to GPU-equipped edge devices, larger models, or highly heterogeneous multi-client deployments remains open. The paper also notes that tree-based speculative decoding, while potentially complementary, is less suitable for bandwidth-constrained cloud-edge links, leaving the interaction between tree drafting and pipeline scheduling as an unexplored direction.
