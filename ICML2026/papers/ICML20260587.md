## Problem

Production LLMs trained on web-scale data have absorbed malicious scam content into their weights, yet no systematic, automated framework existed to audit whether these models reproduce malicious endpoints in response to ordinary developer-style prompts. The November 2024 incident where ChatGPT generated a cryptocurrency trading script containing a live phishing URL (costing a user $2,500) demonstrated the real-world severity, but it remained unclear whether this was a rare anomaly or a systemic vulnerability across the industry.

## Input / Output

The framework takes seed scam URLs from two established databases (eth-phishing-detect with 187,555 URLs and PhishFort with 119,828 URLs), filters them to 28,570 still-accessible pages, and crawls their visible text content. It produces Innoc2Scam-bench, a curated set of 1,377 human-validated developer-style prompts (704 Web3-related, 673 non-Web3) that trigger malicious code generation across all four audited LLMs, along with newly discovered malicious domains reported to security databases. All prompts are explicitly non-adversarial: no jailbreaking, prompt injection, or crafted exploitation is involved.

## Method

Scam2Prompt is a five-stage automated pipeline: (1) security-conscious web crawling of known scam URLs using HEAD-then-GET requests restricted to text content types; (2) prompt synthesis where a Prompt LLM (GPT-4o, GPT-4o-mini, or Llama-4-Scout) infers the page's functional intent and generates innocuous developer-style coding requests; (3) code generation by a Codegen LLM (GPT-4o, GPT-4o-mini, Llama-4-Scout, or DeepSeek-V3) responding to those prompts; (4) URL extraction and malice detection via an oracle ensemble of three independent detectors (ChainPatrol, Google Safe Browsing, SecLookup), where any single flag marks a URL as malicious; and (5) human validation by three annotators to confirm prompts are genuinely benign developer requests. The key insight is that malicious actors deliberately craft documentation to maximize keyword overlap with common user requests, so LLMs trained on such content will surface scam endpoints when given matching legitimate prompts—no adversarial technique required. The resulting prompt-code pairs are filtered to those where all four Codegen LLMs produced malicious output, yielding the stress-test benchmark.

## Results

On Innoc2Scam-bench (1,377 developer-style prompts), all seven evaluated 2025 production LLMs generate malicious code at non-negligible rates, ranging from 12.9% (Gemini-2.5-Pro) to 47.3% (DeepSeek-Chat-V3.1). In the initial large-scale audit of 265,000+ prompts across four 2024 models, an average of 4.24% of generated programs contained malicious URLs. Existing defenses provide minimal protection: NeMo Guardrails detect only 0–0.7% of malicious outputs, OpenAI Moderation API flags none, and a RAG-based agent reduces GPT-4o's malicious rate only from 50.04% to 29.41%.

## Baselines & Comparisons

The paper evaluates two widely deployed defense mechanisms against the malicious code generation threat. NeMo Guardrails (with Llama Nemotron Safety Guard V2) blocks none of the developer-style prompts and detects only 0–0.7% of malicious code outputs across models; OpenAI Moderation API flags 0 out of 3,452 malicious outputs, while Llama Guard 3 flags 291/3,452 (8.43%). A RAG-based agent (GPT-4o with web search and explicit URL-safety instructions) reduces GPT-4o's malicious URL generation rate from 50.04% to 29.41%, leaving substantial residual risk. The authors conclude that none of these existing defenses are sufficient, and that explicit oracle-based URL validation (e.g., via Google Safe Browsing, ChainPatrol, or SecLookup) after code generation is necessary but not yet implemented by any production LLM provider.

## Relation to Prior Work

This paper carves out a distinct threat vector from three adjacent lines of work: (1) indirect prompt injection and external-tool contamination (Zeng et al. 2025, BIPIA), which require the LLM to access poisoned content at inference time; (2) active data-poisoning attacks (Schuster et al. 2021, Aghakhani et al. 2024, Carlini et al. 2024), where adversaries deliberately inject malicious training data; and (3) CWE-based code security benchmarks (Pearce et al. 2022, SecCodePLT, SAFEGENBENCH), which target logic-level vulnerabilities. Scam2Prompt departs from all three by auditing for *passive* absorption of real-world scam URLs into model weights during ordinary web-scale training, triggered by entirely benign developer prompts with no adversarial technique, no external tool access, and no active poisoning. The framework repurposes existing scam databases (eth-phishing-detect, PhishFort) and industrial URL oracles (Google Safe Browsing, ChainPatrol, SecLookup) into an automated prompt-synthesis-and-audit pipeline, a methodology not previously applied to LLM code generation.

## Why It Matters / Open Questions

The finding that every tested production LLM (across 2024 and 2025 releases, seven providers) generates malicious code at rates of 12.9%–47.3% under ordinary developer prompts, and that standard guardrails and RAG-based agents reduce this by less than 20 percentage points, exposes a gap in the current LLM safety stack that is neither addressed by training-time curation nor inference-time filtering. The discovery of 62 previously unlisted active scam domains that had evaded detection for over a year underscores that the threat is ongoing and under-monitored. Open questions include whether machine unlearning or targeted data sanitization can remove memorized scam endpoints without degrading model utility, whether explicit post-generation URL validation (the paper's recommended mitigation) is sufficient or whether deeper architectural changes are needed, and how the vulnerability scales to other forms of malicious code beyond URLs (backdoors, worms). The released Innoc2Scam-bench (1,377 prompts) provides a reusable stress-test resource that will likely become a standard evaluation for future LLM releases.
