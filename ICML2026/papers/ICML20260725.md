## Problem

Tokenizers in LLM inference pipelines are treated as negligible overhead and run as generic CPU processes, incurring substantial system-level costs from core selection, context switches, page faults, and redundant network packet copies. These inefficiencies become a significant fraction of end-to-end latency in latency-sensitive applications such as embedding models, small language models, and agentic AI, yet no prior work has addressed tokenization at the hardware, operating system, and networking levels.
![Teaser figure](../imgs/ICML20260725/cropped_page0_idx0.webp)

## Input / Output

The system consumes text arriving as network packets (ingested via DPDK from the NIC) along with a standard tokenizer vocabulary (e.g., GPT-2 byte-level BPE merge rules), and produces token IDs written into a pinned memory zone that is exposed to the Python application as a zero-copy view. Unlike conventional request-response tokenizers, PinTok operates in a continuous poll mode, continuously consuming CPU cycles to request and process new queries, and the output is published to Python without any intermediate data copies.

## Method

PinTok is a tokenizer architecture that eliminates three categories of system overhead through dedicated hardware and OS configuration. First, core pinning (via isolcpus, nohz_full, rcu_nocbs, and irqaffinity boot parameters) dedicates CPU cores exclusively to the tokenizer, while memory pinning via 1 GB hugepages prevents page swaps and improves TLB hit rates by mapping large contiguous regions with single TLB entries. Second, the tokenizer runs in a continuous poll, run-to-completion mode on those dedicated cores, avoiding scheduler-induced context switches and making latency highly predictable. Third, DPDK kernel-bypass networking retrieves packets directly from the NIC into user-space pinned mbuf pools via polling (eliminating interrupts and kernel copies), and tokenization is fused with network protocol logic in a single user-space program—conceptually analogous to kernel fusion in deep learning—so that token IDs are written directly into a pinned buffer and published to Python with zero additional copies.

## Results

PinTok achieves latency reductions of up to 95% (average), 97% (P50), 94% (P90), and 87% (P99) over the Python baseline, with throughput improvements of up to 2,084%. On standalone tokenization (OpenWebText, 128 tokens), PinTok reaches 2,184,300 tokens/s versus 226,336 (Rust) and 100,009 (Python), with average latency of 59 μs versus 566 μs and 1,280 μs respectively. In end-to-end ML applications, PinTok reduces ChromaDB retrieval latency by 43% (11.35 ms vs. 20.06 ms), ChromaDB insertion by 16%, Qwen3 4B TTFT by 2.1%, and GPT-OSS 120b TTFT by 0.64% compared to Python.

## Baselines & Comparisons

PinTok is compared against two baselines: a high-performance Rust tokenizer (re-implementing GPT-2 byte-level BPE) and a standard Python tokenizer (HuggingFace-style). PinTok dominates both baselines across all three corpora (OpenWebText, mC4, GitHub Code) and all input lengths (128–2048 tokens). On standalone tokenization, PinTok achieves roughly 9–10× higher throughput than Rust and 15–20× higher than Python at 128 tokens, with the gap narrowing at 2048 tokens (PinTok ~3.3M vs. Rust ~2.0M vs. Python ~279K tokens/s on OpenWebText). In end-to-end embedding pipelines (e5-base-v2, ModernBERT-base, EmbeddingGemma-300m), PinTok consistently outperforms both baselines in throughput and all latency percentiles. The relative gains are largest for short, tokenizer-dominated workflows (ChromaDB retrieval: 43% saving) and smallest for long LLM inference (GPT-OSS 120b: 0.64%), confirming that PinTok's benefits scale with the fraction of time spent in tokenization.

## Relation to Prior Work

PinTok carves new ground by repurposing well-established systems-level techniques—DPDK kernel bypass, CPU core pinning, and hugepage memory pinning—from the high-performance networking literature and applying them to the tokenizer execution path. It is explicitly positioned as complementary to algorithm-level tokenizer improvements (BPE, WordPiece, SentencePiece) and to GPU-accelerated tokenization (Parallel BPE, RAPIDS cuDF), which the authors argue are ill-suited to the sequential, dictionary-lookup nature of most tokenization algorithms. No prior work has specifically targeted the OS scheduling, context-switch, and network-stack overheads that PinTok eliminates, making this a novel architectural contribution rather than an extension of a single prior method.

## Why It Matters / Open Questions

The paper makes a compelling case that as models shrink and inference accelerates (embedding pipelines, SLM routers, agentic AI), the previously negligible tokenizer becomes a measurable bottleneck, and that system-level overhead—not algorithmic complexity—dominates its latency. However, practical adoption is constrained: PinTok requires dedicated CPU cores, boot-time kernel configuration, and DPDK setup, making it less truly 'drop-in' than the API suggests. Open questions include whether streaming-aware subword algorithms can preserve accuracy under per-packet tokenization, and whether NIC-level deployment (in-network computing) can push latency further. For large LLMs, the end-to-end savings remain modest (~1%), limiting the immediate impact to latency-sensitive small-model and embedding workloads.
