## Problem

Existing GPU code-generation benchmarks treat tool invocation (compilation, verification, profiling) as an internal, ad-hoc feature of each evaluated system, confounding fair comparison of agentic workflows with private tooling and inconsistent budgets. Moreover, they lack out-of-distribution operators resistant to web-search leakage and do not support extensibility across evolving hardware backends and DSL extensions (e.g., TLX, Gluon), making them poor yardsticks for the iterative propose-compile-verify-evaluate loops that define modern agentic code generation.

## Input / Output

Each task provides a PyTorch reference implementation (torch_code), input shapes and data types, an expert-written Triton oracle for performance reference, and optional JSON descriptors for hardware micro-architecture and DSL surface area. The agent produces executable Triton kernel code, which is scored on Pass@K (fraction of K trials passing probabilistic verification against the PyTorch oracle on N random draws per shape) and Perf@K (best oracle-latency-to-generated-latency ratio among correct trials, where values above 1 indicate beating the human expert). The benchmark spans 122 tasks: 82 standard operators, 13 OOD operators with invented semantics, and 27 DSL-extension tasks.

## Method

TritonGym introduces a standardized function-call tool suite—compiler, probabilistic verifier, latency evaluator, web searcher, browser, and NCU profiler—that the benchmark exposes identically to all participating agents, cleanly separating intrinsic LLM capability from workflow design. The dataset is constructed from four sources (maintained production kernels, community samples, hand-crafted OOD operators with no public implementations, and TLX/Gluon extension tasks) to ensure generality against search-based trivialization and extensibility across backends. The evaluation harness reimplements representative agentic workflows (AlphaEvolve's evolutionary search with inspiration sampling, Geak's multi-agent generator-evaluator-reflector-optimizer pipeline) within the same tool interface, recording every invocation for reproducibility. Empirically, frontier LLMs (Claude-4.5, GPT-5, Qwen-3, DeepSeek-V3, Llama-4) are evaluated under one-shot and agentic settings, revealing that agentic workflows substantially improve correctness and performance over one-shot, with the largest gains on OOD and DSL-extension tasks, yet still leave meaningful headroom below expert oracles.

## Results

On the full TritonGym benchmark (122 operators), the best workflow-model combination (AlphaEvolve + Claude-4.5) achieves 54.8% Pass@1 and 0.583 Perf@1, substantially outperforming one-shot generation (32.8% Pass@1, 0.292 Perf@1). Agentic workflows consistently improve over one-shot: AlphaEvolve (avg.) reaches 42.3% Pass@1 vs. 36.7% for Geak (avg.) vs. 32.8% for one-shot (avg.) on the full benchmark. Performance degrades sharply on OOD operators (best: 61.5% Pass@1 with AlphaEvolve + Claude-4.5) and DSL-extension tasks (best: 33.3% Pass@1), indicating that memorization alone is insufficient. Qwen-3 offers the best cost efficiency at $60.1 per Pass@1 point, roughly 6× cheaper than Claude-4.5 ($368.0).

## Baselines & Comparisons

TritonGym reimplements two prior agentic workflows—Geak (Wang et al., 2025a) and AlphaEvolve (Novikov et al., 2025)—within its standardized function-call framework, enabling direct comparison under identical task sets, tool budgets, and evaluation harnesses. AlphaEvolve consistently outperforms Geak across all sample categories and all LLM backbones: on the full benchmark, AlphaEvolve (avg.) achieves 42.3% Pass@1 vs. 36.7% for Geak (avg.), with the gap widening on OOD operators (28.9% vs. 21.2%). Both agentic workflows beat one-shot generation by 4–10 percentage points in Pass@1 on the full benchmark, with the largest gains on OOD and DSL tasks where iterative feedback is most valuable. Among LLM backbones, Claude-4.5 dominates in absolute performance (54.8% Pass@1 with AlphaEvolve), while Qwen-3 delivers the best cost-efficiency ratio ($60.1 per Pass@1 point vs. $368.0 for Claude-4.5). Notably, no workflow-model combination exceeds Perf@1 of 1.0 on the full benchmark, indicating that even the best agentic systems remain below human-expert oracle performance.

## Relation to Prior Work

This paper carves new ground by reframing GPU kernel code generation evaluation from a static, single-shot paradigm to an agentic, tool-augmented one. Prior benchmarks (TritonBench, KernelBench, MultiKernelBench) evaluate generated code in isolation, while Geak introduces agentic workflows but bundles tool access inside each agent, confounding comparison. TritonGym departs from all of these by standardizing tool invocation through a function-call API (compiler, verifier, evaluator, profiler, searcher) that is identical across all participants, cleanly separating intrinsic model capability from workflow design. It also extends the evaluation surface beyond base Triton to DSL extensions (TLX, Gluon) and introduces deliberately out-of-distribution operators with no public implementations to prevent trivialization via web search.

## Why It Matters / Open Questions

TritonGym provides the first standardized, reproducible arena for comparing agentic GPU code generation workflows under identical tool access, budgets, and evaluation harnesses — a gap that has made prior comparisons unreliable. The results reveal that even frontier models paired with the strongest agentic workflow (AlphaEvolve + Claude-4.5) achieve only ~55% Pass@1 on the full benchmark and ~0.58 Perf@1, indicating substantial headroom and that LLM-based GPU kernel generation is far from production-ready. Open questions include whether the OOD operators sufficiently prevent memorization at scale, how results transfer to non-NVIDIA backends (AMD MI300, etc.), and whether the trial-budget framework adequately captures the cost of iterative refinement in real engineering settings. The paper's future work on auto-generated OOD operators, multi-GPU distributed kernels, and PyTorch backend integration suggests the benchmark is designed to grow with the field.
