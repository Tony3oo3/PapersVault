## Problem

Existing RL training pipelines for software engineering agents rely on per-task container images, incurring substantial storage overhead (hundreds of GB to TB), slow environment setup, and a hard dependency on container-management infrastructure. This makes scaling to larger batch sizes or rollout volumes prohibitively expensive and excludes researchers without access to dedicated container server clusters or orchestration privileges.
![Teaser figure](../imgs/ICML20265663/cropped_page2_idx1.webp)

## Input / Output

The system consumes GitHub issue descriptions paired with repository snapshots and agent-generated terminal commands, producing isolated per-instance sandbox environments where commands execute and test-based rewards are computed. Environments are pre-cached as compressed tar.gz archives of Python venvs (~100 MB each) plus the target repository, and are deployed into private directories at runtime. A bounded-concurrency I/O model (Ray resource tags + thread semaphores) caps parallel decompression to a fixed disk bandwidth budget (2000 MB/s in experiments), preventing filesystem saturation under high parallelism.

## Method

SWE-MiniSandbox replaces per-task containers with per-instance Linux mount namespaces and chroot-based filesystem isolation, assigning each task a private directory with bind-mounted system paths (/root, /mnt, /dev) and a copied Python venv. A pre-caching pipeline builds lightweight venv-based environments (rather than Conda or container images), installs task-specific dependencies, and archives them as tar.gz for reuse across runs. I/O contention is controlled by a concurrency model that limits simultaneous decompression tasks so aggregate throughput stays within a fixed disk bandwidth budget. The framework integrates as a drop-in replacement into SWE-Rex (terminal management), SWE-agent (task solving), and SkyRL (multi-node RL), distributing sandbox creation across cluster nodes via Ray remote functions without requiring Kubernetes or any container runtime. This reduces storage to ~5% and environment preparation time to ~25% of container-based baselines while maintaining comparable RL training performance on SWE-bench Verified.

## Results

On SWE-bench Verified, SWE-MiniSandbox achieves evaluation performance comparable to the container-based baseline: SWE-Agent-7B reaches 16.8 (vs. 16.4 for Docker), 3B reaches 9.2 (vs. 8.6), and 7B reaches 11.8 (vs. 12.4). Environment preparation time drops to ~23 s per instance (≈25% of the ~89 s Docker baseline), and average rollout time decreases from 342–367 s to 252–291 s. Storage is reduced to 13.5 GB for SWE-smith (≈5% of the 295 GB image-reuse baseline) and 89 GB for SWE-bench Verified (≈15% of the 605 GB one-to-one baseline).

## Baselines & Comparisons

Against the primary Docker-based SWE-agent baseline, MiniSandbox matches or slightly exceeds final SWE-bench Verified scores (16.8 vs. 16.4 for SWE-Agent-7B; 9.2 vs. 8.6 for 3B) while cutting environment preparation time by ~75% (23 s vs. 89 s) and reducing average rollout time by 15–25%. On storage, MiniSandbox uses 13.5 GB for 50k SWE-smith tasks versus 295 GB for SWE-smith's image-reuse strategy (≈5%), 100 GB for SWE-Mirror's task-mirroring approach, and 6 TB for SWE-Gym's one-to-one mapping. For SWE-bench Verified (500 tasks), MiniSandbox requires 89 GB compared to 605 GB for the one-to-one container approach (≈15%). The paper also validates evaluation fidelity: when the same patches are scored by both the official container pipeline and the MiniSandbox pipeline, there are zero false negatives and only 7–11 false positives (out of 500 instances) with no unexplained discrepancies, confirming that the lighter isolation does not compromise evaluation correctness.

## Relation to Prior Work

This paper builds directly on the SWE-agent/SWE-Rex agent-computer interface and the SkyRL multi-node RL training framework, repurposing their terminal-management and rollout-scheduling layers to run on a container-free backend. It departs from the dominant container-image paradigm established by SWE-Gym (one-to-one task-image mapping), SWE-smith (image reuse across tasks), and SWE-Mirror (task mirroring) by replacing per-instance containers with Linux mount namespaces and chroot, and by substituting container images with lightweight Python venv archives. The I/O-bottleneck management via Ray resource tags and bounded concurrent decompression is a new systems-level contribution not present in prior SWE environment pipelines.

## Why It Matters / Open Questions

By cutting environment storage to ~5% and setup time to ~25% of container-based baselines while maintaining comparable RL training and evaluation fidelity, MiniSandbox removes a major infrastructure barrier for researchers without dedicated container clusters or orchestration privileges. The paper opens a hybrid isolation spectrum—lightweight venv sandboxes for most Python SWE tasks, containers reserved for system-level work—which could reshape how SWE agent training environments are provisioned at scale. Key open questions include cross-platform portability (currently Linux-only), security guarantees for untrusted code under lighter isolation, and whether an overlay-filesystem design can further close the remaining I/O gap under extreme concurrency.
