## Problem

Fine-grained MoE LLMs on memory-constrained edge devices can only cache a small subset of experts in fast memory, forcing frequent fetches from slow storage (e.g., UFS, NVMe SSD) during autoregressive decoding. Standard MoE training uses load-balancing losses that spread tokens across experts for expert-parallel training, producing routing traces with poor temporal locality that are misaligned with the cache-resident working set needed for efficient single-request (B=1) decoding. This training-inference mismatch causes I/O thrashing that dominates decode latency on edge hardware.

## Input / Output

ReMoE takes an already-trained MoE checkpoint (e.g., DeepSeek-V2-Lite with 64 routed experts per layer, Top-K=6) and fine-tunes only the gate parameters θ_gate on a text corpus (OpenHermes 2.5, 100K samples, seq_len=2048) using teacher forcing. All non-router weights—embeddings, attention blocks, and expert FFNs—remain frozen, so the output is a set of updated gate weights that can be dropped into the original inference graph with zero runtime overhead. The fine-tuned model still produces standard text tokens at inference time; the only change is that the router now assigns higher probability to recently selected experts, yielding more cache-friendly Top-K selections.

## Method

ReMoE optimizes a composite objective L = L_CE + λ_KL·L_Trust + α_t·L_Loc, where L_CE is standard next-token cross-entropy, L_Trust is a KL divergence between the trainable routing distribution P_t and a frozen FP32 snapshot of the pretrained gate (acting as a soft trust region that limits semantic drift), and L_Loc is a temporal locality loss with four sub-terms: a reuse loss that maximizes the probability mass P_t assigns to the previous step's Top-K set (a differentiable surrogate for discrete overlap, using stop-gradient on the prior expert set for a one-way signal), a symmetric-KL smoothness loss penalizing adjacent-step distributional jitter, a lagged inertia loss aligning P_t with distributions at multiple earlier lags {1,2,4,8,16} to suppress slow drift, and a working-set compression loss minimizing the entropy of window-averaged routing distributions to encourage compact local expert subsets. The standard MoE load-balancing auxiliary loss is disabled during fine-tuning since it explicitly encourages the expert dispersion that conflicts with cache locality. The approach is architecture-agnostic (operates at the distribution level), requires no inference-time modifications, and is validated through trace-driven cache simulation, real-system serving on vLLM and Jetson Orin NX, and downstream benchmark evaluation.

## Results

On DeepSeek-V2-Lite, ReMoE increases the Expert Overlap Ratio (EOR) from 27.3% to 34.5% (+26.4% relative) while preserving downstream capability (MMLU +0.09 pp, HumanEval +2.44 pp, GSM8K −0.76 pp strict). Under vLLM GPU-CPU expert offloading, ReMoE improves output throughput from 3.58 to 3.88 tok/s (+8.4%) and reduces TPOT from 254.31 ms to 242.99 ms (−4.5%). On Jetson Orin NX with llama.cpp and NVMe SSD-backed expert storage, ReMoE reduces TPOT by 43.6–49.8% across ShareGPT, GSM8K, and HumanEval workloads, corresponding to a 1.77–1.99× decode speedup.

## Baselines & Comparisons

The paper compares ReMoE against two baselines: the pretrained router (Baseline) and a cross-entropy-only router fine-tuning (CE-only) that uses identical data, optimizer, and frozen-parameter settings but omits the locality regularizers and Trust-KL anchor. ReMoE clearly outperforms the pretrained baseline on all serving metrics: +8.4% throughput and −4.5% TPOT on vLLM, and −43.6% to −49.8% TPOT (1.77–1.99× decode speedup) on Jetson Orin NX. The CE-only baseline is substantially worse than both the pretrained baseline and ReMoE: it reduces EOR to 22.9% (below the baseline's 27.3%), degrades throughput to 2.95 tok/s (vs. 3.58 baseline), and increases TPOT to 286.82 ms (vs. 254.31 baseline), confirming that the gains require the explicit locality-aware objective rather than generic continued router adaptation. On capability benchmarks, ReMoE matches or slightly exceeds the baseline (MMLU +0.09 pp, HumanEval +2.44 pp) while CE-only degrades GSM8K by ~2 pp, further isolating the benefit to the locality and trust objectives.

## Relation to Prior Work

ReMoE carves out a distinct niche in the MoE inference-efficiency landscape by targeting the routing trace itself rather than the serving system. It departs from Oracle-MoE, which redesigns the routing architecture and retrains from scratch to preserve locality, by instead performing a lightweight post-training gate-only fine-tune on an already-trained checkpoint. It is complementary to runtime expert-offloading systems (MoE-Infinity, HOBBIT, KTransformers, Fiddler) and to cache-aware routing methods (Mixture of Cache-Conditional Experts) that modify inference-time behavior; ReMoE reshapes the routing distribution offline so that standard cache policies and inference graphs remain unchanged. The training-inference mismatch it exploits—load-balancing objectives that spread tokens across experts for expert-parallel training versus the compact working set that benefits single-request edge decoding—is identified as a previously under-addressed gap.

## Why It Matters / Open Questions

As edge devices gain sufficient storage (UFS 4.0, NVMe SSDs) and MoE models become the default scaling recipe, the cost of expert-weight I/O during decoding becomes a first-order bottleneck that system-level caching alone cannot fully hide. ReMoE offers a drop-in, architecture-agnostic fix (fine-tune only gate weights, ~8 hours on one GPU) that translates a 26% increase in step-to-step expert overlap into up to ~2× decode speedup on SSD-backed edge hardware, without adding any inference-time computation. Key limitations include the B=1, request-isolated evaluation setting (batched serving may dilute the locality benefit), a small but measurable GSM8K regression, and the fact that the vLLM/PCIe result is comparatively modest (8.4% throughput), suggesting the gains are most pronounced when storage bandwidth is the binding constraint. Open questions include interaction with aggressive prefetchers, behavior under multi-request batching, and whether the locality objective can be incorporated into pretraining rather than applied as a post-hoc fine-tune.
