## Problem

Translating natural-language design rules into correct, executable DRC scripts is a labor-intensive bottleneck in chip manufacturing, yet existing benchmarks are small (<200 rule-script pairs), evaluate via surface-level code similarity rather than execution correctness, and are often proprietary. Prior ML-based methods either ignore execution feedback from the DRC engine or unrealistically assume access to labeled evaluation layouts as agent input, leaving a gap in both evaluation infrastructure and selection-time test generation for this domain.

## Input / Output

The coding agent receives only a natural-language design rule and a ~60K-token KLayout API document as context; it must produce a KLayout DRC Ruby script without access to any evaluation layouts or ground-truth violation labels. The tester agent (SplitTester) additionally receives N candidate DRC scripts and iteratively generates GDSII test layouts via the KLayout Python API (pya), scoring each candidate by comparing its DRC engine output against LLM-predicted expected violation labels. The final output is a single selected DRC script, with correctness verified by exact agreement of violation outputs across 13,921 private evaluation layouts.

## Method

SplitTester is a tester agent for Best-of-N script selection that uses a single LLM in two roles (test generator and judge). It first generates an initial set of test layouts, executes all N candidate scripts, and clusters candidates by identical observed outputs. Its key mechanism is targeting the cluster that maximizes s_i·|C_i| (score × size) among non-singleton clusters—prioritizing groups that are both large and high-scoring—then generating new test layouts conditioned on K=3 randomly sampled representatives from that cluster to split it. This contrasts with CodeMonkey (which prunes to top-3 early) and S* (which samples from already-separated clusters). After exhausting the test budget or triggering early stopping (P consecutive failed splits), a final judge LLM selects the best script from the top-3 candidates using only the tests on which their outputs differ. The full pipeline is evaluated on the Rule2DRC benchmark (1,000 tasks spanning SkyWater130 PDK rules, synthetic multi-constraint rules, and syntax-coverage rules) using KLayout as the DRC engine.

## Results

On the Rule2DRC benchmark (1,000 tasks, 13,921 evaluation layouts), SplitTester consistently achieves the highest success rate across all three models and Best-of-N settings. On GPT-OSS-120B with BoN-20, SplitTester reaches 63.8% success and 4.1% error, compared to 62.7%/4.2% for CodeMonkey and 59.3%/4.2% for S*. On GPT-OSS-20B with BoN-20, the gap widens: SplitTester achieves 44.4% success versus 41.1% (CodeMonkey) and 38.2% (S*), while also reducing error from 14.0% to 12.6%. SplitTester also lies on the Pareto frontier of success rate vs. runtime, matching CodeMonkey's runtime while delivering higher accuracy.

## Baselines & Comparisons

SplitTester outperforms all three baselines across every model and BoN setting. Against LLM-as-a-Judge (Zheng et al., 2023), which selects without execution feedback, SplitTester gains 26.2 percentage points in success on GPT-OSS-120B BoN-20 (63.8% vs. 37.6%) and 16.4 points on GPT-OSS-20B (44.4% vs. 28.0%), while also reducing error rates by roughly 40–50 points. Against S* (Li et al., 2025), which generates additional tests for already-distinguishable clusters, SplitTester improves success by 4.5 points on GPT-OSS-120B BoN-20 (63.8% vs. 59.3%) and 6.2 points on GPT-OSS-20B (44.4% vs. 38.2%), attributed to targeting previously indistinguishable clusters rather than already-separated ones. Against CodeMonkey (Ehrlich et al., 2025), which prunes to top-3 before generating further tests, SplitTester gains 1.1 points on GPT-OSS-120B BoN-20 (63.8% vs. 62.7%) and 3.3 points on GPT-OSS-20B (44.4% vs. 41.1%), with the larger gap on the weaker model suggesting that premature top-3 pruning discards more promising candidates when initial test coverage is less discriminative. SplitTester also achieves the lowest error rate in most settings (e.g., 12.6% vs. 14.1% on GPT-OSS-20B BoN-20), and ablations confirm that the gains come from maintaining the full candidate pool during cluster-targeted test generation rather than from any single component in isolation.

## Relation to Prior Work

This paper repurposes the general LLM coding-agent + Best-of-N selection paradigm (Lightman et al., 2024; Brown et al., 2024) into the EDA/DRC domain, where prior work (Zhu et al., 2022/2023; Abdelmalak et al., 2025) treated script synthesis as one-shot translation evaluated by code similarity, and DRC-Coder (Chang et al., 2025) used execution feedback but required labeled evaluation layouts as input. For the selection component, SplitTester departs from CodeMonkey (Ehrlich et al., 2025), which prunes to top-3 before generating tests, and S* (Li et al., 2025), which targets already-separated clusters, by explicitly targeting large indistinguishable clusters and maintaining the full candidate pool throughout test generation. The benchmark itself carves new ground by being an order of magnitude larger than prior DRC evaluation sets and by enabling execution-based scoring without requiring test layouts as agent input.

## Why It Matters / Open Questions

DRC script synthesis is a genuine industrial bottleneck in chip manufacturing, and the open-source Rule2DRC benchmark (1,000 tasks, 13,921 layouts) provides the first large-scale, execution-grounded evaluation platform for this task, lowering the barrier for future research at the EDA–ML intersection. The modest but consistent gains from SplitTester (1–3 points over CodeMonkey) and the ablation showing that both expected-label scoring and final judging are complementary (neither sufficient alone) offer practical guidance for building execution-guided selection agents. Open questions include whether the approach generalizes beyond KLayout/GDSII to other DRC engines and scripting languages, whether it scales to the far more complex multi-layer rules at sub-7nm nodes, and whether the ~64% ceiling at BoN-20 with the strongest model reflects a fundamental difficulty in the task or a limitation of current LLMs in domain-specific code generation.
