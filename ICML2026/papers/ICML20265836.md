## Problem

LLM agents frequently generate incorrect tool calls due to long contexts, high task complexity, and rigid tool definitions. While iterative refinement using real tool execution results can improve tool calls, this process is expensive (API fees, rate limits) and risks unsafe side effects such as unintended tweets, file deletions, or order placements. Existing test-time scaling methods for tool use rely on repeated real-tool calls for feedback, creating a cost-safety gap that this paper addresses.

## Input / Output

Gecko accepts a user task description, tool definitions in heterogeneous formats (OpenAPI 3.1, Python functions, natural-language descriptions), and candidate tool-call sequences from a planning LLM. It produces three types of structured feedback—argument validation errors, schema-conforming simulated tool responses, and task-level completion/failure judgments with remaining objectives—along with a running task-state estimate. The final output of GATS is a validated tool-call trajectory prepended to the original user message as in-context guidance for a separate real-tool agent, rather than the simulated outputs themselves being executed.

## Method

Gecko is a stateful simulation environment with five components: a rule-based plus LLM-based argument validator, an LLM-based response generator conditioned on the tool schema and current task state, an LLM-based task state estimator that tracks cumulative effects of prior calls, an LLM-based task feedback generator that decomposes the objective into a checklist and judges completion, and an LLM-based schema converter that unifies heterogeneous tool definitions into OpenAPI 3.1. GATS, the test-time scaling method built on Gecko, lets a planning LLM iteratively generate candidate trajectories in isolated simulation sessions; each failed attempt returns validation errors, simulated responses, and task-level feedback to guide the next retry, while a successful trajectory is extracted as in-context guidance for the final real-tool agent. The key design choice is maintaining a compact textual task state across calls to ensure cross-call consistency in simulated responses and to enable task-level (rather than per-call) completion judgment, which prior real-tool feedback loops cannot provide without executing the full sequence.

## Results

On BFCLv3, GATS consistently improves all tested planning LLMs: GPT-4o rises from 76.93% to 84.62% overall accuracy (+7.69 pp), Gemini-3.0-pro from 79.97% to 85.19% (+5.22 pp), and GPT-5 from 61.94% to 66.08% (+4.14 pp). On τ²-bench, GATS yields 3–8 pp pass@1 gains, e.g., GPT-4o improves from 54.2% to 60.7% and Gemini-3.0-pro from 78.8% to 82.3%. In direct comparisons against other test-time scaling methods (Table 5), GATS achieves the best accuracy on both τ²-airline (65.0% vs. 60.0% for Reflexion) and BFCLv3 Multi-Turn-Base (72.0% vs. 66.0% for Majority Voting) while using fewer real tool calls than Self-Refine and Best-of-N.

## Baselines & Comparisons

Against SOTA reference models on BFCLv3, Gemini-3.0-pro+GATS (85.19%) surpasses xLAM-2-70b (80.96%) and watt-tool-70B (79.27%), while GPT-4o+GATS (84.62%) also exceeds both. On τ²-bench, Gemini-3.0-pro+GATS (82.3% overall) outperforms Claude Opus 4 (70.9%), Claude Sonnet 4 (65.3%), and Kimi-K2-Instruct (63.6%). In head-to-head comparisons with other test-time scaling methods (Table 5), GATS wins on both settings: on τ²-airline with GPT-5-mini it achieves 65.0% pass@1 versus 60.0% for Reflexion, 59.0% for Self-Refine, 58.5% for Best-of-N, and 59.0% for Majority Voting; on BFCLv3 Multi-Turn-Base with GPT-4o it reaches 72.0% versus 63.5% (Reflexion), 64.5% (Self-Refine), 63.0% (Best-of-N), and 66.0% (Majority Voting). GATS also uses fewer real tool calls than Self-Refine (7.76 vs. 23.88 on τ²-airline) and Best-of-N (7.76 vs. 13.78), while consuming fewer tokens than Best-of-N and Majority Voting in both settings. The Merge-to-one variant (collapsing Gecko into a single prompt) underperforms the baseline, confirming that structured simulation is essential rather than prompt-only emulation.

## Relation to Prior Work

Gecko carves out a distinct niche between two existing lines of work: (1) test-time refinement methods that rely on real tool execution for feedback (Reflexion, Self-Refine, ConAgent, TRICE), which incur API costs and risk unsafe side effects, and (2) simulation/evaluation environments (StableToolBench, τ-bench, ToolSandbox) that are either domain-specific, require pre-collected real responses, or lack stateful task-level feedback. Gecko's key conceptual departure is a general-purpose, schema-driven simulation that synthesizes responses from OpenAPI definitions alone, maintains a running task state, and produces three complementary feedback signals (argument validation, simulated responses, task-completion judgement) specifically designed to drive iterative pre-execution refinement rather than post-hoc evaluation.

## Why It Matters / Open Questions

Gecko provides a practical, low-cost sandbox that removes the primary barrier to test-time refinement of tool calls—namely, the expense and irreversibility of real API calls—while the hybrid mode (real read-only tools + simulated write tools) offers a deployable strategy for domains with hidden database state. The paper also identifies two forward-looking applications: using Gecko as a verifier for tool-call data synthesis pipelines and as an RL environment for tool-use training. Key open questions include how well simulated responses track real behavior for tools with rapidly changing backends or non-text outputs, and whether the observed ceiling effect (~95% on certain BFCL subsets across diverse LLMs) reflects a limitation of Gecko's simulation fidelity or of the benchmark itself.
