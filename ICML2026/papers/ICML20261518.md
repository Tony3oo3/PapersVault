## Problem

While LLMs have been extensively evaluated on code correctness (SWE-Bench) and function-level algorithmic efficiency (Mercury, EffiBench), no benchmark exists for repository-level code performance optimization in authentic software contexts. This paper asks whether language models can meaningfully optimize execution time across multi-file, multi-module codebases, a task that demands cross-cutting understanding and specialized optimization expertise beyond what prior benchmarks capture.
![Teaser figure](../imgs/ICML20261518/cropped_page1_idx0.webp)

## Input / Output

Each instance provides a full repository codebase (averaging 447 non-test files, 170k lines), a set of target functions (7.6 for Oracle, 30.1 for Realistic), performance-related unit tests, and a Docker-executable environment. The model produces a unified diff patch applied to the original codebase; evaluation then re-runs the performance tests on both pre- and post-patch codebases under identical single-core/16 GB constraints. The Performance metric is not a simple speedup ratio but a statistically significant minimum gain (δ) computed via Mann-Whitney U test over 20 repetitions with IQR outlier filtering, ensuring measured improvements exceed noise.

## Method

SWE-Perf is constructed through a five-phase pipeline that filters 102,241 pull requests from 12 popular GitHub repositories down to 140 verified instances. Phase 2 builds Docker images and runs all unit tests (3 replicates) on both pre- and post-patch codebases; Phase 3 filters for PRs where tests pass in both versions and the runtime ratio exceeds 0.3, then uses dynamic execution (yappi) to confirm tests actually exercise the patched code; Phase 4 verifies stability via 20 repetitions, IQR outlier removal, and a conservative Mann-Whitney U test (Algorithm 1) requiring δ > 0.05. Evaluation employs a three-level framework (Apply → Correctness → Performance) under two settings: Oracle (file-level, chain-of-thought prompting with relevant files) and Realistic (repo-level, autonomous agents like OpenHands or Agentless navigating the full codebase). The expert-authored patch from each PR serves as the human gold standard against which all model outputs are benchmarked.

## Results

On SWE-Perf (140 instances from 9 repositories), the expert reference achieves 10.85% average performance gain with 100% apply and correctness rates. Among LLMs, OpenHands (agent-based, Claude-3.7-sonnet) achieves the best performance at 2.26% with 77.86% correctness, while Agentless (pipeline-based, same model) reaches only 0.41% performance with 70.71% correctness. In the Oracle (file-level) setting, the best model (Claude-4-sonnet) achieves 1.76% performance, still far below the expert's 10.85%. All models exhibit a substantial capability gap of 8.59–10.44% relative to expert-level optimization.

## Baselines & Comparisons

The paper compares two representative repository-level SWE frameworks—Agentless (pipeline-based) and OpenHands (agent-based)—both using Claude-3.7-sonnet as the base model, against an expert reference. OpenHands clearly outperforms Agentless on all three metrics: 2.26% vs. 0.41% performance gain (a 5.5× difference), 77.86% vs. 70.71% correctness, and comparable apply rates (87.86% vs. 88.57%). However, both methods fall far short of the expert's 10.85% performance gain, with OpenHands still 8.59 percentage points behind. In the Oracle (file-level) setting, even the strongest single-pass model (Claude-4-sonnet at 1.76%) cannot match OpenHands' repo-level result, suggesting that iterative agent-based reasoning provides a meaningful advantage over one-shot generation for performance optimization. The paper also notes that on specific repositories (e.g., sklearn), OpenHands slightly exceeds expert performance by 0.4%, hinting at early-stage breakthroughs in narrow domains.

## Relation to Prior Work

This paper sits at the intersection of two previously separate research threads: repository-level software engineering benchmarks (SWE-Bench, SWE-Gym, SWE-Dev) that evaluate correctness/bug-fixing, and code efficiency benchmarks (Mercury, EFFIBENCH, EvalPerf, KernelBench) that evaluate function-level performance on algorithmic problems. It adopts the PR-collection and Docker-environment methodology from SWE-Bench and SWE-Gym but repurposes them for a fundamentally different objective—measuring runtime improvement rather than test-pass correctness. The concurrent work GSO also targets performance-improving code changes but relies on LLM-based judges and commit-level heuristics, whereas SWE-Perf uses full pull requests with executable runtime environments and statistical verification.

## Why It Matters / Open Questions

SWE-Perf establishes the first systematic evaluation standard for a capability—repository-level performance optimization—that production software engineering demands but no prior benchmark has measured. The large gap between the best LLM system (OpenHands at 2.26%) and expert performance (10.85%) quantifies how far current models are from practical utility in this domain, while the occasional model superiority on specific repositories (e.g., sklearn) hints at emerging competence. Key limitations include coverage of only 9 Python repositories, reliance on human patches as a potentially suboptimal gold standard, and the constraint of providing target functions rather than full-repo optimization. Open questions include whether models can scale to longer-runtime optimizations, handle multi-function scenarios without degradation, and eventually operate without explicit target-function guidance.
