## Problem

Distributed LLM workloads spend 20–80% of runtime on communication, yet existing tools force a choice between rigid, non-programmable libraries (NCCL, CuBLAS) that block architectural exploration and single-device tile compilers (Triton, TileLang) that lack a unified multi-level abstraction spanning the full cluster hierarchy. No prior system provides a portable, tile-level programming model that simultaneously handles in-device compute, intra-node NVLink transfers, and inter-node NIC communication within a single fused kernel.

## Input / Output

Users write Triton-compatible tile programs augmented with three levels of distributed primitives: core-level signal control and NVLink Sharp operations on static-shaped tiles, device-level DMA/NIC transfers (putmem, getmem) with runtime-dynamic chunk sizes for MoE routing, and task-level registration of entire Triton kernels into a software-scheduled DAG. The compiler emits a single fused MegaKernel as GPU assembly (via LLVM IR with extern-linked NVSHMEM or rocSHMEM symbols), eliminating separate kernel launches for compute and communication. The system requires hardware topology (NVLink, PCIe, IB bandwidths) and parallelism configuration (TP/SP/EP/PP team sizes) as compile-time or runtime parameters.

## Method

DITRON introduces a three-level hierarchical tiling abstraction that maps program semantics to distinct hardware domains: core-level tiles (e.g., 128×128) target Tensor Cores and TMA engines, device-level chunks target asynchronous DMA/RDMA engines with dynamic shapes, and task-level DAGs fuse the entire model into one persistent MegaKernel with a software-maintained scoreboard. The key mid-end optimization is distributed swizzling, which reorders tile execution so each rank begins processing tiles whose data is locally available or already in transit, effectively treating local HBM as a cache for remote memory (Gather mode) or prioritizing tiles destined for the furthest nodes (Scatter mode). The back-end abstracts all communication into hardware-agnostic OpenSHMEM-compliant primitives (distributed, SIMT, and SHMEM device classes), enabling portability by instantiating translation rules per backend—currently supporting NVIDIA (NVSHMEM) and AMD (rocSHMEM) across NVLink, xGMI, PCIe, and InfiniBand fabrics. Additional low-level optimizations include a low-latency protocol bypassing expensive synchronization handshakes, D2D copy fusion into kernels to eliminate driver launch jitter, and software barriers using volatile load/store for PCIe platforms lacking hardware atomics.

## Results

On 8×H800 GPUs, DITRON achieves geometric mean speedups of 1.27×–19.18× over CuBLAS+NCCL across five fused compute-communication workloads (AG-GEMM, GEMM-RS, GEMM-AR, AG-MoE, MoE-AR), and 6%–30% speedups over expert-tuned overlapping CUDA libraries (FLUX, COMET). End-to-end, integrating DITRON into vLLM yields 5%–30% throughput gains for batch sizes above 128, reaching 12k tokens/s on LLaMA3-70B and 17k tokens/s on Qwen3-32B. For distributed MegaKernel inference, DITRON achieves 6.28× speedup over PyTorch Eager and 1.73× over Mirage. On PCIe GPUs, the average speedup over CuBLAS+NCCL reaches 8.33×.

## Baselines & Comparisons

DITRON consistently outperforms the non-overlapping CuBLAS+NCCL baseline across all five workloads, with the largest gains on MoE workloads (19.18× for AG-MoE, 13.89× for MoE-AR) where dynamic shapes and expert routing make static libraries particularly ineffective. Against the tile-level compiler TileLink, DITRON wins on AG-GEMM (1.13×) and AG-MoE (1.89×) but only marginally on GEMM-RS (1.02×), reflecting TileLink's strength in scale-up scenarios. Compared to the hand-tuned FLUX library, DITRON achieves 1.09× on AG-GEMM and 1.30× on GEMM-RS, while matching FLUX's performance on GEMM-AR (which FLUX does not support). Against COMET, DITRON leads by 1.06× on AG-MoE. In end-to-end vLLM integration, DITRON slightly underperforms vLLM's native AllReduce for small batches (<128) but delivers 5%–30% throughput gains at larger batches. For the MegaKernel setting, DITRON surpasses Mirage by 1.73× and PyTorch+CUDAGraph by 1.33×. On the emerging GLA SP operator, DITRON outperforms the SOTA LASP2 baseline by 7% at 16 GPUs and by 38% at 128 GPUs (6.83 ms vs. 11.07 ms), demonstrating its advantage in scaling communication-computation pipelines.

## Relation to Prior Work

DITRON extends the Triton tile-level programming model to the distributed setting, building on the observation that tile compilers have become the dominant kernel programming paradigm in industry. It departs from prior compute-communication overlap libraries (FLUX, COMET) by replacing hand-tuned CUDA/PTX kernels with a programmable compiler, and from distributed DSLs (CoCoNet, DistEinsum) by operating at tile granularity rather than operator granularity. The three-level tiling abstraction (core, device, task) generalizes single-node tile compilers like TileLink and Pallas to multi-node clusters, while the hardware-agnostic OpenSHMEM-based primitives distinguish it from NVSHMEM-only approaches. The MegaKernel task-level scheduling extends prior single-device MegaKernel work (Mirage, Spector et al.) to the distributed setting with a software-maintained scoreboard.

## Why It Matters / Open Questions

With communication accounting for 20–80% of runtime in distributed LLM workloads, a flexible, portable compiler that matches expert-tuned CUDA kernels lowers the barrier for researchers to prototype new distributed algorithms without deep systems expertise. The enterprise deployment (500K GPU-hours saved monthly, >10% MFU improvement) demonstrates real-world impact, and the demonstrated portability to AMD and PCIe platforms addresses a critical gap in the current NVIDIA-centric ecosystem. Open questions include whether the three-level abstraction remains sufficient as hardware hierarchies evolve (e.g., chiplet-based GPUs, in-network compute), how the approach scales beyond 128 GPUs, and whether the compiler can automatically discover optimal tiling/swizzling configurations without manual tuning.
