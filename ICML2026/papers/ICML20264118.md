## Problem

Existing cybersecurity benchmarks for AI agents are limited in scale, scope, or realism: many evaluate only a subset of the vulnerability lifecycle (detection or patching in isolation), provide agents only read-only code access rather than realistic build environments, lack valid post-patch functionality testing, or rely on synthetic data. No prior benchmark simultaneously covers the full end-to-end lifecycle (vulnerability discovery → PoC generation → patch generation) at scale with realistic agentic evaluation environments and developer-written test validation.
![Teaser figure](../imgs/ICML20264118/cropped_page3_idx0.webp)

## Input / Output

In the end-to-end setting, agents receive only the vulnerable C/C++ codebase (median 1,811 files, 613K lines) inside a Dockerized build environment with sanitizer-enabled compilation; in the patch-only setting, they additionally receive the ground-truth PoC binary and crash log. Agents must produce a PoC input file (ranging from a few bytes to 1 MB) that triggers a sanitizer crash and a git-diff-format patch (median 1 file, 7 lines; up to 29 files, 3,988 lines). Evaluation is sequential across four stages: S1 (PoC crashes unpatched binary), S2 (patch eliminates the agent's PoC crash), S3 (developer-written functionality tests pass on patched code), and S4 (patch also eliminates the ground-truth PoC crash, confirming the intended vulnerability was fixed).

## Method

The core contribution is an automated, agent-enhanced pipeline that transforms OSS-Fuzz historical vulnerability data into reproducible end-to-end evaluation environments. Step 1 binary-searches commit history to identify clean single-commit patches; Step 2 reconstructs Dockerized build environments for both vulnerable and patched revisions, validating PoC triggerability; Step 3 deploys a code agent inside the patched repository to identify, build, and run developer-written unit tests (adding necessary build dependencies to the original OSS-Fuzz scripts); Step 4 applies expert validation of test correctness and coverage. The evaluation places agents directly in the same sandboxed build environment as the codebase (with network access disabled and test files locked), mimicking real engineer deployment rather than providing read-only code access. This yields 920 tasks across 139 open-source projects, with the pipeline designed to scale to future vulnerabilities as OSS-Fuzz discovers new ones.

## Results

On the initial 615-task benchmark, the best patch-only success rate is 82.3% (Claude Opus 4.5 + Claude Code), while the best end-to-end S3 (tests pass) rate is only 22.6% (Gemini 3 Pro + Gemini CLI), revealing that vulnerability discovery—not patch generation—is the primary bottleneck. On the expanded 920-task benchmark with newer models, GPT-5.4 achieves the highest end-to-end S3 rate of 65.9% and S4 (matching ground-truth vulnerability) of 22.2%, while Claude Opus 4.6 without a cost cap reaches 62.6% S3 and 26.2% S4. Even the strongest configurations succeed on fewer than 70% of end-to-end tasks, confirming that full-lifecycle cybersecurity remains challenging for state-of-the-art agents.

## Baselines & Comparisons

CyberGym-E2E is the only benchmark in Table 1 that simultaneously covers all four lifecycle stages (detection, PoC generation, patch generation, post-patch functionality testing), provides a realistic agentic environment, and operates end-to-end at scale (920 vulnerabilities, 139 projects). The closest competitor, BountyBench, also evaluates end-to-end but covers only 40 tasks due to fully manual curation; CyberGym-E2E is 23× larger. Among evaluated agents, GPT-5.2-Codex leads in vulnerability discovery (S1 = 30.2%) while Claude Opus 4.5 leads in patch-only performance (82.3%), but no single model dominates all stages—Gemini 3 Pro achieves the best overall end-to-end S3 (22.6%) by balancing detection and patching. The large gap between patch-only (58–82%) and end-to-end S3 (5–23%) across all models confirms that independent vulnerability discovery, not code repair, is the binding constraint. On the expanded 920-task set, GPT-5.4 (65.9% S3) substantially outperforms Opus 4.6 (37.9% S3) under the same $10/90-min budget, though Opus 4.6 without a cost cap narrows the gap to 62.6%.

## Relation to Prior Work

This paper extends the line of cybersecurity benchmarking work (CyberGym, BountyBench, SeCodePLT, SEC-bench) by being the first to combine end-to-end vulnerability lifecycle evaluation (detection → PoC → patch) with a realistic agentic environment, post-patch functionality testing, and large scale (920 vulns, 139 projects) in a single benchmark. It builds on OSS-Fuzz vulnerability data and ARVO's Dockerized infrastructure but introduces an automated, agent-enhanced pipeline for reconstructing build environments, identifying developer-written test suites, and validating coverage—addressing the manual curation bottleneck that limited BountyBench to 40 tasks. The key conceptual departure from prior work is treating the full vulnerability lifecycle as a single sequential task in a sandboxed build environment rather than evaluating detection, PoC, and patching as independent subtasks.

## Why It Matters / Open Questions

The benchmark reveals that vulnerability discovery, not patch generation, is the primary bottleneck for state-of-the-art agents (82% patch-only vs. 19–38% end-to-end S3), redirecting research attention toward code understanding and data-flow analysis rather than code editing. The finding that agents frequently fix a different vulnerability than the ground-truth one (S3 >> S4 gap) suggests current agents lack precise root-cause localization. Key limitations include restriction to C/C++ memory-safety vulnerabilities validated via sanitizer crashes, and the $10/90-min budget that constrains expensive models; extending to logic bugs, injection flaws, and other languages remains open. As a scalable, automated pipeline, it provides a practical foundation for ongoing evaluation as new vulnerabilities emerge.
