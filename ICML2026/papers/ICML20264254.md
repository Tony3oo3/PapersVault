## Problem

Existing tool-use agents equip a single powerful model with utility tools, underutilizing the potential of heterogeneous resources including other LLMs as callable tools. Prompting off-the-shelf models to act as orchestrators introduces systemic biases—self-enhancement bias (favoring one's own variants) and defaulting to the strongest tool regardless of cost—making naive prompting brittle for complex multi-tool coordination. The paper addresses how to train a small model to strategically orchestrate diverse tools and models while simultaneously optimizing for correctness, computational efficiency, and user-specified tool preferences.

## Input / Output

The orchestrator receives a user task instruction (optionally augmented with a natural-language preference instruction specifying cost/latency/tool-usage trade-offs), a JSON-defined tool set with typed parameter schemas, and a preference vector P encoding the user's optimization priorities. It produces a multi-turn trajectory (capped at 50 turns) of alternating chain-of-thought reasoning and structured tool calls, terminating with a final answer. Tools include basic utilities (web search via Tavily, Python sandbox, Faiss-based local search, domain-specific APIs), specialized LLMs (code writers, math models), and generalist LLMs (GPT-5, Claude Opus 4.1, etc.), all exposed through a single unified calling interface.

## Method

ToolOrchestra trains an 8B-parameter Qwen3-8B model end-to-end via Group Relative Policy Optimization (GRPO) with a composite reward that jointly optimizes binary outcome correctness, monetary compute cost, wall-clock latency, and per-tool usage frequency projected onto a user preference vector. The reward is computed by normalizing a trajectory-level vector of tool invocation counts, outcome, compute, and latency across a rollout batch, then taking the dot product with the preference vector P (zeroed if the task is unsolved). To supply verifiable training data, the authors build ToolScale, an automatic synthesis pipeline that generates domain-specific databases, tool APIs, and multi-turn tasks across 10 domains with golden trajectories, filtered for solvability and non-triviality. Training stability is maintained through three filtering strategies: homogeneity filtering (discarding batches with reward std < 0.1), format consistency filtering, and invalid output filtering. The key architectural insight is that a lightweight orchestrator, trained with multi-objective RL beyond accuracy alone, can coordinate more intelligent tools more effectively and cost-efficiently than any monolithic model, generalizing robustly to unseen tools and pricing configurations.

## Results

On HLE, Orchestrator-8B achieves 37.1%, surpassing GPT-5 with basic tools (35.1%) while using only ~30% of the cost (9.2¢ vs 30.2¢) and 2.5× less latency (8.2 min vs 19.8 min). On FRAMES, it reaches 76.3% (vs. GPT-5's 74.0%), and on τ²-Bench it scores 80.2% (vs. GPT-5's 77.7%). In the full tool-set configuration (basic tools + specialized + generalist LLMs), Orchestrator-8B outperforms all baselines including Qwen3-235B-A22B (32.8 HLE), Claude Opus 4.1 (34.6 HLE), and GPT-5 (21.2 HLE) at a fraction of their cost.

## Baselines & Comparisons

Orchestrator-8B outperforms GPT-5 with basic tools by +2.0 on HLE (37.1 vs 35.1), +2.3 on FRAMES (76.3 vs 74.0), and +2.5 on τ²-Bench (80.2 vs 77.7), while reducing cost from 30.2¢ to 9.2¢ (~3.3× cheaper). Against the full tool-set configuration, Orchestrator-8B beats Claude Opus 4.1 (34.6 HLE) by +2.5 points at 5.7× lower cost (9.2¢ vs 52.5¢), and Qwen3-235B-A22B (32.8 HLE) by +4.3 points at 3.2× lower cost. GPT-5 in the full tool-set setting actually degrades to 21.2 HLE due to its inherent bias toward calling GPT-5-mini, making Orchestrator-8B superior by +15.9 points. Among prior tool-use frameworks, RestGPT (21.6 HLE) and ToolLlama (18.8 HLE) are outperformed by 15.5 and 18.3 points respectively, while ToRL (0.9 HLE) and RouteLLM (7.2 HLE) are far behind due to their narrow tool scopes. GPT-4o (5.3 HLE) is the weakest baseline, trailing Orchestrator-8B by over 31 points.

## Relation to Prior Work

This paper extends the tool-use agent literature (Toolformer, ToolLLM, ToRL, Search-R1) by introducing an orchestration paradigm where a small language model coordinates not only deterministic tools (search, code interpreter) but also other LLMs treated as intelligent tools. Methodologically, it builds on GRPO (Shao et al., 2024) for policy-gradient RL but departs from prior tool-use RL work (ToRL, ToolRL, OTC) by optimizing a multi-objective reward that jointly balances outcome correctness, compute/latency efficiency, and user-specified tool preferences, rather than accuracy alone. The paper also contrasts with model-routing approaches like RouteLLM, which select between two fixed models, by training a general-purpose orchestrator that plans multi-turn, multi-tool trajectories over a heterogeneous and dynamically varying toolset.

## Why It Matters / Open Questions

The result that an 8B orchestrator outperforms GPT-5 on HLE while using ~40% of the cost suggests a practical path toward cost-efficient agentic systems that do not require monolithic frontier models for every step. The multi-objective RL framework and the ToolScale synthetic dataset provide reusable infrastructure for training controllable, preference-aware tool-use agents. Key open questions include whether the orchestration paradigm scales to recursive or hierarchical orchestrators, how robust the approach is when the available toolset shifts substantially (e.g., new model releases), and whether the heavy reliance on proprietary API access (GPT-5, Claude Opus 4.1) limits reproducibility and long-term viability of the system.
