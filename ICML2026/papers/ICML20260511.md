## Problem

Repetitive GUI tasks (e.g., daily report filing, flight booking) are poorly served by existing approaches: ReAct-style LLM agents incur substantial per-instance token costs, while traditional RPA scripts are brittle and require significant manual development effort. The paper asks whether LLM agent interactions can be automatically distilled into robust, reusable RPA functions that handle both environmental and instruction variations without repeated LLM reasoning at test time.
![Teaser figure](../imgs/ICML20260511/cropped_page1_idx0.webp)

## Input / Output

The system takes a user-specified task type with N natural-language task instances (e.g., 'Create a note named {file_name} with text {text}'), GUI screenshots annotated via Set-of-Mark, and DOM/accessibility-tree element lists as observations. It produces a parameterized Python RPA function F_k that uses env_op primitives (find_element, click, input_text, ask_mllm) to execute a GUI action trajectory; the function's parameters are extracted from the test-time task instruction by a lightweight executor agent. The RPA code is verified against all building tasks before deployment, and a ReAct fallback is retained for task types where code verification fails after M refinement rounds.

## Method

AutoRPA operates in three phases. First, a ReAct agent explores the GUI to collect successful trajectories, while a translator agent converts each hard-coded action (e.g., click(index=2)) into a soft-coded equivalent that locates elements by semantic attributes (text, content_description, editable) via a find_element function, with a GUI grounding model resolving ambiguities. Second, a builder agent synthesizes the RPA function from the simplified translated trajectory, augmented with a tree-organized RAG mechanism (bottom: interaction blocks; middle: simplified trajectory; top: conclusion) that lets the builder proactively call fetch_info to retrieve detailed observations when its assumptions about the interface are uncertain. Third, a hybrid repair strategy validates the code on seen tasks: on failure, an analyzer agent diagnoses the breakpoint, the ReAct agent resumes from that point to produce a corrective trajectory, and the builder refines the code using the concatenated hybrid trajectory. This iterative loop (up to M rounds) yields RPA functions that reduce token usage by 82–96% relative to ReAct while matching or exceeding its success rate.

## Results

On AndroidWorld with GPT-5, AutoRPA achieves 75.9% success rate using only 30.6k tokens per task, outperforming ReAct† (74.1%, 142.5k tokens) and M3A (57.0%, 164.6k tokens) while reducing token consumption by ~78%. The code-only variant (AutoRPA code only) reaches 70.7% success with just 6.2k tokens, a 95.7% reduction over ReAct†. On MiniWoB++ (all 53 task types) with GPT-4.1, AutoRPA achieves 95.4% success with 1.4k tokens versus ReAct†'s 92.8% at 9.2k tokens, and on the 9 hard tasks it reaches 91.1% vs. ReAct†'s 84.4%.

## Baselines & Comparisons

AutoRPA consistently outperforms all ReAct-style baselines (SeeAct, M3A, ReAct†) on AndroidWorld across all three model backbones, achieving higher success rates with 18–25% of the token cost. On MiniWoB++, AutoRPA surpasses ReAct† by 6.7 points on hard tasks (91.1% vs. 84.4%) and by 2.6 points on all tasks (95.4% vs. 92.8%), while using less than 10% of the tokens. Against skill-learning methods, AutoRPA matches AutoManual on hard tasks (91.1% vs. 91.1%) and slightly exceeds it on all tasks (95.4% vs. 95.2%), and substantially outperforms AdaPlanner (95.4% vs. 90.3% on all tasks) without requiring multiple expert demonstrations. Against the most advanced GUI agents on AndroidWorld (Table 5), AutoRPA with GPT-5 (75.9%) exceeds Mobile-Agent-v3 (73.3%), Gemini-2.5-CU (69.7%), and Agent S3 (68.1%), while using a fraction of the per-task token budget. The code-only variant, which executes only the synthesized RPA without any ReAct fallback, still matches or exceeds ReAct† on success rate in most settings, confirming that the generated RPA code itself is robust.

## Relation to Prior Work

AutoRPA sits at the intersection of two well-studied but previously disconnected lines of work: ReAct-style LLM GUI agents (Yao et al., 2023; Zheng et al., 2024; Rawles et al., 2025) that achieve flexibility at high per-instance token cost, and traditional RPA (Ivanciic et al., 2019) that offers runtime efficiency but demands manual scripting. The paper departs from skill-learning approaches (AutoManual, ICE, ExpeL) that still invoke the LLM at test time, and from Plan-and-Execute code generation (RCI, AdaPlanner) that struggles with robustness without curated demonstrations, by introducing a translator-builder pipeline that distills hard-coded ReAct trajectories into soft-coded, standalone RPA functions. The tree-organized retrieval mechanism (adapted from RAPTOR, Sarthi et al., 2024) and the reflection-based exploration (Shinn et al., 2023) are repurposed as supporting components within this new synthesis architecture.

## Why It Matters / Open Questions

The 82–96% token reduction while matching or exceeding ReAct success rates addresses a critical deployment bottleneck: repetitive GUI tasks (daily reports, flight bookings) currently incur full LLM reasoning cost per instance, making large-scale automation economically impractical. The framework's ReAct-agnostic design means it can wrap any capable GUI agent, broadening its applicability. Key limitations remain: the method requires DOM/accessibility trees (not pure vision), needs multiple task instances per type for the building phase, and the builder agent still shows gaps versus human programmers in code quality and tool usage. Open questions include whether the approach extends to truly novel task types without any prior trajectories, and whether the building-phase overhead can be further reduced or amortized in online settings.
