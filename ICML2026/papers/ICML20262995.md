## Problem

Existing multi-LLM serving systems face a fundamental trade-off: autoscaling approaches suffer from significant cold-start latency when creating instances on demand during request bursts, while GPU sharing approaches constrict KV cache capacity and degrade inference performance. The paper attributes this gap to the lack of awareness of future workload characteristics, despite recent evidence that long-term LLM workload patterns exhibit strong periodicity predictable with ~7% average relative error.

## Input / Output

The system consumes per-model historical workload traces partitioned into 5-minute windows (for the corrective seasonal predictor), model checkpoints with metadata (size, required GPU count, max batch size), and real-time GPU cluster state (free memory per GPU, active instance counts). It produces a ranked list of prewarming actions specifying which model replicas to load and onto which GPU groups, plus CUDA VMM page-table mappings that reconfigure virtual-to-physical memory on each GPU worker. The predictor outputs predicted average and peak concurrent request counts for the next window per model.

## Method

WarmServe introduces one-for-many GPU prewarming, which loads parameters from multiple models into a single GPU's memory so that any of them can be instantly instantiated upon a request burst. Three key techniques enable this: (1) a model placement algorithm that scores each prewarming replica using exponential-decay utility weighted by cold-start latency and burstiness, then greedily assigns replicas to GPU groups while enforcing a no-partial-overlap constraint to isolate high-priority models and minimize cross-model eviction interference; (2) a proactive prewarming strategy that loads new model weights into the unused KV cache space of dedicated GPUs approaching release, using a reservation formula R = max(C·Q/B, T + C/B) to guarantee ongoing requests are not starved; (3) a GPU memory switching mechanism built on the CUDA Virtual Memory Management API that pre-allocates full-size virtual regions per prewarm slot and remaps physical pages on demand, enabling a universal GPU to transition to a dedicated serving instance in negligible time. The system is built on vLLM with Ray Actor orchestration and uses a corrective seasonal predictor (7-day seasonal term plus exponentially-weighted 10-window corrective term) for workload forecasting.

## Results

WarmServe reduces P99 TTFT by up to 50.79× compared to SLLM-GPU and handles up to 2.5× more requests than MuxServe while maintaining low latency. In the 512-GPU large-scale simulation, WarmServe sustains P99 TTFT of 0.18–0.40 s across RPS 320–800, while SLLM-GPU degrades to 8.9–12 s (up to 30× higher) and MuxServe to 0.27–1300 s (up to 3400× higher). Prewarming alone achieves a 60×–88× TTFT reduction over cold-start loading, and the proactive prewarming strategy further reduces tail TTFT by up to 32.87× over reactive prewarming.

## Baselines & Comparisons

Against SLLM-GPU (ServerlessLLM extended with GPU caching), WarmServe achieves a 1.07×–10.06× reduction in P95 TTFT and a 1.53×–50.79× reduction in P99 TTFT in end-to-end experiments, with the gap widening under heavier loads as SLLM-GPU's on-demand instance creation becomes a bottleneck. Against MuxServe (GPU-sharing via CUDA MPS), WarmServe dominates under moderate-to-heavy loads: at RPS=15 with α=0.5, MuxServe's P95 and P99 TTFT are 34.5× and 134.0× higher respectively, and in the 512-GPU simulation MuxServe's P99 TTFT reaches 1300 s (3400× higher) at RPS=800. Under light loads, MuxServe's pre-created instances give it a marginal edge (0.85× lower P99 TTFT on AzureCode at RPS=10), but this advantage vanishes as load increases. A predictive-autoscaling baseline (same CSP predictor, no prewarming) matches WarmServe at light loads but degrades to 4.6×–11.6× higher P99 TTFT at RPS 640–800, confirming that prewarming—not just prediction—is essential for maintaining low tail latency under sustained heavy load.

## Relation to Prior Work

WarmServe builds on vLLM's PagedAttention-based inference engine and extends the multi-LLM serving landscape by synthesizing two previously separate paradigms: autoscaling (ServerlessLLM, BlitzScale, HydraServe) and GPU sharing (MuxServe, AlpaServe, Prism). The core departure is the 'one-for-many' prewarming concept, which borrows the proactive provisioning idea from serverless cold-start mitigation (Catalyzer, XFAAS, RainbowCake) but adapts it to the multi-GPU, large-checkpoint reality of LLMs. The workload prediction component uses a simple corrective seasonal predictor rather than the more sophisticated ARIMA or deep-learning forecasters common in time-series literature, arguing that 7.3% peak-load accuracy is sufficient for placement decisions.

## Why It Matters / Open Questions

The one-for-many prewarming mechanism offers a practical path to resolving the fundamental tension in multi-LLM serving between GPU utilization and inference latency, a problem that will grow as providers host dozens of model variants. Key open questions include whether the approach generalizes beyond Llama2-family models (evaluation is limited to 7B–70B Llama2 variants), how prediction accuracy degrades under genuinely novel or non-periodic workloads (e.g., viral events), and whether the CUDA VMM-based memory switching scales to models requiring 8+ GPUs per instance. The 512-GPU evaluation is simulation-only, leaving real-world cluster-level validation as future work.
